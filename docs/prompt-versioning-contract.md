# Контракт версионирования промптов (EVOL-016 / EVOL-018 / PVR-S1…S6)

Обязательный общепроектный стандарт с 30.10.2026. Не разовый фикс —
постоянное правило для любого модуля и любого способа хранения промптов.
Источники: `plans/current_task.md` §5 EVOL-016/EVOL-018 и EPIC-PROMPT-VERSIONING-UX-01
(§4–§6), замороженный контракт `plans/features/evol/arch/contracts.md`
(CONTRACT 1, §1.1–§1.10) и `plans/features/prompt-versioning-ux/arch/versioning-ux-contract.md`
(§2 baseline, §3 единая запись, §5 три слоя аудита).

## 1. Постоянное проектное правило

> **Любой промпт, отображаемый для редактирования в любом разделе админки, обязан
> регистрироваться в едином `prompt_registry`, сохраняться через единый
> `prompt_release_policy` с полным неизменяемым журналом, иметь одинаковую
> UI-панель версий, diff, активацию прошлых версий, owner baseline и
> восстановление. Новое поле промпта без этого функционала — архитектурная
> регрессия и блокер релиза.**

Практический разбор правила — четыре обязательных элемента любого промпта,
который владелец может править:

1. **Реестр.** Блок объявлен `declare_prompt(...)` (§2) и имеет `pg_key`, то есть
   адрес значения в общем слое (`bot_settings` / `chat_params`).
2. **Журнал.** Значение пишется только через `prompt_release_policy` (§3.1);
   ревизия, событие и значение — в одной транзакции, старый текст остаётся
   immutable-ревизией.
3. **Одинаковый UI версий.** История, просмотр полного текста, diff, активация
   прошлой версии, назначение/снятие/восстановление owner baseline — те же
   компоненты, что у всех остальных промптов, без «особой» истории раздела.
4. **Восстановление.** «Вернуть исходную из кода», «Восстановить базовую»,
   «Назначить», «Снять» — доступны там же, где редактор.

«Отображается для редактирования» = поле (textarea/строка/select значения
промпта) либо карточка модуля, правка которой меняет текст инструкции, отправляемый
модели. Промпт, показанный в истории **read-only**, под это правило не попадает:
у него нет активных кнопок включения версии, а причина честно написана в UI
(code-only или `catalog_pending`).

Правило относится **ко всем** текущим и будущим промптам. Запрет менять
сегодняшние тексты мемов (`meme_joke`, `meme_image`) — ограничение **только
пакета EPIC-PROMPT-VERSIONING-UX-01**, а не проектное правило: следующая
правка мемных промптов проходит обычный путь (реестр + журнал + метка/печать).

Запрещены обходные пути: необъявленные строковые промпты в коде, конфиги без
версии, локальные миграторы с цепочками строк, параллельные «канонические»
константы, специализированные HTTP-эндпоинты, пишущие текст промпта мимо
журнала. Исключений по строковому содержимому, имени промпта или признаку
«был ли изменён» не существует.

## 2. Точка объявления

Единственная точка объявления — `declare_prompt(...)` в
`services/prompt_registry.py` (каталожный ключ `pg_key` + `block_id` + метаданные;
для текста, живущего в коде, — `code_source` вида `module.CONSTANT`). Объявление
идемпотентно; повторная декларация того же `block_id` с другими данными
поднимает `PromptDeclarationError` — две точки объявления одного блока
приравнены к «скрытой инструкции».

Заводская ревизия задаётся парой:

- `FACTORY_REVISION_LABELS[block_id]` — человекочитаемая метка версии;
- `FACTORY_REVISION_SEALS[block_id] = (метка, sha12(текст))` — печать
  содержимого; идентичность ревизии — `fac:sha12(метки)`. Хеши генерируются
  из кода, руками не выдумываются; набор скреплён отпечатком
  `FACTORY_SET_SHA256_12`.

Фактическое состояние реестра на этом кандидате (сверено кодом, не «на глаз»):
114 блоков, 113 с заводским текстом и печатью, 104 метки, 40 блоков с `pg_key`
(38 ключей: `character.core` — документ из двух блоков-полей), 74 code-only блока
без `pg_key`.

Отдельная миграция «по имени ключа» запрещена: заводская ревизия новой
декларации входит в стандартный релизный путь (§3.2).

## 3. Журнал, запись и история

Журнал — таблицы PostgreSQL `prompt_revisions` / `prompt_activations`
(реализация — `services/prompt_release_policy.py`). Активные байты живут
по-прежнему в `bot_settings` / chat-override; журнал — не второй источник правды,
а указатель применённой ревизии.

### 3.1 Транзакция: где она действительно одна

«Ревизия + событие + значение одной транзакцией под advisory-локом»
(`pg_advisory_xact_lock('prompt_release_apply')`, `SET LOCAL lock_timeout='5s'`)
верно для **единого слоя записи**, а не для любого HTTP-запроса целиком:

| Точка | Путь записи | Одна транзакция |
|---|---|---|
| `POST /api/config` (global) | `_write_prompt_items` → `write_prompt_values(scope="global")` | да, для промптных ключей |
| `POST /api/config` (chat) | `write_prompt_values(scope="chat", chat_id=…)` первым этапом | да, включая запись набора overrides на коннекте транзакции |
| `POST /api/initiative/meme-settings` | `_write_prompt_items` (мемные ключи) | да |
| Speech: сохранение блока | `prompt_factory.write_speech_value` → `write_prompt_values` | да |
| Speech: сброс/откат/`apply_factory_reset`/`restore_backup` | те же обёртки | да |
| `activate_revision`, `assign_baseline`, `clear_baseline`, `restore_baseline`, `restore_shipped_factory`, `remove_prompt_override` | `prompt_release_policy` | да |
| Релизная поставка (старт) | `apply_release` | да, весь пакет блоков; сбой → rollback пакета |

Честная граница: в тех же запросах **непромптные** настройки пишутся после
промптных ключей отдельной операцией. Если журнал недоступен — промптная часть
отдаёт 503 и значение не пишется, но непромптные настройки того же запроса
могут быть записаны: это осознанная двухэтапность (§3.5 ТЗ), а не «одна
транзакция на весь HTTP-запрос». Падение на втором этапе отдаётся честным
частичным отчётом `503` + `{code: "partial_save", applied, rejected,
prompt_snapshots}`: в global-ветке — на любое исключение второго этапа, в
chat-ветке — на конфликт `ChatParamsConflict` (не-конфликтный сбой того же
этапа в chat-ветке пока уходит как 500 — остаток в §8 п.5). UI этот формат
не разбирает и показывает общую ошибку, хотя промпты уже сохранены.

### 3.2 Активация и релиз

| Событие | Поведение |
|---|---|
| Рестарт, метка та же, печать цела | no-op: ни строки, ни записи; ручная правка и откат остаются активными |
| Деплой, метка новее применённой, печать цела, scope **не** закреплён | заводской текст активируется автоматически поверх ручной правки; прежний текст остаётся ревизией; устаревший chat-override снимается с эффективного пути (его байты уже в ревизии) |
| Деплой при **owner baseline** (pin) | заводская ревизия пишется в историю, активный текст **не меняется**, chat-override **не снимается**; указатель применённой метки двигается (`factory_superseded_pinned`), поэтому следующий рестарт — истинный no-op |
| Текст сменился, метка та же (или метка без печати) | fail-closed: ERROR `integrity_label_unchanged`, БД не тронута, активный текст остаётся |
| Ручная правка в админке | новая immutable-ревизия `origin=manual`, она активна; `factory_revision_applied` не сбрасывается |
| Ручной откат / вперёд | `activate_revision`: включается **запрошенная** ревизия (не клон), история не удаляется; несовместимая (`schema_compat`) или `retired` — не включается, но доступна для просмотра и сравнения |
| Расхождение журнала и `bot_settings` | ERROR `activation_drift`, источник истины — PG; заводской текст заново не включается до новой метки |

### 3.3 Owner baseline — указатель, не копия

Baseline хранится **событием существующего журнала** `prompt_activations`
(`kind='baseline_assign'` с `revision_id` / `kind='baseline_clear'` с пустым
`revision_id`); новых таблиц и колонок нет, тело текста в событие не
копируется. Действующий baseline — последнее такое событие по
`(block_id, scope, chat_id)`.

- «**Назначить базовой**» (`assign_baseline`) — только указатель: активная
  ревизия и активный текст не двигаются, событие пишется с `outcome='recorded'`;
  повторное назначение идемпотентно.
- «**Снять назначение**» (`clear_baseline`) — пишется `baseline_clear`, текст не
  меняется; далее снова действует обычная релизная политика.
- «**Восстановить базовую**» (`restore_baseline`) — явная активация указанной
  ревизии тем же путём, что ручной откат (`kind='baseline_restore'`), с теми же
  гейтами `retired`/`schema_compat`/чужой scope.
- «**Вернуть исходную из кода**» (`restore_shipped_factory`) — требует `confirm`
  и целой печати; baseline этим действием не снимается.
- При первой миграции baseline **не назначается никому автоматически**:
  поведение действующих промптов не меняется.

### 3.4 История: страницы без потолка

Список «История версий» — keyset-пагинация по `(created_at, id)` без OFFSET:
`HISTORY_PAGE_DEFAULT = 50` — размер **страницы**, `HISTORY_PAGE_MAX = 200` —
предел запрошенной страницы (`clamp_page_size`), а не предел истории. Все
ревизии и все события достижимы курсором, включая 1000+ версий; `total_known`
честно равен `null` (полный `COUNT` страницей не считается). Тела текстов в
списках не отдаются: `body_available` + `chars`/`sha256_12`, полный текст — по
`revision_id` (`get_revision_source`) и в diff (`diff_revisions`).
Легаси-помощник `list_activations(limit=50)` остался в коде, но **не
используется** путём истории (вызовов в продукте нет) — прежний потолок 50
активаций больше ни на что не влияет.

### 3.5 Импорт legacy (провенанс)

До первой записи заводского текста каждый активный текст и каждый per-chat
override снимаются как ревизия `origin=legacy` с **временем импорта** и
причиной `legacy_import` (плюс захват действующих байтов до первой
версионированной записи, `reason='pre_versioning_import'`) — это не дата
редактирования, автор не выдумывается. Даже байты, равные заводским, снимаются
как `legacy`: UI не имеет права подписывать это «Изменена в админке». Пустой
ключ → `skipped_empty`, затем обычная активация. История не теряется при
миграции БД, обновлении VPS, переустановке из той же БД и смене провайдера LLM.
Старый журнал `character.prompt_history` переносится одноразово и
замораживается (`HISTORY_MAX_PER_BLOCK = 12` к новому журналу не применяется).

### 3.6 Честные пределы

- «Все когда-либо сохранённые версии» гарантируется для новых сохранений и для
  всех реально доступных legacy-записей. **Физически удалённые ранее записи
  замороженного `character.prompt_history` не восстанавливаются** и не выдаются
  за полную историю.
- Откат в Speech-разделе ищет версию по `sha256_12` сначала в замороженном
  журнале, затем в PG-журнале: результат тот же (полный журнал — источник
  истины), порядок поиска — совместимость с прежним API.
- Нет журнала/PG — история не «пустая», а недоступная: HTTP 503 с причиной;
  несохранённая правка остаётся в редакторе.

## 4. Scope

- **global** — слой `bot_settings`; **per-chat** — `chat_params.overrides`,
  побеждает глобал; настройки одного чата в другой не перетекают;
  **code** — блоки без `pg_key`: второй копии текста нет, активный текст —
  константа, при смене метки пишется ревизия `origin=factory` без второго
  хранилища.
- Новая заводская метка обновляет эффективный промпт, а не только глобальную
  строку: устаревший per-chat override блока снимается с эффективного пути
  (его текст заранее уходит в ревизию) — **кроме** scope с owner baseline (§3.2).
  Override, созданный **после** применения метки, рестарт не снимает;
  следующая новая метка снимает и его, сохранив в истории.
- Управляемые сообщения пользователю (`content.image_failure.*`,
  `content.image_request_clarify`) — не промпты, а текст-сообщение: в истории
  read-only, правятся как текст возможностей.

## 5. Аудит сборки: что сканируется и что проверяется

Аудит — три слоя, каждый обязан **уметь падать**:

1. **Реестр и UI-доступность** — `tests/test_prompt_field_audit.py`:
   каждый PG-блок реестра имеет ровно одну названную поверхность
   редактирования (общий каталог «Промпты», спец-карточка модуля, названный
   экран, слот-выбор), исключения перечислены с причиной и проверяются на
   загнивание; `pg_key ↔ block_id` согласованы (уникальность `block_id`,
   двусторонняя разрешимость `pg_key`, документ из нескольких блоков-полей,
   `ui='code_only'` ⟺ нет `pg_key`).
2. **Поведенческая матрица по каждой точке записи** —
   `tests/test_prompt_versioning_enforcement.py`: ревизия с ожидаемым
   origin/scope/chat, событие активации, значение в хранилище, повтор тех же
   байтов → `skipped_same` без дубля, недоступный журнал → 503 и значение не
   изменилось.
3. **Рантайм-страж обхода** — `PromptJournalBypass` в
   `prompt_release_policy.assert_prompt_write_allowed`: запись текста промпта
   через `ConfigCache.set/set_many` или `chat_params.set_chat_params` без
   журнального токена отвергается (значение не пишется, ревизий нет). Токен
   выдаёт только журнальный слой (`journal_write_scope`). Проверяется по всем
   37 текстовым ключам реестра (документ Core — мутацией поля внутри
   документа; слот-значение обложки объявлено нетекстовым), плюс негативные
   мутации в `tests/test_prompt_versioning_enforcement.py`.

Дополнительно `tests/test_evol018_prompt_audit.py` проверяет печати
(`seal_integrity()`), отпечаток набора и grep-аудит констант. `pytest.ini`
объявляет `testpaths = tests`, файлы собираются любым прогоном `pytest`;
отдельного CI-раннера в репозитории нет — роль CI выполняет обязательный
тестовый прогон перед релизом.

Grep-аудит `audit_unregistered_prompt_constants(root)` (эвристика контракта
§1.7 п.4):

- сканируются **только** `services/` и `handlers/`; `tests/`, `web/` и корень
  репозитория не сканируются;
- ищутся присваивания `NAME_PROMPT = ...` и `NAME_SYSTEM = """…"""` (блок
  длиннее 80 символов), включая имена с ведущим подчёркиванием и скобочную
  конкатенацию строк;
- `module.attr` обязан встречаться в `code_source` (включая `code_members`)
  какого-либо блока реестра либо входить в `PROMPT_AUDIT_ALLOWLIST` с
  **непустой причиной**.

Фактический прогон (замер на релизном кандидате SMART release train 01):
323 файла, 78 кандидатов — 76 закрыто `code_source`, 2 в allowlist,
0 вне реестра. Базовые 312 файлов / 76 кандидатов относились к линии до
SELF-DIAG-01 и SMART-EXECUTION-RELIABILITY-01; §G добавил один
зарегистрированный кандидат (`services.tool_loop.TOOL_FINALIZE_PROMPT`, блок
`direct.tool_finalize`), а параллельные срезы кандидата добавили
`services.prompt_readback.RESOURCE_KIND_PROMPT` (SELF-DIAG-01; это вид ресурса,
не инструкция модели — поэтому allowlist с причиной) и
`services.factcheck_orchestrator.FACTCHECK_SUBJECT_SYSTEM_PROMPT` (S13;
зарегистрирован блоком `factcheck.subject` и ключом каталога
`prompts.factcheck_subject_system_prompt`). Кандидаты считаются прогоном
`audit_unregistered_prompt_constants` с пустым реестром и пустым allowlist
(78), затем с реальным allowlist (76), затем на реальном реестре (0
нарушений). Эти числа запинены тестом `test_grep_audit_counts_are_stable`:
смена состава `services/`/`handlers/` или реестра роняет тест и заставляет
обновить цифры здесь, вместо того чтобы тихо сделать документ неверным. В
релизной линии 2.58.155 файлов на один меньше (293): новый
`services/anticliche_sources.py` входит в пакет AC-DATA и в тот релиз не
включён; на линии evol/impl с AC-DATA замер даёт 294. Число кандидатов и
результат аудита от этого не меняются (72/71/0, проверено).

Осознанно **не** сканируется (это не шаблоны): f-string сборка запросов,
тела переписки, tool results. Не аудируются байт-эталоны `PREV_*`/`LEGACY_*`
и `services/prompt_migrations.py` (эталонные константы, механизмом активации
больше не являются). Allowlist — только для имён, не являющихся инструкциями
модели: `media_send._QUALITY_PROMPT` (текст кнопки) и `FETCH_PROMPT_XPATH`
(Selenium-локатор web-fetch). «Отставший» настоящий шаблон регистрируется
через `declare_prompt`, а не прячется в allowlist.

Честная граница: сканер эвристический и работает по **модульным константам** —
динамически собранный текст, не проходящий через именованную константу, он по
определению не видит; поэтому правило «постоянная инструкция живёт в
именованной константе и объявлена в реестре» — часть настоящего контракта,
а не только теста. Слои 1–3 тоже не «доказывают всё»: они проверяют
перечисленные инварианты на текущем наборе блоков и маршрутов.

## 6. Последствия нарушения

- Новое редактируемое поле промпта без реестра, журнала, UI версий и baseline —
  **архитектурная регрессия и блокер релиза**: падают
  `tests/test_prompt_field_audit.py` (поле без поверхности/без `pg_key`) и
  `tests/test_evol018_prompt_audit.py` (необъявленная константа).
- Специализированный POST/скрипт, пишущий текст промпта мимо журнала, —
  `PromptJournalBypass` в рантайме (значение не пишется) и падение
  поведенческого теста слоя 3.
- Смена заводского текста без бампа метки (или бамп без печати) —
  **нарушение сборочного контракта**: падает CI-тест и, независимо от него,
  релизная политика при старте отказывается писать в БД (fail-closed).
- Запись в `PROMPT_AUDIT_ALLOWLIST` без причины — падение теста. Регистрация
  новых исключений через allowlist вместо `declare_prompt` запрещена.

## 8. Открытые пункты (честно, с владельцами)

1. **11 блоков (10 ключей) с `ui='catalog_pending'`** вне каталога параметров:
   `character.core` (2 блока-поля) и 9 управляемых сообщений
   `content.image_failure.*` + `content.image_request_clarify`. Владельца
   правки у них нет (`/api/config` их не знает, в истории они read-only), поэтому
   требование §1 на них пока не распространяется. Владелец: **PVR-S6-AUDIT**
   (список назван в аудите и защищён от загнивания); закрытие — добавление
   поверхности редактирования или явного read-only статуса в UI.
2. **`prompt_migrations.normalize_legacy_speech` / `rollback_legacy_speech`** —
   объявленный, но не вызываемый legacy-путь записи (только тесты). Если он
   когда-нибудь запустится, правки не попадут в журнал в общем порядке.
   Владелец: **PVR-S6-AUDIT** (при первом реальном запуске перевести на
   `write_prompt_values` либо удалить функцию).
3. **`scripts/migrate_env_to_pg.py --force`** пишет все ключи каталога напрямую
   `INSERT INTO bot_settings`; с `--force` это перезапись живого текста
   промпта без ревизии. Офлайн-скрипт, не API-путь. Владелец: **PVR-S6-AUDIT /
   DevOps**: исключить промптные ключи из script-пути или перевести скрипт на
   журнал. **Runbook (README, быстрый старт админки): `--force` по промптным
   ключам (`prompts.*`) не применять.**
4. **Три блока с `scope='code'` при наличии `pg_key`**
   (`initiative.meme.joke`, `initiative.meme.image`,
   `factcheck.critique.directive`) — метаданные реестра противоречат §4
   (code = без `pg_key`), из-за чего карточка истории называет scope «code», хотя
   значение живёт в `global`/`chat`. Данные и журнал целы (история читается по
   `block_id`), страдает честность подписи. Владелец: **PVR-S6-AUDIT** (список
   назван и защищён от загнивания в аудите); исправление — смена `scope` в
   объявлении, отдельным срезом с UI-проверкой.
5. **`partial_save` при сбое второго этапа** (`POST /api/config`, запись
   непромптных настроек после промптных). Формат **уже реализован** (PVR-S1,
   `7dd02046`) и отдаётся как `503` + `{code: "partial_save", applied,
   rejected, prompt_snapshots}`: в global-ветке — на любое исключение второго
   этапа (`routes.py:1463-1473`), в chat-ветке — на конфликт
   `ChatParamsConflict` (`:796-807`); тот же формат отдаёт путь снятия
   override (`:4921-4930`). Данные не теряются и «сохранено» ни для чего не
   выдумывается. Остаток — два края, а не открытый формат: (а) в chat-ветке
   не-конфликтный сбой второго этапа по-прежнему уходит как 500 без
   `partial_save`; (б) UI формат не разбирает и показывает общую ошибку, хотя
   промпты уже сохранены. Владелец: **PVR-S1-WRITE** (унифицировать
   chat-ветку до `partial_save` и научить UI читать `applied`/`rejected`).
6. **Страж не видит «неправильную форму» значения документа.** Для блоков-полей
   `character.core` страж сравнивает текст поля внутри документа: запись
   документа с изменённым полем отвергается (проверено тестом), а запись
   сырой строки вместо JSON-документа формально «не меняет ни одного поля»
   и проходит страж. Реальный код так не пишет (все пути идут через
   `write_prompt_values`), это защита от будущей ошибки, а не доступный
   владельцу обход. Владелец: **PVR-S6-AUDIT** (считать смену формы
   документа изменением текста и отвергать).
