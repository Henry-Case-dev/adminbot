# Research: импорт многолетней истории Telegram-чатов в память бота (GraphRAG)

- Дата: 04.09.2026
- Автор: docs-агент (исходные данные собраны research-агентами 04.09.2026)
- Статус: research-отчёт, рекомендация (реализация — отдельный эпик после одобрения пользователя)
- Цель пользователя: бот должен отвечать на вопрос **«что было N-числа 2024»** — нужны факты по дате с метаданными (даты, юзернеймы, id), а не только общий текст «о чём болтали».

---

## 1. TL;DR (вывод в двух абзацах)

Импортировать **всю** историю глубокой LLM-обработкой дорого по деньгам и времени (~$50–70 и 10–20 часов на 1.27 млн сообщений), но для цели «что было N-числа» это и не нужно: в данных уже есть точные даты (`date`, `date_unixtime`), поэтому дешёвый **этап 1 — загрузка сырого текста в `smart_messages` с полным FTS5-индексом** (минуты, $0) уже закроет запрос пользователя через существующий инструмент `query_chat_memory`, который возвращает строки вида `[Имя 2024-05-15]: текст`.

Этапы 2–3 (эмбеддинги и LLM-факт-экстракция) — опциональное улучшение семантики, их можно делать позже и только для нужных чатов/периодов. **Первый вопрос пользователю:** файлы покрывают ТРИ разных чата, а упоминался один (id 2661910336) — нужно уточнить, какие из трёх импортировать.

## 2. Исходные данные: папка `migrate_history/`

Три JSON-экспорта Telegram Desktop, суммарно **~602 МБ** (по данным исследователей; на диске файлы занимают ~574 МБ) и **~1.27 млн сообщений**. Важно: это ТРИ РАЗНЫХ чата.

| Файл | chat_id | Период | Сообщений (оценочно) | Размер на диске |
|---|---|---|---|---|
| `10.2024.json` | 2417005237 | 2024-10 → 2025-03 | ~335 000 | ~151 МБ |
| `10.08.2025.json` | 2661910336 | 2025-04 → 2025-08 | ~339 000 | ~168 МБ |
| `желтая до 10.2024.json` | 1691371902 | 2022-12 → 2024-10 | ~598 000 | ~255 МБ |
| **Итого** | **3 разных чата** | **2022-12 → 2025-08** | **~1 272 000** | **~574 МБ** |

### ⚠️ Несостыковка, требующая уточнения

Пользователь упоминал «чат id 2661910336», но экспорты покрывают три разных чата (2417005237, 2661910336, 1691371902). Возможные объяснения: переименования одной группы, разные группы/личные переписки, частично дублирующиеся экспорты. **Перед этапом 1 нужно подтвердить: какие чаты импортировать и под какими chat_id они лягут в память** (см. §9, шаг 1).

### Формат записей

Каждое сообщение — JSON-объект:

```json
{
  "id": 12345,
  "type": "message",
  "date": "2024-05-15T18:30:00",
  "date_unixtime": "1715789400",
  "from": "Имя Отправителя",
  "from_id": "user1234567",
  "text": "текст сообщения",
  "text_entities": []
}
```

Полезно для импорта: точная дата в двух форматах, имя и id автора (`from_id`), тип записи (служебные типа `service` можно отфильтровать). `text` бывает строкой или списком (если с форматированием) — при импорте склеивать.

## 3. Как устроена память бота сейчас (короткая справка)

Память живёт в SQLite (`local_database.db`, aiosqlite):

- **L1 — `smart_messages`** (`user_id`, `chat_id`, `text`, `timestamp`, `media_type`, `author_name`, `is_forward`, `forward_source`, `tg_message_id`) + **FTS5-индекс**. Инструмент `query_chat_memory` ищет по ней полнотекстово и возвращает фрагменты с датами — рендер `[Имя 2024-05-15]: текст` — и окно `time_range` (`last_day/week/month/all`).
- **L2/L3 — `graph_facts`** (`fact`, `origin`, `created_at`, `expires_at`, `target_user`, `weight`…) + FTS5 + векторная таблица `graph_facts_vec` (sqlite-vec). RAG-факты (`get_rag_context`) сейчас отдаются голым текстом; в этом раунде в рендер фактов добавлены даты `[%Y-%m-%d]`.
- Факт-экстракция из текущих диалогов — LLM-триплеты (`FACT_EXTRACT_PROMPT`) с TTL/весами/квотой.
- Эмбеддинги бот делает через свой `LLMClient`.

Значит, целевой путь для «что было N-числа 2024» уже существует: `query_chat_memory` умеет выдавать датированные строки по FTS5. Импорт истории = наполнить эту же таблицу старыми данными.

## 4. Способы импорта истории: сравнение

| Способ | Что делает | Стоимость | Время | Плюсы | Минусы |
|---|---|---|---|---|---|
| **(а) FTS5 сырого текста** | INSERT всех сообщений в `smart_messages` (+ FTS5), маппинг полей | **$0** | **минуты–час** (1.27M строк) | Сразу отвечает на «что было N-числа» через существующий `query_chat_memory`; даты точные (из `timestamp`); дёшево | Нет семантики («похожее по смыслу»), нет извлечённых фактов; ищет по словам |
| **(б) Чанки + эмбеддинги** | Бьём историю на чанки, эмбеддим, кладём в векторную таблицу | **~$0.3–5** за всё (текст-эмбеддер уровня OpenAI `text-embedding-3-small` ≈ $0.02/1M токенов; у бота эмбеддинг через `LLMClient`) | часы на прогон | Семантический поиск «о чём говорили примерно» | Даты в метаданных надо протаскивать отдельно; без (а) не даёт буквальных цитат |
| **(в) LLM-факт-экстракция** | Пачками по ~25 датированных сообщений LLM вытаскивает факты в `graph_facts` (тот же `FACT_EXTRACT_PROMPT`) | **~$0.05 на 1k сообщений** → 100k ≈ $5 (batch-режим −50% → ~$2.6); **1.27M целиком ≈ $50–70** (или только выжимка по ключевым чатам/периодам) | 100k сообщений ≈ **1–3 часа** (платный DeepSeek, 20–50 параллельных); 1.27M ≈ **10–20 часов** | Готовые «факты с датами» в формате памяти; лучшее качество для вопросов «что было» | Дороже всего; очередь на free-роутах непригодна (см. §5); риск спама/оффтопа чата попадает в факты |
| **(г) Гибрид (рекомендуется)** | Сначала (а) — сразу польза; затем опционально (б) и/или (в) для нужных чатов | Поэтапно | Поэтапно | Максимум ценности на каждом шаге, можно остановиться после этапа 1 | — |

## 5. Стоимость и время: конкретные цифры

### Деньги

- FTS5-импорт сырого текста: **$0**.
- Эмбеддинги всей истории: **~$0.3–5** (зависит от модели/длины; ориентир — OpenAI-класс `text-embedding-3-small` $0.02/1M токенов; бот эмбеддит через `LLMClient`).
- LLM-факт-экстракция (класс DeepSeek, цены $0.28 / $0.42 за 1M токенов):
  - ~**$0.05 на 1 000 сообщений**;
  - **100k сообщений ≈ $5** (в batch-режиме −50%, **~$2.6**);
  - **1.27M сообщений целиком ≈ $50–70**, либо дешевле, если извлекать факты только из «выжимки» (например, саммари по дням/неделям) или только из нужных чатов/периодов.

### Время

- Free-роуты OpenRouter (лимит ~50 запросов/день): на 100k сообщений нужно ~4 000 запросов → **~60+ дней**. Непригодны.
- Платный DeepSeek при 20–50 параллельных запросах: **100k сообщений ≈ 1–3 часа**; вся история (1.27M) ≈ **10–20 часов** однократного прогона.

Вывод: деньги не блокер (этап 1 вообще бесплатный), время блокер только для этапа 3 на всей истории.

## 6. Референсные архитектуры (GraphRAG и импорт чатов)

- **nano-graphrag** (github.com/gusye1234/nano-graphrag) — минималистичная локальная реализация GraphRAG-идей; показывает, что «граф фактов + поиск» можно собирать на простом стеке без тяжёлого пайплайна Microsoft. Ориентир для архитектуры факт-экстракции по пачкам с датами.
- **sqlite-graphrag** (github.com/daniloaguiarbr/sqlite-graphrag) — FTS5 + sqlite-vec + граф в одном SQLite-файле: **ровно текущий стек памяти бота**. Готовый пример, что векторный поиск и граф фактов уживаются в одной локальной БД.
- **Microsoft GraphRAG** (microsoft.github.io/graphrag) — эталонная схема «чанки → LLM → факты → граф → community summary». Важная цифра из их практики: **затраты на LLM-экстракцию ≈ 75% стоимости индексации**; вариант **LazyGraphRAG** снижает это до ~0.1%. Для бота это аргумент: не извлекать факты из всей истории, а индексировать выборочно/лениво (только то, что реально ищут).
- **Импорт Telegram-истории в RAG-память** (insiderllm.com/guides/session-as-rag-local-ai-memory, github.com/vjaykrsna/ragbot) — практические кейсы «чат-экспорт → локальная память»: подтверждают схему «сырой FTS + метаданные сообщений» как стартовый слой памяти.

Общий паттерн референсов: **сначала дешёвый поиск по сырому тексту с метаданными, потом (по мере надобности) LLM-обогащение**. Никто не рекомендует сразу эмбеддить+экстрагировать весь многолетний архив.

## 7. Дата-фильтрация: best practices

Цель — «что было N-числа 2024» — это запрос **с жёстким фильтром по дате**, поэтому:

1. **Хранить дату в метаданных отдельно от текста** (в `smart_messages` уже есть `timestamp` INTEGER) и делать `WHERE date BETWEEN ...` **до** векторного поиска (pre-filter), а не после KNN — иначе релевантные старые сообщения отсекаются ранжированием.
2. **Фолбэк без фильтра**: если по отфильтрованному диапазону пусто — повторить поиск без даты (возможно, пользователь ошибся числом/месяцем) и так и сказать «за эту дату ничего нет, ближайшее: …».
3. **Time-decay / свежесть**: старые факты и строки — ниже весом (в боте уже есть `expires_at`/`weight` в `graph_facts`; для импортированной истории TTL не нужен или очень длинный, но вес по умолчанию стоит делать ниже «свежих» фактов, чтобы бот не путал «что было» с «что сейчас»).
4. **Tiered retrieval**: FTS/BM25-кандидаты → сортировка/фильтр по дате → (опц.) LLM-слияние. Для «что было N-числа» релевантность почти целиком определяется датой, а не смыслом.
5. **Рендер дат в ответе** (уже сделано: `[%Y-%m-%d]` в фактах и `[Имя 2024-05-15]: текст` в L1) — критично, чтобы ответ можно было проверить глазами.

## 8. Риски

| Риск | Описание | Смягчение |
|---|---|---|
| **Объём/время** | 1.27M сообщений — большое, но НЕ проблема для SQLite; проблема — для LLM-этапов (10–20 часов, $50–70) | Импортировать FTS сразу; LLM-этапы — только по нужным чатам/периодам или в batch |
| **Качество данных** | В чатах много спама, оффтопа, служебных сообщений (`service`, пересылки ботов); факты из них зашумят память | Фильтры при импорте (тип `message`, непустой текст), минимальный вес импортированного, вычистка через `weight`/TTL |
| **Дубли с текущей памятью** | Период 2024-10→2025-08 может пересекаться с уже накопленной памятью бота | Импорт с дедупликацией (по `tg_message_id`/`chat_id`), проверка пересечений до импорта |
| **Приватность** | Вся история переписки окажется в локальной БД бота (пусть и личной) | Файлы уже вне git (папка `migrate_history/` — правило в .gitignore по spec memory-sync); БД с историей не должна попадать в бэкапы/логи; вопрос «чьи чаты» — уточнить у пользователя |
| **Rate-лимиты LLM** | Free-роуты (50 req/день) непригодны; даже платные роуты требуют троттлинга | Платный DeepSeek, 20–50 параллельных, backoff; batch-режим для цены |
| **Три разных чата** | Непонятно, какой чат кому принадлежит и что импортировать (см. §2) | Уточнить у пользователя до импорта |
| **`from_id` маппинг** | Telegram-id авторов в экспорте (`user…`/`channel…`) не равен `user_id` в памяти бота | Отдельная таблица/маппинг «from_id экспорта → user_id бота / просто author_name» |

## 9. Поэтапная рекомендация

1. **Уточнить у пользователя:** какие из трёх чатов импортировать (id 2661910336 и/или 2417005237 и/или 1691371902), под какими «именами» они будут видны, надо ли чистить служебные сообщения.
2. **Этап 1 (рекомендуется, дёшево и сразу полезно): FTS-импорт в `smart_messages`.**
   - Парсер JSON-экспортов (склейка `text`, отсев `type != message` и пустых).
   - Маппинг: `from_id → author_name/user_id`, `date → timestamp` (часы-минуты сохраняются), `chat_id → реальный (номер чата или псевдоним)`.
   - INSERT батчами + триггер FTS5 (как сейчас делает бот при сохранении сообщений).
   - Время: минуты–час. Стоимость: $0.
   - **Эффект:** `query_chat_memory` сразу отвечает на «что было N-числа 2024» строками `[Имя 2024-05-15]: …`.
3. **Этап 2 (опционально): эмбеддинги** для семантических запросов («когда обсуждали что-то похожее») — ~$5–10 суммарно, включая хранение векторов. Без LLM-экстракции.
4. **Этап 3 (опционально): LLM-факт-экстракция по датированным пачкам ~25 сообщений в `graph_facts`** — ~$50–70 за всю историю, либо дешевле (только ключевые чаты/периоды или саммари-выжимка). Даёт «факты с датами» как у текущей памяти, с весами и TTL.
5. Реализацию вести **отдельным эпиком** после одобрения пользователем (объёмы, какие чаты, бюджет этапов).
