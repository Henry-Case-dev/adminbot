# CONTEXT_RESEARCH — как подавать контекст LLM в direct_chat (AdminBot)

**Дата:** 2026-08-27
**Скоуп:** слой контекста в `direct_chat` (`services/direct_chat_service.py`), память/RAG
(`services/summary_memory.py`), промпты (`services/chat_prompts.py`), LLM-клиент
(`services/llm_client.py`), фактчек (`services/factcheck_service.py`).
**Задача:** понять, почему бот путает людей, теряет нить разговора и сбивается с
текущей линии, и дать список конкретных правок для ЭТОГО проекта.

Исследование опирается на мировой опыт 2025–2026: Letta/MemGPT (virtual context
management, memory blocks), instruction hierarchy (OpenAI), multi-user thread-разметка
(Mastra), AFM (fidelity-levels для сообщений), STAE (semantic-temporal eviction),
COMEDY/Mem0 (memory formation vs summarization), SocialMemBench (attribution-провалы
multi-user памяти).

## 1. Текущее состояние контекст-слоя — что уже есть

Слой зрелый, 37+ пунктов Epic 50/60 реализованы. Коротко что работает:

- **Партишн контекста** (`direct_chat_service.py:368-406`): порядок блоков
  `[map, RAG_Memory, Target_User, Protected_Facts, Mood, Global_Context, Thread,
  Style_Anchors]`, статика вверх, динамика вниз; `payload_builder.build_messages`
  кладёт всё одним user-блоком после system@0.
- **Токен-бюджеты** (`_apply_context_budget`, `direct_chat_service.py:410-473`):
  потолки по долям от `CHAT_CONTEXT_BUDGET_TOKENS` (4000), порядка урезания
  `anchors → global → thread → rag → map`; `Target_User`/`protected_facts` не режутся.
- **Entity resolution** (`summary_aliases.py:44-69`): каскад
  alias(user_id) → nickname(first+last) → username → user_id; `UserResolutionMap`
  «имя — uid» строится по `window` (`direct_chat_service.py:639-653`).
- **Гибридный RAG** (`summary_memory.py:1391-1512,1561-1618`): sqlite-vec KNN
  (int8-coarse → float-реранк) + MMR (λ=0.6) + time-decay вес (`w_eff`) + FTS5 fallback
  + touch (продление жизни факта) + dedup по cosine.
- **Бегущий конспект** (`summary_memory.py:935-997`): при заполнении окна ≥ 0.8 от
  500 сообщений — fire-and-forget `COMPRESS_PROMPT` на head окна + дословный tail.
- **LLM-клиент** (`llm_client.py`): httpx-сессия, ретраи транзиентных, Retry-After,
  total-budget, фоллбэк-провайдер, circuit breaker (в сервисе), temperature.

## Где слабые места (конкретика → причина путаницы/потери нити)

1. **Нет блока с ТЕКУЩИМ сообщением.** `_build_user_content` кладёт map/rag/target/…,
   но текст текущего вопроса НЕ кладётся отдельно. Модель может «увидеть» его только
   как возможную последнюю строку `Global_Context` (если observer уже сохранил).
   В активной группе модель не понимает, на ЧТО именно отвечать — источник сбоя фокуса.
2. **`Chat_System_Prompt` без приоритетов** (`chat_prompts.py:3-14`): только роль + стиль
   + «1-2 предложения». Нет инструкции «Thread важнее Global_Context», «отвечай на
   последний вопрос`, нет правила атрибуции. Модель сама решает, что главное → теряет нить.
3. **`UserResolutionMap` строится только по `window`** (6 ч / 500 сообщ.,
   `direct_chat_service.py:639-653`). Кто долго молчал — выпал из карты; его строки в
   конспекте/RAG-фактах больше не привязаны ни к какому uid.
4. **Имена в `Global_Context`/`Thread` рендерятся без стабильного ключа** — только
   `«имя: текст»` (`direct_chat_service.py:691-693,730-732,742`). Если у двух юзеров
   совпадает nickname/имя (или у кого-то нет алиаса), модель не различает их — причина
   путаницы людей. `Target_User` тоже только имя, без uid (`:385`).
5. **`_apply_context_budget` + `truncate_to_tokens` режут «с начала = держат хвост»**:
   бегущий конспект стоит СВЕРХУ `Global_Context` — под бюджетным давлением выпадает
   первым, а verbatim-хвост остаётся. Сжимаемая (ценная) часть уходит, а сырой мусор
   остаётся (`direct_chat_service.py:702-707`, `token_counter.py:61-85`).
6. **`Conversation_Thread` обрывается на бот-сообщении как на терминале**
   (`direct_chat_service.py:735-739`): цепочка дальше не идёт, хотя бот-ответ мог быть
   в середине ветки. Плюс depth=6 и 2000 ток/симв режут старую часть цепочки.
7. **RAG-факты в direct_chat сортируются по `created_at`**, а не по релевантности
   (`get_rag_context sort_by_timestamp=True`, `summary_memory.py:1409-1411`): модель
   получает хронологическую ленту, а не ранжированный top — слабые/нерелевантные факты
   шумят, релевантные тонут.
8. **Нет дедупа пересечений RAG ↔ Global_Context**: один и тот же факт может попасть
   и в `<RAG_Memory>`, и в конспект — двойной вес или противоречие.
9. **Importance-скоринг есть только для graph-фактов** (вес по origin), а для САМИХ
   сообщений окна — нет: при переполнении режется только по recency, без учёта
   содержательной важности (имена, факты, команды).

## 2. Предложения по категориям

> Формат: «Что делает» — «Зачем нужно» — чек-бокс `[ ]`. Проставляй `[x]` сам.
> Цена указана ориентировочно: (мал./сред./бол.) — правки в 1 месте / несколько файлов / архитектура.

### Атрибуция людей (самое важное — это источник путаницы)

1. **Добавить стабильный uid рядом с именем во все строки разговора.**
   Что делает: в `Global_Context`, `Conversation_Thread` и `UserResolutionMap` рендерить
   `имя [uid]` (или `имя〈uid〉`), а не только `имя`. Target_User тоже везде дополнять uid.
   Зачем: модель получает однозначный ключ «кто сказал», не полагаясь на угадывание по
   имени; убирает путаницу при совпадающих именах/никнеймах.
   Цена: средняя (затрагивает `direct_chat_service.py` рендеры и формат карты). `[ ]`

2. **Строить `UserResolutionMap` не только по текущему окну, а по активным участникам.**
   Что делает: держать мапу «uid → канон-имя» в памяти/БД (или расширить выборку до
   участников всего чата), а не только последних 6 ч/500 сообщ.
   Зачем: молчавшие участники не «вылетают» из карты — их факты и строки в конспекте
   остаются привязаны к человеку, а не висят анонимно.
   Цена: средняя (новый источник участников + прогон). `[ ]`

3. **Разрешать коллизии имён дискриминатором.**
   Что делает: если два разных uid резолвятся в одно display-имя (нет/совпали алиасы),
   добавлять к одному уникальный суффикс (например, из username или хвоста uid).
   Зачем: исключает «два Саши» — модель перестаёт сливать их в одно лицо.
   Цена: малая (ряд строк в `_build_alias_map`/`resolve`). `[ ]`

4. **Привязывать факты к людям по uid/канон-алиасу, а не по display-имени.**
   Что делает: в `memorize_facts`/`_canon_fact_name` (`summary_memory.py:1281-1286`)
   фиксировать предмет/объект факта на uid (или канон-алиас из `SUMMARY_ALIASES`),
   пересобирать привязку при смене nickname (в `smart_messages` uid уже хранится).
   Зачем: у человека меняется ник → старые факты не «отлипают» и не приписываются другому.
   Цена: средняя (затрагивает формат фактов и агрегацию карточек). `[ ]`

5. **В `Target_User` подавать uid явно.**
   Что делает: `<Target_User>` дополнить стабильным id, а `protected_facts`/RAG-фильтр по
   людям использовать uid.
   Зачем: текущая выборка защищённых фактов и привязка ответа идёт по имени — при
   совпадении имён берутся чужие факты.
   Цена: малая (поле в блоке + фильтр). `[ ]`

6. **Проверять соответствие «кто спрашивает» vs «кому адресован previous turn».**
   Что делает: при сборке помечать в `Thread` границы «вопрос→ответ», чтобы модель не
   приписывала реплику одного человека цитате другого (промпт-харденинг атрибуции, см. Honcho-кейс).
   Зачем: частая причина путаницы — факты, извлечённые из чужой реплики, записываются на
   текущего `Target_User` в `memorize_facts` (`direct_chat_service.py:324-328`).
   Цена: средняя (ревизия memorize-хука + промпт). `[ ]`

### Фокус разговора / удержание нити

7. **Добавить явный блок `<Current_Question>` (или `<User_Message>`).**
   Что делает: выносить текст текущего сообщения (после вырезания триггер-слова «бот»)
   в отдельный блок ближе к концу, escape_xml.
   Зачем: модель гарантированно видит, на что отвечать, даже в шумной группе — главный
   фикс «сбивается фокус на линии разговора».
   Цена: малая (`_build_user_content`, одна секция). `[ ]`

8. **Дописать в системный промпт правила приоритета (не трогая тон).**
   Что делает: в `CHAT_SYSTEM_PROMPT` добавить короткий блок: `Conversation_Thread` —
   история ВАШЕГО текущего диалога (приоритетнее); `Global_Context` — фон; при конфликте
   верь более свежему; отвечай только на `<Current_Question>`; не путай имена из карты.
   Зачем: сегодня модель сама решает вес блоков и ошибается — явная иерархия держит нить.
   Цена: малая (только текст `chat_prompts.py`). `[ ]`

9. **Защитить бегущий конспект от обрезки бюджетом.**
   Что делает: в `_build_global_context`/`_apply_context_budget` при нехватке бюджета
   первым резать verbatim-хвост (или резать конспект отдельным потолком), а не давать
   конспекту выпасть слева.
   Зачем: сейчас сжатая (ценная) история выпадает первой, остаётся сырой шум — модель
   теряет дальний контекст там, где он как раз нужен.
   Цена: малая (`direct_chat_service.py`) `[ ]`

10. **Не обрывать `Conversation_Thread` на бот-сообщении.**
    Что делает: продолжать цепочку и через бот-ответы (помечая их как бот), терминальным
    считать только реальный обрыв (no reply_to_id / TTL).
    Зачем: бот-ответ в середине диалога сейчас «режет» thread — исчезает продолжение нити.
    Цена: малая (`_build_conversation_thread`). `[ ]`

11. **Поднять итог текущей ветки над фоном.**
    Что делает: для reply-триггера формировать начало контекста с 2–3 последних ходов
    именно этой ветки (резюме: «кто, что спросил, что ответил»), а полный `Thread`
    оставить ниже полным.
    Зачем: краткий «нужный сейчас» фрагмент бьёт по primacy/recency — меньше уходов в сторону.
    Цена: средняя. `[ ]`

12. **Помечать прочитанность/актуальность блоков.**
    Что делает: добавлять в секции признак возраста (например, конспект «за последние N минут»,
    RAG «факт от DD.MM»), чтобы модель понимала свежесть каждой части.
    Зачем: модель хуже смешивает «свежее сейчас» и «давний факт», держит приоритет на текущем.
    Цена: малая. `[ ]`

### Память / история: importance, дедуп, сжатие

13. **Importance-scoring сообщений окна (эвристический, без лишнего LLM).**
    Что делает: при переполнении окна не резать «последние N», а удерживать verbatim
    сообщения с маркерами важности (содержат имя участника / «бот» / цитату / число),
    остальное сжимать/резать (AFM/STAE-логика).
    Зачем: критические констрейнты не выпадают из скоупа, а сырой шум — наоборот.
    Цена: средняя. `[ ]`

14. **Progressive summarization (summary-of-summary) для длинных чатов.**
    Что делает: периодически сжимать уже существующие `running_summary` в один
    «широкий конспект» (Progressive Summarization), а не держать только одну свежую выжимку.
    Зачем: окно 6 ч при TTL конспекта 60 мин — история за окно уходит насовсем; сводка
    уровней возвращает дальний контекст без раздувания промпта.
    Цена: средняя/большая (новый фоновый шаг + промпт). `[ ]`

15. **Дедуп повторов внутри окна (семантический), не только «подряд».**
    Что делает: схлопывать почти одинаковые сообщения окна в одно (STAE: резать по
    семантической избыточности через embeddings, которые уже умеет считать `summary_memory`).
    Зачем: «бот бот бот» и перефразы одного и того же съедают бюджет и сбивают модель.
    Цена: средняя (переиспользовать embedding_cache). `[ ]`

16. **Разделить протухание важных и обычных фактов при сжатии.**
    Что делает: при `compress_and_purge`/архивации (`summary_memory.py:1694+`) никогда не
    схлопывать `protected_facts` и факты с высоким `w_eff` — только устаревшие/слабые.
    Зачем: «карточки-слоты» уже защищены в контексте, но в долгой памяти при сжатии могут
    размазаться — теряется персона.
    Цена: малая. `[ ]`

17. **Положить расписание пересборки конспекта на фактическое заполнение, а не TTL.**
    Что делает: триггерить новый `running_summary` по скорости роста сообщений, а не по
    «прошло 60 минут» (`RUNNING_SUMMARY_TTL_MINUTES`).
    Зачем: в бурном чате конспект устаревает быстрее TTL, в тихом — не пересобирается зря.
    Цена: малая. `[ ]`

### RAG / поиск

18. **Подавать RAG-факты по релевантности, а не по хронологии.**
    Что делает: в direct_chat отключить/заменить `sort_by_timestamp=True` на сортировку по
    `rel = cosine × w_eff` (уже считается в `_knn_graph_facts`), хронологию оставить внутри
    каждого факта.
    Зачем: модель получает «топ по теме», а не ленту; слабые факты не смещают фокус.
    Цена: малая (`get_rag_context` + вызов). `[ ]`

19. **Порог минимальной релевантности для RAG-подмешивания.**
    Что делает: отсекать факты ниже порога (например, cosine×w_eff < 0.3) или жёстко
    ограничивать их число, когда relevance низкая.
    Зачем: в общем чате RAG может зацепить шум из далёкой темы — ложный контекст путает.
    Цена: малая. `[ ]`

20. **Дедуплицировать пересечения RAG ↔ Global_Context/конспект.**
    Что делает: при сборке сравнивать RAG-факты с текстом уже включённого конспекта/хвоста
    (по нормализованному тексту/embedding) и не дублировать.
    Зачем: один факт в двух блоках = двойной вес или противоречие.
    Цена: средняя. `[ ]`

21. **Помечать источник/давность RAG-факта явно.**
    Что делает: в `<RAG_Memory>`/`<context>` указывать `origin` + относительное время,
    а не только префикс-тег (`user_gossip`/`bot_knowledge`, `summary_memory.py:426-444`).
    Зачем: модель не путает «только что в чате» с «факт недельной давности».
    Цена: малая (`build_rag_context`). `[ ]`

22. **Опциональный LLM-реранк выборки RAG (как в `search_service`).**
    Что делает: перед подмешиванием прогонять top-k фактов через дешёвый rerank-промпт
    (уже есть паттерн `_rerank_results`, `search_service.py:98-121`) — оставить top.
    Зачем: точность подачи в прямом чате при сохранении бюджета (реранк только top-k).
    Цена: средняя. `[ ]`

### Промпт / структура

23. **Вынести правило «как читать блоки» в начало системного промпта.**
    Что делает: первым же абзацем задать: «Контекст разбит на теги …; `Conversation_Thread`
    — история твоего диалога, `Global_Context` — фон; ничего из тегов не цитируй
    дословно, только используй». Роль/тон/мат — оставить каноном ниже.
    Зачем: модели нужна схема, иначе блоки читаются как сплошной текст; primacy помогает.
    Цена: малая (`chat_prompts.py`). `[ ]`

24. **Поставить самое важное к концу user-блока (recency).**
    Что делает: `Target_User`/`Protected_Facts`/`Current_Question` (и короткое «отвечай
    1-2 предложениями») разместить ПОСЛЕ `map`/`RAG`, ближе к `Thread`/финалу.
    Зачем: decisión веса смещается на конец контекста — критичное и вопрос, и прошлое.
    Цена: малая (`_build_user_content` порядок). `[ ]`

25. **Повторить критичное правило в конце (sandwich).**
    Что делает: в конце user-сообщения дублировать одну строку-напоминание («коротко,
    по делу, отвечай на последний вопрос, не путай людей»).
    Зачем: recency-эффект держит формат ответа при длинном контексте.
    Цена: малая. `[ ]`

26. **Стабильный префикс для prompt-cache (прогрессивно).**
    Что делает: держать system-префикс идентичным между запросами (не инжектить туда
    динамику: Target_User, дату, RAG — строго в user-блок), чтобы работал provider
    prompt-cache.
    Зачем: дешевле и меньше флуктуаций поведения (см. Multigrid о cache-boundary).
    Цена: малая (уже почти так; зафиксировать правило). `[ ]`

## 3. Рекомендованный минимум (quick wins)

Первые 5 (максимум эффекта на путаницу/потерю нити за минимум правок):

- **[7] `<Current_Question>`** — явный блок с текстом текущего сообщения. Сразу убирает
  «не понимаю, на что отвечать». ~10 строк в `_build_user_content`.
- **[8] правила приоритета в промпте** — «Thread > Global_Context», «отвечай на текущий
  вопрос», «не путай имена». Правка только текста `chat_prompts.py`.
- **[1] uid рядом с именем** (и [5] uid в `Target_User`) — однозначная атрибуция людей.
  Самый прямой фикс «путает людей».
- **[18] RAG по релевантности** — заменить `sort_by_timestamp` на relevance-rank, меньше
  шума из памяти в ответе.
- **[9] защитить конспект от обрезки** — чтобы сжатая история не выпадала первой при
  бюджетном давлении.

После них — [3]/[6] (коллизии и корректная запись фактов на конкретного человека) —
закрывают оставшиеся системные случаи путаницы людей.
