# Research: масштабирование на десятки чатов (multi-chat scaling)

- Дата: 07.09.2026
- Автор: research-агент (опрос внешних источников 07.09.2026; контекст кода сверен с `plans/ARCHITECTURE.md` §1–21 и grep'ом чтений памяти)
- Статус: research-отчёт; рекомендация для владельца. Приложение к `plans/docs/sqlite-to-pg-research.md` (Epic 86) и `plans/ARCHITECTURE.md`.
- Вопрос: бот сегодня фактически живёт в одном основном чате (код уже per-chat). Что менять, если бота добавляют в НОВЫЕ чаты десятками: архитектура, память (SQLite/PG), фоновые воркеры (сон/ностальгия/лор на N чатов = токены), TMA-админка, мульти-тенантность, изоляция лора/отношений, модерация.

---

## 1. TL;DR (вывод)

**Главный вывод: «десятки чатов» — это НЕ инфраструктурная проблема (процесс/БД потянут), а три другие:** (1) бюджет и поведение фоновых воркеров на N чатов (сон/ностальгия/лор/саммари = токены, которых нет бюджета), (2) рост SQLite-памяти и диска 24 ГБ (вектора 3072 занимают ~15,6 КБ/факт; импорт большой истории в каждый новый чат — главный пожиратель, а не live-поток), (3) продуктовый «гейт онбординга» и TMA: какие фичи включены в каком чату, кто админ чата, как выглядят настройки «профиля чата» без превращения глобального конфига в кашу.

**Честная оценка готовности:** изоляция данных по `chat_id` уже пронизывает всю память (проверено: чтения `smart_messages_fts`/`graph_facts_fts`/`protected_facts`/`nodes`/`users_meta`/`dream_state`/`nostalgia_log` — почти везде `WHERE chat_id = ?`), PG-профили чатов (`chat_profiles` + `chat_admins` + `chat_links` + lifecycle входа/выхода бота) уже multi-chat «с первого дня», воркеры уже итерируют по активным чатам с кучей per-chat лимитов. Это редкая позиция: **база для варианта A (один бот + изоляция + бюджеты воркеров) на 80% уже написана.** Не хватает: бюджета токенов фона (глобального суточного счётчика), heаrtbeat-гейта «тишина vs спам» на уровне процесса, per-chat параметров конфига (сейчас параметры глобальные), архивного режима памяти, авто-регистрации админов чата и честного «профиля новых чатов» с тумблерами фич.

**Рекомендация:** вариант **A** (шагами, неделя-две суммарно), Epic 86/PG — не сейчас, но с триггерами (см. §5). Вариант C (мульти-процесс) — только после реальных упоров: RAM/CPU одного инстанса, тысячи чатов, несколько ботов, жёсткие TPM провайдера. Polling одного бота не масштабируется на 2 процесса в принципе (`TerminatedByOtherGetUpdates`), а фоновые воркеры — да, и это дешевле.

## 2. Что уже готово к масштабу (честно, со ссылками на код)

Не «мы потом перепишем», а то, что реально работает per-chat сегодня:

| Готово | Где | Детали |
|---|---|---|
| **chat_id-изоляция в памяти (SQLite)** | `services/database.py` | Почти каждое чтение памяти фильтрует `chat_id`: `smart_messages_fts … AND m.chat_id = ?` (строки 1425/1440), `graph_facts_fts … AND f.chat_id = ?` (2114/2141/2689/2746), `protected_facts … WHERE chat_id = ?` (2623-2639, частичный UNIQUE `(chat_id, fact) WHERE user_name IS NULL`), `nodes/edges`, `users_meta` PK `(chat_id, user_id)`, `chat_summary_levels`, `dream_state` PK chat_id, `nostalgia_log`, watermark-курсоры |
| **PG-профиль чата — настоящий мульти-тенант** | §19 ARCHITECTURE, `services/chat_lore_store.py` | `chat_profiles` (PK chat_id): manual/auto лор, авто-период, relations JSONB, тумблеры; optimistic-lock по `updated_at` (409); история изменений `chat_lore_history`; `chat_links` — переезд чатов; `chat_admins` — per-chat права |
| **Lifecycle входа/выхода бота** | §19, `handlers/chat_lifecycle.py` | `my_chat_member` (бот добавлен/удалён) → `ensure_profile` + `is_active`; `migrate_to_chat_id` → remap. Новый чат получает профиль автоматически при добавлении |
| **Per-chat параллельность** | §21, `services/smartmodule_concurrency.py` | `ChatConcurrencyPool`: semaphore N=3 на ЧАТ (а не на процесс), busy-ответы вместо блокировки чатов друг другом |
| **Воркеры уже «по всем чатам»** | `services/dream_worker.py`, `nostalgia_worker.py`, `lore_worker.py` | LoreWorker: `list_active_chats()` + `auto_period_hours` + тихие окна + advisory-локи; DreamWorker: watermark `id > last_processed_fact_id` per чат, `dream_max_chats_per_run=10`, окно 4–6, пропуск «шумных» чатов; NostalgiaWorker: только активные PG-профили `chat_id < 0`, тишина ≥45 мин, quiet hours 23–8, cooldown 12 ч, `max_per_day=3`, пауза «без ответа» 24 ч |
| **Per-chat троттлинг/антиспам direct** | §4 ARCHITECTURE | per-chat `asyncio.Lock` → пул, кулдауны фактчека/поиска/видео на (chat, user) |
| **RBAC: глобальный админ + per-chat админы** | §19/§21, `web/api/chat_lore.py` | `can_access_chat`: админ чата A физически не получает чат B; глобальный admin (роль admin/wildcard) видит все; TMA «Лор чатов» уже имеет селектор чатов с поиском, превью, историей, админами |
| **Изоляция лора при инжекте** | §19 (D1/Q1), `direct_chat_service.py:673` | PG-лор активен → SQLite chat-level канал исключается (`include_chat_level=False`), дублей нет |
| **Fail-open везде** | весь PG-слой | PG down → старое поведение; бот жив; кэш-инвалидация NOTIFY + TTL 120 с |

Вывод: «одна схема на всех» + `tenant_id` = `chat_id` в ведущей позиции — уже фактически реализованный SaaS-паттерн row-level изоляции (см. §4 источники по мульти-тенантности). Прикручивать RLS/схемы-на-чат НЕ нужно: чат-граница в Telegram — это целое число, и она уже во всех таблицах.

## 3. Узкие места при росте (таблица рисков)

Сценарий: бот добавлен в 10–50 супергрупп, «живых» одновременно 5–20. Оценки объёма — от текущей БД (≈3,2 ГБ на 1 чат с импортированной историей; 2,2M строк FTS ≈ 0,7 ГБ, ~166k фактов-векторов ≈ 2,5 ГБ; свободно на диске ~14 ГБ, RAM ~1 ГБ).

| # | Узкое место | Что происходит на 10–50 чатах | Тяжесть | Что уже смягчает |
|---|---|---|---|---|
| 1 | **SQLite: объём и диск 24 ГБ** | Live-поток не страшен: ~300–400 Б/строка FTS → ~50 МБ/год/чат сырья; факты-вектора 3072 (float+int8 ≈ 15,6 КБ/факт): при density 0,15 ≈ 4–5k фактов/год → ~70–80 МБ/год/чат. 20 живых чатов ≈ +1,5–2 ГБ/год — хватит на годы. **Взрывает диск только импорт большой истории в каждый новый чат (+0,6–3 ГБ за раз/чат)** и бессрочный режим (`memory.infinite_retention`). Плюс: бэкапы БД рядом на том же диске | Высокая (медленная) | индексы по (chat_id, timestamp); окно 30 дней; ретенция уже управляемая |
| 2 | **Воркеры: токены фона без бюджета** | Сегодня лимиты per-chat есть, но нет суточного ГЛОБАЛЬНОГО счётчика/стопа. Оценка «на пальцах» на активный чат: ностальгия ~2–4 LLM-вызова/день (~3–5k токенов), дистилляция сна ~1–2×5k в окне 4–6, лор-merge ~1 раз в 1–3 дня ×10–15k, крон-саммари 0/6/12/18. Итого ≈ 10–30k токенов/день/чат → 30 чатов ≈ 0,3–1M токенов/день **фоном**. Денежно при DeepSeek-классе это терпимо; проблемы — всплески TPM провайдера, «все тики разом» после простоя, деградация качества (спам в 30 чатах одновременно) | Высокая (быстрая) | per-chat quiet hours/cooldown/max_per_day; dream `max_chats_per_run`; тик-интервалы 30–60 мин |
| 3 | **Интерактив на N чатов** | 50 чатов × ~100 обращений/день × ~3–8k токенов контекста ≈ 15–40M токенов/день — вот это уже деньги и TPM-потолок. Реально «живых» чатов обычно 5–15, но потолок надо считать | Средняя (экономическая) | per-chat контекст-бюджет уже жёсткий; редко-активные чаты мало едят |
| 4 | **Один процесс, один polling** | aiogram polling одного бота нельзя запустить в 2 процессах (`TerminatedByOtherGetUpdates`) — вертикаль ограничена инстансом. На десятки чатов это не упор (событийный loop тянет тысячи сообщений/с), на тысячи — упор | Низкая (сейчас) | — |
| 5 | **RAM 1 ГБ** | SQLite-страницы кэшируются ОС; 3,2 ГБ файла читаются кусками. Опасно: VACUUM/большой импорт/одновременные эмбеддинги. Фон-воркеры + polling в одном процессе делят loop | Средняя | один процесс, WAL, батчи |
| 6 | **Изоляция: «спящие» чтения без chat_id** | Греповый аудит показал: почти все чтения с `chat_id`. Риск — редкие ветки (self-heal, backfill, пер-чат дедуп при импорте истории, легаси-канал `ensure_chat_lore`), которые всплывут на 10-м чату. Нужен тест-инвариант «чат A не видит B» на все точки чтения | Средняя | уже есть per-chat фильтры; нужен аудит-тест |
| 7 | **Legacy «один главный чат»** | `services/chat_lore.py`: константа `CHAT_LORE_2661910336` + startup-инжект `ensure_chat_lore` (SQLite protected-facts чат-уровня). В новых чатах не мешает (факты с chat_id старого чата), но путает картину и тесты дедупа | Низкая | сид в PG `chat_profiles`; SQLite-канал легаси |
| 8 | **TMA: параметры глобальные, чат-специфичных нет** | `bot_settings` — один глобальный набор (372 параметра). Чтобы админ чата B поменял тон/персону «своего» бота, нужен слой per-chat override поверх глобальных дефолтов (наследование global → per-chat), иначе каждый чат либо одинаковый, либо правки руками «назад» в PG | Высокая (продуктовая) | лор/relations уже per-chat — паттерн есть |
| 9 | **TMA: вкладка «Чаты»** | Селектор чатов есть только в «Лоре чатов» (список+превью+админы — отличная база). Нужна общая вкладка: поиск по чатам, статус (активен/тих/удалён), per-chat тумблеры фич, кто админ, расходы/счётчики | Средняя | RBAC/`can_access_chat` готов |
| 10 | **Модерация и онбординг в новый чат** | Бот с privacy ON не видит сообщения без админки; с OFF — видит всё и (после добавления) начнёт отвечать на direct-триггеры везде = токены и риск «не в том чату». Нет: проверки прав при входе, дефолтного «профиля нового чата» (что включено), авто-добавления TG-админов в `chat_admins`, антиспам-политик для чужих чатов | Высокая (продуктовая) | троттлинг/кулдауны per-chat; RBAC |
| 11 | **Telegram-лимиты отправки** | ~1 msg/s на чат, ~20 msg/мин в группу, ~30 msg/s глобально (без Paid Broadcasts). На десятки чатов с ностальгией и реакциями — не упор, но всплеск фона может пересечься с интерактивом в одном чату | Низкая | RetryAfter уже обрабатывается в llm_client; нужен общий limiter отправки при всплесках |
| 12 | **Бэкапы/восстановление** | БД 3,2 ГБ + WAL; архивная копия на том же диске. На N чатов бэкап и время восстановления растут линейно | Средняя | VACUUM INTO / файл-копия уже есть; мониторинг диска — добавить алерт |

## 4. Варианты архитектуры

### [ ] Вариант A — один бот, per-chat изоляция данных + бюджеты воркеров (минимальные изменения)

**Суть:** остаёмся на одном процессе/polling/SQLite+PG. Делаем только то, что реально блокирует десятки чатов: бюджеты фона, профиль нового чата, per-chat параметры (узкий whitelist), архивный режим, аудит изоляции, TMA-вкладку «Чаты».

**Что менять (файлы/таблицы/эндпоинты):**

1. **Бюджет фоновых воркеров** (главный пункт).
   - Новый `services/worker_budget.py`: суточный лимит LLM-вызовов и токенов фона (счётчик в PG `bot_settings`, ключ вида `worker_budget.<date>`), общий `asyncio.Semaphore` для фоновых вызовов (приоритет: интерактив всегда вперёд), лимит «чатов/тик» и ротация-справедливость (не «топ новых», а дефицит-круг, чтобы тихий чат не голодал).
   - Тики с **jitter/размазыванием**: дистилляция (окно 4–6) и ностальгия (8–23) не должны стартовать во всех чатах одновременно; к сущ. per-chat лимитам добавить глобальный `background_max_llm_per_minute`.
   - REGISTRY: группа `limits`/`memory` +6–10 ключей (лимиты), `Settings`-поля, `.env.example` — по образцу §21. Читаются через `hot.get`.
   - Косметика: гейты «фон выключен, если фон за прошлые сутки > X% суточного расхода» — деградация по приоритетам (как P2-лейн в источниках: сначала ностальгия, потом лор, сон в последнюю очередь).
2. **«Профиль нового чата» и онбординг** (продуктовый гейт).
   - `chat_profiles` += колонка `feature_gates JSONB NOT NULL DEFAULT '{}'` (ключи: `direct_chat`, `memory`, `dream`, `nostalgia`, `lore_auto`, `relations` — дефолты из глобального шаблона). Новый чат при входе (`chat_lifecycle.py`) получает шаблон «по умолчанию» — иначе бот начинает отвечать и копить память везде без спроса.
   - `handlers/chat_lifecycle.py`: при входе проверка прав бота в чату (`getChatMember`/админ) и, опционально, авто-добавление TG-админов в `chat_admins` (бот в группе видит админов: `getChatAdministrators`).
   - `handlers/chat_lifecycle.py`/новый роут: команда/кнопка «активировать» для владельца (бот молчит, пока чат не активирован, кроме /start-подсказки).
3. **Per-chat параметры (узкий whitelist).** Новый слой «override поверх глобальных»:
   - PG: `chat_profiles.chat_params JSONB` (или отдельная таблица `chat_params (chat_id, key, value)`); **не все 372 параметра**, а whitelist ~15–30 «профильных» (`direct_chat`-тон/персона/mood, лимиты ностальгии/сна, включение модулей).
   - Резолв: `hot.get(key)` (глобал) → при наличии `chat_id` — слой `chat_config.resolve(chat_id, key)`: global → chat_params → дефолт кода. Инжектировать только в точках чтения direct_chat/воркеров (не трогая `ConfigCache`).
   - Эндпоинты: `GET/PUT /api/chat_lore/{chat_id}/params` (переиспользовать `can_access_chat`, 409-оптимизм как у лора).
4. **Архивный режим памяти** (защита диска).
   - Новый статус чата `is_archived` (в `chat_profiles` или SQLite-таблице статусов): архивный чат не участвует в RAG/ностальгии/сне, сырьё старше TTL можно чистить, история выгружается (`VACUUM INTO`-подобный экспорт) — см. §2 риска №1.
   - Триггеры: «чат неактивен > X дней» → предложение архивировать; порог свободного диска → алерт в `status_service`/Betterstack (сейчас алертов на размер БД нет).
5. **Аудит изоляции** (тест-инвариант).
   - Тест «чат A не видит память чата B»: пройтись по всем точкам чтения (FTS-поиск, RAG, protected, dig, golden, watermark-курсоры, ностальгия-кандидаты) с двумя чатами в одной БД. Grep-аудит показал фильтры почти везде; тест зафиксирует «спящие» ветки.
6. **TMA: вкладка «Чаты»** (обобщение chat_lore-UI).
   - `web/app.js`/`index.html`: новая вкладка «Чаты» (список с поиском/превью/статусом — рендер переиспользует селектор из «Лора чатов»), внутри: тумблеры `feature_gates`, per-chat params-редактор, «Сгенерировать лор/сон сейчас», история, админы; глобальный админ видит все, per-chat админ — свои (уже через `can_access_chat`).
   - `web/api/chat_lore.py` (или новый `web/api/chats.py`): обобщённые роуты списка/профиля.
7. **Счётчик расходов per чат** (для №2 и экономики): таблица `chat_usage (chat_id, day, llm_calls, tokens_in, tokens_out)` — пишется из llm_client (тег чата есть в вызовах) → вкладка «Чаты» показывает, кто ест токены. Это же даст данные для решения «когда B».

**Плюсы:** минимум изменений схемы (2 аддитивные колонки PG + 1 новая таблица); вся тяжёлая изоляция уже есть; деплой остаётся один процесс/systemd; быстро (1–2 недели с тестами); обратимо (все новые фичи — тумблеры).

**Минусы:** потолок объёма/CPU остаётся вертикальным (SQLite на одном файле, один процесс); per-chat параметры вводятся только для whitelist (не все 372); TMA-вкладка растёт (нужен аккуратный UI).

**Риски:** «профиль чата» по умолчанию выключит direct_chat в новых чатах — надо явно проговорить UX активации; бюджет фона не должен резать интерактив (приоритеты строго P0>P2); тест изоляции может вскрыть легаси-ветки — заложить время.

**Стоимость:** ~1,5–2 недели инженерных работ (бюджеты+онбординг ~5–6 дней, per-chat params ~3–4 дня, TMA-Чаты ~2–3 дня, архив+алерты ~1–2 дня, аудит-тесты ~1–2 дня) + привычный раунд каталога/тестов.

### [ ] Вариант B — A + вынос тяжёлой памяти в PG/отдельное хранилище и шардирование

**Суть:** A + начало Epic 86 (см. `plans/docs/sqlite-to-pg-research.md`, статус «заморожен» владельцем 04.09.2026) или его облегчённая версия. Переносим не «всё и сразу», а то, что даёт масштаб: тяжёлые/горячие таблицы в PG, сырьё остаётся с ретенцией.

**Что менять:**

1. **Что и когда переносить** (порядок по ценности):
   - Сначала **`graph_facts`** (факты+вектора 3072): pgvector HNSW (int8-квантование как компромисс с диском), FTS-факты → tsvector+GIN (russian); **ведущая колонка во всех индексах — `chat_id`** (это и есть «шардинг»: PG сам разложит по партициям позже, см. источники по tenant_id-индексам). Это снимает главный вес (~2,5 ГБ векторов на 1 чат) с SQLite и диска.
   - Потом **холодное сырьё** (`smart_archive`/импортированная история): в PG-«архив» или отдельный файл-архив с TTL-выгрузкой; активное окно остаётся в SQLite.
   - `smart_messages` live-поток можно оставить в SQLite до реального упора (single-writer одного процесса — штатный режим, источники: chat-архитектуры держат SQLite in-process сознательно).
2. **Пер-чат шардирование (альтернатива/дополнение):** «database-per-tenant» на уровне SQLite-файлов: тяжёлый чат = отдельный `db_<chat_id>.sqlite` (изоляция максимальная, бэкап/перенос чата тривиален, импорт истории не раздувает общий файл). Плюсы/минусы — см. §6 (Azure/Bytebase/JusDB): на десятки чатов ок, на сотни — боль в админке и кросс-чат-аналитике. Для нашего случая скорее «архивный файл на чат», чем боевое разделение.
3. **Шардирование на PG** (когда сотни чатов/сотни ГБ): декларативные партиции по `chat_id` (или RANGE по месяцам внутри чата); вводятся без переписывания кода, если PK/индексы уже начинаются с `chat_id` — поэтому требование «tenant_id ведущим» фиксируем уже сейчас в A.
4. **Таблицы учёта:** `chat_usage` (из A) становится основой per-chat лимитов и «выключить чат-обжору».
5. **Per-chat параметры** (из A) расширяются на любые ключи каталога.

**Плюсы:** снимает оба «потолка» — объём/диск и скорость поиска на больших объёмах; RLS-уровень защиты не нужен, но row-изоляция уже в схеме; путь к C становится коротким (данные не прибиты к файлу процесса).

**Минусы:** дорого (research Epic 86: тяжёлое — слой доступа aiosqlite→asyncpg и схема FTS5→tsvector, vec→pgvector; риски CHECK-типов, rowid-семантики — весь чек-лист §4 sqlite-to-pg-research); двухБД-период (обе БД живут параллельно, откат = переключение); операционные риски PG (пул, дедлоки, MVCC-bloat) впервые появляются у памяти.

**Риски:** замороженное решение владельца (Epic 86 freeze) — нужен явный пересмотр; инцидент «строгие типы» из §3.1 research повторится при переносе легаси-данных; векторный KNN и FTS-ранжирование дадут другие результаты (golden-тесты).

**Стоимость:** эпик уровня 86 (недели), выполнять только по триггерам: свободный диск < 5 ГБ, БД > 10–15 ГБ, RAM-дефицит, потребность в кросс-чат-аналитике/расходах на уровне SQL, несколько серверов.

### [ ] Вариант C — мульти-процесс/микросервисы (боты-воркеры, API-слой). Когда нужно

**Суть:** 2+ процесса вместо одного.

**Что менять:**

1. **Ограничение, которое нельзя обойти:** polling одного бота = один процесс (`TerminatedByOtherGetUpdates`, SO-источник). Любой мульти-процесс для одного бота → **webhook** + балансировщик + общее хранилище состояний (aiogram: `RedisEventIsolation`/shared storage `with_bot_id`; DeepWiki-источник) — а Redis у нас нет, это новая инфраструктура.
2. **Что реально выносимо без webhook:** фоновые воркеры (сон/ностальгия/лор/саммари) можно запустить вторым процессом **уже сейчас**, если посадить их на общую очередь задач:
   - Паттерн «cron-тик + выборка из БД» (источник cron-driven AI): таблица-очередь `background_jobs (id, chat_id, kind, run_at, status, attempts, idempotency_key)`; тик выбирает due-задачи `WHERE status='queued' AND run_at <= now() ORDER BY priority LIMIT n FOR UPDATE SKIP LOCKED` — это даёт и приоритеты (P0-интерактив не в очереди вообще), и горизонтальность (2-й процесс `--worker-only` подхватывает те же задачи), и дед-линию по `attempts`.
   - Это превращает A в C без переписывания: бюджеты из A становятся полями очереди, а не локальными счётчиками.
3. **Когда C оправдан:** RAM/CPU инстанса упирается (сейчас 1 ГБ — реальный кандидат при «живых» 20+ чатах с видео/STT/эмбеддингами); 1000+ чатов; несколько ботов/аккаунтов (тогда — паттерн aiogram multi-bot в одном процессе, DeepWiki, или N процессов через webhook); независимые деплои TMA-API и бота.
4. **Микросервисы-«настоящие»** (FastAPI отдельно, свои БД, события через брокер) — для нашего масштаба не нужны; тянут операционку (деплой, мониторинг, версионирование контрактов) без выгоды.

**Плюсы:** единственный путь за вертикальный потолок одного инстанса; воркер-процесс без Telegram-polling можно крутить на той же машине/втором сервере.

**Минусы:** новая инфраструктура (webhook/очередь/Redis или PG-очередь + второй process manager), переезд FSM-состояний в Redis при webhook, усложнение деплоя и отладки.

**Риски:** сделать слишком рано = платить операционную сложность за несуществующую нагрузку; локальный telegram-bot-api контейнер и локальный Bot API завязаны на один процесс (проверить при webhook-переезде).

**Стоимость:** заметная (недели) + инфраструктура; не сейчас.

## 5. Рекомендация

**Делать вариант A, шагами, в этом порядке:**

1. **Сначала онбординг-гейт** (профиль нового чата + `feature_gates` + активация владельцем): без него добавление бота в новые чаты сразу начнёт жечь токены и копить память. Это 2–3 дня.
2. **Потом бюджеты фоновых воркеров** (глобальный суточный лимит, семофор фона, приоритет интерактива, jitter тиков, счётчик расходов per chat): снимает риск №2 и даёт данные для решений. 4–5 дней.
3. **Затем аудит-тест изоляции** (чат A ≠ чат B) — дёшево, фиксирует «спящие» ветки до того, как они станут инцидентом на 10-м чату. 1–2 дня.
4. **Per-chat параметры (whitelist)** + **вкладка TMA «Чаты»**: продуктовая видимость и управление. 4–6 дней.
5. **Архивный режим + алерт на размер БД/диска**: страховка потолка 24 ГБ. 1–2 дня.

Итог A ≈ 2 недели. В backlog (не выполнять сейчас): B — с триггерами «диск < 5 ГБ свободного / БД > 10–15 ГБ / RAM-дефицит / нужна SQL-аналитика по чатам» (переоткрыть Epic 86 с учётом «chat_id ведущим в индексах» и порядка переноса: graph_facts → архив сырья → live-поток); C — с триггером «упираемся в инстанс при 1000+ чатов или несколько ботов» (тогда: PG-очередь `FOR UPDATE SKIP LOCKED` из A плавно превращается в 2-й процесс-воркер; webhook+Redis — только для multi-polling).

Отдельное продуктовое решение (не техника): **хочет ли владелец, чтобы бот был «компаньоном» в каждом новом чату** (с персоной/лором/отношениями) — тогда пер-чат шаблоны «персона чата» и право чат-админов настраивать тон — ключевая фича A; или бот в чужих чатах — только «модератор/помощник» без AGI-слоя (тогда `feature_gates` по умолчанию = memory/dream/nostalgia off, direct_chat on для reply/mention).
