## 1. TL;DR — что предлагаем

Сейчас бот — это «поисковик по своей памяти»: на вопрос «а помнишь?» он лезет в FTS5/вектора и возвращает цитаты. Работает, но память у него **пассивная**: факты копятся как есть, ничего из них не выводится, отношения не учитываются, а сам он никогда не вспоминает первым. На ~2M сообщений (~1.93M импортированных + live-сообщения, растёт ежедневно) сырой поиск всё равно что спрашивать «что интересного было в жизни?» у человека, который не спал неделю и помнит всё подряд.

Предлагаем четыре направления, которые превращают бота из «поисковика» в «существо с памятью»:

1. **«Сон» (мета-рефлексия)** — фоновый синтез: раз в сутки бот «перебирает» новые факты, находит повторяющиеся темы и дистиллирует из них **убеждения/стереотипы** («Вася всегда жадничает на пиво», «в этом чате мем про ёжика — святое»), с цитатами-доказательствами. Дешёво: кластеризация без LLM + один LLM-вызов на кластер.
2. **dig_into_lore** — инструмент «глубокого копания»: когда юзер говорит «помнишь, в 2024 мы…» или просто ностальгирует, бот ОБЯЗАН сначала копнуть FTS5 + граф (multi-hop по именам, сезон «год назад») и выдать 5–8 сниппетов с датами, а потом отвечать. Ложится на существующий tool_loop.
3. **A-Life-отношения** — у каждого юзера появляется «карточка отношений» (стадия: нюфаг → знакомый → свой → ветеран, плюс активность/доверие). Перед ответом боту инжектится строка «это ветеран, с ним можно теплее» — тон становится зависимым от стадии. Дёшево, одна таблица + SQL-агрегаты.
4. **Проактивная ностальгия** — слой (A) бесплатный: при обычном ответе, если в уже найденных фактах есть «золотой» старый, добавить в промпт «кстати, вспомни: …»; слой (B) heartbeat-воркер: в тихий час бот сам пишет «кстати, год назад мы…». С жёстким анти-спамом.

Приоритет внедрения (Фаза 2, после апрува): **2a «Отношения + dig_into_lore»** (быстро, осязаемо, почти без токенов) → **2b «Сон»** (убеждения становятся топливом для 2c) → **2c «Ностальгия»** (слой A, затем B). Каждая фаза самостоятельна и откатываема тумблером в TMA.

Главная мысль «на пальцах»: мы не добавляем новый «мозг» — мы добавляем **сон, привычки и биографию** существующему. Вся тяжёлая работа либо бесплатная (SQL/кластеризация), либо — редкие облачные LLM-вызовы в непиковые часы.

**Решение по моделям:** локальная LLM — только для разовых миграций; боевые воркеры (сон/ностальгия/отношения) работают на облачных моделях через существующий LLMClient (apinet/deepseek + существующие fallback).

## 2. Контекст: что есть сейчас (коротко)

### Схема памяти (SQLite `local_database.db`, aiosqlite, WAL, single-writer)

| Слой | Что | Ключевое |
|---|---|---|

| L2/L3 | `graph_facts` (триплеты-факты) + FTS5 + vec0 `graph_facts_vec` (dim 3072, float + опц. int8-coarse) | колонки: `fact, origin (CHECK 9 значений), expires_at, created_at, target_user, weight (default 0.5), status (confirmed/unconfirmed), last_confirmed_at, supersedes, message_timestamp` |
| L2 | `smart_archive` — vec0-архив для KNN | |
| L4 | `protected_facts` — неприкосновенное (чат/юзер) | инжект в `<protected_facts>` |
| L4 | `bot_replies` — ответы бота (TTL 3600, cap 200) | `<style_anchors>`, цепочки reply |
| PG | `chat_profiles` (manual/auto lore), `chat_lore_history`, `bot_settings`, `uptime_events` | TMA/настройки/RBAC |

Origins `graph_facts` (`services/database.py:59` `_GRAPH_FACT_ORIGINS_SQL`): `chat_history` (вес 0.5), `search_fact`, `youtube_content`, `web_content`, `bot_direct_reply` (hot-вес `limits.graph_fact_weight_direct`), `voice_transcript`, `video_transcript`, `user_memory` (вес 1.0, вечно), `history_import` (вес 0.3, вечно, `message_timestamp`=дата). Веса гниют time-decay (half-life `limits.graph_time_decay_half_life_days`, пол `limits.graph_time_decay_floor`, тумблер `flags.graph_time_decay_enabled`).

### Как бот «вспоминает» сегодня

- **RAG-инжект при ответе**: `direct_chat_service` собирает `<protected_facts>` + `<chat_lore>` + `get_rag_context` (KNN→FTS fallback, топ-K, даты `[%Y-%m-%d]`) + `<style_anchors>` + mood. Всё это — **пассивная подсказка**; LLM сама решает, вспоминать или нет.
- **Инструменты в direct_chat** (`services/tool_schemas.py:8-51`): только два — `execute_web_search` и `query_chat_memory` (FTS + точный count + `time_range`). Цикл `chat_with_tools` (`services/tool_loop.py`): максимум 4 вызова LLM (`TOOL_MAX_ROUNDS=4`), ≤2 tool_calls за раунд, при не-2xx провайдера — деградация до обычного ответа.
- **Запись**: summarize-крон 4×/день (0/6/12/18, `summary_scheduler.py`) экстрактит факты; fire-and-forget `memorize_facts` после ответов бота (`origin='bot_direct_reply'`), поиск/фактчек-сервисы пишут `search_fact` и т.п.
- **Обслуживание** (`memory_maintenance.py`): merge эпизодов (KNN-кластеры ≥0.85 + LLM-слияние, лог `graph_fact_compressions`), review (склейка дублей ≥0.95, выброс истёкших/unconfirmed), WAL-checkpoint. Память-команды `/clear /forget`, тумблер `memory.infinite_retention`.
- **Лор**: LoreWorker (тик 30 мин, `IntervalTrigger(minutes=limits.lore_tick_minutes)`), макро-мерж с PG-профилями, `<chat_lore>` инжект. Аналог фонового «медленного» воркера уже есть — на него будем опираться.
- **Импорт истории** (`tools/history_import/`): FTS-импорт готов; graph-воркер на локальной Ollama (qwen3.5:9b, `llm_worker.py`, режим 'ollama', think off) с чекпоинтами (разовая миграция, выполнена; в боевом цикле локальная LLM не используется).

### Почему «пассивный RAG» не тянет на 2M сообщений

1. **Сигнал тонет в шуме.** При 2M сообщений любая тема даёт тысячи совпадений; топ-K по cosine/BM25 вытаскивает «похожее», но не «важное». Нет слоя, который сводит тысячи повторений к одному выводу («этот человек в этом чате — постоянный персонаж, а не случайный прохожий»).
2. **Семантика не выше уровня цитаты.** RAG отвечает на «что писали про X», но не на «какой Вася» — для этого нужен синтез (belief), а не поиск.
3. **Бот не знает, с кем говорит.** Одна и та же интонация и для человека, который в чате 3 года, и для новичка. Стадии отношений — дешёвая и очень заметная фича.
4. **Нет проактивности.** Память «срабатывает», только когда юзер спросил. А самое человеческое — вспомнить самому («кстати, год назад…»).
5. **Цена поиска растёт.** FTS на 2M — ок, KNN — ок, но чем больше данных, тем ниже «плотность пользы» на токен контекста; нужен пре-отбор важности (importance) ещё на записи, а не на чтении.

## 3. Направление 1 — «Сон» (мета-рефлексия)

### Идея на пальцах

Люди не запоминают 2M сообщений — они спят, и во сне мозг **сжимает повторяющееся в убеждения**: «Вася опять не заплатил», «по воскресеньям все смотрят футбол», «о ёжике шутить можно, о маме нельзя». Даём боту такой же режим. Не каждое сообщение — а редкий фоновый синтез того, что **повторялось и было важно**.

### Как работает под капотом

**Фаза «бодрствования» (онлайн, в момент записи факта)** — присвоение importance 1–10:
- Стоит дёшево: правило (тип origin: `user_memory` → важнее, `history_import` → ниже, длина/наличие имени/цифр/даты → выше) и/или один LLM-вызов на пачку фактов (например, LLM-раз на 20–30 фактов, как уже делает `history_import/llm_worker.py` пачками по 25 сообщений).
- Полная стоимость важности: ~0 добавочных вызовов в hot-path (считаем правилом или добавляем к существующему пачечному вызову экстракции summarize-крона).
- Записываем в новую колонку `graph_facts.importance` (см. ниже).

**Фаза «сна» (фоновый воркер, 1–2 раза/сутки на активный чат, не в часы пик)**:
1. **Отбор кандидатов** — новые факты за период (created_at > last_dream_at) + критерии как в Gen Agents: сумма importance кластера > порога; и/или повторяемость темы (RecMem: N≥2–3 повторений по FTS/BM25 или KNN-соседству).
2. **Кластеризация — БЕЗ LLM**: BM25/эмбеддинг-кластеры по эмбеддингам фактов (у нас уже есть vec0 `graph_facts_vec` + FTS5 — и то и другое бесплатно). Повторяемость можно посчитать даже без векторов: FTS-токены субъекта/объекта триплета → группы с общими сущностями.
3. **Дистилляция — 1 LLM-вызов на кластер**, только если кластер прошёл пороги (важность и/или повторяемость): промпт «вот N фактов с датами и source-ссылками — сформулируй 0–2 стереотипа/убеждения/правила поведения, каждое с цитатами». Модель — **облачная через существующий LLMClient** (apinet/deepseek + существующие fallback — тот же путь, что обычные ответы бота); локальная qwen3.5:9b в боевом цикле не используется.
4. **Запись**: новый факт в `graph_facts` с `origin='derived_belief'`, `kind`, `belief_meta` (kind/уверенность), `weight`, `importance`, `valid_from` (=created_at), `source_ids` (JSON-массив id исходных фактов). Если новая дистилляция **противоречит** старому belief — старый помечается `supersedes`-ссылкой (механизм колонки `supersedes` уже существует в схеме!).
5. **Подтверждение повторением**: belief не «вечный» — он живёт, пока факты-источники повторяются/подтверждаются (инкремент `last_confirmed_at`, как уже делает `status`/`last_confirmed_at` у обычных фактов); без подтверждения — decay/удаление через существующий review-воркер.

**Бюджет и пороги** (все — hot-ключи, см. TMA):
- «Сон» не чаще 1–2 раз/сутки на активный чат; глобальный лимит кластеров/LLM-вызовов в сутки (напр. `limits.dream_distillations_per_day` = 30–60) — он же денежный бюджет.
- Дистилляция — облачная через существующий LLMClient (apinet/deepseek + существующие fallback, путь обычных ответов); при дефолтном лимите ~30–60 дистилляций это ≈ **$0.1–0.3/сутки** (локальная LLM в боевом цикле не используется).
- Порог важности (`limits.dream_importance_sum_threshold`), порог повторяемости (`limits.dream_repeat_threshold` ≥2–3), лимит токенов/сутки.
- Воркер НЕ должен работать во время диалогов: окно по умолчанию 04:00–06:00 (настраивается). Анти-рейс — `max_instances=1` + `coalesce` по образцу `memory_maintenance`: состояние «сна» в SQLite, поэтому PG-advisory-lock не нужен (он есть только у `lore_worker`, где состояние в PG).

### Новые таблицы/поля (минимально, аддитивно)

| Объект | Что |
|---|---|
| `graph_facts.importance INTEGER` | важность 1–10, правило/пачечный LLM на записи |
| `graph_facts.source_ids TEXT` | JSON-массив id фактов-источников (для цитат и анти-галлюцинаций) |
| `graph_facts.kind TEXT` (`'fact'\|'belief'\|'stereotype'`) | тип записи |
| `graph_facts.belief_meta TEXT` | JSON: уверенность, последний раз подтверждён, конфликт |
| CHECK-список origins += `'derived_belief'` | graph_facts: миграция v8 (rebuild + CHECK + новые колонки) по прецеденту v7 (пересоздание таблицы, `services/database.py:618-683`) |
| `memory_dream_log` (новая таблица) | когда/какой чат/сколько кластеров/сколько beliefs создано/source_ids — аудит + экран «последние сны» в TMA |

### TMA

Раздел «Память и RAG» (вкладка `memory_rag`, `web/app.js:33-39`) → новый блок «Синтез (сон)» (категория `memory`, группы `flags_memory`/`limits_memory` по образцу REGISTRY в `services/param_catalog.py`):
- тумблер `flags.dream_enabled`;
- частота в часах `limits.dream_interval_hours` (по умолчанию 24);
- порог важности `limits.dream_importance_sum_threshold`; порог повторяемости `limits.dream_repeat_threshold`;
- лимит токенов/сутки и лимит дистилляций/сутки;
- кнопка «Запустить синтез сейчас» (эндпоинт по образцу `/api/chat_lore/{chat_id}/generate`);
- просмотр последних beliefs (`memory_dream_log` + записи `kind='belief'`) с кнопками «удалить»/«повысить в protected_facts».

## 4. Направление 2 — dig_into_lore (агентное копание)

### Идея на пальцах

Юзер пишет: «помнишь, как мы тогда с Васей…» — и бот сейчас отвечает по куцему топ-K из одной попытки RAG. А должен **покопать**: что именно было «тогда», в каком году, кто участвовал, чем закончилось. Как старый друг, который на секунду задумался, прежде чем ответить: «А, точно, это было в июле 2024…».

### Как работает

**Новый tool `dig_into_lore`** в тул-сет direct_chat (`services/tool_schemas.py` — третий элемент `TOOL_CALLING_TOOLS`; тул-сет остаётся ≤6):
```json
{
  "name": "dig_into_lore",
  "description": "Глубокое копание в истории чата: «помнишь/а помните/как мы тогда/в 2024/что было с <имя>»…",
  "parameters": {
    "query": "строка",                    // о чём вспомнить
    "year": "число|null",                 // фильтр по году («в 2024»)
    "person": "имя|null",                 // фильтр по участнику
    "mode": "messages|facts|both"         // FTS по переписке / по фактам графа (имена → FTS) / везде
  }
}
```

**Роутинг** — новая ветка `_dig_into_lore` в `services/tool_router.py` (рядом с `_query_chat_memory` :141), результат:
1. **FTS5 по `smart_messages`** (как `_query_chat_memory`/`get_rag_context`, но с расширенным окном и сортировкой по релевантности+давности);
2. **граф-обход — источник имён, а не сниппетов**: `graph_facts` не связаны с `nodes`/`edges` (нет FK), `nodes`/`edges` не несут текстов/дат, датированные сниппеты даёт только FTS5 по `smart_messages` — поэтому multi-hop по графу (до 2) даёт имена/связи (`target_user` и т.п.) для расширения FTS-запроса;
3. **сезонный фильтр** «год назад в этот день/месяц» — дешёвый диапазон по `timestamp` (индекс `idx_smart_messages_chat_ts`);
4. результат: 5–8 сниппетов с датами (`[Имя 2024-07-12]: текст`) — их даёт FTS5 по `smart_messages` (запрос расширен именами из граф-обхода) + краткая справка «что это было» (LLM-вызов только на этапе справки, и то опционально: в первой версии можно чистыми сниппетами).

**Улучшение вызова** (это 70% пользы фичи):
- (а) **контракт в system-промпте** (`services/chat_prompts.py`, канон + авто-миграция PG-значения через `prompt_migrations.py` — прецедент раунда 5): «если юзер говорит "помнишь/а помните/как мы тогда/в 2024" или упоминает старое событие/человека — ОБЯЗАН вызвать dig_into_lore ДО ответа»;
- (б) few-shot примеры прямо в description инструмента;
- (в) ночные/общие тулы ограничить — чтобы модель не тратила раунды на web-search при ностальгии (порядок тулов в промпте и описание);
- (г) **дешёвый пре-гейт в коде**: если в сообщении есть маркеры ностальгии («помнишь», «а помните», «как мы тогда», год, «год назад», «кто был тот…») и RAG-инжект пуст/беден — принудительный retrieval-раунд (не ждём, пока LLM сама догадается вызвать тул).

**Реализуемость на текущем tool_loop**: да. `chat_with_tools` (`services/tool_loop.py:27-85`) уже умеет цикл assistant(tool_calls)→role:tool→повтор; добавить инструмент = схема + ветка роутера + рендер результата. Лимит раундов уже есть (4), лимит на 2 вызова/раунд — не мешает (1 вызов dig = 1 round).

### TMA

- «Промпты» (вкладка `prompts`): редактируемый канон-промпт «dig-контракта» (по образцу `prompts.direct_chat_system_prompt`, с авто-миграцией при смене канона);
- «Лимиты» (`limits_memory`/`limits_graph`): глубина графа (`limits.dig_graph_hop_depth`), макс. сниппетов (`limits.dig_max_snippets`), макс. символов результата;
- «Память и RAG»: тумблер `flags.dig_enabled`.

## 5. Направление 3 — A-Life отношения

### Идея на пальцах

У бота в чате есть «свои» и «чужие», старички и новички. Сейчас он общается с ветераном трёхлетней давности так же, как с человеком, который зашёл вчера. Добавляем «сердце»: табличка отношений, где у каждого юзера есть стадия. Новичку бот — ироничный и сдержанный; ветерану — тёплый, с правом на ностальгию и личные отсылки. Это самый дешёвый способ сделать бота «живее» из всех четырёх направлений.

### Как работает под капотом

**Новая таблица `users_meta`** (SQLite, аддитивно — CREATE TABLE без rebuild и без номера версии, по образцу `user_prefs` в своё время; рядом живут `message_counters` и `user_presence` — их НЕ трогаем):
```
user_id, chat_id,
first_seen, last_seen, msg_count, active_days,
activity_score REAL,            -- экспоненциальный decay
relationship_stage TEXT,        -- stranger|acquaintance|regular|veteran
trust REAL, intimacy REAL,
last_stage_change INTEGER
```

**Расчёт** — SQL-агрегаты по `smart_messages` + экспоненциальный decay (дёшево, можно лениво при ответе юзера + по крону):
- `msg_count`, `active_days` — из существующих `message_counters`/`smart_messages`;
- `activity_score` — скользящее среднее с decay (полураспад ~14–30 дней);
- стадия — по правилам: `stranger` (новичок) → `acquaintance` (несколько дней/сообщений) → `regular` (регулярно недели-месяцы) → `veteran` (**порог: 3+ месяца и >N сообщений/неделю**, настраивается);
- **стадии не откатывать резко** (урок Replika: резкая «деградация» ломает иллюзию): при долгом отсутствии — только плавный decay `activity_score`; стадия понижается не чаще раза в месяц и только с «мягким» потолком (veteran→regular, но не veteran→stranger). Тон при абьюзе регулируется отдельно (существующие кулдауны/молчание), а не понижением стадии.

**Интонация**: перед генерацией в `direct_chat_service` (в `_build_prompt_sections`/сборку context-секций, рядом с `<protected_facts>`/`<chat_lore>` в `direct_chat_service.py:420-438`) инжектится блок **`<user_relations>`** — 1 строка на активного юзера: стадия + 2–3 параметра (активность/доверие) + 1–2 любимые темы/факта из графа. Дёшево (десятки токенов). Промпт-инструкция рядом с dig-контрактом: «нюфаг → холоднее/ироничнее, меньше отсылок к лору; ветеран → теплее, можно личные отсылки и ностальгию».

### TMA

**Решение: отдельного TMA-раздела «Отношения» НЕ заводим** — настройки/параметры отношений живут ВНУТРИ существующего раздела «Лор чатов» (PG `chat_profiles`, per `chat_id` — масштабирование на несколько чатов уже заложено). Вкладка «Лор чатов» → новый блок **«Участники и отношения»**: список юзеров чата (стадия, скор, активность, с датами); ручная корректировка стадии админом (эндпоинты по образцу `web/api/chat_lore.py` — у нас уже есть паттерн per-chat admin API; per-chat параметры — в `chat_profiles`). Тумблеры `flags.relations_tone_enabled` (влияние на тон вкл/выкл) и `flags.relations_manual_stage` остаются в существующих группах горячих ключей, без новой вкладки.

## 6. Направление 4 — Проактивная ностальгия

### Идея на пальцах

Самое человеческое в памяти — **вспоминать без спроса**. В воскресенье вечером, когда чат притих, бот вдруг пишет: «кстати, ровно год назад вы тут обсуждали, что ёжик — наш талисман…». Если делать это редко, уместно и по делу — это магия. Если часто — это спам-бот. Вся фича — в анти-спаме.

### Два слоя

**(A) Бесплатный встроенный (при ответе).** Уже сейчас при ответе идёт retrieval (`get_rag_context`). Добавляем в выборку «золотые» старые факты (важность ≥ порога И давность ≥ порога, напр. 6+ месяцев, тема совпадает с запросом по KNN/FTS) и, если такой нашёлся, в промпт добавляется одна строка: «кстати, вспомни: <факт> (дата) — можешь вплести, если уместно». **0 дополнительных LLM-вызовов** — решение о вплетении принимает сама LLM. Стоимость: чуть больше токенов на инжект и чуть шире KNN-окно.

**(B) Heartbeat-воркер (каркас `lore_worker`, но БЕЗ его PG-lock).** Раз в 30–60 мин (`IntervalTrigger`, `max_instances=1` + `coalesce`, как в `memory_maintenance`; PG-advisory-lock — только у `lore_worker`):
1. условие: в чате есть юзер, чьё последнее сообщение > N минут назад (тихий период);
2. кандидат-тема из последнего диалога (эмбеддинг/ключевые слова) сопоставляется с историческим «золотым» фактом (KNN по `graph_facts_vec` + FTS5 + дешёвый приём «год назад в этот день» по диапазону `timestamp`);
3. **один LLM-вызов на срабатывание** (облачная через существующий LLMClient — apinet/deepseek + существующие fallback, тот же путь, что обычные ответы бота; локальная qwen3.5:9b не используется): модель пишет 1–2 фразы «кстати, в 2024 мы…» в стиле бота;
4. бот шлёт сообщение (обычным relay-механизмом).

**Анти-спам (обязателен, это условие приёмки):**
- макс. в сутки (2–3 на чат, `limits.nostalgia_max_per_day`);
- quiet hours (по умолчанию ночь);
- cooldown между срабатываниями 12–24 ч;
- стоп после 2 неотвеченных срабатываний подряд (юзеру неинтересно — не долбим);
- тумблер `flags.nostalgia_enabled` + ползунок агрессивности 0–100 (`limits.nostalgia_aggressiveness` — частота/пороги);
- кнопка «показать последние срабатывания» (лог срабатываний в таблице, аудит).

### TMA

Блок «Ностальгия» (вкладка `memory_rag`): `flags.nostalgia_enabled`, ползунок агрессивности, `limits.nostalgia_max_per_day`, quiet hours (`limits.nostalgia_quiet_start/end`), «последние срабатывания».

## 8. Риски и ограничения (общие)

1. **Токены «сна» и проактивки.** Дистилляции и ностальгия жгут токены. План: облачная LLM через существующий LLMClient (apinet/deepseek + существующие fallback), вызовы — редкие и фоновые (сон 1–2×/сутки на чат, ностальгия ≤2–3/сутки), НЕ в диалоговом hot-path и не в часы диалогов. Локальная Ollama (qwen3.5:9b) в боевом цикле не используется — она осталась только для разовой векторизации истории. Бюджеты в hot-ключах с дефолтами «консервативно» (лимит дистилляций/токенов/срабатываний в сутки = и денежный лимит).
2. **Качество дистилляции / галлюцинации beliefs.** LLM может сочинить «Вася всегда жадный» по двум случайным фактам. Защита: обязательные `source_ids` + цитаты; порог повторяемости ≥2–3; supersede при противоречии; неподтверждённые beliefs вычищает существующий review (`memory_maintenance`); «золотые» факты для ностальгии берутся ТОЛЬКО с source-датами.
3. **Приватность.** Синтез 2M сообщений остаётся локально: всё пишется в тот же `local_database.db`, никуда не отправляется, кроме уже привычных LLM-API (и то — только сниппеты-кандидаты, как сегодня RAG). Отдельного внимания: не дистиллировать в beliefs содержимое `protected_facts` (гейт, как в merge-воркере).
4. **Нагрузка SQLite / single-writer.** FTS5 и KNN на 2M — ок (уже работает), но всё новое пишется через единственное соединение с WAL + `busy_timeout` 5с. Воркеры «сна»/«ностальгии»: `max_instances=1`, редкие короткие транзакции, вне пиков; WAL-checkpoint уже автоматизирован (`memory_maintenance`), для новых таблиц пересчитать частоту.
5. **Промпт-регрессии.** Любая правка канона (`chat_prompts.py`) требует авто-миграции PG-значения (`prompt_migrations.py`), иначе прод-промпт перетрёт/разойдётся с каноном. Инжекты новых блоков — строго по бюджетам контекста (порядок урезания уже есть, 66.12).
6. **Тон по стадиям ≠ «человечность».** Плохо сделанная интонация даёт эффект «подлизывающегося бота». Правило: инжект — 1 строка, стиль абьюзера из канона не трогаем, только «температура отсылок».
7. **Спам-ностальгия убивает фичу.** Анти-спам — не «желательно», а условие приёмки 2c.

### Таблица «что НЕ делаем» (сознательные ограничения)

| Не делаем | Почему |
|---|---|
| Полный MemGPT-пересказ контекста / бесконечный роллинг истории в каждом ответе | Дорого токенами, ломает стиль, даёт мало сверх существующего `<Conversation_Thread>` |
| LLM-реакция (importance/суммаризация) на КАЖДОЕ сообщение | Десятки тысяч вызовов в день — неприемлемо; importance правилом + пачечно |
| Graph community detection / full-graph пересчёт на 2M | Дорого (CPU/память) и ненужно: у нас уже есть граф фактов и edges; «сообщества» заменяют кластеры повторяемости |
| Хранение больших «профилей личности» на каждого юзера (LLM-генерируемые тексты) | Разрастается, тяжело модерировать; замена — beliefs (короткие, с source_ids) + `users_meta` (числа) |
| Отдельный TMA-раздел «Отношения» в стороне от чат-лора | Решение: настройки/параметры отношений живут внутри «Лор чатов» (PG `chat_profiles`, per `chat_id`) — блок «Участники и отношения»; иначе дублировали бы per-chat управление лором |
| Автоматическое понижение стадии отношений за абьюз/молчание | Replika-урок: резкая деградация разрушает доверие; тон-санкции — существующими кулдаунами |
| Ностальгия без source-фактов («я помню, что ты…» без доказательства) | Прямой путь к «ложным воспоминаниям» и газлайтингу юзера |

## 9. Глоссарий

- **Belief (убеждение)** — синтезированный вывод из многих фактов («Вася вечно тормозит с оплатой»), в отличие от fact (единичное событие). Хранится в `graph_facts` c `kind='belief'`/`'stereotype'`, `origin='derived_belief'`.
- **Дистилляция** — один LLM-вызов, превращающий кластер фактов в 0–2 убеждения с цитатами-источниками.
- **Importance (важность)** — оценка 1–10 «насколько это запомнится», присваивается на записи факта (правило/пачечный LLM). Используется порогами «сна» и отбором «золотых» фактов.
- **«Сон»** — фоновый цикл синтеза (кластеризация без LLM → редкие дистилляции → запись beliefs), 1–2 раза/сутки на активный чат.
- **Heartbeat** — периодический тик воркера (у нас уже есть в `lore_worker` 30 мин, в `uptime_heartbeat` 60 с); здесь — тик воркера ностальгии.
- **A-Life** — «искусственная жизнь»: бот ведёт себя как живое существо (стадии отношений, тон, проактивные воспоминания), а не как stateless-обработчик запросов.
- **supersede** — механизм «новый факт отменяет старый» (колонка `graph_facts.supersedes` уже есть, используется для beliefs-конфликтов).
- **«Золотой» факт** — старый (давность ≥ порога), важный (importance ≥ порога), с реальной датой — кандидат на ностальгию.
- **Multi-hop** — обход графа «через одного»: Вася → связь → событие/другой участник → Оля; до глубины 2. Даёт имена/связи для расширения FTS-запроса, а не готовые тексты (`nodes`/`edges` текстов и дат не несут, с `graph_facts` не связаны FK).
- **RecMem / Gen Agents** — research-ориентиры: критерии «повторяемость темы» (RecMem) и «сумма важности кластера > порога» (Gen Agents) — отражены в порогах «сна».
