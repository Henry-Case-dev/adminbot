Финальная матрица/витрина/самообучение/диагностические действия — `mca-17c` (Wave 5), но «новый процесс без наблюдаемости» = незавершённая интеграция (§27.1). В release-отчёте — матрица покрытия каждого фактического процесса.
2. **MCA-13 — базовый контракт событий.** Все фичи пишут события по §17.1 и используют словарь reason_code §17.2; иначе наблюдаемость MCA-17 не собирается. Поэтому `mca-13` — Wave 0.
3. **MCA-14 — аддитивная схема сначала.** Любое изменение DDL/таблиц идёт через механизм `mca-14` (backup с WAL → проверка места → идемпотентная миграция → сохранение старых ID/таблиц). Несовместимый откат кода запрещён — только rollback build / forward fix. Kill-switch (env-only по прецеденту проекта, default ON) у каждой функции; релиз — с ними ON.
4. **§2.12 ANU-ключ.** Интеграция обязательна, но активируется только с **реальным** ключом и реальной проверенной партией чисел (`quantum_activated`). При отсутствии/неисправности ключа — `provider_unconfigured/auth_failed/quota_exhausted` и **видимый блокер только квантовой интеграции**; остальные функции работают по fallback-политике. Fallback ≠ успешная активация. Ключ — только из секрета источника/защищённого хранилища.
5. **§6.2 cookies/профиль.** Не удалять работающие cookies/профиль/авторизацию без доказательства безопасного сохранения. Исключить секреты из упаковки, не удаляя файл на сервере; при невыясненной зависимости — `cleanup_deferred_dependency_unverified`, runtime-файлы оставить. Не блокирует остальные функции.
6. **Игровой stub 14.12 — единственная намеренно неактивная функция** (вне SmartModule, `not_implemented`, без side effects/квоты/tools/UI). В effective-state §20.2 он «только код stub».
7. **Один координатор; один выбор exploration на автономную ситуацию; один RandomSource; один контур инициатив.** Ни одна фича не создаёт второй контур отправки/второй канал телеметрии (§4/§27.1).
8. **REUSE-дисциплина (§3/§3.1).** Epic 1–3 (миниапп/IA, Summary Hybrid, координатор/ExecutionGraph, ToolResult, identity/dossier, action≠style) — исходная архитектура; уже исправленный дефект подтверждается тестом, а не дублируется; end-to-end проверки — на обновлённых путях; перенос старого unit-теста недостаточен.
9. **R17/R18.** Секреты источника не переносятся; `plans/current_task.md` не изменяется; API-ключ/SSH — только на шаге деплоя из источника; маскирование в логах/отчётах/KG.

## 5. Стратегия доставки (единый production-релиз §20)

**Принцип:** одна интегральная версия; все фичи вливаются в общую ветку; единственный деплой на фиче `mca-release`; пер-фичевых тегов/деплоев нет (§2.4–2.5). Порядок волн — только зависимости разработки.

**§20.1 — ДО переключения (выполняется на `mca-release`):**
1. Интеграция с актуальной основной веткой без затирания чужих задач.
2. Обязательные проверки §19 + migration smoke.
3. Backup и проверка возможности чтения копии (согласованно с SQLite+WAL; §18).
4. Manifest изменений, config changes, путь возврата кода, команды проверки.
5. Деплой существующим способом и секретами; секреты — не в команды/логи.

**§20.2 — Включение:** применить совместимую схему, развернуть код, применить **явно сохранённую** production-конфигурацию (новых defaults недостаточно при перекрытии старыми значениями в БД). Effective state — по таблице §20.2 (все MCA ON; игровой stub — только код; новые денежные лимиты OFF; при отсутствии ключа ANU — деградация только квантового источника с видимой причиной).

**§20.3 — СРАЗУ после деплоя:**
- Проверить через runtime/API: effective config, direct reply в предназначенном контексте, retrieval, создание/закрытие намерения, свежий source link, archive checkpoint, данные витрины, один доступный video path, журналы. Не рассылать синтетику участникам.
- Наблюдать первые реальные операции и ≥1 короткое окно телеметрии (ориентир 15 мин, без блокирующих sleep в агенте). Не ждать планового глубокого сна сутки: путь проверить контролируемым запуском с защитой от дублирования.
- При сбое — исправить и повторить затронутую проверку; при риске порчи/спама — временно выключить только неисправный компонент, сохранив приём сообщений, с точной причиной; возобновить после исправления.
- При отсутствии production-доступа — закончить код/проверки/manifest/точные команды и написать «деплой не выполнен: нет …», не запрашивая повторное одобрение.

**Финальные шаги (после §31, из конца ТЗ):** максимальное покрытие тестами + прогон + перепроверка логики и отсутствия конфликтов → README (ироничный тон) → коммит в основную ветку на русском + push → деплой на прод по инструкции владельца (SSH/`git pull`/`.env`/`systemctl restart|status admin_bot`; секреты — только из источника) → человекочитаемый отчёт простыми словами. Выполняются на фиче `mca-release` (@PM/@Builder/@Reviewer/@Scanner/@Architect/@DevOps/@Memory по воркфлоу).
