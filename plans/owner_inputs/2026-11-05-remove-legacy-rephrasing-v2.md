**Тип:** обязательная корректировка текущих работ **UNIFIED-REPLY v1.1 / UR-A**, **BEHAVIOR-GATES-SIMPLIFICATION-01 (BGS)** и их интеграции. **Это задание на реализацию**, не исследовательский эпик и не разрешение остановить существующий workflow.

**Область:** Telegram Direct и Initiative; все реально достижимые варианты ответа, в том числе legacy/System2, tool-loop, fallback, долгие ответы, rich/plain delivery и смежные точки отправки. Специализированные пайплайны сохраняются в границах, описанных ниже.

После его завершения допускаются только технически необходимые или явно выбранные владельцем **детерминированные, несмысловые** преобразования, а не второй автор текста.

Проверено по опубликованной `release/2.58.158` (состояние на момент подготовки корректировки). **Перед изменениями исполнитель обязан работать с актуальным локальным `current_task.md`, HEAD рабочей ветки и незакоммиченными правками**, поскольку `evol/impl` и рабочие ветки могут опережать опубликованный релиз. Ниже — ориентиры для точечного поиска по call graph, **не жёсткий перечень имён, которыми можно ограничиться**:

Это разные вмешательства; удалить одно перефразирование недостаточно.
6. Существуют специализированные factcheck/summary/meme и доставочные пути, у которых промежуточный анализ, JSON, извлечение фактов или генерация изображения **не тождественны** незапрошенному переписыванию окончательного Telegram-ответа.

**Вывод для реализации:** удалить достижимую цепочку и её замены, а не просто выключить `SYSTEM2_DIRECT_ENABLED` и объявить победу. Подтвердить фактическую топологию **после** слияния последних волн UNIFIED-REPLY, не подменять описание опубликованной ветки утверждением о локальном коде.

## 1. Точная терминология и границы

**Подготовка** — поиск, память, построение темы/адресата, разбор пользовательской задачи, анализ, извлечение фактов, схема L1, дедуп источников, упаковка Evidence и создание структурированного промежуточного представления; эта стадия может включать LLM-вызовы, но **не владеет финальной Telegram-репликой**.

**Финальный Writer (L2)** — единственная логическая стадия, которая, увидев plan + факты + диалог + характер + время чата, формулирует окончательное смысловое сообщение от имени бота. Нужный стиль и жанр создаются **внутри неё**, а не добавляются отдельным литературным переписчиком.

**Запрещённый rewrite** — незапрошенная операция «уже пригодный для отправки содержательный ответ → новый смысловой текст» после Writer или между двумя конкурирующими писателями: перефразирование ради голоса/стиля, устранение клише, метатекста, чисел, отрицаний, схожести с прошлой репликой, неподтверждённого предложения, форматной эвристики, или поздний fallback в другой литературный маршрут. Запрет касается **поведения и reachability**, независимо от имён модулей и флагов.

**Разрешённое техническое преобразование** — преобразование **без нового смыслового авторства**: удалить настоящие machine/reasoning/target markers; экранировать HTML/Markdown; нормализовать платформенные разделители; разрезать Telegram-сообщение без потерь; применить выбранные владельцем буквальные пунктуационные правила с protected spans; сформировать допустимую структуру RichMessage из **того же** текста. Изменения должны быть трассируемы и не удалять информацию или менять утверждения.

**Не считать повторным Writer:**
- технический retry **того же незавершившегося LLM-вызова** из-за сетевого/провайдерского сбоя, когда прежний ответ не был принят как завершённый; модельный fallback на том же этапе с тем же планом и обязательными evidence (перепаковка под меньшее окно fallback допустима по правилам UNIFIED-REPLY, но без потери защищённых источников/вопроса);
- продолжение ответа, если провайдер вернул `finish_reason=length` (дописывание того же логического сообщения, не написание альтернативного текста);
- заново начатый **новый ход** после нового сообщения пользователя/нового события, с новым idempotency key;
- обязательный разбор фактов до финального Writer, а также самостоятельные специфицированные задачи пользователя на перевод/редактирование/пересказ.

**Не считать сохранением идемпотентности:** генерацию альтернативного ответа потому, что строка похожа на предыдущий бот-ответ. Идемпотентность проверяется по **идентичности события/доставки**, а не по совпадению текстов двух разных событий.

## 2. Конечная архитектура

### R-01. Единый основной маршрут

Для содержательного ответа Direct и Initiative обязательно:

`TurnRequest + ContextSelection → L1 Plan/Decision → Tools + EvidenceBundle (при необходимости) → единый L2 Writer → технический delivery renderer → Telegram`.

1. L1 решает отвечать ли, кому, в какой форме, насколько подробно, нужны ли инструменты/веб-поиск и какой контекст взять. **Не производит заменяющий финальную речь draft.** Если решение `silent`/`react`, L2 не нужен.
2. ToolRouter выполняет инструменты, собирает результаты и source provenance. Формат промежуточного результата для Writer — данные/evidence, **не готовая фраза для переписывания**. Если старый инструмент возвращает свободный текст, сохранить его как атрибутированный `tool_result`, не как авторский черновик, если только действие специально объявлено терминальным и детерминированным.
3. L2 пишет окончательный текст **сразу** в настроенном характере. Он получает общий для Direct/Initiative базовый речевой composer, реальные факты, владельческие настройки, reply-привязку, релевантную память (включая собственные слова бота), текущий ChatClock и результаты поиска. Не дублировать character/style в нескольких слоях.
4. Степень подробности определяют план и задача, **не** скрытый fixed cap/жанровая инструкция «будь кратким» для инициативы или повторный Formatter. Физические API/Telegram границы остаются.
5. Сохранить специфические решения инициативы (уместность, silence/react, SendRecheck, target, cooldown, дедуп отправки) и Direct (явное обращение, reply). Это бизнес-логика выбора/доставки, **не** второй Writer.

### R-02. Удалить legacy System2 как альтернативного автора

1. Из всех достижимых маршрутов удалить вызов `_synthesize_direct_answer()` как схемы `готовый tool-loop ответ → Stage-1 JSON → Stage-2 новое литературное изложение`. Удалить/переиспользовать её технические функции по фактическим consumers, не оставив обратный путь по `SYSTEM2_DIRECT_ENABLED`, отключённому L1, failover или недоступным инструментам.
2. Если Stage-1 производил **уникальные нужные факты** или извлекал полезную структуру из инструмента, эти операции выполнить **до L2** в существующей evidence/normalization стадии, предпочтительно без нового LLM. Не потерять provenance, цитаты, JSON-временную шкалу и источники.
3. Лишний текстовый Stage-2 Verbalizer убрать только из **обычного Direct/Initiative**. Функция/слово `verbalizer` не основание автоматически удалять её из фактчека, саммари или специальных продуктов, если именно она впервые создаёт конечный текст из анализа.
4. **Нет fallback в legacy.** Ошибка L2 — диагностируемая ошибка, допустимый retry транспортного вызова/переход на fallback-модель **в рамках того же этапа**, либо честное сообщение о недоступности, но не публикация непрозрачно обработанной «каши» tool logs и не второй автор.
5. После слияния UR-A поискать все альтернативные call sites: legacy switches, aliases, old handlers, feature gates, fallback routes, background workers. Не объявлять удаление только по отсутствию текстового совпадения `_synthesize_direct_answer`.

### R-03. Убрать `FormContract`-костыль там, где больше нет переписывания

1. Для свободного Direct/Initiative удалить построение `FormContract(source_text=draft_text)` из промежуточного ответа tool loop и сравнение его со свободным итогом L2; сам контракт здесь логически некорректен — финальная формулировка **не обязана** сохранять число токенов, отрицаний, упоминаний и имён в черновике инструмента.
2. Не расширять списки `не/ни/без/ничего` и regex-окна для «защиты» этого отсутствующего преобразования. Исправления формы из релиза 2.58.158 остаются применимыми лишь там, где реально есть **явная трансформация с исходным текстом и требованием сохранить смысл**.
3. Для отдельных явных пользовательских команд переписать/отредактировать/перевести допустим **узкий, проверяемый, целевой** контроль неизменяемых данных (имён, дат, чисел, отрицаний), но никакой обязательной дополнительной LLM-стадии литературной правки после готового результата. Возвращать прозрачный исход/попросить уточнить при принципиально неоднозначной трансформации, а не молча заменять новым текстом.
4. В specialised Factcheck/statistical output сохранилось требование не фабриковать измерения/данные. Делать валидацию на уровне facts, `MetricResult`, `NumericClaim`, evidence/claim binding и до финальной публикации; не заменять проверку источника лексическим сравнением двух авторских ответов.

### R-04. Перестать перегенерировать завершённую речь из-за постгардов

**Свободный текст L2 не может вызывать новый LLM-вызов и смысловую правку по причинам:** `form_retry`, `numeric_claim_retry`, `metatext_retry`, `format_retry`, `cliche_retry`, `evidence_egress_retry`, `duplicate_guard_retry`, `freshness_retry` и эквивалентным aliases.

1. `negative_constraints.verbalize_validated()`: разнести **обязательный протокол** (структура машинных JSON, схемы function-call и т.п.) и **проверку готового разговорного текста**. Для свободного L2 исключить циклы полной перегенерации из-за формата, отрицаний, чисел, метаречи, «клише» и речевых привычек. Anti-Cliché оставить как существующее диагностическое наблюдение, если включён настройкой.
2. `apply_numeric_guard()` и его финальное повторное применение после freshness: не подменять содержательные предложения готового L2, не вставлять `verified_phrase` вместо него и не превращать нормальный разговор в молчание. Научить L2 получать точные числа/источники **до генерации**; структурированная проверка измерений/итогов статистики — самостоятельная data-stage responsibility.
3. `_run_evidence_egress_guard()` / `_evidence_rewrite()` / `drop_claim_sentence()`: выполнять позднее решение BGS-02 — **убрать из обычного финального ответа** автоматические повторы с дополнительным поиском и смысловое удаление предложений. До Writer выполняется поиск и сбор фактов; после Writer — диагностика, но не содержательная цензура. Фактчек по-прежнему должен различать подтверждение, опровержение и нехватку данных и не придумывать источники.
4. `public_speech_guard`: выполнить BGS-03 — не вырезать естественные формулировки вроде «по моим наблюдениям», «по инструкции», «я программа» по словарям и не делать ради них новую генерацию; оставить узкую очистку настоящих служебных артефактов. Разница между служебным token и естественной речью должна быть формальной, не очередной псевдо-семантической эвристикой.
5. `format_retry`: Telegram может принимать текст и реальные списки. Не пересоздавать весь ответ ради списков или таблиц; при необходимости **рендерить существующее содержимое** безопасным plain/HTML renderer. Специализированные машинные схемы валидировать **до** передачи итогов Writer; пользовательский специально запрошенный формат — часть задачи и плана Writer.
6. Сохранять явно настроенный владельцем deterministic стиль, но не добавлять второй LLM для исправления косметики. Если форматная реализация не поддерживается Telegram, по возможности преобразовать разметку без изменения текста или честно использовать plain fallback.

### R-05. Отличать дубль текста от дубля доставки

1. Проверить и удалить `duplicate_guard_retry` и любые аналогичные обходы, когда завершённый авторский текст переписывается только потому, что он совпал или похож на прошлое **другое** сообщение бота. Это скрытый reroll и противоречит цели.
2. Сохранить защиту от **повторной доставки одного логического действия**: `correlation_id`, `tg_message_id`, durable idempotency key, retry-send semantics, логические send reservations и SendRecheck. Повторная обработка одного входящего события не должна отправлять дубль.
3. Если бот слишком часто повторяется, лечить причину в L1/контексте/истории собственных ответов и разрешённых владельцем настройках, **не** постфактум редактировать одинаковый текст. Для двух разных пользовательских вопросов одинаковый ответ может быть законным.
4. Не делать «вместо duplicate guard — случайную вставку, jitter-фразу, синонимайзер или отказ отвечать».

### R-06. Структурированные выходы, исключения и пограничные случаи

- **Фактчек:** Claim Extraction/verification, источники, evidence mapping, verdict и review **до** конечного пользовательского вывода остаются. Конечная речевая стадия из валидированной фактологической структуры — это один final Writer, не «второе перефразирование». Сохранить PVR-FC, в том числе право выдавать `insufficient_evidence` и технические ошибки. Не удалять схему ради общего лозунга.
- **Саммари / глубокий сон / память / GraphRAG:** создание конспекта и аналитических выводов — отдельные продукты/данные, а не переписывание готового Telegram-ответа. Сохранять их семантические стадии и валидаторы структурированных данных.
- **Мемы:** `выжимка → генерация прикола → генерация изображения` — этапы создания разных объектов; менять их данным поручением запрещено. Не трогать текст действующих мем-промптов и версионирование.
- **Явный запрос «перепиши»/«переведи»:** L2 является автором запрошенной трансформации. Нужный оригинал — source data, а не скрытый конкурентный бот-черновик. Допустимо показать результат и обоснованное ограничение, без второго автоматического редактора.
- **Специальные терминальные инструменты:** если зарегистрированное действие формирует законченный deterministic report, файл, изображение или доставляет медиа, оно может завершить ход без текстового L2; не отправлять второе пояснение после успешно отправленной картинки. Если инструмент вернул только evidence, нужен L2.
- **Ответы без инструментов:** L1 → L2; без forced synthetic Stage-1.
- **Молчание/реакция:** не добавлять L2 ради форматирования, доставка согласно принятому решению.
- **Временные данные:** ChatClock по выбранному часовому поясу приходит в L1/L2 и фактчек/саммари по их требованиям; не замещать живое время выдуманным.
- **Точные цитаты, ссылки, числа, авторство:** не переписывать дословные отрывки и явные доказательства после Writer; при сборе evidence сохранять provenance и ссылку на конкретное сообщение/URL.
- **HTML/RichMessage:** renderer может экранировать/разбивать текст, но не сокращать/пересказывать; fallback Rich → plain использует тот же смысловой payload.

## 3. Принцип отказов и продолжения — без скрытого возвращения legacy

1. **Provider failure до получения завершённого L2:** разрешён bounded retry по документированной политике провайдера или fallback-модель на том же смысловом пакете/плане (с capacity-aware перепаковкой, защищающей исходный вопрос, роль, время и обязательные доказательства). Не трактовать это как второй этап авторства; фиксировать фактический provider и причину.
2. **`finish_reason=length`:** продолжать **тот же логический ответ** с явной границей накопленных токенов; не выдавать обрезок и не запускать независимого «переписчика для завершения». Защититься от дублирования и противоречивых продолжений. При невозможности полного продолжения — честное техническое состояние, не фиктивный успех.
3. **Tool failure:** L2 получает статус ошибки инструмента и доступные факты; может честно ответить без выдуманной проверки. Если обязательного evidence нет — явно обозначить неполноту, а не публиковать сырой tool dump как ответ и не регенерировать незаметно старым маршрутом.
4. **Invalid machine JSON/schema:** исправление схемы возможно только в подготовительном машинном слое, в пределах реального бюджета, с видимыми retry reason. Не запускать свободный Verbalizer для преобразования неверного JSON в «человеческий ответ» после финального Writer.
5. **Invalid Telegram formatting:** сериализовать тот же текст в plain, не отправлять как HTML с ошибкой и не просить LLM переписать.
6. **Empty final:** не заменять произвольной фразой «к сожалению...», не доставлять фальшивые verified claims. Использовать существующий законный error/silence/clarification outcome в соответствии с trigger и планом; фиксировать причину.
7. **Cancel/restart:** одно и то же logical send не исполняется дважды; сохранённые результаты инструментов и контекст не теряются. Не возобновлять с устаревшим текстом, если изменился target/reply в инициативе.

## 4. Границы удаляемого и сохраняемого

| Компонент/механизм | Решение | Причина |
|---|---|---|
| `SYSTEM2_DIRECT_ENABLED` как gateway к старому double-writer | Удалить из нового активного call graph; конфиг мигрировать/депрецировать | Может вернуть двойной маршрут при OFF L1 |
| `_synthesize_direct_answer` как «tool final → JSON → prose» | Удалить достижимую цепочку; сохранить только реально нужную нормализацию facts pre-L2 | Лишнее авторство |
| `FormContract(source_text=draft_text)` для свободного chat | Удалить consumer, далее удалить dead code при отсутствии других целей | Лексическое сравнение различных авторских текстов |
| `verbalize_validated` global free-form retry | Удалить поведенческие reroll-ветки; сохранить machine-contract validation отдельно при необходимости | Переписывает живой текст |
| `apply_numeric_guard` с заменой/обнулением финала | Убрать постфактум смысловую правку free-form; расчёты/claims проверять до L2 | Может потерять корректное содержание |
| `evidence_policy.guard_egress` content rewrite/drop | Применить решение BGS-02; оставить provenance и диагностику | Содержимое удаляется после L2 |
| `public_speech_guard` словарь режущих фраз | Применить BGS-03; сохранить machine-artifact cleanup | Речевой цензор |
| `duplicate_guard_retry` по совпадению текстов | Удалить reroll, оставить durable idempotency | Не идентично защите от повторной отправки |
| Anti-Cliché | Оставить диагностикой/владельческими настройками | Не должен влиять на free-form generation после факта |
| `style_policy` owner-selected `no_quotes/no_emoji/no_trailing_period` и др. | Оставить ровно один прозрачный deterministic pass | Явный выбор владельца |
| L1 planning, Web Search, `ToolEvidence`, memory, ChatClock | Сохранить/развить по UR-A | Это интеллект и вход, не rewrite |
| Factcheck judgement/citations, Summary, meme pipeline | Сохранить специализированные стадии | Разные реальные задачи |
| SSRF/URL guard, secret redaction, tool permissions, output marker-strip, Telegram escaping, send idempotency | Сохранить | Техническая целостность |

Зафиксировать Conflict Resolution Matrix с точными ссылками на заменённые пункты. **Не отправлять владельцу инженерные вопросы.**

## 6. Админка, API, конфигурация и миграция

1. Удаление/изменение поведения **обязательно** должно быть отражено в UI выбранного чата, глобальных настройках, API, схеме конфигурации, диагностике, документации параметров и тестах. Никаких «мертвых» переключателей, которые обещают новую перегенерацию, но ничего не делают.
2. Параметры старого пути (`SYSTEM2_DIRECT_ENABLED`, старые form/validator retries, duplicate-content regeneration и др.) классифицировать в конкретный migration manifest: `removed`, `retained_as_technical`, `retained_for_explicit_transform`, `retained_for_specialized_pipe`, `deprecated_compat`. Не удалять по совпадению слова `guard`: некоторые нужны для структурных протоколов.
3. Если удалённому ключу соответствует **сохранённое пользовательское значение**, оставить его в историческом/миграционном журнале и ревизиях, но вывести из активного UI. Не модифицировать текущие тексты ручных промптов, их factory baseline или прежние версии; не создавать новую активную редакцию от простого изменения кода.
4. Конфиг-совместимость старого БД: читать устаревший ключ без ошибки и **игнорировать** его для нового маршрута; не позволять `false`, `0` или null по старому ключу активировать двойную архитектуру. Нужные migration scripts должны быть обратимыми и не затрагивать данные памяти/эмбеддинги.
5. Отобразить понятную **диагностику одного ответа**: L1 → tools → Writer → фактические разрешённые deterministic ops → delivery; причина fallback, extra attempts, фактический модуль, количество вызовов LLM и источник временного контекста. Ни одна UI-метка «прошла проверка» не должна скрывать произошедший retry/замену текста.
6. Пользовательские формулировки: «Единое написание ответа»; «Сохранение исходного смысла при явном редактировании» (если доступно); «Техническая очистка сообщений» — не навязывать новую панель с десятками машинных флагов. Отражать только реально управляемое.
7. На мобильном и десктопе существующие редакторы промптов и история версий должны оставаться работоспособны. Не «улучшать» старый UI глобальным редизайном в рамках этой коррекции; это отдельный PVR.

## 7. Наблюдаемость и доказуемая неизменность авторского текста

Для каждого логического хода по `correlation_id` собрать доступные в существующем tracing/oversight (с доступом по правам):

- trigger `direct|initiative|factcheck|...`, source message/author, active chat, ChatClock/version;
- L1 action/plan ID; tool invocations, их источники, ошибки и coverage;
- L2 request manifest: контекстные блоки и ревизии owner prompts, fallback provider/model; **без обязательного хранения полного приватного payload в открытом логе**;
- L2 completion: `finish_reason`, завершённость, length/usage и устойчивый digest raw final;
- ordered list доставочных операций (`reasoning_marker_strip`, `HTML_escape`, `owner_style_punctuation`, `Telegram_chunk`, etc.) и итоговый digest;
- `semantic_rewrite_count=0` для обычного ответа; LLM-calls classified as planning/tool/final/continuation/provider_retry (не «всё под stage2»);
- delivery outcome, исходный идемпотентный ключ, фактические Telegram IDs;
- при расхождении raw_final ↔ delivered — точная разрешённая причина, без нового LLM-судьи.

**Критично:** скрытые `retry` или `return draft` после неудачной проверки не должны считаться обычным успехом. Для защиты приватности логов достаточно digest/метаданных и доступа к существующему Inspector, без новой БД сырых переписок. Существующий журнал `mca_bot_outputs` не очищать и не отключать.

## 8. Проверки: не только зелёные unit-тесты

### R-07. Статическое покрытие всех путей

Строго установить reachability в HEAD: direct with tool/no tool, L1 enabled/disabled, legacy flags, initiative, fallback, error return, deep_research/HTML, direct images, tool-delivered media, factcheck, summary, scheduled messages, user-requested rewrite. Для каждого пути показать: **сколько независимых финальных авторских генераций** и где происходит реальная постобработка.

Не ограничиваться grep/поиском имени: нужно проверить import graph, call sites, toggles, реальные конфигурации/рантайм и возможные поздние `rewrite` функции. В интеграционном отчёте достаточно таблицы с конкретными call-site и route outcome; отдельный бесконечный аудит не создавать.

### R-08. Обязательные тест-кейсы

| Сценарий | Ожидаемое поведение |
|---|---|
| Прямой ответ без инструментов | L1 → один L2; после L2 ни LLM-rewrite, ни смыслового удаления |
| Прямой ответ с поиском/историей | Tools/Evidence → один L2; нет промежуточного свободного авторского черновика, который затем литературно пересказывает другая модель |
| Инициатива с поиском | L1 может решить `silent/react/reply`; при `reply` использует общий L2, evidence и не постперегенерирует |
| L1 или старый `SYSTEM2_DIRECT_ENABLED=false` | Старый флаг не может активировать двойной Writer; технологическая деградация не меняет архитектуру |
| Совпавший текст двух разных входящих событий | Два независимых правильных ответа могут совпасть; не запускается `duplicate_guard_retry`; настоящая повторная доставка одного события заблокирована |
| «Вася не писал» / «Вася писал» / «Вася никогда не писал» / «Вася не отказывался» | После L2 смысл не меняется ни regex, ни переписчиком, ни fallback-черновиком |
| «Не без таланта», «никогда», «неделя», «небо», «немного» | Не возникает ретрая free-form ответа по лексическому правилу |
| Несколько отрицаний / мат / сарказм / намеренно странная речь | Никаких post-L2 semantic rewrites ради «приличия» или «формы» |
| Не подтверждённый внешний факт при временно недоступном поиске | Никакого автоматического удаления целого предложения / post-L2 переписывания; L2 получает честный статус evidence до генерации |
| Stats/измерения/калькуляции | В writer входят проверенные MetricResult; post-L2 не вставляет чужую фразу и не скрывает невозможность данных |
| Explicit rewrite/translate | Работает как задача; при исходном формальном контракте не меняет protected facts; нет скрытого post-editor |
| Factcheck многосоставного утверждения | Сохраняет sources→claims→verdict, не превращает `insufficient_evidence` в `mixed`; нет литературного переписывания готового вердикта |
| Невалидная схема tool-call | Исправляется на machine stage или честно завершается, не вторым текстовым писателем |
| `finish_reason=length` | Продолжение этого ответа, нет оборванного слова и нет нового варианта с нуля |
| Модель fallback/отвал провайдера | Retry/fallback в той же стадии и на семантически эквивалентном контексте с защищёнными блоками; нет перехода на legacy System2 |
| HTML, RichMessage и plain fallback | Один смысловой текст, без потерь/сжатия и без LLM-reroll |
| Длинная Telegram-реплика | Chunking без обрыва или перестановки, авторство/ссылки сохранены |
| Настройки `no_quotes/no_emoji` | Единственный предсказуемый механический pass, protected spans не сломаны |
| Отправленная картинка/файл | Не появляется второй текст от Writer; сохраняются record/send/idempotency |
| Смерть/перезапуск процесса после отправки | Нет повторной отправки этого логического ответа |

**Каждый негативный сценарий проверять с учётом реальных конфигов и feature gates**, а не только мокированного идеального happy path.

### R-09. Доказательство на реальном LLM и поставке

- Минимальный реальный прогон Direct без tools, Direct с поиском, Initiative с reply, fallback модели, длинный ответ, explicit rewrite и factcheck (при доступных ключах); дополнить controlled fixtures для отказов, если провайдер недоступен.
- В trace показать `LLM calls`: L1/Tool planning, **единственная финальная смысловая генерация**, допустимые continuation/transport retry с отдельными reason, `semantic_rewrite_count=0`, реальные операции postprocess.
- Reviewer обязан сравнить `L2 raw_final` с фактически отправленным Telegram payload по сохранённым/извлечённым частям (не только хеши без возможности расследования), подтвердить, что ни одна скрытая функция не переписывает/не удаляет смысл.
- Убедиться, что не сломались точность из источников, история собственных ответов, reply/время, продуктовые форматы, память/эмбеддинги и речевые настройки.
- Нельзя считать DONE по прохождению unit tests, внешнему документу, изменению boolean flag, комментарию `paraphrase disabled` или непроверенному деплою.

## 10. Definition of Done — все пункты обязательны

- [ ] Каждый активный Direct/Initiative `reply` имеет одну финальную логическую Writer-стадию, все tools/evidence до неё; `silent/react` не вызывают L2.
- [ ] Нет достижимого System2 `tool-final → JSON → Verbalizer` как второго автора; при сбоях/флагах нет скрытого возврата в него.
- [ ] Нет post-L2 LLM reroll для free-form из-за form/numeric/metatext/format/evidence/duplicate/freshness/style/cliché; нет автоматического смыслового drop/replace.
- [ ] Честный provider fallback и continuation по length сохранены, не маскируют unfinished outputs.
- [ ] Idempotency Telegram-доставки, специальные продукты, пользовательские правила речи и source provenance сохранены.
- [ ] Обновлены API/админка/конфиги, нет dead controls, старые настройки не реактивируют legacy.
- [ ] Все сохранённые пользовательские промпты и их история/заводские версии не изменены, память и эмбеддинги не пересозданы.
- [ ] Conflict Resolution Matrix + route matrix по актуальной ветке приложены к человеческому отчёту.
- [ ] Независимый Reviewer подтвердил реальный call graph и выходные payload; DevOps выполнил релиз и прод-проверку; итог записан в durable state.

**Финальное указание:** цель — *удаление источника скрытых искажений*, а не замена старого костыля новым. Не усиливать лексические списки, не вводить новый LLM-постпроцессор, не уходить в чистый аудит. Если техническая развилка возникла внутри текущего планирования, принять инженерное решение и зафиксировать его в PR без переноса на владельца.
