# ЧАСТЬ II. ЗАЩИТА ДАННЫХ ПЕРЕД УДАЛЕНИЕМ СТАРОЙ УСТАНОВКИ

## 8. Проверить независимую резервную копию

После очистки старого VPS прежний вариант отката перестанет существовать.

Поэтому перед удалением необходимо подтвердить наличие **актуальной независимой копии production state**.

Использовать уже созданную резервную копию, если она включает состояние после переключения и её целостность доказана.

Иначе выполнить согласованное резервное копирование нового production штатными безопасными средствами.

В резерве должны присутствовать:

- SQLite с полной актуальной историей и памятью.
- PostgreSQL.
- Настройки и секреты приложения.
- Медиа.
- Данные, без которых невозможно восстановить локальный Telegram Bot API.
- Важные пользовательские файлы.
- Сведения о версии и конфигурации сервисов.

Предпочтительное место хранения — независимое от обоих VPS хранилище под контролем владельца.

Копия на другом каталоге того же диска не считается полноценным независимым резервом.

Проверить контрольные суммы, структуру архивов и возможность чтения/восстановления.

Не публиковать содержимое резервных копий и секреты.

**Если надёжную независимую копию создать или проверить невозможно — не удалять последнюю сохранную копию на старом сервере. Сообщить конкретный блокер владельцу.**

Не создавать повторные большие копии, если уже существует подходящий проверенный backup.

Остановить и удалить исключительно контейнеры, принадлежащие Adminbot.

- Массовое удаление Docker volumes.

- Удаление всех контейнеров сервера.
- Удаление всех Docker images.

Из общего конфигурационного файла удалить только подтверждённый блок виртуального хоста Adminbot.

После изменения проверить синтаксис конфигурации и работоспособность оставшихся сайтов.

Не удалять общие сертификатные хранилища.

Не выполнять глобальный `certbot delete` или очистку всего TLS storage.

Не выключать Xray, прокси или VPN, если они используются другими проектами.

Не очищать общий credential store целиком.

Не трогать глобальные настройки Git, не относящиеся к проекту.

- Очистку всей истории команд пользователя.
- Перезапись общих системных журналов.
- Удаление общих файлов мониторинга.
- Массовое удаление временных каталогов системы.

Исторические записи о запуске приложения могут оставаться в системных логах, резервных копиях хостера и иных общих источниках.

Не заявлять о гарантированном физическом удалении всех следов с SSD.

**Требуемый результат — отсутствие рабочей установки, данных и собственных файлов Adminbot в пределах разрешённой области, а не повреждение общей операционной системы ради удаления исторических метаданных.**

# ЧАСТЬ V. ПРОВЕРКА ОЧИСТКИ

## 19. Проверить старый сервер

После удаления провести одну итоговую read-only сверку.

Подтвердить:

- Процесс Adminbot отсутствует.
- Systemd unit Adminbot отсутствует или не может быть запущен из старой конфигурации.
- Bot-specific timers отключены и удалены.
- Контейнеры Adminbot отсутствуют.
- Принадлежащие ему Docker volumes удалены.
- Каталог приложения и его приватные файлы отсутствуют.
- Отдельные базы Adminbot отсутствуют.
- Старые media и embeddings отсутствуют.
- Bot-specific cron entries отсутствуют.
- Reverse proxy не содержит маршрута старой установки.
- Git working tree и выделенные deploy credentials отсутствуют.
- Не осталось фоновых процессов, продолжающих использовать Telegram Bot Token.

При этом проверить:

- SSH-доступ старого сервера сохранён.
- ОС загружаема и работает.
- Системные службы не повреждены.
- Общие сервисы не остановлены.
- Чужие пользовательские данные не изменены.
- Docker daemon и общая инфраструктура сохранились там, где нужны другим проектам.

Не проводить повторное удаление методом угадывания.

Если обнаружен объект с неоднозначной принадлежностью — не трогать его.

## 20. Проверить новый production ещё раз

После очистки старого сервера:

- Новый Adminbot работает.
- Git HEAD соответствует принятому релизу.
- Домен и HTTPS доступны.
- SQLite и PostgreSQL доступны.
- Счётчик сообщений продолжает соответствовать актуальному состоянию.
- Память и настройки доступны.
- Новых критических исключений нет.
- Telegram polling работает.
- Нет зависимости от сервиса, случайно удалённого со старого VPS.
- Все будущие команды деплоя указывают на `192.255.209.205`.

Отдельно проверить, не оставалось ли скрытых запросов к старому IP в настройках нового production.

Если такие зависимости найдены, исправить их на новом сервере без изменения данных.

# ЧАСТЬ VI. ОТЧЁТ И ЗАВЕРШЕНИЕ

## 21. Формат финального отчёта

Отчёт должен быть кратким, понятным владельцу, без переписывания тысяч внутренних требований.

Сообщить:

**Новый production**

- Версия и Git SHA.
- Состояние сервиса.
- Проверка обеих баз.
- Актуальное число сообщений.
- Состояние памяти.
- Состояние админки и TLS.
- Причины 3 ошибок и 17 предупреждений, если счётчики подтвердились.
- Наличие либо отсутствие подтверждённых регрессий.

**Резервная копия**

- Где хранится.
- Когда создана.
- Что включает.
- Как подтверждена целостность.
- Есть ли ограничения восстановления.

Не выводить секреты или содержимое пользовательских данных.

**Очистка старого VPS**

- Какие каталоги удалены.
- Какие systemd units удалены.
- Какие Docker-контейнеры и volumes удалены.
- Что сделано с PostgreSQL.
- Что сделано с Git и выделенными ключами.
- Что удалено из конфигурации веб-сервера.
- Сколько дискового пространства освобождено.
- Что намеренно оставлено, поскольку принадлежит ОС, хостеру или другим пользователям.

**Итог**

- Новый VPS является единственным production.
- Старый VPS не содержит работающей установки Adminbot.
- Чужие данные и общие сервисы не затронуты.
- Будущие деплои направлены на новый VPS.
- Оставшиеся неопределённые пункты перечислены честно.

## 22. Workflow

Поручить DevOps выполнить основную работу.

Reviewer должен проверить:

- Итоговые результаты нового production.
- Наличие независимой резервной копии.
- Правильность области удаления.
- Отсутствие повреждения чужих сервисов.
- Реальное отсутствие старых процессов и данных Adminbot.

Architect привлекать только при реальной неопределённости принадлежности ресурсов или архитектурной зависимости.

Не создавать дополнительный эпик.

Не переписывать `plans/current_task.md`.

Не возобновлять прежнюю задачу миграции с нуля.

Не ждать нескольких суток ради запуска Sleep или Summary.

Не создавать искусственные обязательные ручные проверки.

Если обнаружен критический дефект нового production или невозможно подтвердить сохранность данных, не начинать необратимое удаление до устранения конкретной проблемы.

После успешной очистки восстановить обычную работу Orchestrator с оставшимися задачами.
