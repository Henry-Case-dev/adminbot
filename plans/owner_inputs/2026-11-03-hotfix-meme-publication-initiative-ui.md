# HOTFIX-MEME-PUBLICATION-AND-INITIATIVE-UI — обязательное корректирующее ТЗ

**Дата:** 2026-11-03  
**Редакция:** v2 — уточнена семантика пустого поля «Потолок длины» и её отображение.  
**Назначение:** исправить ложные отмены готовых мемов и перекомпоновать экран «Модули → Инициатива».  
**Статус:** implementation, не аудит/эскиз/предложение.  
**Приоритет:** P0 — публикация мемов; P1 — интерфейс.  
**Область:** текущая действующая кодовая база (HEAD и продакшен-ревизия). Скриншоты содержат функции, которых нет в доступном публичном `master`, поэтому агентам необходимо работать с актуальным рабочим деревом, а не слепо привязывать решение к устаревшим путям.

## 0. Неизменяемые контракты

- Текстовая инициатива и мемы имеют независимые тайминги, условия, квоты, собственные вероятностные решения/журнал. Они совместно предотвращают столкновение публикаций в одном чате через существующий ledger/delivery-контур; не создавать второго планировщика, второго RandomSource или общего глобального lock между чатами.
- Мем-пайплайн: выжимка → генерация прикола через действующие Core/Identity/Expression/Humor → изображение → публикация. Ручной `/meme` только для админа; обход автоматических кулдаунов/квот, но не прав, доступности backend и технической безопасной доставки.
- Успешный мем отправляется **только изображением**, без caption, промпта или второго текстового сообщения. Сохраняются права, журнал и аналитика.
- UI-рефакторинг этой конкретной страницы разрешён и прямо запрошен владельцем. Ранее установленное ограничение визуальной неизменности относится к отдельному треку оптимизации производительности; оно не должно блокировать это целевое изменение. Сохранить стиль админки (тёмная тема, стекло, цвета и фон) и **всю функциональность**. Не копировать нынешнюю неудачную компоновку.

## 1. P0: `publication_stale` не должен браковать готовый мем только из-за нового сообщения

### 1.1. Зафиксированный инцидент

В Telegram бот сообщает: «Переписка в чате изменилась за время генерации — мем не отправлен, попробуйте ещё раз». Админка показывает `publication_stale`. Это означает, что публикационная проверка забраковала результат, а не обязательно что генерация изображения сломалась. На снимках видны прохождения стадий «выжимка», «генерация прикола», «генерация картинки» и публикационные исходы; точные условия текущего guard определить по одному скриншоту невозможно.

### 1.2. Требуемая семантика

1. При начале генерации зафиксировать снапшот источника (чат, идентификатор запроса или инициативного события, исходные сообщения / их версии, причина/цель, run/correlation ID). Это **входной материал конкретного мема**, а не требование, чтобы чат оставался неподвижным.
2. Появление новых сообщений, реакции, несвязанные реплики, смена `latest_message_id`, движение общего watermark и обычный рост переписки **не являются основанием для `publication_stale`**.
3. Ручной `/meme`: после авторизованного запроса и успешной генерации доставлять итоговый мем, даже если за время работы появились другие сообщения или сменилась тема. При необходимости отправлять reply к инициирующему `/meme` с сохранённым `message_id`, если это поддерживается действующим транспортом. Не требовать повторного `/meme` и не расходовать ещё одну генерацию только из-за обновившегося чата.
4. Автоматический мем: перед отправкой остаются обязательные проверки полномочий, фактической активности модуля, технической пригодности output, существующего dedup/ledger и координации публикаций с текстовой инициативой. Если по **содержательной причине** мем действительно нельзя публиковать (например, отменённая инициатива, удалённый/недопустимый исходный материал, смена прав или явное выключение модуля) — отдельный точный reason code с реальными фактами, а не общая `publication_stale` из-за любого изменения чата.
5. Для автоматического конфликта публикации с другим механизмом — дождаться разрешённого слота/переоценить возможность доставки в рамках существующего durable-механизма либо отменить по реальному терминальному условию. Не терять уже сгенерированную картинку и не генерировать её второй раз только потому, что кто-то написал сообщение или сработал второй механизм.
6. Если результат уже доставлен, повторное выполнение того же run не отправляет дубль; если статус доставки неизвестен, применять существующий idempotency/ledger-протокол. При рестарте не терять подтверждённые стадии/готовый артефакт.
7. Ошибка пользователю должна соответствовать факту. `publication_stale` — только для доказанной утраты релевантности/валидности, а не для сравнения двух timestamp/message ID. Не сообщать об отмене после успешной доставки. Для автоматического кандидата не публиковать в чат объясняющую ошибку без прямого запроса; причина фиксируется в админке. Для ручного `/meme` — короткая правдивая ошибка только при фактической невозможности выполнить действие.
8. Не добавлять LLM-судью на каждый send, новые жёсткие временные лимиты, искусственные бюджеты, фиксированные имена/чаты/фразы и postgen-перегенерацию по стилю. Смысловое решение использовать из уже существующего intent/context; техническую сверку оставить детерминированной по явным инвариантам.

### 1.3. События и измерения

Раздельно показывать: `source_snapshot`, `digest_ready`, `joke_ready`, `image_ready`, `publication_requested`, `publication_deferred_conflict`, `publication_sent`, `publication_cancelled` / `publication_failed`, `delivery_unknown`; для каждого — время, run ID, режим manual/automatic, источник, причина, ссылка на предыдущий этап и факт реальной доставки (без секретов/сырых персональных данных в публичных логах). Не путать «генерация прошла» и «отправка прошла».

## 1.4. P0.5: пустой «Потолок длины итогового промпта» = автоматический режим, не ошибка и не скрытый лимит

Дополнительный пользовательский кейс: при незаполненном поле «Потолок длины» интерфейс/расчёт не должен выдавать некорректные значения, ломать этап прикола или отправки либо неявно применять прежний потолок выжимки. На форме уже заявлена семантика «пусто — авто» — выполнить её во всём тракте UI → API → PG → runtime → диагностика, в том числе после перезапуска.

1. **Три разных состояния:** пустое/`null`/пробелы = `auto` (наследование/автоматическая оценка); явно заданное положительное целое = фиксированный потолок итогового image prompt; некорректный ввод (отрицательное число, десятичное, нечисловой текст) = ошибка формы с точным сообщением. Не трактовать пустоту как `0`, `NaN`, `undefined`, «запретить всё» либо автоматически как `800`. Если для исторической конфигурации `0` означает `auto`, обработать его совместимость отдельно, не стирать значение при сохранении.
2. **Источник auto:** использовать реальные ограничения выбранной модели/провайдера, если они документированы и доступны через существующие capabilities/config. Если в runtime нет достоверного числового ограничения image prompt, **не изобретать своё**: не накладывать искусственный лимит символов, сохранять естественное требование «короткий прикол» и соблюдать только фактические границы модели/провайдера.
3. **Расчёт при фиксированном потолке:** доступная длина прикола = `L - длина реально отрендеренного image prompt без прикола`. Включать все постоянные части, разделители, пробелы и скрытую служебную обвязку, которая действительно отправится провайдеру. Использовать существующий production renderer; не выводить число только по длине видимого textarea, если payload отличается. Если места нет, показать конкретную конфигурационную ошибку **до LLM/image-generation**, не генерировать испорченную шутку и не обрезать её «по живому».
4. **Генерация прикола:** для известного эффективного лимита передать вычисленное положительное ограничение LLM на этапе прикола и проверить реальный image prompt перед отправкой. Для `auto` без подтверждённого предела не подставлять фиктивное `максимум 0/800` и не обрезать выжимку. Если провайдер отклоняет длину, отразить ошибку точным reason code и настройку, но не маскировать её под `publication_stale`.
5. **UI:** при пустом поле показывать `Автоматически`, источник эффективного значения, а ниже — либо реальное вычисленное число, либо честное `Числовой предел не задан / определяет провайдер`; бюджет прикола не может показывать отрицательное число, ноль из-за `null`, `NaN` или мнимые 771/800. Смена режима фиксированный→auto→фиксированный немедленно обновляет предпросмотр и после сохранения/перезагрузки остаётся согласованной с backend. Глобальное значение и чатовый override не должны путаться; снятие override возвращает наследование, а не сохраняет локальный «0».
6. **Не связывать с publication freshness:** этот кейс касается конфигурации промпта, а не изменений чата. Ошибка потолка, если она реальна, должна остановить конвейер до дорогостоящей генерации с понятной диагностикой; новые сообщения во время генерации не превращаются из-за неё в `publication_stale`.

## 2. P1: точная перекомпоновка экрана «Модули → Инициатива»

### 2.1. Проблемы по скриншотам

- Огромная страница: «Обзор / Основные настройки / Лимиты» сверху, внутри настроек заодно отдельный блок мемов, затем длинная история повторяющихся «Рассмотрено / фактов этапа нет» и весь технический манифест речевой сборки.
- Одни и те же сведения показаны несколько раз, но понять «что происходит сейчас, когда следующий тик, почему не отправило» можно только после длительной прокрутки.
- Поля промптов спрятаны внизу под журналом; нет нормального соседства с собственно мем-пайплайном, сохранением и предпросмотром.
- На узком экране текущий подход умножает количество прокрутки; числовые диагностические данные конкурируют с управляющими элементами.

### 2.2. Новая навигация: фиксированная структура, без дублирования

**Верхняя панель страницы (одна):** `Инициатива` + область действия `Глобально / [название чата]` + итоговое состояние + ссылка в каталог модуля. Ниже навигация по 5 вкладкам:

1. **Обзор** — оперативное состояние двух механизмов и ближайшие действия.
2. **Текстовая инициатива** — настройки, условия, тайминги, квоты, история решений именно текста.
3. **Мемы** — весь отдельный мем-конвейер, настройки, два редактора промптов, статистика, пробный запуск и последняя попытка.
4. **Публикации** — общий журнал доставок/конфликтов с фильтрами текст/мем/manual/auto, без копирования тех же строк в других вкладках.
5. **Диагностика** — раскрываемые технические трассы, метаданные prompt manifest, source/decision/rng/recheck, конкретные reason codes и экспорт. Только тут полный debug.

**Никакого** второго блока «Мемы» внутри «Текстовой инициативы». «Лимиты» не отдельная разрозненная вкладка: индивидуальные лимиты рядом с соответствующим механизмом. Общие системные рубильники в компактном блоке управления/каталоге с ссылкой, без копирования управляющего тумблера.

### 2.3. Детальное содержимое вкладок

**Обзор:**
- Два равнозначных столбца/карточки: «Текстовая инициатива» и «Мемы». Для каждого отдельный effective ON/OFF, право управления, последняя проверка и её исход, следующая запланированная проверка, последняя реальная публикация, собственный кулдаун, дневная квота, конкретная текущая причина ожидания (если есть), кнопка открыть настройки соответствующего механизма.
- Небольшая общая полоса «Координация отправки» — свободно/ожидает другой механизм/отложено, реальное событие и оставшаяся пауза. Состояния только из API, не симуляция отсчёта.
- Последние 3–5 действительно значимых событий с переходом в «Публикации», без полного журнала и без многократного дублирования.
- Никакой огромной пустой рабочей области или стеклянного блока с одной строчкой на всю ширину.

**Текстовая инициатива:**
- Одна секция «Включение и условия»; одна «Частота и лимиты» с единицами измерения; одна «Последнее решение» с объяснимой причиной (включая вероятность и реальный источник случайности, если draw был). Нет мем-настроек.
- Настройки разделить на поля с понятными заголовками и текстом помощи, а не сырые флаги в главном потоке.

**Мемы:**
- Верхняя строка: собственный ON/OFF + effective source; текущий статус, сегодняшняя квота, последний готовый/опубликованный результат и причина недавнего пропуска.
- **Две смысловые колонки:** слева «Триггер и расписание» (окно сообщений, минимум сообщений, индивидуальный cooldown, квота, тихие часы, модель выжимки, текущие условия), справа «Создание мема» (pipeline из 4 шагов: выжимка → прикол → картинка → публикация). На мобильном: эти секции вертикально.
- Сразу под pipeline: **два редактируемых промпта рядом на десктопе** — «Промпт прикола» и «Шаблон изображения». Каждый имеет заголовок, источник inherited/global/chat, редактор, «Отменить изменения», «Вернуть наследование», общую кнопку сохранения с индикацией реального результата. Не прятать поля под логами и не создавать двух разных save endpoints.
- Под полями: вычисляемый бюджет итогового image prompt: потолок, длина шаблона, доступно для прикола, фактическая длина последней сборки; показать источник настроек и состояние при ошибке/переполнении. Лимит не применять к выжимке.
- Ниже компактная панель «Последняя попытка»: четыре статуса по этапам + timestamp, точный reason code + русское объяснение, факт реальной публикации, ссылка «Подробная трасса» в «Диагностику»; не показывать 12 повторов «Рассмотрено / фактов этапа нет». 
- Диагностический ручной `/meme` обозначить как админскую команду и показать, когда он использовался, но не маскировать его под авто-триггер.

**Публикации:**
- Фильтры: период, чат, тип, режим, outcome, reason. Каждая логическая попытка одной строкой: время, механизм, стадия, причина, исход, доставка. По клику details: точная цепочка событий, в том числе «генерация успешна, отправка отменена».
- Пагинация/виртуализация для длинных журналов. Пустые детали не превращать в отдельные строки; показывать `нет данных для этой стадии` только там, где оно действительно уместно.

**Диагностика:**
- Технический инспектор конкретной попытки, а не сплошная простыня. Группы «условия», «случайное решение», «контекст/снапшот», «этапы генерации», «речевые слои Core/Expression/Humor», «send/recheck», «события и ошибки».
- Для Core/Prompt показать ревизию и status инъекции, по раскрытию — безопасный текст итогового prompt manifest в админском доступе. Сжатый view по умолчанию (Core вошёл, юмор вошёл, прочее пропущено с причиной); полные hashes/IDs только при раскрытии.
- Убирать дублирование идентичной секции в двух местах страницы. Любой индикатор `вошёл/пропущен` должен отражать реально отправленный payload, а не только сборку до вызова провайдера.

### 2.4. Строгие правила UI/UX

- Desktop >= 1200 px: ограничить читаемую ширину контента, 2 колонки в контекстных местах, равные отступы, компактные карточки; на 768–1199 px автоматически переходить к одной колонке там, где тесно.
- Mobile <= 767 px: навигация вкладками с горизонтальной прокруткой, **без горизонтальной прокрутки всей страницы**; все поля, логические статусы и кнопки доступны; редакторы шириной viewport, sticky save bar при dirty form — только если не перекрывает клавиатуру Telegram WebView.
- На любых ширинах не строить бесконечные вертикальные колонки с пустыми «фактами этапа нет». Массивы событий показывать по актуальному состоянию и раскрытию, с пагинацией.
- Контраст текста, удобные hit areas, фокус-клавиатура, стабильность при выборе чата и навигации; все изменения сохраняются по текущей модели глобального наследования и per-chat override.
- Все существующие параметры, диагностические данные и функции сохраняются и имеют новую очевидную точку доступа. Не удалять техническую диагностику — перенести и упорядочить. Не менять стеклянный дизайн, цветовую систему, анимации/фон ради работы по UI.
- Не загружать тяжёлые трассы и длинные журналы при первом открытии «Обзора»: по вкладкам и требованию. Не создавать duplicate polling для каждого виджета и не ломать параллельный трек оптимизации.

## 3. Проверки для Reviewer — обязательны

1. `/meme` запускается, во время генерации в чат приходит 1, 10 и 50 новых сообщений: готовый мем публикуется один раз, без `publication_stale` по одному лишь изменению окна.
2. Автоматический мем с теми же новыми сообщениями публикуется, если остальные действующие условия выполнены, либо откладывается из-за настоящей коллизии по ledger с точной причиной — не бракуется автоматически по `latest_message_id`.
3. Смена прав, отключение модуля, недоступность image backend, реальное изменение жизненного цикла intent проверяются отдельно; один универсальный reason code на все случаи запрещён.
4. Два фоновых воркера и рестарт: не отправляют дубль, не теряют успешный готовый артефакт, не расходуют квоту дважды за одну попытку. Ручной `/meme` имеет приоритет в конфликте с автоматическим механизмом, но не обходит RBAC/безопасность.
5. Нет caption/текста после успешного мема; по ручному запуску фактический сбой описывается честно.
6. В UI каждый параметр из старой страницы имеет новое место и продолжает работать; оба промпта редактируются/наследуются/сохраняются; глобальный и чатовый контексты корректны.
7. Проверить desktop 1536x960, мобильные 390x844 и 360x740, Telegram WebView и браузер: без переполнения, без перекрытия сохранения клавиатурой, со стабильной навигацией.
8. Последний run: общая карточка показывает правильный исход; подробная трасса отличает image_ready от publication_sent, почему `publication_stale` стало недопустимым для новых сообщений.
9. Снимки экрана и e2e-сценарии до/после, отсутствие регрессий других модулей, интерактивное тестирование Reviewer, а не только unit-pass Builder.
10. Пустое поле потолка при глобальной настройке и чатовых переопределениях, после сохранения/перезапуска и при разных image backend: автоматический режим работает, не возникает `0`/`NaN`/подставного `800`, доступный бюджет честно обозначен; при явном фиксированном значении проверена длина **фактического** prompt payload и учтены обвязка/разделители. Проверить некорректный ввод, переполненный шаблон, снятие override и переходы auto↔fixed.

## 4. Порядок исполнения и сдачи

1. P0 публикации мемов — исправить, тестировать, независимо принять и выкатить как срочный пакет, **не удерживать релиз до полного UI-рефакторинга**.
2. P1 UI — после устранения P0 либо параллельно на независимых файлах, отдельная приёмка responsive и поведения.
3. Отчёты включают реальный SHA/версию, подтверждённые сценарии, причины отклонений, ссылки на события/скриншоты. Код и успешное состояние production важнее объяснительного отчёта.
4. Никакого хардкода под этот конкретный чат, пользователей, слова или тексты; никаких заглушек/фальшивых счётчиков, новых рабочих агентов, искусственных таймаутов или дублирующей инфраструктуры.
