# 0. Статус, назначение и границы поручения

Настоящий документ является окончательной версией дополнения FACTCHECK-REQUEST-INTEGRITY к SMART-EXECUTION-RELIABILITY-01.

Предыдущие варианты данного дополнения не были переданы в разработку. Использовать только настоящую редакцию.

Не создавать отдельный конкурирующий эпик, второй фактчек, параллельный поисковый движок или отдельную систему бюджетов.

Настоящее поручение решает три конкретные проблемы:

1. Фактчек может потерять содержательное уточнение пользователя и проверить другой предмет.
2. Фактчек использует чрезмерно жёсткие собственные ограничения поиска, которые не соответствуют возможностям современной LLM и могут работать даже при отключённых бюджетах.
3. Из-за преждевременного завершения исследования бот получает недостаточные доказательства и формирует ответ, который не соответствует поставленному вопросу.

**Цель задачи — восстановить надёжность уже существующего фактчека, а не изменить его назначение, основной пользовательский сценарий или характер ответа.**

Обычный фактчек должен остаться обычным фактчеком.

Не превращать обработку уточнения в обязательный предварительный этап определения фокуса для каждого вызова.

Не превращать увеличение доступных ресурсов в обязательное увеличение количества поисковых запросов, длительности проверки или размера ответа.

Не начинать новое исследование вариантов архитектуры. Продуктовые решения зафиксированы владельцем в настоящем документе.

# 1. Production evidence и исходный дефект

## 1.1. Пользовательский сценарий

14.11.2026, около 00:32–00:34 UTC+12.

В групповом чате обсуждалась древняя традиция женского обрезания, её распространение и влияние внешних держав.

Пользователь ответил на сообщение другого участника:

«Фактчек, бот, реально есть страны с этой традицией на которые не влияли такие гегемоны как Франция/Великобритания/Германия/США?»

Исходное сообщение содержало утверждения о древности традиции, её распространении и влиянии США.

Фактический запрос пользователя содержал конкретный вопрос о существовании стран, удовлетворяющих указанным условиям.

Фактическое поведение:

- бот не сразу сформировал ответ;
- затем сообщил: «Проверка не завершена: истёк лимит времени»;
- основной текст ответа разбирал древность традиции и происхождение практики;
- значительная часть ответа была посвящена контрфактическому тезису о том, исчезла бы традиция без внешнего влияния;
- конкретный вопрос пользователя о странах не получил прямого ответа;
- единственным отображённым источником оказался Facebook с неполноценной выдержкой.

Нужно исправить именно общий механизм, который допускает подобное поведение.

Не создавать предметные правила для данной исторической темы, не добавлять специальные поисковые запросы для неё и не подгонять фактчек под ожидаемый конкретный политический вывод.

Этот случай используется как регрессия универсального механизма.

## 1.2. Подтверждённые участки реализации

В проверенном `release/2.58.199` обнаружены следующие участки.

`handlers/factcheck.py::_parse_trigger()`:

- корректно выделяет исходное сообщение;
- сохраняет текст после команды в `user_hint`.

`services/factcheck_suitability.py::evaluate_suitability()`:

- может сформировать отдельный `ClaimItem` из `user_hint`.

`services/factcheck_orchestrator.py`:

- передаёт в `build_retrieval_plan()` `external_claim`, построенный вокруг исходной публикации.

`services/factcheck_planner.py`:

- `_build_plan_inner()` при наличии `claim_text` использует его как основной текст исследования;
- `_claim_units()` может отбрасывать выбранные части, если они не входят дословно в исходный `claim_text`.

`services/temporal_factcheck.py`:

- temporal envelope может сохранять исходную публикацию как основной проверяемый тезис;
- `decompose_claim()` декомпозирует `envelope.claim_text`.

`services/factcheck_service.py`:

- temporal analyst получает `env.claim_text`;
- validator и verbalizer также используют данные temporal envelope и claim coverage.

Таким образом, обнаружена реальная архитектурная возможность рассогласования:

пользовательский вопрос → suitability decision → исходный claim → retrieval → verdict.

Обработчик может сохранить вопрос, suitability — даже распознать его, но последующие стадии способны вернуться к исходному сообщению.

Перед реализацией сверить актуальный deployed SHA и действующий runtime-путь.

Если production trace конкретного запроса сохранён, использовать его для подтверждения фактической причинной цепочки. Если trace недоступен, воспроизвести сценарий через существующий контролируемый контур.

Не утверждать, что конкретная причина данного production-сбоя полностью доказана только статическим просмотром старой ветки.

# 2. ГЛАВНЫЙ ИНВАРИАНТ: обычный фактчек не меняется

Этот раздел имеет обязательную силу для всех последующих изменений.

## 2.1. Обычная команда без уточнения

Существующий сценарий:

пользователь отвечает на сообщение словом «фактчек».

Это полноценный, завершённый и явный запрос на проверку соответствующего материала.

Отсутствие текста после команды НЕ означает:

- отсутствие пользовательского намерения;
- отсутствие предмета проверки;
- отсутствие запроса;
- необходимость попросить уточнение;
- невозможность составить retrieval plan;
- необходимость определить дополнительный исследовательский фокус.

В этом сценарии предмет проверки определяется исходным материалом и существующим контекстом.

Должны сохраниться:

- обычная проверка текста;
- проверка нескольких существенных утверждений в сообщении;
- проверка цитат;
- проверка пересланных публикаций;
- проверка сообщений с изображениями;
- проверка альбомов;
- проверка транскрибированного материала;
- разрешение неполного тезиса через существующий reply/context механизм.

Не добавлять дополнительный обязательный LLM-вызов только для того, чтобы модель подтвердила очевидное намерение обычной команды «фактчек».

Существующий обработчик команды продолжает запускать фактчек.

## 2.2. Исходное сообщение без самостоятельного тезиса

Сохранить уже утверждённое поведение EVOL-REPLY-CONTEXT-INTEGRITY-01.

Если сообщение, на которое ответили, содержит короткую оценку, неполную отсылку, указание на ранее обсуждавшееся событие или иной зависимый от контекста материал, использовать существующие:

- canonical reply context;
- структурные связи сообщений;
- связанный материал;
- историю разговора;
- разрешённый семантический контекст;
- существующее мультимодальное evidence.

Не превращать отсутствие самостоятельного утверждения в первой строке сообщения в автоматическое «нечего проверять».

При этом не подменять явно выбранную пользователем цель произвольным соседним сообщением.

Если после использования доступного контекста цель действительно остаётся неопределимой, допустимо короткое содержательное уточнение.

Не требовать уточнения просто потому, что после команды нет текста.

## 2.3. Не расширять обычную проверку без основания

Новый механизм не должен превращать обычный фактчек в бесконечный тематический ресёрч.

Если сообщение содержит несколько существенных проверяемых утверждений, проверить их в необходимом объёме.

Не добавлять к исходной проверке:

- случайные утверждения из соседних сообщений;
- всю историю спора;
- биографию участников;
- не относящиеся к запросу контрфактические рассуждения;
- дополнительные исторические и политические темы только потому, что они связаны с обсуждением.

Контекст помогает понять предмет проверки. Он не означает, что необходимо проверять весь контекст.

Не заменять исходный тезис тем, который модели кажется более интересным, удобным или простым для исследования.

# 3. Дополнительный сценарий: фактчек с пользовательским уточнением

## 3.1. Основной контракт

Пользователь может после существующей команды «фактчек» добавить любой содержательный текст.

Этот текст является частью запроса пользователя.

Исходный материал остаётся источником и контекстом, а уточнение определяет, как пользователь хочет использовать этот материал.

**Отсутствие уточнения — нормальный основной сценарий. Наличие уточнения — дополнительная возможность управлять проверкой.**

Не превращать эту дополнительную возможность в обязательную часть интерфейса или архитектуры каждого фактчека.

## 3.2. Различать три сущности

В рамках существующего factcheck request необходимо различать:

1. Исходный материал — то, на что ссылается пользователь.
2. Пользовательский запрос — содержимое команды и возможного уточнения.
3. Предмет проверки — то, что в действительности необходимо проверить с учётом запроса и материала.

Эти сущности не должны сливаться в одну строку с потерей происхождения и смысла.

Исходный материал необходимо сохранить без изменения.

Пользовательский запрос необходимо сохранить без содержательной обрезки.

Предмет проверки может совпадать с исходным материалом, быть его частью либо представлять связанную с ним самостоятельную проверку.

Использовать существующие структуры FactcheckRequest, ClaimPublication, ClaimItem, SuitabilityDecision, TemporalClaimEnvelope и связанные контракты.

Не создавать для этого параллельную систему FactcheckRequestV3 или второй набор сущностей.

Допускается минимальное расширение действующих структур, если текущий контракт действительно не способен различить исходный материал и предмет проверки.

## 3.3. Семантика уточнений

Текст после команды может иметь разные функции.

Модель должна понимать его смысл в контексте.

### Сценарий A. Уточнение отсутствует

Проверяется исходный материал.

### Сценарий B. Уточнение не изменяет предмет

Пользователь выражает сомнение, просит внимательно проверить сообщение или добавляет разговорный комментарий.

Проверяется исходный материал. Дополнительный текст учитывается только в применимой части.

Не превращать разговорную фразу в самостоятельный новый тезис.

### Сценарий C. Уточнение сужает проверку

Пользователь интересуется конкретной частью сообщения, числом, датой, цитатой или утверждением.

Приоритет получает указанная часть.

Остальной материал используется для правильного понимания и необходимых оговорок, но не становится обязательным самостоятельным предметом полного фактчека.

### Сценарий D. Уточнение добавляет условие

Пользователь добавляет временной период, географическое ограничение, сравнение, дополнительную сущность или иную существенную характеристику.

Предмет проверки сохраняет связь с исходным материалом и включает добавленное условие.

Не игнорировать условие только потому, что его нет в исходном сообщении.

### Сценарий E. Уточнение задаёт самостоятельный вопрос

Пользователь просит установить конкретный факт, используя исходный материал как контекст.

Проверяется этот вопрос.

Не требовать, чтобы пользовательский вопрос дословно содержался в исходной публикации.

Не подменять самостоятельный вопрос проверкой всех утверждений исходной публикации.

### Сценарий F. Уточнение расширяет проверку

Пользователь просит проверить исходный тезис и дополнительно связанное утверждение или сопоставить несколько фактов.

Проверяется необходимый расширенный предмет.

Не отбрасывать исходный тезис, если по смыслу пользователь просил проверить и его тоже.

### Сценарий G. Уточнение относится к форме ответа

Пользователь просит объяснить результат короче, подробнее, показать основания либо выделить конкретную часть вывода.

Это не обязательно изменение предмета проверки.

Не запускать лишние поисковые исследования только из-за пожелания к форме результата.

## 3.4. Не превращать категории в хардкод

Сценарии A–G являются описанием пользовательского поведения и приёмочных случаев.

Они НЕ являются перечнем обязательных лексических правил и НЕ требуют отдельного программного классификатора.

Не создавать:

- regex по словам;
- списки синонимов;
- словари запросов;
- соответствия фраз типам уточнений;
- наборы обязательных терминов;
- ручные таблицы выбора фокуса;
- новые команды;
- отдельный prompt-router с фиксированными фразами.

Смысл определяется существующей LLM-архитектурой.

Детерминированный код исполняет уже установленное решение и сохраняет структурные связи.

# 4. Исправить рассогласование стадий фактчека

## 4.1. Один согласованный предмет проверки

После определения предмета проверки все последующие стадии должны работать с одним согласованным содержательным контрактом.

Включая:

- suitability/admission;
- temporal envelope;
- декомпозицию;
- retrieval plan;
- поисковые запросы;
- claim coverage;
- evidence attribution;
- analyst;
- validator;
- verbalizer;
- renderer;
- cache/reuse.

Запрещено:

- принять уточнение на входе, но потерять его в retrieval plan;
- выбрать пользовательский вопрос, но исследовать только исходное сообщение;
- искать доказательства одного тезиса, а формировать вердикт по другому;
- сформировать вердикт по уточнению, но вернуть в финальном ответе исходный спор;
- незаметно заменить объект проверки в fallback-ветке.

## 4.2. Исправить конфликт claim_text и claim_items

В существующем `_claim_units()` проверка вида:

`if claim_thesis and text.lower() not in claim_low: continue`

не должна отбрасывать содержательно корректный предмет проверки только потому, что он не является дословным фрагментом исходной публикации.

При этом не удалять проверки provenance и согласованности без замены необходимого контракта.

Нужно различать:

- дословную часть исходного утверждения;
- корректную семантическую формулировку этого утверждения;
- условие, добавленное пользователем;
- самостоятельный пользовательский вопрос;
- новый тезис, который модель ошибочно приписала исходному автору.

Не решать проблему простым отключением всех проверок принадлежности тезиса.

Новый пользовательский вопрос не требуется доказывать как часть исходной цитаты. Но его связь с запросом и контекстом должна сохраняться.

Если planner получил уже установленный корректный предмет проверки, он не должен повторно выбирать исходное сообщение в качестве более приоритетного текста.

## 4.3. Temporal envelope

Сохранить действующий временной контракт фактчека.

Исходная дата публикации, дата репоста, дата сообщения и время проверки не должны смешиваться.

Если уточнение меняет временной период проверки, это изменение должно дойти до temporal analyst и всех последующих стадий.

Не переносить дату исходной публикации на самостоятельный вопрос пользователя автоматически.

Не разрушать существующие режимы contextual и knowable_at_time.

Не добавлять специальные регулярки для распознавания новых пользовательских формулировок времени.

Технический парсинг уже установленных дат и структурных параметров разрешён.

## 4.4. Авторство и provenance

Сохранить раздельно:

- автора исходного сообщения;
- автора запроса;
- исходный материал;
- выбранную часть материала;
- сформулированный пользователем вопрос;
- источники каждого проверяемого утверждения.

Не приписывать автору исходной публикации слова, которых он не говорил.

Если пользователь добавил собственный вопрос, этот вопрос не становится цитатой исходного автора.

Не терять Telegram message ID, reply-связи, forward provenance, принадлежность к альбому, идентификаторы media assets и analysis revision.

Не изменять сохранённый текст исходной истории ради передачи нового claim в модель.

## 4.5. Кэш

Повторная проверка одного исходного сообщения с разными уточнениями может требовать разных результатов.

Исправить действующий cache identity, чтобы он учитывал:

- фактический предмет проверки;
- существенные условия;
- временной режим;
- применимый исходный материал;
- необходимые ревизии исходного evidence.

Не возвращать готовый verdict другого вопроса только потому, что оба запроса ссылаются на один Telegram message ID.

При этом не запрещать переиспользование уже прочитанного подходящего источника.

Source cache и verdict cache выполняют разные задачи. Повторное использование доказательства допустимо, если оно действительно относится к новому предмету
