## 1. Цель и неоспоримые решения владельца

Создать единый **гибридный AntiCliche**: он получает знания о русскоязычных речевых штампах из нескольких разрешённых источников; при фоновом обновлении LLM извлекает и обобщает эти знания; банк содержит как конкретные нежелательные фразы, так и семейства поведения; действующий Prompt Composer до генерации добавляет Writer небольшой релевантный фрагмент стилевых указаний. Все стадии и их результаты наглядно видны администратору. Никаких клише-перегенераций.

**Инварианты, которые нельзя пересмотреть ради удобства реализации:**

1. **AntiCliche НИКОГДА не вызывает дополнительную генерацию, reject, best-of, fallback, scrub, автоматическое вырезание фразы или задержку исходящего Telegram-сообщения.** Это относится к старым regex, ручным спискам, динамическим правилам, новым семействам, pinned и к множественным совпадениям. AntiCliche работает **до** ответа и пассивно **после** ответа.
2. Не отключать независимые проверки фактов, numerical claims, form guard, метатекста и формата доставки. Их назначение не менять, но отделить от стиля: `plain_no_tables` относится к совместимости Telegram, а не к анти-клише. Не переназывать стилистический отказ в `format`/`metatext`, чтобы скрытно оставить retry.
3. **Без LLM на каждом сообщении ради AntiCliche:** ни классификатора ситуации, ни проверки готового ответа, ни «писателя негативного промпта» на горячем пути. Только уже существующий вызов Writer, дешёвый детерминированный выбор из готового опубликованного snapshot.
4. Одна подсистема `anticliche_worker` + существующий PG cache/согласованное расширение + текущий Prompt Composer. Не создавать второй сборщик, второй Validator Loop, второй Writer, независимую «базу клише» или дублирующую страницу конфигурации.
5. AntiCliche — **подраздел «Речь и характер»**, а не невнятная карточка в конце «Библиотеки промптов». **Тумблер один.** Существующий основной характер, русский язык, мат/сленг, owner overrides, жанры, фактчек, типографика имеют приоритет над чужими советами из источников.
6. Гибрид: `pinned_literal` для конкретных фраз (пример «классика жанра»), `family_guidance` для обобщённых речевых привычек, `bank_only` для кандидатов и пассивных наблюдений. Все в **одном каноническом каталоге**. Никогда не помещать весь банк в каждый Writer prompt.
7. **Источники и анализ должны быть наблюдаемы без гадания:** честный статус каждого источника и отдельный статус кэша; пошаговая история фактического чтения документов, реальных вызовов модели, извлечённых кандидатов, группировки, одобрения, публикации; итоговые правила **читаемым текстом**; отдельно — **точный дополнительный AntiCliche-блок, реально передаваемый Writer**, а не его теоретический шаблон.
8. На ошибках внешних сервисов/LLM хранить и использовать последнюю работоспособную опубликованную версию. Не показывать ложные «0 правил / версия 0», если действующий набор существует. Никогда не называть успешным полный анализ, если случился только HTTP 200 или LLM вернула мусор.
9. Не обходить Wikimedia robot policy браузерным User-Agent, прокси или сменой IP. Разрешённые источники независимы: ошибка Wikipedia не препятствует обновлению из других.
10. **Никакой фиктивной аналитики:** если исторических событий/токенов/статусов нет, писать «Нет данных», «Не измерялось», «Не проверялось», а не 0, зелёный индикатор или выдуманную длительность. Каждое отображаемое число иметь вычислимый источник.

## 2. Архитектура: один поток данных, два выходных представления

```text
[Разрешённые внешние репозитории/материалы]   [Manual / legacy / локальные сигналы]
                       \                       /
                  существующий AntiClicheWorker
                      |     |      |
              независимые source adapters
                      |     |      |
          Fetch + source status + revision/ETag
                       |
          Canonical Parse + content checks
                       |
             LLM analysis (фоновый)
     extract → group → propose guidance → validate
                       |
          Staging: candidate / review / quarantine
                       |
             Atomic PublishedSnapshot
                 /                 \
        PromptHintView          ObservationView
              |                       |
         current Composer        read-only telemetry
              |                       |
         existing Writer         НИКАКИХ retry/reject
              |
         Telegram delivery
```

**Принцип:** внешний источник не является автором системных инструкций Writer. Он сообщает доказательства/примеры, LLM предлагает структурированные кандидаты, валидатор/политика их оценивает, а **одобренная локальная инструкция** компилируется в prompt. Все промежуточные артефакты связаны идентификаторами.

### 2.1. Канонические объекты (логическая модель; архитектор адаптирует к существующему PG)

- `Source` — конфигурация разрешённого источника: стабильный ID, тип/URL/пути, доступность по политике, лицензия/атрибуция, включённость, revisions/ETag, source-specific retry policy.
- `SourceCheck` — одна **реальная** попытка проверки: `check_id`, `source_id`, время, HTTP result, сетевой/политический статус, удалённый revision, unchanged/changed, сколько документов и байт доступны, ошибок/предупреждений. Поле `health_status` не смешивать с доступностью кэша.
- `RefreshRun` — один запуск refresh (плановый/ручной): `run_id`, начало/конец, инициатор, итоги по источникам, status всего процесса, `active_version_before/after`.
- `DocumentProcessing` — конкретный документ/файл/ревизия, его parser status, число реально разобранных символов/сегментов, checksum; не хранить полный текст чужих статей без прав.
- `ModelAnalysis` — вызов/пакет к модели: model reference и **разрешённое** действующее подключение, caller/step, входных документов и фрагментов, статус модели, JSON validity, число предложений, использование токенов/latency **если реально доступно**, ошибка; отдельный `analysis_id`/`call_id`.
- `ClicheCandidate` — предложение: normalized phrase или family/variant, scope/genre, source provenance, evidence reference, status, reason codes, test outcomes, owner decisions; **не инструкция**.
- `RuleFamily` — каноническая речевая привычка, варианты, guard/исключения, утверждённая короткая инструкция Writer, источники и оценка уверенности.
- `OwnerLiteral` — конкретная вручную закреплённая фраза/owner override с областью действия, приоритетом, датой и автором настройки; никогда автоматически не «очищать».
- `PublishedSnapshot` — атомарная согласованная версия банка с `rule_set_version`, `compiler_version`, `checksum`, `published_at`, `source_revisions`, `publisher`, `parent_version`, `status`, `effective_rule_count`.
- `PromptCompileTrace` — диагностическая запись применения опубликованного snapshot: применённый scope/route, выбранные family IDs/pinned IDs, причины, effective hash, количество токенов/символов и статус; **без пользовательского текста и секретов** в общем event log.
- `AuditEvent` — именованное неизменяемое событие действий и переходов состояния с `run_id`, `source_id`, `analysis_id`, `snapshot_version`, кодом результата и безопасным описанием.

**Хранение:** это логические сущности, **не требование создать девять новых таблиц**. Изучить текущий `anticliche_cache`, event ledger, versioned prompt registry, существующие hot-config/PG schemas. Допустимо добавить минимально необходимые поля или связанные события в имеющийся журнал. Источник истины один, опубликованная версия атомарна, все snapshot-данные переживают рестарт и деплой. UI не должен требовать обходить частные логи по SSH для восстановления истории.

### 2.2. Разделить виды здоровья

Не смешивать в одном `ok/error` четыре разных вопроса:

1. **Source reachability** — можно ли легально и технически получить данные из источника прямо по последней настоящей проверке?
2. **Source content readiness** — удалось ли проверить и разобрать полезные документы на определённой ревизии?
3. **Analysis readiness** — LLM на самом деле отработала нужный batch и дала валидные, проверенные предложения?
4. **Runtime effectiveness** — есть ли опубликованный рабочий snapshot и действующий Prompt Compiler, даже если все источники сейчас недоступны?

Возможен абсолютно честный экран: `Источник Wikipedia — заблокирован (403); Последний анализ GitHub A — завершён; Активный snapshot v18 — работает; Новое обновление — частичный успех`. Нельзя перекрасить всё в зелёный по состоянию кэша и нельзя показать полную недоступность AntiCliche по одному 403.

### 3.2. Транспорт и статус источника

У `Source` есть отдельно `enabled` и **результат последней реальной проверки**. Статусы в UI/контракте:

| Внутренний status | Показываем пользователю | Смысл | Цвет/иконка |
|---|---|---|---|
| `available` | «Доступен» | Последний разрешённый fetch и проверка ожидаемого формата/путей успешны | зелёная точка |
| `unchanged` | «Доступен · без изменений» | Сверка revision/ETag реальна, данные не изменились | зелёная точка |
| `rate_limited` | «Ограничение запросов (429)» | Запрос отклонён лимитом; next retry по `Retry-After` | янтарная |
| `policy_blocked` | «Доступ запрещён политикой (403)» | Конкретная robot-policy/forbidden блокировка; не обходить | красная |
| `auth_failed` | «Нет доступа / авторизация» | 401/403 авторизации, не путать с robots | красная |
| `network_error` | «Ошибка соединения» | timeout/DNS/TLS/сетевой сбой | красная |
| `parse_error` | «Источник доступен, формат не распознан» | HTTP успешен, но документы не разобраны | янтарная/красная согласно пригодности |
| `missing` | «Документ не найден» | 404/отсутствующий путь | красная |
| `unchecked` | «Ещё не проверялся» | Ни одной реальной проверки | серая |
| `disabled` | «Выключен» | Конфигурационно исключён из обновлений | серая |

`available` **не означает**, что LLM обработала материал или что появились новые правила. `unchanged` — успешная проверка без обязательного вызова модели. `stale` — **отдельная пометка свежести**, а не замена транспортного результата. При истечении принятого интервала надпись «Последняя проверка N дней назад» + «Данные устарели» (порог из существующей политики refresh; явный конфиг/объяснение); не выдавать старую зелёную проверку за доступность прямо сейчас.

Не вводить «Live»/«онлайн» без фактического probe. Бейдж `Доступен` трактуется как **последняя проверка**, timestamp рядом всегда виден; через ручную проверку обновляется новое timestamp. `Last fetched` и `Last succeeded analysis` отдельно. HTTP 200 при пустом/битом файле — не «готов к анализу».

### 3.3. Правила обновления

- Сохранить один scheduler existing `anticliche_worker`, per-source независимые исполнения, bounded параллелизм, текущий budget provider; не делать бесконечный loop из-за одного сбоя.
- `If-None-Match`/revision SHA/checksum: если документ неизменён, не делать LLM-анализ повторно, не увеличивать published version и не объявлять «новые правила».
- 403 robot policy → `policy_blocked`, запрет частых автоматических попыток; ручное действие «Проверить доступ» допустимо по явному намерению и в рамках разрешённых политик; не автоматический storm.
- 429 → уважать `Retry-After` с ограниченным backoff/jitter; 5xx/timeout → bounded backoff; 404/смена структуры → источник degraded, остальные живы.
- Любая ошибка источника/модели/PG оставляет published snapshot и owner overrides; ошибка записана и видна.
- «Проверить доступ» ≠ «Загрузить и проанализировать» ≠ «Опубликовать». Отдельные операции и надписи, никакого одного неясного «Обновить» с неизвестной семантикой.
- Автообновление не трогает исходящие сообщения и не ждёт 7 дней после **осознанного** ручного запуска/починки конфигурации.

## 4. Что именно делает LLM и как доказать, что она это сделала

### 4.1. Честная формулировка архитектуры

**Не говорить в UI, что «LLM ходила по сайтам», если HTTP выполнял worker.** Подписи должны различать: «Worker проверил источники и скачал документы» → «Модель проанализировала полученный материал» → «Система проверила результаты» → «Опубликован итоговый набор». Если разрешённая интеграция действительно даёт модели tool access, это также должно отражаться фактическими событиями, но отдельный web-browsing агент **не нужен**.

### 4.2. Пошаговый конвейер одного `RefreshRun`

**Stage A — SOURCE_FETCH:** каждый включённый источник проверяется отдельно; пишется перечень реально доступных документов, SHA, bytes/chars, `source_check_id`, время/HTTP status. Ошибки не затирают прошлые данные.

**Stage B — DOCUMENT_PARSE:** детерминированный парсер для известных Markdown/JSON файлов отделяет пример клише от пояснения/исключения, сохраняет краткие evidence ссылки/offsets; не выполнять инструкции из чужого Markdown. Неясная разметка → `parse_error`/quarantine, а не фальшивые кандидаты.

**Stage C — MODEL_ANALYSIS:** выбранная через действующий реестр модель *фоново* получает только допустимые, bounded текстовые фрагменты и жёсткую схему structured output. Задачи: извлечение **реально встречающихся русских** выражений с evidence; семантическая группировка; краткие русские guidance; контекстные исключения; оценка уверенности и пометка неуверенности. Не переводить английское клише механически и не принимать модельный вымысел за источник.

**Stage D — QUALITY_GATE:** детерминированные проверки нормализации, дублей, provenance, источников, лицензий и корректной JSON-схемы; проверка разрешённых шаблонов, отсутствия model hallucination, конфликтов с owner style; leave-unchanged fixtures. Слабые/неоднозначные кандидаты → `candidate`/`quarantined`, не «approved» по одному уверенному описанию модели.

**Stage E — REVIEW/APPROVAL:** при действующем утверждённом auto-policy допускается автоматическая публикация только низкорисковых обобщённых guidance после прохождения quality gate и fixtures; вручную pinned literal активируется **только действием владельца**. При отсутствии подтверждённой политики auto-approve оставлять в staging. Интерфейс показывает `auto policy`/`owner`, конкретный reason и test verdict.

**Stage F — ATOMIC_PUBLISH:** после полного gate выпускается новый versioned snapshot, его PromptHintView и ObservationView проходят синхронную совместимую сборку. Публиковать только новый полезный delta, `0 новых` корректный `no_change`, не `failed`. При сбое — предыдущая версия и дата остаются.

**Stage G — RUNTIME:** Compiler выбирает готовые hints из snapshot; Writer генерирует один раз относительно AntiCliche; пассивное наблюдение за собственным исходящим текстом может записать агрегированные совпадения без влияния на отправку.

### 4.3. Состояния всего run

`queued` → `fetching` → `parsing` → `analyzing` → `validating` → `awaiting_review` (если нужен ручной review) → `publishing` → terminal: `published`, `no_change`, `partial_success`, `failed`, `cancelled`.

Не показывать 100% по прохождению fetch, если анализ ещё не был. Если все данные собраны, но awaiting review, UI пишет «Анализ завершён, публикация ожидает утверждения»; активный snapshot не меняется. Если один источник упал, а другой дал валидный delta, terminal `partial_success` с опубликованным изменением; проблема видна, а не спрятана. Если входной материал не изменился, этап LLM = `skipped_unchanged`, **не** `completed`.

### 4.4. Метрики, обязательные для реальной прозрачности

По каждому run и по каждому источнику сохранять/выводить раздельно:

- начало/конец, duration; trigger = schedule/manual/reanalysis; кто запустил (ID/role), из какого snapshot;
- реальные source checks: всего/OK/unchanged/blocked/error; количество проверенных файлов, реально скачанных/разобранных; версия/ETag/commit, doc checksum, source URLs;
- число документов/фрагментов, **переданных модели**, реально обработанные символы и сегменты; не путать fetched и analyzed;
- выбранная **конкретная** модель/provider reference, effective inherit/override, response status, число попыток, успех/ошибки JSON, контекст/лимиты без раскрытия secrets;
- количество вызовов LLM, input/output/total tokens и примерная стоимость **только если provider вернул usage/есть достоверная цена**; если нет — `Не измерялось`, а не `0`;
- extracted candidates, lexical phrases, proposed families, merged duplicates, quarantined, rejected (по reason), approved (auto/manual), pinned unchanged, published delta, total active approved;
- `prompt hints compiled` и `pinned included` по профилям **для версии**, effective bytes/tokens, compiler SHA; отдельное «сколько кандидатов предложено» и «сколько реально попало в Writer»;
- сколько правил привязано к каждому исходному документу и на основании какой ревизии; сколько из предложенных LLM элементов потеряно на gate с объяснимым кодом;
- summary of errors с точными source/model/stage, retry/cooldown time; last successful end-to-end analysis, last published version;
- AntiCliche-triggered retries = **0 (инвариант)**; другие Validator Loop retries — отдельная статистика, не смешивать;
- счётчики пассивных срабатываний (если включена read-only аналитика) и ложноположительных на тестовом корпусе, пометка что **совпадение ≠ вина и не доказывает авторства ИИ**.

**Правило честного 0:** если стадия исполнялась и действительно дала 0, показывать `0`. Если стадия не выполнялась, `Не запускалась`; если поле недоступно — `Нет данных`; если право/лицензия не разрешили читать — `Не обрабатывалось: ограничение доступа`. Никакой вымышленной «точности 98%» или прогрессбара на основании estimates без подписи.

### 4.5. Что значит «анализ завершён»

Только факты позволяют отрисовать фразу **«Модель проанализировала документы и сформировала набор»**, если есть доказанные `ModelAnalysis.completed` (валидный проверенный JSON), документы с reference, результат валидатора и завершённый staging; отдельно указывать, **опубликован ли** этот набор. HTTP 200 проверки подключения модели, `ModelAnalysis.started`, несколько обработанных фрагментов из неполного batch или пустой ответ без проверки не являются таким доказательством.

Детальные reasoning/CoT модели UI **не выдумывает и не требует**. «Полная прозрачность» означает **проверяемые входные/выходные артефакты, решения quality gate, связи и события**, а не доступ к скрытым рассуждениям. Можно показывать согласованное с правами и безопасностью summary действий и полные **структурированные результаты**, созданные моделью.

## 5. Интерфейс: обязательная информационная архитектура, без самодеятельности

### 5.1. Границы и входы (строго)

**Главный дом:** существующий раздел стилевых настроек **«Речь и характер»**. Не создавать новый пункт верхнего левого sidebar, не прятать в «Статус» или «Библиотека промптов». В «Речь и характер» разместить **одну компактную полноценную карточку AntiCliche** между другими настройками речи, а не невидимую строку внизу длинной страницы. Порядок относительно соседей уточнить по текущей компоновке; не переносить соседние модули без UX-причины.

Карточка содержит **ровно**:

- заголовок `Антиклише`, описание `Снижает шаблонность речи заранее, через инструкции Writer. Готовые сообщения не переписывает.`;
- **один основной toggle** `Включено / Выключено` с сохранением через действующий config-механизм, показом состояния сохранения/ошибки;
- компактную строку состояния: `Работает` / `Работает на прошлой версии` / `Нет опубликованных правил` / `Выключено` / `Ошибка компилятора`, вторая строка `Источники: X доступно / Y проблем / Z не проверены` **на основании последних измерений**;
- `Активная версия v…` и время публикации/обновления; если нет — `Не опубликована`;
- явную **ссылку/кнопку `Открыть антиклише`** (одна точка входа на канонический экран, не accordion со всеми настройками).

При OFF выключать дополнительные AntiCliche prompts и пассивное AntiCliche-наблюдение, не стирать банк/версии/логи. Автозагрузку источников по умолчанию приостановить; **ручная** проверка/анализ допустимы с явной подсказкой, что функция выключена и Writer пока не изменится. При ON вернуть прежний подтверждённый snapshot; если snapshot нет, сразу показать `Включено, но нет опубликованных правил`, не фальшивое «Работает».

**Второй вход:** в прежней «ИИ → Библиотека промптов» удаляется прежний standalone редактируемый/загружаемый блок `Анти-клише: динамический список`, который сейчас показывает «ошибка загрузки». При необходимости оставить **одну ссылку** `Настройки антиклише → Речь и характер` плюс read-only упоминание версии (не список, не редактор, не отдельный fetch состояния). Не оставлять legacy fetch, который продолжит рисовать отдельную ошибку загрузки.

**Третий вход и единственное место выбора фоновой модели:** в **«ИИ → Модели и подключения» → «Фоновые задачи»** добавить карточку **`LLM для антиклише (извлечение и анализ)`** в существующую сетку (на текущем скриншоте свободная ячейка справа от «LLM для саморефлексии»). Карточка использует **тот же компонент выбора подключения/модели и сохранения/проверки**, что соседние задачи: не копировать поля `Адрес сервера`, `Модель`, `Ключ` и отдельную логику тайного хранения. Если соседний компонент предполагает копии настроек подключения, Architect должен при необходимости привести только новую карточку к реестровой ссылке; не размножать key/server в AntiCliche. Внутри AntiCliche на вкладке «Обзор» показывать **только read-only `Модель: основная (наследуется)` / выбранная модель + `Изменить в «Модели и подключения»`**, ведущую к этой же карточке. **Двух независимых селекторов модели не создавать**.

**Наследование модели:** `override = null/empty` → использовать основную модель на момент запуска анализа, с записью **реального effective model id/provider** в run. Наследование не означает «не задана модель / ошибка», и не должно показывать «Не настроено». Если override выставлен, использовать существующее подключение модели, включая авторизацию, route/provider и его статус. Если модель недоступна, не потерять LKG. Кнопка `Проверить` должна проверять не только 200, но фактический минимальный structured output JSON через тот же путь, которым работает extraction; показывать результат, не записывать эту проверку как состоявшийся анализ источника.

### 5.2. Одна страница «Антиклише» — состав и порядок

Путь: `ИИ / Речь и характер / Антиклише` (либо точный route существующей навигации, но **один канонический route**). Заголовок `Антиклише`, подзаголовок `Источники, анализ модели, банк речевых шаблонов и инструкции Writer`. Ссылку `← Речь и характер` и текущий status показать в шапке. Не создавать отдельные top-level страницы `Источники` и `Правила`, если их можно реализовать вкладками на **одной** странице.

**Вкладки и фиксированный порядок:**

1. `Обзор`
2. `Источники`
3. `Анализ`
4. `Правила`
5. `Промпт Writer`
6. `Журнал`

Шесть коротких названий. Вкладки не перезагружают весь SPA и не сбрасывают текущий выбранный run/source без причины. URL/back-navigation сохраняют активную вкладку и, если применимо, `run_id`/`source_id`/`rule_id` в допустимой схеме маршрутизации; клавиша Back возвращает к предыдущему смысловому состоянию. Не делать два разных навбара одновременно. На мобильном: горизонтально прокручиваемая строка tabs с явной подсказкой доступности крайних вкладок либо компактное существующее adaptive-tabs решение; не сжимать их до нечитаемых обрубков.

**Шапка всей страницы (общая для всех вкладок):**

- слева заголовок + короткое описание + `Активная версия: v…` или `Нет`;
- справа компактный **эффективный** статус `Вкл/Выкл/Деградация` и дата *последней успешной публикации*;
- глобальная кнопка `Проверить источники` — выполняет только source health checks; `Обновить и проанализировать` — запускает полный source fetch→analysis pipeline с учётом unchanged; эти кнопки нельзя сливать в одну неопределённую. При running не открывать 2-й конфликтующий refresh.
- главного тумблера **на этой странице НЕ дублировать**: состояние read-only и ссылка `Управлять в «Речь и характер»`. Допускается sticky-компактная шапка, если согласуется с текущим UI. Не добавлять незапрошенную сложную global preferences drawer.

### 5.3. Дизайн-параметры по данным скриншотам

Визуально продолжать **текущую тёмную стеклянную тематику** Adminbot: прозрачные матовые/рефракционные панели, сине-фиолетовая атмосфера, аккуратные радиусы, тонкие границы, достаточный контраст. Не заменять приложение на стандартный белый SaaS. Сдержанно использовать акцент для активного действия, состояние ошибок выделять по смыслу, а не для декора. **Нельзя** размещать узкую колонку из 3 карточек, оставляя треть рабочей ширины экрана пустой (проблема видна на первом скриншоте). Заполнить main content сеткой данных, с отступами, не растягивать каждую карточку до бессмысленной ширины.

**Десктоп (эталонная проверка 1536×960):**

- Левая существующая навигация остаётся как есть; новые экраны живут в основном content area.
- Под общим header вкладки одной строкой; после вкладок блок состояния и содержимое. Главный экран **не начинается** с вертикального полотна из одинаковых карточек.
- `Обзор`: первая строка из **4 компактных KPI** на всю полезную ширину (источники / анализ / опубликованные правила / runtime Writer), ниже две смысловые колонки: **слева список источников с индикаторами**, **справа последний анализ с временной шкалой и итогом**. Под ними — широкая читабельная карточка `Текущие инструкции Writer` с реальным текстом и переходом к полной вкладке. Не прятать итог текста в collapsed accordion по умолчанию.
- `Источники`: полноширинная таблица/row grid; при 3–6 источниках видны все без дополнительной горизонтальной прокрутки на 1536 px, история/детали раскрываются по клику на строку в side panel или detail area внутри main, а не по hover-only. Не ставить 6 высоких карточек по 320 px без необходимости.
- `Анализ`: слева (условно 35%) список запусков, справа (65%) подробности выбранного запуска. Если журнал большой, нормальный pagination/virtualization существующего стека; не рендерить бесконечно растущие DOM-деревья. Содержимое выбранного run должно быть видно **без открытия отдельных страниц**.
- `Правила`: строка фильтров и счётчиков сверху, ниже список слева и подробности справа, либо wide table с раскрытием. Редактируемое поле итоговой инструкции достаточно широкое для нескольких строк; provenance/версии не прятать в tooltip.
- `Промпт Writer`: верхняя панель параметров preview, ниже **текст компиляции на всю ширину**, рядом или снизу таблица реально выбранных правил/причин. Не заменять текст превью одной строкой hash/«скопировать».
- `Журнал`: timestamps+codes+stage+run_id в компактном списке с фильтрами, отдельная раскрываемая карточка события; не использовать нечитаемые сырьевые JSON строки как единственный интерфейс.

**Планшет (ориентир 768–1279 или breakpoints действующего приложения):** блоки в 1–2 колонки в зависимости от ширины; длинные таблицы переходят в строки с лейблами. **Мобильный (эталон 390×844):** одна колонка, все важные состояния и действия доступны без hover, нет горизонтального переполнения viewport, sticky-шапки не съедают половину высоты, клавиатура не закрывает Save/Apply, модальные окна и source URLs умеют перенос/scroll, код/текст промпта — выделяемый и прокручивается **внутри** контейнера, без сдвига всей страницы по оси X.

**Стили статусов:** состояние всегда несёт и **текст**, и иконку/цвет (не только цвет). `Доступен` — зелёный, `Проблема/частично` — жёлтый, `Ошибка/блокировка` — красный, `Не проверялся/Отключён` — серый. **Отдельные** индикаторы для транспорта, анализа и published snapshot; нельзя одним зелёным бейджем утверждать, что всё хорошо. Текст ошибки объясняет действие, а не `fetch_error` без контекста. Время показывать в установленной timezone интерфейса, UTC доступен в раскрытии события/логах; не подставлять серверное время под локальное без маркировки.

### 5.4. Вкладка «Обзор» — точный состав

**Ряд KPI (слева направо):**

1. `Источники`: **`N/M доступно`** из M *включённых и реально проверенных сетевых источников*; рядом `K проблем`, `U не проверены` и tooltip с определением. **Не включать отключённые/manual/editorial-only в denominator**. Если последнее измерение старое — `Последняя проверка ... · данные устарели`.
2. `Последний анализ`: `Завершён / Частично / Ошибка / Не запускался / Ожидает утверждения` + точное время завершения и модель, если отработала; сноска `Проверенные документы: X; вызовы модели: Y`.
3. `Активные правила`: `N опубликовано` + `P закреплённых / F семейств` + `Версия vX`; **не** считать candidate как active, а при ошибке refresh не показывать 0 вместо LKG.
4. `Использование в Writer`: `Подключено / Выкл / Используется LKG / Сбой компиляции`, `Последнее применение ...` (если telemetry существует), `Дополнительно в prompt: N правил в выбранном профиле` с пометкой примера/trace; не выдавать snapshot totals за per-message selection.

**Левая большая карточка `Источники`:** сверху `Источники · последняя проверка ...`, ссылка `Все источники`, ниже каждая строка `точка + название + короткий статус`, мелкая строка `последний успех / последний сбой`. По клику открывается **тот же источник на вкладке «Источники»**. Поле источника не зелёное просто потому, что у него есть старая копия.

**Правая большая карточка `Последний запуск анализа`:** header `Run #... · дата · outcome`, **истинная** временная цепочка `Проверено 3 источника → 4 документа разобрано → 2 LLM-вызова → 18 кандидатов → 6 предложений/2 в карантине → опубликовано +3 правила` **только если эти данные есть**. Каждая стадия получает свой terminal status (`done/skipped/error`) и число из ledger. Строка `Что делала модель` даёт модель/сколько документов обработала, на сколько смысловых семей сгруппировала, какие правила предложила. Ссылка `Подробности` открывает run на вкладке «Анализ». При model failure писать `Модель не завершила анализ: причина`, даже если fetch успешен.

**Нижняя широкая карточка `Итоговый набор правил и подсказок`:**

- шапка: `Опубликованная версия vX · дата · N одобренных правил`, раскрываемое provenance summary, `Открыть полный список`, `Посмотреть полный промпт`;
- **обязательно выводить реальный читаемый текст** 3–5 выбранных актуальных family guidance + pinned для **примерного профиля `Обычный чат`**, с явной пометкой `Предпросмотр для профиля «Обычный чат», не универсальный список на каждый ответ`. Не скрывать список за кнопкой без предпросмотра;
- если правил много, `Показать все N утверждённых правил` ведёт в `Правила`, **не подрезать без объяснения**;
- при недоступных источниках, но LKG: заголовок `Работает на последней опубликованной версии vX`; показывать реальный текст этой версии;
- при пустом банке: `Опубликованных правил ещё нет` + `Начать анализ`/`Добавить фразу` по правам, **без заглушек с фиктивными правилами**.

### 5.5. Вкладка «Источники» — конкретные поля и действия

**Верхняя сводка:** `Проверено: N / M; Доступно: A; Ограничения: B; Ошибки: C; Не проверены: U; последний общий check: time` и `Проверить все` (только checks), `Обновить и проанализировать` (full run). Раздельно показывать `Локальные источники` (owner rules) и `Справочные материалы` (ручные ссылки), чтобы их нельзя спутать с активными HTTP адаптерами.

**Каждая строка источника, строго видимые поля:**

1. Текстовый индикатор `Доступен / Запрещён доступ / ...` с цветом и иконкой.
2. `Название`, `Источник / type`, кликабельный исходный URL (показывать только безопасную ссылку без токенов).
3. `Последняя проверка`: точное время (или `Никогда`) + её HTTP/transport code (или `локальный`).
4. `Последний успешный fetch`: дата, revision SHA/ETag и фраза `Содержимое получено`/`Без изменений`; нет успеха — `Нет`.
5. `Последний успешный анализ`: дата или `Не анализировался`, **отдельно** от fetch.
6. `Документов / обработано моделью`: `X / Y` с объяснением denominators (если неизвестно — не показывать фиктивный ноль).
7. `Кандидатов / опубликованных`: `proposed`, `approved contributing`, `newly published` на текущем run или clearly labeled total; не смешивать run и lifetime.
8. `Доступность лицензии`: тип разрешений и attribution; при `not permitted` автоанализ недоступен.
9. `Следующая попытка`: конкретное время/`Приостановлено: 403 policy`/`По расписанию`/`Не запланирована`.
10. `Включён` — существующий разрешённый per-source control; `Проверить` и `Анализировать` разрешены согласно состоянию.

**Клик по строке раскрывает подробности (а не только raw log):** `source_id`, полные configured paths, retrieved commit/ETag/checksum, история минимум последних пригодных проверок, HTTP reason и sanitized truncated error (не тело с секретами), retry policy, raw→parsed document counts, список документов со статусом и короткими evidence IDs, ссылки `Показать связанные правила`/`Открыть run`/`Проверить доступ источника`. Скриншот-ориентированный UI не должен сводить это к маленькой плашке `Ошибка загрузки`.

**Кнопки:**

- `Проверить` делает только разрешённый health check выбранного source и записывает событие. Если source disabled, сначала предложить `Включить` или явно разрешить одноразовую проверку по нажатию; никакого скрытого enable.
- `Обновить данные и проанализировать` создаёт реальный run только для этого source, запускает анализ при changed content; при unchanged пишет `Без изменений; LLM не вызывалась`.
- `Включить/Выключить` влияет только на future polling, не удаляет исторические правила и published snapshot. Не изменяет owner-pinned.
- `Показать правила` открывает вкладку `Правила` с source filter.
- Для `policy_blocked` ручная кнопка не должна делать обход блокировки, а tooltip объясняет причину.

### 5.6. Вкладка «Анализ» — подробная доказуемая история работы модели

**Список запусков:** каждая строка содержит `run_id` (сокращённый), `время`, `trigger`, `status`, `source success/attempted`, `docs parsed/analyzed`, `LLM calls`, `candidates`, `published delta`, `model`. Список фильтруется `Все / Успех / Частично / Ошибки / Ожидает одобрения` и датой; сортировка от нового к старому. `Нет запусков` показывается пустым состоянием, не скрывается спиннером.

**Правое детальное представление запуска (обязательно):**

**A. Метаданные:** run id с копированием, trigger/кто, start/finish/duration, scheduler job ID, existing model ref (наследованная/override), snapshot до и после; итоговое состояние + причина. Два разных run не могут перепутаться при параллельных проверках.

**B. Последовательность стадий:**

| Стадия (строго по порядку) | Показываемое доказательство | Допустимый результат |
|---|---|---|
| `1. Получение` | точные source IDs, timestamps, HTTP, source SHA, files X/Y, bytes | complete / partial / failed / unchanged |
| `2. Разбор` | имена файлов, checksum, parsed snippets/chunks, flags | complete / partial / failed / skipped |
| `3. Анализ LLM` | model/provider, вызовов, actual input segment refs, JSON valid, tokens (если есть) | complete / partial / failed / not_run |
| `4. Систематизация` | proposed expressions, families, merges, reason codes и context guards | complete / partial / failed / not_run |
| `5. Проверка качества` | accepted / quarantined / rejected, fixtures и причины | complete / failed / not_run |
| `6. Публикация` | old/new snapshot, delta, checksum, publisher, rollback pointer | published / no_change / awaiting_review / failed |

Каждый этап кликабелен и показывает **его собственные артефакты/ошибки**, а не общий `completed`. Прогрессбар (если предусмотрен) основан на реально завершённых стадиях и количестве work units; `100%` только при terminal stage; нельзя считать fetching ≈ 80% при ещё не известном количестве документов.

**C. Блок `Модель фактически обработала`:** список **конкретных документов**, их `source / revision / path`, `segments_sent`, `chars_sent`, `segments_done`, `analysis_ids`, последнее model status; выбор документа раскрывает краткий evidence preview, если права позволяют, иначе ссылку на origin+position. Это должно визуально отличать скачанные 15 файлов от реально переданных 4 документов. Показывать общий elapsed, реальные token usage / `Нет данных`, model calls и error breakdown. Не требовать chain-of-thought.

**D. Блок `Результаты анализа модели` (не только счётчики):** читаемые текстовые записи:

- `Выражение`: оригинал/нормализованная форма, найденный short evidence, source/revision;
- `Предложенное семейство`: нормальное русское название, ID, какие фразы объединены и почему (structured `rationale_summary`, а не секретный chain-of-thought);
- `Предложенная инструкция для Writer`: **полный текст**;
- `Исключения и применимость`: `цитата / нормативный термин / легитимное противопоставление` и genre/scope;
- `Решение gate`: `Одобрено / Карантин / Отклонено / Изменено владельцем`, code и explanatory human label;
- `Итог`: попало ли в опубликованную версию, её номер, если нет — почему.

Важное требование: **нельзя показать «LLM обработала 100 фраз» и ни одного просмотра фактического извлечённого результата**. Список кандидатов должен быть открываемым и поисковым; paginated для большого batch. Текст может быть закрыт от обычного viewer, но доступен администратору с соответствующим правом и законной целью.

**E. Нижняя строка `Итог run`:** `Модель предложила X → валидатор пропустил Y → опубликовано Z / отклонено Q / в карантине K`, таблица причин отбраковки. Это не равно `в банке всего ...`. Кнопка `Перейти к опубликованным правилам` фильтрует вкладку `Правила` по этому run. Если run failed, показать **какие шаги успели**, last-good state и ссылку на конкретную ошибку `Журнал`.

**Действия в «Анализе»:** `Повторить анализ сохранённых допустимых документов` — явно **не** повторный сетевой fetch, создаёт новый run со ссылкой `rerun_of` и новой версией model prompt/schema, если документы всё ещё доступны для анализа по лицензии; `Загрузить заново и проанализировать` — сетевой fetch. Нет кнопки `Регенерировать сообщение` ни здесь, ни где-либо ещё в AntiCliche.

### 5.7. Вкладка «Правила» — весь итоговый набор в читаемом виде

**Это ключевая вкладка владельца.** Она показывает **реальный опубликованный набор**, а не 3 примера, не скрытый prompt hash и не необъяснимый JSON. Администратор должен быть способен открыть каждую утверждённую инструкцию, прочитать её дословно, увидеть варианты фраз, происхождение и то, применяется ли она к Writer.

**Вверху:** `Опубликованный snapshot vX` + точные `published_at`, `approved=N`, `pinned=P`, `families=F`, `bank-only=B`, `pending review=C`, `quarantine=Q`. `Сравнить версии` и `Откатить` только при наличии предыдущего совместимого snapshot и достаточных правах. **Кнопка `Скопировать утверждённый набор текстом`** — копирует все активные readable rules с заголовками и IDs, без secret/protected provenance; экспорт Markdown/JSON по действующим возможностям приложения, без новой избыточной инфраструктуры.

**Фильтры:** строка поиска по русской фразе/тексту guidance/ID; `Тип: Все / Закреплённые фразы / Семейства / Только наблюдать`; `Статус: опубликованные / кандидаты / карантин / отключённые`; `Источник`, `Маршрут: чат / фактчек / публичный саммари / другое существующее`, `Область: глобально / конкретный чат`, `Последний run`, сортировки `По приоритету / Названию / Дате / Источнику`. Применение фильтра не меняет сами данные.

**Строка семейства:** `Название`, `family_id`, короткое описание, **полный или разумно развернутый текст действующей инструкции**, `применяется: route/scope`, `источников N`, `enabled`, `приоритет`, timestamp. У строки есть раскрытие с **полным** текстом guidance и всеми связанными фразами, исключениями, `Evidence: source/document/revision`, `reviewed_by`, `approved_at`, версия публикации, `Последняя попытка применения в preview` (если есть trace), `Кандидат предложен моделью в Run #...`.

**Строка закреплённой фразы:** сама фраза текстом, scope, `ИЗБЕГАТЬ В СОБСТВЕННОЙ РЕЧИ` (не «блокировать сообщение»), категория/семейство если есть, `владелец закрепил`, enabled, время. Например `классика жанра`. В раскрытии: точная добавляемая в Writer инструкция, допустимые исключения `цитата/объяснение выражения`, provenance, где в текущем preview она включена. **Отмечать, что 100% исключить фразу без проверки результата невозможно.**

**Строка `bank_only`:** исходная фраза и `НЕ ПЕРЕДАЁТСЯ WRITER` / `пассивная аналитика`, источник, причина неактивации. Не делать вид, что все кандидаты являются активными.

**Редактирование:**

- `Добавить фразу` → inline/modal с полями `Фраза`, `Область действия`, `Тип: закрепить/в банк`, `не применять к цитатам/объяснению выражения` (значение по умолчанию защищает цитаты), необязательное объяснение владельца. Проверить нормализацию и дубли; предупреждать о пересечении с `ANTI_BOT_BLOCK`/иным правилом, не молча дублировать. Сохранить через существующий config/PG и пересобрать совместимый snapshot.
- `Закрепить / Открепить`, `Включить / Выключить`, `Редактировать guidance`, `Изменить применимость`, `Карантин / Одобрить`, `Откатить правку` — только при правах; каждое изменение даёт mutation event с before/after version и audit actor. Внешний refresh не переигрывает owner override.
- `Удалить` (если действительно требуется) — с подтверждением и возможностью отката; по умолчанию предпочтителен disable/archive ради аудита. Не очищать legacy фразы автоматически.
- Auto-generated family guidance не меняет owner style и не попадает в prompt до gate/approve. Текст from-source не становится system prompt по одному факту попадания в БД.

**Представления `Опубликованные` и `Кандидаты`:** различать визуально. На основной вкладке **по умолчанию показывать активный опубликованный набор**, а не staging queue, иначе невозможно проверить фактический результат работы.

### 5.8. Вкладка «Промпт Writer» — не фейковый preview

**Задача:** продемонстрировать с точностью до применённой версии, **какой именно дополнительный блок AntiCliche получит Writer** для заданной комбинации профиля и области, и какие правила отобраны или пропущены. Это не полный system prompt со всеми приватными memory/owner данными.

**Верхние controls (использовать существующие поля):**

- `Профиль ответа`: `Обычный чат`, `Фактчек`, `Публичный саммари` и любые **реально поддерживаемые** текущим маршрутизатором; если новый тип отсутствует в коде, не выдумывать его. По умолчанию `Обычный чат`.
- `Область`: `Глобальная` или конкретный chat scope, доступный администратору. При разрешении конфигурации показывать `effective origin`, если есть chat override.
- `Режим речи`: `casual / serious / deep_research`, **только если поддерживается этим маршрутом**. Недопустимое сочетание не молча переключать: показывать понятную подсказку.
- `Версия`: `Текущая опубликованная` по умолчанию, опциональный выбор предыдущих согласованных версий для сравнения (preview только; **не** меняет runtime).
- `Скомпилировать предпросмотр` — запускает **тот же deterministic compiler**, что runtime, без LLM, без Telegram, без записи нового source run. Передавать реальный context metadata fixture для выбранного профиля, не подделывать Observer/L1 результаты.

**Текстовый блок `AntiCliche → Writer`**:

- **полный, selectable/copyable текст** именно тех дополнительных инструкций, которые compiler создаёт для выбранных параметров. Сохранить реальные пробелы/строки/кавычки; не заменять строки на «список правил» из БД. Указать `snapshot v`, `compiler version`, `effective hash`, `selected IDs`, `bytes/chars`, `estimated tokens` (если точного tokenizer нет, явно `Оценка`).
- не показывать приватные owner/system prompts без отдельного доступа; текст AntiCliche можно просматривать администратору, а агрегированную статистику — остальным по ролям. Не включать в `copy` секреты.
- **ниже — таблица правил** `Выбрано / Не выбрано`, ID, тип, причина: `owner pinned`, `релевантно factcheck`, `уже покрыто базовым AntiBot`, `не входит в scope`, `банк / не approved`, `исключено owner`, `слабый сигнал`; при нехватке места в hint view покажите **честное предупреждение, какие owner pinned не вошли**, не молчаливое выпадение.
- Текст, видимый в preview, **сравнить интеграционным тестом байт-в-байт с тем, что Composer реально передаёт Writer** для идентичного route/scope/snapshot. Если динамическая информация на текущем ходу меняет выбор, preview говорит `пример для выбранного профиля; конкретный ход может отличаться`, а **фактический runtime compile trace** показывает реально выбранные IDs/hash для конкретного обезличенного вывода.

**Раздел `Фактическое применение`**: таблица последних безопасных `PromptCompileTrace` без текста личной переписки: `time`, `route/scope pseudonymous`, `snapshot/compiled hash`, `selected family/pinned counts`, `effective length`, `status`, `reason codes`. По клику на trace разрешённому администратору показывать восстановленный **только AntiCliche block** из immutable snapshot+metadata, если это возможно; если exact text не сохранялся и восстановление недоказуемо, писать `Точный текст недоступен; доступны IDs и hash`, а не показывать новый preview как будто он был историческим. Общее число вызовов модели Writer здесь не путать с LLM extraction calls.

**Ошибки:** если compiler fails, текст `Сбой компиляции; Writer применяет последнюю совместимую версию/базовый стиль` с точным reason и актуальной active version. Нельзя показывать пустой текст как будто решение сознательно было `0 hints`.

### 5.9. Вкладка «Журнал» — настоящий технический аудит с человеческим объяснением

Вверху фильтры `Период`, `Источник`, `Run`, `Стадия`, `Уровень (info/warn/error)`, `Событие/код`, строка поиска по безопасным кодам/IDs. Основная таблица: `timestamp`, `level`, **человеческое событие**, `source/model/stage`, `run_id`, `result`. Развёрнутое событие содержит `event_code`, структуру метаданных, ссылку к `run/source/rule`, длительность, technical error code, retry/next attempt, `trace_id` где доступен.

**Не заменять этот экран подключением к сырым файлам логов**. Данные должны быть доступны из existing event ledger/PG в рамках авторизации. Для разработчика есть `Скопировать диагностические сведения`, без ключей, cookies, auth headers, приватных сообщений и больших лицензированных текстов. Для администратора должна быть отдельная кнопка `Открыть источник` только на исходный разрешённый URL.

**Примеры названий событий (не настоящие логи, а контракт):**

- `Источник проверен: GitHub A, revision 8f…, изменений нет`
- `Источник недоступен: Wikimedia, HTTP 403, robot policy; автоматические повторные запросы приостановлены`
- `Документ обработан: patterns.md, 6 фрагментов переданы модели`
- `Модель завершила извлечение: 14 предложений, JSON проверен`
- `Два предложения объединены в одно семейство: ru.filler_importance_opener`
- `5 кандидатов ожидают проверки; 2 отклонены из-за риска ложного срабатывания`
- `Опубликован snapshot v19: +3 семьи, предыдущий v18 сохранён`
- `Обновление завершилось частично: 1 из 3 источников недоступен; активна v19`
- `Prompt Compiler: выбраны 1 pinned + 2 family, нет действий с готовым ответом`

**События и частота:** не писать event на каждый токен/каждую мелкую проверку; источник событий должен позволять восстановить stage/run audit, а для пассивного наблюдения собственных сообщений — только bounded агрегаты. Сохранять `request_id/run_id` для корреляции frontend↔API↔worker↔LLM↔PG; проверять, что ошибки не исчезают при рестарте. Политику retention использовать из приложения; не хранить бесконечно raw response с приватными/копирайтными данными.

### 5.10. Общие UI-состояния и запреты на декоративные подделки

**Для каждого экрана/виджета реализовать и протестировать**:

- `loading` — skeleton/прогресс того endpoint, который запрошен, без обнуления предыдущих корректных данных;
- `empty-never-run` — текст «Пока не запускалось», CTA для разрешённой операции;
- `empty-no-new` — источник проверен/LLM пропущена unchanged/новых кандидатов нет, **это успех без изменений**, не ошибка;
- `partial-data` — часть данных есть, некоторые поля `Недоступно/не измерялось`, ссылки на ошибки;
- `network-error` — последний кэш виден, явный retry CTA, причина и timestamp;
- `model-error` — fetch successful, analysis failed, **никакого** нового опубликованного набора;
- `source-blocked` — HTTP 403 с объяснением политики и next-allowed attempt;
- `stale-cache` — source status проблемный, но версия активна; оба состояния показаны одновременно;
- `off` — основной toggle OFF; версии/история доступны read-only, run вручную возможен по правилам;
- `running` — текущий этап/статус, кнопки повторного запуска защищены от двойного клика, данные старой версии остаются;
- `forbidden` — нет прав управления: read-only метрики по роли, опасные controls не видны/disabled с причиной;
- `conflict` — concurrent edit: stale version, не silently overwrite, показывать понятное предложение перечитать данные/разрешить конфликт;
- `snapshot-rollback` — обновляется версия атомарно, UI показывает настоящую активную версию; в истории остаётся ссылка на откат.

**Без инертных кнопок, пустых карточек, декоративных графиков/иконок, неработающих «Подробнее», фальшивых скорингов и отсутствующих данных.** Каждая строка источника, run, rule и event имеет действие, ведущее к действительному объекту. Имена и тексты на русском, единая терминология. Клавиатурная доступность, фокус, Enter/Space на controls, aria-labels у иконок, контраст на стекле. Любая опасная мутация (`disable/delete/rollback`) подтверждается в соответствии с действующими UI-паттернами; простая навигация и фильтры подтверждения не требуют.

## 6. Контракт банка, группировки и Prompt Compiler

### 6.1. Три стратегии, одни данные

| `strategy` | Запись в каталоге | В Writer | После генерации |
|---|---|---|---|
| `pinned_literal` | Владелец закрепил точную фразу (пример `классика жанра`), scope/исключения/приоритет | Дословно, **однократно** при соответствующем scope; инструкция «старайся избегать в собственной речи» | Только необязательная passive telemetry, никогда retry |
| `family_guidance` | Из источников сгруппирован вид речевого поведения + одобренная guidance | Короткое положительное поведенческое правило, только при актуальном route/scope | Только passive telemetry |
| `bank_only` | Низкая уверенность/редкая/дублирующая/ещё не одобренная фраза | Не передаётся | При разрешении — наблюдение/предложение для ревью |

**Никакой «четвёртой» автоматической стратегии `reject`, `hard retry`, `rewrite`, `scrub`.** Исторические `hard/soft` — оценка наблюдения/приоритет, не действие с сообщением. Внешние источники не закрепляют owner literal самостоятельно. Legacy regex `classic_genre`, `summing_up`, `in_conclusion`, `hope_helped`, `mirror_no_you`, `you_asked_before` инвентаризировать и перевести в подходящие стратегии; **не** делать весь legacy список pinned. `as_ai` и identity/metatext требования уже существуют в других канонах — не дублировать; `plain_no_tables`, `bullet_list` принадлежат форматным/жанровым настройкам, не AntiCliche.

### 6.2. Семантическое объединение

Например, из разных разрешённых источников извлечены `важно отметить`, `стоит подчеркнуть`, `следует отметить`. Вместо трёх почти одинаковых строк создаётся семейство `ru.filler_importance_opener` с утверждённой guidance: `Сразу формулируй мысль; не объявляй её важность отдельной дежурной вводной.` Связь исходных фраз с тремя source/evidence сохраняется. Никакого «вся русская речь с глаголом отметить плохая». `Не X, а Y` не запрещать как класс: это часто нормальная антитеза.

Кандидат из одного репозитория не становится автоматически истиной; одинаковые форки/копии одного humanizer не считаются независимыми. LLM должна представить `rationale_summary` и `evidence_refs`, но это не chain-of-thought. Quality gate проверяет точность и false-positive fixtures. Существующие `ANTI_BOT_BLOCK`/Expression/Style учитываются при дедупликации, чтобы не повторять один запрет три раза.

### 6.3. Компиляция: два независимых цикла

**При publish:** из утверждённого каталога создаются согласованные `PromptHintView` (approved guidance, pinned, applicability, versions) и `ObservationView` (пассивные matchers, исключения, IDs, версии). Оба хэшированы одной published snapshot версией. PG/cache invalidate атомарен. Ошибка построения → old LKG остается активным.

**При конкретном исходящем сообщении:** уже существующий route/Observer/L1 определяет genre/scope/response_mode; детерминированный selector использует готовые метаданные, owner pinned и проверенные агрегаты прошлых **исходящих** ответов, если есть. **Никакого нового API/LLM, semantic rewriting, поиска/удаления фраз из готового сообщения.** Компилятор вставляет один AntiCliche-блок в один определённый слот текущего Prompt Composer, после инвентаризации versioned Prompt Registry. Произвольный source Markdown, regex, URLs, imperative-инструкции из внешнего текста не допускаются как system prompts.

**Приоритеты:** техническая безопасность/доставка → owner/чатовые overrides → Persona/Expression/Style/Profanity/русский язык/типографика → AntiCliche уточнения. Уважать сознательные цитаты, обсуждение самой фразы, точные названия, терминологию, подтверждённые факты и реальную неопределённость. «Не просто X, а Y» в обоснованном противопоставлении остаётся нормальной речью.

**Профиль выбора — начальные экспериментальные параметры, не новые жёсткие потолки:** короткий чат обычно pinned owner + 1–3 relevant families; длинный фактчек/саммари — по фактической уместности; банк из 1000 кандидатов не превращается в 1000 prompt lines. Размер подсказки ограничивается доказанным качеством и latency, не количеством токенов контекстного окна Writer. Если закреплённые фразы не вмещаются, показать список исключённых и причину в UI; не молча нарушить owner override. По умолчанию `0 relevant hints` — нормальный результат, **не ошибка**.

### 6.4. Версионирование и результаты редактора

Версионировать: `source revisions`, `extractor model ref`, `extractor prompt/schema revision`, `rule_set_version`, `prompt_compiler_version`, `owner overrides`, `effective content hash`; полный текст утверждённых guidance и pinned хранится и читается по каждой опубликованной версии. Revision меняется **только при содержательном изменении**, не на unchanged cron. Исторические версии доступны read-only и сравнимы с текущими. Rollback publish не уничтожает staging/source status. Не пересобирать эмбеддинги памяти/GraphRAG ради AntiCliche.

### 6.5. Логика error/fallback

1. `Source A=403`, `B=200/changed` → независимый анализ B; UI `partial_success`; при approved delta публикация может состояться, A показывает причину.
2. Все sources недоступны → no new publish, last-known-good in Writer, source health красный/жёлтый, runtime status `Работает на прошлой версии`.
3. Model unavailable / invalid JSON → no fake `completed`; предыдущий snapshot работает, кандидаты/ошибки просматриваются.
4. Parser returns empty → `no usable documents`, не `0 approved = новый snapshot`; old remains.
5. Publish/PG error → old snapshot and owner override остаются; UI явно `Публикация не состоялась`.
6. Prompt compiler error → fallback to previous compatible published view or existing base style, never block a Telegram reply, no AntiCliche retry.
7. Passive observer error → пропустить observation, сообщение неизменно.
8. `OFF` → не создавать новых AntiCliche hints и observations, старые версии доступны; можно вручную обновить банк для будущего ON.

## 7. Телеметрия и логи: событийная модель, корреляция, честные данные

### 7.1. Единые события через существующую инфраструктуру

Переиспользовать существующие `agentic_events`, `mca_events`, `external_log`, `anticliche_cache` status и действующий журнал админки, не создавать второй logger/event-bus. Architect должен документировать фактическое место хранения и retention. При необходимости расширить **структурированные** события минимальным контрактом. Предлагаемые имена (адаптировать к текущему event naming, не создавать два дубля на одну стадию):

| Event semantics | Обязательные безопасные атрибуты | Когда происходит |
|---|---|---|
| `anti_cliche_run_started` | `run_id`, `trigger`, `time`, `snapshot_before` | реальный запуск worker |
| `anti_cliche_source_checked` | `run_id`, `source_id`, `check_id`, `transport_status`, `http_code?`, `revision?`, `unchanged?`, `duration` | один завершённый source probe |
| `anti_cliche_document_parsed` | `run_id`, `document_id`, `source_id`, `checksum`, `fragments_count`, `chars_count`, `status` | завершённый parse |
| `anti_cliche_analysis_started` | `run_id`, `analysis_id`, `effective_model_ref`, `documents/segments_count` | вызов модели реально начат |
| `anti_cliche_analysis_completed` | `run_id`, `analysis_id`, `provider_status`, `json_valid`, `candidates_count`, `usage_if_available`, `duration` | **валидированный** результат, не HTTP 200 |
| `anti_cliche_analysis_failed` | `run_id`, `analysis_id`, `reason_code`, `provider_status_if_known` | отказ модели/JSON/schema |
| `anti_cliche_candidates_classified` | `run_id`, `proposed`, `families`, `duplicates`, `quarantined`, `rejected`, `reasons_count` | закончена группировка/gate |
| `anti_cliche_snapshot_published` | `run_id`, `old/new_version`, `content_hash`, `delta_counts`, `publisher` | атомарный commit прошёл |
| `anti_cliche_run_finished` | `run_id`, `terminal_status`, `source_breakdown`, `snapshot_after`, `duration` | ровно один terminal event |
| `anti_cliche_owner_changed` | `actor_id`, `action`, `rule_id`, `old/new_version`, `scope`, `time` | подтверждённая ручная мутация |
| `anti_cliche_compiler_applied` | `compile_trace_id`, `snapshot_version`, `profile/scope_id`, `family_ids`, `pinned_ids`, `hash`, `length`, `status` | безопасный bounded runtime trace/aggregate |
| `anti_cliche_compiler_failed` | `compile_trace_id`, `snapshot_version`, `reason`, `fallback_version` | runtime compiler failed |
| `anti_cliche_observation` | `family/rule IDs`, `count`, `time_bucket`, `scope_alias_if_safe` | только агрегат; не триггер retry |

**Имена для справки; не переписывать существующие event codes под них, если в приложении уже утверждён словарь.** Важно покрыть семантику и связать записи, не плодить параллельные события под разные UI.

### 7.2. Корреляция от кнопки до результата

- Каждая ручная операция получает `operation/request id`, настоящий `run_id`/`check_id` и ответ сервера с `accepted/running/already_running/failed`, не «успех» по одному клику.
- UI сверяет terminal status с ledger; прогресс подсвечивается **по поступившим фактам**. После refresh страницы можно вернуться к текущему run с теми же ID.
- Для фоновых jobs `run_id` генерируется ровно один раз; `source_check_id` всегда привязан к одному run, а `analysis_id` к реальному вызову модели. События могут приходить с задержкой; UI не переставляет их в несуществующую последовательность, а сортирует по timestamps/stage sequence.
- Любой опубликованный `rule_id` должен указывать на source evidence и `analysis_id` или `manual owner`, опубликованную версию и решение gate. Если provenance отсутствует у legacy, честно метка `legacy / provenance не восстановлен`, а не выдуманный GitHub-источник.
- Кнопка `Показать историю` идёт по реальным IDs: source → check → document → model analysis → candidate → family → publish → prompt trace. Не обязать пользователя вручную искать SHA в terminal.

### 7.3. Безопасность, доступ и авторские права

- В обычные application logs нельзя писать тексты сообщений/приватную историю, complete system prompts, ключи, Authorization, cookies, полные скачанные статьи, provider secrets. Безопасные identifiers, counts, result codes и hashes — да.
- **Утверждённые собственные AntiCliche-инструкции**, короткие словарные фразы и structured proposal, которые законно сохранять, можно показывать полным текстом администратору на вкладках `Анализ`/`Правила`. Это **не равно** разрешению хранить и републиковать весь исходный HTML/Markdown статьи.
- `Evidence preview` = разрешённый короткий фрагмент или координаты/ссылка на строку и revision. Для источников без прав на хранение excerpts — metadata only. Лицензии MIT при заимствовании материалов — attribution и notices.
- RBAC: те, кто могут только читать dashboard, видят агрегаты/здоровье; просмотр чувствительных owner prompts, source artifacts, ручной approve/rollback и model connection — только существующая разрешённая admin role. Не выносить raw prompt в доступ обычных участников чата.
- Prompt injection: внешний документ untrusted, инструкция типа «игнорируй правила» не повышает полномочия; parser+schema+allowlist fields, model output treated as untrusted proposal; только собственная утверждённая guidance попадает в Composer.
- Retention большого event stream держать bounded по политике проекта; source revisions/опубликованные snapshot/owner audit сохранять для отката. Исторические run stats нельзя удалять без соблюдения действующей retention policy.
- При массовых выходных сообщениях хранить только агрегаты AntiCliche и идентификаторы разрешённой аналитики; не записывать весь чат только ради поиска стилевых фраз, не отправлять историю сторонним моделям без необходимого разрешённого основания.

### 7.4. Определения метрик (чтобы два экрана не показывали разные цифры)

- `sources_enabled` — включённые активные сетевые адаптеры, у которых permitted machine access. `manual` и bibliography-only excluded.
- `sources_checked` — из `sources_enabled` реально имеют `last_checked_at`.
- `sources_available` — последний source check успешно разрешил fetch+recognized document(s) и находится в policy-defined freshness; если checker не проверял freshness — выводить `по последней проверке`, а не `сейчас онлайн`.
- `docs_fetched` — количество реально скачанных доступных файлов; `docs_parsed` — валидно разобранных; `docs_analyzed` — реально входивших в завершённые `ModelAnalysis` (при partial отдельно).
- `model_calls_started/completed/failed` — реальные provider calls по IDs; test-connection вызовы в отдельном namespace, не включать в эти метрики источников.
- `patterns_proposed` — число raw candidates из валидного model/parser output; `patterns_unique` — normalized canonical candidates; `families_proposed` — semantic families; `families_approved` — passed gates + policy; `published_delta` — фактические изменения snapshot.
- `bank_size` — candidate+approved+archived according to explicit filter; `approved_count` — активный approved; `pinned_count` — активные owner-pinned; `selected_count` — правила в одном **конкретном** compiled prompt, а не глобальная константа.
- `last_source_success` ≠ `last_analysis_success` ≠ `last_publish_success`; `refresh_status` ≠ `runtime_health`. На каждого важного KPI есть однозначный field и timestamp.
- `usage_tokens` — только реальные provider stats, либо clearly labeled tokenizer estimate; `cost` не вычислять по ценам неизвестного gateway. `retry_count` модели extraction ≠ `AntiCliche-induced Writer retries` (последнее строго 0).
- `snapshot_version` — последняя успешно опубликованная совместимая версия; failed attempt не может записать `0` туда, где есть прошлое значение.

## 8. Серверный/API контракт интерфейса (минимальные требования, не фиктивные endpoint names)

Не назначать новые URL `api/anticliche/v2/...` до инвентаризации existing routes. Ниже перечислены **действия и поля**, которые UI должен получать реальными API/queries. Использовать подход текущего приложения (HTTP/GraphQL/WS/polling), без нового самостоятельного BFF. Архитектор составляет mapping `UI → существующий endpoint или минимальный extension → PG/job/event` и фиксирует его в плане.

### 8.1. Read operations

1. `getAntiClicheOverview(scope)` → effective enabled, active snapshot version/hash/published time, runtime health, source counts and health timestamps, last run summary, pinned/families/approved counts, preview summary and `data_present` flags.
2. `listAntiClicheSources(filters, pagination)` → configurable source metadata, last source check, last success fetch+analysis, next retry, enabled status, error details, revision, counts.
3. `getAntiClicheSource(source_id)` → exact source doc paths/license/link/history and run associations.
4. `listAnalysisRuns(filters, pagination)` → run summaries; `getAnalysisRun(run_id)` → stage-by-stage telemetry, documents, analysis batch/call usage, classification breakdown, readable structured proposals and publish outcome.
5. `listAntiClicheRules(snapshot_version, filters, pagination)` and `getAntiClicheRule(rule_id, version)` → full **renderable** guidance text, literal, provenance, exceptions, status, owner overrides, version; candidate queue separate filter.
6. `previewAntiClichePrompt(profile, scope, mode, version)` → **true deterministic compile output**, selected/skipped IDs+reasons, exact AntiCliche text, hash, measured lengths, error/fallback.
7. `listAntiClicheCompileTraces(filters, pagination)` → recent safe events; optional historic precise text only if immutable data allows exact reproduction.
8. `listAntiClicheAuditEvents(filters, pagination)` → structured persisted safe events, deep links to source/run/rule.

### 8.2. Mutations

1. `setAntiClicheEnabled(scope, bool, expected_version)` — единственный контроллер состояния, without silent config drift.
2. `setSourceEnabled(source_id, bool, expected_version)`, `checkOneSource(source_id)`, `checkAllSources()`, `refreshAndAnalyze(sources?, force_reanalysis=false)` — **разделить** lightweight check и полный анализ.
3. `reAnalyzeStoredDocuments(run/source_ids, analysis_settings)` — новый run с унаследованными documents/evidence; disabled if data usage rights no longer permit.
4. `add/update/disable/pin/unpin/approve/quarantineRule(expected_version)` — статус/owner priority/scopes, audit and snapshot rebuild.
5. `rollbackSnapshot(target_version, expected_current_version)` — atomic compatible pair + audit + status, RBAC + confirmation.
6. `testConfiguredExtractorModel()` — test structured output on synthetic non-sensitive example, **не** считается source analysis.
7. `saveExtractorModelOverride(ref|null)` — **только** через canonical config control в «Модели и подключения», same source of truth and actual inherited preview elsewhere.

**Mutations не должны блокировать отправку сообщений** и не должны запускать на ней Validator Loop. Из UI показывать `operation accepted` отдельно от `finished successfully`. Single-flight/locks предотвращают duplicate cron/manual run, но не приводят к тихой потере запросов. При stale version -> 409/conflict-equivalent and clear UI. При offline/error прошлые данные остаются видны.

### 8.3. Пример данных, чтобы разработчики не заменили поля одним `status`

## 9. Контроль качества: отдельные риски и строгая приёмка Reviewer

### 9.1. Что считать готовым результатом (Definition of Done)

- **Рабочая подсистема**: реальные независимые разрешённые sources, LKG и prompt compiler, только одна точка конфигурации.
- **Нулевая AntiCliche-перегенерация** во всех legacy/manual/dynamic/новых сценариях; независимые guards не сломаны.
- **Доказуемая end-to-end история** source fetch → документы → model calls → candidates → gate → approved rule text → published snapshot → фактический Writer hint.
- **UI на реальных данных**: шесть вкладок, truthful health, readable result, no dead controls/duplicates, desktop/mobile.
- **Устойчивость**: 403/429/model fail/PG fail/unmodified sources сохраняют активную версию, не генерируют ложные KPI.
- **Версионирование**: owner overrides, ревизии источников, snapshot, compiler и prompt registry совместимы, rollback работает.
- **Демонстрация по живой системе**: один разрешённый smoke run с понятным readout и screenshot/video screens, при этом без живого спама в Telegram и не через фейковые данные. Если внешняя реальная проверка запрещена или недоступна, Reviewer честно пишет `NOT_LIVE_VERIFIED`, не «PASS live».

### 9.2. Обязательные backend unit / integration тесты

**Источники и статус:**

1. GitHub-A и B здоровы, ревизии известны, source checks независимо записываются.
2. A=403 robot policy, B=200+changed: B идёт до publish; A остаётся красным и отмечен partial-run.
3. Wikimedia=403: нет подмены User-Agent/IP/прокси, нет tight retry storm, LKG active.
4. Source A=429 `Retry-After`: правильное `next_attempt_at`, нет hammering.

6. Source=401/403 credentials: `auth_failed`, не robot-policy по одному коду 403.
7. Source=404/renamed file: точный `missing/parse_error` и failed doc, не зелёное complete.
8. HTTP 200 + HTML вместо Markdown + невалидный JSON: transport success, content parse fail, analysis not marked done.
9. HTTP 304/unchanged SHA: fetch successful, **0 новых LLM calls**, snapshot version/checksum unchanged.
10. Пустой разрешённый документ: `no usable content`, не затирает active snapshot.

12. Все sources падают, LKG существует: runtime works, overview degraded with old version.
13. Все sources падают, LKG отсутствует: честно `Нет опубликованных правил`, не мнимый success.

**Prompt Writer/Validator:**

### 9.4. Независимый Reviewer: как не обмануться зелёными тестами

Reviewer не ограничивается тестами Builder и `200 OK`. Обязательные независимые проверки: read-only code walk по `negative_constraints.py` и trigger paths; negative tests с намеренно сломанными rule IDs/source statuses; сравнение JSON/PG event data с каждым показанным KPI; проверка UI в браузере desktop/tablet/mobile; функциональный click-through `source → run → candidate → rule → prompt`; прицельная проверка prompt injection/owner overrides, порогов и сохранности русской речи; измерение tokens/latency с нулевыми AntiCliche retry. Если реальный внешний source недоступен, использовать mock для регрессии и отдельно пометить live status `NOT_VERIFIED`, не изображать success.

**Нужны два класса fixtures:**

- «Клише действительно мешает»: ритуальная похвала, пустые вводные, бессодержательная «классика жанра» в собственном тексте и накопление одинаковых завершений.
- «Оставить как есть»: объяснение значения фразы «классика жанра», цитирование собеседника, литературная/ироническая реплика, доказанный контраст «не новый отчёт, а решение по убыткам», технические/юридические термины, источники/числа/оговорки, мат/сленг согласно owner mode. Нельзя оценивать качество только исчезновением слов.

Baseline vs new: first-pass качество, доля уместных/неуместных штампов при независимой оценке, **retries caused by AntiCliche = 0**, other retry paths separately, p50/p95 latency and real token usage, сохранение фактов и характера. Допустимо не достичь идеального исчезновения клише: запрещено компенсировать это скрытым retry или зачисткой готового текста.

## 10. План реализации AntiCliche (без отдельного исследовательского этапа)

1. **Интеграция на актуальном коде.** PM/Architect по ходу реализации сверяют файлы на HEAD/deployed SHA, configs, PG cache/schema, существующие UI-компоненты и EVOL/ASAP, затем сразу вносят требуемые изменения. Это не автономная исследовательская задача и не отдельный gate с отчётом вместо кода. Сохранять совместимость, не переписывать весь интерфейс ради простоты.
2. **P0 invariants/repair.** Отвязать **все** AntiCliche-only hits от retries/ranking/rewrites, проверить независимые guards. Исследовать активный PG LKG после 403, устранить ложные нули и source retry storm. Доказать это трассами прежде чем менять словарь.
3. **Core sources + canonical data.** Независимые source adapters, accurate source status/revisions, license compliance, data versioning; structured parser/LLM analysis only where needed; gate/merge/approved snapshots.
4. **Compiler + runtime.** Переиспользовать Prompt Composer, build stable published Hint/Observation views, owner pinned and route-based family selection; zero LLM calls on runtime AntiCliche path; provenance/telemetry.
5. **Telemetry before UI.** Persist real run/source/document/analysis/decision/publish events, expose reliable read API and accurate counts. Только потом строить 6 вкладок над настоящими данными; не делать сначала красивые моковые counters.
6. **UI/integration.** Карточка toggle в «Речь и характер», background extractor model card в «Модели и подключения», удаление старого prompt-list editor, шесть вкладок с source indicators, analysis trace, **полным текстом правил** и **actual Writer prompt**. Проверить пользовательские сценарии и мобильную адаптацию по §5.
7. **Review/evidence.** Пройти все 84 сценария с отдельной отметкой `PASS/FAIL/NOT_VERIFIED/N/A` и ссылкой на evidence. Обязательны screenshots desktop+mobile, реальные UI/API/PG count reconciliation, no AntiCliche retry code path, controlled smoke-fetch (если permitted) и LKG under error. Builder не сдаёт задачу с отсутствующим UI или фиктивным статусом. Reviewer независим, не доверяет только тестам Builder.
8. **После merge/deploy.** Провести одну controlled live проверку (не требующую ожидать недельного cron), подтвердить active snapshot+versions/status/model run, UI readouts and no new delays. Сохранить версию/rollback. Продолжить `current_task` и остальные задачи workflow; не останавливаться после отчёта «деплой выполнен».

**Инженерные неопределённости (названия файлов/endpoint/SQL schema) — это задачи исследовать и решить на HEAD, не вопросы владельцу.** Если реальный архитектурный конфликт действительно затрагивает пользовательскую семантику/безопасность/невозможность выполнить конкретное обязательное решение, Architect пишет ограниченный human gate с вариантами, но не спрашивает, где разместить кнопку или как назвать вкладку — это определено здесь.

## 11. Запреты и критерии недопустимого «выполнения»

**Запрещено:**

- прятать AntiCliche в конце «Библиотеки промптов» как старый неработающий accordion или оставлять второй backend/config редактор;
- заменить доказуемый UI одной плашкой «Источник работает», одним `version=42` или счётчиком LLM calls без просмотра реальных кандидатов/инструкций;
- выдумывать проценты «LLM прочитала 100%», «изучено 200 правил», если это не следует из фактического run ledger;
- показывать зелёный источник без timestamp и отдельной проверки реальной доступности, успешный LLM анализ по HTTP 200 или новый published version при нулевом delta;
- подставлять mock/data fixture в живой production dashboard под видом реальных значений;
- хранить полную чужую статью/приватный чат в audit logs, считать copied repositories независимым источником, обходить блокировки политики;
- запускать новую extraction модель для каждого исходящего сообщения; создавать отдельный AnticlicheAgent/Writer/Validator/PromptComposer/службу бюджета;
- вставлять весь словарь/сырой Markdown/regex в Writer, дублировать owner style, проводить скрытое «улучшение» текста после генерации;
- вызывать ANY AntiCliche-only retry/reject/best-of/fallback/scrub; скрывать такой retry в `format`/`metatext`;
- удалять владельцем закреплённые фразы при источниковом refresh; терять версию при failed analysis;
- добавлять пустые неработающие кнопки, невидимые на мобильном действия, красивую анимацию вместо фактических данных;
- помечать задачу `DONE` до внедрения, проверки в UI и backend и деплоя; файл не запускает работу сам собой, а становится задачей после добавления владельцем в `current_task`.

## 13. Зафиксированные решения и преемственность спецификации

## 14. EVOL-MEMORY-RELEVANCE-01 — РЕАЛИЗАЦИЯ осмысленного использования памяти и корректной идентичности

**Дата дополнения:** 02.11.2026. **Статус:** READY FOR IMPLEMENTATION via `current_task`. **Приоритет:** P1. **Владение:** существующие Memory/GraphRAG, Retrieval, AliasResolver, ToolRouter, ToolLoop, Composer, Writer и telemetry; отдельный функциональный workstream, не AntiCliche. **Тип задачи: IMPLEMENTATION, НЕ RESEARCH/AUDIT.** Исследовательский отчёт, «найти вероятную причину», «составить предложения», отдельная диагностическая фаза перед исправлением и закрытие с формулировкой «данных недостаточно для реализации» НЕ принимаются как результат. Нужные локальные проверки HEAD/схем/флагов — обычная часть разработки, а не самостоятельный deliverable или human gate.

### 14.1. Проблема установлена из полного диалога; это обязательный регрессионный fixture

**Основание:** ниже не OCR/предположение по сжатому скриншоту, а переданная владельцем дословная последовательность сообщений. Хранить в тестах **обезличенный структурно эквивалентный фрагмент**, а не сырые приватные сообщения. Не использовать совпадение с буквальным именем/песней/числом как костыль в production.

1. Участник публикует большой шуточный русско-фонетический текст иностранной песни, второй просит `фактчек`. Бот выдаёт обстоятельный, местами чрезмерно уверенный разбор. То, что искажённая песня не находится, само по себе не дефект Memory и не основной предмет этого epic.
2. На реплику «как же он разобрал эрон дон дон то» бот без достаточного основания пишет: **«Кирилл, я так понял, что это нейросетка, которая распознаёт песни на слух. Ну, из серии Шазама»**. Здесь бот сам вводит имя, не установив человека или адресата. Не считать это доказанным фактом о Кирилле.
3. После «че за Кирилл» и прямого «бот кто такой Кирилл» бот выдаёт без оснований несколько **несогласованных идентичностей**: «олдфаг ... с джаббер-времен»; «недавно закончил аспирантуру»; история, что «Кирилл — это не Вася ... а Кирилл и Фотий». Он не признаёт, что мог ошибиться, сам произнеся имя.
4. На настойчивое «кто такой Кирилл, давай рассказывай...» бот отвечает, что «следствие ведём не мы, а граф памяти», пересказывает якобы найденные сведения о религиозных персонажах, **подменяя обсуждаемого неизвестного участника историческими именами**. Наличие совпадающего имени/сущности в базе не подтверждает нужного референта.
5. В тот же ответ выпущены служебные данные **«сообщений с совпадением: 428494; метод: совпадение по префиксу (не морфологический анализ); чат -1002661910336; полнота: полная»**. Такое число нельзя представлять как доказанное количество упоминаний Кирилла: показан широкий/нецелевой метод, неизвестно, к какому запросу и области оно относится. Вопрос пользователя вообще не был о статистике.
6. Ответ продолжен случайными подробностями о нескольких других участниках и заключительным перечнем посторонних тем. Это **memory dump**, а не естественное вспоминание нужного контекста. Общая проблема: технически успешный retrieval принят за обязательный контент ответа.
7. Для сравнения: развёрнутый FactCheck о заявлении про Иран из другого присланного диалога — **положительный эталон** аргументированного, выразительного ответа. Сохранить выбранный голос, сленг, резкость и отличие независимого подтверждения от перепечатки; достоверность конкретных внешних источников по скриншоту отдельно не утверждать.

**Главный продуктовый контракт:** у бота память должна работать как у внимательного участника чата: он может вспомнить уместное, опереться на прошлое для шутки или понимания отношений, но **не обязан озвучивать каждый найденный факт, ссылаться на систему памяти или пересказывать справку**. Цель — подходящая по смыслу информация, а не максимальное количество находок.

### 14.2. Непересматриваемые решения владельца

1. **Не отключать инициативное вспоминание.** Память используется как по прямому вопросу «помнишь/кто такой», так и в обычной беседе, когда ранее известное действительно помогает: поддерживает шутку, объясняет отсылку, уточняет отношения или делает ответ точнее. Нельзя заменить это правилом «доставать память только по явному запросу».
2. **Не превращать ответ в выдержку из БД.** На выходе — связная реплика участника, написанная его текущим голосом. Логи, ID, веса, ранги, provenance и сырые служебные поля остаются внутри; даты/источники упоминаются только когда содержательно нужны или пользователь просит доказательства/историю.
3. **Не путать извлечение с доверием и уместностью.** Наличие записи, высокое embedding similarity, результат FTS, graph edge, совпадение имени или успешный статус ToolResult не означают, что факт истинный, про нужного человека и нужен в текущем ответе.
4. **Не вызывать дополнительную LLM ради проверки каждой записи или каждого ответа.** Переиспользовать имеющиеся Observer/L1, данные текущего хода, существующий retrieval/rerank по его действующим правилам, Composer/Writer и функциональность памяти. Новых агентов, нового retrieval движка, второго GraphRAG, нового системы бюджетов не создавать; не перестраивать embeddings, не менять поставщика/модель и не проводить миграции памяти «для чистоты».
5. **Не добавлять перегенерации/штрафы за «не тот факт».** Проблему решать правильным выбором, структурой и передачей доказательств до генерации, а не очередным Validator Loop, scrub по словам или блокировкой Telegram ответа.
6. **Не хардкодить конкретный инцидент**: имена Кирилл, Мефодий, Фотий, «нейросетка», название песни, статистическое число, темы других участников не становятся особым blacklist/regex. Это воспроизводимые примеры общего дефекта.
7. Сохранить **owner style и FactCheck Voice**: мат, подколы, ирония, русский живой язык, отсутствие морализаторства. Снижение памяти до нуля или стерильная речь — провал приёмки.
8. Не вводить human gate ради инженерных решений. Builder исправляет, Reviewer независимо проверяет. Отчёт об исследовании или список рекомендаций вместо работающего кода = `FAIL`.

### 14.3. Конкретные существующие точки исправления (предмет реализации, а не задача «найти что-нибудь»)

Подготовлено по публичной ветке `master` на момент формулирования требований; сопоставить имена с актуальным HEAD в процессе разработки и **внедрить контракт по фактически существующим путям**:

- `services/tool_router.py::_memory_lookup_general`: сейчас выборка `get_rag_facts(chat_id, name)` → `search_long_term(... keywords(name))` → `get_rag_context(chat_id, name)` преимущественно ориентирована на **имя**, а не на смысл и текущую тему. Изменить построение запроса и отбор **до** формирования tool-visible `facts`: учитывать текущий `ToolContext.query`, актуальную тему/reply и заданный `purpose`. Сохранить полезную выдачу о человеке по прямому запросу, но не включать чужие, неподходящие факты и целое досье автоматически.

Разделить `verified_id`, `name_only_unverified`, `ambiguous`, `unresolved` с совместимостью действующего API и alias-priority. **Не связывать автоматически граф-факты другого Кирилла** и не называть произвольное имя участником конфы.

Сделать нормализованный разбор структурированных результатов с разделением текста и метаданных, дедупликацией и фильтрацией по текущему вопросу. Нельзя отправлять Python repr и «сырые объекты» как готовую прозу.
- `services/tool_router.py::_dig_into_lore`, `_get_user_context`, его обработчики `identity/biography/relationships/general/speech_style` и stats-ветка: привести к **общим** условиям релевантности, identity и provenance. Текстовый/биографический поиск и точная статистика — разные намерения; запрос «кто такой» не запускает массовый подсчёт и не смешивает статистический результат с биографией.

Реально существующий rerank допустим там, где уже предусмотрен; не требовать нового LLM-вызова на каждом сообщении. Контекст `bot_knowledge`/`RAG_Memory` — информация, не повеление перечислить все строки.

Проверить оба канала поступления текста к модели и убрать опасные преобразования/эскалацию tool metadata в ответ. По месту допустима минимальная совместимая функция/DTO в текущих сервисах, чтобы использовать один контракт вместо множества разных фильтров.

### 14.4. Семантический retrieval: два последовательных решения, не случайный top-k

**A. Что искать.** Для каждого обращения к памяти восстановить из уже имеющегося контекста текущую цель: `topic/question`, `intent` (прямой факт о человеке, воспоминание о событии, вопрос о цитате, историческая справка, обычная болтовня, статистический вопрос), `subject(s)`, `speaker`, `reply target`, границы актуальной темы/ветки, временную привязку. Это **не новый LLM-классификатор**: использовать сигналы Observer/планера, `ToolContext.query`, `reply_source_*`, existing canonical query planning и уже переданные scope/intent. Когда сигнал невыведен — не сочинять user ID или тему.

**B. Какие записи реально передать Writer.** Кандидаты из существующих exact/FTS/vector/GraphRAG/episode ранжируются **внутри установленной цели**, а не по одному имени и не по общей близости всего чата. Учитывать:

- **Предметная связь:** отвечает ли запись на текущую мысль/вопрос, помогает ли объяснить актуальную отсылку, шутку, собеседника; есть ли обоснованный переход от темы текущего reply. «Об одном Кирилле» и «о нашей шутке» — разные области.
- **Identity/attribution:** кто утверждал, о ком говорили, кто цитируется, кому адресована реплика, какой чат. Exact identity сильнее похожего имени; совпадение написания не связывает две сущности.
- **Время:** время события и создания записи различаются; учитывать свежесть, отменённые/заменённые факты, устаревшие свойства и последующую явную коррекцию участника. Историческое воспоминание не теряет ценности просто от возраста, если вопрос исторический.
- **Качество свидетельства:** собственное высказывание человека, пересказ, чужой сарказм, шутка, результат другого генеративного ответа и утверждение внешнего источника имеют разные роли и степень доверия. Бот не может подтвердить сам себя повторением собственных реплик.
- **Отношение к текущему ответу:** candidate может быть `useful_context` (подсказывает смысл, но не требует упоминания), `direct_evidence` (отвечает на вопрос), `not_applicable` или `identity_uncertain`. Не превращать `background` в команду «вставь этот факт».

Детерминированные ограничения допустимы для **сохранения типов, целостности, границ чатов и явной несовместимости сущностей**. Не вводить ломкий ручной список тематических слов, жёсткий age cutoff, blanket rule «всё кроме топ-1», абсолютное обнуление низкого similarity или обязательный однострочный ответ. Использовать имеющиеся эмбеддинги/FTS/rerank, а не создавать второй индекс.

**Интеграция в Composer:** выделить `direct_evidence`, `useful_context`, `uncertain/contradictory`, источники и датировки как **типизированные данные с короткими пояснениями для Writer**, а не длинные raw-list и не инструкции от внешнего контента. В реальном промпте Writer получить ровно необходимый контекст; отбор должен происходить **до** prompt compaction/trimming (чтобы неконтролируемое обрезание не оставляло мусор вместо полезного факта). Если связанного материала нет — пустое пространство памяти, без искусственного «вспомнить хоть что-то».

**Свободное вспоминание:** допустимо вставить лёгкую отсылку к прошлому даже без прямого запроса, если есть понятная связь с текущим событием. Исторический joke или разговорный колбэк не требует официальной ссылки на каждую строчку; при запросе доказательств модель должна иметь возможность назвать первичный источник/дату и не выдумывать их. Редкие ассоциации не исключаются потому, что они не главная тема, если они действительно поддерживают текущую мысль.

### 14.5. Личности, цитаты и собственные ошибки бота

1. **Каноническая личность** — стабильный Telegram `user_id` при наличии подтверждённой привязки. Алиас и nickname — текстовые формы для человека; приоритет локальный > глобальный > nickname > username; эти подписи не образуют автоматически identity. Если есть лишь строка «Кирилл», **это упоминание имени**, а не установленный пользователь.
2. **Роли в одном факте** не смешиваются: `speaker_author_id`, `subject_entity_id`, `quoted_speaker`, `mentioned_entity`, `reply_to_user_id`, `bot_output`, `historical_person`. Нельзя делать сообщение о Кирилле доказательством, что Кирилл его произнёс, или считать исторического Кирилла участником чата.
3. **Нет доказанного отождествления → нет персонального утверждения.** Разрешено обсуждать неизвестное имя как упоминание или шутку с явной неопределённостью. Нельзя приклеивать к нему чужую биографию, историю религии, нейросеть или свойства собеседника на основании совпадения строки.
4. **Сам бот ввёл необоснованное имя.** Если пользователь затем спрашивает «кто такой Кирилл?», сначала установить референт из **собственной предыдущей реплики и reply-цепочки**, а не искать случайную сущность с тем же именем. При отсутствии основания бот естественно признаёт промах: например, «Да я сам Кирилла приплёл ни к месту, хз кого имел в виду». Не требовать этой фразы дословно, не запрещать мат. Не строить новые версии биографии из попыток обосновать первую выдумку.
5. Разделять «собеседник сообщил факт о себе», «другой участник пошутил», «бот ранее сказал», «внешняя ссылка утверждает». Без подтверждения self-report чужая шутка не превращается в устойчивый dossier. Исправления и противоречия сохранять со временем, не склеивать в единый бесспорный факт.
6. Не смешивать **исторических персон** с участниками чата из-за имени; источник, который релевантен запросу «расскажи о Кирилле и Мефодии», не релевантен запросу «кого ты сейчас Кириллом назвал?».

### 14.6. Статистика и инструментальные результаты не подменяют память

- `chat_statistics` и `query_chat_memory(stats)` запускаются/используются как **численные ответы только когда вопрос реально про количество, частоту, период, распределение** либо численная величина прямо нужна для ответа. Вопрос «кто такой Кирилл?» не предполагает подсчёт всех сообщений чата.
- `428494` из кейса — **пример опасной интерпретации**, а не установленный баг самого счётчика. Нельзя вывести «столько раз упоминали Кирилла» из широкого prefix/OR-поиска по другой области. Для сообщаемой цифры обязателен связанный `MetricResult`: metric, unit, actual query/match mode, time window, chat/sender scope, provenance и корректная формулировка результата. Невалидная/неполная область означает «не могу утверждать это число», а не 0 или «полная полнота».
- `coverage='full'` говорит о полноте **конкретного корректно определённого измерения**, не о доказательности отдельного факта. Сервисные поля `chat_id`, `method`, `match_mode`, `coverage`, `truncated`, `reason`, `source_ref`, `confidence`, `rank`, `status` не включаются в разговорную речь автоматически.
- Если пользователь **явно** просит технический отчёт, метод поиска или метрики — предоставлять точные данные понятным языком, а при необходимости структурой. **Не устанавливать общий запрет на числа/JSON/названия инструментов/темы технологий.** Исправлять границу данных и речевой вывод.
- `ToolResult.ok`, число найденных кандидатов и хороший score не означают «ценно для ответа». Model-visible результаты должны быть структурированными, безопасно сериализованными, ограниченными предметом запроса и с ясной ролью каждого поля. Out-of-band envelope остаётся в телеметрии.

### 14.7. Принцип «память возникает естественно», а не цитируется

Ожидаемый пользовательский ответ при обычном общении:

- Бот понимает текущую мысль и по необходимости использует подходящий прежний контекст **как предпосылку** ответа. Может шутить, припоминать знакомую ситуацию, отсылать к давнему разговору или использовать прошлое знание как основание, не объявляя об извлечении.
- **Не** говорит без причины «согласно графу памяти», «в моей базе найдено», «данные говорят», «я нашёл 8 фактов» и не перечисляет в столбик извлечённые фрагменты. Не вставляет случайные имена и сообщения ради объёма/эффекта осведомлённости.
- На прямое «что ты помнишь?», «откуда ты это знаешь?», «покажи, когда говорил» уместно назвать эпизод, дату, источник и даже привести требуемую цитату; ограничение относится к **непрошенному дампу**, а не к законному запросу пользователя.
- При точном FactCheck, статистике и историческом расследовании ссылки/даты/метод обязательны **по содержанию задачи**. «Натуральность» не является основанием скрыть источник или исказить факт.
- Не добавлять новый LLM-судейский проход, регенерацию, style sanitizer или хардкод на фразы «граф памяти». Использовать уже существующие инструкции Composer/Writer о различии **внутреннего evidence** и того, что составляет естественный ответ, с инвентаризацией действующих prompt revisions и owner overrides. Снять противоречащие требования «озвучь всю память» только там, где они реально есть.
- Сохранять произвольность живого разговора: это **политика контекстной полезности**, не автоматический запрет длинных сообщений или личных воспоминаний.

### 14.8. Диагностика и интерфейс: реализовать видимую цепочку отбора без новой подсистемы

Расширить существующий trace/drill-down в «Память» / «Истории» / «Аналитика» **вместо новой страницы**. Для каждого обращения к памяти показывать кликабельную цепочку:

`Триггер и reply → intent/topic/subject (если установлены) → вызванный инструмент → кандидаты → оставлены/отклонены с reason → контекст, переданный Writer → ответ`.

**Обязательные поля на карточке одного обращения:** дата/время, корреляция с сообщением/route, scope чата, purpose, выбранный инструмент и статус; raw candidate count, selected count, rejected count (только реальные значения); source type и кликабельный `source_ref` к сообщению/факту; роли `subject/speaker`, дата события/источника, trust/verification/stale; код причины отбора/отклонения; ошибка/деградация и флаг truncation; итог, попал ли факт в Writer или остался только candidate. Показывать **человеческое описание** причин, например «другой человек», «не связано с вопросом», «источник не подтверждён», «устаревшее/заменено», «уже присутствует», «только фоновый контекст».

Не строить интерфейс на фейковых нулях: для не записывавшихся ранее стадий — «Нет данных». Тексты приватных сообщений доступны только авторизованному администратору по запросу, без полного их копирования в обычные логи и LLM-провайдеры; в событиях только разрешённые идентификаторы/счётчики/статусы/хэши. Использовать существующие `correlation_id`, ToolResult, MCP events, provenance ledger, logger и существующие UI-паттерны; новый второй логгер, endpoint только ради красивого экрана или отдельная DB-копия истории не нужны.

**Структурные события**, переиспользуя существующий домен (имена согласовать с каноном): `memory_query_planned`, `memory_candidates_collected`, `memory_relevance_selected`, `memory_context_emitted`, `memory_result_used_or_suppressed`, `memory_identity_unresolved`, `memory_metric_not_applicable`, `memory_tool_payload_invalid`. Нужные причины: `topic_mismatch`, `other_subject`, `unknown_identity`, `unverified_attribution`, `stale_or_superseded`, `duplicate`, `self_generated_only`, `irrelevant_metric`, `invalid_tool_payload`, `prompt_excluded`, `no_relevant_candidates`. Не делать отдельный жёсткий лимит отбора или новый глобальный budget.

### 14.9. Реализация — последовательность обязательных изменений (не forensic-research)

**Это обязательные инструкции Builder/Architect, а не список вопросов:**

1. **Внести исправления в существующие пути** `get_user_context`, `query_chat_memory`, `dig_into_lore`, canonical retrieval, GraphRAG/relevance, alias-resolution, ToolLoop result packaging и Composer/Writer, перечисленные в §14.3. Сверка конкретного названия функции/схемы с HEAD допустима лишь как шаг интеграции. Нельзя закончить этапом аудита, запиской или «предположением о root cause».
2. **Провести контракт цели запроса** (тема/вопрос, тип намерения, субъект, reply, время, чат) от входа/Observer/L1 через существующий ToolContext/retrieval до выбора фактов. Добавлять поля аддитивно и совместимо; неизвестные значения оставлять unknown, а не синтезировать.
3. **Поправить выбор кандидатов**, отделив тематическую связь, идентичность, доказательность и временную применимость; исключить постороннее до Composer. Использовать действующие FTS/vector/rerank, не новый LLM/индекс. Проверить fallback, повторения, missing metadata и short casual turns.
4. **Исправить сериализацию** (прежде всего `str(fact)` в vector fallback) и model-visible контракт. В Writer попадают подходящие предметные сведения и служебные атрибуты как внутренний metadata context, а не как готовые абзацы/сырые Python dict для публикации. Обеспечить естественный вывод без цитирования памяти по умолчанию.
5. **Исправить resolution/self-correction**: no verified person without ID/достоверной связки; различить historical entity и чат; разобрать вопрос о собственном неверном именовании из предыдущего хода как вопрос о причине **этой реплики**, не как команду искать всех одноимённых.
6. **Изолировать статистические намерения**: счётчики и scope с typed MetricResult, без подмешивания в биографию/песню/обычную болтовню. Не отключать законные статистические запросы.
7. **Встроить телеметрию и существующий UI drill-down** с реальными selected/rejected decisions и provenance. Актуальные события должны позволять воспроизводить путь одного поиска. Не выдумывать telemetry за прошлые ходы.
8. **Написать воспроизводимые fixtures и тесты §14.10**, сравнить baseline/new по точности привязки к лицам, смысловой релевантности и сохранности стиля, затраты и задержки. Исправить реальные падения и интеграционные проблемы до Review PASS.
9. **Reviewer independently подтверждает runtime поведение**, включая негативные контролируемые сценарии, не только зелёные тесты Builder. После merge/deploy — контролируемая проверка без спама в чате, продолжение current_task, без ручной остановки после отчёта.

**Не является обязательным:** восстановить недоступный старый production trace, установить единственную причину исторического инцидента, написать 40-страничный read-only аудит, переобучить модель, изготовить новый эпик, ждать скрины от владельца. Если трасса есть — использовать её как дополнительную проверку; если нет — **не блокировать реализацию**, проверить контракт на зафиксированном fixture. Отсутствие старых журналов не является исключением из критериев приёмки.

### 14.10. Acceptance / Reviewer — конечные проверки, воспроизводимые без реального чата

**Реконструкция текущего сбоя:**

1. На шуточный транслит песни и слово «фактчек» бот без надёжных внешних свидетельств не выдумывает оригинальную песню и не делает это памятью о посторонних людях. Сохранить разговорный стиль и уместный разбор.
2. На «как же он разобрал ...» контекст без установленного адресата/имени не создаёт достоверную идентичность «Кирилл», не называет случайного участника LLM или музыкальным распознавателем.
3. Если в предыдущей реплике бот **сам необоснованно ввёл Кирилла**, на «бот кто такой Кирилл» он может признать, что ошибочно употребил имя; не выдумывает «олдфага», «аспиранта», череду независимых персон и не маскирует свою ошибку псевдоисточниками.
4. Исторический факт, содержащий имя Кирилл (включая религиозных деятелей), **не получает идентичность участника чата**; при прямом вопросе о конкретном историческом человеке соответствующий факт доступен.
5. Запрос «кто такой Кирилл» не вызывает/не цитирует **428494** или любое широкое несвязанное измерение. Никакие `chat_id/method/coverage` не попадают в обычный текст; при явном статистическом запросе корректная scope/unit/method-величина доступна.
6. Память содержит десятки unrelated фактов о нескольких участниках: в ответе **нет дампа посторонних историй**, но на последовательные тематические вопросы эти факты по-прежнему извлекаются.

**Семантика и идентичность:**

7. `general` lookup с `person + topic` выбирает относящиеся к теме сведения и не выносит биографию, когда пользователь говорит о песне.
8. Отдельный direct recall «вспомни старый спор о X» может достать старый эпизод и упомянуть его без шаблонного перечисления; не потерять длинную память только потому, что событие старое.
9. Лёгкий дружеский callback на прошлое событие допустим при явной смысловой связи без команды «вспомни»; не превращать все short turns в «не помню».
10. Несвязанные высокий vector score и lexical name-match не вытесняют менее похожий, но нужный `SourceRef` с верным `subject_entity_id`/reply anchor.
11. Рядом находятся два одинаковых имени в одном/разных чатах; никакого cross-user и cross-chat слияния; неизвестный `user_id` не отображается как проверенная личность.
12. Различаются `speaker`, `quoted_speaker`, `subject`, `reply target`, `author`, `bot_output`; чужой подкол об ИИ не сохраняется как доказанный факт, будто человек — нейросеть.
13. Старый факт с явной датой и свежим опровержением не выдаётся как актуальное положение дел; по историческому вопросу остаётся с правильной датировкой.
14. Противоречащие рассказы не превращаются в синтетическую «достоверную биографию»; когда пользователь спрашивает непосредственно, бот честно объясняет неопределённость.
15. Нормальные факты (например, знакомство, предпочтение, история группы) используются как **внутренняя опора разговора**, а не буквально цитируются после каждого вызова.
16. Прямой «покажи источник / когда он об этом говорил» даёт корректный первичный `SourceRef` и дату либо честно признаёт отсутствие; не подавлять provenance по запросу.

**Инструменты и упаковка:**

17. FTS empty → vector fallback с dict/object: в Writer не попадает `{'fact':...}` как готовая речь и финальный ответ не содержит внутренний Python repr/JSON metadata.
18. `get_user_context`, `query_chat_memory`, `dig_into_lore`, existing canonical retrieval, GraphRAG и direct context composer согласованно применяют общий смысловой и identity-контракт на затронутых маршрутах.
19. Mixed tool calls (memory→web→factcheck, web→memory, reply→memory): типизированный evidence не подменяет task/фактчек, tool statuses и мета-поля не выдаются за фактический ответ.
20. При no-data/stale/empty/error/truncated модель либо даёт нормальный ответ без незапрошенного filler, либо честно признаёт отсутствие именно запрошенного факта; не блокирует отправку.
21. Stats requested explicitly — корректная численная величина + unit, scope, метод и даты; stats unsolicited — не попадает в биографический/разговорный ответ. Проверить и numeric-claim guard, не менять его полномочия.
22. Ни одного дополнительного LLM-прохода ради relevance, нет нового Validator Loop, нет пересоздания эмбеддингов, нет бессодержательных строгих лимитов на число фактов.
23. Форматированный фактчек про Иран сохраняет доказательность, ссылки, естественный стиль/мат, **без внезапного unrelated фрагмента памяти**. Приписка о картинке появляется только при реальной текущей image target/request.
24. Логи и админка отражают фактические кандидаты/selected/excluded и коды причин; где события не сохранены — `Нет данных`; исходные приватные диалоги не публикуются в обычные логи.
25. Reviewer подтверждает не только прохождение своих и Builder тестов, но и качество 8–12 обезличенных пар **query → retrieved candidates → response**, включая дружеский юмор и случаи правильного молчания о памяти.
26. Время/расход токенов на сходных запросах не растут из-за новой модели/дублирующего ранкера; при ухудшении выяснить и исправить до PASS, не маскировать повышением лимитов.

### 14.11. Защита от неверных «исправлений»

**Недопустимо выдавать за выполнение:**

- исследовательскую записку и рекомендации без merged working code;
- глобально выключенную память, ToolLoop, инициативу, RAG или весь профиль участника;
- бессмысленный regexp на слово «Кирилл»/«нейросеть»/«граф памяти» или постфактум scrub финального ответа;
- новую per-turn LLM-проверку фактов памяти, дополнительные генерации, бесконечный retry или отдельный «агент качества памяти»;
- выбор «первых N фактов» без проверки того, о чём текущая реплика, кто субъект и что подтверждено;
- запрет всех цифр/ссылок/цитат/технических объяснений даже там, где пользователь их прямо запрашивает;
- исключение старых или неожиданных воспоминаний только по давности или «не главная тема», если они реально полезны;
- молчаливое изменение user ID / алиаса для подгонки тестов; чужая шутка ≠ self report;
- пересборку эмбеддингов или замену провайдера, другую БД/память, новый Prompt Composer, повторные источниковые хранилища;
- «исправлено» лишь потому, что бот ответил коротко, не использовал память или перестал ругаться;
- закрытие задачи с `NOT_VERIFIABLE` только потому, что старые production traces не сохранились. Новый fixture + наблюдаемое runtime-поведение **обязательны**.

**Связь с AntiCliche:** это независимое устранение ошибок понимания, памяти и подачи контекста, не добавляющее AntiCliche исключений, отказов/перегенерации или вторую стилевую подсистему. В одном EVOL допустимы параллельные задачи при разных критериях приёмки и переиспользовании общего Prompt Registry и UI.


### 14.12. Усиление архитектурного контракта: память и собственные высказывания бота

**Обязательная реализация без создания подсистем:**

1. **Разрешение вопроса об имени, которое только что назвал сам бот.** При реплике «кто такой X?», «какой X?», «ты о ком?», «что за человек?», в первую очередь установить, относится ли вопрос к предыдущему собственному высказыванию бота, используя имеющиеся `reply`/thread/последние сообщения и существующий журнал исходящих сообщений. Вывод «сам назвал X» — это provenance для контекста, **не** доказательство, что X реально существует как участник. Если надёжной личности нет — честно поправить собственное употребление, не сочинять биографию. Историю чата и персональные досье использовать, только если в запросе есть связь с конкретным человеком/темой либо эту связь подтверждает первичный источник.
2. **Никаких буквальных ловушек.** Запрещено распознавать этот случай по regex/списку `Кирилл|нейросеть|Шазам`, по фиксированным фразам «кто такой» или по идентификатору конкретного чата. Требуется общий механизм reference/subject resolution, который работает и для другой формы имени, клички, роли, местоимения, quoted speech, нелинейных цепочек `reply`, а также для случая, где собственное сообщение бота имеет неоднозначную ссылку. Ни одно слово само по себе не делает человека известным или неизвестным.
3. **Свой ответ ≠ внешняя память.** Предыдущие сообщения бота различать с входными сообщениями и историческими фактами, не переписывать `user_id`/`author` и не сливать утверждения модели с self-report человека. Статус собственного неверного утверждения должен позволять исправить его разговорно; **не** создавать отдельное долговременное досье «ошибка бота» и не загрязнять GraphRAG этим исправлением как фактом о пользователе.
4. **Общий контекст запроса через уже существующие структуры.** Передавать текущий intent/topic, актуальный вопрос, чат, thread/reply, предполагаемый subject, время и тип источника сквозь работающие `ToolContext`, канонический retrieval и Composer. Если отдельный атрибут уже представлен — переиспользовать. Если отсутствует — минимальное аддитивное поле в действующем контракте, без новых сервисов `MemoryJudge`, `QueryPlanner2`, `IdentityResolver2`, новых индексов/таблиц копий и без тяжёлого дополнительного pipeline.
5. **Разделить выбор фактов и их словесную подачу.** Retrieval даёт кандидатов, различая релевантность, субъект, дату, источники, подтверждённость и связь с вопросом. Composer получает выбранную доказательную опору, не готовый список фрагментов для дословного зачитывания. Writer может применить память неявно, пошутить на основании неё или не упоминать ничего; при прямом запросе источника/фактов — дать их точно, а не скрыть. Не вынуждать цитировать всё найденное и не превращать отсутствие результата в шаблон «в базе нет данных» для обычной беседы.
6. **Соблюдать датировку и отрицания.** Событие, рассказанное три года назад, не становится текущим состоянием; противоположный свежий факт и статус противоречия учитываются, но старый эпизод остаётся доступным в историческом вопросе. Чужая реплика, шутка, форвард и собственный факт человека не получают равный уровень доверия только потому, что есть в одной таблице.
7. **Перевести существующие tool-ответы в корректный model-visible формат.** Не отдавать готовой речи сырые `str(dict)`, `repr`, `chat_id`, `confidence`, `source_ref` и кодовые поля как абзацы естественного текста. Не исправлять это regexp-зачисткой исходящего Telegram. Данные provenance должны оставаться доступны для явных источников/статистики/админской трассы. Проверить склейку tool outputs и неожиданных довесков от других задач.
8. **Статистика только при релевантном intent.** Вопрос о человеке/песне не разрешает подмешивать 428494, префиксные OR-счётчики и служебную полноту измерения. При явном статистическом вопросе не отключать счётчики, а использовать типизированные `MetricResult` с реальными scope, method, unit, временем и доказуемым числом.
9. **Никаких новых бюджетов и скрытых повторов.** Не вводить `max_memory_facts=3`, `20-minute stall`, caps по длине обычного ответа, бюджеты на число воспоминаний, токеновые квоты/измеряемые «красные линии» без доказанной необходимости для работающего интерфейса/безопасности. Не ослаблять существующий разумный механизм предотвращения переполнения запроса, но не выдавать механический `top N` за релевантность. Нельзя запустить второго LLM-судью на каждое сообщение или перегенерацию из-за памяти. Показатели латентности/токенов — **телеметрия и регрессия**, а не новый блокирующий бюджет.
10. **Никакого `human gate` по техническим вопросам.** Архитектор самостоятельно решает по текущим исходникам, как перенести контекст в функцию, где разместить поля, как сериализовать ToolResult, какие тесты написать и какие запросы сделать к БД. Поднять вопрос владельцу только при действительно неразрешимой продуктовой развилке; техническая ошибка возвращается Builder/DevOps на исправление, не становится причиной остановки.

**Дополнительные обязательные тесты:** (a) одно и то же содержание диалога с минимум пятью различными вымышленными именами/алиасами и изменёнными формулировками; (b) `reply` на собственное ошибочное высказывание и follow-up без явного `reply`; (c) имя встречается в историческом тексте, но не относится к участнику; (d) два человека с одинаковым именем; (e) бот произнёс имя в цитате другого человека — это не self-report; (f) свежий и устаревший противоречащие факты; (g) связанный и несвязанный RAG-кандидат с обратным порядком scores; (h) обычная разговорная отсылка к памяти остаётся возможна; (i) явная просьба об источнике действительно показывает первичный источник; (j) статистика по явному запросу работает, по биографическому не вмешивается. Reviewer проверяет исходники на специальные условия по буквальным словам из кейса, подмену top-k и отдельные LLM-регены.

## 15. ASAP-ADMIN-UI-RUNTIME-01 — мобильная загрузка, история ошибок, выбор чата, тумблеры модулей, мем-инициатива

**Тип:** обязательная реализация существующего веб-приложения (Telegram Mini App + desktop), не отдельный дизайн-эпик, не предложение макета. Основной визуальный язык (тёмное стекло, рефракция, геометрический фон, действующая навигация) **сохранять**; устранять неисправности функционала и компоновки без удаления эффекта стекла. Скриншоты 02.11.2026 — критерии воспроизведения, а не разрешение менять всю админку.

### 15.1. UX приложения при первоначальной загрузке и при сбоях

**Сейчас:** Telegram Mini App иногда остаётся на «Загружаем настройки…», под надписью три скелетон-полосы не завершают отображение. Нельзя интерпретировать анимацию скелетона как подлинный процент загрузки. Нельзя выпускать страницу, которая бесконечно выглядит загружающейся после завершившегося/провалившегося запроса.

**Обязательное поведение:**

- Начальный экран отделяет состояния `initializing`, `loading`, `ready`, `empty`, `degraded`, `error`, а также **повторную попытку**, не смешивая их. Реальное разрешение готовности определяется завершением необходимых async-запросов и обработкой ответа, а не фиксированным `setTimeout(3000)` или «доползанием» CSS-полосы до 100%.
- Три полосы являются **скелетонными плейсхолдерами**, а не прогресс-баром; они могут визуально двигаться, пока грузится соответствующий контент, но **обязаны исчезнуть** при `ready`, `empty` или `error`. Если необходим настоящий процент — он строится только на измеряемом количестве завершённых известных шагов; не рисовать фиктивные 90–99% при неизвестном объёме работы.
- Не дожидаться всех вторичных карточек/аналитики для показа уже пригодного основного интерфейса. Показать живую оболочку с навигацией и фактическими данными, а отдельные панели до-загружаются в своём состоянии. Ошибка одного раздела не удерживает весь стартовый экран.
- На разрешённой ошибке конфигурации/авторизации/сети дать разборчивый статус с причиной и рабочую кнопку «Повторить»; если разрешён безопасный stale-cache — указать, что показана старая информация. Не выдавать «настройки загружены», когда fetch завершился 401/403/500/HTML вместо ожидаемого JSON.
- При blur/focus, возврате из меню, смене глобального/чатового scope, закрытии модального окна и повторном открытии Mini App не застревать в прежнем loading. Исключить `Promise` без терминальной ветки (`finally`), гонку двух запросов, устаревшие результаты перезаписи выбранного чата и бесконечные retry после ошибки.
- На Android/Telegram WebView корректно учитывать безопасную область, нижнюю системную панель, экранную клавиатуру и изменения высоты viewport. На ширине 390 px не должно быть бокового горизонтального скролла/обрезанных кнопок; на 1536 px сохраняется существующая композиция. Скелетон/спиннер поддерживает `prefers-reduced-motion`.

**UI-акцептанс:** быстрый ответ, медленный ответ, 401/403, 5xx, network error, пустой список настроек, повторная попытка, переключение чатов до окончания запроса, смена вкладки, возвращение из background. У каждого сценария есть завершённое состояние без вечных трёх полос. Reviewer наблюдает экран физически/через browser mobile emulation, не принимает только тест `fetch mocked → 200`.

### 15.2. Полные логи с начала запуска вместо расходящихся счётчиков

**Воспроизведение:** экран «Статус» показывает «Ошибок с момента старта: 42», но журнал в «Аналитике» отображает `ERROR 0 / WARN 3` и три предупреждения. Пример из предупреждений: `tool-loop degraded reason=partial`, `tool_call status=denied`, `[vision] claim sweep slow`. Вывод: текущие **видимые** ошибки не охватывают весь период, к которому относится накопительный счётчик; это не основание приравнивать предупреждение к ошибке.

**Обнаруженная кодовая граница (публичная `master` на дату ТЗ):** `services/status_service.py` отдаёт `bot.errors_total` через `services/log_ring.py::get_errors_total()` — накопительный счётчик процесса; `/api/status/logs` в `web/api/routes.py` берёт `get_entries()` из `deque(maxlen=LOG_RING_MAX_ENTRIES)`, по умолчанию 1000, и `level_counts()` считает **только сохранённое в кольце**. Уже после заполнения кольца эти числа закономерно расходятся. Просто повысить maxlen, проставить `limit=1000` или переименовать «ошибки» в «предупреждения» **не считается исправлением**.

**Требуемый контракт данных:**

1. Для текущего запуска доступен **полный перечень log records с момента фактического начала логирования**, а не последние N сообщений. Использовать существующий штатный долговечный sink (file/journald/приложенный journal, если он реально доступен этому deployment); при необходимости аддитивно обеспечить сохранение записей через существующую logging инфраструктуру. Не строить второй независимый logger, не дублировать весь raw stream в новой таблице PostgreSQL только ради UI. Если прежняя часть текущего запуска безвозвратно утрачена, **не имитировать восстановление**: показывать честную нижнюю границу `доступно с ...` и разрыв; **для новых запусков после исправления** полный охват обязателен.
2. Каждая запись имеет достоверные `timestamp (UTC+отображение local)`, `level`, `component/logger`, `message` (sanitized), `startup/run epoch` (или эквивалентный идентификатор процесса/запуска), а где имеется — `chat_id`, `trace_id`, `pipeline_run_id`, `reason_code`; без фантомных полей из regex, если их источник неизвестен.
3. Один и тот же backend-набор и одно и то же определение определяют «ошибки с момента запуска» и фильтр истории `ERROR/CRITICAL` за **тот же run epoch**. Отдельно учитывать `WARNING` и информационные события; общие «Проблемы: 4» иметь видимое объяснение и drill-down, не представлять как количество ERROR. Если на экране разные scopes/сервисы (web, bot, worker) — явно подписать их и не сравнивать как единый счётчик.
4. API и UI поддерживают **постраничный** read/scroll назад до старта эпохи: стабильный cursor по времени+монотонному ID, порядок newest→oldest, выбор level и свободное фильтрование по существующим `trace_id`, `chat_id`, `component`, `reason_code`; «Загрузить ещё»/infinite scroll без потери позиции и дублей. Конкретный размер транспортной страницы — только для производительности и может меняться; **не** новый бизнес-бюджет, не ограничение глубины истории и не 1000 записей как потолок.
5. На экране журнала обязателен заголовок: `Запуск: <фактическое время>` / `Доступно с: <timestamp>` / `Покрытие: полное | частичное` / `Всего за запуск: ERROR N, WARNING M` / `Показано: K из ...` по фильтру. Если точное полное количество неизвестно, показывать `Нет данных`, а не ноль. Смена уровня/чата/поиска не уничтожает доступ к ранним страницам и не подменяет count текущей маленькой выдачей.
6. Реальный `timestamp` в статусной карточке форматировать по локальной зоне приложения понятной датой и временем; ISO UTC хранится для машинной трассировки. `errors_since_start` никогда не используется как `errors_in_last_200_logs` без явной подписи. Переход «К логам» из статусной карточки открывает журнал с применённым `ERROR` и run epoch, а не просто прокручивает вниз к последним трём WARN.
7. Полный текст ошибок, включая stacktrace, доступен **только** имеющему соответствующие права администратору. Сохранять действующую очистку секретов, URL credentials, личных сообщений и PII. Глобальные логи не раскрывать обычному участнику/админу другого чата; при фильтре чата видны только разрешённые события, отдельно — разрешённые глобальные системные ошибки. Нельзя ценой истории сломать безопасность `/status/logs`.
8. Ротация файлов/рестарт web-процесса/новый bot run не должны молча создавать впечатление полноты: эпохи, состояние архивирования и реальное наличие старых логов явно разделять. При штатной ротации логи **текущей эпохи** не должны пропадать из UI.

**Приёмка:** генерировать в безопасном локальном тестовом запуске несколько ERROR и WARNING, затем значительно больше INFO, чем размер текущего ring; проверить, что ошибки с начала запуска открываются и общие числа совпадают с тем же фильтром. Проверить две последовательные выгрузки через API, reload клиента, поиск по `trace_id`, отсутствие дублей/пропусков, RBAC, отсутствие секретов. Не притворяться, что прошлые 42 записи можно восстановить задним числом, если источника этих записей нет.

### 15.3. Селектор чата: раскрытие должно быть у самого селектора, а не у нижнего края экрана

**Сейчас:** выпадающий список для селектора «Весь бот / GLOBAL / <чат>» расположен в верхней шапке, но на мобильном открывается как огромное меню **внизу экрана**, оторванное от управляющего элемента.

**Желаемый UX — точно:**

- При касании верхнего селектора под ним (или непосредственно над ним при реальном недостатке места) возникает **привязанный к селектору popover** с видимой строкой поиска, «Весь бот», разделителем и доступными чатами. Его позиция и ширина рассчитываются относительно trigger; не рисовать фиксированный `bottom:0` или modal bottom sheet. В обычном случае открывается **под header selector**, не по центру и не у системного жеста Android.
- Popover поверх контента с корректным stacking context даже при glass/refraction/transforms, не обрезается `overflow:hidden` родительского контейнера. Обновляет координаты при прокрутке/resize/Telegram `viewportChanged`, умеет поместиться в доступной высоте и имеет **собственный скролл** списка; задняя страница не прыгает.
- Полная иерархия: поисковое поле; отдельная строка `Весь бот` с маркировкой `GLOBAL`; затем чаты с аватаром/названием и читаемым scope/ролью. Строки/поля не должны быть обрезаны так, что нельзя понять выбранный чат. Не показывать недоступные по RBAC чаты.
- При выборе: явно устанавливается один scope, меню закрывается, выбранная область видна в заголовке; все связанные экраны перечитывают scoped данные в соответствии с выбранным контекстом. Повторное открытие показывает выбранную строку. Отмена/закрытие/тап снаружи/`Escape` закрывает без изменения; Enter/клавиатурная навигация работают в web; 44px+ тач-цели.
- Смена чата во время медленного запроса не должна позволять опоздавшему старому ответу перезаписать новую область. Фокус/клавиатура Android не сдвигают меню за границы видимой области.

**Приёмка:** 390×844 Telegram Android WebView, маленькая высота с клавиатурой, длинное имя чата, ≥10 чатов, пустой поиск, смена области в «Статус», «Модули», «Речь и характер», «Аналитика». Скриншоты открытого меню и выбранного scope, проверка hit testing и z-index. Никакого root-level dropdown, не привязанного к trigger.

### 15.4. Единый контракт тумблеров модулей в GLOBAL и конкретном чате

**Нынешний дефект:** на экране «Модули» при `GLOBAL` почти все карточки имеют тумблеры; в чатовом scope у части карточек тумблер исчезает, без понятного объяснения доступного управления и действующего значения. Публичный CSS уже содержит `module-toggle.is-readonly`, `.module-global-hint`, `.module-global-btn`; **не плодить вторую параллельную визуальную модель**, довести существующий путь до целостного поведения.

**Единая классификация модулей на основании реального runtime/config schema:**

- **Per-chat override разрешён:** в `GLOBAL` виден мастер-тумблер глобальной настройки; в выбранном чате видны **тот же** master-state индикатор и явное управление `Наследовать глобальную / Включить для чата / Выключить для чата` (три состояния либо доступный эквивалент в однозначном UI), с заметным `Эффективно: включено/выключено` и `Источник: GLOBAL/этот чат`. Переключение влияет на настоящий runtime, не только на UI; reset к наследованию удаляет override, не копирует текущее глобальное значение.
- **Реально global-only:** в чате карточка по-прежнему показывает положение тумблера как **read-only** (не исчезает!), ярлык `Управляется глобально` и кнопку `Настроить глобально` для пользователя с разрешением. Для пользователя без прав — честный RBAC-индикатор без активной редактируемой кнопки. Нельзя фальсифицировать per-chat действие, если backend/runtime его не поддерживают.
- **Модуль неприменим в конкретном scope:** показать доступную читаемую причину `Недоступно для этого типа чата` или `Нет прав` и статус, не молча удалить переключатель и не выдавать `выключено` при unknown. Не превращать все глобальные модульные флаги автоматически в чатовые; разрешённость должна совпадать с настоящей конфигурацией.

**Компоновка карточки (во всех случаях):** название и краткое назначение; видимый переключатель/его read-only положение в правой верхней части; рядом либо прямо ниже — состояние `Включено/Выключено` и происхождение; `Настройки` открывают параметры в том же scope, если он применим; глобальные-only ведут на global настройки, сохраняя возможность вернуться к выбранному чату. Во всех режимах сохранять одинаковые размеры карточки и слоты действий, без скачка верстки и невидимых кнопок.

**Требования к backend:** UI читает фактический `global`, `chat_override` (если существует), `effective`, `source`, `editable_here`, `scope_type`, `reason`. При переключении scope не переписывать config, не терять несохранённые изменения без предупреждения, не сохранять глобальный секрет в чатовый слой, сохранять optimistic/concurrency контракты. Предпросмотр и actual runtime обязаны давать одинаковое effective. Не добавлять независимое хранилище модульных тумблеров.

**Приёмка:** полная матрица по реальным модулям из реестра, не только по двум примерам: GLOBAL ↔ chat A ↔ chat B; унаследованное ON, унаследованное OFF, override ON, override OFF, reset; global-only виден и честно read-only; RBAC глобального и локального админа; reload и restart; быстрые смены scope; кнопка `Настроить глобально`; совпадение с фактическим server effective.

### 15.5. Мем-инициатива: глобальные настройки обязательны, чатовые — наследуемые

**Нынешний дефект:** мемы в «Инициативе» можно настраивать только после выбора определённого чата; в `GLOBAL` поля отсутствуют либо недоступны. Это противоречит общему принципу настройки. **Целевое правило:** глобальный администратор задаёт базовую конфигурацию мем-инициативы **в глобальной области**, а каждый чат может наследовать её либо явно переопределить там, где этот параметр по смыслу зависит от чата.

**В GLOBAL — обязательные видимые и сохраняемые controls действующей мем-инициативы:** `enabled` (включена/выключена), текущий шаблон промпта для генерации мема (редактируемый, без скрытой замены), лимит мемов в сутки (сохранить существующее значение по умолчанию — исторически 3, сверить реальный config), настройки выбора/инициирования и остальные **действительно существующие** параметры модуля, если предусмотрены runtime; источник/время и effective. Не выдумывать новых генераторов, квантовых переключателей или параметров ради заполнения UI. Модель и подключение показываются через уже действующий выбор моделей, без дублирования ключей. Global save действительно влияет на чаты, не имеющие override.

**В конкретном чате:** для каждого разрешённого per-chat поля показывать `Эффективное значение`, `Источник (Global/Chat override)` и `Наследовать/Изменить`. При редактировании chat override сохранять только заданную разницу; остальные глобальные изменения продолжают наследоваться. `Сбросить переопределения` возвращает наследование, а не сбрасывает глобальный шаблон или лимит. Для действительно global-only параметра отображать значение read-only и возможность перехода в global при наличии прав.

**Проверить реальное исполнение:** schedule/инициатива/мем-worker разрешает одинаковые effective значения, получаемые через UI и backend; не должно быть скрытого chat-only default, из-за которого глобальные настройки невидимы или игнорируются. Не менять генеративный pipeline и лимит в сутки без необходимости; **не добавлять новые бюджеты**. Если функция отключена глобально, чатовая политика должна соответствовать текущим разрешённым override rules, ясно показывая, почему мемы включены или выключены; не противоречить остальной матрице модулей.

**Приёмка:** (1) настройка GLOBAL сохраняется и видна после reload; (2) chat A без override наследует новые глобальные значения; (3) chat B с override сохраняет только изменённые поля; (4) сброс chat override возвращает global; (5) два чата работают независимо; (6) global и локальный администратор получают корректные права; (7) tooltip/label показывает true provenance; (8) фактический запуск мемов читает тот же effective; (9) нет нового duplicate prompt editor для мем-инициативы в другом разделе.

### 15.6. Сквозные требования к UI, состояниям и независимому Review

- Не вводить новые sidebar-разделы для этих пяти багфиксов, если уже существуют «Статус», «Аналитика», «Модули», «Инициатива» и header-selector. Нужные поля и тексты внедрить в эти места. Исключение — уже предусмотренная полноценная страница AntiCliche в «Речь и характер» (§5).
- В Android шириной 390 px обязаны быть доступны действия без горизонтального скролла; контент под клавиатурой не закрывается. На desktop 1536×960 не нарушать плотность и визуальную иерархию. Не сломать кастомные glass backgrounds, refraction, sticky header, системные safe areas, шрифты и анимацию; не заменять всю тему админки.
- Кнопка/тумблер/селектор **не считаются работающими**, пока реальное API изменение и runtime effective не подтверждены. Disabled state, loading, success, error, conflict и no-data демонстрируются на реальных/замоканных backend сценариях, а не на заранее заполненных декоративных объектах.
- Проверять screenshot-паритет и взаимодействия через настоящий browser/WebView harness, в том числе touch, scrolling, focus, open/close/popover, late requests. Для ошибок загружать не один скриншот, а систематические кейсы. Исправить ошибки консоли/сети, которые влияют на конкретные экраны.
- Не смешивать scoped global/chat конфигурацию и глобальные process logs: разные понятия подписывать. Не ломать существующие RBAC, safe logging и owner controls.

## 16. Общий план реализации и неизменные инженерные запреты

**Эта секция распространяется на AntiCliche, Memory и Admin UI одновременно.**

1. PM обязан создать из этого ТЗ исполняемые задачи с зависимостями, задействовав существующих Architect/Builder/Reviewer/DevOps. Разрешён параллелизм независимых участков, но не два писателя в одни файлы одновременно. Никаких новых workflow-систем, новых агентов, `openspec` или новой `current_task` ради этого документа.
2. Architect делает только рабочие проектные решения там, где код требует связать уже существующие части; **реализация обязательна**. Рабочие пакеты: (A) AntiCliche, (B) memory/relevance и self-reference, (C) loading/header selector, (D) logs/observability, (E) module-scopes/meme. Если текущий runtime уже имеет часть механизма, расширить её, а не продублировать.
3. Начать с HEAD/deployed SHA и списка действительно затронутых точек; проверка версий — краткая часть внедрения, не отдельный исследовательский отчёт. Не переписать DONE_AND_VERIFIED. При конфликте с другими EVOL/ASAP внести совместимую правку или скоординировать очередь; не терять этот файл среди отчётов.
4. **Запрет тематического хардкода:** никаких `if name == "Кирилл"`, чатов из данного скриншота, статического списка «случайных» людей, regex на исходящую фразу «граф памяти», специальных веток «фактчек про песню», фиктивных успешных тестовых данных в production. Правила должны обобщаться на новые темы, имена, alias и последовательности сообщений.
5. **Запрет расползания архитектуры:** нет второго memory engine, data store, LLM judge, `QualityAgent`, BudgetManager, дублированного Prompt Composer, логгера, UI-state store; для новых решений использовать действующие retrieval, ToolContext/ToolResult, Prompt Registry, ConfigCache, background worker, log sink и UI-компоненты.
6. **Запрет дополнительных искусственных бюджетов/таймаутов:** не вводить произвольные per-turn и per-process cap'ы, 20-минутный watchdog, ограничение фактов до N ради зелёного теста, искусственный потолок tokens или жёсткий TTL, который может прерывать законные долгие операции. Существующие меры безопасности и защиты от реального переполнения/эксплуатационного отказа сохранить, но не создавать новые ворота без обоснованного риска. Пагинация истории логов — способ транспорта, **не** лимит истории.
7. **Запрет нового retry для стиля/памяти:** никакой перегенерации из-за клише или случайно упомянутого факта. Нельзя притвориться, что style rejection стал independent form guard. Не ломать действующие доказательно нужные fact/numeric/security gates.
8. **Инженерные трудности не human gate:** вопросы типа CSS positioning, поля конфигурации, выбор существующего лога, корректная сортировка фактов или тесты — компетенция Architect/Builder; когда Reviewer находит дефект, вернуть на исправление. DevOps при ошибке деплоя обязан довести до рабочего результата, а не закрывать задачей «невозможно».
9. Сначала сделать backend-состояние и настоящие API-контракты, затем UI поверх реальных данных. Ни одна аналитическая цифра не может быть вымышленной. Если источник отсутствует, в UI честно `Нет данных`; если операция недоступна, причина и рабочее recovery-действие.
10. Все затронутые prompts versioned через действующий registry. Новые стилевые инструкции не удаляют русский язык, мат/сленг по owner mode, прямую критическую манеру FactCheck. Прежние чаты/настройки не терять, existing embeddings/apinet model не перестраивать. Миграции PG — только когда действительно необходимо, с rollback и проверкой данных; не плодить параллельные таблицы.
11. Каждый merge/deploy сопровождается smoke/health с реальными runtime значениями, включая мобильный UI, сохранность пользовательских overrides, отсутствие дополнительных LLM-вызовов, статус источников и logs coverage. Тесты без живого спама по Telegram, разрешён только контролируемый smoke там, где это безопасно.
12. Не завершать весь `current_task` после выполнения этого файла: вернуть управление оркестратору, обновить исполняемые статусы и продолжить следующую работу автоматически в соответствии с текущим workflow.

## 17. Единая конечная приёмка, которую нельзя заменить отчётом

**AntiCliche (обязательно §9):** исходники и runtime подтверждают 0 AntiCliche-only retry, полезные русские источники, частичный отказ 403 без потери LKG, source/model/candidate/publish trace, видимый полный published rule set, точный дополнительный prompt Writer и один toggle в «Речь и характер».

**Memory (обязательно §14):** пять+ переименованных версий кейса; бот не притворяется, что ошибочно названный им самим человек — известная личность; не смешивает одноимённых людей и исторических персонажей; использует тематический контекст; проверяет даты, provenance, противоречия; не выдаёт непрошенный дамп/поле `chat_id`/428494; сохраняет возможность естественных callbacks и точного показа источника по прямому запросу. Нет новой LLM-проверки или жёсткого лимита на число воспоминаний.

**UI loading:** для success/slow/error/retry/bootstrap все состояния завершаются, скелетоны исчезают, карточки не застревают; прод и тестовый WebView на мобильном корректно отображаются.

**Logs:** для одной эпохи `errors_since_start == count(ERROR+CRITICAL)` по полной доступной истории после внедрения; WARN отдельный. После вытеснения ring запрашивается самая ранняя запись активного run, cursor pagination без дублей, role scope и sanitization соблюдены. Исторический недоступный gap открыт текстом и не рисуется зелёным.

**Chat selector:** popover визуально привязан к top trigger, не к нижнему экрану, работает touch/keyboard/search/safe area; quick switch не приводит к поздней перезаписи старого чата.

**Modules:** все карточки показывают статус и реальное происхождение значения в GLOBAL и CHAT; доступный chat override редактируется и сбрасывается; global-only отображается read-only; RBAC и actual runtime не расходятся.

**Meme initiative:** GLOBAL содержит реальные настройки мемов, наследуемые чатовыми; per-chat delta, reset, refresh и фактическая генерация соответствуют выбранным значениям, сохранены исходный промпт и заданная суточная политика, новых budgets нет.

**Reviewer обязан независимо:** (i) просмотреть исходники на хардкод/дубли/новые budgets и скрытые retry; (ii) сделать отрицательные и неочевидные кейсы кроме тестов Builder; (iii) пройти приложение на реальном/эмулированном Android viewport и desktop; (iv) сверить UI с API и persistent state; (v) дать ссылки на тесты, скриншоты, run IDs, QA-доказательства и deployed SHA. `PASS` допустим только при полном рабочем контракте. `NOT_VERIFIED` не равен `PASS`; если живой внешний сервис ограничен политикой, честно зафиксировать внешний blocker и подтвердить внутренний контракт контролируемым fixture без ожидания недели. По исправимым техническим проблемам — возврат Builder/DevOps, без human gate.

**Человеческий отчёт workflow:** дата/время в действующей зоне, `выполнено/всего`, одно ASCII progress bar, простые названия фич, какая роль что делает, что дальше. Технический отчёт не подменяет человеческий; завершение итерации не означает остановку оркестратора.
