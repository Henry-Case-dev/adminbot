# FACTCHECK POST-RELEASE CORRECTIVE — Устойчивость к отказам инструментов, полноценная проверка без интернета и отказ от кеширования вердиктов

**Тип:** обязательная корректива существующей архитектуры Fact-check  
**Основание:** production-инцидент 28.10.2026  
**Проверенная кодовая база:** `release/p0-2026-10-26`, релиз 2.58.135 по последнему отчёту  
**Порядок:** добавить к действующей очереди после ранее зарегистрированных задач, не прерывая POST-ASAP5 и текущую работу  
**Статус:** заменяет предыдущую версию FACTCHECK POST-RELEASE CORRECTIVE

## 0. Основное требование владельца

**Fact-check не должен прекращать содержательную проверку только потому, что недоступен интернет-поиск или другой необязательный инструмент.**

Поиск - это источник дополнительной информации и доказательств, а не фундаментальное условие функционирования Fact-check.

Если поиск недоступен, бот обязан продолжить проверку настолько, насколько позволяют:

- Само утверждение.
- Контекст текущей беседы.
- Доступная история сообщений.
- Уже полученные и проверяемые материалы.
- Существующая память и provenance.
- Общие знания модели с учётом возможной устарелости.
- Логическое рассуждение.
- Математические и технические вычисления.
- Анализ внутренней согласованности утверждений.

Неудача поиска сама по себе не является причиной выдавать пустой ответ или превращать Fact-check в сообщение об ошибке.

**Цель - максимально содержательный, достоверный ответ в пределах реально доступных сведений.**

При этом запрещено:

- Выдумывать источники.
- Симулировать успешный поиск.
- Представлять предположения как документально подтверждённые факты.
- Выдавать собственный прежний ответ модели за независимое доказательство.
- Подменять отсутствие проверяемой информации уверенностью.
- Проводить повторный поиск только ради соблюдения формального требования.
- Создавать новые блокирующие этапы проверки.
- Подавлять содержательный ответ лишь потому, что один вспомогательный инструмент недоступен.

**Необходимо устранить зависимость работоспособности всего Fact-check от успешности отдельных этапов.**

Это требование не отменяет реальную обработку ошибок, техническую безопасность, защиту приватных данных и проверку допустимости пользовательских операций.

# 1. Установленная первопричина

## 1.1. Текущий дефект

В `services/factcheck_service.py::check_claim_envelope()` реализован следующий путь:

1. Выполняется retrieval.
2. Формируется evidence.
3. Если evidence отсутствует, выставляется `insufficient_evidence`.
4. Полноценный аналитический verdict-вызов не выполняется.
5. Вербализатор получает технический статус и недостаток доказательств.
6. LLM генерирует разговорный текст о неудавшемся поиске.
7. Renderer оформляет его как ответ Fact-check.

Это неверная логика.

**Отсутствие внешнего evidence не тождественно невозможности разумно проверить утверждение.**

В частности, модель может определить математическое противоречие, выполнить технический расчёт, обнаружить неверное допущение или установить, что для окончательной проверки не хватает конкретной характеристики устройства.

Даже если нельзя подтвердить точный факт, можно дать содержательную оценку условий, при которых утверждение было бы верным.

Сейчас эти возможности фактически блокируются на уровне серверной логики.

## 1.2. Не подменять проблему косметическим исправлением

Недостаточно:

- Убрать шутки из вербализатора.
- Сократить сообщение об ошибке.
- Заменить `insufficient_evidence` другим текстом.
- Добавить ещё один fallback-ответ.
- Подменить поиск ответом "проверить невозможно".
- Изменить только Renderer.

Нужно исправить сам путь принятия решения о возможности продолжать проверку.

# 2. Fact-check должен работать с поиском и без поиска

## 2.1. Единая архитектура

Не создавать два независимых фактчекера.

Сохранить существующий pipeline:

`Target Resolution → Context → Retrieval → Analysis → Verdict → Verbalization → Delivery`

Этап Retrieval может вернуть:

- Достаточные внешние доказательства.
- Частичные внешние доказательства.
- Результаты поиска без пригодных доказательств.
- Нерелевантную выдачу.
- Техническую ошибку.
- Недоступность всех провайдеров.
- Отсутствие необходимости выполнять внешний поиск.

Все эти исходы должны обрабатываться в рамках существующего аналитического маршрута.

Если один этап возвращает ошибку или пустой результат, pipeline должен сохранять возможность продолжать работу, когда для этого достаточно остальных входных данных.

## 2.2. Режим с внешними доказательствами

Когда поиск успешно предоставил пригодные материалы:

- Анализировать найденные доказательства.
- Проверять соответствие источников утверждению.
- Различать подтверждение, опровержение и недостаточность данных.
- Не считать URL доказательством сам по себе.
- Сохранять ссылки и provenance.
- Учитывать актуальность источников.
- Формировать обычный полноценный фактчек.

Этот путь уже существует.

Не переписывать его без подтверждённых дефектов.

## 2.3. Режим с частичными доказательствами

Если часть источников получена, а дальнейшие запросы не удались:

Продолжить проверку по имеющимся материалам.

Не выбрасывать уже найденные доказательства из-за ошибки следующего провайдера.

Не понижать автоматически результат всей проверки до технической ошибки.

Разграничивать:

- Утверждения, которые удалось проверить.
- Утверждения, которые удалось оценить только косвенно.
- Утверждения, которые остались неподтверждёнными.

Если имеющихся материалов достаточно для надёжного вывода, использовать их.

Если нет - объяснять содержательную границу вывода, а не просто сообщать, что инструмент сломался.

## 2.4. Режим без внешнего поиска

Это главное новое требование.

Если внешние источники недоступны, бот должен использовать уже существующий аналитический компонент.

Ему необходимо предоставить:

- Проверяемое утверждение.
- Релевантный контекст.
- Доступную историю обсуждения.
- Уже установленные факты.
- Сведения о неудавшемся поиске.
- Разрешение выполнять самостоятельный логический и технический анализ.
- Явное разграничение между проверенными данными, знаниями модели и предположениями.

**Модель не должна получать системную команду считать содержательный анализ невозможным только из-за пустого evidence.**

В частности, проверить серверный блок:

`factcheck_service.py::check_claim_envelope`

```python
if not evidence:
    raw_payload = {
        "factual_verdict": "insufficient_evidence",
        ...
    }
```

Устранить безусловную зависимость полноценного анализа от `evidence`.

При этом не заменять её противоположной ошибкой, когда LLM вправе без доказательств объявлять произвольный факт подтверждённым.

В качестве исхода без внешней верификации необходимо сохранить честную неопределённость относительно тех сведений, которые нельзя проверить самостоятельно.

Использовать существующие схемы verdict, uncertainty и provenance.

Не вводить новый параллельный набор вердиктов, если достаточна корректировка действующего контракта.

## 2.5. Что именно может делать модель без поиска

Допускается:

**Логическая проверка.** Установить, следует ли вывод из предоставленных предпосылок.

**Математическая проверка.** Проверить числа, формулы, соотношения, арифметику и размерности.

**Техническое рассуждение.** Объяснить устройство технологии на основе известных принципов.

**Проверка внутренней согласованности.** Обнаружить противоречия между частями утверждения.

**Условный вывод.** Объяснить, при каких условиях утверждение может быть истинным.

**Оценка правдоподобия.** Рассмотреть, соответствует ли утверждение общим известным закономерностям, явно отделяя оценку от подтверждения.

**Проверка по доступным локальным материалам.** Использовать релевантную историю, доступные файлы, уже проверенные документы и другие штатные источники.

**Выявление нехватки сведений.** Указать конкретный параметр, без которого нельзя установить истину.

Не допускается:

- Придумывать измерения.
- Выдумывать технические характеристики неизвестного устройства.
- Придумывать публикации производителей.
- Заявлять, что информация только что проверена, если поиска не было.
- Использовать уверенность самой LLM как достаточное доказательство.
- Выдавать устаревшие знания за актуальные спецификации.
- Превращать правдоподобие в статус документально подтверждённого факта.

## 2.6. Степень достоверности

Различать как минимум три содержательные ситуации.

**Проверено.** Доступные доказательства или непосредственно воспроизводимый расчёт позволяют сделать определённый вывод в рамках установленных условий.

**Аргументированно оценено.** Модель может объяснить вероятную ситуацию или технический принцип, но не может подтвердить конкретный внешний факт.

**Не установлено.** Доступных сведений недостаточно даже для полезного предметного вывода.

Не обязательно вводить эти слова как новые enum-значения.

Использовать существующую структуру данных, дополнив необходимую информацию о происхождении вывода.

Нельзя помечать внешнюю характеристику продукта как подтверждённую только потому, что модель вспомнила похожую цифру.

При этом правильно выполненный математический расчёт на явно заданных входных данных не должен искусственно понижаться до неопределённости из-за отсутствия интернета.

# 3. Конкретный production-сценарий

## 3.1. Исходный запрос

В Telegram пользователь написал:

"там 96 линий"

Другой участник ответил:

"Фактчек"

Поиск не дал пригодных результатов.

Бот выдал длинный текст о технической недоступности поисковиков вместо анализа исходного утверждения.

## 3.2. Что необходимо проверять

Первоначально определить:

- К какому сообщению относится команда Fact-check.
- О каких линиях идёт речь.
- Какое устройство или архитектура обсуждается.
- Достаточно ли окружающего контекста.
- Не относится ли число к совершенно другому техническому параметру.

Если контекст позволяет установить предмет спора, бот должен продолжить.

Например, при обсуждении PCIe он может:

- Объяснить, что такое количество линий PCIe.
- Разграничить линии CPU, чипсета и доступные устройствам линии.
- Рассмотреть конфигурацию интерфейсов.
- Проверить возможные арифметические несоответствия.
- Установить, каких характеристик не хватает для подтверждения числа 96.

Не утверждать, что речь обязательно идёт о PCIe, пока предмет не установлен по фактическому контексту.

Если даже после исследования истории объект не определён, допустимо краткое уточнение.

**Не задавать уточняющий вопрос, если достаточный контекст уже присутствует.**

## 3.3. Ожидаемое поведение

Бот должен пытаться ответить по существу.

Если внешний поиск недоступен, он может объяснить технические принципы и сформулировать предварительный вывод.

Если конкретное число нельзя подтвердить, нужно назвать именно это ограничение.

Не сводить весь ответ к объяснению технического сбоя.

Не создавать специальный сценарий под число 96.

Эта же логика должна работать в математике, истории, программировании, экономике, науке и других областях.

# 4. Устойчивость pipeline: запрет на каскады искусственных блокировок

Это отдельное обязательное требование.

В проекте уже возникали ситуации, когда избыточное количество проверок приводило к фактической неработоспособности сложной функции.

Повторять такую архитектуру в Fact-check запрещено.

## 4.1. Неблокирующие проверки

Каждый этап необходимо оценивать по его роли.

Если проверка служит:

- Повышению качества.
- Поиску дополнительных данных.
- Ранжированию источников.
- Обогащению контекста.
- Проверке релевантности.
- Дополнительной валидации вывода.
- Получению даты публикации.
- Уточнению атрибуции.

Её неудача сама по себе не должна останавливать весь Fact-check, если оставшихся данных достаточно для полезного и допустимого ответа.

Неуспех вспомогательного этапа фиксируется в диагностике и учитывается в содержательном выводе.

## 4.2. Что нельзя отключать

Сохранить обязательные технические контракты:

- Корректность целевого сообщения.
- Авторизацию и права доступа.
- Изоляцию данных разных чатов.
- Безопасность запросов и инструментов.
- Защиту приватных данных.
- Проверку достоверности ссылок, которые выдаются как источники.
- Разграничение доказательств и неподтверждённых утверждений.
- Валидность данных на границе инструментов.
- Защиту от повторной отправки.
- Корректную обработку необратимых ошибок.

Если данные нельзя безопасно использовать, система не должна обходить эту защиту ради красивого ответа.

## 4.3. Fallback сохраняются

**Не удалять существующие fallback-механизмы только потому, что они относятся к обработке ошибок.**

Fallback нужен для продолжения работы.

Удалять или исправлять требуется лишь тот участок, который превращает неудачу необязательного инструмента в обязательный отказ всего pipeline.

При недоступности одного источника использовать другие.

При отсутствии всех внешних источников переходить к доступному содержательному анализу.

При неудаче второстепенного валидатора не уничтожать уже корректно построенный результат.

Не заменять отказ поиска ещё одной обязательной проверкой, которая в результате тоже сможет остановить всё выполнение.

## 4.4. Никакой новой цепочки обязательных проверяющих LLM

Не создавать дополнительного агента, который проверяет доступность поиска.

Не добавлять обязательный повторный анализ после каждого отказа.

Не добавлять новый независимый Fact-check.

Не вводить отдельный универсальный контрольный LLM-вызов.

Использовать действующие Analyst, Validator, Verbalizer и соответствующие fallback, оптимизируя их роль.

Если существующий вызов аналитика может работать с пустым внешним evidence, использовать его, а не запускать второй анализатор.

# 5. Разобраться с причинами поисковых неудач

Проверить:

- `services/search_aggregator.py`
- `services/factcheck_planner.py`
- `services/factcheck_service.py::classify_retrieval`
- `services/factcheck_orchestrator.py`

Существующий каскад Tavily → Exa → DuckDuckGo сохранить.

## 5.1. Разные технические причины

Корректно различать:

- Недоступность провайдера.
- Timeout.
- Ошибку API.
- Пустую выдачу.
- Нерелевантную выдачу.
- Ошибку обработки источника.
- Отсутствие подтверждений в доступных материалах.
- Частичную успешную выдачу.

Нельзя объявлять "поисковики недоступны", если они отвечали, но результаты не прошли relevance-фильтр.

Нельзя объявлять "данных нет", если на самом деле не состоялся поиск.

## 5.2. Проверить relevance-фильтр

Сейчас релевантность выдачи частично определяется лексическим совпадением терминов.

Это может приводить к отклонению содержательно подходящих документов, использующих другую терминологию.

Проверить реальную частоту подобных ложных отрицаний.

Не превращать проблему в расширение словарей синонимов по отдельным предметным областям.

Не вводить специализированные хардкоды для PCIe, LPDDR или конкретных устройств.

Если результаты пригодны, они должны доходить до аналитического этапа.

Если результатов нет, это не должно прекращать работу аналитического этапа.

## 5.3. Диагностика

В технических логах сохранять реальные причины неудачных запросов.

Человекочитаемый ответ должен содержать только те технические подробности, которые помогают понять ограничения вывода.

Не превращать сообщение Fact-check в отчёт о работе инфраструктуры.

# 6. Полностью удалить кеш готовых результатов Fact-check

**Решение владельца: кеширование готовых вердиктов Fact-check больше не требуется.**

Каждое новое обращение к Fact-check должно выполнять актуальную проверку с доступными на этот момент сведениями.

Старый ответ не должен возвращаться только потому, что такое же утверждение проверялось ранее.

Это особенно важно для:

- Современных технических характеристик.
- Политических и экономических событий.
- Новостей.
- Динамически изменяющихся данных.
- Исправленных публикаций.
- Новых доказательств.
- Изменившегося контекста разговора.

## 6.1. Найденные места кеширования

Проверить и удалить кеширование конечных результатов во всех действующих маршрутах:

**`handlers/factcheck.py`**

- Legacy `cache.get(cache_key)`.
- Legacy `cache.set(cache_key, verdict)`.
- Temporal cache read/write.
- Раннее завершение Fact-check при cache hit.

**`services/factcheck_orchestrator.py`**

- `_run_envelope_branch()` и temporal cache.
- `_run_legacy_branch()` и кеш обычного вердикта.
- Запись через `cache.set(...)` для legacy.
- Логику возврата ранее готового `CheckedVerdict`.

**`services/temporal_factcheck.py`**

- `build_temporal_cache_key`.
- `temporal_cache_key_with_bucket`.
- `read_temporal_cache`.
- `write_temporal_cache`.
- Связанные механизмы TTL и bucket, если они используются только для кеширования конечных вердиктов.

**`services/mca_gates.py`**

- `temporal_factcheck_cache_enabled`.
- Соответствующий feature gate и устаревшие настройки.

Проверить остальные фактические вызовы, чтобы не оставить второй скрытый read/write-путь.

## 6.2. Границы удаления

Удаляется именно кеш конечных результатов проверки и механизм выдачи старого ответа вместо новой проверки.

Не удалять автоматически:

- Общий SmartCache, используемый другими модулями.
- Исторические записи о выполненных проверках.
- Журналы диагностики.
- Доказательства прежних проверок как архивные данные.
- Механизм идемпотентности одного запуска.
- Защиту от одновременной повторной отправки.
- Кеши других подсистем.
- Безопасные временные данные одного текущего выполнения.

Временное повторное использование уже полученного результата внутри одного и того же запуска допустимо, если оно не приводит к повторному использованию устаревшего вердикта при следующем пользовательском запросе.

Не удалять исторические записи из production-базы без отдельной необходимости.

## 6.3. Конфигурация и UI

Убрать неиспользуемые настройки кеширования готовых Fact-check-вердиктов из действующей конфигурации и админки.

Не оставлять переключатели, которые фактически больше ни на что не влияют.

Не создавать новый механизм кеша взамен старого.

Не использовать другое имя для аналогичного хранения готовых вердиктов.

Устаревшие настройки и данные должны обрабатываться безопасно при обновлении.

## 6.4. Приёмка

Повторный Fact-check одного утверждения должен запускать новый анализ.

Если доступны внешние источники, выполнять актуальный retrieval.

Если поиск недоступен, выполнять доступный содержательный анализ.

При появлении новых доказательств последующий запрос должен иметь возможность изменить прежний вывод.

Никакие старые технические ошибки или verdict-cache-hit не должны подменять новую проверку.

При этом не допускать дублирования сообщений из-за повторной обработки одного и того же Telegram update.

# 7. Вербализация должна передавать содержание, а не сочинять его

Проверить:

- `factcheck_service._temporal_verbalize`
- `factcheck_prompts.py`
- `factcheck_orchestrator.build_presentation`
- `factcheck_renderer._serialize`

Вербализатор получает результат анализа и превращает его в естественный ответ.

Он не должен создавать новые фактические доказательства.

## 7.1. Когда анализ содержательный

Если аналитик способен проверить расчёт, объяснить техническую ошибку или сформулировать аргументированную оценку, вербализатор должен передать именно этот результат.

Сохранять:

- Personality Core.
- Expression.
- FREQUENT.
- Разговорный характер.
- Сарказм и юмор.
- Свободу длины и композиции в рамках выбранных настроек.

Не требовать сухого бюрократического отчёта.

## 7.2. Когда данных действительно недостаточно

Если анализ не установил ничего содержательного, вербализатор не должен компенсировать это длинными шутками о неработающих инструментах.

Не нужно генерировать абзацы ради абзацев.

Достаточно обозначить фактическое ограничение, при необходимости указав, какой информации не хватает.

Но запрещено вводить универсальное правило, ограничивающее длину всех ответов без поиска.

Отсутствие поиска и отсутствие содержательного анализа - разные ситуации.

## 7.3. Не дублировать технические сведения

Renderer не должен второй раз сообщать то же ограничение, которое уже корректно выражено в основном ответе.

Не создавать заголовок, абзац и отдельную концовку с тремя одинаковыми сообщениями о сбое.

Использовать структурированные поля результата для определения формы сообщения.

## 7.4. Не задавать обязательную композицию

Не требовать:

- Всегда начинать с вердикта.
- Всегда отвечать списком.
- Всегда писать 2-4 пункта.
- Всегда шутить.
- Всегда заканчивать оговоркой.
- Всегда извиняться за недоступность поиска.

Структура определяется фактической задачей и объёмом содержательного анализа.

Сохранить безопасную разметку Telegram и привязку реальных источников к проверяемым утверждениям.

# 8. Обновить роль существующего аналитика

Проверить действующий Analyst System Prompt и его реальное прохождение через Composer.

Не создавать новое многословное эссе инструкций.

Не переписывать Personality Core.

Не дублировать одну и ту же инструкцию во всех слоях.

### Требуемая смысловая директива

"Проверяй утверждение по всем доступным данным. Внешний поиск используй для получения актуальных доказательств, но его недоступность не отменяет анализ. Проверяй логику, расчёты, внутренние противоречия и известные технические принципы. Различай подтверждённые факты, самостоятельные выводы и предположения. Не выдумывай источники и неизвестные характеристики. Если точный факт установить нельзя, объясни, что удалось выяснить и чего не хватает."

Использовать эту директиву в соответствующем существующем компоненте.

Она должна дополнять архитектурное исправление, а не заменять его.

# 9. Регрессионные проверки

Reviewer обязан подтвердить фактическое поведение.

## 9.1. Поиск

**F1.** Все поисковые провайдеры недоступны. Аналитический этап продолжает работать.

**F2.** Первый провайдер недоступен, второй предоставляет данные. Проверка использует полученные доказательства.

**F3.** Поиск возвращает пустую выдачу. Система не утверждает автоматически, что интернет недоступен.

**F4.** Поиск возвращает нерелевантную выдачу. Fact-check не объявляет это отсутствием самих фактов.

**F5.** Найдена часть доказательств, затем возникает ошибка. Уже полученные материалы сохраняются.

**F6.** Поиск доступен, но утверждение не подтверждается. Система не выдаёт это за технический отказ.

## 9.2. Содержательный анализ без интернета

**F7.** Арифметическое утверждение с достаточными входными параметрами. Модель выполняет расчёт.

**F8.** Техническое утверждение содержит логическое противоречие. Модель объясняет противоречие.

**F9.** Техническое утверждение частично опирается на неизвестные характеристики устройства. Модель отделяет известный принцип от неподтверждённой спецификации.

**F10.** Историческое утверждение не может быть независимо подтверждено. Модель не выдумывает источник, но анализирует имеющийся контекст.

**F11.** Пользователь предоставляет документ или данные, достаточные для проверки без поиска. Они используются.

**F12.** Утверждение противоречит проверяемому математическому соотношению. Модель не объявляет его неопределённым только потому, что нет веб-источников.

**F13.** Доступных сведений недостаточно даже для предметной оценки. Модель честно указывает это, не создавая фиктивный вердикт.

## 9.3. Кеш

**F14.** Повторный Fact-check идентичного тезиса запускает новую проверку.

**F15.** Между двумя запросами появляются новые доказательства. Второй запрос может изменить результат.

**F16.** Первый запрос завершился технической ошибкой. После восстановления поиска следующий запрос не получает старую ошибку из кеша.

**F17.** Temporal и legacy-пути не читают готовые вердикты из SmartCache.

**F18.** Исторические журналы и записи прошлых проверок остаются доступны.

**F19.** Повторный Telegram update не приводит к двойной отправке одного и того же результата.

## 9.4. Неблокирующие проверки

**F20.** Сбой одного вспомогательного этапа не уничтожает корректный результат другого.

**F21.** Ошибка необязательного валидатора не приводит к потере имеющихся доказательств.

**F22.** Недоступность внешнего инструмента не подавляет допустимый самостоятельный анализ.

**F23.** Отказ одного источника не запрещает использовать другие доступные источники.

**F24.** Критически невалидный или небезопасный вход не обходит обязательные защитные проверки.

## 9.5. Речь

**F25.** При наличии содержательного анализа ответ не сводится к сообщению о сбое.

**F26.** При отсутствии содержательного вывода не генерируется бессмысленная простыня.

**F27.** Renderer не дублирует одну и ту же оговорку.

**F28.** FREQUENT и Personality Core продолжают применяться.

**F29.** Ответ с полноценными доказательствами сохраняет содержательность и свободную разговорную форму.

**F30.** Наличие шутки или мата не считается дефектом само по себе.

Проверки должны использовать разнообразные фактические сценарии, а не один диалог о числе 96.

Не вводить хардкод под проверочные утверждения.

# 10. Инженерная реализация

## 10.1. Использовать существующую архитектуру

Переиспользовать:

- FactCheckService.
- FactcheckOrchestrator.
- Existing Analyst.
- Existing Verbalizer.
- SearchAggregator.
- FactcheckPlanner.
- Temporal Fact-check.
- Provenance.
- Existing Error Handling.
- Existing Renderer.
- Existing ToolRouter.

Новых независимых систем не создавать.

## 10.2. Не повторять проблему с Summary

Не внедрять многочисленные обязательные проверки, каждая из которых может остановить весь процесс.

Для каждого этапа определить:

- Является ли он необходимым для безопасности и корректности контракта.
- Или лишь повышает достоверность и качество результата.

Второй тип должен иметь возможность неблокирующей деградации.

Не скрывать реальные ошибки: регистрировать их в диагностике и отражать в результате, когда это существенно.

Не прерывать весь pipeline только потому, что качество одного источника или инструмента оказалось ниже ожидаемого.

## 10.3. Не превращать отсутствие поиска в универсальное доказательство

Доработка нужна для сохранения способности рассуждать.

Она не должна позволять LLM подтверждать любую непроверенную новость на основании собственных предположений.

Существующий запрет выдуманных ссылок и доказательств сохранить.

Нужно обеспечить различие между:

- Самостоятельно проверяемой логикой.
- Установленными доказательствами.
- Вероятностной оценкой.
- Неизвестными фактами.

## 10.4. Не удалять полезные fallback

Удаление verdict cache и исправление блокирующих проверок не означает удаления механизмов восстановления после ошибок.

Сохранять штатные fallback провайдеров, LLM, транспорта, форматирования и доставки.

Не заменять их жёстким отказом от выполнения.

## 10.5. Порядок выполнения

1. Сверить актуальную очередь и существующие требования.
2. Зарегистрировать только отсутствующие пункты.
3. Не прерывать текущие задания.
4. После наступления очереди подтвердить технические причины.
5. Исправить существующие маршруты.
6. Удалить кеш конечных вердиктов.
7. Выполнить регрессионные проверки.
8. Получить независимое ревью.
9. Выполнить штатный production deployment.
10. Проверить фактическую версию и работоспособность.

Без тестовых сообщений в рабочих Telegram-чатах.

Без дополнительных owner approval, если штатные полномочия уже позволяют выполнить работу.

Не задерживать выполнение ради повторных проверок уже подтверждённых контрактов.

3. Как различаются подтверждённые факты и самостоятельные выводы.
4. Какие ошибочные блокирующие зависимости удалены.
5. Какие fallback сохранены.

7. Почему ранее возникало сообщение "поиск недоступен".
8. Как теперь используется частичная поисковая выдача.
9. Какие реальные и офлайн-проверки выполнены.
10. Какая версия работает на production.

Не выдавать прохождение тестов с моками за доказательство доступности реальных поисковиков.

Не утверждать, что отсутствие ошибок в тестах автоматически подтверждает качество всех возможных LLM-ответов.

# Главный критерий приёмки

**Fact-check должен оставаться полноценной интеллектуальной функцией даже при отказе поисковых инструментов.**

Работает поиск - бот использует свежие внешние доказательства.

Поиск частично работает - использует полученные материалы и продолжает анализ.

Поиск полностью недоступен - применяет доступный контекст, знания, технические принципы, логику и вычисления.

Достоверность внешнего факта установить невозможно - честно говорит об этом, но не отказывается от всего содержательного анализа.

Данных нет вообще - не выдумывает ответ.

Никаких новых каскадов искусственных блокировок.

Никакого кеширования готовых Fact-check-вердиктов между пользовательскими запросами.

Никаких семантических хардкодов под конкретные сообщения и числа.

Никакого переписывания Personality Core или подавления разговорного характера.

**Исправить причины деградации существующего Fact-check, сохранить его возможности и обеспечить устойчивую работу независимо от доступности необязательных инструментов.**
