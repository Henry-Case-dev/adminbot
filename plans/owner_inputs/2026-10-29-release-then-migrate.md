## 1. Модель выполнения и ответственная роль

Orchestrator: сначала довести **уже активную текущую задачу** из `plans/current_task.md` до инженерного завершения, Review и полноценного деплоя на **старый** VPS; получить подтверждение реально работающей версии. После этого на время миграции не запускать новые независимые деплои, при этом очередь, журнал прогресса и `plans/current_task.md` сохранять. Architect: ограниченный проход по критичным контрактам текущего релиза и точкам записи при переносе. DevOps: релиз на старый production, затем ведущий исполнитель подготовки и миграции. Builder: до завершения релиза исправляет только обнаруженные дефекты текущей задачи; во время миграции — только подтверждённые несовместимости нового окружения. Reviewer: сначала приёмка текущего релиза на старом production, затем проверка целостности переноса и фактического поведения нового production. Не придумывать отдельные многократные гейты, не требовать одобрения на каждый технический шаг.

Не обещать минимальное время без предварительных измерений — вычислить объём и скорость переноса, заранее подготовить переносимый набор и зафиксировать фактическое время простоя. Не закрывать задачу по HTTP 200 при непроверенных БД.

## 1.5. ФАЗА A–C — завершение, деплой и приёмка ТЕКУЩЕЙ задачи на СТАРОМ VPS (строго до миграции)

**Текущая задача** — та, которая реально активна в Orchestrator / `plans/current_task.md` на момент выполнения распоряжения, включая её поздние уточнения. Нельзя выбирать вместо неё одну из удобных закрытых задач, считать её выполненной по числу галочек, урезать scope ради быстрого переноса или пропускать реально необходимые Builder/Reviewer действия. Если текущая задача уже задеплоена, не повторять бессмысленный деплой: документально подтвердить текущий SHA, версию, независимую приёмку и фактическую работу на старом production.

**A. Завершить текущую задачу:** сверить актуальные требования, незавершённые acceptance criteria, активные Builder/Reviewer и состояние рабочего дерева; реализовать оставшееся, выполнить соответствующие тесты и исправить обнаруженные регрессии. Не начинать новую задачу из очереди и не отменять уже принятые требования. Никакого создания новых задач ради миграции.

**B. Выпустить релиз на СТАРОМ production:** проверить Git-состояние и переносимость release commit из локальной рабочей копии в remote, выполнить текущий штатный релизный workflow (сборка, независимый Reviewer, git commit/push/merge по установленному порядку, `git pull --ff-only` на старом VPS, зависимости/перезапуск затронутых сервисов). Установить, что именно новый код, а не прежняя версия, реально работает на старом VPS. Зафиксировать **полный Git SHA**, APP_VERSION/build, ветку, deployed timestamp и артефакты Reviewer. Не выводить секреты.

**C. Проверить этот релиз именно на старом production:** проверить systemd, health, Docker/PG/SQLite соединения, фактические логи после перезапуска, отсутствие runtime exceptions, работу затронутых текущей задачей функций и связанных основных маршрутов без тестовых отправок в рабочие чаты. Не принимать один HTTP 200 за доказательство работы фичи; допустимы изолированные non-delivery проверки, read-only runtime-диагностика и анализ реальных штатных событий. Если нужное живое пользовательское событие пока не произошло, отметить эту часть `not_observed`, а не симулировать успешный тест или блокировать другие допустимые проверки.

**ОБЯЗАТЕЛЬНЫЙ RELEASE GATE:** к миграции можно перейти только когда текущая задача инженерно завершена, Reviewer принял исправления, актуальный релиз задеплоен на старом VPS и доступные production-проверки пройдены без критических дефектов. Если выявлена неисправность — исправить текущую задачу и повторить релизную приёмку; **не использовать новый VPS как способ скрыть или обойти проблему**. Если временный внешний блокер объективно препятствует релизу или критической проверке — зафиксировать его и не проводить cutover, пока нет безопасной принятой базовой версии. Не объявлять миграцию выполненной раньше времени.

**Заморозка версии для миграции:** после успешной приёмки зафиксировать immutable `MIGRATION_SOURCE_SHA` = SHA реально работающего старого production, состояние рабочих файлов и конфигурации. На новый VPS перенести **именно эту версию**, а не случайно более новый `master`, незадеплоенный локальный код либо устаревший снимок. Любые последующие изменения кода до cutover означают необходимость повторной сверки release gate. Дальнейшие независимые кодовые деплои во время переноса не проводить. Инфраструктурные различия нового хоста допускаются только после проверки и с фиксацией, что прикладная логика и версия не изменились.

После прохождения gate немедленно переходить к инвентаризации, подготовке, синхронизации и cutover по разделам ниже; не останавливаться на отчёте о текущем релизе.

## 6. Финальный cutover с коротким гэпом

Перед переключением убедиться, что на старом production продолжает работать **принятая текущая задача** и SHA совпадает с `MIGRATION_SOURCE_SHA`; сверить долговременную память и состояние заданий. 1. Сохранить удобную точку возврата и последний preflight нового сервера, убедиться, что PostgreSQL и приложение там готовы, но бот НЕ принимает updates.

По необходимости остановить старый локальный Bot API после его безопасного завершения; учитывать способ polling/webhook.
3. Сделать консистентные **финальные** snapshots SQLite (включая активное состояние WAL), PostgreSQL (SQL dump), `.env`/hot-settings и изменяемых runtime-файлов. Выполнить быструю окончательную дельта-синхронизацию media и данных, изменившихся со времени предварительного копирования.
4. Перед загрузкой в новый сервер проверить целостность файлов/SQLite `PRAGMA integrity_check`/PG restore, важные счетчики строк и контрольные границы истории, ID чатов, алиасы, память и задания. Не заменять работающее состояние на непроверенный дамп.
5. Восстановить окончательный набор на новом VPS, строго сопоставив владельцев файлов, переменные окружения и PG пароли/DSN. Не выполнять `initdb`, seed, миграции с очисткой, reset или `docker compose down -v` на боевых данных.

При использовании локального Telegram Bot API проверить правила переключения `TELEGRAM_LOCAL` и `logOut/close` согласно реально используемому режиму; не потерять pending updates и не породить двойную обработку.
7. Перевести DNS/внешний reverse proxy/админку на новый VPS (учесть TTL, HTTPS, TLS и публичные media URLs), не открывая служебные порты наружу.
8. Проверить health endpoint, systemd, Docker, PostgreSQL, SQLite, чтение памяти, корректность админки и существующих настроек, отсутствие fatal ошибок в journald. Telegram входящие/исходящие проверить безопасным штатным способом без тестовых сообщений в рабочих группах. **После старта обязательно перейти к расширенной post-migration приёмке production (раздел 7.1), а не останавливаться на HTTP 200.** Зафиксировать точное время первого рабочего старта и фактическую длительность гэпа.

Не приписывать `DONE` только по HTTP 200: нужны сравнения данных и подтверждение единственности экземпляра.

## 7. Проверка без потерь

Критические критерии:

- SQLite `integrity_check` OK, размеры/таблицы/row counts и последние записи равнозначны зафиксированному старому snapshot; сохранены `smart_messages`, history, mca memory, graph facts, episodes, embeddings, alias/identity, summary/nostalgia/initiative state, pending jobs, если применимо;
- PostgreSQL восстановлен из финального дампа: chat settings, admin roles, providers, prompts, dashboard state и другие реальные таблицы на месте;
- `.env`, приватные runtime-конфигурации, media files и директории доступны, нет пустых замен вместо ранее настроенного;
- текущий git HEAD соответствует принятому production; `.env` и `deploy_commands.txt` не вошли в Git;
- приложения и сервисы используют те же настройки/маршруты, HTTP/TLS/домен работают, персистентные volumes подключены;
- нет двух одновременно активных bot pollers, второго scheduler, дублирующих инициатив/саммари/уведомлений;
- доступы администратора и права ролей сохранены, GraphRAG работает с существующими embeddings без перестройки;
- старый VPS сохранён и остановлен как fallback, не удалены файлы/базы/скрипты.

Точечные сравнения и тесты привязать к фактическому старому snapshot, а не к установленному по умолчанию чистому серверу. При неожиданном расхождении данных откатить cutover до запуска новых писателей либо исправить на новой копии без потери пользовательских событий.

## 7.1. ОБЯЗАТЕЛЬНАЯ post-migration проверка РЕАЛЬНОГО PRODUCTION

Проверить не только то, что бот запустился, но и что **актуальная задача, задеплоенная сначала на старый сервер, осталась рабочей после переноса**, а остальные существующие функции не пострадали. Использовать фактические параметры и включённые модули чатов, не включать выключенные специально функции ради формальных проверок. Привести сравнение *до (старый принятый релиз) / после (новый production)*.

**Точка 1 — версия и единственный production:** полный Git SHA и build на новом VPS совпадают с `MIGRATION_SOURCE_SHA`; старый `admin_bot` и production-writers остановлены, нет двойных Telegram pollers, scheduler/worker, повторной инициативы или дублирующихся отправок. Убедиться, что Git/DevOps будущего деплоя указывает на новый IP, а не на старый сервер.

**Точка 2 — процессы и зависимости:** systemd service устойчиво работает после старта, корректно поднимается после управляемого рестарта без потери данных; Docker Compose сервисы и необходимые healthcheck доступны; PostgreSQL, SQLite, локальный Telegram Bot API, Cobalt, прокси, веб-сервер, TLS и публичные media URLs проверены по фактическим активным настройкам. Нет повторяющихся exceptions, error loops, stuck jobs или неожиданных рестартов.

**Точка 3 — данные и память:** сравнить проверяемые row-counts/checksums/границы последних сообщений и IDs чатов в SQLite и PG против согласованных финальных snapshots; подтвердить доступность историй, alias → Telegram ID, embedding index, GraphRAG, dossiers/episodes, Golden Facts, L1/L2, памяти чатов, summary/nostalgia/initiative state, pending jobs; проверить не только количество записей, но и выборочные чтения и целостность связей. Никаких новых импортов или перестроек памяти.

**Точка 4 — прикладное поведение:** по существующим диагностическим средствам и изолированным non-delivery вызовам проверить критичные маршруты: Direct Chat/L1/Writer, ToolRouter и поиск, Fact-check с fallback, Summary и расписания, Initiative, Nostalgia, Vision/media, генерацию и редактирование изображений (без платных live-запросов, если требуется только контракт), а также админку (логин, роли, права, глобальные и per-chat настройки, сохранённые провайдеры, промпты). Для **текущей релизной задачи** отдельно воспроизвести её основные acceptance criteria в безопасной среде и проверить связанные реальные runtime-логи. Контрактный mock не выдавать за живую проверку провайдера.

**Точка 5 — штатное production-наблюдение:** после переключения изучить реальные новые `journalctl`/структурированные события, результаты штатных фоновых тиков и доступные естественные входящие обновления. Не генерировать тестовые сообщения в рабочие Telegram-чаты и не ждать искусственно несколько часов ради будущего события. Если по некоторой функции ещё не было естественного события, отметить `not_observed` и указать, что проверено косвенно. Не объявлять «все функции проверены на проде» только на основании health или тестов с моками.

**Точка 6 — сеть и клиент:** проверить публичный домен админки, DNS и сертификат снаружи, `healthz`/`/api/health`, нужные функции Mini App и пути медиа, отсутствие открытых наружу портов PG/локального Telegram Bot API и служебных сервисов; старые URL и IP не должны оставаться конечным адресом активного production, если они больше не используются.

**Критерий приёмки:** нет потери данных, не потеряны или не перезаписаны настройки, сервисы работоспособны, текущий релиз и включённые основные маршруты доступны, нет подтверждённых новых критических регрессий относительно последнего проверенного состояния на старом VPS. При обнаружении критической регрессии — локализовать причину и безопасно исправить на новом production или выполнить rollback по разделу 8 с сохранением всех данных, созданных после cutover. Нельзя делать слепой откат к старому snapshot, если новый сервер уже принял обновления.

**Финальный артефакт приёмки:** короткая таблица `компонент | старый production | новый production | evidence | status`, где статусы `PASS`, `FAIL`, `NOT_OBSERVED` честно соответствуют реальным данным; отдельно приложить контрольные суммы/числа по БД и подтверждение того, что `MIGRATION_SOURCE_SHA` действительно соответствует принятой текущей задаче. `NOT_OBSERVED` не превращать в `PASS`.

## 8. Rollback

Пока новый VPS не обработал новых обновлений Telegram и не создал новых записей, допустимо вернуть старый VPS к заранее сохранённому состоянию, убедившись, что новый остановлен.

После того как новый VPS начал принимать сообщения или выполнять фоновые задачи, **нельзя** просто включать старый snapshot: это потеряет уже созданные на новом данные или повторит отправки. Для возврата нужно сначала останавливать новых писателей, согласованно переносить изменения назад, восстановить состояние очередей/offset и только потом запускать старый экземпляр. Если безопасный обратный перенос невозможен, сохранить новый сервер как единственный источник истины и устранять проблему там. Всегда исключать одновременный запуск двух экземпляров.

## 9. Интеграция с OpenCode workflow и отчёт

После успешного переключения обновить deploy target в применимых конфигурациях DevOps/AGENTS, но сохранить данные старого сервера для rollback и историю релизов. Проверить, что Orchestrator/DevOps теперь делает `git pull --ff-only` и `systemctl restart admin_bot` на **новом** VPS, а не по старому IP. Проверить конфигурацию fail2ban/SSH доступов, чтобы скрипты не блокировали себя повторными подключениями.

Вывести короткий отчёт **с двумя отдельными фазами**: (1) текущая задача завершена, принята Reviewer, выкачена на старый VPS, указан полный `MIGRATION_SOURCE_SHA`, проверены основные acceptance criteria на старом production; (2) перенос именно этого SHA на новый VPS, ОС/версии runtime, размеры SQLite/PG/media, проверка переноса данных, время начала/окончания cutover, фактический гэп, состояние `/api/health`, PG/Docker/systemd, домен/TLS, Git access и результаты расширенной post-migration проверки из §7.1. Отдельно указать фактически проверенные функции, не наблюдавшиеся сценарии, серьёзные регрессии (если есть), их исправление/rollback, и что осталось проверить. Секреты в отчётах не раскрывать.

Не останавливать основную очередь разработческих задач без технической необходимости после успешного переноса. Следующий обычный деплой должен попадать уже на новый VPS.

**Критерий завершения:** **текущая задача сначала успешно задеплоена и проверена на старом VPS**, после чего **именно её принятый SHA** перенесён на новый VPS; новый VPS — единственный работающий production, данные сверены с финальным snapshot, Git-деплой работает, пройдена расширенная post-migration приёмка приложения и функций без критических регрессий, старый сервер сохранён с выключенными production-писателями для возможного возврата. До прохождения обоих этапов не заявлять DONE.
