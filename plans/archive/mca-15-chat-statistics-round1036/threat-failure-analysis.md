## 1. Угрозы и отказы пайплайна

### THR-1 — Ложное число из неверной семантики измерения (Integrity/Trust)
**Механизм:** текущие пути смешивают единицы: `build_fts_query` строит prefix-OR, а не фразу (`summary_memory.py:877–889`); `_dig_into_lore` добавляет person/graph-имена в тот же FTS-запрос счётчика (`tool_router.py:697–712`); `search_messages_fts_count_by_author` считает COUNT(*) сообщений, не вхождений (`database.py:5849–5864`); сниппеты фильтруются по `person_uid`, счётчик — нет (`:745–747` vs `:839–842`); результат рендерится как «Найдено N упоминаний» (`:667`). Число может относиться к другому измерению, чем думает человек.
**Митигация:** D1 (typed `metric`/`match_mode`, единицы, фильтры count/examples из одной спеки в SQL до LIMIT, `human_label`+method), FIX §24.1 п.1–6, truth set A38/A39 (фраза 1 / prefix-OR 5 / +имя 6 / prefix «шиз» 4). **Остаточный риск:** unicode61-токенизация без морфологии — честно маркируется как prefix/токен, не «корень».

### THR-2 — Незаземлённое число проскакивает на одном из путей отправки (Repudiation)
**Механизм:** число может попасть в Telegram через direct-ответ, System2, fallback, готовую lore-story в обход verbalizer (`direct_chat_service.py:2425–2427`) или постпроцессор; точечный гард в одном месте не покрывает остальные.
**Митигация:** D5 — один детерминированный `check_numeric_claims` в существующем контуре, вызовы: `verbalize_validated` (direct System2 `:2728`, factcheck `:195`) + финальная сборка direct после lore-подстановки; ≤1 коррекция внутри бюджета ≤2 → `fallback_text`/`verified_phrase`/снятие неподтверждённой части; тест «число через lore fallback не публикуется» (A41). **Остаточный риск:** число вне стат-контекста (обычная речь/дата) намеренно не блокируется — принято владельцем (`:1159`).

### THR-3 — Число другого запроса/метрики как ложное подтверждение (Spoofing/Integrity)
**Механизм:** «число где-то было в tool output» — не доказательство; реальное число другого запроса при подстановке даёт ложный ответ (`:1159`). Модель может перепутать единицы (messages vs occurrences) или авторов.
**Митигация:** per-turn реестр MetricResult (числа прошлых ходов не видны); проверка совместимости единицы числа с маркерами стат-контекста; `verified_phrase` — единственный разрешённый слот; A41-тест. **Остаточный риск:** перефраз вокруг числа без маркеров единицы — компенсируется детерминированной фразой и одной коррекцией; семантический обход вне чисел не проверяется (не строим несостоятельный NLP).

### THR-4 — Подкол превращается в обязательный отчёт / юмор глобально блокирует память (Integrity/Behavior)
**Механизм:** кейс Васи: реплика без просьбы проверить могла запускать широкий поиск и «отчёт» с числами; обратный перегиб — жёсткая реплика на конкретный пример или запрет инструментов для юмора (`:1126–1133`).
**Митигация:** D6 — детерминированный классификатор `social_banter`/`historical_evidence`/`chat_statistics`/`mixed` по закрытым маркерам, контексту и reply (не по словам «никогда»/«бот»); для banter нет stats-хинта и нет MetricResult → гард не публикует числа; инструменты не блокируются; жёсткой реплики на пример нет; `mixed` → две цели; reason-коды цели. Тест-инвариант «нет пути, где подкол получает обязательный статистический отчёт» (A42). **Остаточный риск:** неоднозначная формулировка → `mixed`/banter, не форсированный отчёт (принято).

### THR-5 — Двойной счёт дублей import/live или сложение хранилищ (Integrity)
**Механизм:** повторный импорт/повторное live-наблюдение одного сообщения; соблазн сложить counts SQLite+PG без проверки пересечения (`:1147`).
**Митигация:** каноническая `(chat_id, tg_message_id)` (mca-03 `save_smart_message_identity:5269–5350`), `import_key` UNIQUE `(chat_id, import_key)`, dedup-проверка области (`count_duplicate_identity_rows:2066`) → дубли → `partial`+`stats_partial_corpus`; корпус один (`smart_messages`), сумма хранилищ → `unsupported`; fixture «duplicate import» (A40). **Остаточный риск:** неполный dedup-мэппинг → честный partial с предупреждением, не общий точный счёт.

### THR-6 — Число и примеры из разных версий данных (Consistency)
**Механизм:** между count-запросом и выборкой examples приходит live-запись/правка — показанные примеры не соответствуют числу.
**Митигация:** watermark `{max_id,max_timestamp}` в count-запросе; examples с `id <= watermark.max_id`; `data_as_of`; повторный запрос — пересчёт (durable-кеша нет, stale cache невозможен по построению). **Остаточный риск:** in-place правка текста в узком окне измерения — следующий запрос пересчитывает; заявка на «вечный факт» исключена.

### THR-7 — Тяжёлое измерение блокирует event loop / длится бесконечно (DoS-доступность)
**Механизм:** occurrences по 2 млн строк; скан всех совпавших сообщений в одном запросе; неограниченные examples.
**Митигация:** отбор FTS/индексами; occurrences — keyset-порции с капом `MCA_CHAT_STATS_OCCURRENCE_MAX_ROWS` (20000) → `partial`+`value=null`; examples ≤ `MCA_CHAT_STATS_EXAMPLES_MAX` (20); read-only bounded операция, существующие tool-таймауты; без новых очередей/job-типов. **Остаточный риск:** очень частые тяжёлые запросы — вне mca-15 (лимиты/расходы — mca-11, CA-15-10).

### THR-8 — Ошибка/таймаут счётчика выдаётся за ноль/«никогда» (Repudiation)
**Механизм:** fail-open счётчик `_dig_into_lore` (`:851–855`) оставляет `total_mentions=0`; исключение счётчика неотличимо от «нет совпадений»; «не найдено» превращается в утверждение о прошлом.
**Митигация:** статусы `error`/`partial` + `value=null`, отдельный `stats_count_error`; «в доступной истории» вместо «никогда» при неполном корпусе; `insufficient_output_budget` при урезании; A40. **Остаточный риск:** нет (статус обязателен в контракте).

### THR-9 — R17-утечка: сырой текст/термы/цитаты в журналы и события (Information Disclosure)
**Механизм:** диагностика §24.5 хочет «исходный/нормализованный запрос», а события/логи durable — канал утечки личных сообщений и цитат.
**Митигация:** в durable-канал — `query_spec_hash`, методы/единицы/числа/ID/статусы; сырой и нормализованный текст не журналируется; WARNING-и без текста (маскирование); R17-скан на T-4937/T-4938. **Остаточный риск:** владелец читает «откуда цифры» по hash+методу+области, а не по сырому тексту — принято как компромисс R17.

### THR-10 — Неполный OFF-паритет (Availability/Behavior)
**Механизм:** три слоя (stats-режим, гард, intent) поверх горячих путей; неполный OFF меняет поведение незаметно.
**Митигация:** K1–K3 env-only default ON, per-surface байт-в-бит тесты, все три OFF — полный паритет 2.58.55; `build_fts_query` default-режим = старая формула; новые параметры `verbalize_validated` default None; DDL=0 (нечего откатывать). **Остаточный риск:** нет при обязательных OFF-тестах.

### THR-11 — Ослабление mca-22/постпроцессора: второй судья/парафразер (Integrity/Process)
**Механизм:** соблазн добавить LLM-проверку чисел или отдельный paraphrase-модуль — второй контур искажения смысла/чисел.
**Митигация:** один детерминированный гард в `negative_constraints` (D5), REUSE числовой нормализации mca-08, второй LLM-судья и paraphrase-модуль запрещены (инвариант `tests/test_mca22_core_round1027.py:810–813`); `sanitize_outgoing` — неизменный egress-канон. **Остаточный риск:** нет (структурный запрет + тест).

### THR-12 — Ложная приёмка: числа Васи «сверены» фиктивно (Process/Trust)
**Механизм:** исходные tool arguments/output/БД кейса отсутствуют (`:1106`); можно «воспроизвести» три числа подгонкой или объявить фикс без RED.
**Митигация:** no-false-acceptance (`:15167`): RED-доказательство на текущем HEAD (probe §26, синтетический truth set), три числа — только при наличии исходных данных, иначе `PENDING OWNER` без имитации; live-сценарии — реальный чат (T-4940). **Остаточный риск:** live-часть ждёт владельца — честный статус.

## 3. Выводы
- Критическая масса рисков закрывается **типизацией измерения** (единицы/режимы/метод/статусы), **одним детерминированным гардом** в существующем контуре и **честными статусами** (error/partial/unsupported/null) — без новых хранилищ, очередей, LLM-судей и второго retrieval.

- Δ DDL = 0 → деградационные сценарии БД не создают миграционного долга; OFF-контур K1–K3 возвращает бит-в-бит 2.58.55.
