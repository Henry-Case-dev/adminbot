# ADR-1019-7 — Устойчивость извлечения фактов GraphRAG: `[]` ≠ невалидный ответ, восстановление после `LLMError`, не-спамящая диагностика

- **Статус:** Proposed (Step 2 @Architect, раунд 10.19)
- **Дата:** 2026-09-15
- **Раунд:** 10.19, фича F8 `graphrag-memorize-robustness` (T-1845)
- **База:** HEAD `fd6acc7`. **Связано:** §3 (SmartModule), §7 (summary_memory), F-15 §4 (10.3), ADR-1018-5 (канон `FACT_EXTRACT_PROMPT`), ADR-1013-3 (правка канонов), F7.
- **AMEND:** **F-15 §4** (раунд 10.3 `direct-sandbox-budget-investigation`), часть «graphrag memorize JSON list»: расширяет контракт устойчивости с «невалидный ответ → fallback + 1 retry» на «`LLMError` первичной экстракции → восстановление» и «валидный `[]` ≠ невалидный ответ». Не supersede — существующий fallback/retry сохраняется.

## Context

1. Чекап (UPD2, строка 160): nano-gpt отваливается по таймауту, «три ретрая в молоко», фолбэк deepseek-flash; «graphrag пытается это за Memorize и просто скипает, потому что пришёл не json, а **пустой список**; **два раза подряд**; память жрёт мусор и не запоминает».
2. F-15 §4 (10.3) реализовала: WARNING с маскированным raw (`parse_fact_list:527-529`), `_fallback_parse_facts` (проза/буллеты), один retry жёстким промптом (`_memorize_facts_inner:1742-1769`).
3. **Дыра 1:** валидный `[]` возвращает `[]` **без логов** (`parse_fact_list:531-539`) — «пусто валидно» неотличимо от «ничего не нашлось»; отсюда ощущение «скипает молча».
4. **Дыра 2:** `_extract_facts` при исчерпании bounded-ретраев `raise exc` (`:1728`); `memorize_facts` ловит `LLMError` на верхнем уровне (`:1694-1700`) → `WARNING "LLM failed"` и **выход**: ни fallback-парсер, ни retry-промпт не применяются (таймаут nano-gpt = молчаливая потеря).
5. **Дыра 3:** дублированные WARNING (в `parse_fact_list` и в `_memorize_facts_inner`) — «спам».
6. Инварианты: **канон `FACT_EXTRACT_PROMPT` байт-в-байт** (R46-2 + F5-абзац, ADR-1018-5), `PROMPT_MIGRATIONS` не трогается, R17 (`_mask_llm_raw`), R16, каталог Δ=0, крон-ветка без агрессивных ретраев (канон F-15).

## Decision

### D1. Явный статус парсинга: `ok` / `empty_valid` / `invalid`
Новая `parse_fact_list_ex(raw) -> (facts, status)` (`PARSE_OK|PARSE_EMPTY_VALID|PARSE_INVALID`). `parse_fact_list` сохраняется как тонкая совместимая обёртка (результат байт-в-байт). WARNING эмитится **только** для `invalid`; `empty_valid` — `debug`. Это снимает «неотличимость пустого списка».

**D-08 (ревью Батча A):** `invalid` включает **два** подслучая — (а) ответ не является JSON-списком, (б) структурно валидный список, где **все** элементы отсеяны `_validate_fact` (промпт-дрейф). При `warn=True` WARNING (маскированный raw, R17) эмитится в **обоих** — иначе (б) был бы тихим. В memorize-ветке `warn=False` (единый WARNING даёт `_log_memorize_lost`, без дубля).

### D2. Восстановление при `LLMError` первичной экстракции (**AMEND F-15 §4**)
`_memorize_facts_inner` перехватывает `LLMError` от `_extract_facts` **внутри** и продолжает пайплайн: fallback-парсер по доступному тексту + **одна** попытка `_FACT_RETRY_SYSTEM_PROMPT` (как в F-15 §4.3). Верхний `memorize_facts.except LLMError` перестаёт быть «глушилкой потери» и становится страховкой (unexpected). Итог: таймаут провайдера не приводит к молчаливой потере фактов; при неудаче восстановления — явный WARNING «lost» с причиной.

### D3. Бюджет восстановления — строго bounded
Не более **1** дополнительного LLM-вызова на memorize-событие (существующий `_FACT_RETRY_SYSTEM_PROMPT`). При `empty_valid` retry **не** делается (валидный пустой ответ — не ошибка). Число вызовов не растёт сверх F-15.

### D4. Не-спамящая диагностика
Единый WARNING на событие (`_log_memorize_lost`) вместо двух; rate-limit ≤ **60 с** на `(chat_id, source)`; повторные — `debug` + агрегированный счётчик. Поля лога: `status`, `reason` (`empty|not_json|llm_error`), `lost=N`, `raw=_mask_llm_raw(raw)` (R17). Восстановление — `INFO recovered=N`.

**D-06/D-07 (ревью Батча A):** модульные словари диагностики — **bounded** (`_MEMORIZE_WARN_STATE_MAX=512`, эвикция старейших при вставке), иначе рост по `(chat_id, source_type)` на весь срок процесса; «ещё не логировали» — сентинел `None` (не `0.0`), поэтому первое событие ВСЕГДА даёт WARNING даже при uptime процесса < 60 с (`time.monotonic()` ≈ 0).

### D5. Крон-ветка без агрессивных ретраев
`_extract_and_save_graph` (`EXTRACT_PROMPT`/`parse_triplets`) получает только различение `[]`/невалидный в лог; **дополнительных LLM-вызовов/ретраев нет** (канон F-15 §4.3 сохранён). Промпты не меняются.

### D6. Канон и каталог — без изменений
`FACT_EXTRACT_PROMPT` байт-в-байт (байт-тесты), `PROMPT_MIGRATIONS` не трогается, лимиты ретраев — существующие `limits.graph_memorize_*`; Δ каталога = 0; DDL нет.

### D7. Feature flag не вводится
Устойчивость парсинга — базовая логика; откат — `git revert`.

## Consequences

**Positive**
- Таймаут nano-gpt больше не означает молчаливую потерю фактов (попытка восстановления).
- Валидный пустой ответ отличим от невалидного — «скипает молча» становится объяснимым.
- Диагностика стала точной и не спамит (один rate-limited WARNING + счётчик).
- Канон/каталог/схема не затронуты; расход bounded.

**Negative**
- При полном отказе провайдера добавляется один лишний LLM-вызов на событие (неуспешный) — осознанная цена за попытку не потерять факты; митигируется rate-limit и бюджетами F2/F3.
- Rate-limit может скрыть частоту сбоев в логе — компенсируется агрегированным счётчиком.
- Небольшое усложнение `_memorize_facts_inner` (ветка `LLMError`) — нужны тесты.
- Валидный `[]` теперь логируется (debug) — рост debug-объёма (не в прод-уровне INFO).

## Alternatives

- **A1. Считать `[]` ошибкой и всегда ретраить.** Отклонено: валидный пустой ответ — легитимный результат; лишний расход.
- **A2. Увеличить bounded-ретраи `_extract_facts` (например, до 5).** Отклонено: множит расход при недоступном провайдере; «три ретрая в молоко» — уже симптом.
- **A3. Повысить уровень лога «LLM failed» до ERROR.** Отклонено: ожидаемый внешний сбой — не ERROR (шум); важна не громкость, а попытка восстановления.
- **A4. Править `FACT_EXTRACT_PROMPT` (жёстче JSON).** Отклонено: канон байт-в-байт (R46-2/ADR-1018-5); F-15 уже ввела отдельный `_FACT_RETRY_SYSTEM_PROMPT`.
- **A5. Ретраить и крон-ветку.** Отклонено: канон «деградация без потерь» — ретрай только в fire-and-forget-ветке memorize.
- **A6. Хранить сырой ответ LLM в БД для отладки.** Отклонено: нарушает R17/минимизацию; достаточно маскированного фрагмента в логе.
- **A7. Отдельная метрика recover/lost в health сразу.** Отклонено (фаза 2): в F8 достаточно логов; интегрируется с F7 при необходимости.
