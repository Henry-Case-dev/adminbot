## 1. Цель, объём и исключённый объём

**Цель.** Каждый модуль получает **отдельную страницу-рабочее пространство** (§46): «Модули → `<модуль>`» с вкладками и **генеральным переключателем из того же канонического store F4**. Библиотека промптов становится **гибридной** (§48): desktop — дерево/редактор/описание, mobile — список → полноэкранный редактор; «**один промпт — один источник**»: два маршрута открывают **один config-item** `prompts.*`, без копий. Раздел ИИ (§47) сохраняет свои страницы; модели и подключения (§49) группируются в 6 групп с карточками и «Проверить»; прямой чат (§84) получает UI-карточки L1/L2, Саммари (§85) — вкладки-каркас **без backend-пайплайна** (Эпик 2).

## 3. D1. Маршрут рабочего пространства (§46)

### 3.1. Грамматика hash-маршрута

| Форма | Смысл | Пример |
|---|---|---|
| `#/modules` | витрина-каталог F4 (без изменений) | `#/modules` |
| `#/modules/<slug>` | workspace модуля, вкладка по умолчанию — **Обзор** | `#/modules/factcheck` |
| `#/modules/<slug>/<wt>` | workspace, конкретная применимая вкладка | `#/modules/factcheck/synthesizer` |
| `#/modules/<slug>/<stage>/<promptKey>` | workspace с **фокусом на промпте** (mobile → полноэкранный редактор; desktop → выбран в центре) | `#/modules/factcheck/synthesizer/factcheck_system` |
| `#/ai/prompts/<slug>/<stage>` | библиотека промптов: **тот же** объект (D3) | `#/ai/prompts/factcheck/synthesizer` |

- **`<slug>` = `m.id` без префикса `mod_`** (`summary`, `direct`, `factcheck`, `search`, `transcribe`, `video_summary`, `media_download`, `web`, `checkup`, `sleep`, `nostalgia`, `budgets`, `images`). Хранится в JS `MODULES` как `routeSlug` (витрина, Δ каталога = 0).
- Существующие статические записи `#/modules/budgets`/`#/modules/images` **совместимы** (slug совпадает) — backward compatibility без новых исключений.
- `<wt>` — id применимой вкладки (§4); не-применимая вкладка → нормализация в `#/modules/<slug>` (дефолт «Обзор») без белого экрана.
- `<promptKey>` — канонический ключ config-item (`prompts.*`), URL-энкодится.

### 3.2. Резолвинг маршрута (расширение F1-роутера, без слома существующего)

1. Вводится **динамический резолвер** workspace-маршрутов: `normalizeRoute`/`routeToTab` дополнительно распознают `#/modules/<slug>[/…]` для `slug ∈ MODULES[].routeSlug`.
2. `routeToTab('#/modules/<slug>[/…]')` возвращает **`m.tab`** (существующий config-tab модуля). Следствие: RBAC (`canViewTab`) и kill-switch (`_flagTabHidden`, напр. `mod_images`) продолжают работать **без изменений**, а маркер `activeTab === 'mod_images'` остаётся зелёным (Ф16).
3. `applyRoute` дополнительно выводит **производное workspace-состояние**: `workspaceModuleId` (из slug), `workspaceTab` (из `<wt>` или `overview`), `promptFocusKey` (из `<stage>/<promptKey>`). Состояние — **производная от hash**, своей копии маршрута нет.
4. `ROUTE_PARENT`: `#/modules/<slug>` → `#/modules`; `#/modules/<slug>/<wt>` → `#/modules/<slug>`. `routeDepth` даёт глубину (0/1/2) → нативная кнопка Telegram-«назад» ведёт по иерархии (каталог ← модуль ← вкладка/промпт).
5. **Неизвестный slug** (`#/modules/<неизвестный>`) → `#/modules` + toast «Модуль не найден» (не белый экран, не `#/`). Существующие `ROUTE_ALIAS` (`features|switches|reactions|custom`) сохраняются.
6. Legacy-алиасы F1 и корневые маршруты **не меняются**; `ROOT_ROUTES`, `NAV_ITEMS`/`NAV_ITEMS_V2`, порядок навигации hotfix4 не затрагиваются.

### 3.3. Шов F4 и регресс-путь

- **`openModuleWorkspace(m)`** перестаёт возвращать модалку: теперь это **навигация** `navigateTo('#/modules/' + routeSlug(m))`. Точка входа (кнопка «Настроить» `index.html:1267`) **не меняется**.
- **`openModuleWindow(m)` сохраняется** как рабочий регресс-путь (§60.2/§79/§116) и как **fallback**: если у модуля нет workspace-определения (неизвестный/неприменимый slug) или hash-навигация недоступна (file://, unit-стаб без hashchange) — шов вызывает модалку. Обе точки входа фиксируются тестом (T-2732).
- Модалка остаётся владельцем старого рендера групп (`activeModuleGroups`, Ф13) и НЕ удаляется/не переписывается.

### 3.4. Генеральный переключатель (§46)

Верхняя часть страницы workspace рендерит тумблер модуля **из store F4** (`getModuleState`/`setModuleState`/`modulePending`, `moduleRuntimeNotice`). **Локальный boolean не вводится**; одно действие = **ровно одна** серверная мутация (`persistItems`). Синхронность с карточкой каталога и панелью избранного — по построению (тот же `configItems` + overlay).

## 5. D2. Раздел ИИ (§47)

- В `HUBS_V2['#/ai']` остаются **ровно 5** внутренних страниц §47 и приводятся к порядку ТЗ: **Библиотека промптов** (`#/ai/prompts`, `prompts`) → **Модели и подключения** (`#/ai/llm`, `llm_providers`; карточка переименовывается из «LLM Провайдеры», **маршрут/tab не меняются**) → **Личность и стиль** (`#/ai/persona`) → **Имена и алиасы** (`#/ai/names`) → **Умный кэш** (`#/ai/smart-cache`).
- «ИИ — не свалка»: настройки памяти/лора/отношений остаются в «Памяти» (F1, уже сделано); настройки конкретных функций — в «Модулях». F5 **не переносит** ничего нового в ИИ и **не дублирует** параметр в двух разделах — проверяется тестом «нет config-item, достижимого из двух разделов как независимый владелец» (для модульных настройки владелец — workspace; ИИ даёт только промпты через библиотеку).
- Аудит-карта «старый экран → новый» (T-2704) сохраняется как артефакт §117(1) — `plans/reports/round1025_f5_ai_map.md` (**принято** `⟨предложено⟩` как требование §117(1)).

## 6. D3. Гибридная библиотека промптов (§48)

### 6.1. «Один промпт — один источник»

- **Идентичность промпта = канонический ключ config-item `prompts.*`** (группа `prompts_*`, категория `prompts`). Оба маршрута — **Модули → `<модуль>` → Синтезатор/Вербализатор** (`#/modules/<slug>/<stage>`) и **ИИ → Библиотека промптов → `<модуль>` → Синтезатор/Вербализатор** (`#/ai/prompts/<slug>/<stage>`) — резолвят **один и тот же элемент `configItems`**. Ни клиентских, ни серверных копий не создаётся; второй маршрут видит то же значение.
- **Один write-path:** правка пишется через `saveConfigItem` → `persistItems` (F0). Никакого второго канала записи, никакого «промпт-объекта» в `localStorage`/домене UI.
- Deep-link `#/ai/prompts/<slug>/<stage>` и `#/modules/<slug>/<stage>` — **две двери в одну комнату**; при переключении между ними выбранный промпт сохраняется, значение не переинициализируется.

### 6.2. Desktop (master-detail)

- 3 зоны (container queries): **слева** дерево `модуль → этап → промпт` (из `MODULES` + `promptSections`/`promptStageItems`); **центр** — редактор (`textarea` **видно сразу**, не в аккордеоне); **справа** — описание/переменные/параметры (технический ключ, группа, этап, источник значения F3, сброс override).
- **Навигация — дерево/табы, не аккордеоны** (§48/§69, REVISE 10.24 F6). `promptsShowAccordion` в новых раскладках возвращает `false`; аккордеоны остаются допустимы **только** для редких технических параметров (вне основной навигации) и в legacy-раскладке `openModuleWindow`.

### 6.3. Mobile

- `<768px`: **список промптов → полноэкранный редактор** (отдельный экран). Возврат — нативная/внутренняя «назад» (§3.2 п.4: `promptFocusKey` в маршруте → `routeDepth` 2). Никакого сжатия редактора «в нечитаемое состояние».

### 6.4. Reuse механики (без регресса режимов)

Переиспользуются как есть: `promptSections`, `promptStageItems`, `promptOtherItems`, `promptVisibleItems`, `itemAdvanced`, `promptModeTabs`, `switchPromptMode`, `savePromptFallbackMode`, `selectPromptMode` (OFF-карточка), бейджи источника/override F3. Расширяется **только** контейнер раскладки; поведение режимов Вербализатора не меняется (маркеры F6/10.24 зелёные).

### 6.5. Канон промптов без потерь (ADR-1013-3)

- Исходный текст промптов переносится **без изменений**. Новых канонов/`PREV_*`-слепков и **новых миграций F5 не вводит**; существующая идемпотентная миграция ADR-1013-3 не трогается. Если текст при переносе обязан сменить константу — использовать существующую идемпотентную миграцию, повторный запуск = no-op. Δ каталога = 0.
- Каноны в `plans/docs/canon/` не редактируются.

## 7. D4. Модели и подключения (§49)

### 7.1. Шесть групп — маппинг существующей структуры

Источник — `PROVIDER_BLOCKS` + группы `models_*` (Δ каталога = 0, новых групп не создаётся):

| Группа §49 | Существующие блоки/группы |
|---|---|
| Генерация текста | блок `direct` (основная/запасная модель), `models_main`, `models_fallback`, `models_llm_timeouts`, `models_llm_guard`, `models_extra_providers` |
| Распознавание речи | блок `transcription` (`transcribe_groq`, `transcribe_openrouter`) |
| Видео | блок `video_summary` |
| Эмбеддинги | блок эмбеддингов, `models_embeddings` |
| Фоновые задачи | блоки фонового интеллекта (`intel_history`/`intel_bg`/`intel_reflection`) |
| Генерация изображений | блок `image_generation`, `models_images` |

**Инвариант полноты:** каждый `PROVIDER_BLOCKS`-блок принадлежит **ровно одной** из 6 групп; тест «нет блока вне групп и нет дубля» (гарантия, что ни один провайдер не потерян — §117(3)).

### 7.2. Карточка подключения (§49)

Поля: **название · назначение · основная модель · резервная модель · статус · «Проверить» · «Настроить»**.
- **«Проверить»** — reuse `testBlock(b)` (Ф12): `POST /api/llm/test` / `POST /api/images/test`. **Новых API нет** (R16). Маска секрета в пробу **не отправляется** (бэкенд резолвит сохранённый ключ); результат — понятный статус без утечки секретов (R17).
- **«Настроить»** — раскрывает/открывает форму блока, reuse существующего рендера провайдеров (`PROVIDER_BLOCKS`, поля с `role`/`secret`). Ключи живут в категории `keys` (раздел секретов, F9) и **не копируются** в конфигурацию модуля (§46).

### 7.3. Инвариант «не менять сохранённую модель при открытии формы» (§49)

- Форма **читает** значения `configItems` (v-model) и **ничего не пишет при открытии**: нет авто-сохранения на mount, нет сброса выбора.
- `select`-опции модели формируются из статического списка **+ сохранённое значение**, если его нет в списке (иначе браузер подставил бы первый пункт). Сохранённая модель остаётся выбранной при открытии и повторном открытии.
- Тест: «открыть форму → сохранённое значение неизменно; ровно 0 POST на открытие»; доказательно падает при подстановке дефолта.

### 7.4. Сохранность всех параметров (§49)

Провайдеры, `base_url`, `model`, `keys`, fallback-модели, тайм-ауты, специальные режимы API — остаются доступны; чек-лист «параметр → экран» заполняется, покрытие гарантируется инвариантом §9.3.
