# ADR-1023-7 — Token Analytics: PG-таблицы событий/цен, сквозной correlation-id, расширение source

- **Статус:** **Accepted + реализован** (Step 2 @Architect, часть 2/3 раунда 10.23, 19.09.2026; Merge — Step 7, 19.09.2026; деплой — Step 9 @DevOps, см. `plans/ARCHITECTURE.md` §49). **AMEND (принят):** целевая БД DDL — **PostgreSQL**, SQLite остаётся **v12**; синхронизировано в `plans/features/round1023-architecture.md` §3.4 и в глобальном каноне `plans/ARCHITECTURE.md` **§49**
- **Фича:** F7 `token-analytics-dashboard-round1023`
- **Тип:** backend (DDL/telemetry) + UI (dashboard)
- **Связано:** ADR-1018-7 (резолв настроек), ADR-1019-2 (бюджет ключа), ADR-1019-8 (идемпотентные PG-миграции/сиды), ADR-1013-3 (канон-миграции — F7 не трогает), `round1023-architecture.md` §1/§3.4/§5/§8
- **Задачи:** T-2157…T-2166

## Context

1. ТЗ требует писать `module`, `step`, `input_tokens`, `output_tokens`, `cost_usd`, `timestamp` и показывать дерево последнего вызова + графики день/неделю/месяц.
2. Сейчас usage только логируется (`llm_client.py:704-715`); в бюджеты пишется `source='global'` (`chat_usage.report_call`); **таблицы цен нет**.
3. Требуется сквозной id, связывающий Stage-1 → Stage-2 → tool-раунды в одно дерево.
4. Инварианты: бюджетный учёт нельзя ломать (`chat_usage`/`worker_budget`, `source='global'`); R17 — без секретов/сырья; R16 — API аддитивно; каталог Δ = 0; меню мини-аппа заморожено.
5. Обязательный веб-ресёрч расчёта `cost_usd` выполнен (см. References): usage-объект отдаёт `prompt_tokens`/`completion_tokens`, цена — USD за 1M токенов, формула `(in/1e6·in_price)+(out/1e6·out_price)`, reasoning-токены биллятся как completion.

### Ключевой факт кода, определяющий целевую БД

- **Запись** usage: `llm_client._record_global_usage` → `chat_usage.report_call` использует **runtime PG** (`hot.get_config_cache().pg`).
- **Чтение** дашбордов: `web/api/gates.py:161` (`get_day_summary(cache.pg)`), `web/api/routes.py:680` (`key_status(cache.pg)`) — **только PG**; доступа к SQLite у web-API нет.

→ Телеметрию нельзя класть в SQLite: дашборд её не прочитает, и она разойдётся с бюджетами. Поэтому целевая БД — **PostgreSQL**.

## Decision

### D1. DDL в PostgreSQL (AMEND Part 1 §3.4)
- Таблицы `llm_usage_events` и `llm_model_prices` создаются идемпотентно в `services/pg_db.py` (`CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`), сид цен — `INSERT ... ON CONFLICT (model) DO NOTHING`.
- **Δ SQLite = 0** (user_version остаётся **v12**). Предварительная формулировка Part 1 §3.4 («SQLite v12→v13») **AMEND'ирована**: целевая БД — **PostgreSQL** (web-API читает только PG), SQLite остаётся v12; Part 1 сам оговаривал, что целевые Δ/DDL F4–F9 фиксируются в Part 2/3. На Merge синхронизировано в §3.4 feature-дока и зафиксировано в глобальном `plans/ARCHITECTURE.md` §49. PM-задача T-2158 (`pg_db.py`) — согласована.
- Изоляция: новые таблицы **не** пересекаются с `chat_usage`/`worker_budget`; откат — `DROP TABLE` (телеметрия безопасна).

### D2. Схема `llm_usage_events`
`id, ts, correlation_id, module, step, tool_name, source, chat_id, model, input_tokens, output_tokens, tokens_estimated, cost_usd NUMERIC(12,6), price_known` + индексы по `ts`, `correlation_id`, `(module, ts)`. Значения из реального `usage` ответа; при отсутствии — оценка + `tokens_estimated=true`.

### D3. Таблица цен `llm_model_prices`
`model PK, input_usd_per_1m NUMERIC(12,6), output_usd_per_1m NUMERIC(12,6), currency, updated_at`; идемпотентный сид стартовых цен (значения владелец уточняет). Резолв — `services/llm_pricing.py` (in-process кэш + invalidate), **fail-safe**: нет цены → `cost_usd=0`, `price_known=false`. Δ каталога = 0 (управление ценами — PG/опц. admin-API).

### D4. Сквозной correlation-id
- `usage_events.new_correlation_id()` (UUID4 hex) создаётся **один** раз на ответ оркестратором.
- Опциональные kwargs `module/step/correlation_id` добавляются в `llm_client.generate`/`generate_chat` (default `None` → внутренний id) и `tool_loop.chat_with_tools` (проброс в каждый раунд, `step="tool"` + `tool_name`).
- Stage-1 → `stage1`, tool-раунды → `tool`, Stage-2 → `stage2`, изображение F5 → `image`.
- `services/system2_handoff.py` — **no-op по коду** (ступень **F3 → F6 → F7**): модуль не делает LLM-вызовов, `correlation_id` — не поле Stage-1 JSON; id идёт kwargs-ами `оркестратор → llm.generate/generate_chat`/`tool_loop.chat_with_tools`. Поля F3/F6 (`response_mode`, `cover_prompt` и др.) не трогаются.

### D5. Расширение `source`
- `source` расширяется до `'global'|'chat'|'byok'|'worker'|'image'` **только** в `llm_usage_events`. Бюджетный контур не меняется: `_record_global_usage` по-прежнему трактует только `source='global'` (иначе бюджет не тратится), а событие аналитики пишется для любого source.

### D6. Флаг, ретенция, откат
- `TOKEN_ANALYTICS_ENABLED` — env-only `ClassVar`, default ON, Δ каталога = 0. OFF → нет записи/дашборда, бюджеты байт-в-байт.
- `TOKEN_ANALYTICS_RETENTION_DAYS` — env-only, default 90; opportunistic cleanup, fail-open.
- Откат: OFF / `git revert` + `DROP TABLE`.

## Consequences

**Positive**
- Единый, читаемый web-API источник телеметрии в той же PG, что и бюджеты → корреляция «бюджет ↔ дерево вызовов» без кросс-БД.
- Бюджетный учёт изолирован и не ломается; ошибки аналитики fail-open.
- Стоимость считается по реальным токенам, с честным флагом «цена неизвестна».
- Каталог/меню не растут (Δ 0); API аддитивно (R16).

**Negative**
- Две новые PG-таблицы и рост объёма (ретенция 90 дней; при необходимости — партиционирование позже).
- Точность стоимости зависит от актуальности таблицы цен (владелец ведёт).
- Проброс `correlation_id` затрагивает несколько файлов (аддитивные kwargs) — нужен сквозной тест, что id не теряется в tool-loop.
- **AMEND** к Part 1 §3.4 по целевой БД — требует подтверждения на Human Gate (влияет на ожидания Part 3/F9).

## Alternatives

- **A1. SQLite v12→v13 (буквально Part 1)** — **отклонено**: web-API читает только PG; телеметрия была бы недоступна дашборду и разошлась бы с бюджетами.
- **A2. Расширять `chat_usage` новыми колонками** — **отклонено**: риск сломать бюджетный контур (High), нет `cost_usd`/`module`/`step`/`correlation_id` по смыслу.
- **A3. Считать cost на клиенте/UI** — **отклонено**: нужно персистентно и централизованно.
- **A4. Генерировать correlation-id внутри `llm_client`** — **отклонено**: не свяжет Stage-1/Stage-2/tool в одно дерево (нужен единый id оркестратора).
- **A5. Жёстко зашитые цены в коде** — **отклонено**: цены меняются; таблица + fail-safe.
- **A6. Новый каталоговый ключ цен/флага** — **отклонено**: Δ каталога = 0.
