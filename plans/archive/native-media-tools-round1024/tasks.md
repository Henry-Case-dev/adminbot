## Цель
Ситуация: «Бот скачай видос» реплаем на **нативное TG-видео** → срабатывает Fast-Track `handlers/video_download.py`; если у видео в сообщении есть непустой caption-URL, запрос уходит в URL-ветку вместо `_handle_native_media`; при probe-fail нет меню качества и нет объяснения причины («⏳ Скачивание без выбора качества…» / «че ты мне суешь? я не могу это скачать»). Плюс: инструменты `summarize_video`/`download_media` требуют обязательный `url` и не умеют нативное медиа. Исправить маршрутизацию, дать инструментам работать с нативным медиа и объяснять причину отказа.

## Критерии приёмки
- Реплай «скачай» на нативное видео (в т.ч. с ссылкой в caption) скачивает/пересылает **нативное** видео, не уходя в URL-ветку.
- При probe-fail пользователь видит **понятную причину** отказа, причина есть в логах.
- Инструменты умеют работать с нативным медиа из реплая; ссылочный путь не сломан.
- Канон R9 консистентен: счётчик на момент F14 — 9, финальный **10** (после `transcribe_video`, F19); устаревший комментарий исправлен.
- Полный pytest — 0 failed; `git diff --check` чист.

## Риски
- **R1 (High):** изменение схем инструментов ломает tool-loop/фактчекер → тесты (b)/(e), согласование с ADR-1015-3.
- **R2 (High):** приоритет медиа над ссылкой ломает легитимный «скачай <ссылка>» при случайном видео → решение T-2299 + тест (a)/(e).
- **R3 (Medium):** двойное скачивание (нативный fetch + downloader) → переиспользование существующей инфры, лимиты.
- **R4 (Medium):** расхождение канона инструментов (8/9) → синхронная правка комментария + тест (d).
- **R5 (Low):** секреты/пути в логах probe → R17-маскирование.
