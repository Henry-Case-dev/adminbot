# ADR-1024-3 — Анти-клише: снятие потолка 20 (default 200, регулируемый) и починка крона

- **Статус:** **Accepted** (Step 2 @Architect, часть 1/2 раунда 10.24, 19.09.2026). **AMEND ADR-1023-4 D2.**
- **Фича:** F7 `anticliche-cron-limit-round1024`
- **Тип:** backend/worker (крон) + каталог/UI-подпись
- **Связано:** ADR-1023-4 (динамический кэш, лимит ≤20), ADR-1024-1 (логирование крона), `round1024-architecture.md` §3.3/§3.4
- **Задачи:** T-2237…T-2243

## Context

1. `ANTICLICHE_MAX_PATTERNS = 20` — код-константа (`services/anticliche_cache.py:26`), применяется в `_rules_from_patterns` (`:94`), в `build_patterns` (`services/anticliche_worker.py:117,142-143`), в промпте `EXTRACT_SYSTEM_PROMPT.format(max=…)` (`:321`) и отдаётся в API (`web/api/anticliche.py:79`). Владелец: «снять хардкод 20, по умолчанию 200, сделать регулируемым, числовое поле в UI» (UPD3 п.3).
2. Крон: `services/anticliche_worker.py:192-198` — `IntervalTrigger(days=REFRESH_DAYS=7, jitter=3600)`. У `IntervalTrigger` первый тик — **через 7 дней**, поэтому после деплоя список не обновлялся сам; ручное обновление работало → «крон не отработал» (UPD2 п.5).
3. `asyncpg`/деплой: рестарты бота должны не «съедать» окно и не слать LLM лишний раз.
4. R17: список клише — литеральные фразы; наружу/в логи только коды/счётчики (ADR-1023-4 D4 сохранён).
5. Техдолг: диагностируемость падения крона (фаза) — пересекается с F2.

## Decision

### D1. Лимит — динамический резолв, default 200 (AMEND ADR-1023-4 D2)
- `ANTICLICHE_MAX_PATTERNS_DEFAULT = 200`, `ANTICLICHE_MAX_PATTERNS_HARD_CEILING = 1000` (защитный код-потолок от раздувания промпта/стоимости).
- `max_patterns() -> int` резолвит `hot.get("limits.anticliche_max_patterns", settings.ANTICLICHE_MAX_PATTERNS)` (per-chat → global → env), clamp `[1, ceiling]`.
- Старая константа `ANTICLICHE_MAX_PATTERNS` сохраняется как deprecated-alias (=default) для совместимости импортов, но **вся логика** читает `max_patterns()`.
- Применение: `_rules_from_patterns` (кэш детектора), `build_patterns(max_patterns=resolved)`, `EXTRACT_SYSTEM_PROMPT.format(max=resolved)`, `web/api/anticliche.py` (отдаёт резолвленное значение).
- Δ каталога: **+1 ключ** `limits.anticliche_max_patterns` (int, default 200) + **+1 группа** `limits_anticliche` (category `limits`), замапленная на вкладку `prompts` (там карточка монитора `data-block="anticliche-monitor"`). Структура табов/меню не меняется (`tma-menu-freeze` соблюдён).

### D2. Крон: первый прогон вскоре после старта + защита от лишних вызовов при рестарте
- В `start()` джоб получает `next_run_time = now + ANTICLICHE_FIRST_RUN_DELAY_MINUTES` (default **5**), далее `IntervalTrigger(days=7, jitter=3600)`.
- `tick(force=False)`: перед `refresh()` читает `anticliche_cache.fetch_cache()`; если `fetched_at` свежее `REFRESH_DAYS` — `skip reason=fresh` (без LLM). Ручной форс (`POST /api/anticliche/refresh`) — `force=True`.
- Это закрывает «первый запуск через 7 дней» и делает рестарты безопасными **без persistent job store и без DDL** (источник истины — `fetched_at` в PG).
- Лог при старте: `next_run_time`, `interval_days`; при тике — итог/причина.

### D3. Диагностируемость (совместно с F2)
- `refresh()` логирует фазу падения (`fetch|llm|parse|empty|write`), `exc_info`, число полученных/сохранённых — через `external_log`.
- `misfire_grace_time=3600`, `max_instances=1`, `coalesce=True` сохраняются.

### D4. Канон/совместимость
- Промпт `EXTRACT_SYSTEM_PROMPT` остаётся **код-константой без перечисления клише** (grep-тест тропов сохранён); меняется только подставляемое `{max}`.
- Δ DDL = 0.

## Consequences

**Positive**
- Парсер забирает все клише источника в пределах защитного максимума (default 200).
- Поле в UI даёт владельцу регулировать потолок без деплоя.
- Крон отрабатывает самостоятельно вскоре после деплоя; рестарты не вызывают лишний LLM-вызов (freshness-skip).
- Причина любого сбоя крона видна в логах (F2).

**Negative**
- Длинный список (до 200 правил) увеличит in-process детектор и (при ручной правке) UI-список — митигируется hard-ceiling 1000 и нормализацией/дедупом.
- +1 группа/ключ каталога → обновление пин-тестов `test_param_catalog`/`test_frontend_tab_mapping` в том же коммите.
- `jitter=3600` остаётся — точное время первого прогона не гарантировано после смещения, но `next_run_time` фиксирует старт.

## Alternatives

- **A1. Оставить 20 или убрать лимит вовсе** — **отклонено**: 20 искусственно режет (ТЗ), безлимит раздувает промпт/стоимость.
- **A2. Persistent APScheduler job store (`SQLAlchemyJobStore`/файл)** — **отклонено** в этом раунде: лишняя инфраструктура; freshness-check по `fetched_at` проще и без DDL.
- **A3. `DateTrigger` (одиночный первый запуск) + отдельный interval-джоб** — **отклонено**: два джоба сложнее в тестах/очистке; `next_run_time` на interval-джобе решает задачу.
- **A4. Хранить лимит в `bot_settings` без каталога** — **отклонено**: владелец требует числовое поле в UI → каталоговый ключ единственно корректный путь.
- **A5. Запускать refresh безусловно на каждом старте** — **отклонено**: лишние LLM-вызовы при частых рестартах.
