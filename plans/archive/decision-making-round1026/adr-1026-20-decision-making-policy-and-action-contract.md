## Контекст

§38 фиксирует проблему: «Сейчас бот часто отвечает на любое обращение, даже если ответ не нужен» (пример: бот отправил картинку, пользователь «АХАХА» → полноценная генерация и длинный ответ); «Необходимо расширить существующий механизм принятия решений». Бот должен уметь: ответить текстом; вызвать инструмент; поставить реакцию; проигнорировать сообщение. §39 требует **разделить ACTION** {reply, react, silent, tool} и **STYLE** {casual, serious, deep_research}; молчание/реакция — не стили Вербализатора; `style=silent` запрещён; Вербализатор не генерирует пустой текст «на удаление»; дополнительные поля допустимы. §40 задаёт **пример** контракта `{action, style, target_message_id, reaction, reason_code}` («не обязательно использовать именно такую схему»), требует явно определять действие/цель/необходимость инструментов/стиль/причину и запрещает вывод служебного JSON в чат. §42 перечисляет тривиальные сообщения, но запрещает жёсткое правило «короткое → молчание» (контрпример «Почему?») и требует учитывать тред/`reply_to`/предыдущее сообщение бота/вопрос/намерение/завершённость. §43 требует, чтобы явные содержательные обращения получали ответ/действие, не терялись молчанием, а недоступный инструмент давал корректную ошибку ожидающему результат. §44 разрешает реакцию для эмоции без ожидания содержательного ответа, но запрещает реагировать на каждое сообщение, использовать одну и ту же реакцию всегда и случайность как основной механизм; реакция должна соответствовать контексту и характеру. §45 перечисляет условия молчания и требует не делать бота полностью пассивным, сохранив автономную активность. §46 задаёт порядок: silent → без Вербализатора и без сообщения; react → без Вербализатора при выбранной реакции; reply → стиль + Вербализатор; tool → инструменты, затем итоговое действие; текст не генерируется ради решения о молчании. §47 требует знать контекст предыдущих действий (reply_to, что бот отправил — изображение/статья, был ли вопрос, ожидается ли результат инструмента). §48 задаёт маршрут «Модули → Ответы в чате → Принятие решений» и ровно 3 параметра, запрещая «десятки произвольных коэффициентов» и требуя поддержки global/local.

**Фактическое состояние baseline (Step 0 + карта кода).** A1 ✅ (Merge §83, ADR-1026-14) уже ввёл **программный слой** решения о действии внутри существующего Синтезатора: `services/direct_chat_service.py:467–643` — константы `ACTION_REPLY/REACT/SILENT/TOOL` (`:468–472`), `@dataclass CoordinatorDecision` (`:499–515`), `coordinator_enabled()` kill-switch `DIRECT_COORDINATOR_ENABLED` (`:518–523`), `_coordinator_intent/_addressee/_tool_names/_evaluate/_choose_action/_memory_need` (`:526–600`), `build_coordinator_decision` (`:603–623`), R17-логи (`:626–643`); интеграция до Stage-2 (`:1015–1051`), гейт Stage-2 (`:1037–1043`). При этом `_coordinator_choose_action` (`:579–591`) выбирает **только `tool|reply`**; wire-`action`/react/silent/`reason_code` **не введены** (граница A7, ADR-1026-14 D2). Молчание/реакция сейчас возникают только как реакция на пустой/битый ответ: legacy пустой-reply → `react_moai` (`:1061–1070`), провайдер-пустой (`LLMBadResponseError`) → `react_moai` (`:1004–1008`); реакция — существующий примитив `smartmodule_utils.react_moai:93–107` (🗿, best-effort, fail-silently). Контекст сообщений — `bot_replies`/`remember_bot_reply`/`get_bot_reply_parent` (`:726–764`). Stage-1 System 2 (`_synthesize_direct_answer`) запускается **только** на ходах с реально вызванными инструментами (`:1037–1043`) и несёт `response_mode` (стиль, ADR-1023-3). `physical-two-call-pipeline` для direct-чата закреплён **ADR-1022-5** (ровно 2 физических LLM-вызова, tool-loop внутри Stage-1). Настройки direct-чата живут в `mod_direct` (`param_catalog.py:2149–2156`; `web/app.js:489–494`, `WORKSPACE_TABS.mod_direct:573`); legacy silence — `CHAT_SILENCE_ENABLED`/`CHAT_SILENCE_AFTER_COOLDOWNS` (`:846/:1251`, троттлинг-путь `:782–793`). **GAP A7:** (a) нет wire-разведения `action`/`style`; (b) нет политики молчания/реакций; (c) нет контекста §47; (d) нет 3 настроек §48; (e) нет `reason_code`.

## Решения

**D1. U-A7-1 — контракт решения: расширение существующего `CoordinatorDecision`, а не LLM-JSON; `action` отдельно от `style`.**
- **Выбрано:** аддитивное расширение **существующего** A1-объекта `CoordinatorDecision` (`direct_chat_service.py:499–515`) полями: `action` {reply,react,silent,tool}; `style` {casual,serious,deep_research}|"" ; `target_message_id: int|None`; `reaction: str|None`; `reason_code: str`; `needs_tools: bool` + `tool_calls`; A1-поля (`intent`/`addressee`/`memory_need`/`evaluation`/`enabled`) сохраняются. Контракт — **внутренний** (§40 «схема — пример», «не выводить служебный JSON в чат»); JSON Stage-1/Stage-2 **не меняется**; второй контракт/координатор не вводится.
- **Разведение:** `style` — только текстовые действия (на tool-пути — существующий `response_mode` Stage-1, ADR-1023-3; на простом пути — существующая доставка модельного текста); `style="silent"` **невозможен** (нормализация/тест); молчание/реакция не стили (§39). `action` — **поле решения**, не tool (канон 12).
- **Почему не «новый wire-объект»:** A1 уже объявил `CoordinatorDecision` домом решения (`:499–515`, D2); §38 требует **расширить существующий** механизм; второй контракт = дублирование/дрейф.
- **Альтернативы:** (i) расширить `CoordinatorDecision` — **выбрано**; (ii) отдельный wire-dataclass/LLM-JSON — отклонено (дублирование, дрейф канона, запрет JSON в чат).

**D2. U-A7-2 — где вычисляется `action`: программный слой внутри Синтезатора, двухфазно, без 3-го LLM-вызова (AMEND `physical-two-call-pipeline`).**
- **Выбрано:** `action` вычисляется **программно** в существующем direct-контуре A1:
  - **Фаза P (до генерации текста):** детерминированная политика над сигналами §42–§45/§47 → `silent`/`react`/`reply`. `silent`/`react` — **короткое замыкание**: LLM-вызов вывода текста **не** выполняется, Вербализатор не запускается. `reply` — продолжение существующего пути.
  - **Фаза T (A1, после LLM/tool-loop):** существующий `_coordinator_choose_action` (`:579–591`) расширяется `reason_code`; если инструменты вызваны и финал не деградировал/не `lore_compiled` → `tool`; иначе `reply`. `tool` → существующий Stage-2 (Вербализатор) → итоговое `reply` (или `reply` с честной ошибкой при недоступности — §43).
- **Инвариант `physical-two-call-pipeline` (ADR-1022-5):** ровно **2** физических LLM-вызова System 2 на tool-ходе (`await_count==2`) сохранены; на `silent`/`react` — **0** LLM-вызовов вывода текста; новых вызовов нет. Это **AMEND-заметка** к ADR-1022-5: decision-слой встроен в существующий пайплайн, не добавляя вызова.
- **Отвергнутая альтернатива (модель предлагает `action` в Stage-1 JSON):** (1) Stage-1 System 2 запускается **только** на tool-ходах (`:1037–1043`) — не покрывает первичные §42/§45-кейсы (ходы без инструментов, где и решаются молчание/реакция/простой ответ); (2) «решать молчание» генерацией текста противоречит §46/инварианту 13; (3) дублирует A1-слой и провоцирует дрейф канона (A1 D2 уже отклонил JSON-поле `action`).
- **Альтернативы:** программный слой (выбрано); Stage-1 JSON-поле (отклонено, см. выше); третий LLM-вызов (запрещён).

**D3. Политика §42–§45 — детерминированный приоритетный отбор `action`; никакой случайности; реальные задачи не теряются.**
- **Классы (программно):** `explicit_request` (§43-маркеры/адресованность), `question`, `laughter` («АХАХА»/«Лол»), `emoji_only`, `acknowledgement` («Ок»/«Понял»/«Спасибо»/одобрение), `other`.
- **Приоритет (первое совпадение):** (0) kill-switch OFF → A1-baseline; (1) explicit_request/question → `reply` (или `tool`); (2) сработал image/dig-пре-гейт → `reply`/`tool`; (3) ожидается результат инструмента → `reply`/`tool_unavailable`; (4) реакция на собственное изображение + toggle → `react` (`image_reaction`/`laughter`); (5) эмоция без ожидания контента + toggle → `react` (`laughter`/`emotion`/`emoji_reaction`); (6) acknowledgement + toggle → `silent`/`react` (`acknowledgement`); (7) не адресовано → `silent` (`not_addressed`); (8) диалог завершён/бот недавно ответил → `silent` (`dialogue_completed`/`recent_reply`); (9) иначе → `reply` (`default`); fail-safe (ошибка) → `reply` (`error`).
- **§42 «нет жёсткого правила короткое → silent»:** длина **не** решающий признак; «Почему?» → `question` → `reply` (REQ-A7-12).
- **§43 «реальные задачи не теряются»:** explicit/question никогда не `silent`; недоступный инструмент → `tool_unavailable` + честный ответ (REQ-A7-14/-15/-16).
- **§44 «не на каждое сообщение / не одна и та же всегда / не случайность»:** `react` — только контекстно-обусловленный класс, не универсальный исход; выбор детерминирован (повтор входа → тот же исход), без `random` (REQ-A7-18/-19).
- **§45 «не пассивен»:** `silent` — только для не-адресованных/тривиальных/завершённых; явные обращения всегда обслуживаются (REQ-A7-21).
- **§46 порядок:** `silent` → без Вербализатора/сообщения; `react` → без Вербализатора; `reply` → стиль + существующий текстовый путь; `tool` → инструменты → итоговое действие; текст не генерируется ради решения о молчании (REQ-A7-22…-26).
- **Альтернативы:** эвристика по длине — отклонено (§42); случайный выбор реакции — запрещено (§44); ML/второй вызов для классификации — отклонено (нет 3-го вызова; детерминизм важнее).

**D4. Порядок исполнения §46 и изоляция Вербализатора.**
- `silent` → `return` без отправки и без Вербализатора (0 LLM-вызовов текста).
- `react` → `react_moai` (существующий примитив) на `target_message_id`; Вербализатор не запускается; текст не генерируется.
- `reply` → стиль выбран (tool-путь: `response_mode` Stage-1 → Stage-2 Вербализатор, как сегодня; простой путь: существующая доставка модельного текста, без нового вызова). Новый LLM-вызов не добавляется.
- `tool` → существующий `tool_loop` (A2; не переписывается) → итоговое действие; недоступность/ошибка при ожидании результата → `reply` с `tool_unavailable`.
- **Существующие safety-net-фолбэки не ломаются:** пустой reply → `react_moai` (`:1061–1070`), провайдер-пустой → `react_moai` (`:1004–1008`) остаются **ниже** слоя решения (только reply-ветка). Пустой текст «на удаление» не генерируется (REQ-A7-07).
- **Альтернатива «генерировать текст, потом скрывать» (silent-after-generation)** — отклонено: нарушает §46/инвариант 13 и есть нежелательное поведение §38.

**D5. U-A7-3/U-A7-5 — реакция: правила = A7, механика = A8; фиксированная 🗿 через существующий `react_moai`.**
- **A7-решение:** при `action=react` `reaction` = **🗿** (`REACTION_MOAI`); `target_message_id` = id **trigger-сообщения пользователя** (не `reply_to_id` и не id предыдущего сообщения бота); причина — `reason_code`.
- **Исполнение:** reuse **существующего** примитива `smartmodule_utils.react_moai:93–107` (best-effort, fail-silently). A7 **не реализует** новый механизм `setMessageReaction` и не вызывает его напрямую. Полная §41-механика — доступность реакции в конкретном чате, разрешённая альтернатива/отказ, постановка на правильное сообщение при сбоях, «не превращать ошибку реакции в длинный текстовый ответ» — **A8** (не переопределяет политику A7).
- **Fallback:** недоступная реакция → `react_moai` уже fail-silently (WARNING, без текста) → поведение = молчание, не длинный ответ (REQ-A7-16/-34). Выбор «skip vs reply»/альтернативный эмодзи — A8.
- **Интерпретация §44 «не использовать одинаковую реакцию в любой ситуации» (не ослабление):** на уровне политики `react` **не** является универсальным ответом и выбирается только контекстно; «одинаковая реакция» относится к политике ответа (не реакция на всё), а разнообразие эмодзи через доступный набор — §41/A8. Контекстная реакция — дальняя волна/A8.
- **Note для @PM:** `tasks.md` T-3654/§18 («без вызова `setMessageReaction`») уточняется: A7 не реализует **новый** механизм и не вызывает `setMessageReaction` напрямую, но переиспользует существующий `react_moai` как исполнитель. Реконсиляция — T-3650.
- **Альтернативы:** контекстный выбор эмодзи в A7 — отклонено (требует §41-доступности/набора = A8); новый механизм реакции в A7 — отклонено (граница A8); не реализовывать реакцию вовсе — отклонено (противоречит §38/§44/§52 п.16).

**D6. U-A7-4 — настройки §48: секция «Принятие решений» в `mod_direct`, ровно 3 параметра; санкция Δ каталога.**
- **Маршрут:** «Модули → Ответы в чате → Принятие решений» = новая **группа** внутри `mod_direct` (`param_catalog.py:2149–2156`; карточка `web/app.js:489–494`).
- **3 параметра** (категория `flags`, type `bool`, default **ON**, per-chat-совместимые, `get_chat_param` override→global→default):
  1. `CHAT_DECISION_IGNORE_TRIVIAL_ENABLED` — «Игнорировать незначимые обращения»: «Позволяет боту не отвечать на сообщения, которые не требуют продолжения разговора».
  2. `CHAT_DECISION_REACTIONS_ENABLED` — «Использовать реакции вместо ответа»: «Бот может поставить реакцию, если полноценный текст не нужен».
  3. `CHAT_DECISION_IMAGE_REACTIONS_ENABLED` — «Реакции на короткие ответы к собственным изображениям»: «Позволяет использовать реакции или молчание вместо развёрнутого ответа».
- **Новая группа:** `GroupSpec("flags_decision_making", "flags", "Принятие решений", <описание>, <order>)`; добавлена в `frozenset` `CATEGORY_FLAGS` правила `TAB_MOD_DIRECT`. Новых вкладок/TAB_RULES-записей нет.
- **Минимум (§48):** ровно 3; «десятки коэффициентов» запрещены; новые — только после отдельного исследования/санкции.

**D7. U-A7-6/U-A7-8 — сосуществование и kill-switch: `CHAT_SILENCE_*` не пересекается; env-only `DIRECT_DECISION_MAKING_ENABLED`.**
