# ADR-1019-4 — Развязка контекстных лимитов direct-чата: per-block caps vs общий бюджет, целевые значения, аварийный chars-fallback

- **Статус:** Proposed (Step 2 @Architect, раунд 10.19; **итерация 2 — UPD3, 15.09.2026**)
- **Дата:** 2026-09-15
- **Раунд:** 10.19, фича F4 `direct-context-limit-expansion` (T-1809) + итерация 2 (T-1853)
- **База:** HEAD `fd6acc7`. **Связано:** §4 (direct_chat_service), §20 (context-layer X-features), F3/ADR-1019-3, **ADR-1019-8** (sentinel-таблица, сид настроек чатов, изоляция), ADR-1013-1.
- **AMEND:** уточняет контракт двух контуров обрезки контекста, заложенный раундами 8/10 (`_build_global_context` vs `_apply_context_budget`); значения 64.7 (`token_default=1000`) объявляются устаревшими. **AMEND (итерация 2):** D3 дополнен per-chat sentinel `−1`/`0` и потолком безопасности (UPD3 п.2-3). Не supersede — формализует неявную модель.

## Context

1. Симптом владельца (UPD2, строки 162,174): «контекст глобальный обрезают с семи тысяч токенов до 869 — недопустимо; объясни, почему так жёстко; нужна понятная настройка».
2. Root cause: `_build_global_context` (`direct_chat_service.py:1993-2002`) вызывает `resolve_chat_limit(..., token_default=1000, …)`; при `CHAT_GLOBAL_CONTEXT_MAX_TOKENS=None` и незаданной env-чарсе (`CHAT_GLOBAL_CONTEXT_MAX_CHARS` не в окружении) функция возвращает `("tokens", 1000)` → `safe_budget(1000) = 1000/1.15 = 869` (`token_counter.py:119-121`). Обрезка — следствие **код-дефолта**, а не настройки.
3. Вторая, независимая обрезка: `_apply_context_budget` (`:1125-1258`) режет общий контекст по долям от `CHAT_CONTEXT_BUDGET_TOKENS=4000`; global-доля ≈1200, а порядок урезания (`anchors→rag→thread→global→map`) может резать global **второй раз** после per-block cap.
4. `CHAT_THREAD_MAX_TOKENS=None` → штатный путь уходит в chars-fallback 2000 с WARNING «токенный лимит не задан» (`token_counter.py:124-140`) — «костыль» по чекапу.
5. Инварианты: R16, R17, канон промптов не трогается, каталог-Δ только с санкцией, порядок роутеров `bot.py`.

## Decision

### D1. Явная модель «два контура, разные владельцы»
- **Per-block caps** (`limits.chat_global_context_max_tokens`, `limits.chat_thread_max_tokens`) — максимум токенов конкретного блока; владелец — сборщик блока (`_build_global_context` / сборка ветки).
- **Total budget** (`limits.chat_context_budget_tokens` + доли) — суммарный потолок; владелец — `_apply_context_budget`.
- Один и тот же блок **не режется дважды «наугад»**: `_apply_context_budget` не опускает блок ниже его per-block потолка, если сумма влезает в общий бюджет. **Реализация (D-1, 16.09.2026):** `global`/`thread` исключены из безусловного прохода по долям — они участвуют только в цикле урезания и только при фактическом переполнении общего бюджета (`total > budget`). Прочие блоки (`map`/`rag`/`branch`/`anchors`) по-прежнему ограничиваются долями (у них собственного per-block потолка нет).

### D2. Инвариант конфигурации (видимая причина усечения)
Инвариант сравнивает **реально применяемые доли** `_apply_context_budget` от `effective = max(1, budget − fixed_tokens)`:
`global_share = CHAT_BUDGET_GLOBAL_RATIO × effective ≥ safe_budget(global_cap)` **и**
`thread_share = CHAT_BUDGET_THREAD_RATIO × effective ≥ safe_budget(thread_cap)`.
При нарушении — один `WARNING` с числами (`[direct] context config inconsistent | budget=… fixed=… -> effective=… | global_share=… < global_budget=… …`), работа продолжается (fail-open). Это заменяет «непонятную тихую обрезку» на диагностируемую. **Почему не `budget ≥ Σcaps + fixed`:** фактическая обрезка идёт по долям (0.30/0.20) от `effective`, а не по `Σcaps`, поэтому проверка «budget < caps» пропускала реальный случай (fixed≈2822, budget=16000: доля 0.30×13178=3953 < 4347). D-1: при вызове передаётся оценка `fixed_tokens` (сумма неприкосновенных блоков).

### D3. Целевые значения (глобальный предохранитель) + per-chat sentinel (итерация 2)
`CHAT_GLOBAL_CONTEXT_MAX_TOKENS`: `None`(→код-дефолт 1000) → **5000** (эфф. ≈4347, было 869);
`CHAT_THREAD_MAX_TOKENS`: `None` → **3000** (эфф. ≈2608);
`CHAT_CONTEXT_BUDGET_TOKENS`: **4000** → **16000** (global-доля 4800 ≥ 4347, thread 3200 ≥ 2608). Доли `CHAT_BUDGET_*_RATIO` не меняются.
**UPD3 (итерация 2):** значения — **предохранитель для всех чатов**; безлимит — **только per-chat sentinel** `−1` (эффективно = `CHAT_CONTEXT_UNLIMITED_CEILING_TOKENS`, env-only, default 32000; `0` = «не задано» → глобальный дефолт). Целевой чат `-1002661910336` → `−1` сидом (ADR-1019-8 §D2/D4). Обоснование 16000: при 4000 общий бюджет физически меньше одного потолка `<Global_Context>` — двойная обрезка конструктивно неизбежна.

### D4. chars-fallback — аварийный путь, не штатный
`resolve_chat_limit` возвращает `("tokens", token_default)` когда токенный лимит не задан нигде; chars-ветка применяется только при **явно заданном** chars-значении. «Ной»-WARNING понижается до `logger.debug`; `WARNING` остаётся только при фактическом усечении по chars. Дефолт `CHAT_THREAD_MAX_TOKENS=3000` убирает chars-fallback из основного пути.

### D5. Человекочитаемое описание в каталоге
Единицы в UI — **«слова (кусочки текста)»**: round-10.9 jargon-гейт
(`test_webapp_round109_ui.py::test_no_forbidden_jargon`) запрещает слово
«токены» в `title_ru`/`description` каталога; технически значение — токены
(зафиксировано в docstring/комментарии `param_catalog.py`). Формулировки о
`<Global_Context>`/`<Conversation_Thread>`/общем бюджете и последствиях
увеличения (см. spec §4.5) + sentinel-пояснение (`0`/`−1`). Δ записей
каталога = 0.

### D6. Feature flag не вводится
Значения и так конфигурируемы; расширение — новые дефолты + данные. Откат — `git revert` + возврат значений. Progressive delivery — по чату (тестовый → прод). При желании владельца — per-chat override без нового флага.

### D7. Обязательный замер
T-1815: токены контекста и латентность сборки до/после на реальных данных; результат — в evidence раунда.

### D8. Фиксы Батча D (16.09.2026, ревью @Reviewer)
- **D-1/D-2:** инвариант учитывает `fixed_tokens` и доли (см. D2); `_apply_context_budget` не режет `global`/`thread` по долям при `total ≤ budget` (см. D1). Регресс-тест: блок ≥ `safe_budget(5000)=4347` + `protected` ~3000 при `budget=16000` — без усечения.
- **D-7:** безлимит общего бюджета (`-1`) пишет `context_limit=None` + флаг `unlimited` (`record_context_usage`, `_PROCESS_ACCOUNTING`, `status_service`), UI показывает «Безлимит (∞)» вместо ложных 100% (`used/used`).
- **D-8:** `token_counter` клампит `token_default` снизу (`max(1, int(...))`) — отрицательный env-дефолт не даёт `safe_budget(-1)=1` (S10.19-13).

## Consequences

**Positive**
- Обрезка 869 устранена; бот снова «помнит» существенную часть фона.
- Причина любого усечения видна (инвариант + точечные логи) — владелец получает объяснение, а не «чёрный ящик».
- Два контура формализованы; будущий дрейф ловится тестом инварианта.
- Каталог-Δ=0.

**Negative**
- Рост контекста → выше стоимость и латентность на вызов (митигируется конфигурируемостью и замером T-1815).
- Изменение `resolve_chat_limit` затрагивает несколько вызовов (global/thread/summary-пути) — нужны регресс-тесты.
- PG-значения прод не мигрируют автоматически (`ON CONFLICT DO NOTHING`) — фактическое применение через UI/@DevOps.
- Формально меняется поведение при `None`-конфигурации: вместо 1000/869 будет 5000/4347 (осознанно).

## Alternatives

- **A1. Просто поднять `token_default=1000` в вызове.** Отклонено как半-мера: не лечит двойную обрезку и `None`-конфигурацию, оставляет chars-костыль.
- **A2. Убрать `_apply_context_budget` совсем.** Отклонено: общий бюджет нужен для контроля суммы (RAG+карта+ветка+фон) и стоимости.
- **A3. Убрать per-block caps и полагаться только на общий бюджет.** Отклонено: тогда один блок (RAG) может вытеснить фон; per-block потолки дают предсказуемость.
- **A4. Оставить `None` и «чинить» chars-веткой.** Отклонено: чекап прямо называет это костылём; штатный путь должен быть токенным.
- **A5. Огромный общий бюджет (64k) «на всё».** Отклонено: кратно растёт стоимость/латентность; 16000 — рабочий баланс при заявленных целях.
- **A6. Feature-flag «расширенный контекст».** Отклонено: dead-code-ветка, значения уже настраиваемые.
