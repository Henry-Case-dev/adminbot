# ADR-1019-5 — Локальный файловый fallback для медиа/аватаров: общий хелпер + диагностика рассинхрона ФС↔БД

- **Статус:** Accepted (реализовано в F6, Step 4 @Builder, раунд 10.19; **итерация 2 — фиксы ревью Батча E: honest-контракт диагностики (D-4), scan вне event loop (D-3), TTL-кэш (D-5), `restore_missing_files` убран в backlog**).
- **Дата:** 2026-09-15
- **Раунд:** 10.19, фича F6 `media-files-avatars-sync` (T-1826)
- **База:** HEAD `fd6acc7`. **Связано:** §7 (медиа-релеи), §14 (media_download/D292), раунд 10.17 (avatars-warnings-hygiene, BUG-4), ADR-1013-1.
- **AMEND:** распространяет контракт локального чтения `media_download.fetch_media_to_tmp` (Epic 78/D292) на **все** потребители Bot API-файлов, включая аватары; уточняет политику негативного кэша (не меняет).

## Context

1. Прод-симптом: приложение не находит `photos/file_456.jpg` / `file_457.jpg`; аватары «отлетают» с `fetch failed` для юзера `525660918`; «файловая помойка не синхронизирована с БД» (UPD2, строка 158).
2. `services/media_download.fetch_media_to_tmp` (`:43-102`) знает root cause: **локальный Bot API возвращает относительный `file_path`**, `aiogram.download` читает его от cwd → `FileNotFoundError`; решение — чтение из `TELEGRAM_API_FILES_DIR/<bot_id>:<token>/<path>` с 3 ретраями и fallback `bot.download`.
3. `web/api/avatars.fetch_avatar_bytes` (`:120-160`) этого fallback **не имеет** → та же ошибка в другом сайте.
4. Рассинхрон ФС↔БД не диагностируется: нет счётчиков «в БД есть — на диске нет» / «на диске есть — в БД нет».
5. Инварианты: R17 (строка `<bot_id>:<token>` и абсолютные пути — никогда в логи), R16 (аддитивные поля API), каталог Δ=0, `media/` не трогать, порядок роутеров `bot.py`.

## Decision

### D1. Единый хелпер локального чтения — источник истины
Новый публичный helper в `services/media_download.py`:
`read_local_file_bytes(bot, file_id, *, attempts=3, sleep=1.0) -> bytes | None` и
`local_file_path(bot, file_path) -> Path | None` (traversal-guard, только относительные пути под корнем `TELEGRAM_API_FILES_DIR`).
`fetch_media_to_tmp` рефакторится на эти хелперы **без изменения поведения** (гейт `flags.download_enabled`, 3 попытки, fallback `bot.download`). Дублирование логики запрещено.

### D2. Аватары используют fallback
`fetch_avatar_bytes`: при локальном режиме и относительном `file_path` — `read_local_file_bytes`; при `None` — прежний `bot.download_file`. Классы исключений и политика кэша **не меняются** (транзиент `TelegramRetryAfter`/`TelegramNetworkError` → без негатива; `TelegramBadRequest` → дефинитивный негатив, debug; прочее → warning+traceback, R17-safe).

### D3. Диагностика рассинхрона ФС↔БД — аддитивно (honest-контракт, D-4)
Новый `services/media_integrity.py`:
`audit_media_files(db, bot=None, *, chat_id=None, sample_limit=200) -> dict` → `{db_media_rows, text_media_paths, files_on_disk, missing_on_disk, orphan_files, sample_missing: [хвосты имён], reliable: false, basis: 'text_scan'}`. **D-4 (ревью Батча E):** схема БД не хранит реальные `file_path` (Bot API транзиентен), поэтому `db_media_rows` — достоверный COUNT медиа-строк, а `text_media_paths`/missing/orphan — ЭВРИСТИКА по тексту сообщений; числа не выдаются за точный рассинхрон (`reliable=false`). **D-3:** обход диска (`rglob`, до 20000 файлов) вынесен в `asyncio.to_thread` — event loop не блокируется. **D-5:** эндпоинт TTL-кэшируется (120с). Наружу — аддитивный `GET /api/status/media-health` (R16): только числа и примеры хвостов `photos/file_*.jpg`; `<bot_id>:<token>` и абсолютные пути не отдаются/не логируются.

### D4. R17 — жёсткий контракт логирования
В логах/ответах API допустимы только: имя файла, `photos/…`-хвост, `file_id`, числовые счётчики, тип исключения. Абсолютный путь с `<bot_id>:<token>` — **никогда** (в т.ч. в `exc_info`/сообщениях OSError).

### D5. Восстановление — УБРАНО из публичного API (ревью Батча E)
Recommend: фаза 1 — диагностика (лог + API); фаза 2 — восстановление. **Факт:** `restore_missing_files` не имел call-site и реального маппинга path→file_id (Bot API `file_path` транзиентен) → фактически не восстанавливал файлы и отдавал бы вводящие в заблуждение числа. Функция удалена из публичного API; реализация перенесена в `backlog.md` (только при появлении персистентного маппинга медиа). Откат — `git revert`.

### D6. Кейс `525660918` — диагностируется, а не «глушится»
Причина устанавливается по коду исключения: отсутствие файла локально (покрывается D2) vs `TelegramBadRequest` (нет фото/приватность) → обоснованный негатив/404. Результат фиксируется в отчёте фичи.

## Consequences

**Positive**
- Аватары перестают «отлетать» из-за относительных путей локального Bot API; поведение выровнено с медиа-скачиванием.
- Дублирование логики устранено (один источник истины для локального чтения).
- Рассинхрон ФС↔БД становится измеримым; возможна осознанная процедура восстановления.
- Каталог-Δ=0, DDL нет, R16/R17 соблюдены.

**Negative**
- Добавляется чтение с диска в путь аватаров (небольшая задержка при первом обращении; кэш 1ч сохраняется).
- Фон-восстановление при неаккуратном запуске даёт нагрузку на Bot API/диск — ограничено limit/соном/fail-open.
- Источник строк БД для аудита зависит от фактической схемы — полнота выборки может быть ограничена (задокументировать).
- `media_integrity` — новый модуль (сопровождение), но чисто диагностический.

## Alternatives

- **A1. Продублировать локальное чтение внутри `avatars.py`.** Отклонено: дрейф от `media_download`, риск расхождения traversal-guard/ретраев.
- **A2. Всегда использовать `bot.download` (без локального чтения).** Отклонено: именно это и даёт `FileNotFoundError` в локальном режиме.
- **A3. Полностью перейти на облачный Bot API.** Отклонено: архитектурное решение проекта (локальный Bot API для лимитов/приватности), вне скоупа фичи.
- **A4. Агрессивное автовосстановление без limit.** Отклонено: риск нагрузки и «пинг-понга» файлов.
- **A5. Считать рассинхрон «нормой» и не диагностировать.** Отклонено требованием владельца.
- **A6. Отдельный фича-флаг восстановления.** Отклонено: превышает нужды; существующий `flags.download_enabled` достаточен.
