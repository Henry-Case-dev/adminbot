## 0. Цель

Починить «отлетающие» аватары: `web/api/avatars.py::fetch_avatar_bytes` качает файл напрямую (`bot.get_file → download_file`) и **не имеет локального fallback**, тогда как `services/media_download.py::fetch_media_to_tmp` умеет чинить относительный `photos/file_*.jpg` через `TELEGRAM_API_FILES_DIR/<bot_id:token>/<path>` с ретраями. Дать аватарам тот же fallback и диагностику рассинхрона файлового хранилища и БД.

**Требуется (UPD2 п.6, строка 158):**
- Аватары должны использовать **локальный fallback** как `media_download` (починка `photos/file_*.jpg` через `TELEGRAM_API_FILES_DIR`).
- **Диагностика** рассинхрона файлового хранилища и БД (файлы есть в БД, но отсутствуют на диске — и наоборот).
- Разобрать `fetch failed` для юзера **525660918**.

## 1. Доказательства / карта кода (HEAD `fd6acc7`)

- `web/api/avatars.py:120-160` — `fetch_avatar_bytes`: `bot.get_file(file_id)` → `bot.download_file(path, buf)`; **без** локального чтения с диска; исключения 4 категорий (транзиент → не кэшировать; BadRequest → негатив).
- `services/media_download.py:43-102` — `fetch_media_to_tmp`: при `flags.download_enabled` и **относительном** `file_path` читает `TELEGRAM_API_FILES_DIR/<bot_id:token>/<path>` (`local_files_subdir`), 3 ретрая по 1 с, при отсутствии — `bot.download`; R17 (не логирует `<bot_id>:<token>`).
- `services/media_download.py:30-40` — `local_files_subdir` (формирование `<bot_id>:<token>` — **не логировать**).
- `web/api/avatars.py:163-166` — `safe_exc_text` (безопасный текст исключения).
- `web/api/avatars.py:169+` — `_log_bot_api_failure` (политика WARNING/debug из раунда 10.17).
- Наблюдение чекапа: `photos/file_456.jpg`, `photos/file_457.jpg` — **файлов нет на диске** → `FileNotFoundError`/ошибка скачивания; аватары пользователей «отлетают».

## 2. Требования

- [ ] `fetch_avatar_bytes` использует **локальный fallback**: при относительном `file_path` и локальном режиме — чтение из `TELEGRAM_API_FILES_DIR/<bot_id:token>/<path>` (как `media_download`), с ретраями.
- [ ] При отсутствии локального файла — прежний `bot.download` (cloud) как фоллбэк; поведение «транзиент → не кэшировать» сохранено (BUG-4/10.17).
- [ ] Диагностика рассинхрона: обнаруживать и логировать/отдавать счётчики «в БД есть — на диске нет» (для медиа-путей); без утечки `<bot_id>:<token>` (R17).
- [ ] Разобрать `fetch failed` юзера 525660918: причина (тип/код ошибки, наличие фото) и фикс/объяснение.
- [ ] Не увеличивать нагрузку на Bot API/диск сверх разумного (ретраи ограничены).
- [ ] Общая логика локального fallback с `media_download` — **не дублировать** без нужды (рассмотреть общий хелпер; решает ADR).
