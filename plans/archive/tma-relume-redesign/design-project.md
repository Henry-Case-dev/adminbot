## 0. Резюме для владельца (TL;DR)

1. **Что делаем.** Мини-апп остаётся **одной страницей** `web/index.html` + `web/app.js`
   (Vue3 global, без сборки — OD3). Но навигация становится **как в эталоне**: сверху
   **navbar из 6 пунктов** (как на всех 15 страницах референса), внутри — **hub-страницы
   с карточками**, и **15 "экранов"**, между которыми ходим по **hash-ссылкам** (`#/ai/llm`).
2. **Ничего не теряем.** Все **17 текущих вкладок** (проверено по коду; в `tasks.md` было
   «18» — это ошибка счёта, см. §3.0) + все «фичи» (Oversight, ЛС/DM, BYOK, гейты/бюджет,
   per-chat override, отношения, дерево ролей, копирование логов, ~359 Settings) получают
   **новый дом** на одном из 15 экранов. Таблица «фича → новый экран» — §3.
3. **Красиво.** Палитра = **цвета эталона** (4 схемы: тил, тёмная, магента, пурпур), но
   оформленные как **переливающиеся (анимированные) градиенты** (OD4). Текст всегда лежит
   **на плотной подложке**, поэтому контраст WCAG AA держится в любом кадре анимации.
   При `prefers-reduced-motion` анимация **выключается**, остаётся статичный градиент.
4. **Иконки.** Material Symbols **Rounded** (как в эталоне), переменный шрифт, размеры и
   палитра заданы по элементам (§5). Если шрифт сейчас не подключить — временно **эмодзи**
   по приложенной карте, затем замена без изменения разметки.
5. **Главная техническая тонкость.** Telegram кладёт свои данные в `#tgWebAppData=…` —
   **в тот же hash**, где будет наша навигация. Если писать hash «в лоб», можно сломать
   авторизацию мини-аппа. Проект решает это: **initData читаем и кэшируем ДО любой записи
   hash**, наши маршруты начинаются с `#/` и не трогают `tgWebAppData` (§6).
6. **Порядок работ (OD2 — всё сразу).** Но внутри big-bang соблюдаем безопасный порядок:
   **токены → shell/navbar → hub-экраны → все 15 экранов → QA** (§7). Иначе каскадные регрессы.
7. **⚡ Scope-switcher (OD7 — САМЫЙ важный элемент).** «Чат-Профиль» становится
   **глобальным переключателем контекста** в шапке: **GLOBAL** (весь бот) · **конкретный
   ЧАТ** · **ЛС/DM**. Это **не 7-й пункт меню** (navbar остаётся 6 пунктов по OD6) — это
   **промитентная scope-bar** (аватар + имя + тип скоупа + dropdown). Список чатов приходит
   **уже отфильтрованным сервером** по членству админа (`/api/access/chats`, `chat_admins`);
   UI его не расширяет; «GLOBAL» видят только глобалы. Выбор скоупа определяет, **куда
   читаются/пишутся все настройки**. Спека — **§15.1**.
8. **Стоимость backend — точечная (не «≈0»).** 15 экранов живут на существующих
   эндпоинтах. Новые доработки нужны только по OD8/OD10/OD16: **B1** (динамич. провайдер/модель
   + код ответа + история доступности) и **B3** (role-scoped права на каждый параметр +
   **создание/правка ролей**), плюс **OD16** (UI-редактируемость провайдера/модели/адреса).
   **B2 — OUT.** Инварианты: **ноль новых PG-DDL, SQLite v8; итоговый каталог
   REGISTRY 387 / GROUPS 74 / Settings 359** (383 → +2 STT OD11 → 385 → +2 адреса OD16 → 387;
   см. §15.2/§15.3).
9. **Back-навигация — без своей кнопки.** Владелец верно заметил: у TMA уже есть нативные
   back/close в шапке. Мы **не рисуем свою стрелку**, а переиспользуем нативный слот через
   `Telegram.WebApp.BackButton` (на вложенных экранах ← заменяет ✕, на корне — скрыт). Так
   Android system-back не закрывает апп на глубине > 0 и нет двух конфликтующих «назад» (§6.4).
10. **Компактный список ключей + график (OD8/B1).** Вместо «раздутого» блока — плотный
    список всех ключей: **имя по модулю + динамически подтянутый провайдер/модель + код
    ответа (HTTP) + индикатор доступности**; мелкий шрифт, узкий line-height; ниже —
    **график доступности по времени + компактная легенда**. Хардкод `GROQ_TRANSCRIBE_MODEL`/
    `OPENROUTER_TRANSCRIBE_MODEL` в `llm_registry()` **убирается**. Спека — **§15.2**.
11. **Полная матрица ролей + управление ролями (OD10/B3).** Все параметры мини-аппа,
    сгруппированные **по тем же секциям**, что и мини-апп (источник `param_catalog.TAB_RULES`
    — каталог не меняется); по каждому — роли на **ЧТЕНИЕ** и на **ЗАПИСЬ**; **отдельно** —
    управление ролями, включая **создание новых**. Спека — **§15.3**.
12. **Иконки (OD5/D11→OD14).** Владелец **предоставил полный** файл
    `MaterialSymbolsRounded[FILL,GRAD,opsz,wght].woff2` (5.11 МиБ, корень проекта). **Инспекция
    T-1137 (выполнена):** файл **валиден**, оси точны, все **26/26** иконок есть, лицензия
    **Apache-2.0**; **но 5.11 МиБ нельзя отдавать в TMA напрямую** — обязателен субсет до
    **~5.5–13.2 КБ**, рендер по **PUA-коду** (не по тексту-лигатуре). Точная спека/замеры —
    **§15.4** + **§16.2**. Фолбэк emoji §5.4 сохраняется.
13. **Deep-link (D9) — ✅ OFF (OD13).** Отключён: `__TMA_DEEPLINK__=false`; задач реализации нет
    (§6.4.5, §15.5). Back-навигация (`__TMA_BACK__=true`) работает независимо.
14. **Хардкод моделей (OD11) — ✅ устранён.** Аудит **T-1136**: найдены и устранены все P0-хардкоды
    (STT-модели, base_url Groq/OpenRouter, видео-каскад); **безопасная миграция** сохраняет
    текущие значения; каталог **383→385** (§16.1). **Текущие значения не меняются.**
14a. **Адреса провайдеров — UI-редактируемы (OD16) — ✅ подтверждено владельцем.** `base_url`

### 1.2. Что такое эталон (кратко, по факту из `reference-analysis.md`/`spec.md`)

- **Статический мокап** Relume, 15 страниц на русском, с реальными текстами про нашего бота.
- **Не функциональное ТЗ:** во всех 15 `index.htm` — **0 `<input>`, 0 `<form>`, 0 `<select>`,
  0 `<table>`**. Кнопки/тумблеры/матрицы — это `<div>`-мокапы. Мы берём **структуру и вид**,

- **Навигация эталона:** плоский **fixed navbar из 6 пунктов** (лого слева, меню справа) +
  **hub-страницы** с сеткой карточек. Вложенных dropdown в navbar нет.
- **Дизайн-язык:** Inter (400/500/600), Material Symbols Rounded, типографика/радиусы/
  spacing/тени/motion — точные значения в `spec.md` §1.4.

### 1.3. Как эталон становится оболочкой (главная идея проекта)

```
┌─────────────────────────────────────────────────────────────────────┐
│  NAVBAR (6 пунктов, как в эталоне)   [лого]   [SCOPE ▾ аватар+имя]  │  ← sticky, ≥992px
│  #/  #/how  #/modules  #/ai  #/permsoc  #/access                    │
│  ── SCOPE-BAR (OD7): GLOBAL · ЧАТ · ЛС — определяет маршрут настроек ─│  ← всегда видна
├─────────────────────────────────────────────────────────────────────┤
│  HUB-экран (карточки разделов) — как hub-страницы эталона           │
│    ┌───────────┐ ┌───────────┐ ┌───────────┐                        │
│    │ icon H4   │ │ icon H4   │ │ icon H4   │  ← клик → hash-экран   │
│    │ subtitle  │ │ subtitle  │ │ subtitle  │                        │
│    └───────────┘ └───────────┘ └───────────┘                        │
├─────────────────────────────────────────────────────────────────────┤
│  ЭКРАН (одна из 15 страниц): PageHeader (tagline+H2+описание)        │
│  → SectionCard'ы / KPI-плитки / панель логов / таблица / конфиг-поля │
│  → весь контент лежит на ПЛОТНЫХ подложках (контраст над градиентом) │
└─────────────────────────────────────────────────────────────────────┘
```

- **Desktop (≥992px):** navbar сверху, контент по центру (как эталон).
- **Mobile (≤991px):** navbar сворачивается в **drawer** (боковое меню), как принято в TMA;
  breakpoints эталона `991px` / `479px` сохраняем.
- **Hub-экраны** появляются там, где эталон их и имеет: «Модули», «Настройки AI»,

### 2.4. Scope-switcher — краткая модель (полная спека — §15.1)

> **OD7:** «Чат-Профиль» = **глобальный переключатель контекста** (САМЫЙ важный элемент).
> Он определяет, **какой слой настроек** читается и пишется на **всех** экранах.

| Scope | Что это | `X-Chat-Id` | Кто видит | Что маршрутизирует |
|---|---|---|---|---|
| **GLOBAL** | «весь бот» | заголовок **не шлётся** | только `is_global_admin` | глобальные `bot_settings`; глобальные ключи/модели; Oversight |
| **ЧАТ** | конкретная группа | `chat_id < 0` | админ, имеющий грант (`chat_admins`) | `chat_params` overrides; per-chat гейты; Лор/Имена/Отношения |
| **ЛС/DM** | свой приватный чат с ботом | `user.id > 0` | любой авторизованный (`is_dm_owner`) | DM-профиль; `models.*` read-only; permsoc скрыт |

- Список пунктов = **ровно то, что вернул сервер** `GET /api/access/chats` (RBAC-фильтр
  по `chat_admins` + синтез DM-строки). UI **не добавляет** чаты и **не ослабляет** RBAC.
- Рядом с выбранным пунктом — **имя + аватар** (`GET /api/avatar/chat/{id}` либо
  `photo_file_id` из ответа; у DM — `user`).
- Смена скоупа **сбрасывает/перезагружает** всё chat-scoped состояние (обобщение
  R10.4-2, было только для `relations`): `chatRelations`, `chatLoreProfile`,
  `chatLoreSelectedId`, `configError`, кэши; затем — перезагрузка активного экрана.

> Без `@property` анимация градиента «дёргается» (discrete step).

### 4.4. Спецификация анимированного градиента (обязательные пункты T-1091)

**Где применяется (строго 4 поверхности, не больше):**
1. **navbar-band / hero-band** — фоновая полоса за navbar и заголовком экрана.
2. **Активная карточка / KPI-плитка** — подсветка текущего элемента (glow).
3. **Primary-кнопка** (например «Сохранить», control) — переливающийся fill.
4. **Фон-подсветка страницы** (page wash) — большая мягкая полоса за контентом.

**Техника (две, обе чистый CSS, без JS):**
- **T1 — typed angle spin** (для ограниченных поверхностей: band, button, active card):
  `background: conic-gradient(from var(--grad-angle), var(--grad-a), var(--grad-b), var(--grad-c), var(--grad-a));`
  `animation: grad-spin var(--grad-speed) linear infinite;` где
  `@keyframes grad-spin { to { --grad-angle: 495deg } }`.
- **T2 — background-position drift** (для большой page wash):
  `background: linear-gradient(120deg, var(--grad-a), var(--grad-b), var(--grad-c));`
  `background-size: 200% 200%; animation: grad-drift 24s var(--grad-ease) infinite alternate;`
- **Ограничение по краскам:** не более **3–4 цветов** в одном градиенте (иначе «мутнеет
  в коричневый» — Superdesign/Aurora research).
- **Ограничение площади:** анимируем только маленькие/ограждённые области; таблицы, формы,
  логи, длинные списки — **только на плотных подложках**. `contain: paint` на band.

**Производительность:**
- Градиентная анимация идёт по main thread (перекраска) → **держим область маленькой**,
  используем `transform`/`opacity` где можно, `filter: blur()` — только на маленьком
  hero-band (blur дорогой в WebView), не на весь экран.
- Не анимируем десятки элементов одновременно: 1–3 живых поверхности на экран.

**Доступность / контраст (обязательно):**
- `@media (prefers-reduced-motion: reduce)`:
  ```css
  @media (prefers-reduced-motion: reduce){
    .grad,.grad-band,.grad-btn,.page-wash{ animation:none !important; }
    :root{ --grad-angle:135deg; }              /* «безопасный» статичный кадр */
    .page-wash{ background:var(--surface-1); } /* без перелива */
  }
  ```
- `@media (prefers-contrast: more)` → тема `mono` (solid, без градиента).
- **Правило WCAG AA:** весь текст/иконки/бейджи — на `--surface-1/2/3` (плотный),
  контраст ≥ **4.5:1** (крупный ≥ **3:1**). Проверяем **худший кадр** градиента и
  **reduced-motion кадр**. Ориентиры (белый текст):
  `#F5F5F5` на `#161616` ≈ 16:1 ✅ · `#14CBB6` на `#161616` ≈ 9.9:1 ✅ ·
  `#FFFFFF` на `#664EA0` ≈ 6.3:1 ✅ · `#FFFFFF` на `#8D6BDC` ≈ 3.6:1 ⚠ (только крупный /
  через подложку) · `#16B364`/`#FF4848`/`#EAAA08` на `#161616` — 4.6–9:1 ✅.
- Если владелец захочет текст на градиенте — только `--surface-glass` (rgba+blur) под ним,
  с `backdrop-filter` fallback на непрозрачный `--surface-2`.

## 6. Навигация и роутинг (OD1 + OD3; hash-routing ОБЯЗАТЕЛЕН)

### 6.1. Почему hash и главный риск

При `OD1(B) + OD3(zero-build)` 15 «страниц» референса живут в **одном `index.html`**.
Разделяем их через `location.hash`. **Риск (критично):** Telegram передаёт launch-параметры
в **том же hash** (`#tgWebAppData=...&tgWebAppVersion=...`). Если записать `location.hash='#/ai'`
до чтения, `Telegram.WebApp.initData` может стать пустым → 401. Подтверждено research:
`docs.telegram-mini-apps.com/platform/launch-parameters` (параметры в hash; «если приложение
использует hash-routing, он может потерять исходный hash — сохраните данные при старте»),
и баг `vuejs/router#2155` (роутер ломает закодированный `tgWebAppData`).

### 6.2. Правила роутинга (обязательные)

1. **Стартовый порядок:** на DOMContentLoaded **сначала** читаем
   `initData = Telegram.WebApp.initData` и кладём в переменную + `sessionStorage`
   (`adminbot.initData`); **только потом** трогаем hash.
2. **Разбор hash:** маршрут = hash **только если он начинается с `#/`**; иначе (там
   `tgWebAppData=...`) маршрут = дефолт `#/`. `tgWebAppData` **никогда** не парсим повторно.
3. **Дефолт:** `#/` → `status`.
4. **Не перезаписываем launch-hash «в лоб»:** при первом старте, если hash не наш,
   используем `history.replaceState` для установки `#/` (не создаёт лишней истории).
5. **`hashchange` → `applyRoute(route)`**: **источник истины навигации — `route` (hash)**;
   `activeTab`/контент — **производные** (`routeToTab(route)`). `routeToTab` / `tabToRoute` /
   `routeParent` / `routeDepth` — чистые функции, покрыты тестом. Единственный «применитель»
   роута — обработчик `hashchange` (§6.4.4); `BackButton.onClick` лишь инициирует
   `navigateTo(parent)`, не применяя роут сам. Состояние датаскопа (активный чат, фильтры)
   **не** является частью роута и не сбрасывается при навигации.
6. **RBAC-гейт:** перед применением маршрута — `canViewTab(tabId)`; при отказе →
   редирект на `#/` + toast. UI **не ослабляет** серверные проверки.
7. **Смена чата не теряет экран:** `activeChatId` (localStorage) сохраняется; текущий
   hash остаётся; chat-scoped данные перезагружаются (R10.4-2).
8. **Refresh:** Telegram может заново вбросить launch-hash. Тогда: маршрут берём из
   `sessionStorage['adminbot.route']` (последний), иначе `#/`. Так экран не «слетает».

### 6.4. Back-навигация: нативные back/close TMA vs. `BackButton` (D8, research T-1119)

> **Ответ на замечание владельца.** Да, у Mini App **уже есть встроенные кнопки** в верхней
> шапке: по умолчанию — **закрыть (✕, Close)**. **Свою кнопку «назад» рисовать нельзя** — она
> конкурировала бы с нативной и с системным back на Android (два разных поведения «назад»,
> adsgram TMA-mistakes §4). Правильный путь: **не добавлять свой контрол**, а
> **переиспользовать нативный слот шапки** через `Telegram.WebApp.BackButton`. Когда
> `BackButton` показан, Telegram **сам заменяет ✕ на ←**; когда скрыт — возвращается ✕.
> Конфликта/дублирования нет по определению: это **один и тот же** слот шапки.

#### 6.4.1. Что даёт API (Bot API 6.1+, 20.06.2022)

`Telegram.WebApp.BackButton` (объект; `isVisible` по умолчанию `false`):

| Метод/поле | Назначение |
|---|---|
| `isVisible` | виден ли сейчас (bool) |
| `show()` | показать ← в шапке (**заменяет ✕**) |
| `hide()` | скрыть ← (возвращает ✕) |
| `onClick(cb)` | подписка на нажатие (алиас `onEvent('backButtonClicked')`) |
| `offClick(cb)` | снять подписку |

Событие нажатия: `backButtonClicked` (WebApp) = `back_button_pressed` (сырое web-событие),
**v6.1+**. Нажатие **не выполняет встроенного действия** — «назад» реализует приложение.

#### 6.4.2. Кто владеет состоянием (native header ↔ `BackButton` ↔ Android OS back)

| Слой | Кто владеет | Поведение |
|---|---|---|
| Нативная шапка (✕/←) | Telegram | ✕ по умолчанию; при `BackButton.show()` — ← |
| Android OS/hardware back | Telegram | при `is_visible=true` → эмитит `back_button_pressed`; при `false` → **закрывает** WebView |
| Наш «back»/history | **приложение** | `BackButton` **не хранит историю**; наш роут-стек — единственный владелец |

Официально (`core.telegram.org/api/web-events`): «on supported platforms, the OS back button
can be used instead of a custom back button: if `is_visible` is true pressing the OS back
button should emit a `back_button_pressed` event, otherwise the webview should be closed».
**Следствие:** чтобы Android-back шёл «на шаг назад», а не закрывал апп, `BackButton`
**обязан** быть видимым на вложенных экранах. На корне его прячем — там закрытие и есть
правильное «назад».

**Escape hatch сохранён:** Telegram специально оставляет **свайп вниз** для закрытия, даже
когда ✕ заменён на ← (docs `/platform/sticky-app`). Мы **не вызываем**
`disableVerticalSwipes()` (v7.7) — пользователь не окажется заперт в аппе.

#### 6.4.3. Правило видимости (depth)

- **depth 0** = 6 пунктов navbar и корневой `#/` → **`BackButton.hide()`** (нативный ✕;
  OS-back закрывает — корректно для верхнего уровня).
- **depth 1** = вложенные экраны (`#/oversight`, `#/modules/*`, `#/ai/*`, `#/access/*`) →
  **`BackButton.show()`**.

`routeDepth(route)` и `routeParent(route)` — **чистые функции** (покрываются тестом):

| Route | parent | depth |
|---|---|---|
| `#/`, `#/how`, `#/modules`, `#/permsoc`, `#/ai`, `#/access` | — | 0 |
| `#/oversight` | `#/` | 1 |
| `#/modules/switches`, `#/modules/reactions`, `#/modules/custom` | `#/modules` | 1 |
| `#/ai/llm` … `#/ai/lore` | `#/ai` | 1 |
| `#/access/roles`, `#/access/local`, `#/access/admins` | `#/access` | 1 |

#### 6.4.4. Конечный автомат (рекомендуемая интеграция)

**Единственный источник истины навигации — `route` (нормализованный hash).** `activeTab` и
контент — **производные** от `route` (это уточняет §6.2 п.5: hash **авторитетен** для
навигации; состояние датаскопа — активный чат/фильтры — остаётся отдельным и не сбрасывается).

| # | Событие | Действие |
|---|---|---|
| 1 | **BOOT** | прочитать `Telegram.WebApp.initData` (сырую строку) → кэш в память/`sessionStorage`; **только потом** трогать hash (§6.1) |
| 2 | **BOOT** | прочитать `start_param` (не из hash! — §6.4.5) → если `__TMA_DEEPLINK__` → `route = mapStartParam(p)`, иначе `#/` |
| 3 | **BOOT** | `history.replaceState(null,'','#/…')` — стартовый роут **без** лишнего history-entry |
| 4 | **route change** | `applyRoute(route)`: normalize → **дедуп** (равен текущему → no-op, ничего не пушим) → `canViewTab` (RBAC): отказ → `replaceState('#/')` + toast; иначе отрисовать, сохранить в `sessionStorage`, вызвать `syncBackButton()` |
| 5 | **hashchange** | единственный «применитель» роута → `applyRoute(hash)`; если hash не `#/…` (launch-хэш `tgWebAppData`) → `applyRoute(sessionStorage route ?? '#/')` |
| 6 | **BackButton.onClick** | `goBack()` — обработчик регистрируется **ровно один раз** на BOOT, никогда не перерегистрируется |
| 7 | **syncBackButton()** | **единственное** место смены видимости: `(toggle ON && depth>0) ? show() : hide()`; вызывать только при фактической смене `isVisible` |
| 8 | **OS/Android back** | при visible → приходит как `backButtonClicked` → `goBack()`; при hidden (root) → закрывает апп (нативно) |

`goBack()`: `p = routeParent(route)`; если `p` → `navigateTo(p)`; иначе — **no-op** (кнопка и
так скрыта на depth 0).

`navigateTo(r)`: если `r === route` → **no-op**; иначе `location.hash = r` (ровно **один**
history-entry) → `hashchange` → `applyRoute`.

**Чего НЕ делать (защита от петель/двойной обработки):**
- ❌ `history.back()` как основную реализацию «назад» (на deep-link входе у истории 1 запись →
  «мёртвая» кнопка или выход из аппа; прецедент BEDOLAGA-DEV). Вместо этого —
  **детерминированный parent** из `routeParent`.
- ❌ отдельный `popstate`-обработчик рядом с `hashchange` (двойное применение роута).
- ❌ перерегистрировать `onClick` на каждой смене роута (накопление stale-колбэков).
- ❌ писать `location.hash` внутри самого `hashchange` (кроме RBAC-редиректа через
  `replaceState` — он не создаёт петель).
- ❌ пушить запись при переходе на **тот же** роут (иначе «надо жать назад много раз без
  видимого эффекта» — tma.js issue #303).

#### 6.4.5. Deep-link, `start_param` и сохранность launch-параметров

> **✅ OD13 (deep-link OFF) — РЕШЕНО ВЛАДЕЛЬЦЕМ (10.09.2026).** `window.__TMA_DEEPLINK__ = false`.
> Открытие по `start_param` **не внедряется**; задач реализации нет. Ниже сохранён полный
> дизайн-разбор (для истории и на случай будущего включения). **Back-навигация независима** и
> работает (`__TMA_BACK__ = true`). `start_param` всё равно читаем как launch-параметр, но в
> маршрутизацию не вовлекаем.

- **`initData` в hash:** Telegram кладёт `tgWebAppData=…` в `location.hash`. Читаем **сырую**
  строку `Telegram.WebApp.initData` **до** любой записи hash; кэшируем
  (`sessionStorage['adminbot.initData']` — для refresh-устойчивости; **не логировать**, R17);
  не пересобираем и не парсим `tgWebAppData` повторно.
- **`start_param` — НЕ в hash:** docs `/platform/start-parameter` — `tgWebAppStartParam` лежит
  в **query-параметрах** URL (не в hash) и дублируется в `initData.start_param`. Источник
  чтения — `initDataUnsafe.start_param` (или разбор сырой `initData`); **не** из hash.
- **Маппинг (НЕ активен при `__TMA_DEEPLINK__=false`)** — whitelist:
  `{ 'ai':'#/ai', 'ai-llm':'#/ai/llm', 'ai-prompts':'#/ai/prompts',
  'access-roles':'#/access/roles', … }`; неизвестное значение → `#/`.
- **Тумблеры (финал):** два независимых:
  `window.__TMA_BACK__` (показ ← по depth; **решено владельцем = `true`**) и
  `window.__TMA_DEEPLINK__` (**решено владельцем = `false` (OFF), OD13**; код-путь остаётся
  выключенным, но сохранён для будущего). При `__TMA_BACK__=false` — `hide()` всегда.
- **Refresh:** Telegram может заново вбросить launch-hash → роут восстанавливаем из
  `sessionStorage['adminbot.route']`, иначе `#/` (экран не «слетает»).

#### 6.4.6. Платформенные оговорки и версии

| Платформа | Нативная шапка | System back | Замечания |
|---|---|---|---|
| **iOS** | `show()` → ← вместо ✕ | нет аппаратной; свайп-вниз закрывает | `backButtonClicked` приходит стабильно |
| **Android** | `show()` → ← вместо ✕ | **hardware/OS back → `back_button_pressed` только при `is_visible=true`**, иначе закрывает WebView | **ключевой кейс**, ради которого и нужен `BackButton` |
| **Desktop** (tdesktop/web/webk) | ← в шапке | нет | событие идёт через `TelegramGameProxy`/`WebView.receiveEvent`; `onClick` абстрагирует |
| **Обычный браузер** | `BackButton` может отсутствовать | браузерная история | hashchange/прямые URL работают; всё под guard-ами |

- **Bot API:** `BackButton`/`onClick`/`offClick`/`show`/`hide`/`backButtonClicked` — **6.1+**.
  Guard: `window.Telegram?.WebApp` + `isVersionAtLeast?.('6.1')`.
- **Fallback (если 6.1 нет / вне TMA):** небольшая **in-app** стрелка «назад» в шапке
  navbar **только при depth>0** (документированный фолбэк, adsgram). Она появляется **лишь**
  когда нативной нет → дублирования нет. Label `Назад`/`Back` для a11y.
- **Bot API 10.2 (14.07.2026):** методы Mini App запрещены с чужих origin (iframe/партнёрский
  домен) → все вызовы `Telegram.WebApp` держим **на своём origin** (важно для CSP/шрифтов, §5).
- **Не вызывать** `disableVerticalSwipes()` (v7.7) — сохраняем escape hatch свайпа вниз.

### 11.1. D6 — простыми словами (для решения владельца)

> **⛔ SUPERSEDED (10.09.2026, OD7).** Владелец решил: «Чат-Профиль» **не сворачивается** —
> это **глобальный scope-switcher** (§15.1). Текст ниже оставлен **только как история**
> разъяснения варианта «свернуть». **Не реализовывать рекомендацию «B — свернуть».**

**Вопрос.** Что делать с разделом «Чат-Профиль»: оставить ему **отдельный пункт в верхнем
меню** или **убрать пункт** и положить три его экрана («Имена», «Участники и отношения»,
«Лор чата») **карточками внутрь «Настройки AI»** (как в эталоне Relume)?

**Что это значит на практике.**

| | Вариант A — отдельная секция | Вариант B — свернуть в «Настройки AI» **(рекомендация)** |
|---|---|---|
| Верхнее меню | **7 пунктов**: Статус · Как это работает · Модули · Настройки AI · Функции PERMsoc · **Чат-Профиль** · Доступы и Роли | **6 пунктов** — ровно как в эталоне |
| Где Имена/Отношения/Лор | внутри своей секции navbar | **3 карточки** на hub-экране «Настройки AI» |
| Кликов до экрана | меню → экран (**1 клик**) | Настройки AI → карточка (**2 клика**) |
| Соответствие эталону (OD6) | расходится (+1 пункт) | **полностью совпадает** |
| Что меняется в коде | `MENU_ORDER` + добавляем `chat_profile` второй раз; `MENU_LABELS`; маркер-тесты навигации | `MENU_ORDER` теряет секцию `chat_profile`; `MENU_LABELS`; маркер-тесты (меньше правок) |

**Что пользователь увидит:**
- **A:** в шапке появится лишний пункт «Чат-Профиль»; зайдя в него — три экрана.
- **B:** лишнего пункта нет; в «Настройках AI» появится блок карточек «Имена», «Участники и
  отношения», «Лор чата»; маршруты `#/ai/names`, `#/ai/relations`, `#/ai/lore` сохраняются.

**Последствия, если выбрать B:** ничего не теряется (все 3 вкладки живы, просто на клик
глубже); меню чище и совпадает с эталоном; меньше правок тестов. **Минус:** «чат-специфичные»
экраны визуально спрятаны в AI — компенсируется понятными карточками (при желании — командной
палитрой, §10 A8). Доступность (кто что видит) **не меняется** ни в одном варианте.

**Рекомендация @Architect: B (свернуть).** Причина — OD6 «структура = эталон», меньше пунктов
меню лучше читается, и это самый «дешёвый» путь по регрессам. Если владелец считает эти экраны
частотными — компромисс: оставить ярлык-ссылку в мобильном drawer, но не в основном navbar.

### 11.2. D7 — простыми словами: B1/B2/B3 (для решения владельца)

> **⛔ SUPERSEDED (10.09.2026, OD8/OD9/OD10).** Владелец решил: **B1 — В СКОУПЕ** (§15.2),
> **B2 — OUT** (read-only сохраняется), **B3 — В СКОУПЕ и расширен** (§15.3). Текст ниже
> (в т.ч. рекомендации «B1/B2 отложить») оставлен **только как история**. **Не реализовывать
> старые рекомендации.**

**Общее:** это **три необязательные backend-доработки**. Редизайн **не зависит** ни от одной из
них — все экраны можно собрать на существующих эндпоинтах. Ниже — что это, зачем, что будет
при отказе, цена/риск.

**B1 — история доступности ключей API.**
- *Что это:* сейчас на «Статусе» видно **текущее** состояние ключей (работает/нет). B1 —
  сохранять результаты проверок **во времени** и рисовать **график** «когда ключи падали».
- *Зачем:* замечать деградацию провайдера и связывать её со сбоями. В эталоне такой график
  есть, но это **статичный мокап**.
- *Если отложить:* на экране остаётся текущий статус + плейсхолдер. Истории не будет, но
  функциональность бота **не страдает**.
- *Цена/риск:* **высокая** — новый фоновый сэмплер + хранение временного ряда (новая
  таблица/DDL, что противоречит инварианту «ноль новых PG-DDL») + эндпоинт. Риск роста БД и
  фоновой нагрузки.
- *Рекомендация:* **отложить.** Дёшевая версия «на потом»: писать статус в уже существующий
  журнал/`log_ring` без графика; полноценный график — отдельным раундом.

**B2 — CRUD кастомных модулей.**
- *Что это:* сейчас «Кастомные модули» — **только просмотр** (включён / бюджет / триггеры).
  B2 — разрешить **создавать/редактировать/удалять** свои модули из админки.
- *Зачем:* расширять бота без правки кода.
- *Если отложить:* экран остаётся read-only карточкой; текущие 12 модулей и их настройки
  **не теряются**.
- *Цена/риск:* **высокая** — новая сущность в БД (DDL), эндпоинты, валидация, RBAC, аудит,
  UI-форма; риск безопасности (кто и какие модули может создавать) и роста скоупа.
- *Рекомендация:* **отложить** (в эталоне — статичный мокап).

**B3 — read-only «Матрица ролей» для не-глобальных админов.**
- *Что это:* сейчас полную матрицу ролей видит **только глобальный админ**. B3 — показать
  локальным/чатовым админам матрицу **только для чтения** (без редактирования), обычно лишь
  для своей роли.
- *Зачем:* человек понимает, какие у него есть права; меньше вопросов «почему нет доступа».
- *Если отложить:* не-глобалы продолжат видеть карточку «Мой доступ» (она **уже есть**).
- *Цена/риск:* **низкая–средняя** — либо role-scoped ответ существующего
  `GET /api/roles/tree`, либо лёгкий read-only эндпоинт + `readonly`-режим существующей
  матрицы. Риск: не показать лишние данные (фильтр по «своей» роли).
- *Рекомендация:* **опционально.** Если делать — строго read-only и только «своя» роль.

**Итог по D7:** **B1/B2 — отложить; B3 — по желанию владельца.** Ни один пункт не блокирует
редизайн и hard-gate.

### 15.1. T-1123 — Chat/Scope context switcher (OD7, «Чат-Профиль»)

> **Решение владельца (OD7):** «Чат-Профиль» — **САМЫЙ важный элемент**: глобальный
> переключатель контекста/скоупа **GLOBAL ↔ конкретный ЧАТ ↔ ЛС(DM)**, управляющий
> маршрутизацией всех настроек. Промитентный dropdown; список чатов **отфильтрован RBAC**;
> показ **имени и аватара** выбранного. **НЕ** сворачивается в AI-hub.

#### 15.1.1. Модель скоупа (три режима)

| Scope | Условие доступности | `X-Chat-Id` | Что читается/пишется |
|---|---|---|---|
| `global` | `is_global_admin == true` | заголовок **не отправляется** | `bot_settings` (глобальные); ключи/модели; Oversight |
| `chat` | сервер вернул чат в `/api/access/chats` (грант `chat_admins` или глобал) | `chat_id < 0` | `chat_params` overrides; per-chat гейты; Лор/Имена/Отношения |
| `dm` | `is_dm_owner` (свой ЛС: `chat_id == telegram_id`, `chat_id > 0`) | `user.id > 0` | DM-профиль; `models.*` read-only; `keys.*` скрыты (кроме BYOK); permsoc скрыт |

- Инвариант: DM идентифицируется **только** как `chat_id == telegram_id` (канон
  `services/chat_params.is_dm_scope`, `global_map.md` Round 10.3). Отрицательные `chat_id`
  групп с DM не пересекаются.
- Значение скоупа хранится в `activeChatId` (как сейчас: `null` = GLOBAL; число = ЧАТ/ЛС) +
  явный `scopeKind: 'global'|'chat'|'dm'` для UI; persisted в `localStorage`.

#### 15.1.2. Размещение — reconcile с OD6 (6 navbar-пунктов)

- **Navbar остаётся ровно 6 пунктов** (OD6). Scope-switcher — **не nav-пункт**.
- **Desktop (≥992px):** scope-контрол в правом кластере navbar, слева от юзер-чипа:
  `[ avatar | Имя чата · БЕЙДЖ(GLOBAL/ЧАТ/ЛС) | ▾ ]`. Высота/паддинги под navbar
  (`--navbar-height`), акцентная подсветка `--teal-500`.
- **Mobile (≤991px):** navbar сворачивается в drawer; scope-контрол выносится в **отдельную
  полосу (scope-bar)** прямо под navbar, **на всю ширину**, всегда видимую (не прячем в drawer —
  это ключевой элемент).
- **Промитентность:** scope-bar закреплён (`position: sticky`) и **не скроллится вместе с
  контентом**; визуально выделен (band-градиент §4.4 как фон-подсветка, текст — на плотной
  подложке).
- Прежний одиночный `<select>` (`web/index.html:424-435`) и бейдж `#id`/`ЛС #id` **заменяются**
  этим контролом (та же data-связка, новый UX).

#### 15.1.3. Селектор UX

- Кастомный **listbox** (`ScopeSwitcher`, Vue) — не нативный `<select>`, т.к. нужны аватары
  внутри опций. A11y: `role="listbox"`/`role="option"`, `aria-expanded`, фокус-менеджмент,
  `Esc` закрывает, стрелки перемещают. Reuse токенов/паттерна `Modal` (z-index 50).
- Секции панели (сверху вниз):
  1. **«Весь бот»** (scope=GLOBAL) — только если `is_global_admin`.
  2. **«Чаты»** — список из `/api/access/chats` (кроме DM-строки), каждый: аватар + title +
     бейдж доступа (`global_admin`/`local_admin`/`moderator`/`custom`), пометка `is_active`.
  3. **«Личные сообщения»** (scope=DM) — строка `is_dm:true` (avatar `user/{self.id}`).
- Поиск-фильтр появляется при >8 чатов (клиентский, по title).
- Текущий выбор подсвечен (`aria-selected`), вверху панели — тот же чип имя+аватар.

#### 15.1.4. RBAC-фильтрация списка чатов

- **Единственный источник** списка — `GET /api/access/chats` (`web/api/access.py:192-238`).
  Он уже фильтрует по `chat_admins` (`CHATS_FOR_USER_SQL`, строки 46-53) + синтезирует DM-строку;
  неглобальный пользователь видит **только** чаты со своим грантом (`_CHAT_ROLE_DOMAIN`).
- UI **обязан**: (a) рендерить **ровно** ответ сервера; (b) не добавлять пункт GLOBAL, если
  `is_global_admin != true` (`GET /api/access/me`); (c) при `403/404` от любого эндпоинта —
  не показывать данные и откатывать выбор.
- Серверные гейты (`can_access_chat`, `access_for`, DM-ветки) — **источник истины**; UI их
  **не дублирует как единственную защиту** и **не ослабляет**. «Случайный» пользователь не
  увидит запрещённый чат и не сможет сменить в нём параметры (POST вернёт 403/422).
- Кэш: `accessChats` обновлять при boot, после `access/me` и инвалидировать по смене
  глобальной роли (редко). Не кэшировать «навсегда».

#### 15.1.5. Имя + аватар выбранного

- `title` — из `/api/access/chats` (`chat_display_info`; fallback `Чат {id}`).
- Аватар: если у чата есть `photo_file_id` — можно тянуть `GET /api/avatar/chat/{id}`
  (существующий прокси, `web/api/avatars.py`; кэш 1ч). DM — `GET /api/avatar/user/{self.id}`.
- Fallback аватара (нет фото/404): кружок с первой буквой title (инициал), фон `--surface-3`.
- Аватар — **ленивый** (как relations, R10.4-4): `loading="lazy"`/`IntersectionObserver`,
  `onerror` → инициал (не долбить API).

#### 15.1.6. Scope-aware routing (что где доступно)

| Экран/зона | GLOBAL | ЧАТ | ЛС |
|---|---|---|---|
| `#/` Статус, key-availability | ✔ | ✔ | ✔ |
| `#/oversight` (global-only) | ✔ (только global admin) | ✖ | ✖ |
| `#/modules/*`, `#/permsoc` | чтение/справка | ✔ (per-chat) | ✖ permsoc скрыт |
| `#/ai/*` config | ✔ | ✔ (overrides) | ✔ кроме `keys.*` (read-only `models.*`) |
| `#/ai/names`, `#/ai/relations`, `#/ai/lore` | ✖ (нет чата) → подсказка «выберите чат» | ✔ | relations/lore → заглушка/404; names — по правилам |
| `#/access/*` | ✔ (global admin) | ✔ (свой чат) | «мои права» |

- Переход в GLOBAL из чат-скоупа и обратно **не теряет роут**: активный hash сохраняется,

### 15.5. T-1122 — Deep-link простыми словами (D9) — ✅ РЕШЕНО: OFF (OD13)

> **✅ ОБНОВЛЕНО v4 (OD13):** владелец **ВЫКЛЮЧИЛ** deep-link. `window.__TMA_DEEPLINK__ = false`;
> открытие экрана по `start_param` **не внедряется**; задач реализации нет. Разбор ниже сохранён
> как история (и на случай будущего включения). Back-навигация независима (`__TMA_BACK__=true`).

> **Что это такое.** У Telegram Mini App есть «стартовый параметр» — короткая метка, которую
> можно передать при открытии (например, ссылкой `t.me/PERMsoc_bot/app?startapp=ai-llm`).
> **Deep-link** — это возможность бота **сразу открыть нужный экран** по этой метке
> (например, `ai-llm` → сразу экран «LLM Провайдеры»), а не всегда стартовый «Статус».
> Механически: параметр лежит **не в hash**, а в query (`tgWebAppStartParam`) и дублируется в
> `initData.start_param`; читать надо из `initData`, по заранее заданному белому списку.

**Что увидит пользователь:**
- **Deep-link ВЫКЛ (рекомендуемый дефолт):** любое открытие мини-аппа начинается с `#/`
  (Статус). Ссылка `?startapp=...` игнорируется. Проще, безопаснее, предсказуемо.
- **Deep-link ВКЛ:** открытие по `?startapp=ai-llm` сразу показывает «LLM Провайдеры»;
  обычное открытие — по-прежнему Статус. Неизвестная метка → игнор → Статус.

**Плюсы ВКЛ:** удобные «прямые ссылки» из чата/документации; экономия кликов.
**Минусы/риски ВКЛ:** (а) метка — это «вход в середину» приложения — нужно правильно
выставить «назад» (родителем считать hub), иначе кнопка «назад» ведёт «в никуда»
(мы это решаем: `routeParent`, §6.4.4); (б) лишний параметр в авторизационном hash при
перезагрузке — нужно бережно читать `initData` **до** записи hash (уже заложено, §6.1);
(в) нужен строгий белый список маршрутов (никаких «произвольных» экранов) и RBAC-гейт
после перехода; (г) при `refresh` Telegram может заново вбросить параметры — маршрут
восстанавливаем из `sessionStorage` (уже заложено, §6.4.5).

**Рекомендация @Architect:** сделать **отдельный независимый тумблер** `window.__TMA_DEEPLINK__`
с дефолтом **`false`**. Back-навигация (`__TMA_BACK__ = true`) уже работает независимо.
Включать имеет смысл только если владелец реально будет рассылать ссылки на конкретные экраны.

**Как это выглядит:** «Deep-link: выкл» по умолчанию; включение — одна константа; никаких
других изменений в UI. **РЕШЕНИЕ ВЛАДЕЛЬЦА (OD13): ВЫКЛЮЧЕНО. ✅**
