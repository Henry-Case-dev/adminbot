## 3. Q2 — Селектор чатов

- **Источник**: `GET /api/access/chats` (F-7 §6) — первичный; фолбэк `GET /api/chat_lore/chats` (существующий; если part-1 ещё не выкатан — UI работает по старому).
- **Поля селектора**: `chat_id`, `title` (title берётся из ответа доступов; иначе из `chat_lore`-списка; иначе «Чат -100…»), активный — localStorage `adminbot.active_chat_id`.
- **Правила:**
  1. Пользователь с глобальным доступом к >1 чату (global admin) → селектор виден, значения: «Весь бот» (глобальный режим, NULL) + каждый чат; дефолт при загрузке — «Весь бот» (старое поведение).
  2. global admin с 1 чатом/0 чатов → селектор **скрыт**, режим «Весь бот».
  3. Локальный админ/mod-грант (список непустой) → селектор виден, дефолт — первый доступный; «Весь бот» недоступен (у них нет глобального режима).
  4. user (нет чатов) → селектор скрыт, режим глобальный (только status/info — старое поведение).
  5. Сохранённый `active_chat_id` не в списке → сброс к правилу 1/3, `localStorage.removeItem`.
- **Применение**: при выборе чата `api()` автоматически добавляет `X-Chat-Id` (F-7); при «Весь бот» — заголовок отсутствует. Конфиг-вкладки/«Чат-Профиль» перерисовываются (`activeChatChanged`-событие).
- Индикатор активного скоупа в шапке: чип-бейдж «Весь бот» / название чата + мелкий chat_id (прецедент T-873).

## 4. Q3 — Прогрессивное раскрытие

### 4.1 Разметка `progressive_level`

- `ParamSpec.progressive_level: str = ""` (пусто = basic).
- **Правило по умолчанию** (функция `resolve_progressive_level(spec)` в `param_catalog.py`): `advanced`, если:
  - `spec.group` ∈ {`limits_memory`, `limits_graph`, `flags_memory`, `memory_infinite`} (память/RAG-группы), ИЛИ
  - ключ (`ship пустое — это техgroup` читаем по pg_key) содержит одно из: `search_top_k`, `vector`, `graph`, `rag`, `retr`, `timeout`, `context`, `summary_length`, `budget`, `dedup`, `ttl`, `window`, `density`, `chunk`.
  Для остальных — `basic`.
- Для конкретных ключей, где правило неоднозначно (например `prompts.*`), разметка **явно** в REGISTRY (`progressive_level='basic'`).
- Потребители: `GET /api/config` (F-7 `params-meta` — включить `progressive_level` в состав) + фронт-рендер.

### 4.2 Рендер (config-вкладки: llm_providers, prompts, limits, memory_rag, reactions_triggers)

- generic-рендер групп (index.html :320-440 по 84.24) получает `item.progressive_level`; группы делятся: «Базовые» рендерятся как сейчас; «Расширенные» — аккордеон `<details class="advanced">` (первый `<summary>` — «Расширенные настройки»), по умолчанию `closed` (без `open`).
- Расширенные **не рендерятся вообще**, если параметр отфильтрован по min-ролям (F-7: `hidden_from_local`/ключи) — удаление до раскрытия, НЕ схлопывание.
- Состояние раскрытия per tab в localStorage: `adminbot.expand:<tab_id>` = `'1'` (другие значения — closed); меняется по клику на `<summary>` (без реактивных событий — нативное поведение).

### 4.3 Видимость для ролей

- **User (read-only)**: ТОЛЬКО «Главная/Статус» и «Как это работает» (`canViewTab` → false для остальных; меню-секции кроме home — скрыты).
- **Local admin/moderator**: видят свои секции (по F-7 `can_view_param`+секциям); расширенный блок доступен (его содержимое всё равно фильтруется по min-ролям).
- **Global admin**: всё.

## 10. Ре-дизайн 10.2 (09.09.2026, @Architect) — BUG-5: пустые блоки «(0)»

**Жалоба владельца (рекон раунда 10):** расширенные подсекции, в которых нет
параметров, не должны рендериться (сейчас `<details class="advanced">` с
`(<N>)` и пустая сетка «Базовых» рендерятся всегда, включая `(0)`).

**Решение — правило рендера ПО ГРУППЕ (generic-конфиг-витрины, index.html :455-627):**

| Условие | Рендер |
|---|---|
| `basicItems(grp).length > 0` И `advancedItems(grp).length > 0` | блок «Базовые» (существующая сетка) + `<details class="advanced">` с счётчиком |
| `basicItems(grp).length > 0`, advanced == 0 | только «Базовые»; **`<details>` не рендерится вовсе, никакого «(0)»** |
| `basicItems(grp).length == 0`, advanced > 0 | `<details class="advanced">` рендерится СРАЗУ РАСКРЫТЫМ (`:open="true"`) — иначе «Базовых» нет и блок выглядит как пустая вкладка |
| **оба == 0** | **вся карточка группы НЕ рендерится** (заголовок+описание+тело — всё) |

Реализация (рекомендация): фильтр в `app.js groupedForTab()` — финальный
`result` отбрасывает группы с `basicItems(grp).length === 0 && advancedItems(grp).length === 0`
(или v-if-гвард на карточке с теми же условиями — что удобнее; маркеры-строки
в шаблоне остаются). Тогда тройные состояния:
- `currentTabGroups.length === 0` → существующие пустые состояния («вкладка
  пустая» / «ничего не найдено», index.html :449-454) — без изменений;
- часть групп пуста → они просто пропадают (искомое поведение владельца);
- группа непустая по basic, но вся advanced-часть отфильтрована правами
  (`can_view_param`/`hidden_from_local` — сервер отдаёт только видимые ключи,
  F-7 §3) → `<details>` не рендерится.

**Безопасность от «намеренно пустых групп»:** витрины собираются ТОЛЬКО из
REGISTRY (`configGroups`/`configItems`), группа с 0 параметров в каталог не
попадает — пустая группа = все её параметры отфильтрованы правами/поиском →
скрывать безопасно (в проде «намеренно пустых» категорийных групп нет).

**Тот же правило — для per-chat override UI:** пер-чат-редактирование идёт
ЧЕРЕЗ ТОТ ЖЕ generic-рендер (бейджи `чат`/`скрыт`, `↪ глобальное`, роль-пикер —
F-7 §7) — правило применяется автоматически. Другие пустые-состояния
(«Модули и Фичи»/Oversight/access-карточки) — карточная структура, НЕ группания
(только states «нет данных» существует — без (0) — не трогаем). Роль-пикер и
перм-модалка — категории не подсекции.

**Маркеры тестов:** `test_frontend_tab_mapping.py` ищет `<details class="advanced"` —
строка остаётся в шаблоне (v-if/v-for-условия — литерал в index.html сохраняется;
в runtime `<details>` появляется только при advancedItems>0 — это допустимо:
как минимум одна группа конфиг-вкладки обычно имеет advanced; для вкладки
`permsoc` (Ре-дизайн 10.2 BUG-3) группы `limits_persons`/`reactions_persons`
непродвинутые — но маркер ищется по исходнику, не по рендеру).
