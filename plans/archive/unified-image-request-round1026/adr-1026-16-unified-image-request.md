## Контекст

§18 фиксирует **два способа** генерации: прямая ключевая фраза («Бот, нарисуй …») и вызов инструмента из LLM при свободной форме; требует **единый механизм подготовки и генерации**, запрещает **два независимых image pipeline** и требует сохранить прямой вызов без регрессий.

§19 фиксирует, что прямой вызов сейчас передаёт генератору только текст после «Бот, нарисуй»; поведение нужно **расширить**, не ломая простые запросы («Бот, нарисуй красного кота» — без обязательного RAG/досье), но «память не использовать в каждом запросе ради факта её существования» (пример «Лёху в образе самурая» — контекст может понадобиться).

§20 требует **единое внутреннее представление** запроса (пример полей: `source`, `chat_id`, `requester_id`, `original_message_id`, `user_request`, `resolved_subjects`, `context_required`, `context_sources`, `final_prompt`, `generator_config`; имена — на выбор), чтобы оба способа шли в **один pipeline**, и запрещает **двойную генерацию**, когда запрос сработал и по ключевой фразе, и через tool calling.

§21 требует **исследовать, почему текущие tool-вызовы не работают**, проверить описание инструмента (6 пунктов понимания модели: когда вызывать / обязательные аргументы / как формировать описание / что при отсутствии контекста / как интерпретировать результат / как сообщать об ошибке), не заставлять модель формировать HTTP-запросы, передавать **структурированные аргументы**, на бэкенде **валидировать и вызывать существующий генератор**, корректно возвращать результат в цикл и **не заменять реальную ошибку генератора вымышленным отказом модели**.

**Фактическое состояние baseline (A0 EVIDENCE + карта Step 0).** Оба входа **уже** сходятся в один генератор `image_generation.generate_and_send` (`:936`); прямой пре-гейт (`direct_chat_service.py:874–883` → `_image_pre_gate_block:1574` → `maybe_handle_keyword:968`) и tool-путь (`tool_router._generate_image:1553`) отличаются лишь **подготовкой** запроса (`extract_prompt` vs model `prompt`) и наличием/отсутствием общего представления. При срабатывании пре-гейта tool-путь **детерминированно выключен** на ход (`image_enabled=False:934–939` → `active_tools` исключает `generate_image`) + `<image_result>`-guard (`:988–991`). **GAP §20:** единого `ImageRequest` нет; **GAP §18:** подготовка запроса расходится; **GAP §20/идемпотентность:** двойная генерация защищена только «выключением инструмента», без авторитетного серверного маркера; **GAP §21:** причина неработоспособности tool-вызовов **не доказана** (A0: доказаны code-path механизмы — пре-гейт ключевиков, plain-fallback при отказе провайдера `tools`, OFF-рубильники; опровергнуты «описание/схема/передача промпта» и «нет второго шага»; **неподтверждены** провайдер/модель и реальная ошибка генератора — HY-01…HY-06).

**Открытые вопросы Step 1 (a)–(f)** требуют lasting-решений: (a) доказательство причины HY-01…HY-06 без фикса на гипотезе; (b) контракт/точка входа `ImageRequest`; (c) гарантия отсутствия двойной генерации; (d) правки `TOOL_GENERATE_IMAGE` и судьба канона; (e) политика памяти §19 без реализации памяти (A4); (f) санкции/deploy/риск.

## Решения

**D1. Диагностика §21 — «фикс не на гипотезе» (протокол HY-01…HY-06 + таблица «причина → минимальный фикс»).**
- **Процедура (блок B, T-3555…T-3558; только чтение/пробы/логи, R17-safe):**
  - **HY-06** (форма запроса) — прогнать фактические «сбои» через `is_image_keyword`/`IMAGE_KEYWORD_RE`: если это форма ключевика, симптом объясним (tool намеренно OFF), иначе — определён scope реального симптома.
  - **HY-03** (рубильники) — прочитать эффективные `IMAGE_GENERATION_ENABLED` (env) и `resolve_module_enabled()` (per-chat слой каталога); OFF → детерминированный блокер (фикс = конфигурация/наблюдаемость, не код генерации).
  - **HY-02** (реальная ошибка генератора) — разобрать `[image] generation failed | reason=…` (`image_generation.py:810–813`), `[image] attempt failed | reason_class=…` (`:914–916`), timeout-лог; классифицировать по `reason_class` (`timeout/network/unauthorized/bad_request/rate_limited/budget/bad_json/too_large/…`).
  - **HY-04** (plain-fallback) — найти `[tools] provider rejected tools — plain answer` (`tool_loop.py:290–292`).
  - **HY-01** (tool-совместимость провайдера/модели) — реальный пробный `chat/completions` c `tools` (активный список) → `finish_reason` + наличие `tool_calls` (T-3555).
  - **HY-05** (описание/схема) — A/B текущего vs уточнённого описания на фикс-наборе свободных промптов → call-rate (только если HY-01 показал поддержку `tools`).
- **Таблица решения:** унификация §18/§20 (ImageRequest) выполняется **всегда** (требование ТЗ, не следствие причины); минимальная «починка» tool-пути выбирается **по фактическому вердикту** (HY-06 → scope; HY-03 → конфигурация; HY-02 → довести реальную ошибку; HY-04/HY-01 → провайдер/модель; HY-05 → обоснованное уточнение описания). Вердикт по каждой HY («подтверждено/опровергнуто») пишется в `evidence.md` и вносится в **этот ADR AMEND-записью** (T-3558/merge).
- **Внешняя причина — честно:** если провайдер/модель не поддерживает `tools`, это фиксируется как внешнее ограничение; «отказ модели» **не выдумывается**; действия ограничены наблюдаемостью/описанием/маршрутизацией, а смена провайдера/модели — отдельное решение владельца (`ARCHITECT_DECISION_REQUIRED`, если потребуется).
- **Альтернативы:** (i) «сразу починить описание» — отклонено: A0 опроверг дефект описания/схемы по коду; (ii) «форсировать `tool_choice`» — отклонено каноном R9/ADR-1023-5 A1; (iii) «фикс по наиболее вероятной гипотезе» — отклонено (Critical KG `Risk-a3-unproven-root-cause`).

- **AMEND (D1/T-3558 — результат блока B; внесено @Architect в rework T-3580, remediation B-1).** Протокол D1 выполнен; источники — `image-diagnostics.md` и `evidence.md` §1/§7. Итоговые вердикты:
  - **HY-06 — механика ПОДТВЕРЖДЕНА** (узкий scope пре-гейта доказан кодом: только «бот/bot + глагол рисования»).
  - **HY-03 — env-слой ОПРОВЕРГНУТ** (все рубильники ON: `IMAGE_*`/`TOOL_CHAIN_*`/`ARTICLE_*`); per-chat слой — **`INCONCLUSIVE`** (PG-каталог недоступен с билд-машины).
  - **HY-01 / HY-02 / HY-04 / HY-05 — `INCONCLUSIVE`** (живые прод-пробы/прод-логи недоступны из билд-окружения: env-эндпоинт LLM лежит целиком — HTTP 500 `get_channel_failed` и **с tools, и без**; прод-конфиг поднимается из PG и не эквивалентен билд-окружению; journald/corpus недоступны).
  - **Протокол дополнен веткой `INCONCLUSIVE` (недоступность билд-окружения)** — легитимный документируемый вердикт при обязательном **блокере + плане проб**. `INCONCLUSIVE` **не** означает «фикс на гипотезе» и **не** активирует ветку «внешняя причина»; «отказ модели» **не выдумывается**; внешняя причина объявляется только по живой пробе.
  - **Owner-гейт прод-проб — статус `PENDING OWNER VERIFICATION`** (владелец/оператор, прод-хост): **HY-01** — живая проба провайдера с активным набором `tools` (`finish_reason=="tool_calls"`); **HY-02** — прод-логи `[image] generation failed`/`attempt failed │ reason_class=`; **HY-04** — grep journald `[provider rejected tools]`; **HY-05** — живая A/B описания (call-rate); **HY-03 (per-chat)** — чтение `flags.image_generation_module_enabled` из PG-каталога. До выполнения проб вердикты остаются `INCONCLUSIVE`; ветка «внешняя причина → `ARCHITECT_DECISION_REQUIRED` (маршрутизация/модель/провайдер)» активируется **только** по живой пробе, доказывающей внешнюю причину.
  - **Следствие по D1:** внешняя причина **не доказана** ⇒ блоки C/D/E выполнены как **безусловное требование ТЗ** (унификация §18/§20) и **страховочный минимум** (D3-маркер, §21-обязательства, D4-текст), без «фикса на гипотезе». KG `Risk-a3-unproven-root-cause` — **закрыт письменно** (реальная причина не доказана; фикс на ней не строится). Контракты §18/§20 **не переписывались**. Решения **D2–D11 по существу не менялись**; product-код в рамках amend не менялся.

**D2. Единый `ImageRequest` (§20) — контракт + единая точка входа в `services/image_generation.py`; reuse существующего генератора.**
- **Контракт:** `source` (`direct|tool`), `chat_id`, `requester_id`, `original_message_id`, `user_request`, `resolved_subjects` (заглушка), `context_required`/`context_sources` (политика/заглушки), `final_prompt`, `generator_config` (резерв; **не** меняет §104-параметры). Имена — рабочие; семантика §20 сохранена.
- **Дом:** `services/image_generation.py` (общий модуль обоих входов) — новый dataclass + `build_image_request(...)` + `build_final_prompt(request)` + `run_image_request(request, *, bot)`. Нового модуля/pipeline нет.
- **Сходимость:** `run_image_request` вызывает **существующий** `generate_and_send(bot, chat_id, final_prompt, reply_to_message_id=original_message_id, correlation_id=…)`; генерация не переписывается (§104). Прямой пре-гейт и `_generate_image` оба строят `ImageRequest` и вызывают раннер.
- **`final_prompt`:** единственная сборка (`build_final_prompt`); в A3 переиспользует `extract_prompt` → прямой канонический запрос даёт прежний промпт (нет регресса); расширение сборки под память — A4 (§25 — ориентир).
- **Альтернативы:** (i) контракт в новом модуле — отклонено (дубль карты/лишний контур); (ii) оставить два независимых пре-пайплайна — отклонено (§18/§20); (iii) перенести генерацию в раннер — отклонено (§104).

**D3. Двойная генерация — сохранён принудительный OFF + авторитетный маркер прогона.**
- Слой 1 (**сохраняется**): срабатывание пре-гейта → `image_enabled=False` → `generate_image` не объявляется.
- Слой 2 (**новый, авторитетный**): существующий сигнал `image_pre_gate_fired` прокидывается в аддитивное поле `ToolContext` (напр. `image_request_handled`); `_generate_image` первым делом проверяет его и при `True` возвращает `{"status":"skipped","reason":"already_handled",…}` **без вызова генератора** (без второго платного вызова/списания `image_calls`).
- Слой 3 (**сохраняется**): `<image_result>`-guard — мягкая модельная подсказка (не авторитет).
- **Не per-phrase:** маркер привязан к прогону сообщения, а не к фразе/инструменту.
- **Альтернатива:** полагаться только на `<image_result>`-инструкцию — отклонено (модель может не подчиниться → потенциальная двойная платная генерация).

**D4. `TOOL_GENERATE_IMAGE` — санкционированное текстовое уточнение описания; канон остаётся 11.**
- Уточняются **только текст** `description` и поле-описание `prompt` под 6 пунктов §21. **Состав/имена/порядок/`required` не меняются:** `generate_image` — 9-й; `prompt: string` **required**; `additionalProperties:false`; новых аргументов нет; `factcheck_tools`=3 без изменений. Канон **11** не расширяется и не сужается (ADR-1020-4 «новое — в хвост» не применяется).
- **§104 не затронут** (описание инструмента ≠ генератор).
- **Результат/ошибка:** бэкенд валидирует `prompt` и вызывает существующий генератор; при провале доводится **реальный `reason`** генератора; текст-сообщение нейтрально и **не** утверждает «отказ модели». Reuse **A2-envelope** (JSON классифицируется `_classify_output` → `tool_results`) — **не** новый контракт.
- **ADR-1013-3 — NOT_APPLICABLE** (описания инструментов — не промпт-канон; `PREV_*`/`PROMPT_MIGRATIONS`/эталоны не добавляются; прецедент A2/`fetch_article`).
- **Связь с D1:** уточнение описания обосновано §21 как требование понимания модели; оно **не** выдаётся за доказанный фикс (§21-причина — по D1); при HY-05-подтверждении — усиливается A/B-доказательством.

**D5. Политика памяти/досье §19 — условная; в A3 только поля-заглушки; реализация — A4.**
- `context_required` (default `False`) и `context_sources` (default `[]`) присутствуют в `ImageRequest`; `resolved_subjects` — заглушка. A3 **не читает** RAG/досье и не разрешает имена.
- Простые запросы — по обычному промпту; «память ради факта» не используется. §19 «расширить поведение» реализовано переходом к структурированному запросу с публичной политикой контекста и хук-точкой сборки; фактическое извлечение — **A4** (reuse этих полей).
- **Альтернатива:** реализовать эвристику «нужен контекст» в A3 — отклонено (пересечение с A4/A6, риск дубля/ложных срабатываний).

**D6. Санкции: Δ DDL = 0, Δ каталога = 0; один env-only киль-свитч.**
- Новых таблиц/колонок/индексов нет; состояние — in-memory на прогон. `param_catalog.py` вне diff; новый киль-свитч — **env-only `ClassVar`** `UNIFIED_IMAGE_REQUEST_ENABLED` (default **ON**, Δ каталога=0; прецедент ADR-1026-14 D6 / ADR-1026-15 D5). **OFF → прежнее поведение** (legacy-путь, исходное описание инструмента, без маркера).

**D9. Risk-Level: R3 + усиленные требования.**
- A3 меняет рантайм-семантику **разделяемых** модулей (`image_generation.py` — новый контракт+раннер; `tool_router.py` — `_generate_image`+идемпотентность; `direct_chat_service.py` — пре-гейт+прокид маркера), затрагивая живой direct-чат и tool-путь, при двух **Critical** KG-рисках (`Risk-a3-unproven-root-cause`, `Risk-a3-direct-path-regression`) и трёх High (`Risk-a3-double-generation`, `Risk-a3-second-image-pipeline`, `Risk-a3-fake-model-refusal`).
- **Усиленные требования (обязательны):** (1) threat/failure-анализ с тестом на угрозу; (2) rollback-доказательства (OFF/legacy-эквивалентность, hot/cold, анкер `e8646af`); (3) adversarial-приёмка (двойной триггер, tool при пре-гейте, ошибка генератора, OFF-киль-свитч, 2-вызовность) + diff-аудит (Δ DDL/каталог, §104/§85-UI, ExecutionGraph, канон).
- **Понижает до R2:** доказанная аддитивность OFF + отсутствие новых наблюдаемых исходов + **доказанный** (не внешний) вердикт блока B с минимальным фиксом. **Reviewer может повысить.**
- **Примечание (remediation B-2, R3-артефакт; исполняет @Builder):** обязательный R3-артефакт `threat-failure-analysis.md` (spec §10 п.1: 8 угроз «механизм → код → тест», по образцу A2) создаётся **@Builder** как отдельный файл фичи. Задача на его создание добавляется/адаптируется **@PM** при сверке `tasks.md` (в текущих блоках F/G она не выделена). До создания файла R3-приёмка не закрыта; при агрегатном эпик-релизе threat-анализ A3 обязан присутствовать в манифесте.

**D10. Наблюдаемость — R17-safe, reuse существующих логов/событий/ExecutionGraph.**
- Логируются только числа/коды/id/`reason_class`/`source`/длины; без сырых промптов/текстов/URL/ключей/аргументов. Вторая аналитика/карта не создаётся.

**D11. Порядок блоков B ↔ A (для сверки T-3554) + AMEND-протокол.**
- Этот ADR фиксирует **протокол** диагностики (D1), а не её результат → сверка T-3554 допустима сразу после T-3553. Фактический вердикт HY-01…HY-06 и минимальный фикс вносятся **AMEND-записью** после T-3558 (без переписывания контрактов §20/§18); при изменении scope фикса — реконсиляция @Architect через @Orchestrator.
- **AMEND внесён (@Architect, rework T-3580 / remediation B-1):** вердикты HY-01…HY-06 зафиксированы в D1 (HY-06 подтверждена; HY-03 env-слой опровергнут; HY-01/02/04/05 — `INCONCLUSIVE` из-за недоступности билд-окружения). Протокол дополнен веткой `INCONCLUSIVE` + owner-гейтом прод-проб (`PENDING OWNER VERIFICATION`). Контракты §18/§20 не переписывались; решения **D2–D10 по существу не менялись**.

## Последствия

- Оба способа генерации получают **единое представление** запроса и **единую** точку подготовки/исполнения; генератор `generate_and_send` (§104) не переписывается — **второго pipeline нет**.
- Двойная генерация исключена **двумя слоями** (OFF-инструмент + серверный маркер прогона), не per-phrase.
- Причина §21 фиксируется **доказательно**; при внешней причине — честная фиксация и ограниченные действия (наблюдаемость/описание/маршрутизация), без выдуманного «отказа модели».

- Память §19 — **условная политика**; реализация отложена в A4; простые запросы без обязательного RAG/досье.
- Δ DDL=0, Δ каталога=0; §104/§85-UI вне diff; REUSE ExecutionGraph; reuse A2-envelope; 2-вызовность сохранена.
- Риск **R3**; усиленные требования (threat/failure, rollback-доказательства, adversarial + diff-аудит).
