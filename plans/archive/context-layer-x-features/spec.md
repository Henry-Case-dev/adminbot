## 1. Обзор

Эпик устраняет 4 класса проблем контекст-слоя direct_chat (research §1), реализуя 24 пункта `[х]` в 5 категориях:

- **Атрибуция людей (п.1–6):** uid рядом с именем во всех внутренних рендерах разговора; карта участников не только
  по окну; дискриминатор коллизий имён; привязка фактов к людям; `Target_User` с uid; memorize-хук «про кого факт».
- **Фокус разговора (п.7–12):** блок `<Current_Question>`; правила приоритета в промпте; защита конспекта от обрезки;
  thread сквозь бот-ответы; компактный итог ветки над фоном; метки свежести секций.
- **Память/история (п.13, 14, 16, 17):** importance-удержание verbatim; summary-of-summary (уровни конспекта);
  purge не трогает protected/высоковесные факты; пересборка конспекта по заполнению окна, а не по TTL.
- **RAG (п.18, 20–22):** факты по релевантности; дедуп RAG↔Global_Context; метки origin+давность; опциональный
  LLM-реранк top-k (флаг off по умолчанию).
- **Промпт/структура (п.23–26):** «как читать блоки» в начале системного промпта; важное к концу user-блока;
  sandwich-строка в конце; стабильный system-префикс для prompt-cache.

**Ключевые инварианты (комментарии владельца):** каскад алиас → никнейм → юзернейм продолжает работать без
изменений; в ЧИСТОВЫХ сообщениях бота нет технических «хвостов» (uid/суффиксы/коды) — только
алиас-никнейм-юзернейм; тон/стиль канона («торопливое письмо», запрет «»/—, 1–2 предложения) не меняется.

Сквозной принцип: **uid — служебный дискриминатор ВНУТРИ контекста, display-имя всегда остаётся результатом
каскада резолва** (резолв-функции не меняются; uid — только добавка на этапе рендера).

### 2.2 NFR (нефункциональные)

- **NFR-1 (тон и порядок регистрации не ломаются):** текст системного промпта сохраняет блоки
  `СИСТЕМНАЯ РОЛЬ / ПРАВИЛА ОФОРМЛЕНИЯ И СТИЛЬ / ИНСТРУМЕНТЫ / ГЛАВНОЕ ОГРАНИЧЕНИЕ`, «торопливое письмо»,
  запрет «»/— в ответах, ограничение 1–2 предложениями — правки только аддитивные (новые абзацы в начале и/или
  между существующими). Порядок регистрации роутеров/handler'ов не меняется (меняется только сборка user-блока
  внутри `_build_user_content`).
- **NFR-2 (в чистовых путях нет «хвостов»):** uid/дискриминаторы `[123]`, `(#1234)`, `[bot]` появляются ТОЛЬКО в
  контекстных блоках direct_chat (`<UserResolutionMap>`, `<Global_Context>`, `<Conversation_Thread>`,
  `<Target_User>`, `<Conversation_Branch>`, `<RAG_Memory>`/`<context>`). Чистые пути — persona-карточка
  (build_persona_card), рендеры protected_facts, канон-имена графа (`_canon_fact_name`), `_resolve_name`,
  RAG-факты как тексты (не строки-рендера), сообщения каналов/справки — НЕ содержат uid-форм и суффиксов.
  Подтверждается: (а) промпт-инструкцией B1 («служебные числа в скобках не выводи и не упоминай»), (б) тестами
  на рендер (суффиксы только в контекстных блоках) и на payload-сборку.
- **NFR-3 (prompt-cache-стабильность):** system@0 (значение `prompts.direct_chat_system_prompt`/канон) — 100%
  статично между запросами; ВСЯ динамика (Target_User, Current_Question, даты/метки RAG, mood, thread, summary,
  имена) — строго в user-блоке. Правило фиксируется докстрингом `services/chat_prompts.py` и структурой канона
  (п.26/FR-24).
- **NFR-4 (SQLite v7):** никаких ALTER/пересозданий существующих таблиц; новые таблицы — только идемпотентные
  `CREATE TABLE IF NOT EXISTS` (2 шт., §3.G1); `PRAGMA user_version` не поднимается.
- **NFR-5 (канон-дисциплина):** каждая правка user-facing промпта — PREV-слепок + ступень `PROMPT_MIGRATIONS` +
  байт-тесты + авто-миграция PG на деплое.
- **NFR-6 (fail-open):** любая новая точка (карта участников, дедуп RAG, LLM-реранк, уровни конспекта, метки,
  parent-линки) при ошибке БД/LLM откатывается к предыдущему поведению с WARNING (без падения запроса и без
  лишних LLM-денег).

## 3. Техдизайн (секции B–F с решениями Q1–Q13)

### 3.0 Общий рендер-канон имён (применяется во всех секциях)

**Формат-инварианты** (проверено по коду: `_build_alias_map` :899 — строка `f"{name} — {uid}"`, EM-DASH; строки
global/thread :930/:942/:992 — `f"{name}: {text}"` без uid; `Target_User` :425 — только имя):

| Рендер | Было (HEAD b198d13) | Стало |
|---|---|---|
| строка `<UserResolutionMap>` | `{имя} — {uid}` | `{имя} — {uid}` (без изменений; при коллизии — см. ниже) |
| строка Global_Context / Conversation_Thread / Conversation_Branch | `{имя}: {текст}` | `{имя}[{дискр}][ {uid}]: {текст}` |
| `<Target_User>` | `<Target_User>{имя}</Target_User>` | `<Target_User>{имя}[ {uid}]</Target_User>` |
| бот-строка (thread/branch) | `{имя_бота}: {текст}` | `{имя_бота} [bot]: {текст}` (вместо uid — маркер роли) |

Правила:
- `{имя}` = результат НЕизменённого каскада `aliases.resolve(uid, nickname/author_name, username)` (комментарий
  владельца п.1). Резолв-функции и канон-механизмы не трогаются.
- `{uid}` рендерится только когда он есть и ненулевой (`user_id IS NOT NULL AND user_id != 0`); иначе — без скобки
  (существующее поведение для анонимов/None).
- `{дискр}` — дискриминатор коллизии (§3.C3), пустой при отсутствии коллизии.
- Вся строка участника (display-часть) перед рендером проходит `escape_xml_text` только в XML-контексте блока —
  точное место экранирования сохраняется как сегодня (body блока целиком через `escape_xml_text`, :960/:1008;
  для Target_User/Current_Question — точечный escape значения).
- uid не «конфликтует» с именами: скобочная форма рядом с display-именем не участвует в каскаде резолва и не
  интерпретируется (проверка владельца п.1). Цифровой никнейм без uid остаётся самим именем.

#### 3.B2 Структура user-блока и порядок блоков (T-791; решение Q7/A1 по п.24)

Порядок сборки `_build_user_content` (новый; «важное к концу»). ВАЖНО: это порядок КОНТЕНТА payload'а; порядок
построения (что раньше вычисляется) может отличаться (см. F2 — двухпроходность), т.к. blocks — список кортежей:

```
 1  map        <UserResolutionMap>
 2  branch     <Conversation_Branch>            — только reply-ветка с глубиной >= 2 (D4); иначе нет
 3  rag        <RAG_Memory>
 4  global     <Global_Context>
 5  thread     <Conversation_Thread>
 6  target     <Target_User>{имя} [{uid}]</Target_User>          НЕ режется
 7  protected  <protected_facts>                                 НЕ режется
 8  lore       <chat_lore>                       — сразу после protected (раунд 7 флоу, Q1)
 9  mood       <mood>                            — поведение доли target сохраняется
10  current    <Current_Question>                НЕ режется (D1)
11  anchors    <style_anchors>
12  sandwich   строка-напоминание                НЕ режется (FR-23/п.25)
```

Обоснование (п.24/FR-22): статика вверх, критичное (target/protected/current_question) — после thread, у конца;
anchors (стиль) — после current_question, но до sandwich (форма ответа, не содержание); sandwich — последняя
строка user-контента (recency). Относительный порядок пары `lore → protected` из раунда 7 сохранён
(chat_lore строго после protected_facts), равно как связка target→protected→lore→mood.

- **Sandwich-строка (константа модуля direct_chat_service):**
  `_SANDWICH_REMINDER = "отвечай коротко, по делу, на последний вопрос (<Current_Question>); людей называй именами из карты, без скобок и номеров"`
  Добавляется в список blocks отдельным последним кортежем (`("sandwich", _SANDWICH_REMINDER)`) ДО
  `_apply_context_budget`; kind вне лимитов → не режется; если blocks пуст — не добавляется.
- **Бюджет (`_apply_context_budget`, T-791):**
  - нережущиеся kinds: target, protected, lore, current, sandwich (вне per-block лимитов и вне порядка урезания);
  - fixed_tokens = сумма токенов нережущихся kinds; лимиты долей применяются к
    `effective_budget = max(1, budget - fixed_tokens)` (аналог существующего правила «target+mood делят долю
    target», обобщённый на весь набор неприкосновенных);
  - новые доли: `branch` (0.03) добавляется в словарь limits; доли map/rag/global/thread/target/anchors остаются;
  - порядок урезания при превышении общего бюджета (новая важность; D2/E1):
    `("anchors", "rag", "thread", "global", "map")` — global режется ОСОБЫМ образом «держать голову» (D2),
    поэтому его место в порядке — после thread; map — последний (карта атрибуции не жертвуется);
  - mood продолжает делиться долей target (внутри фиксированного target+…; механика переносится на
    effective-базу) и НЕ участвует в общем цикле урезания (как сегодня);
  - `_truncate_block` для kinds global/branch использует keep-head-семантику (§3.D2); thread/map/anchors — как
    сегодня (keep-end).

   междометия, повторы AFM/STAE-смысл).
2. Алгоритм (порядок ASC сохраняется, строки НЕ переупорядочиваются): пока
   `count_tokens(join(lines)) > max_tokens`: выбрасываем самую старую строку без маркеров; если таких нет —
   самую старую с ровно одним «слабым» маркером ((г)/(е)/(ж)); если и таких нет — самую старую строку вообще
   (после — вступает D2-шаг 2, резерв токен-обрезания). Жертва всегда со стороны начала диапазона (старое).
3. Флаг `flags.chat_importance_keep_enabled` (default **true**); off → ровно старое поведение (срез keep-end/по
   D2-шагам без маркер-фильтра).
4. Интеграция: (а) в `_build_global_context` при отборе tail/recent-строк под внутренний лимит; (б) при
   бюджетном урезании kind="global" (D2). Thread НЕ участвует (весь verbatim-диалог; урезается keep-end как
   сегодня).
5. Тесты: бюджетное давление — строки с именами/«бот»/числами остаются, шумные выпадают; маркер-матрица;
   флаг off → старое поведение.

#### 3.E2 Progressive summarization (FR-14; T-804) — решение Q13 (п.14+п.17)

Уровни: существующий `running_summary` (chat_running_summary) = **level 1**; новый «широкий» слой = **level 2**.

1. **Хранилище** — новая таблица (DDL §3.G1):
   ```sql
   CREATE TABLE IF NOT EXISTS chat_summary_levels (
       chat_id INTEGER NOT NULL,
       level INTEGER NOT NULL,
       summary TEXT NOT NULL,
       updated_at REAL NOT NULL,
       msg_count_highwater INTEGER NOT NULL DEFAULT 0,
       PRIMARY KEY (chat_id, level)
   );
   ```
2. **Фоновый шаг** (в `_build_running_summary`, summary_memory.py:1075-1104, до/после upsert нового L1 — точно:
   после успешного upsert нового level-1 читается ПРЕДЫДУЩИЙ level-1, который только что перезаписан — поэтому
   чтение старого L1 делается ДО upsert (в начале `_build_running_summary`), а сжатие — после, отдельной
   fire-and-forget-задачей `_build_level2(chat_id, prev_l1_row)`):
   - условие запуска: `prev_l1` существует И `prev_l1["raw_count"] >= limits.chat_level2_min_raw_count`
     (default 250) И (`existing_level2` отсутствует ИЛИ `existing_level2.msg_count_highwater < prev_l1.raw_count`);
   - сжатие: `llm.generate` с каноном `COMPRESS_PROMPT` (тот же, что L1; **новая константа/миграция НЕ вводятся** —
     решение Q13: единый compress-канон, вход = старый конспект; hot.get("prompts.compress_system_prompt",
     COMPRESS_PROMPT) как в L1), user = текст `prev_l1.summary`;
   - результат (непустой, ≤ 10 строк) → UPSERT в chat_summary_levels (level=2) с `msg_count_highwater =
     prev_l1.raw_count`; пустой/LLMError → WARNING, без записи (fail-open).
3. **Инжект в Global_Context** (`_build_global_context`): при наличии L2 и L1 — строки L2 первой строкой body
   (после метки «широкий фон:», D5), кап `limits.chat_level2_max_chars` (default 1500) символов (обрезание
   keep-end по токенам для L2-текста), участие в бюджете global по D2-иерархии жертв (L2 жертвуется ПОСЛЕ L1).
4. TTL: срок жизни L2 не вводится (уровень — «широкая история», запасная очистка: перезапись highwater при новых
   сжатиях; в крайнем случае — удаление строк уровня вручную админом). TTL остаётся «запасным» механизмом L1
   (пишется, но при чтении не «убивает», см. E4).
5. Тесты: уровень пишется при достаточном raw_count и не перезаписывает L2 на меньший highwater; при недостижении
   порога уровня нет; формат инжекта + метка; LLM-ошибка → без записи WARNING; регресс running_summary-тестов.

#### 3.E3 Purge: не трогать protected и высоковесные факты (FR-15; T-805)

Аудит purge/eviction-путей (проверено): `compress_and_purge` (summary_memory.py:1912-1970) → (а) DELETE сырья
smart_messages по cutoff; (б) `_purge_archive` (:2126+) — smart_archive_facts по
`limits.archive_memory_retention_days`; (в) `db.purge_expired_graph_facts` (:1451-1492, edges/nodes/graph_facts по
expires_at; гейт infinite_retention есть); (г) `_enforce_user_quota` (:1411-1427) и `get_quota_victim` (db) —
вытеснение по квоте. `protected_facts` — отдельная таблица, кроном не затрагивается (подтверждается тестами).

Решение по E3:
1. protected_facts не удаляются ни одним purge/eviction путём (уже так — закрепить тестом-инвариантом для всех
   четырёх путей).
2. Граф: факты НЕ являются кандидатами на TTL/purge-удаление, если выполнено хотя бы одно:
   - `weight >= limits.graph_purge_protect_weight` (default **0.8**; вес по origin: bot_direct_reply 0.7, user_memory
     1.0 — см. `_origin_weight` :140-152; порог 0.8 защищает user_memory и вечные origin, не трогая обычные
     chat_history 0.5/direct 0.7), ИЛИ
   - `last_confirmed_at` свежее `limits.graph_purge_protect_days` (default 3 дня; подтверждение = недавний дедуп-
     hit) — критерий «недавнее подтверждение», ИЛИ
   - `expires_at IS NULL` (вечные: user_memory по «запомни», chat_history по D175 — поведение сохраняется).
   Реализация — гейт в `db.purge_expired_graph_facts` (доп. условие WHERE) и в `get_quota_victim` (victim не
   выбирается из защищённого множества — расширение существующего исключения protected).
3. «Запомни» (origin user_memory, expires_at NULL) — вечные, не удаляются (покрыто п.2/гейтом infinite_retention).
4. Тесты: purge не удаляет protected/high-факты и вечные; слабые/старые удаляются; граница порога (0.79/0.8);
   регресс L3-сжатия.

#### 3.E4 Пересборка по заполнению, чтение без TTL-смерти (FR-16; T-806) — решение Q11 (п.17)

Проверено: триггер (summary_memory.py:1057-1067) пересобирает по `fill_threshold` + новизне
(`current.window_end_ts < last_ts`) — заполнение уже является триггером (фиксируется тестом). Дефект: чтение
`db.get_running_summary` (:1820-1837) лениво DELETE'ит просроченный конспект → в тихом чате конспект «умирает»
до нового переполнения.

Решение: **expires_at при ЧТЕНИИ не убивает конспект**:
1. `db.get_running_summary`: убрать lazy-DELETE по `expires_at <= now` — возвращать строку при любом expires_at;
   expires_at продолжает писаться (диагностика/запасной механизм), колонки не меняются. ВАЖНО: убрать удаление
   только здесь — пересборка по-прежнему происходит по заполнению окна новыми сообщениями (существующий
   триггер), т.е. конспект в тихом чате остаётся в Global_Context (метка D5 показывает объём; возраст-метки
   намеренно не вводим).
2. Очистка старых строк при реальном устаревании — вне скоупа (строк одна на чат; перезапись при пересборке).
3. Тесты: тихий чат — конспект в контексте после истечения TTL (новое поведение); бурный чат — пересборка по
   заполнению; существующие TTL-тесты get_running_summary актуализируются (db-уровень), триггер-тест
   (пересборка при новых сообщениях и заполнении) добавляется.

   напрямую); внешний вид legacy-структуры `<context>` сохраняется только для не-direct потребителей.

## 4. Edge cases

1. **uid None/0 (аноним/канал):** строка рендерится без `[uid]` (без изменений поведения резолва; каскад падает на
   `str(user_id)` только при user_id ≠ None — как сегодня в resolve). Карта пропускает uid None.
2. **Два одинаковых имени при отсутствии username у обоих:** суффикс ` (#хвост_uid)` у второго; при полной
   неразличимости display оба различимы по `[uid]` (атрибуция не теряется).
3. **Коллизия «[123]»-подобного никнейма с uid-скобкой:** допустимо (дискриминатор контекстный, каскад не
   интерпретирует скобки; промпт-правило запрещает их вывод — модель не смешает).
4. **Бот-ответ без parent-линка (старые строки/edited/replay-dedup):** thread обрывается на бот-сообщении ровно
   как сегодня (обратная совместимость); запись линка идёт только для новых ответов.
5. **Тихий чат после раунда 8:** конспект не «умирает» по TTL (E4) — Global_Context продолжает показывать старый
   конспект; метка объёма (D5) не врёт; пересборка — только по новым сообщениям, заполнившим окно.
6. **Бурный чат:** триггер пересборки по заполнению работает (тест), L1→L2 сжимает пред-окно при raw_count ≥
   порога; highwater не даёт перезаписать широкий конспект меньшим окном.
7. **Current_Question после среза префикса пуст** (сообщение «бот»): блок не рендерится; sandwich остаётся.
8. **Query длиннее капа Current_Question:** обрезка по символам (не по токенам) — фиксированный предел.
9. **Бюджетное давление с L2:** жертвы в порядке tail → L1 (keep-head) → L2 → метки; нережущиеся kinds
   (target/protected/lore/current/sandwich) неприкосновенны; effective-база не даёт им вытеснить режущиеся в 0.
10. **RAG пустой/флаг RAG off:** дедуп/реранк-шаги не выполняются (ранний выход), блок не рендерится — регресс
    `test_empty_rag_section_omitted`.
11. **Реренк-LLM ответил не-номерами/пустотой:** fail-open → исходный rel-порядок (WARNING); 0 лишних вызовов
    при флаге off.
12. **origin неизвестный (будущие):** `_ORIGIN_LABELS.get(origin, origin)` — метка = сам origin; легаси-рендер
    обрабатывает как сегодня (без префикса).
13. **«Запомни» (user_memory, вечный):** purge-гейт (expires_at NULL) не удаляет; E3-тест.
14. **Purge при включённом infinite_retention:** существующие гейты G2-G5 сохраняются (ветка extract-only), новые
    гейты не конфликтуют (пуринг и так отключён).
15. **Факты диалога про третьих лиц с одинаковыми именами:** привязка по карте участников; полная коллизия
    канонов — факт остаётся на спрашивающем (не на «чужом» тёзке) — безопаснее.
16. **map cap vs бюджет:** cap 150 строк до бюджета; бюджет режет хвост карты (менее активные) — при флаге
    budgets off карта ограничена только cap.
17. **Prompt-cache:** system@0 идентичен между запросами одного чата (динамика только в user-блоке); изменения
    только через канон-миграцию (ступень PREV_R8).
