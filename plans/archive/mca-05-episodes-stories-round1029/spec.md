## 1. Scope / Excluded scope

### 1.1. В скоупе

1. **Модель Episode/Story** (§9.1): связный эпизод разговора; история из ≥1 эпизодов с продолжениями; карточка (участники по ID, две даты, содержание, утверждения, итог/открытые вопросы, source links, версия, состояние `open/closed/uncertain`, статус проверки, excluded_from_retrieval, overrides).
2. **Δ DDL SQLite v21** — таблицы эпизодов/историй/версий/связей-продолжений/redirect + overrides-поля + индексы (ADR-1027-12 D2/§5). PG — no-op.
3. **Пайплайн сборки** (§9.2 п.1–7): детерминированная сегментация → LLM-извлечение с источниками → кандидаты/подтверждение продолжений → сборка истории → повторы/противоречия без потери различий → индекс + событие витрины post-commit.
4. **Resumable backfill job** по архиву на `task_jobs` (checkpoint, heartbeat, счётчики, честная финализация).
5. **Интеграция**: фасад для `lore_compiler_service` (потребитель, без второго каталога), AMEND mca-07 episode-канала на новый store через фасад, carry-over **M-MCA07-2** — наполнение `local_context` EvidenceBundle.
6. **Provenance**: SourceRef/EvidenceLink (`mca-04a`) для каждой записи или явный unknown.
7. **События витрины** `story_discovered` / `story_extended` / `source_linked` / `contradiction_found` / `story_rebuilt` через `mca_events` (mca-13), post-commit.
8. **Наблюдаемость**: процесс `episodes.build` (+backfill) в `mca_process_registry`, стадии, reason_code-расширение, kill-switch-набор.

### 1.2. Вне скоупа (явные исключения)

1. **UI-виджет/лента/таблица/карточка/настройки историй** — `mca-12-miniapp-stories` (§2 п.13/п.14: отдельный верхнеуровневый раздел «Истории» не создаётся; mca-05 не создаёт ни маршрутов, ни настроек).
2. **Публикация в Telegram**: backfill/сборка физически не имеют пути отправки; выбор инициативы — контур координатора/mca-09 (§2 п.2, второй контур запрещён).
3. **Verbatim-episode прямого контекста ASAP-3** (`model_slots`/composer) — не трогается (граница: слово «episode» там ≠ EpisodeService; регресс-тест T-4267).
4. **Сон/досье контуры** (mca-04b/mca-06) — только потребительская кооперация (чтение готовых эпизодов будущими контурами), не реворк.
5. **Фоновый ремап legacy `lore_stories`** — не создаётся; маппинг ленивый (ADR-1027-12 D8).
6. **Интеграция бюджета с Model Capacity Resolver ASAP-3.1** — отклонена (прецедент ADR-1027-9 D14; будущая отдельная санкция).
7. **Новый retrieval-движок / второй SourceRef-контракт / второй каталог историй / второй bundle** — запрещены (GEN-R19).

## 3. Контракты (a)–(l)

### (a) Модель и хранилище Episode/Story (Q1) — REQ-MCA05-R1

**Хранилище — SQLite** (прецедент `lore_stories` `services/database.py:1117`; §4 «по фактической реализации»: текущий lore живёт в SQLite). **PG — no-op** (GEN-R4; `pg_db.py` вне diff). Логический компонент **EpisodeService** (§4) — отдельный модуль в стиле проекта (`services/mca_episodes.py`-эквивалент; имя финализирует Builder в стиле проекта).

- **Episode**: связный эпизод одного разговора (сегмент по времени/reply-графу/участникам); поля: `episode_id`, `chat_id`, `title`, `summary`, `participants_json` (устойчивые ID mca-03), `event_start_ts`/`event_end_ts`, `discovered_at`, `updated_at`, `claims_json` (утверждения с message-refs, R17-safe), `outcome`/`open_questions`, `extraction_version`, `mapping_status`.
- **Story**: история из ≥1 эпизодов; поля §9.1 `:316` дословно: ID, chat_id, название, краткое содержание, участники по ID, `event_start`/`event_end`, `discovered_at`, `updated_at`, фактические утверждения, итог/открытые вопросы, source links, версия, **`state ∈ {open, closed, uncertain}`**, **статус проверки** (`verification ∈ verified/tentative/unknown/rejected` — словарь `mca-04a`), **`excluded_from_retrieval`** (bool), **ручные overrides**, `extractor_version`.
- **Инвариант 1 (разные поля):** состояние завершённости истории (`state`) и статус задания обработки (`task_jobs.status` / job-поле) — **разные сущности**; `story_closed` при незавершённом job невозможен и наоборот (контрактный тест).
- **Инвариант 2 (тема ≠ история):** общая тема не создаёт общую историю; уникальность записи — по `story_id`/canonical event-идентичности, **не** по `topic_key`.
- **Инвариант 3 (две даты):** `event_start/end` — по проверяемому времени исходных сообщений (mca-03 revision); `discovered_at` — отдельно; событие 2022, найденное сегодня, — событие 2022 (A11, детерминированный тест без LLM).
- **Инвариант 4 (честный исход):** при неизвестном исходе — «исход неизвестен» / `state='uncertain'`; финал не выдумывается (негативный тест).
- Repository-слой для всего SQL; UI/пайплайн не ходят в БД напрямую (GEN-R21).

### (b) Δ DDL SQLite v21 (Q2) — REQ-MCA05-R1 + MCA14-R1/R2

**Санкция: v21** (полное обоснование и состав объектов — ADR-1027-12 D2 и §5; рамка `mca-round1027-arch-frames.md` **§1.2.6** дополнена этим Step 2). Кратко: аддитивно/идемпотентно через реестр `MigrationStep` (mca-14): `CREATE TABLE IF NOT EXISTS mca_episodes`, `mca_stories`, `mca_story_versions`, `mca_story_episode_links`, `mca_story_continuations`, `mca_story_redirects`, `mca_story_legacy_links`; `ALTER TABLE mca_stories ADD COLUMN` override-полей (nullable); индексы — только под фактические запросы репозитория (EXPLAIN QUERY PLAN на этапе Build; список кандидатов в ADR §5). Guard `sqlite_master`/`PRAGMA table_info`; повторный прогон — no-op; `user_version` → 21 по книге `schema_migrations`; backup-дисциплина mca-14 (учёт WAL); **старые `lore_stories` не трогаются**; PG no-op; stable ID старой памяти сохраняются.

### (c) EpisodeService: владелец пайплайна и границы записи (Q3)

- Один владелец сборки — EpisodeService; таблицы (a)/(b) пишутся **только** им через `write_transaction`/`_serialized_write` (single-writer mca-01), короткие транзакции: чтение → LLM → короткая запись разделены (MCA14-R3).
- `lore_worker`/dream/summary **не трогаются**: кооперация — только coexistence на single-writer и общий TaskSupervisor; EpisodeService не является вторым контуром обработки сообщений — он читает уже сохранённые сообщения (`smart_messages`/`message_source_records`), ничего не принимая из Telegram.
- `mca_process_registry` (mca-17a) — процесс `episodes.build` (+ `episodes.backfill`), code-declared по прецеденту `dossier.rebuild`; без второго store/очереди.

### (d) Backfill job (Q4)

- **Отдельный resumable job** на durable `task_jobs` (mca-01): unique key `episodes.backfill:<chat_id>` (без дублей/параллельного старта, coalescing); checkpoint продвигается после фиксации результата batch; heartbeat/attempt/lease (v19-поля); счётчики `processed/linked/unresolved/errors`.
- **Не врезка** в dossier backfill (mca-04b — другой домен: субъектные факты) и не в mca-10b (будущий archive_sample). Два доменных прохода сосуществуют по прецеденту mca-04b; от дублирования защищают unique key, 1 активный LLM batch/чат, приоритет direct и отдельный kill-switch.
- Стабильный порядок прохода — keyset `(timestamp, id)`, без OFFSET по миллионам строк; порция ≤ `MCA_EPISODES_BATCH_MAX_MESSAGES` (default 500) с делением по токенам/эпизодам; archive не грузится в RAM/одним промптом.
- Честная финализация (прецедент mca-04b D3): `queued/running/paused/interrupted/failed/completed`; budget/ошибка/отмена → `paused`/`failed`, **никогда ложный `completed`**; нулевой результат при полном корректном проходе валиден.
- **Revision-реакция (§7/§9.2):** изменение источника (mca-03 revision) ставит зависимые эпизоды/истории на перепроверку — постановка в очередь (`story_source_recheck_queued`), без немедленной рекурсивной каскадной ветки.

### (e) Извлечение и LLM-бюджет (Q5, Q7)

- Существующие провайдеры/маршрутизация (GEN-R2); новый ключ канона промптов (`episodes_extract`, `continuation_confirm`) с canon-версией; миграция канона по прецеденту реестра промптов.
- LLM-контракт извлечения: участники — устойчивые ID (identity mca-03), утверждения — с message refs (→ SourceRef T-4263), неизвестные детали — **unknown** (не факт); offline-валидатор контракта (fixture без LLM) + опциональный offline-прогон выбранной модели.
- Бюджет — **standalone env-only** (прецедент ADR-1027-9 D14): `MCA_EPISODES_BATCH_MAX_MESSAGES` (500), `MCA_EPISODES_DIRECT_PRIORITY_ENABLED` (ON); старт — 1 активный LLM batch/чат; источник исчерпания — существующий worker-бюджет lore-стиля; инвариант «budget exhaustion ≠ completed» обязателен. Интеграция с auto-budgets/Model Capacity Resolver — вне фичи (D-решение ADR-1027-12 D6).
- Прямые ответы приоритетны: backfill уступает direct-пути (не блокирует его).

### (f) Сегментация — детерминированное ядро (Q7)

- Разбиение по времени (гэп-порог), reply-графу, участникам; **параллельные разговоры не смешиваются** (тест двух параллельных тем — база A12).
- Перекрывающийся контекст на границах batch без дублей: дедуп по стабильному message-ключу mca-03 (`chat_id + tg_message_id`/source record), overlap не создаёт второй эпизод из тех же сообщений.
- LLM используется только для тематического суждения внутри/между детерминированными сегментами — не для порядка сообщений и не для границ по времени.

### (g) Продолжения и сборка (A12)

- Кандидаты продолжений — поиск в другие дни/месяцы по **событию** (участники + сущность + время), не только по теме; тема/сходство — кандидат, не доказательство.
- **Подтверждение связи до склейки**: LLM-подтверждение с источниками (время+участники+содержание); без подтверждения — кандидат остаётся несвязанным (`story_continuation_rejected`).
- Сборка истории: объединение подтверждённых продолжений при сохранении эпизодов и версий; связывание повторов, противоречащих пересказов и исправлений **без потери различий** (canonical event-идентичность; повтор ≠ независимое событие — тот же принцип, что A10/mca-04a).
- Противоречие фиксируется (`contradiction_found`, статус `verification='tentative'`/conflict-поле), **не разрешается молча**; `uncertain` при неизвестном исходе.

### (h) Версии, merge/split, redirect, overrides (Q9) — A13

- Повторная сборка создаёт **новую версию** (полный снимок в `mca_story_versions`; старая доступна); активная запись ссылается на версию.
- **Ручные правки переживают пересборку**: override-поля пайплайн никогда не затирает; при пересборке override переносится на новую версию (A13-тест).
- Merge/split — с сохранением истории (новая версия + записи в `mca_story_redirects`); **redirect старых ID** (old → new) резолвится фасадом для внешних ссылок (mca-07 канал, будущие события mca-12/убеждения) — внешние ссылки не ломаются.
- **Конкурентная правка защищена версией** (оптимистичный CAS `expected_version` — прецедент F0 persistItems/mca-04b staging): stale update отклоняется, не затирает.

### (i) Фасад компилятора + legacy-маппинг (Q8) + mca-07 канал и `local_context` (M-MCA07-2)

- `lore_compiler_service` — **потребитель/совместимый фасад**: `topic_key` не используется как уникальная идентичность реального события; записи компилятора связываются с новой моделью через `mca_story_legacy_links` **без создания конкурирующего каталога**; инструмент `compile_lore_story` и потребители лора продолжают работать.
- **Legacy `lore_stories`**: сохраняются целиком; сопоставление — **ленивое, без автоматической ложной склейки**: маппинг устанавливается только подтверждённой event-связью (LLM-подтверждение с источниками), никогда по равенству темы; unmapped-записи видимы с честным `unknown` (`mapping_status ∈ mapped/legacy/unmapped`; `story_legacy_unmapped`).
- **mca-07 episode-канал AMEND**: `_episode_candidates` читает новый store через фасад (REUSE `list`-контракт), уважает `excluded_from_retrieval`, chat scope и статусы; fail-open по контракту mca-07 сохранён (второй retrieval-движок запрещён — L-MCA07-5).
- **Carry-over M-MCA07-2**: EpisodeService — владелец наполнения поля `local_context` EvidenceBundle (текущая ветка/важный локальный контекст); инвариант пустого = `not_available`; второй bundle запрещён.

### (j) События витрины + индекс (Q10) — граница §2 п.13/п.14

- Post-commit испускание `story_discovered` / `story_extended` / `source_linked` / `contradiction_found` / `story_rebuilt` **через существующий `mca_events`** (mca-13: start+terminal outcome, reason_code, маскирование; имена событий фиксированы §16.1 — контракт потребителя mca-12, менять нельзя).
- Поля (в `entity_ids` JSON + кодовых полях): `story_id`/`episode_ids`, обе даты (`event_start/end`, `discovered_at`), участники-ID, краткое фактическое описание (R17-safe), `reason_code`.
- **Событие — только после фиксации результата** (тест: rollback → события нет); индекс (поисковый/линейный) обновляется атомарно с фиксацией в одной короткой транзакции.
- Дедуп/курсор-совместимость: события живут в `mca_events` с ретенцией 14/90; mca-12 читает bounded history — **никакого нового канала телеметрии** (§27.1: одна система).
- **Никакого нового верхнеуровневого раздела «Истории», настроек/виджетов в этой фиче** — граница §2 п.13/п.14/§16 (UI — mca-12).

### (k) Provenance (§8.1)

- Каждый эпизод/история обязаны иметь ≥1 валидную ссылку `derived_from` на исходные сообщения через **существующие** `mca_source_refs`/`mca_evidence_links` (mca-04a; второй SourceRef-контракт запрещён) — или явный unknown.
- В ссылке: версия экстрактора, способ установления, статус проверки; валидатор ссылок (существование сообщения/версии/чата).
- Пересказы бота и компилятора — **не** независимое подтверждение события (`independence=self_referential`, контракт mca-04a); unknown — явно, не выдуманная ссылка.

### (l) Наблюдаемость, kill-switch, reason_code (Q11)

- Kill-switch (env-only `ClassVar`, default ON, OFF = паритет baseline): master **`MCA_EPISODES_ENABLED`**; сегментные **`MCA_EPISODES_BACKFILL_ENABLED`** (фоновый проход не запускается), **`MCA_EPISODES_CONTINUATION_ENABLED`** (кандидаты/подтверждения продолжений не строятся), **`MCA_EPISODES_COMPILER_FACADE_ENABLED`** (компилятор/mca-07 канал работают как сегодня). Env-лимиты: `MCA_EPISODES_BATCH_MAX_MESSAGES`, `MCA_EPISODES_DIRECT_PRIORITY_ENABLED`. Состав — в manifest-список релиза (прецедент «26+1»).
- **Расширение словаря reason_code (10, финальный набор):** `episode_extracted`, `story_segment_empty` (INFO: пустой результат сегментации с причиной), `story_continuation_confirmed`, `story_continuation_rejected`, `story_contradiction_found`, `story_legacy_unmapped`, `story_backfill_paused_budget`, `story_source_recheck_queued`, `story_merged`, `story_split`. Переиспользуются существующие: `parse_error`, `model_unavailable`, `evidence_invalid`, `provenance_unresolved`, `source_revision_changed`, `cancelled`, `insufficient_evidence`, `contradictory_evidence`.
- События пайплайна: `start`+terminal `outcome` на каждый запуск/стадию (segment/extract/confirm/assemble/link/index); WARN/ERROR с влиянием и fallback; маскирование; SourceRef вместо сырого контекста; ретенция по умолчанию 14/90 (mca-13).
- Процесс `episodes.build`/`episodes.backfill` в `mca_process_registry` (стадии, widget-ID, `state_source=task_jobs`, heartbeat/lease, `mca_pipeline_runs`); «новый процесс без наблюдаемости = незавершённая интеграция».

## 5. Миграция и обратная совместимость

- v21 аддитивна (см. (b) и ADR §5); старые `lore_stories`, их ID и потребители сохраняются; повторный прогон — no-op; rollback кода оставляет новые данные (совместимая схема).
- Legacy-записи никогда не удаляются и не мутируются; маппинг — только добавление link-строк.
- Migrационный smoke: до/после — `user_version=21`, книга миграций дописана, backup читается.

## 6. Безопасность/приватность

- R17: в записях/событиях — id/коды/короткие R17-safe строки; сырой контекст не дублируется (SourceRef/context version); секреты не журналируются; `sanitize()` до записи.
- `excluded_from_retrieval` уважается каналом mca-07; chat scope не расширяется (эпизоды строго в пределах своего chat_id).
- Участники — только устойчивые ID в durable-данных; отображение имён — на потребителе (mca-12).

## 9. Риск: **R2** — ратификация

**Обоснование R2 (не R3):** фича портит только **производную** память (эпизоды/истории) — первичные сообщения не трогаются; ущерб обратим версионированием + redirect + kill-switch (OFF = паритет); нет merge идентичностей (участники по готовым stable ID mca-03), нет новой внешней/network-поверхности, нет удаления данных.
