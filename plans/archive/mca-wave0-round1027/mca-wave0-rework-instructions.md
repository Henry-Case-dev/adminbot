## Блокеры к исправлению (все, без ослабления требований)

1. **B-MCA01-1 (High) — неполный охват «единого write-механизма».**
   По `spec.md`/`adr-1027-3` (D3) требуется: аудит ВСЕХ записей в общую SQLite connection по смыслу (не по тексту `.execute`) и проведение их через согласованный механизм (включая embedding cache, backfill, сводки, chat_lore, dossier, maintenance/rebuild, throttling, служебные UPDATE/DELETE). Сейчас покрыта ~1 точка из ~90.
   - Реализовать охват; там, где запись законно вне механизма (отдельные соединения/внешние БД/read-only) — перечислить в evidence с обоснованием.
   - Добавить **аудит-тест** (реестр/перечень точек + проверка, что новые прямые commit вне механизма не появляются), чтобы охват не деградировал.
   - T-3736 в `tasks.md` — привести статус к правде.

2. **B-MCA01-2 (High) — дедлок важной очереди.** Ожидание свободного слота происходит под тем же мьютексом, который нужен для освобождения слота; при переполнении важной очереди task_supervisor зависает (воспроизведено ревьюером). Перепроектировать (освобождение ожидания/слота без взаимной блокировки), добавить регресс-тест на переполнение важной очереди.

3. **B-MCA01-3 (Medium) — fencing не применяется.** `fencing_token` инкрементируется при takeover, но ни одна запись его не проверяет. Ввести проверку токена при записях результата (устаревший владелец не перезаписывает), тест на takeover-запись.

4. **B-MCA01-4 (Medium) — rollback вне блокировки.** Восстановительный rollback «деградировавшего» соединения выполняется вне lock — это возвращает исходный класс дефекта. Выполнять строго под блокировкой.

5. **B-MCA13-1 (High, кандидат R2→R3) — нет R17-маскирования.** Контракт событий обязан маскировать секретоподобные значения в строковых и JSON-полях ДО записи в durable-хранилище `mca_events` и в лог (ключи/токены вида `sk-…`, Authorization, cookies, initData, секретные query-параметры и т.п.). Существующий тест «на маскирование» фиктивен.
   - Реализовать маскирование (включая вложенные JSON-структуры).
   - Заменить/добавить реальные негативные тесты: секретоподобные значения не должны попадать в store/лог дословно.
   - Если по итогам риск действительно R3 — обновить риск-поле в spec, threat-артефакт и evidence.

6. **B-MCA13-2 (Medium) — §17.4 метрики/фильтры (SC-13/SC-14) не реализованы**, при этом T-3773 помечен [x]. Предпочтительно реализовать в рамках mca-13 (метрики витрины: active/pending, queue, lock, cache, provider latency/errors, деградации, provenance, archive, инициативы, доставка, random source, стоимость; UNKNOWN≠0; фильтры по trace/chat/component/reason).
