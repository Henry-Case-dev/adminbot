# ADR-1023-1 — Маркировка целевого сообщения-команды в обоих рендерерах истории

- **Статус:** **Accepted** (Step 2 @Architect, 19.09.2026)
- **Фича:** F1 `target-message-marking-round1023`
- **Тип:** backend/LLM-контекст + канон промптов
- **Связано:** ADR-1020-1 (канонический контракт метаданных), ADR-1013-3 (канон-миграции), R11 (саммари), F2/F3 (общий канон-контур)

## Context

Сейчас сообщение-триггер пользователя (`/summary`, `/фактчек`, обычный прямой запрос) попадает в историю чата наравне с прочими сообщениями. LLM иногда трактует его как часть диалога и пересказывает собственный триггер («а потом юзер попросил бота пересказать это»). ТЗ запрещает **физически вырезать** сообщение из истории — это сломало бы таймлайн. Нужна визуальная маркировка.

В проекте два независимых рендерера истории:
- `services/summary_xml.py::XmlGroundingBuilder.build` — XML `<chat_history><message …>текст</message></chat_history>`, текст экранируется `saxutils`;
- `services/canonical_context.py::format_context_item` — plain-строка `[ts | автор | ID | Переслано]: текст` (используется direct-чатом, `chat_context` фактчека, RAG).

Промпты трёх Stage-1 Синтезаторов (`SUMMARY_EDITOR`, `FACTCHECK_ANALYST`, `CHAT`) должны получить правило «помеченное — инструкция, не событие».

## Decision

1. **Единый токен** в новом модуле `services/target_marking.py`:
   - `TARGET_MARKER = "<<< [ЭТО ТВОЯ ТЕКУЩАЯ КОМАНДА]"` (точная форма ТЗ, plain-рендер);
   - `TARGET_MARKER_CORE = "[ЭТО ТВОЯ ТЕКУЩАЯ КОМАНДА]"` — escape-стабильное ядро, не содержит `<`, поэтому идентично в XML и plain; служит якорем промпт-правила и паритет-теста;
   - `is_target_row(row, trigger_message_id)` + `append_marker(body)`.
2. **Сопоставление — по Telegram `message_id`** (`smart_messages.tg_message_id`), не по внутреннему `id`. Нет id / нет совпадения → маркер не ставится.
3. **XML-рендер:** маркер приписывается к body **до** `_escape` → в промпт приходит well-formed XML `…&lt;&lt;&lt; [ЭТО ТВОЯ ТЕКУЩАЯ КОМАНДА]`. Рендер остаётся валидным XML (инвариант существующих тестов/парсеров).
4. **Plain-рендер:** `format_context_item(..., is_target: bool = False)` — маркер приписывается после текста в сыром виде `<<< [… ]`. Дефолт `False` → все прочие вызывающие без изменений.
5. **Обратная совместимость:** `trigger_message_id=None` → **байт-в-байт** прежний вывод обоих рендереров (legacy-путь, авто-крон, фактчек без явного триггера).
6. **Промпт-правило** — единый блок в трёх Stage-1 Синтезаторах: помеченное сообщение — инструкция; запрещено пересказывать/упоминать/анализировать как событие. Формулировка не цитирует запретные клише дословно.
7. **Байт-эталоны** обоих рендереров и инвентарные сэмплы `CONTEXT_POINTS` обновляются осознанно (T-2103) в том же коммите.
8. **Канон-миграция атомарна** (ADR-1013-3): `PREV_*_R1023` + `PROMPT_MIGRATIONS` + `ROLLBACK_MIGRATIONS` + `plans/docs/canon/**` + тесты — одним коммитом.
9. **Порядок:** маркировка — первая ступень канон-контура (`F1 → F2 → F3 → F4 → F6`).

## Consequences

- LLM получает однозначный указатель, не теряя сообщение из истории; лечится симптом «пересказ собственной команды».
- Оба рендерера сохраняют валидность; в XML маркер виден как `&lt;&lt;&lt;`, в plain — как `<<<`.
- Эталоны тестов меняются — обязательный осознанный шаг (иначе High-регресс).
- Нулевые Δ каталога и DDL; откат — `git revert` + обратная канон-миграция.

## Alternatives

- **Физически вырезать сообщение-команду** — отклонено: нарушает таймлайн и причинно-следственные связи (прямой запрет ТЗ).
- **Ставить маркер сырым `<<<` в XML после экранирования** — отклонено: ломает well-formed XML.
- **Только XML-атрибут `is_target="true"` без текстового токена** — отклонено: промпт-правило опирается на видимую пометку в тексте; атрибут не гарантирует, что модель заметит.
- **Сопоставление по внутреннему `db.id`** — отклонено: `message.message_id` из aiogram — это Telegram-id; возможны коллизии.
- **Новый `CONTEXT_POINT` для маркера** — не требуется: меняется содержимое существующих строк, не появляется новая точка подачи (счётчик `CONTEXT_POINTS`=14 сохраняется).
