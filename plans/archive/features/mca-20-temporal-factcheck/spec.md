## 1. Единый вход и TemporalClaimEnvelope (MCA20-R1; T-5132–T-5133)

**D1. `TemporalClaimEnvelope` — frozen-DTO нового модуля `services/temporal_factcheck.py`, не расширение mca-22.** Поля — ровно §30.1 `:1763`: `claim_id`; `target` MessageRef/revision (mca-03); `trigger` MessageRef; `claim_text`/`claim_span`; `source_type ∈ {text, caption, ocr, transcript, url, free_text}`; `attribution`; `repost_received_at`; `original_published_at`; `claim_time/window` (from/to + precision); `date_source`; `date_precision`; `date_timezone`; `uncertainty`; `requested_mode`; `analysis_as_of`; `related` MediaAnalysis revision. Имя класса — `TemporalClaimEnvelope` (CA-20-14: символ `ClaimEnvelope` занят mca-22, `services/claim_envelope.py`; домены не смешивать, DTO mca-22 не трогать). Envelope иммутабелен после сборки; все стадии пайплайна и fallback читают один и тот же объект (A72).

**D2. Только канонические метаданные, сервер валидирует scope.** Источники полей: Origin-блок v32 (`smart_messages`: `origin_type`/`origin_sent_at`/`origin_sender_user_id`/`origin_chat_id`/`origin_display_name` — mca-19, включая `hidden_user`), MessageRef/revision mca-03, MediaAnalysis mca-19 по замороженному контракту `(asset_id, analysis revision)` + селектор части (ADR-1028-19 D11) через SourceRef mca-04a. Модель/LLM выбирает **только target reference** (`tg_message_id` текущего чата); сервер проверяет chat scope и доступ и собирает envelope сам — произвольные аргументы модели (даты, message_id чужого чата, URL-авторство) в envelope не попадают (CA-20-7/12). Невалидный target/вне scope → отказ с reason `temporal_envelope_rejected`, без выдуманных подстановок.

**D3. Один resolver/service на все входы (команда/reply, tool, авто, ручной UI).** `FactCheckService` остаётся единственной точкой; resolver в `services/temporal_factcheck.py` строит envelope из `InputRef(kind ∈ {command, reply, tool, ui, auto})`. Свободный текст без источника → envelope с `source_type=free_text`, `date_source=unknown`, `original_published_at=NULL`, `uncertainty.origin=explicit_unknown` — **explicit unknown origin**, запрет приписывать выдуманные message/date (`:1765`). Существующий OFF-путь (`handlers/factcheck.py:228–324`, легаси-вызов `check_claim` `:298`) не трогается — это бит-в-бит паритет kill-switch; ON-путь добавляет сборку envelope до кеш-секции (`:268` — точка замены ключа, D12). Ранние возвраты хендлера (флаг `flags.factcheck_enabled`, кулдаун, пул `smartmodule_concurrency`) — REUSE без изменений.

**D4. Tool `fact_check` — один адаптер к общему сервису (канон 13→14).** Регистрация в `tool_schemas.py` (`:1761`: публичного check_claim-тула нет; план `:211` — «один адаптер, без второго пайплайна»). Аргументы: `claim` (обяз.), `target_message_id` (опц., только текущий чат), `mode` (опц. enum), `claim_period_hint` (опц. свободная строка — parsed как extracted_claimed, никогда не авторитетен). Scope/права — из доверенного runtime, от LLM не принимаются chat_id/URL-источник/дата/флаги обхода. ToolResult: `status ∈ {ready, disabled, unavailable, insufficient_evidence, failed}` + payload (factual_verdict, temporal_status, evaluated_period, as_of, date_source, uncertainty, run_id, cache_hit, reason). Внутренний tool loop фактчекера **не вызывает `fact_check` рекурсивно**: стадии analyst/validator/verbalizer — data-only вызовы без привязки инструментов (уже гарантировано mca-18 spec §5 D6) + серверный depth-guard в tool loop (belt-and-suspenders; CA-20-12). Tool метричный: +1 в `METERED_TOOLS` (`tool_loop.py`; cache_hit — 0 токенов).

**SC-R1a (→A72):** команда/reply, tool, fallback и поздний OCR проходят один resolver и один envelope; provenance (target revision, asset/analysis revision, date_source) сохраняется до результата; рекурсивного `fact_check` нет (негативный тест depth-guard).
**SC-R1b:** tool и handler дают согласованный envelope — одинаковый claim+target из двух входов даёт одинаковые envelope-поля (кроме `trigger`/`kind`).
**SC-R1c:** свободный текст → `free_text`+`unknown` без выдуманных message/date; target вне scope → `temporal_envelope_rejected`, проверка не зависима от аргументов модели.

## 2. Правила выбора времени и режимы (MCA20-R2; T-5134–T-5136)

**D5. Пять времён и priority-каскад дат (`:1771–1779`).** Различаются и хранятся раздельно: (1) доставка в чат (`repost_received_at`), (2) дата оригинальной Telegram-публикации (`original_published_at`), (3) заявленное время события внутри текста (`claim_time/window`), (4) дата публикации/редактирования веб-источника (evidence.published_at), (5) время проверки (`analysis_as_of`). `forward_origin.date` = дата исходного сообщения пересылки — не доказательство даты события и не всегда самый ранний первоисточник. Каскад приоритета `date_source`: **telegram_origin** (все MessageOrigin, включая `hidden_user` — у него есть date; скрытый автор ≠ неизвестная дата) → **telegram_message** (`message.date` обычного сообщения; дату запроса не подставлять) → **publication_metadata** (URL + происхождение значения; `updated_time`/HTTP Last-Modified ≠ publication time без проверки; snippet — не доказательство) → **extracted_claimed** (дата в тексте/OCR/изображении — до подтверждения; молча не повышать над Telegram metadata; конфликт — показать, не разрешить; EXIF ≠ дата публикации) → **unknown** (NULL/интервал/точность day|month|year; `now` не подставлять для удобства поля).

**D6. Период утверждения, относительные даты, вложенность, TZ (`:1781`).** Явный период утверждения важнее даты публикации для содержания («в 2019 году…» → evaluated_period=2019). Относительные «сегодня/вчера/завтра» разрешаются относительно автора **соответствующего фрагмента** и его публикации, не времени пересылки; вложенная цитата несёт собственную дату — дата внешнего поста не переносится на её «сегодня» автоматически. Неизвестный часовой пояс → диапазон пограничных суток (интервал ±границы), а не точка. UTC-хранение (все INTEGER-поля — epoch UTC) и TZ чата для рендера — разные задачи; хранение ≠ отображение.

**D7. Режимы проверки (`:1783`).** `requested_mode` в envelope; дефолт — `contextual` (смысл на релевантный исходный период + текущая актуальность для изменяемых утверждений, если существенна). Явные просьбы маршрутизируются при сборке envelope: «это сейчас правда?» → `current`; «было ли верно тогда?» → `historical_truth`; `knowable_at_time` — только явный запрос (владелец может сменить дефолт каталогом, D14/§7). `historical_truth` может использовать более позднее расследование — только с явной меткой ретроспективы; смешивать с «что автор мог знать тогда» запрещено (это семантика `knowable_at_time`).

**SC-R2a (→A69):** forward 2022→2026 со «сегодня» — «сегодня» разрешается относительно даты оригинала; возраст публикации не делает утверждение ложным (contextual: old_but_valid ≠ refuted); актуальность отделена в temporal_status.
**SC-R2b (→A71):** дата скриншота неизвестна/спорна → unknown/интервал сохраняется, `now` не подставляется; historical и knowable дают различимые результаты на позднем evidence (ретроспектива помечена).
**SC-R2c:** конфликт дат (extracted vs Telegram) сохранён и показан, не разрешён молча; hidden_user даёт дату как обычный origin.

## 3. Поиск, TemporalVerdict, сквозной пайплайн (MCA20-R3; T-5137–T-5140)

**D8. Декомпозиция и temporal search (`:1789`).** Многочастное утверждение → проверяемые части с собственными периодами; проверяемые числа — REUSE mca-15 `NumericClaim`/`MetricResult` (`services/chat_statistics.py`; CA-20-3: статистика чата ≠ фактчек, второй числовой контур не строится). Запросы формируются с сущностью + событием + временными ограничениями; date filter поисковика — вспомогателен, не единственный механизм. Поисковый инструмент — REUSE существующего (`execute_web_search` в арсенале фактчекера, `:1761`); никаких новых поисковых движков.

**D9. Evidence-контракт (`:1789`).** Каждое evidence: source URL, quoted/summarized support, `published_at` (+`published_at_source` — происхождение значения), `retrieved_at`, temporal relevance, отношение к части claim (supports/refutes/context); SourceRef — по форме mca-04a (`services/provenance.py`, claim_key/checks_json — REUSE формы, не запись в `mca_evidence_links`: фактчек-вердикт не является личным фактом). Первичные источники предпочтительнее (source_kind primary/secondary). Нет результатов → `insufficient_evidence`, не false; недоступная/исчезнувшая исходная страница → `temporal_source_unavailable`, не доказательство подделки (CA-20-10, no-false-acceptance). URL — только через существующий fetch-контур/SafeFetcher mca-02 (SSRF-гейды, CA-20-… threat TH-3).

**D10. `TemporalVerdict` (`:1791`).** frozen-DTO: `factual_verdict ∈ {supported, refuted, mixed, insufficient_evidence}` и `temporal_status ∈ {current, outdated, old_but_valid, misleading_reuse, unknown}` — **раздельно**; плюс `evaluated_period`, `assessment_mode`, `as_of`, `evidence_refs`, `uncertainty`. Один неверный элемент не делает весь пост ложным без указания частей (per-part verdicts в uncertainty/parts). В «Аналитику» — объяснимые основания (стадии, date_source, evidence-периоды); скрытая цепочка рассуждений модели не требуется и не сохраняется.

**D11. Один envelope через все ветки + misleading_reuse по признакам (`:1793`).** analyst → validator (CoVe REUSE) → verbalizer и **все** fallback-пути получают один и тот же `TemporalClaimEnvelope`; даты/оговорки — обязательная часть payload каждой стадии, сокращение/стилизация не стирает их; mca-18 BehaviorFrame применяется **после** TemporalVerdict (CA-20-13: сначала вердикт, затем стиль; тех-стадии analyst/validator — data-only без стиля, граница mca-18 spec §5 D6). `misleading_reuse` ставится **только** при признаках предъявления старого как нового (маркеры «сейчас», «только что», контекст пересылки, подача свежести); сам факт пересылки — никогда (CA-20-11).

**SC-R3a (→A70):** одинаковый claim в разные даты/режимы даёт корректно различённые вердикты (разные evaluated_period/as_of/temporal_status); multipart — части указаны явно.
**SC-R3b:** отказ поисковых движков и исчезнувший первоисточник → `insufficient_evidence`/`temporal_source_unavailable`, никогда `refuted`.
**SC-R3c:** вербализованный ответ во всех ветках (включая fallback и стилизацию) сохраняет существенные даты/оговорки; `misleading_reuse` без признаков предъявления — негативный тест.

## 4. Кеш и freshness (MCA20-R4; T-5141–T-5142)

**D12. Составной ключ вместо text-only; legacy вне namespace; режим OFF (`:1795`).** AMEND точки `handlers/factcheck.py:268` (`cache.build_key("factcheck", target_text)`) и `services/smart_cache.py:47` (`_NORMALIZERS`): новый slug **`factcheck_temporal`** (нормализатор text), `raw_input` — каноническая сериализация составных компонент: `scope доступа` + `canonical claim/span` + `target revision/content_hash` + `origin fingerprint` (origin_type+origin_sent_at+origin ids) + `режим+период` + `tz_resolution_version` (D13) + `MediaAnalysis revision` (если related) + `evidence/pipeline version` + `freshness bucket` (для current). Старый slug `factcheck` на ON-пути не читается и не пишется (legacy-кеш остаётся на диске для OFF-отката — namespace сменился без удаления несвязанных кешей, `:1797`). При неизвестном происхождении (`free_text`/`unknown`) готовый **атрибутированный** ответ не переиспользуется для другого сообщения (ключ содержит trigger-независимые компоненты, но origin-fingerprint неизвестен → ключ не строится). **Авто-bypass:** если корректный ключ построить нельзя (unknown origin, спорные компоненты) — вычислять без кеширования готовых вердиктов с reason `temporal_cache_disabled`; кеш поиска/загрузок (slug `search`/`web`/`youtube`) не затрагивается. Ручной аварийный OFF — kill-switch `MCA_TEMPORAL_FACTCHECK_CACHE_ENABLED` (§7.3). as_of и дата проверки хранятся **внутри** закешированного payload — hit не получает сегодняшнюю дату (CA-20-9).

**D13. Freshness-политика и versioning (`:1797`).** Buckets по виду утверждения: `volatile` (текущие показатели/должности/события; temporal_status=current) — короткий TTL (каталог, дефолт 6 ч); `stable` (исторический вывод; old_but_valid/outdated) — длинный TTL (дефолт 720 ч) с инвалидацией при новых материалах/правках (новый target revision/content_hash → новый ключ автоматически). Механизмы mca-22 (`response_freshness` closure/update-дедуп) и mca-04a (`mca_provenance_status.freshness_status`) — **не дублируются**: mca-20 не пишет в provenance-status и не строит второй closure; свежесть фактчек-вердиктов — это TTL-политика кеша + bucket в ключе (CA-20-5). `TEMPORAL_TZ_RESOLUTION_VERSION = "tzr1"` — ClassVar `services/temporal_factcheck.py`: версия алгоритма разрешения timezone/границ суток; входит в ключ кеша и запись run; изменение алгоритма → bump версии → старые вердикты естественно выпадают из ключей.

**SC-R4a (→A70):** одинаковый текст за разные годы/чаты/режимы — разные ключи; устаревший вердикт не выдан за свежий; unknown origin не разделяет атрибутированный ответ (негативный тест кросс-контекста).
**SC-R4b:** cache hit сохраняет оригинальный as_of (тест: hit после TTL-сдвига показывает старый as_of, не now); legacy slug не обслуживает ON-запросы; переключение ключа не удаляет чужие кеши.

## 5. UI, trace, наблюдаемость (MCA20-R5; T-5143–T-5144)

**D14. Виджет в существующей «Аналитике» + настройки (`:1803`).** Данные — из durable-записей run (v33, §7.1); новые routes +2 в существующем экране (прецедент mca-19 routes +2, RBAC как `/api/random/test`): `GET /api/factcheck/temporal/runs` (последние runs чата/системы) и `GET /api/factcheck/temporal/runs/{run_id}` (детали: original/repost/claim/as_of timeline; «почему выбрана эта дата» = date_source+date_uncertainty+каскад; карточки evidence с периодами; cache hit/version; OCR uncertainty; branches/fallback). Просмотр — под действующими правами; без приватного контента в общих видах (R17). Настройки владельца — в существующей вкладке `mod_factcheck`: дефолтный режим, 2 TTL freshness, доступность tool (§7.2). Витрина — «последнее событие» (контракт mca-12); нового верхнеуровневого раздела/маршрута нет. widget_id процесса — контракт для mca-17c.

**D15. Trace-стадии и честные reason (`:1805`).** Процесс **`temporal.factcheck` v1** (AMEND плейсхолдера v0 `mca_process_registry.py:1134–1140`, прецедент `vision.analyze v0 → vision.media v1`): стадии ровно `target_resolve → origin/date_resolve → claim_decompose → temporal_search → evidence_validate → verdict → verbalize → deliver` (8); события — `factcheck_temporal` (component/stage/reason — только id/коды/числа/refs, без контента, R17). Ошибка извлечения даты (`temporal_date_extract_failed`) ≠ её отсутствие (`temporal_date_unknown`) — разные reason-коды (§7.4); fallback не заменяет historical на current без явного статуса (`temporal_fallback_mode` + assessment_mode в вердикте). Ответ пользователю — краткая существенная дата/неопределённость без технической схемы (дата оригинала при существенности; «проверено на период…»; статус актуальности отдельно).

**SC-R5a (→A73):** виджет и trace работают на реальных запусках (run+evidence видны, стадии 8/8 в «Аналитике»); версии/ошибки/причины раскрываются; R17-запреты соблюдены.
**SC-R5b (→§30 преамбула `:1753`):** в деталях видны исходный пост, дата пересылки, дата оригинала, выбранный период, источники с датами, причины вердикта; настройки режима/freshness/tool доступны владельцу.

## 6. Границы, стоимость, приватность (GEN-R17/R18; CA-20-2…6/13)

Приватность: приватный контент в логи/события не попадает (R17); dаты/тексты claims — в durable run-записях под scope, в events — только ссылки.
