# ADR-1024-12 — BYOK/безопасный путь для ключа изображений (F11)

> **Статус:** proposed → применяется в раунде 10.24.
> **AMEND:** ADR-1023-5 §D3 (image-ключ как глобальный секрет, сохраняемый через общий путь).
> **Слой:** web (`app.js`/`index.html`) + backend (`web/api/routes.py`,
> `services/chat_keys.py`). Δ DDL = 0, Δ каталога = 0.
> **Human Gate №6** закрыт владельцем (UPD3 №6).

## Контекст

`keys.image_api_key` — **глобальный** секрет провайдера генерации изображений
(`category=keys`, `secret=True`, `per_chat=False`). `services/image_generation`
резолвит его только из глобального слоя (`_resolve_str(KEY_API_KEY)`), не из
per-chat BYOK.

В TMA владелец не может сохранить ключ: общий `POST /api/config` **с чат-контекстом**
(`${CATEGORY_KEYS}`) отвечает 422 «ключ-секрет задаётся через /api/config/keys/own
(BYOK-путь)», а BYOK-эндпоинт per-chat требует `X-Chat-Id` и принимает только
`keys.llm_api_key` (whitelist). Дополнительно: при перезагрузке поле ключа пустое.

UPD2 п.9 и UPD3 №6 требуют: сохранять ключ **отдельным безопасным запросом** на
`/api/config/keys/own`; показывать заглушку; блокировать/очищать поле в GET-режиме.

Физический конфликт модели: **BYOK исторически per-chat**, а image-ключ — **глобальный**.

## Решение

### D1. Безопасный эндпоинт с явным `scope`

`/api/config/keys/own` получает опциональный `scope: "auto"|"global"|"chat"`:
- `chat`/`auto`+`X-Chat-Id` — прежний per-chat BYOK (только `keys.llm_api_key`);
- `global`/`auto` без `X-Chat-Id` — сохранение **глобального** секрета в глобальный
  слой (тот же `cache.set`, что и текущий глобальный путь), возврат маски.

Это даёт единый «безопасный путь» для фронта (как просил владелец), не заводя
строк в `chat_keys` для глобального ключа и не расширяя per-chat-семантику.

### D2. Per-chat image-ключ НЕ добавляем в `BYOK_KEYS_WHITELIST`

Соблазнительно «просто» расширить whitelist, но backend не умеет резолвить
per-chat image-ключ (`image_generation` читает глобальный кэш) → получилась бы
«ручка без эффекта» (нарушение «один дом/без мёртвых ручек»). Поэтому:
- `BYOK_KEYS_WHITELIST` остаётся `{"keys.llm_api_key"}`;
- вводится `GLOBAL_SECRET_KEYS = {"keys.image_api_key"}` + `is_global_secret()`;
- global-ветка пишет туда, откуда `image_generation` реально читает.

### D3. `GET /api/config` не меняется

Он и так отдаёт `keys.*` только как `{configured,last4}` (never raw) — требование
«не возвращать ключ в общих настройках» уже выполнено backend'ом; F11 закрывает
**frontend-маршрутизацию** (секрет больше не попадает в общий POST) и **UX маски**.

### D4. Frontend: секреты — только через safe-эндпоинт

`saveBlock` перестаёт класть `f.secret`-поля в общий `POST /api/config`; для
`keys.image_api_key` вызывает `/api/config/keys/own` (`scope:'global'`, без `X-Chat-Id`).
Маска/композит → no-op.

### D5. GET-режим

При `models.image_get_mode=true`: поле ключа `disabled` + черновик очищается; очистка
**UI-only** (без DELETE из БД) — ключ не теряется, когда пользователь вернёт POST-режим.

### D6. Kill-switch

`BYOK_IMAGE_KEY_ENABLED` (env-only, default ON) через `ui_flags`; OFF →
`GLOBAL_SECRET_KEYS` пуст, global-ветка отключена.

## Последствия

**Плюсы:** ключ сохраняется без ошибки; R17 соблюдён (наружу только маска); модель
прав не расширена на per-chat image-ключ; `image_generation` не меняется; существующий
глобальный ключ совместим (то же хранилище).
**Минусы/долг:** у эндпоинта появляется параметр `scope` (нужно аккуратно с RBAC и
тестами); если когда-нибудь понадобится **per-chat** image-ключ, потребуется отдельно
научить `image_generation` читать `chat_keys` (сейчас сознательно не делаем).
**Безопасность:** global-ветка доступна только global admin; raw никогда не отдаётся;
audit записи сохраняется (как у BYOK).

## Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Просто `global:true` в общий `POST /api/config` (без safe-эндпоинта) | владелец явно требует безопасный отдельный эндпоинт; UX маски/GET-режим всё равно нужны |
| Расширить `BYOK_KEYS_WHITELIST` на `keys.image_api_key` | per-chat ключ не резолвится backend'ом → «ручка без эффекта» |
| Хранить image-ключ в `chat_keys` с sentinel-`chat_id` | грязная семантика, обход домена `bot_settings`, риск конфликтов |
| Сделать `image_generation` читать per-chat BYOK | рост scope: async/DB-резолв ключа в горячем пути генерации; не требуется владельцем |
| Ничего не менять, только поправить сообщение об ошибке | не решает невозможность сохранения |
