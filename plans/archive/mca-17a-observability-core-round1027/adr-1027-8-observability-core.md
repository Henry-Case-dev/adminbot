## Контекст

§27.1 требует технический реестр всех фактически работающих процессов из актуального кода (поля + mapping стадий на события + статус с причиной; «новый процесс без наблюдаемости = незавершённая интеграция»). §27.3 расширяет контракт MCA-13 до сквозного trace/span (все поля; correlation в durable queue и при resume; root job + отдельные batch traces; parent-child только для реального вложения; singleflight — links; retry — новая попытка; монотонные часы/UTC; связь по ID/sequence). §27.4 задаёт 9 состояний стадии + run `partial/degraded` + диагностическое `stalled`, контракт обязательных/необязательных стадий по pipeline version и честный итог (linked job вместо скрытого успеха; информативная ошибка). §27.5 — heartbeat/lease/progress/deadline/checkpoint/`next_retry_at`, ориентиры 15 s/60 s, progress-stall по типу, fencing, детект вне loop, recovery по checkpoint, `delivery_unknown`. §27.6 — инциденты (группировка, `acknowledged ≠ resolved`, история), доставка ≤10 s в миниапп, cursor-сверка, только миниапп. §27.7 — durable/полнота/безопасность телеметрии (без случайного семплинга, tx/подтверждения/`status pending`, bounded batch, spool/`telemetry_degraded`/`gaps`, ретенция 14/90, пагинация/индексы, R17). §27.9 — ядро диагностических действий (права/audit/идемпотентность; без слепого повтора side effect; fault injection вне prod).

**Фактическое состояние baseline (сверено с рабочей веткой, §1.3 spec):** единый durable-стор `mca_events` (v15) и `TaskSupervisor`/`task_jobs` (v14) существуют; span-полей нет; `status` в `_CODE_FIELDS`, но колонки нет (теряется при flush); `flush_events`/`prune_events`/`recover_stale`/`TaskSupervisor`/`metrics(runtime=…)` подключены только в тестах (не в проде); watchdog-цикла и продюсера runtime-метрик нет; таблиц `mca_pipeline_runs`/`mca_incidents` нет; SSE/WebSocket в `web/app.js` нет (polling); L-MCA01-5 подтверждён (`run()` передаёт `fencing_token` только в success; cancelled/failed — без токена). Все разрывы присутствуют.

## Решения

### D1. Process-registry — code-declared runtime-каталог (единственный источник правды)
- **Выбрано:** реестр процессов — модуль `services/mca_process_registry.py` (упорядоченные `ProcessDefinition`: `process_id`/`version`/`purpose`/`inputs`/`outputs`/`stages`+branches/`trigger_kind`+`schedule`/`settings_ref`/`state_source`/`recovery_ops`/`widget_id`/`stages_to_events`/`instrumentation`/`owner_feature`). Runtime-статус (`enabled`/`implemented`/`disabled`/`not_run`/`not_instrumented`) **вычисляется при чтении** из декларации + резолва kill-switch per-call + наличия событий/стадий. Доменная таблица `mca_process_registry` **не создаётся**.
- **Обоснование:** §27.1 «составить реестр из актуального кода… реестр сверяется с фактическими handlers/workers/расписаниями» — единственная непротиворечивая копия это код; прецеденты code-declared каталогов — `KILL_SWITCHES` (`services/mca_gates.py`) и `param_catalog.py`; REUSE/GEN-R19 запрещают дублирующие контуры.
- **Альтернатива (таблица `mca_process_registry`):** отклонена — вторая копия дрейфует от кода, требует sync-механизма и не улучшает §27.1 (viewer читает code-контракт через read-only API). Хранение только runtime-статуса в БД — отклонено (статус производный от per-call резолва; не нужен durable).
- **Следствие:** Builder обязан сверить реестр с фактическими workers/schedulers/handlers и зафиксировать расхождения как незавершённую интеграцию.

### D2. Δ DDL = v19; размещение durable-состояния; PG no-op; бронь версии
- **Выбрано:** **v19** через `MigrationStep` (`mca-14`), аддитивно/идемпотентно, `user_version` +1, PG — no-op: `mca_pipeline_runs` (+3 индекса) + `mca_incidents` (+3 индекса) + 8 nullable-колонок `task_jobs` (`pipeline_run_id`/`span_id`/`parent_span_id`/`causation_id`/`attempt_id`/`progress_at`/`next_retry_at`/`checkpoint_ref`; +3 индекса) + 15 nullable-колонок `mca_events` (span-контракт + `status`; +3 индекса). Точные `CREATE/ALTER/INDEX` — spec §5.1. `event_id` = существующий `mca_events.id`; `start`/`end` = `ts` start/терминального события (run-level — `mca_pipeline_runs.started_at`/`finished_at`); `heartbeat_at`/`fencing_token`/`generation`/`attempt`/`deadline_at`/`coalesce_key` в `task_jobs` не дублируются.
- **Обоснование:** §27.7 (durable run/state + индексы по run/status + пагинация), §27.3 (correlation в durable queue/resume, root job + batch), §27.6 (durable `acknowledged≠resolved` + история + trace-ref), §27.5 (`checkpoint_ref` для recovery). Хранение этих полей в существующих JSON-колонках сделало бы их неиндексируемыми → SC-14/SC-15 не проверяемы.
- **Альтернатива (Δ DDL=0):** отклонена — durable lifecycle/incidents/recovery невыразимы; см. spec §5.3.
- **Бронь:** **v19 за `mca-17a`**; advisory `mca-04b` «v19+» сдвигается на **v20+** (рамка §1.2.4). REUSE-механизм `mca-14` соблюдён; старые ID/таблицы/vec сохранены.

### D3. Сквозной trace/span-контракт — расширение `mca_events`
- **Выбрано:** поля §27.3 принимает `build_event` и персистит `flush_events` в `mca_events` (v19). Логическая модель: `pipeline_run_id` (корень, `mca_pipeline_runs`), `span_id`/`parent_span_id` (вложение), `linked_span_ids` (links без владения: singleflight/кеш/async continuation), `job_id` (`task_jobs`), `attempt_id` (попытка), `causation_id`, `event_id` (= `id`), `event_sequence` (монотонный в run), `status`, `reason_code`, `heartbeat_at`/`progress_at`/`deadline_at`/`checkpoint_ref`. `sanitize()` до записи. Второй store/канал запрещён.
- **Обоснование:** §27.3 verbatim; §17.1 (start+outcome); MCA13-R1/R2; GEN-R19.
- **Альтернатива:** новый trace-store/OTel-коллектор — отклонено (§27.3 «адаптация к существующему ExecutionGraph допустима; новых SaaS/Kafka/cluster не требуется»; GEN-R19). Отдельная таблица span — отклонено (дублирует события).

### D4. Correlation в durable queue, resume, root job + batch, время/порядок
- **Выбрано:** `TaskSupervisor.run()`/`TaskJobStore` хранят correlation-колонки в `task_jobs` (v19) и восстанавливают при resume (событие продолжения наследует `pipeline_run_id`/`span_id`); retry = новый `attempt_id` в рамках того же логического этапа (прошлая ошибка не затирается). Длительный archive job — root span + batch spans (`linked_span_ids`), внутри batch — диапазон/счётчики + ссылки на проблемные записи; усреднение не скрывает failures. Длительность — `time.monotonic()`; отображение — UTC; связь — по `event_id`/`event_sequence`.
- **Обоснование:** §27.3 verbatim; A49; L-MCA01-3-прецедент (singleflight до durable-enqueue).
- **Альтернатива:** один span на весь archive job — отклонено (прямо запрещено); timestamp как ключ порядка — отклонено (разные хосты/часы); parent-child для singleflight — отклонено (ложный владелец).

### D5. Lifecycle/states + honest outcome + контракт pipeline version
- **Выбрано:** состояния стадии (`status`): `queued/running/waiting_external/retry_scheduled/succeeded/skipped/failed/cancelled/interrupted`; run: `running/succeeded/partial/degraded/failed/cancelled/interrupted`; `stalled` — **диагностическое**, вычисляется на чтении (не персистится как outcome). Для каждого `pipeline_type`/version — декларация стадий `required`/`optional` + ветвей (`mca_process_registry.py`); итог run: все обязательные `succeeded` → `succeeded`; optional с fallback → `partial`/`degraded` + описание; обязательная невыполнена → `failed`/`interrupted`; run не success при незафиксированной записи/обязательном дочернем job. Async продолжение — отдельный linked job (pending). `skip` — причина+влияние. Ошибка расширяется (`failed_stage`/`last_successful_stages`/`attempt`/`elapsed_ms`/`deadline_at`/`dependency`/`impact`/`fallback`/`checkpoint_ref`/`recovery_action`; `suspected_cause` отдельно).
- **Обоснование:** §27.4 verbatim; A50; §17.3 (ошибки) REUSE `build_error_metadata`.
- **Альтернатива:** успех по факту «LLM вернул текст» — отклонено (ложный success); `stalled` как outcome — отклонено («не заменяет outcome»); скрытое async-завершение как success — отклонено (нужен linked job).

### D6. Ядро диагностических действий (control-plane) + fault-injection-границы
- **Выбрано:** cancel/resume/retry только для разрешённых job-типов; по существующим правам (RBAC), с actor + audit event (через MCA-13-событие), идемпотентно; refresh — read-only; повтор внешнего side effect запрещён без безопасной семантики; `delivery_unknown` — сверка по operation ID вместо слепого retry; нет интерфейса произвольного кода/SQL. `MCA_FAULT_INJECTION_ENABLED` — default OFF, dev/test-only, **не** product-функция/виджет, вне effective-state §20.2 (spec §5.5). UI — `mca-17c` (A56).
- **Обоснование:** §27.9 verbatim; §20.2 («единственное неактивное исключение — stub §14.12»): fault injection не product-функция, поэтому «все ON» не нарушается.
- **Альтернатива:** UI-кнопки в `mca-17a` — отклонено (граница `mca-17c`); fault-injection как production-виджет — отклонено (прямо запрещено).

### D7. Heartbeat/lease/progress/deadline/next_retry
- **Выбрано:** `task_jobs` несёт `heartbeat_at` (есть) + `progress_at`/`next_retry_at`/`checkpoint_ref` (v19); `deadline_at` (есть); ожидаемая внешняя операция — в событии стадии/`error_json`. Пороги env-only: `MCA_JOB_HEARTBEAT_SECONDS=15`, `MCA_JOB_STALE_SECONDS=60`, `MCA_PROGRESS_STALL_<TYPE>_SECONDS` по типу стадии; конфигурируемы. Heartbeat ≠ progress; heartbeat не продлевает абсолютный deadline без объяснимой смены этапа; очередь/внешнее ожидание — отдельно от исполнения.
- **Обоснование:** §27.5 (`:1416–1418`) verbatim; A52.
- **Альтернатива:** единый таймер stale для всех стадий — отклонено (законная длительная транскрибация); progress==heartbeat — отклонено (прямо запрещено).

### D8. Watchdog/takeover/fencing + L-MCA01-5 + детект вне loop
- **Выбрано:** `services/mca_watchdog.py` — background asyncio-задача (старт при инициализации) + проверка **на старте**; при stale lease → `TaskJobStore.recover_stale()` (interrupted + fencing/generation бампаются) → безопасный retry по политике. **Все** терминальные записи `TaskSupervisor.run()` (success/**cancelled/failed**/coalesce/full) передают `fencing_token` — **L-MCA01-5** закрывается здесь (сейчас cancelled/failed — без токена); threat H17a выравнивается на «во все терминальные записи»; тест no-op устаревшего владельца. Детект недоступности процесса — **вне** основного loop (REUSE `services/uptime_heartbeat.py` + внешний менеджер процессов); при отсутствии внешнего наблюдателя ограничение отражается явно, сбой обнаруживается после восстановления. UI при потере backend → `telemetry stale/unknown`.
- **Обоснование:** §27.5 (`:1420–1422`) verbatim; A51; `ARCHITECTURE.md` §95.5 (L-MCA01-5 — обязательный вход).
- **Альтернатива:** watchdog в том же заблокированном loop — отклонено (не диагностирует себя); fencing только в success — отклонено (L-MCA01-5); «зелёный» после потери backend — отклонено.

### D9. Recovery по checkpoint + `delivery_unknown`
- **Выбрано:** recovery читает `get_checkpoint(job_id)` (`task_jobs.payload`), определяет подтверждённые записи/side effects, возобновляет только безопасные этапы; bounded retries (`next_retry_at`, `max_attempts`); неопределённая доставка/платная операция — `delivery_unknown` до сверки по operation ID; рестарт не даёт права повторить вслепую; опасное задание без обязательного durable checkpoint завершается/приостанавливается явно.
- **Обоснование:** §27.5 (`:1424`) + §27.9 verbatim; A51/A52.
- **Альтернатива:** повтор всех незавершённых job после рестарта — отклонено (дубли/слепые платные операции); бесконечный retry — отклонено (прямо запрещено).

### D10. Инциденты + доставка (polling) + cursor
- **Выбрано:** durable `mca_incidents` (v19); fingerprint = `process_id|pipeline_type|stage|reason_code|error_type|dependency` (без свободного текста/слова «timeout»); отдельные trace (`first_trace_id`/`last_trace_id`) и `repeat_count`; `acknowledged ≠ resolved`; resolved — только после проверки (`resolution_evidence`); история сохраняется. Успешный fallback (`fallback_used`) снижает `severity`/`impact`, но инцидент основного пути остаётся. Доставка — incremental polling на существующей инфраструктуре (SSE/WS нет), интервал ≤10 s (`MCA_INCIDENT_PUSH_INTERVAL_SECONDS`); reconnect — пропущенные по cursor + сверка; только миниапп; stack traces не публикуются; R17.
- **Обоснование:** §27.6 verbatim; A55; §1.3 (отсутствие SSE).
- **Альтернатива:** новый SSE-endpoint/panel — отклонено («SSE/WebSocket использовать, если уже есть инфраструктура»; иначе polling; и UI — `mca-17c`); группировка по тексту/слову — отклонено (прямо запрещено); удаление инцидента при исчезновении ошибки — отклонено (история обязательна).

### D11. Хранение/полнота/безопасность телеметрии
- **Выбрано:** durable без случайного семплинга; где возможно — result/checkpoint/outbox в одной локальной tx (`write_transaction`); SQLite↔PG подтверждения/сверка и `status pending` (без обещания общей атомарности); сеть/LLM вне tx (writer lock не удерживается при сети). Ограниченная очередь batch writes (существующий `_pending` maxlen 256) + `flush_events` одной короткой tx; при недоступном хранилище — ограниченный дисковый **spool** (`MCA_TELEMETRY_SPOOL_ENABLED`, `MCA_TELEMETRY_SPOOL_MAX_EVENTS`) или структурный fallback + счётчик + `telemetry_degraded`; при исчерпании — не бесконечный RAM; потеря — `gaps`; нет ложного полного trace. Ретенция REUSE 14/90; серверная пагинация + индексы v19; «детали удалены по сроку хранения». trace/user/message ID — не высококардинальные labels. R17 во все каналы, включая `error_json`/экспорт; роли/chat isolation; без дублирования промпта/архива; без скрытых рассуждений.
- **Обоснование:** §27.7 verbatim; A53; GEN-R14/R21.
- **Альтернатива:** fire-and-forget логгер — отклонено (durable state не зависит от лога); неограниченный RAM-буфер — отклонено; случайный семплинг — отклонено.

### D12. Санкции: Δ DDL v19, Δ каталога 0, kill-switch, fault-injection, риск/деплой
- **Выбрано:** Δ DDL **v19** (D2); Δ каталога **0** (все рубильники/пороги — env-only `ClassVar`; F8 NOT_APPLICABLE); kill-switch (утверждены, §«Санкции»); `MCA_FAULT_INJECTION_ENABLED` default OFF dev/test-only (D6). Risk **R3** (подтверждён reassessment). Deploy `DEFERRED_TO_RELEASE`. Hot-откат — kill-switch; cold — `git revert`→`05bc870`.
- **Обоснование:** MCA14-R1/R2/R4/R5; §18; §20; A28.
- **Альтернатива:** Δ DDL=0 — отклонено (D2); Δ каталога≠0 — отклонено (нет UI-настроек).

### D13. REUSE-карта (без второго контура)
- **Выбрано:** ExecutionGraph §82–§92 (`execution_graph_source`/`GET /analytics/execution/latest`/`execution_graph.js`) и `mca_events` — расширяются **аддитивно**; второй store/аналитика/`TaskSupervisor`/write-механизм **запрещены**; UI не ходит в БД напрямую (GEN-R21). Carrey-over UI — REUSE существующего viewer/endpoint (`/api/oversight/summary` — аддитивный `mca_metrics`; `/api/status/logs` — аддитивные фильтры), **без новых панелей/маршрутов/endpoint**. **Уточнение (AMEND F5/D16):** «без новых endpoint» относится к **carry-over UI** и витрине; read-only **данные-API ядра** (§4.6/§4.10: `incident_changes`/`active_incidents`, `registry_snapshot`) — это аддитивные read-only endpoint'ы на **существующем** роутере `oversight` (`web/api/oversight.py`), а не вторая аналитика/панель.
- **Обоснование:** GEN-R19/R21; §4 (один контур телеметрии); §27.3 (адаптация к существующему допустима).
- **Альтернатива:** второй дашборд/панель — отклонено (GEN-R19; полная витрина — `mca-17c`).

### D14. L-MCA01-5 — fencing во все терминальные записи (обязательный вход)
- **Выбрано:** `TaskSupervisor.run()` передаёт `fencing_token=fence` в **cancelled** и **failed** пути `_safe_finish(...)` (сейчас — нет) **до** первого production-подключения TaskSupervisor; добавлен тест «устаревший владелец после takeover не перезаписывает терминальную строку нового»; формулировка threat H17a — «во **все** терминальные записи».
- **Обоснование:** `ARCHITECTURE.md` §95.5 (L-MCA01-5, обязательный вход `mca-17a`); A51; §27.5 (fencing).
- **Альтернатива:** оставить success-only — отклонено: после takeover «медленный» владелец перезаписывает `interrupted`-строку нового владельца.

### D15. Carry-over `mca-13` §94.5 (обязательный вход)
- **Выбрано:** (1) **UI SC-13** — метрики §17.4 (`mca_events.metrics()`) аддитивным блоком на **существующей** витрине (`/api/oversight/summary` → `#/oversight`), без новых панелей/endpoint; поле без продюсера — `available=false`/`null` (`UNKNOWN ≠ 0`). (2) **UI SC-14** — фильтры `trace_id`/`chat_id`/`component`/`reason_code` аддитивно к существующему `GET /api/status/logs` + переход из карточки к связанным событиям (`query_events`, deep link на trace) в существующем log viewer. (3) **Живые продюсеры** `runtime`-метрик (`rss_mb`/`cache_entries`/`downloads`/`provenance_coverage`/`histories`/`episodes`); до подключения — честно `unknown`. (4) **Wiring** `flush_events`/`prune_events` в worker-loop/периодический job/shutdown, уважая **оба** kill-switch (`MCA_EVENT_CONTRACT_ENABLED` + `MCA_TELEMETRY_STORE_ENABLED`). (5) **Reassessment** триггера «конкуренция записи»: при подключении flush в worker-loop триггер **срабатывает → R3** (запись батчей конкурирует за single-writer lock).
- **Обоснование:** `ARCHITECTURE.md` §94.5 (обязательный carry-over register `mca-13 → mca-17a`); A48/A53; §27.7.
- **Альтернатива:** не подключать flush (durable-персистенция мертва) — отклонено; новые панели/endpoint — отклонено (carry-over требует REUSE viewer).

### D16. AMEND F5 (post-review adjudication): транспорт ядра — в `mca-17a`; представления — в `mca-17c`
- **Контекст:** ревью T-3885 (F5) показало, что `active_incidents`/`incident_changes`/`registry_snapshot` реализованы, но **не выставлены ни одним endpoint** (`web/api/**` их не импортирует) → SC-16/A55 «доставка ≤10 s» и §4.10 «read-only API реестра» end-to-end не достигнуты. Прямая задача @Architect — подтвердить границу `mca-17a`/`mca-17c`.
- **Решение:** транспорт — **в `mca-17a`** (дореализация, а не перенос); визуализация — в `mca-17c`.
  - `mca-17a` (read-only данные-API на **существующем** роутере `oversight`, RBAC global-admin, fail-open shape-compatible, R17-safe; гейты `MCA_INCIDENTS_ENABLED`/`MCA_INCIDENT_PUSH_ENABLED`/`MCA_PROCESS_REGISTRY_ENABLED`): `incident_changes`/`active_incidents` (cursor ≤10 s) + `registry_snapshot`; минимальный refresh **существующего** компактного индикатора ≤ `MCA_INCIDENT_PUSH_INTERVAL_SECONDS` (без новой панели/UI-маршрута).
  - `mca-17c`: полное представление «Инциденты»/«Обзор процессов»/«Запуски», фильтры/drill-down/уровни/граф, диагностические действия (A54/A56/A57/A73).
- **Почему это НЕ сужение §27.6:** вещество §27.6 (данные инцидентов, группировка, `acknowledged≠resolved`, доставка ≤10 s, cursor, только миниапп) остаётся в `mca-17a`; в `mca-17c` выносится только графическое представление (полный список), что и есть место матрицы/витрины (§27.2/§27.10). Перенос транспорта в `mca-17c` **отклонён**: он сузил бы §27.6 в `mca-17a` и сделал бы A55 недоказуемой.
- **Альтернатива (перенос транспорта целиком в `mca-17c`):** отклонена — `mca-17a` закрылась бы с невыполненной A55/SC-16; `mca-17c` пришлось бы строить transport ядра, смешав ядро с витриной.
- **Следствие (binding):** AMEND меняет `spec.md`/ADR → Spec-Hash/ADR-Hash из `review.md` устаревают; T-3885 Merge **не выполняется** на старом binding; требуется повторный @Reviewer gate (обе линзы) → `Approved` → Merge §100+ → ADR `Accepted`.
