## 1. Цель, объём и исключённый объём

**Цель.** «Модули» становится оперативным пультом (§31): найти модуль → убедиться в выбранной области → включить/выключить → получить подтверждение сервера — **без открытия отдельной страницы параметров**. Три визуальных экземпляра тумблера (панель быстрого управления, карточка каталога, головной тумблер страницы модуля) работают с **одним каноническим состоянием**, одно действие даёт **ровно одну** серверную мутацию, при ошибке состояние **откатывается** к подтверждённому сервером.

## 3. Контракты: `ModuleConfigurationStore` (§37–§39), мутация (§40–§42), фактическое состояние (§43)

### 3.1. Где живёт состояние (D1)

`ModuleConfigurationStore` — **тонкий слой на существующем реактивном экземпляре Vue 3 (global zero-build)**, внутри `web/app.js`. **Новых библиотек нет** (§39 запрещает; CSP `script-src 'self'`, ADR-1016-2/ADR-1024-13). **Канонический источник значений — существующий `configItems`** (наполняется `loadConfig` → `GET /api/config`); store **не создаёт копию конфигурации** и не вводит своего API.

Добавляемые данные (реактивные, на корне компонента):
- `moduleOptimistic: { [storeKey]: { value: boolean, opId: string } }` — **только** оптимистичное значение в полёте;
- `modulePending: { [storeKey]: true }` — блокировка повтора;
- `moduleSaveError: { [storeKey]: string }` — понятная ошибка по ключу;
- `moduleQuickpicks: string[]` и `moduleQuickpicksOpen: boolean` (§4).

Методы (логический контракт §39):

| Метод | Контракт |
|---|---|
| `storeScope()` | `{ type: 'global'|'chat'|'dm', id: null|number }` — из `scopeKind`/`activeChatId` (F3) |
| `storeKey(scope, moduleId)` | `scope.type + '/' + (scope.id == null ? 'null' : scope.id) + '/' + moduleId` |
| `getModuleState(scope, moduleId)` | `{ known, effective, globalValue, hasOverride, display, runtime, pending, error }` — **производное** от `configItems` + overlay; `display` = overlay (в полёте) → `effective`; `known=false`, если элемента нет/`value==null` |
| `setModuleState(scope, moduleId, enabled)` | одна мутация (§3.3); возвращает `OperationResult`-подобный итог `{ ok, skipped, error }` |
| `refreshModuleState(scope, moduleId)` | `loadConfig()` **только** если `scope` = активная область (иначе no-op — данных чужой области в памяти нет); без нового API |
| `subscribeModuleState(scope, moduleId, cb)` | `this.$watch` на геттер ключа → `cb(state)`; **возвращает** функцию отписки. Шаблоны подписаны неявно (реактивность Vue) — контракт §39 обеспечен без ручных подписок |

**`module_id`** — идентификатор модуля каталога (`m.id`, напр. `mod_summary`); на провод (`/api/config`) уходит канонический `m.toggleKey` (`flags.summary_enabled`). Ключ store: `global/null/mod_summary`, `chat/123/mod_summary`, `chat/456/mod_summary` — **три разных контекста** (§38).

### 3.2. Резолв фактического состояния (§43, D3)

Приоритет отображения: `moduleOptimistic[key].value` (только пока `pending`) → эффективное `value` из `configItems` → `null` (**неизвестно**, ≠ выключено).

Три уровня показываются явно: **глобальное значение** (`global_value`), **локальное переопределение** (`chat_source === 'chat'`; в глобальной области отсутствует), **фактическое состояние** (эффективное значение + runtime-поправка D3).

**Runtime-поправка (проверено по коду, ADR-1025-14 §D3).** У модулей разная природа мастер-флага:
- `gate = 'global'` — код читает флаг **без чата** (`hot.get`), локальный override **не влияет** на работу модуля;
- `gate = 'per_chat'` — код резолвит `override → global → default` (`get_chat_param`), локальный override действует;
- `gate = 'unknown'` — метаданных нет (защита от будущих модулей).

Метаданные `runtimeGate` (+ `parentGate`) задаются в JS `MODULES` — это **не каталог** (`services/param_catalog.py` не трогается, Δ каталога = 0). Значение по умолчанию при отсутствии метаданных — `'global'` (консервативно: не утверждать действие локального значения без доказательства кодом).

Правила подписи (новый helper `moduleRuntimeNotice(m)`, **отдельно** от `configItemNotice`):

| Условие (область ≠ global) | Подпись |
|---|---|
| `global_value === false && effective === true && gate === 'global'` | **«Не работает: отключён глобально»** + «локальное значение сохранено» |
| `global_value === false && effective === true && gate === 'per_chat'` | «Включено для этой области (глобально выключено)» |
| `global_value === false && effective === true && gate === 'unknown'` | «Локальное значение сохранено; глобально модуль выключен» |
| `effective === false && hasOverride && gate === 'global'` | «Отключение для этой области не влияет: модуль управляется глобально» |
| родительский гейт выключен глобально (`flags.summary_enabled`) | «Не работает: отключён глобально» (для модулей с `parentGate`) |
| иначе | пусто |

`configSourceLabel` (F3) используется как есть. **`configItemNotice` не изменяется** — его формулировку фиксирует F3-тест (Ф16).

- **Override не уничтожается.** F4 не вызывает `DELETE /api/config/chat/{key}` из карточек/панели; смена глобального значения не сбрасывает локальные override (серверный `_post_config_global` пишет только глобальный слой).
- **«Ожидает применения» — N/A.** Конфигурация read-through (Ф15); отдельного applied-state сервер не имеет → показывать нечего. Показ такого индикатора = выдуманное состояние (§43 запрещает). «Работает» не показывается, пока значение не подтверждено сервером — по конструкции: `display` берётся из ответа `GET /api/config` / из результата мутации, а оптимистичное значение живёт только в overlay до подтверждения.

### 3.3. Мутация: одна на действие, откат, scoped-ключи (§40–§42, D2)

`setModuleState(scope, moduleId, enabled)` — строгая последовательность:

1. **RBAC** — `canEditModule(m)`/`canEditConfig(m.toggleKey)`; нет права → тост, выхода нет.
2. **Канонический элемент** — найти в `configItems` по `m.toggleKey`; нет → предупреждение, **мутации нет** (не выдумывать запись).
3. `key = storeKey(scope, moduleId)`, `epoch = scopeEpoch`, `scopeId` фиксируются **до** `await`.
4. **Блокировка повтора:** `modulePending[key]` → выход (no-op). Вторая линия — in-flight-guard `persistItems` по `m.toggleKey` (`skipped`).
5. **Оптимистично** (только overlay): `moduleOptimistic[key] = { value: !!enabled, opId }`, `moduleSaveError[key] = ''`. **`configItems[i].value` НЕ мутируется** — это конструктивная гарантия отката.
6. **Ровно одна мутация:** `persistItems([{ key: m.toggleKey, value: !!enabled, per_chat: item.per_chat }], { operationId })`. Один элемент → одна группа → **один** `POST /api/config` (chat-пакет с `X-Chat-Id` либо глобальный). Три представления **не** порождают три запроса. (`opts.reason` принимается, но в `persistItems` не используется — не полагаться на него.)
7. **Применение результата — только к зафиксированному ключу и только если `epoch === scopeEpoch`.** Если epoch не совпал (пользователь сменил область) — результат отбрасывается, чужая область не меняется; overlay снимается. Ни в одной ветке не читается «текущий чат на момент ответа».
8. **Успех** (`res.saved` содержит ключ или `res.revalidated`): overlay снимается; значение в UI = результат `loadConfig()` внутри `saveConfigItem`/`persistItems`.
9. **Ошибка / 409 / частичный успех:** overlay снимается → UI **автоматически возвращается к подтверждённому сервером значению** (`configItems` не мутировался) + `moduleSaveError[key]` + **одно** итоговое уведомление F0 (`notify`, идемпотентен по `operationId`). **Авто-ретраев нет**; ветка 409 переиспользует контракт F0 (`conflicting[]`, один re-read, `stickyConflict`) без дублирования.
10. `finally`: `modulePending[key] = false`.

**Индикатор сохранения** — спиннер/disabled у тумблера при `modulePending[key]`.

**Ограничение-наследство.** В `persistItems` есть известное остаточное окно (L-F3-4: epoch снимается после `await`); F4 **не полагается** на него — scoped-применение обеспечено собственным `key`+`epoch` в store. Починка окна — follow-up F0, не этот пакет.

**Один store для всех представлений (§40):** панель быстрого управления, карточка каталога и головной тумблер страницы модуля (а также счётчики §45) читают **один** store. Локальных boolean-дублей нет.

### 3.4. `moduleEnabled`/`toggleModule` (адаптация без изменения внешнего поведения)

- `moduleEnabled(m)` → `getModuleState(storeScope(), m.id).display === true` (с учётом overlay);
- `toggleModule(m, checked)` → `setModuleState(storeScope(), m.id, checked)`;
- сигнатуры и RBAC сохранены; существующие вызовы шаблона продолжают работать.

## 4. Панель быстрого управления и избранное (§34–§36, D4)

- **Кандидаты стартового набора (не жёстко заданный список):** Сводки чатов (`mod_summary`), Ответы в чате (`mod_direct`), Проверка фактов (`mod_factcheck`), Поиск (`mod_search`).

Значение — JSON-массив `m.id`, валидируется по `MODULES` (неизвестные id игнорируются), порядок сохраняется, размер ограничен.
  - Отклонено: **серверное per-user хранилище** — требует DDL/новой таблицы/эндпоинта (запрет Δ DDL = 0, R16); **только фиксированный набор** — ТЗ §34 предпочитает самостоятельное закрепление, а `localStorage` уже является принятым механизмом UI-предпочтений проекта (Ф17).
  - Fail-open: нет `localStorage`/исключение/битый JSON → стартовый набор; операции закрепления не падают.
- **Избранное — представление, не конфигурация:** не участвует в `/api/config`, не влияет на состояние модуля; закрепление/открепление **не** включает/выключает модуль.

Лимит отображения (первые N избранных) + кнопка **«Все избранные»** (раскрывает остальные); карусели нет.

Ниже — **фактическое состояние для выбранной области** (эффективное значение + `configSourceLabel`/`moduleRuntimeNotice`). Ниже — кнопка **«Настроить»**. Тумблер доступен вне страницы параметров.

### 5.2. Тач-цель и разделение действий
- Зона нажатия тумблера — **≥ 44×44** CSS px (визуальный трек не увеличивается; растёт hit-area метки/`::before`), **без** уменьшения ради 4 колонок панели.
- **Вся карточка не работает как тумблер:** клик по телу/описанию/иконке не переключает модуль; тумблер — единственный переключатель; «Настроить» — отдельное действие.
- `aria-label` на тумблере сохраняется.

### 5.3. Модули с особенностями (решение (d), D6)
- `noToggle` (шаблон `web/index.html:1175`; сейчас не используется): карточка показывает бейдж «без тумблера», «Настроить» доступно, модуль **входит только в «Всего»**, не входит в Включено/Выключено/Есть проблемы и в панель.
- **uiFlag-скрытый модуль** (`mod_images`, `visibleModules`): при `IMAGE_MODULE_CARD_ENABLED=OFF` модуль **исключён** из витрины, поиска, панели и **всех** счётчиков; он **никогда** не считается «Выключено».
- Правило распространяется на любой будущий uiFlag-гейт (счётчики работают по `visibleModules`).

### 5.4. «Карточка ≠ тумблер» — проверяемо
Клик по карточке → ноль мутаций; клик по тумблеру → одна мутация; клик по «Настроить» → ноль мутаций.

### 5.5. «Настроить» → рабочее пространство F5 (решение (e))
Вводится **единственный шов**: `openModuleWorkspace(m)` — точка входа, которую **F5** перенаправит на маршрут `Модули → <модуль>` (§46). В F4 шов делегирует в **существующую модалку** `openModuleWindow(m)` (регресс-путь: параметры модуля остаются доступны — §79/§116), а кнопка переименовывается «Параметры» → **«Настроить»**.

**Отклонено:** регистрировать сейчас маршрут `#/modules/<id>` / «заглушку-страницу». Причина: маршрут и рабочее пространство — собственность F5 (§46); F4-заглушка создала бы пустую страницу и изменила IA/роутинг F1, не давая функциональности. Отклонение от буквального «диплинк/заглушка» в T-2626 — осознанное, зафиксировано в ADR-1025-14 §D6 (см. §12).

## 6. Поиск, фильтры и индикаторы (§32/§44/§45)

### 6.1. Поиск (§44, решение (b), D5)
- Поле «Найти модуль…» — **inline-фильтрация** основного каталога; **отдельной страницы результатов нет**; результаты сохраняют генеральные тумблеры.
- Поля поиска: **русское название** (`title`), **описание** (`subtitle`), **техническое название** (`toggleKey`), **синонимы** (`keywords`).
- Метаданные поиска — **в JS `MODULES`** (`keywords: [...]`), `services/param_catalog.py` **не изменяется** → **Δ каталога = 0**. Отклонено: модульные метаданные в каталоге (Δ каталога > 0).
- Обязательно: «Саммари», «сводка», «суммаризация», «summary» находят «Сводки чатов»; старые названия остаются в `keywords` (поиск не ломается при витринном переименовании).
- Пустой результат — понятный empty-state; на mobile корректно (без горизонтального скролла).

### 6.2. Витринные названия (решение (f))
Переименование **только витрины JS** (не каталог): `mod_summary.title` → **«Сводки чатов»**, `mod_direct.title` → **«Ответы в чате»**. `id`/`toggleKey`/`tab` **не меняются**; `TABS[].label` (`web/app.js:64,71`) и `PROVIDER_BLOCKS` **не трогаются** (на них опираются тесты); старые названия остаются синонимами. Проверено: маркер-тесты ищут подстроки в JS целиком (`tests/test_round106_ia_smoke.py:125-130`, `tests/test_webapp_nav_disclosure_ui.py:162-166`) — строки сохраняются в `TABS`/`PROVIDER_BLOCKS`, поэтому проходят. При любом расхождении — атомарное обновление маркеров (T-2648).

### 6.3. Фильтры (T-2623)
«Все / Включённые / Выключенные / Есть проблемы / Избранные» + сброс. Фильтры — **представление**: ноль мутаций, не теряют генеральные тумблеры, работают в связке с поиском и областью; «нет результатов» — empty-state. «Включённые/Выключенные» используют **runtime-состояние** §3.2 (неизвестное не попадает ни туда, ни туда).

### 6.4. Общие индикаторы (§45, D6/D7)
Считаются **для выбранной области** по набору `visibleModules` (S):

| Индикатор | Определение |
|---|---|
| **Всего** | `|S|` (включая `noToggle`) |
| **Включено** | `#{m ∈ S : runtime === 'on'}` |
| **Выключено** | `#{m ∈ S : runtime === 'off'}` |
| **Есть проблемы** | `#{m ∈ S : unknown (нет элемента/`value==null`) **или** конфликт runtime↔конфигурация (§3.2: «Не работает: отключён глобально»/override не влияет) **или** сохранение по ключу провалилось (`stickyFailedKeys`/`moduleSaveError`)}` |

Инвариант: `Всего = Включено + Выключено + Неизвестно + БезТумблера`. **Неизвестное состояние не попадает в «Выключено»** и не подменяется им; `noToggle` не попадает в on/off. Цифры меняются при смене области и при переключении модуля **после подтверждения сервера** (оптимистичное значение в счётчики не течёт — счётчики считают по подтверждённому состоянию + overlay только для визуальной согласованности тумблера; изменение счётчика происходит по факту применения store-состояния).

## 8. Наблюдаемое поведение, условия отказа и тесты (§72/§73/§79/§116)

### 8.1. Основные сценарии (приёмка)
1. **§72 единый переключатель:** выбрать чат A → открыть «Модули» → выключить Сводки **в избранном** → проверить карточку каталога → проверить головной тумблер страницы модуля → проверить серверное значение → перезагрузить страницу → проверить сохранённое. Ожидаемо: три представления одинаковы; **ровно одна** серверная мутация; после перезагрузки состояние сохранено.
2. **§73 независимость чатов:** выключить Сводки в A → переключиться в B → проверить B (не изменился) → вернуться в A → проверить A. **Повторить с незавершённым запросом:** ответ A, пришедший после перехода в B, **не меняет** B (применение только к исходному scope по `key`+`epoch`).
3. **§43 наследование:** изменить глобальное → чат без override наследует новое; чат с override сохраняет override (не уничтожен); при глобально выключенном и локально включённом — подпись по таблице §3.2 («Не работает: отключён глобально» для `gate='global'`).
4. **§41 ошибка:** сервер вернул ошибку → успешное изменение **не** показывается, тумблер вернулся к серверному значению, показано понятное сообщение, повторов нет.
5. **Двойной тап / быстрое переключение:** одна мутация, индикатор появляется и снимается.
6. **RBAC:** нет права → тумблер disabled, мутации нет.

### 8.2. Условия отказа (fail-cases)
| Отказ | Ожидаемое поведение |
