## 0. Цель

Устранить спам `[betterstack] send failed | reason=status=401` и восстановить доставку логов BetterStack, приведя **хост** и **исходный токен** в соответствие US-кластеру; зафиксировать корректную роль Sentry и обновить зависимость от рестарта.

**Требуется (ТЗ §1):**
- Отправка логов идёт на корректный **US-хост** (не EU `in.logs.betterstack.com`).
- Токен — **Source Token** (не public key из `SENTRY_DSN`); конфликт зафиксирован и закрыт.
- Аудит: Sentry и BetterStack не конфликтуют, каждый инициализируется своим провайдером.
- Задокументировано, что `.env` подтягивается **только при рестарте** (нет рантайм-перечитывания).

## 1. Контекст и доказательства (@Memory Step 0)

- **Посылка ТЗ неточна:** `LogtailHandler` из библиотеки `logtail-python` **не используется** с раунда 4/5. Реальная точка инициализации — `bot.py:141-145` → `BetterStackHandler(source_token=os.getenv("LOGTAIL_SOURCE_TOKEN"))`.
- **Хендлер уже умеет host:** `services/betterstack_handler.py:39` (`DEFAULT_HOST = "in.logs.betterstack.com"`), `:99`, `:109` — конструктор принимает `host=`. Дополнительная правка библиотеки не нужна.
- **Диагноз 401 (раунд 5, T-746):** в `LOGTAIL_SOURCE_TOKEN` залит **public key из `SENTRY_DSN`**, а не Source Token. Значение токена в ТЗ **совпадает** с public key из `SENTRY_DSN` → 401 на US-хосте.
- **Противоречие в репо:** есть комментарий/тест, утверждающий обратное («совпадение токена с public key — НОРМА»). Требуется ревизия и устранение противоречия (без секретов в тексте тестов/доков).
- **Рантайм-подтягивание `.env` невозможно** без рестарта: `load_dotenv` выполняется при импорте, хендлер создаётся на уровне модуля. Задача — зафиксировать это (startup-лог/док), а не «научить читать на лету».
- **Секреты:** `plans/current_task.md` — untracked, `.gitignore:70`. Токены/SSH-пароль из ТЗ **нельзя** коммитить, вносить в спеки/ADR/KG. Ротация SSH — **CANCELLED** (пароль действующий, вне раунда).
- **Каталог:** новый env/ключ хоста → **REGISTRY 435 → 436** (санкционированный Δ, фиксируется в пин-тестах).
