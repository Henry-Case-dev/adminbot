# ADR-1026-4 — S2 «Восстановление контекста»: контракт, границы S2↔S3, лимиты и интеграция

- **Статус:** Accepted (Step 2 @Architect, 23.09.2026)
- **Фича:** S2 `summary-context-restore-round1026` (Эпик 2, шаг «Восстановление контекста»)
- **Тип:** backend/алгоритм (детерминированный, 0 LLM-вызовов); Δ каталога = 0; Δ DDL = 0
- **Связано:** **ADR-1026-1 D5/D6** (границы S1↔S3, врезка) — **AMEND (уточнение)**; ADR-1026-2 (переиздание F8 — **не требуется**); ADR-1022-3/4/5 (ровно 2 LLM-вызова); ADR-1023-1/-2 (маркер, цепочка реплаев); ADR-1013-3 (промпт-канон — не задействован); ADR-1025-24 **D4** (публикация/hybrid — гейт S6/S10)
- **Baseline:** HEAD `7895e77`, `APP_VERSION` 2.58.20, pytest 8525/0, JS 43/43, каталог 467/426/442/100/98/21, Δ DDL=0

## Контекст

§80 вводит этап «Восстановление контекста» между алгоритмическим фильтром (S1, ✅ выкат 2.58.18) и L1-кластеризатором (S3). §90 требует: найти сохранённые сообщения, определить `reply_to`, добавить необходимые родители, добавить **ограниченный** ближайший контекст, сохранить хронологию и исходные `message_id`, удалить дубли — но **не возвращать весь шестичасовой лог**. §91 задаёт спец-случаи, §92 — структуру данных L1, §93 — лимит/фрагменты. Публикационный путь менять нельзя (ADR-1025-24 D4), система обязана сохранить **ровно 2 LLM-вызова** (ADR-1022-4).

S1 уже оставил всё необходимое: обратимый `dropped`, резерв `restored_count`, ключи `context_neighbors`/`context_max_messages`/`reply_context_enabled`, общий потолок `summary_max_context_tokens`/`_chars`. PM-задачи содержали скрытое противоречие: pure-core «без БД/сети» (T-3227) против обязательного reuse `collect_thread_chain` (async, читает БД) — разрешено ниже двухслойным дизайном.

## Решения

**D1. Контракт S1 → S2 → XML: отдельный `RestoreResult`, XML не меняется.**
- Новый pure-core `services/summary_context_restore.py::restore_context(kept, dropped, window, params, *, extra_parents=(), token_limit=None, char_limit=None, bot_id=None) -> RestoreResult`.
- `RestoreResult{kept, restored, restored_count, parent_count, neighbor_count, restored_tg_ids, skipped_ids, budget, status, duration_ms}` — **аддитивный** объект, не расширение `FilterResult`.
- В `summary_xml.build` уходит **`RestoreResult.kept`** — строки того же типа/полей, что и `FilterResult.kept`; подпись и модуль XML **не меняются** (D4-гейт). `_apply_filter` переносит `restored_count` в `FilterResult` (`dataclasses.replace`) только для метрик/логов.
- Обратимость: входные `kept`/`dropped`/`window` не мутируются; результат детерминирован и воспроизводим. Fail-open: исключение → `status='error'`, `kept = FilterResult.kept`.
- **Двухслойность (разрешение противоречия pure vs thread_chain):** pure-core делает **только in-memory** достраивание над `window`; родители **вне окна / сквозь бот-ответы** добываются async-адаптером в генераторе через **существующий** `thread_chain.collect_thread_chain` и подаются как `extra_parents`. Вторая реализация обхода цепочки не создаётся, `thread_chain.py` не изменяется.
- Альтернатива (async/БД внутри core) отклонена: ломает детерминизм/тестируемость и обещание «core без I/O». Альтернатива (правка `summary_xml.build`) отклонена: нарушает D4-гейт.

**D2. Границы §93: S2 ↔ S3.**
S2 — **только детерминированное достраивание контекста**. «Разделить вход на фрагменты / обработать фрагменты / объединить темы / устранить дубли / сохранить связи» в семантической части — **S3** (§94–§95, L1 LLM). `FilterResult.fragments` — контракт неизменен (`Fragment{index, message_ids, overlap_message_ids, reason}` | `None`) и остаётся входом **S3**; **S2 фрагменты не потребляет** и не пересчитывает (работает с полным окном и `kept`/`dropped`). Механический дедуп по `id` и сохранение `reply_to_id`/`tg_message_id` — S2 сохраняет. Это уточняет ADR-1026-1 D5 (там S2 описан как потребитель `dropped` + §89-ключей — подтверждается; добавлено явное «фрагменты — не S2»).

**D3. `restored_count`: число ДОБАВЛЕННЫХ, после дедупа/cap/бюджета.**
`restored_count = len(restored)` — reply-родители + соседи, реально добавленные в XML-вход; дедуплицированные пересечения с `kept` не считаются. `saved_count` = `kept` S1; размер XML-входа = `saved_count + restored_count`. Считается в core, переносится в `FilterResult.restored_count` (§108/§109/S7 — единый источник). Логи: `FILTER_COMPLETE.restored_count` (фактический), плюс аддитивные `RESTORE_START/COMPLETE/ERROR` с `run_id=correlation_id` (R17: только числа/коды/id).

**D4. Лимиты §89/§93 — существующие ключи, детерминированный порядок, «не резать молча».**
- `limits.summary_filter_context_neighbors` (1) — ближайших соседей **с каждой стороны** от якоря; `limits.summary_filter_context_max_messages` (50) — жёсткий cap на **добавляемые** сообщения; `flags.summary_filter_reply_context_enabled` — мастер-гейт всего S2 (OFF → восстановления нет, байт-в-байт S1); общий бюджет — существующие `limits.summary_max_context_tokens`/`_chars` через `resolve_context_tokens`/`resolve_chat_limit`. Резолв per-chat (`_chat_limit`), новых ключей **нет**.
- Порядок: **родители** (транзитивно; вне окна — `collect_thread_chain`, глубина ≤ код-константы `RESTORE_CHAIN_DEPTH=10`) → **соседи** → **cap 50** → **токенный/символьный бюджет**. Тай-брейк `(timestamp, id)`.
- **«Не резать молча»:** S2 никогда не удаляет из `kept`; усечение возможно только для добавляемых кандидатов и всегда даёт `status='truncated'` + лог + `skipped_ids`. Жёсткий cap символов в XML — последняя страховка (вне diff).
- Альтернатива (cap на весь набор) отклонена: имя/описание ключа — «Лимит **восстановленных** сообщений» (дополнения). Альтернатива (новый параметр) отклонена: Δ каталога=0.

**D5. Спец-случаи §91 и идентификация авторов §92.**
- Короткие важные треды — приоритет родителей; длинные бессодержательные — ограничены `context_neighbors`/cap; параллельные разговоры — связь только по `reply_to_id`/соседству, без склейки несвязанных веток.
- Медиа (`media_type != 'text'`, пустой текст) — валидный родитель/сосед, не отбрасывается; подпись/транскрипт сохраняются.
- **Бот-ответы и предыдущие Саммари — не события** (§91): элементы `collect_thread_chain` с `is_bot=True` и строки с `user_id == bot_id` **не восстанавливаются**; сквозь бот-ответ проходим, но бот-ход в набор не попадает (согласовано с S1).
- §92: `author_id ← user_id`, `display_name ← author_name`, `message_id ← tg_message_id`, `reply_to_id`, `message_type ← media_type`, `chat_id` из запуска; поля `mentions` в окне нет — **не выдумывать**; отсутствующие метаданные не фабрикуются.

**D6. Интеграция / логи / UI.**
- Врезка внутри `_apply_filter` **после** `filter_window` и **до** `xml.build` (строго между `get_window_messages` и XML). `_run`, порядок этапов, RAG/память/граф/memorize — без изменений (на исходных `rows`). **0 новых LLM-вызовов.**
- Логи `RESTORE_START/COMPLETE/ERROR` (`status=truncated`), `run_id=correlation_id`; метрики аддитивно в `_filter_metrics` для S8 (узлы `algorithm` — S8). R17/R18.
- **UI (блок H) = NOT_APPLICABLE:** новых параметров нет; §89-ключи уже рендерятся в «Подготовка сообщений» (`mod_summary`), группой «Тонкая настройка». Δ каталога=0, Δ JS `MODULES`=0, новых API нет.

**D7. Инварианты / deploy.**
Δ DDL=0; **Δ каталога=0** (переиздание frozen-артефактов F8 по ADR-1026-2 **не требуется**); `summary_xml.py`/`summary_prompts.py`/публикация — вне diff (D4-гейт S6/S10 закрыт); ровно 2 LLM-вызова; CSP/zero-build; R17/R18; reuse `thread_chain.py` без модификации; §57–§72/F0–F11/S1, IA, сердцебиение не тронуты. **Deploy = ДА:** новый рантайм `services/summary_context_restore.py` + правка `services/summary_generator.py` → **bump `APP_VERSION` 2.58.20 → 2.58.21** + `README.md` + cache-bust. Откат: hot-OFF `flags.summary_filter_reply_context_enabled=false` (байт-в-байт S1) / `flags.summary_filter_enabled=false`; `git revert` + тег `pre-round1026-s2`. §17: после деплоя workflow не останавливать, live-проверки — PENDING OWNER VERIFICATION, продолжение — S3 `summary-l1-clusterizer`.

## Последствия

- Появляется чистый переиспользуемый этап восстановления без Δ каталога/DDL — минимальный риск для контура S1/публикации.
- `dropped` S1 впервые используется по назначению (обратимость подтверждена на живом коде).
- Ограничения (документируются): `mentions` отсутствует в окне; родители **вне** 6-часового окна достаются только через `collect_thread_chain` с ограниченной глубиной; семантика тем/дублей остаётся на S3.
- `restored_count` становится реальным сквозным показателем (§108/§109/S7/S8) вместо резерва.

## Альтернативы (сводно)

- Расширение `FilterResult` вместо `RestoreResult` — отклонено (смешение слоёв, ломает контракт S1/S3).
- Правка `summary_xml.py`/подписи `build` — отклонено (D4-гейт).
- Async/БД внутри pure-core — отклонено (детерминизм, тестируемость); вместо этого двухслойность D1.
- Cap на весь набор вместо добавлений — отклонено (семантика ключа §89).
- Новый параметр каталога / Δ DDL — отклонено (Δ каталога=0, Δ DDL=0).
- Семантическая склейка тем в S2 — отклонено (это S3, D2).

## AMEND / SUPERSEDE

- **AMEND (уточнение, не замена):** **ADR-1026-1 D5** — S2 не потребляет `fragments` (они адресованы S3); **ADR-1026-1 D6** — добавлена врезка S2 внутри `_apply_filter` (после `filter_window`, до `xml.build`), XML по-прежнему вне diff.
- **SUPERSEDE: нет.** ADR-1022-3/4/5, ADR-1023-1/-2, ADR-1013-3, ADR-1025-24 D4, ADR-1026-1 (D1–D4, D7), ADR-1026-2 — сохраняются без изменений.
- **Frozen-артефакты F8:** — не затрагиваются (Δ каталога=0); переиздание ADR-1026-2 **не запускается**.
- **Затронутые требования S2:** REQ-S2-01…-13 (спека §3) — все привязаны к сценариям SC-01…SC-17; решения D1–D7 — данного ADR.
