# ADR-1024-6 — Устойчивость фонового graph-extract: граф не теряется молча

- **Статус:** **Accepted** (Step 2 @Architect, часть 1/2 раунда 10.24, 19.09.2026)
- **Фича:** F1 `core-llm-error-fixes-round1024` (только п.0a)
- **Тип:** backend/LLM + надёжность
- **Связано:** ADR-1024-1 (логирование), `round1024-architecture.md` §3.1/§4; **п.0b (embeddings) ОТМЕНЁН владельцем (UPD3 п.7)**
- **Задачи:** T-2188…T-2195 (T-2191/T-2192 — **CANCELLED** по embeddings)

## Context

1. Боевой лог: `_extract_and_save_graph` (`services/summary_memory.py:3211-3268`) вызывает `self.llm.generate(...)` с хвостом батча до `_GRAPH_EXTRACT_MAX_CHARS = 8000` (`:462`, применение `:3223`). Провайдер chat-запросов (`nano-gpt.com`) не успевает за общий дедлайн: `LLMTimeoutError` после 3 попыток (`services/llm_client.py:752-755`).
2. Caller (`_compress_purge_extract_only`, `:3179-3187`) **не ставит `mark_smart_messages_processed`** — то есть батч сохраняется. Но крон при каждом тике снова берёт **тот же** самый старый необработанный батч с тем же слишком длинным промптом и снова падает: граф этого батча фактически **теряется навсегда**, а очередь графа стоит (эффект «отравленного» батча).
3. Общий `generate()` используется всем ботом (direct/factcheck/summary/worker) — менять его таймауты/ретраи глобально нельзя (регресс латентности/стоимости).
4. Идемпотентность: `upsert_node`/`upsert_edge(weight_increment=…)` при повторе **наращивают вес** (`MIN(weight+inc, cap)`, `services/database.py:2490-2541`) — нельзя переписывать один и тот же батч многократно.
5. Владелец (UPD2 п.0) требует: чанкование/урезание промпта, отдельный таймаут/бюджет фонового вызова, метрику «батч отброшен», логирование; тихий пропуск графа недопустим.

## Decision

### D1. Отдельный канал фонового вызова (не трогаем `generate` для остальных)
- Новый `LLMClient.generate_background(messages, *, purpose, deadline, max_attempts)`.
- В `_post(...)` добавляются **опциональные** `budget: float | None = None` и `max_retries: int | None = None`; `None` → ровно текущее поведение (байт-в-байт для всех существующих вызовов).
- `generate_background` использует глобальный ключ (chat-независимо), канал `chat`, дедлайн `GRAPH_EXTRACT_TIMEOUT_SECONDS` (env-only, default **120.0**), попытки `GRAPH_EXTRACT_MAX_ATTEMPTS` (default **2**) с bounded backoff.
- Δ каталога = 0, Δ DDL = 0.

### D2. Чанкование батча (bounded)
- `_GRAPH_EXTRACT_MAX_CHARS` (8000) остаётся верхней границей хвоста; он режется на окна ≤ `GRAPH_EXTRACT_CHUNK_CHARS` (default **4000**), не более `GRAPH_EXTRACT_MAX_CHUNKS` (default **3**).
- Если `GRAPH_EXTRACT_RETRY_ENABLED=False` → **прежний** одиночный вызов (kill-switch, байт-в-байт старое поведение).
- Default (чанк 4000): промпт на вызов вдвое короче → устраняет таймаут; стоимость — до 2 фоновых вызовов на батч (вне System-2 счётчика).

### D3. Фазовая запись: extract-then-write (идемпотентность)
- Фаза A: извлечь триплеты **всех** чанков в память (без записи в БД). Частичный сбой чанка не пишет БД → нет наращивания весов при повторе.
- Фаза B (запись) только при одном из исходов:
  - **all-ok** (все чанки успешны) → upsert всех триплетов + `mark_smart_messages_processed` + `INFO`;
  - **partial** (≥1 чанк дал триплеты, часть чанков упала) → upsert успешных + mark + `WARNING event=graph_extract_partial` (явно, видимо) — осознанное принятие частичного графа, но **не молча**;
  - **none-ok** (ни одного триплета) → БД не пишем, mark НЕ ставим, `ERROR event=graph_extract_failed` с причиной/`chat_id` (батч остаётся в очереди; повторится следующим тиком).
- **Защита от «отравленного» батча:** in-process счётчик последовательных полных фейлов батча; при достижении `GRAPH_EXTRACT_MAX_BATCH_FAILURES` (default **3**) — mark + `ERROR event=graph_extract_dropped` + счётчик `graph_extract_dropped_total`. Отброс **явный и логируемый**, а не тихий. Счётчик сбрасывается при успехе/рестарте.

### D4. Метрика «батч отброшен»
- Структурированное лог-событие `event=graph_extract_dropped` (греп/алерт Betterstack) + in-process `summary_memory.graph_extract_dropped_total()`.
- Без PG-таблицы/DDL (согласовано с парадигмой раунда: метрика = лог + счётчик).

### D5. п.0b (embeddings) — ОТМЕНЁН
- Владелец меняет ключ/провайдер сам (UPD3 п.7). Код `embed`/провайдер-схема `requests` **не трогается**; задачи T-2191/T-2192 снимаются, T-2193(b/c) не выполняется.
- Наблюдаемость embed остаётся задачей F2 (лог), но без изменения логики.

## Consequences

**Positive**
- Граф батча либо записывается, либо **явно** повторяется/отбрасывается с логом и метрикой — «тихой» потери нет.
- Промпт короче → таймаут `nano-gpt` устранён, очередь графа разблокируется.
- Общий `generate` не изменён — нулевой регресс direct/factcheck/summary.
- Идемпотентность соблюдена (запись ровно один раз на батч) — нет инфляции весов.

**Negative**
- До 2-3 фоновых LLM-вызовов на батч вместо 1 (в пределах бюджета фона; kill-switch OFF возвращает 1).
- При частичном сбое часть графа теряется, но событие `graph_extract_partial` видимо и считаемо.
- In-process счётчик фейлов сбрасывается рестартом (приемлемо: деградация остаётся видимой в логах).

## Alternatives

- **A1. Увеличить общий `LLM_TOTAL_BUDGET`/timeout** — **отклонено**: регресс латентности всех потребителей.
- **A2. Оставить одиночный вызов и retry до успеха** — **отклонено**: отравленный батч держит очередь вечно.
- **A3. Писать частичные триплеты при любом исходе с повторной обработкой батча** — **отклонено**: повторный upsert наращивает веса (нет idempotency key).
- **A4. Persist-очередь graph-extract (DDL)** — **отклонено** в этом раунде: Δ DDL, усложнение; достаточен bounded-retry + явный drop.
- **A5. Починить embeddings-схему/сменить primary** — **ОТМЕНЕНО владельцем**.
