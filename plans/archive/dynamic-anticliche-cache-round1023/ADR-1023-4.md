# ADR-1023-4 — Dynamic Anti-Cliche Cache: динамический список питает ДЕТЕКТОР, не scrubber и не промпт

- **Статус:** **Accepted** (Step 2 @Architect, часть 2/3 раунда 10.23, 19.09.2026)
- **Фича:** F4 `dynamic-anticliche-cache-round1023`
- **Тип:** backend (worker/PG-DDL/detector/API)
- **Связано:** ADR-1022-6 (validator-loop, клише не режутся), ADR-1013-3 (канон-миграции), ADR-1019-8 (идемпотентные PG-сиды), `round1023-architecture.md` §3.4/§5/§8
- **Задачи:** T-2126…T-2135

## Context

1. ТЗ (строка 46) буквально предписывает: динамически подставлять `{dynamic_cliche_list}` в **системный промпт Вербализатора** и на клише «Regex Scrubber бракует ответ». Это конфликтует с двумя инвариантами:
   - S10.22/10.22-вето владельца: клише кодом **не** вырезаются (ломает грамматику), только брак + регенерация;
   - «список клише живёт в коде» (`negative_constraints.py:49` `FORBIDDEN_CLICHE_PATTERNS`) и grep-тест отсутствия тропов в промпт-константах — динамический список в промпте нарушит оба.
2. Детектор `find_forbidden_cliches` — синхронная чистая функция без I/O; рекурсивный вызов PG из неё недопустим (латентность на каждом ответе + риск зацикливания).
3. Cache-источник нестабилен (внешний сайт/GitHub + LLM); данные могут быть мусорными/вредоносными (произвольный regex → ReDoS/инъекция).
4. Открытый техдолг **S10.22-4b**: `as_ai` ложно срабатывает при запятой.

## Decision

### D1. Динамический список питает **детектор**, а не промпт и не scrubber
- `FORBIDDEN_CLICHE_PATTERNS` **не трогается** и остаётся единственным источником для промпт-канона (его в промптах нет) и первичным детектором.
- Динамические правила добавляются **аддитивным** опциональным параметром `dynamic_rules` в `find_forbidden_cliches` и пробрасываются в `verbalize_validated`.
- Клише по-прежнему **только бракуются и регенерируются** (≤2 ретрая). `outgoing_guard.sanitize_outgoing`/`EXTRA_PATTERNS` не расширяются.
- ТЗ-требование «`{dynamic_cliche_list}` в промпте» **отклонено** и переинтерпретировано: список влияет на вердикт детектора, а не на текст промпта. Это единственная реализация, совместимая с вето владельца и grep-тестом.

### D2. Литеральные фразы + стабильные коды (не regex)
- Из LLM принимаются только **литеральные строки-фразы**; на детекторе — `re.escape(phrase)` (+ `\b` по краям словесных границ).
- Стабильный код: `dyn_<sha1(normalized_phrase)[:8]>` — детерминирован, дедуплицируем, R17-safe (наружу отдаются коды, не подстроки).
- Лимит ≤20, длина 2…120, нормализация, дедуп (внутри динамики и против хардкодных правил). Произвольные regex **не принимаются** (защита от ReDoS/инъекций).

### D3. Хранилище — PG-таблица `anticliche_cache` (singleton + JSONB)
- Причина: нужен JSON-список + метаданные (`source`, `source_url`, `fetched_at`, `version`, `last_status`) + инвалидация in-process кэша после ручной правки/форса; `bot_settings`-ключ перегружает конфиг-KV (RBAC/аудит/ParamSpec) и не даёт метаданных.
- In-process memoization (`services/anticliche_cache.get_rules()`) — детектор **не** делает PG I/O на каждый ответ; `invalidate()` после записи.
- Δ **SQLite DDL = 0** (SQLite остаётся v12); Δ каталога = **0** (флаг — env-only `ClassVar`).
- Идемпотентный DDL (`CREATE TABLE IF NOT EXISTS`, `ON CONFLICT DO NOTHING`), откат — `DROP TABLE` (данные кэша безопасны к удалению).

### D4. Совместимость с grep-тестом канона
- Промпт извлечения паттернов — код-константа в `anticliche_worker.py`, **не перечисляет** сами клише.
- Динамические фразы из PG никогда не попадают в `system`/`user`-сообщения и в промпт-константы.
- **F4 не меняет канон:** позиция F4 в контуре `F1→F2→F3→F4→F6` — no-op (нет `PREV_*`/`PROMPT_MIGRATIONS`/`plans/docs/canon/**`). Регресс-тест фиксирует байт-в-байт промпт-константы. Это осознанное отличие от прочих фич контура.

### D5. Фикс S10.22-4b
- Третьеличное правило `as_ai` дополняется comma-вариантами lookbehind фиксированной ширины (`(?<!\bон,\s)`, `(?<!\bона,\s)`, `(?<!\bоно,\s)`, `(?<!\bэто,\s)`, `(?<!\bлюди,\s)`, `(?<!\bчеловек,\s)`, `(?<!\bсебя,\s)`). Первое лицо («Я, как ИИ…») по-прежнему ловится.

### D6. Воркер и надёжность
- Недельный APScheduler-джоб по паттерну `lore_worker`/`memory_maintenance` (MemoryJobStore, `max_instances=1`, `coalesce`, jitter).
- Сбой источника/LLM/parse → **сохраняется предыдущий кэш**, пишется R17-safe `last_status` (без сырья/фраз).
- API: GET метаданных, POST форс-обновления, PUT ручной правки (RBAC глобального админа).

## Consequences

**Positive**
- ТЗ-цель («автообновляемый фильтр клише») достигнута без нарушения вето владельца и без scrubber'а.
- grep-тест тропов и «список в коде» сохранены; канон не дёргается (меньше риск канон-миграций).
- Детектор не получает I/O/латентности (in-process memo); fail-open без кэша — байт-в-байт прежнее поведение.
- S10.22-4b закрыт.

**Negative**
- Динамические правила могут быть шумными/ложными → редкие лишние регенерации (митигируется лимитом, дедупом, ручной правкой, флагом).
- Ещё одна PG-таблица и недельный фон (расход LLM раз в неделю — в бюджете фона).
- Нет «динамической подстановки в промпт» как в буквальном ТЗ — осознанное отклонение (документировано).

## Alternatives

- **A1. Подставлять `{dynamic_cliche_list}` в промпт Вербализатора (буквальное ТЗ)** — **отклонено**: нарушает вето владельца и grep-тест, ломает инвариант «список в коде».
- **A2. Scrubber/regex-рез клише** — **отклонено** (вето владельца 10.22; ломает грамматику).
- **A3. Заменить хардкод-список динамическим** — **отклонено**: теряем стабильность/детерминизм и канон; хардкод остаётся базой, динамика — надстройка.
- **A4. Хранить кэш в `bot_settings`-ключе** — **отклонено**: нет метаданных (source/version/last_status), перегрузка config-KV/RBAC/аудита; JSONB-таблица чище.
- **A5. PG-чтение прямо в детекторе** — **отклонено**: латентность на каждый ответ + нарушение «чистая функция».
- **A6. Принимать regex от LLM** — **отклонено**: ReDoS/инъекция/нестабильность; только литеральные фразы.
