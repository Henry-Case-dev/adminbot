# ADR-1024-18 — Устойчивость `smart_cache` к `database is locked`: паритет PRAGMA + bounded retry

- **Статус:** **Accepted** (Step 2 @Architect, 19.09.2026)
- **Фича:** F17 `sqlite-lock-resilience-round1024` (UPD4-C)
- **Тип:** backend/надёжность БД (инфраструктура)
- **Связано:** `round1024-architecture.md` §4 (инварианты), §5 (ступени); F2 `logging-infra-round1024` (соглашение `event=...`)
- **Задачи:** T-2322…T-2327

## Контекст

1. `SmartCache` (`services/smart_cache.py`) держит **собственное** `aiosqlite`-соединение к той же БД, что и основное `Database` (`services/database.py`). Основное соединение применяет `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout = 5000`, `PRAGMA synchronous=NORMAL` (`services/database.py:516-520`), а `smart_cache` — **нет** (`services/smart_cache.py:89-103`).
2. Прод-лог (UPD4-C): `services.smart_cache | smart cache: set failed | sqlite3.OperationalError: database is locked`. `_write` ловит исключение, пишет WARNING и делает **no-op** (`services/smart_cache.py:148-174`) — сгенерированный ответ **молча не кэшируется**.
3. Причина конкуренции: пока основной writer (и фоновые воркеры) держат запись, слабо-настроенное соединение кэша почти сразу получает `locked` (нет `busy_timeout`, WAL не гарантирован на этом соединении).
4. Ограничения раунда: `services/smart_cache.py` — **только F17 (эксклюзив)**; `services/database.py` — эталон, **не редактируется** (правило ступеней общих файлов, `round1024-architecture.md` §5). Δ DDL = 0, Δ каталога = 0; R17/R18; `parse_mode=None`; не ломать F1/F2/F7.
5. Прецеденты: `services/memory_rebuild.py:69-72,92-111` — локальные `_LOCK_RETRIES=3` / `_LOCK_BACKOFF=0.1`, детект `"locked" in str(exc).lower()`, экспоненциальный backoff. `services/database.py:589-594` (`initialize_retention`) — другой клиент БД сам применяет те же PRAGMA, не меняя `initialize`.

**Формулировка владельца:** *«лучше подождать, чем потерять запись»* — но ожидание обязано быть **ограниченным**, а потеря при исчерпании — **явной в логах**, не тихой.

## Решение

### D1. Паритет PRAGMA на соединении `smart_cache` (внутри `_ensure_db`)
При открытии соединения применяем ровно те же настройки и в том же порядке, что основной клиент (`database.py:516-520`): `PRAGMA journal_mode=WAL` → `PRAGMA busy_timeout = 5000` → `PRAGMA synchronous=NORMAL`. Значения — **локальные константы-зеркала** (`_BUSY_TIMEOUT_MS = 5000`), как принято в `memory_rebuild.py`. `journal_mode=WAL` — свойство БД, уже активное основным соединением, поэтому повтор безопасен.

*Почему не общий helper:* код-база придерживается конвенции локальных констант на модуль (прецедент `memory_rebuild`), а редактирование `database.py` запрещено ступенью раунда. Новый общий модуль дал бы вторую точку правды без реального устранения дублирования (database.py всё равно не смог бы им воспользоваться в этом раунде).

### D2. Bounded retry **только** на блокировку (в `_read` и `_write`)
- Повторяем исключительно `OperationalError` с `locked` в тексте; прочие исключения → прежняя обработка без повторов.
- Повторяется **вся транзакция** операции; перед повтором — best-effort `rollback` (ошибки игнорируются), чтобы частичная транзакция не «отравила» повтор.
- Лимит: `_LOCK_RETRIES = 3`, экспоненциальный backoff `_LOCK_BACKOFF=0.1` (паузы `0.1/0.2/0.4с`, суммарно ≤0.7с поверх `busy_timeout=5с`). Ожидание конечно и мало́.

### D3. Исчерпание — явный WARNING + счётчик, fail-open остаётся последним рубежом
- При исчерпании `_read` возвращает `None`, `_write` — no-op (поведение хендлера не меняется, кэш не роняет бота).
- Но пишется **структурированный** WARNING `event=smart_cache_lock_exhausted` с реальной причиной (`exc_info`), `op`, MD5-`key` и `attempts`, и инкрементируется in-process счётчик `smart_cache_lock_exhausted_total()`. Тихая потеря исключена.

### D4. Feature flag `SMART_CACHE_LOCK_RESILIENCE_ENABLED` (env-only `ClassVar`, default ON)
Гейтит **и** применение PRAGMA, **и** retry. OFF → ровно прежнее поведение (нет PRAGMA, нет повторов, прежний WARNING/no-op). Вне `param_catalog` → Δ каталога = 0. Прогрессивная раскатка не требуется (локальная обратимая фича).

### D5. `services/database.py` не трогаем
Эталон только читается. Общий connection-helper/унификация PRAGMA по обоим клиентам — **отложено** на будущий раунд (см. Альтернативы A2).

## Последствия

**Positive**
- Кратковременная блокировка → запись/чтение **не теряется**; устранена «тихая» потеря кэша (прод-симптом `smart cache: set failed … database is locked`).
- Настройки соединения кэша теперь консистентны с основным клиентом → меньше конфликтов в WAL-режиме.
- При реальном исчерпании проблема **видима** (лог `event=smart_cache_lock_exhausted` + счётчик), а не маскируется под miss/no-op.
- Успешный путь не изменился: те же возвраты и INFO-логи; нулевая добавленная задержка на быстром пути (PRAGMA — только при инициализации).
- Минимальный blast radius: только `services/smart_cache.py` (+ один `ClassVar`) + тесты; `database.py`, каталог, схема БД не затронуты. Δ DDL = 0.

**Negative**
- Худший случай на операцию — `busy_timeout` (5с) + ≤0.7с retry. Для кэша это может быть заметная задержка на hot-path; считается приемлемой (это оптимизация, но владелец явно предпочёл «подождать, чем потерять»), значение локализовано в одной константе.
- In-process счётчик теряется при рестарте (приемлемо: событие остаётся в логах).
- Дублирование константы `busy_timeout=5000` (в `database.py` и в `smart_cache.py`). Осознанно: устранение дубля требовало бы правки общего файла вне ступени раунда.

## Альтернативы

- **A1. Только PRAGMA, без retry** — **отклонено**: `busy_timeout` покрывает большинство случаев, но не случаи, превысившие таймаут; требование «запись не теряется» осталось бы невыполненным.
- **A2. Общий connection-helper / рефакторинг `database.py` под единый источник PRAGMA** — **отложено**: запрещено правилом ступеней (F17 эксклюзивно владеет `smart_cache.py`, `database.py` не редактируется в этом раунде); выносится как кандидат в backlog.
- **A3. Использовать соединение основного `Database` (DI/переиспользование)** — **отклонено**: циклическая/жизненная связанность (кэш обязан работать независимо, иметь собственный `close()` в `on_shutdown`, и не зависеть от момента инициализации основной БД).
- **A4. Неограниченный retry до успеха** — **отклонено**: риск подвесить hot-path кэша (R1 из `tasks.md`).
- **A5. Ретраить все исключения БД** — **отклонено**: маскирует неретраибельные дефекты, лишняя латентность; только `locked`.
- **A6. Уменьшить `busy_timeout` для кэша (fail-fast вместо паритета)** — **отклонено** в этом раунде: требование — **паритет** настроек с основным соединением; значение — единая константа для будущей настройки.
