## Кратко (без смягчений)

Ядро задачи сделано аккуратно: вкладка `mod_images` реально создана, группа `flags_module_images` без дублей переехала из «Прямых ответов», карточка и тумблер на месте, все счётчики каталога сошлись, пин-тесты обновлены в одном коммите, полный pytest на коммите зелёный. Но фича-флаг `IMAGE_MODULE_CARD_ENABLED` реализован **не по спеку**: гейтится только карточка, а не вкладка; а комментарии в трёх файлах **прямо врут** про то, что при OFF «ручка остаётся достижима в окне „Прямые ответы“». Тумблер оттуда вынесен этим же коммитом. Это не косметика — это неверное описание kill-switch, по которому оператор будет откатывать фичу в проде.

## Findings

### [High] Гейт `uiFlag` накрывает только карточку, но не вкладку
**Файл:** `web/app.js:1212-1220` (`visibleModules`), `web/app.js:2853-2874` (`applyRoute`), `web/app.js:796-803` (`initialRoute`)
**Проблема:** `visibleModules` фильтрует только карточку `mod_images`. Сама вкладка `mod_images` остаётся в `tabs` и достижима через маршрут `#/mod_images`: `applyRoute` проверяет только `canViewTab(tabId)` (RBAC), а `initialRoute()` восстанавливает последний маршрут из `sessionStorage['adminbot.route']`. Значит, при `IMAGE_MODULE_CARD_ENABLED=OFF` у пользователя, который ранее открывал `#/mod_images`, вкладка спокойно откроется после перезагрузки/диплинка.
**Почему это важно:** спека §3.2.5 прямо требует «Карточка/вкладка гейтятся `uiFlag('IMAGE_MODULE_CARD_ENABLED')`». Сейчас это полумеры: kill-switch закрывает витрину, но оставляет рабочий вход в раздел. Флаг заявлен как механика Progressive Delivery — он должен работать целиком, а не наполовину.
**Что сделать:** либо добавить проверку `uiFlag('IMAGE_MODULE_CARD_ENABLED')` в `visibleTabs`/`applyRoute` (для `mod_images` откатывать маршрут на `#/modules`), либо в спеке §3.2.5 явно зафиксировать, что гейтится только карточка, и убрать формулировку «вкладка недоступна». Молчаливое расхождение — недопустимо.

### [High] Ложные комментарии про достижимость тумблера через «Прямые ответы»
**Файлы/строки:**
- `config/settings.py:622-627` — «…сам тумблер остаётся достижим через окно «Прямые ответы» (не теряем ручку)».
- `web/api/routes.py:307-310` — «…карточка/вкладка скрыты из витрины; сам тумблер остаётся достижим через окно «Прямые ответы»».
- `web/app.js:1210-1211` — «…ручка остаётся в окне «Прямые ответы»».

**Проблема:** это фактически неверно. Этим же коммитом `flags_module_images` удалена из `TAB_MOD_DIRECT` (`services/param_catalog.py:2081-2084`), и группа теперь живёт только на `mod_images`. `activeModuleGroups` окна «Прямые ответы» строится из `groupedForTab(TAB_MOD_DIRECT)` — тумблера там больше нет. Итого при `IMAGE_MODULE_CARD_ENABLED=OFF` (карточка скрыта) главный тумблер модуля **недостижим нигде в UI**.
**Почему это важно:** спека §3.2.5 прямо оговаривает «тумблер остаётся достижим через `mod_direct`, чтобы не потерять ручку». Требование не выполнено, а комментарии создают ложную картину безопасности отката. Разработчик, читающий код через полгода, будет считать, что ручка есть. Это ровно тот тип скрытого техдолга, который нельзя пропускать.
**Что сделать:** определиться и привести в согласованное состояние спек/ADR/комментарии/код:
1. если ручка должна оставаться — вернуть группу (или её master-ключ) в окно «Прямые ответы» (например, отдельной группой/строкой) и добавить тест;
2. если нет — вычеркнуть из `spec.md` §3.2.5 и из комментариев ложную фразу про «Прямые ответы» и задокументировать, что при OFF ручка недоступна (только env/kill-switch обратно).
Сейчас расхождение «спека ↔ ADR ↔ комментарии ↔ код» — красный флаг.

## Findings (итерация 2)

### [Medium] Новая ветка `_flagTabHidden` в `applyRoute` обходит RBAC-гейт целевого экрана
**Файл:** `web/app.js:2877-2886` (`applyRoute`), `web/app.js:1429-1435` (`visibleTabs`)
**Проблема:** ветка kill-switch стоит **до** проверки `!canViewTab(tabId)`. При `IMAGE_MODULE_CARD_ENABLED=OFF` диплинк `#/modules/images` безусловно переводит на `#/modules` и **не перепроверяет `canViewTab('modules')`** (а `replaceState` не генерирует `hashchange` → повторного `applyRoute` не будет). Пробник на боевом коде:
```
OFF + canViewTab=false -> route: #/modules  activeTab: modules
ON  + canViewTab=false -> route: #/        activeTab: status   (корректно)
```
То есть при включённом kill-switch RBAC работает, а при выключенном — пользователь без прав на раздел «Модули» попадает на витрину, минуя штатный редирект `#/` с тостом.
**Почему это важно:** это регрессия порядка проверок доступа, внесённая именно фиксом. Влияние ограничено (гейт клиентский, сервер по-прежнему фильтрует параметры; показываются статические карточки), но именно в состоянии отката (OFF) доступ-контроль деградирует — а откат и есть сценарий, ради которого kill-switch существует. Непоследовательность ON/OFF в одной и той же функции недопустима.
**Что сделать (одной правкой):** выстроить порядок так, чтобы RBAC-проверка имела приоритет: сначала `!canViewTab(tabId)` → `#/`, и только затем `_flagTabHidden(tabId)` → `#/modules`; либо после присваивания `route='#/modules'` добавить `if (!this.canViewTab('modules')) { route='#/'; tabId=routeToTab(route); }`. Добавить в `tests/js/round1024_image_module_test.js` негативный кейс «OFF + без доступа → `#/`» (сейчас стаб всегда `canViewTab(){return true}` и дыру не ловит).
