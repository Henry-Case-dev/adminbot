## 5. Root cause (evidence)

1. **Deploy snapshot per release without lifecycle.** Harness creates a full DB copy on every deploy:
   - `/tmp/deploy_main.sh:48` → `backups/pre_deploy_258199_<ts>.db`;
   - `/tmp/remote_258193.sh:42` → `/tmp/predeploy-258193.db`;
   - `/root/d258179.py:32` → `predeploy-258179.db`.
   Releases 258175→258205 (9–15.11) left 18 full copies, 44G.
2. **Official cleanup blind spot.** `python manage.py disk audit` classifies all deploy copies as `other` (40 files / 40.3GiB); `disk cleanup` dry-run returned **candidates=0**. `services/disk_retention.py:344 prune_deploy_backups()` exists but is never called; `plan_cleanup()` (`:433`) covers only daily/facts/JSONL; `services/memory_backup.py:194 _rotate()` prunes only `local_database_*`/`memory_rebuild_*`.
3. **No journald retention config.** `/etc/systemd/journald.conf` had no `SystemMaxUse`/`MaxRetentionSec`; journal reached 905M with files back to 2024/28.10. Fixed on host (7d/500M → 385.7M).
4. **Research/migration leftovers.** VMQ corpus copies 2×3.1G under `/root`, migration staging 3.2G under `/var/lib` from 29.10.
5. Not causes: Docker (all active, 0B reclaimable), `/var/log/syslog` (158M), inode pressure (3%), swap (legit).

Forecast before cleanup: +6.9 GB/day in the observed 6.7-day window (projected 193.5 GiB/30d) — the growth is structural, not a one-off.
