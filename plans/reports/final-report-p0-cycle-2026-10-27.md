# Финальный отчёт владельцу — Speech/Fact-check/P0 DELTA цикл (27.10.2026)

Отчёт по коррективам 25–26.10: P0 CORRECTIVE (речь), P0 FACTCHECK (фото/альбомы),
P0 DELTA (маршрутизация анализа и память). Простым языком, по структуре,
запрошенной владельцем. Версия на production в конце отчёта.

## 1. Почему бот отвечал «и че тут проверять, пустоту?»

Разобран реальный случай: пересланный пост — альбом из 10 фотографий, текст поста
(2846 символов) лежал только на первом фото, пользователь ответил «Фактчек» на девятое
фото. Между сохранением альбома и командой прошло 84 секунды, а буфер альбомов жил
60 секунд и хранил только одну подпись. Буфер опустел → бот увидел «пустое» сообщение
и ушёл в ветку «проверять нечего», не посмотрев ни в сохранённые сообщения, ни на
изображения. Причина доказана production-данными (логи + база), не догадками.

## 2. Как исправлена обработка фото, альбомов и пересылок

- Публикация восстанавливается целиком из постоянного хранилища: все элементы альбома,
  подпись с любого элемента, отдельный текст поста, связь картинок с текстом.
- Ответ на любое фото поста = проверка всего поста (ответ на фото — только точка входа).
- Если в целевом сообщении нет утверждения — бот проверяет окружение: соседние
  сообщения, цепочку ответов и до 300 сообщений вокруг (механизм широкого контекста
  уже существовал, но был выключен — теперь включён по умолчанию, тумблер в
  «Модули → Фактчек»).
- Одиночная фотография без текста — распознаётся через существующий Vision/OCR.
- Различаются честные состояния: «есть фото без текста», «альбом неполный»,
  «распознавание не готово», «на изображении нет проверяемого утверждения»,
  «данных нет». Только последнее — «проверять нечего», и с объяснением, что проверено.
- 15 регрессионных сценариев покрыты тестами; независимое ревью — Approved
  (6 блокеров из первого ревью устранены и перепроверены).

## 3. Алиасы: как решена проблема путаницы имён

Раньше имя человека в разных местах бралось из разных источников: из Telegram-ника,
из старой записи в истории, из памяти — поэтому один человек назывался по-разному,
а бот путал автора цитаты с адресатом.

Теперь одно правило для всего пути: имя всегда определяется по Telegram user ID,
приоритет — алиас чата → общий алиас → нынешний ник → @имя → номер. Смена имени
действует сразу, без перезапуска. Старые записи не переписываются: боту добавлено
указание брать актуальное имя из списка участников по номеру, а история остаётся
доступной для поиска по старым именам.

Проверено по 11 пунктам независимо (Approved): приоритеты, живое применение без
рестарта, «мои сообщения» = автор запроса, автор цитаты ≠ адресат, два одинаковых
имени не сливаются, «Гипербореец» — историческое имя в сохранённых сообщениях, а
действующий алиас «Макс» доходит до модели (проверено в реальном payload).

## 4. Речь: что исправлено и как проверено

- Сложные запросы («проанализируй мои сообщения») снова уходят в разбор: правило
  переписано по смыслу (материал → разбор, тон не меняет тип действия), синонимы
  нормализуются. Стабильность подтверждена живыми прогонами; на грубой форме
  «проникся тоном вместо сути» была нестабильность — правило усилено
  разделением тона и сути, финальный прогон чистый.
- Пустые вступления («давай посмотрим», «сейчас разложу») устранены: 5 из 8 → 0 из 6.
- Формула «начинай с вывода» снята по вашему указанию — NO_META теперь запрещает
  только служебные анонсы и метакомментарии; форма ответа свободная.
- Полный Personality Core (3294 символа) доходит до модели целиком — скрытая обрезка
  убрана, запрет квот инструкций соблюдён (отдельный guard-тест).
- FREQUENT берётся из живой настройки; мат — естественный, без вставок и без
  обязательных примеров. Остаточная вариативность выразительности задокументирована
  как статистическая, не блокер (условия приёмки зафиксированы отдельным документом).
- Старые выдуманные истории помечены provenance и больше не выдаются за факты;
  собственные прошлые ответы исключены из фактического RAG.

## 5. P0 DELTA: понимание запросов и память (выкачено в 2.58.134)

- Готовая история больше не подменяет ответ на анализ — только на заказанный рассказ.
- Период поиска выразим в инструментах (год от/до), доходит до SQL.
- Покрытие истории честное: сэмплирование по всему периоду, «показано X из N»,
  фильтры до ограничения выборки.
- Субъект анализа — по Telegram ID; при неоднозначности — честный отказ.
- Пересказы памяти помечены происхождением и не считаются дословными свидетельствами.
- Убран последний словесный хардкод в резервном классификаторе (12 триггеров).
- Ревью подтвердило: ни одного нового шаблона, ни одного нового слоя или лишнего
  вызова модели (12/12 пунктов анти-шаблонного стража).
- Живая проверка на проде: сценарий «как менялся человек за 2022–2026» теперь даёт
  развёрнутый разбор (1627 знаков) с честной оговоркой о глубине архива, вместо
  заглушки на 125 знаков.

## 10. ASAP 5 — мультимодальность: ностальгия, медиа, Vision, картинки (27.10.2026, 2.58.135)

ASAP 5 — последняя большая волна очереди. Ниже — 10 объяснений из §29 источника,
затем честный остаток.

**1. Почему Ностальгия публиковала бессвязные воспоминания.** Повод выбирался
механически: годовые сводки «назад» публиковались без содержательного повода,
слабые и случайные кандидаты вытягивались из строк памяти, а модель досочиняла
связь между несвязанными фактами. Пересланные новости попадали в воспоминание
как личное событие участника, без пометки источника.

**2. Как устранена механическая склейка.** В канон введён прямой запрет «не
склеивай несвязанные события и не вытягивай смысл из случайных фактов» + новый
страж самоотказа до публикации: явные вердикты «это не та история / вспоминать
нечего» теперь означают, что публикация не происходит (журнал: reason=self_decline,
дневной лимит не тратится, бот молчит). Ироничные формы («нечего, кроме…») не
блокируются; запрет вымысла сохранён. Инцидентная форма воспроизведена тестом:
такой текст не публикуется.

**3. Как учитывается текущая беседа.** Воспоминание публикуется только при
интересной связи с текущим разговором или когда история сама заслуживает
внимания — директива владельца дословно в обоих канонах. Отбор идёт по
существующим механизмам (история, Golden Facts, старые сообщения) с прежними
весами и порогами, без нового вызова модели.

**4. Какие типы медиа распознаются.** Матрица возможностей построена на
существующем определителе типа. Было: фото, изображения-документы, статические
стикеры. Добавлено: GIF/Telegram-анимации, анимированные и видео-стикеры — по
кадру-обложке с честной маркировкой «движение не анализируется»; превью обычных
видео и видеосообщений — новый тип превью. Источник GIF/видео честно
регистрируется без анализа. Типы можно выключать по чату (см. п. 8).

**5. Как обрабатывается ожидание Vision.** Статус медиа на каждой поверхности —
фактический: пока анализ идёт — «ещё обрабатывается» с приглашением
переспросить, без обещаний самостоятельной отправки; «на фото нет текста» —
отдельное состояние, не путается с ожиданием; ошибка, невозможность, выключенный
модуль, недоступный файл — различимые честные состояния. «Последний анализ» в
витрине больше не подменяется результатом чужого чата (атрибуция per-chat).
Завершение анализа во время ожидания будит ожидание и отдаёт честный результат
или ошибку; двойного запуска распознавания нет.

**6. Как устранены противоречия о возможностях инструментов.** Найден реальный
конфликт: при временном сбое провайдера модель получала «не обещай», но
инструмент генерации всё равно оставался анонсирован — противоречивые входы
давали противоречивый ответ. Теперь состояние возможности и доступность
инструмента считаются из одних источников (модуль, ключ, квота, последние
исходы, заявленная способность провайдера): недоступно — честный отказ с кодом
причины. Редактирование картинок получило отдельную возможность image_edit из
тех же источников.

**7. Как работает редактирование изображений.** К Direct Chat подключён
существующий внутренний редактор (edit_image) как обычный инструмент: цель —
только сообщение того же чата; если провайдер правку не умеет — честный отказ,
«генерация вместо правки» запрещена. Второй редактор и второй набор провайдеров
не создавались.

**8. Какие настройки появились в админке.** На существующей вкладке Vision —
группа «Типы медиа»: 5 тумблеров (фото и изображения-документы, статические
стикеры, GIF и анимации, анимированные и видео-стикеры, превью видео и
видеосообщений), настройки отдельных чатов, заводски включены. Выключенный тип —
медиа честно не распознаётся. Плюс диагностика Vision из существующих записей
(исправлен всегда нулевой счётчик неудач).

**9. Какие реальные проверки пройдены.** Интеграционные матрицы — 66 тестов
(медиа×Vision×Direct Chat 22, фактчек целого поста, картинки×админка 14+2,
ностальгия 16, сквозные 5). Регрессия затронутых швов: 265+324+60+158 passed;

## 11. POST-ASAP5 — корректива технических ответов: уточнения, расчёт, поиск, выдумки (27.10.2026, 2.58.136)

_Отчёт: 27.10.2026, 21:35 (UTC+12). Post-ASAP5: [##################--] 24/27 обязательных требований карты VERIFIED; 3 формально открыты — см. «Что осталось»._

**1. Почему бот не понимал уточнения.** В каноне L1 не было правила, что новое
сообщение владельца меняет постановку задачи: уточнение читалось как ещё один
аргумент поверх старого плана. В L1 добавлена секция «ИЗМЕНЕНИЕ ЗАДАЧИ
И ВОЗРАЖЕНИЯ»: перечитывание актуального сообщения, различение
уточнение/возражение/новый вопрос, снятые условия больше не считаются
обязательными. Живой прогон: после «отбросим конструкцию» бот сразу переходит
к расчёту с новыми условиями, бесконечных переспрашиваний нет (два независимых
прогона).

**2. Почему ссылался на отменённые ограничения.** Та же причина: старое условие
(«плата не позволяет») оставалось в силе, потому что в плане его никто не
снимал. Секция intent-update прямо запрещает держать снятые условия
обязательными и вводить ограничения, которых владелец не устанавливал; в живом
прогоне после уточнения бот считает по абстрактным пределам (контроллер,
адресные линии, шина), не возвращаясь к снятому ограничению.

**3. Почему не выполнил элементарный расчёт сразу.** Модель спорила об
ограничении вместо вычисления: различения «математическая оценка / теоретическая
архитектура / физическая реализация» не было ни в одном слое payload. В канон
Writer добавлена секция «ТЕХНИЧЕСКИЕ РАСЧЁТЫ И ГИПОТЕЗЫ»: расчёт с заданными
параметрами выполняется, несовместимость конкретной платы упоминается отдельно
и расчёт не отменяет. Живой прогон: «4 чипа по 32 бита — это 128 бит суммарной
ширины, а не четыре канала», арифметика сходится в обоих прогонах.

**4. Почему не использовал поиск.** Канон L1 вообще не упоминал web_search и
смещал планер к пустому набору возможностей, а без имени инструмента в плане
поиск механически невозможен. Правило 4 L1 переведено на новую редакцию:
существенная зависимость ответа от внешних сведений (современные продукты,
новые архитектуры, спецификации производителей) → запросить поиск; известные
формулы и расчёты с заданными параметрами → без поиска. Живой прогон: на вопрос
о современном продукте поиск реально сработал, на вычислениях не стрельнул —
обе стороны правила подтверждены.

**5. Почему придумал объяснение Crescent Island.** Ни один носитель не различал
«известное / результат поиска / проверенный расчёт / предположение / догадка»,
и модель заполняла пробел знания правдоподобной архитектурой. Секция Writer
теперь требует отделять источник каждого утверждения и запрещает заполнять
пробелы жаргоном; гипотезы и оценки разрешены, но помечаются. Живой прогон:
характеристики Crescent Island названы из результатов поиска с атрибуцией
(Hot Chips 2026, публичный релиз 12.10.2026, 160/480 ГБ LPDDR5X, 350 Вт,
32 Xe3P), выдуманной архитектуры нет, противоречие 160→480 ГБ подсвечено,
а не замолчано.

**6. Что исправлено в L1 и выборе инструментов.** Канон L1: секция intent-update
(W1) и правило 4 новой редакции (W2) — семантика «когда нужен поиск», без новых
инструментов и роутеров. Дублирующий Fact-check не создавался: существующий
фактчек-аналитик по-прежнему обязан искать по real-world тейкам; недоступный
инструмент резолвится честно с кодом причины, из анонса вычищается.

**7. Как теперь исправляются ошибочные ответы.** Прежний ответ модели — контекст,
а не доказательство; возражение с проверяемыми сведениями → перепроверка
доступными средствами и пересмотр вывода без защиты ошибки и без обязательного
многословного извинения. Существующая защита от self-echo не тронута (тесты
PASS). Живой прогон: «Да, x8, признаю — накосячил», разговорность сохранена.

**8. Какие существующие компоненты переиспользованы.** Только существующие
носители по лестнице ADR-1013-3: канон L1 (секция intent-update + правило 4),
tool-phase канон (секция «ПОИСК И НЕПОДТВЕРЖДЁННЫЕ ХАРАКТЕРИСТИКИ»), канон
Writer (секция техрассуждений), план-блок фокуса Writer, честная пометка
недоступной возможности, low-confidence гейт. Новых tools/слоёв/LLM-вызовов
нет; миграция канонов — штатная лестница, в 2.58.136 мигрированы три ключа,
11 пользовательских кастомов сохранены.

**9. Какие проверки пройдены.** Контрактные тесты W1+W2 (18+24 PASS; фокусный

## 12. FACTCHECK POST-RELEASE — факт-чек работает и без поиска (28.10.2026, 2.58.139)

Коротко о коррективе Fact-check (владельческая задача от 28.10.2026): поиск —
вспомогательный инструмент, а не условие работы функции. Реализовано в волнах
W1+W2 (кандидаты `98a4254f` / `065fa22f`, ревью Approved), выкачено штатным
релизом **2.58.139** (deployed `95e6c7c9`), живая проба на задеплоенном коде —
8/8 PASS. По пунктам:

**1. Почему раньше анализ прекращался.** В `factcheck_service` была серверная
ветка «пустой evidence → вердикт `insufficient_evidence`» без единого вызова
LLM-аналитика: поиск вернул пусто/ничего пригодного → анализ даже не
запускался, вербализатор сочинял текст про несостоявшийся поиск. Это и было
прод-симптомом 28.10 («проверять нечего»).

**2. Как теперь работает без внешнего поиска.** Аналитический этап выполняется
всегда. При пустом evidence в payload добавляется серверная секция
`<analysis_context>`: статус поиска по честной таксономии, разрешение
логической/математической/технической проверки и анализа внутренней
согласованности, запрет выдуманных источников. Модель проверяет утверждение по
самой формулировке, контексту беседы, истории, памяти и общим принципам.

**3. Подтверждённые факты vs самостоятельные выводы.** Каждое основание
помечается в `uncertainty.basis` (evidence — внешний источник; reasoning —
расчёт/принцип; assumption — предположение). Положительный вердикт без внешнего
evidence и без пометки основания автоматически понижается до честного
«недостаточно данных» с оговоркой `unbacked_positive` — «вспомнил цифру» не
проходит за «подтверждено», а расчёт по заданным числам с basis остаётся в силе.
Cited-источники фильтруются по allowlist текущего прогона: выдуманный `ev-N`
не может стать ссылкой.

**4. Удалённые блокирующие зависимости.** (а) серверный отказ при пустом
evidence; (б) системная команда аналитику «нет результатов → insufficient»;
(в) кеш готовых вердиктов как источник ответа; (г) учёт пустой выдачи как
«отказ провайдера» (теперь это отдельная причина `empty_results`/`irrelevant`);
(д) принудительная композиция ответа в renderer'е.

**5. Сохранённые fallback.** Каскад поисковых провайдеров (Tavily→Exa→DDG),
fallback-промпт LLM, детерминированный текст вербализатора при отказе LLM
(разбор частей не теряется), plain-деградация renderer'а, доставка
send_chunked_reply, идемпотентность и защита от двойной отправки. Обязательных
проверяющих LLM-агентов не добавлено.

**6. Кеш вердиктов удалён во всех маршрутах.** Temporal-кеш и legacy-кеш
(обработчик, оркестратор envelope/legacy, модуль temporal_factcheck) —
удалены; инертный гейт, env-флаг, мёртвые TTL-настройки и slug-регистрация
сняты (W2); grep-аудит кандидата — 0 скрытых read/write-путей; `cache_hit`
в схемах оставлен только для исторических записей, всегда False. Живая проба:
повтор идентичного тезиса — новый полный прогон, `cache_hit=0` в обеих
run-записях. Исторические журналы прошлых проверок сохранены и доступны.

**7. Почему возникало «поиск недоступен».** Классификатор считал ЛЮБОЙ нулевой
результат «поисковики недоступны» (`search_failed`), включая «ответили, но
ничего не прошло фильтр релевантности». Вербализатор получал этот технический
статус и рассказывал про недоступный поиск. Теперь причины машинно различаются:
`provider_error/timeout/empty_results/irrelevant_results/budget`; «поиск
ответил, но пригодных материалов не дал» — отдельное состояние, и это не
технический сбой и не «фактов не существует».

**8. Частичная поисковая выдача.** Уже полученные доказательства сохраняются,
если следующий запрос упал (F5); несовместимые/нерелевантные строки не
затирают найденное; при наличии evidence контур проверки идёт прежним
проверенным путём (дифф-ревью: байт-идентичный flow при наличии evidence).
Дополнительно снят источник ложных отрицаний relevance-фильтра для
двухсловных запросов (floor=1), мусор фильтр по-прежнему не пускает —
окончательная оценка пригодности за аналитиком.

**9. Реальные и офлайн-проверки.** Офлайн: новая F-матрица 37 тестов (все
PASS) + 12 тестов W2 + целевые фактчек-сьюты (630 passed; 1 pre-existing сбой,
воспроизводится на базе вне скоупа) + сверка полного прогона с базой
(множества сбоев идентичны базе). Живо, на задеплоенном 2.58.139: проба с
реальным LLM и staged-пустым поиском — 8/8 PASS (аналитик выполнился,
`<analysis_context>` в payload, содержательный ответ с calendar-math разбором
и честным basis, директива ровно 1×, повтор = свежий прогон `cache_hit=0`,
ни одного выдуманного источника; реальный Telegram не использовался — FakeBot,
прод-БД и чаты не тронуты). Честные границы: прогоны с моками НЕ доказывают
доступность реальных поисковиков; отсутствие ошибок в тестах не доказывает
качество всех возможных LLM-ответов; реальная частота ложных отрицаний
relevance-фильтра на живой поисковой выдаче — наблюдение дальнейших живых
прогонов (не блокер, карта: FC-05B).

200/2.58.139, NRestarts 0, journal clean, deltaDDL=0, канон-миграции не
требовались (выполнены на 2.58.136).
