## Root cause (reproduced)

`graph_facts_fts` is an external-content FTS5 table
(`content='graph_facts', content_rowid='id'`). FTS5 does **not** observe
writes to the content table. Every ordinary writer in `services/database.py`
explicitly mirrors its DELETE/UPDATE (verified: all 6 `DELETE FROM graph_facts`
sites delete the FTS row first; both text-`UPDATE`s delete the FTS row before
the UPDATE). The leak is in the dossier rollback restore path:

`services/dossier_rebuild_jobs.py::restore_user_snapshot` used
`INSERT OR REPLACE INTO graph_facts` and only afterwards ran
`DELETE FROM graph_facts_fts WHERE rowid = ?` + `INSERT ...`.

`INSERT OR REPLACE` is a **hidden DELETE**:

1. **Non-PK UNIQUE conflict** — `idx_graph_facts_history_import
   (chat_id, fact, message_timestamp) WHERE origin='history_import' ...`:
   REPLACE deletes the conflicting row with a *different id*. The old code's
   FTS phase only touched the snapshot row's own id, so the implicitly deleted
   row keeps its FTS/docsize entry forever → `docsize` > `graph_facts`,
   `MATCH` returns a non-existent id (prod symptom class).
2. **PK text replacement**: `DELETE FROM graph_facts_fts WHERE rowid=?` after
   the content row was replaced reads the *new* text from the content table,
   removes the new tokens (usually absent) and drops the docsize row, but the
   **old tokens stay in the inverted index** forever. A subsequently (correctly)
   deleted fact is still returned by `MATCH` on its old wording.

In-memory probe (real `DatabaseService`, base code):

```
insert A (history_import, ts)            -> facts=1 docsize=1
restore snapshot id=9001, same UNIQUE    -> facts=1 docsize=2 orphan=1
                                            (A gone; FTS row of A leaked)
insert fact "старый факт про трактор"
restore same id, fact="…комбайн"         -> MATCH 'трактор' = [id] (stale)
delete_graph_fact(id)                    -> MATCH 'трактор' = [id] (stale)
```

## Chosen fix — code only, no DDL / no migration

No schema change, `user_version` unchanged, no triggers required (DDL is not
needed to remove the cause).

1. `services/dossier_rebuild_jobs.py::restore_user_snapshot`
   - content REPLACE + FTS reconcile now run in **one** `write_transaction`
     (no window "content updated, FTS not");
   - reads `{id: fact}` before and after the REPLACE and reconciles exactly the
     diff: vanished ids → FTS5 `'delete'` with the **old explicit text**;
     changed ids → `'delete'` old text + INSERT new text; new ids → INSERT;
   - unchanged rows are not touched (idempotent; second run with the same
     snapshot is a no-op).
   - `'delete'` with explicit old text is the documented external-content
     command (plain `DELETE ... WHERE rowid` cannot remove text that is no
     longer in the content table).
2. `services/memory_rebuild.py` — new maintenance primitives:
   - `inspect_graph_facts_fts(db)` (read-only): counts
     `graph_facts` / FTS view / `graph_facts_fts_docsize`, orphan and missing
     docsize rowids (+samples), FTS5 `'integrity-check'`
     (`skipped_readonly` on a `mode=ro` connection) and
     `PRAGMA integrity_check`;
   - `repair_graph_facts_fts(db)`: idempotent; if divergence (or
     `PRAGMA integrity_check` names `graph_facts_fts`) runs the documented
     FTS5 `'rebuild'` in the single-writer transaction and returns
     `{rebuilt, before, after}` ("было/стало"). Second run → `rebuilt=False`.
3. `manage.py` — existing `memory` group:
   - `python manage.py memory fts-check --db <path>` (read-only, rc=1 on
     divergence);
   - `python manage.py memory fts-repair --db <path>` (rc=0 when final `ok`).
   No new daemon, scheduler, subsystem, or DB.

## Limitations / honesty

- The writer defect is deterministically reproduced and fixed. The 20
  historical prod orphan rows are consistent with this hidden-REPLACE class,
  but retroactive attribution of each row to a specific admin rollback cannot
  be proven; the maintenance rebuild is the bounded recovery and the
  regression test prevents recurrence.
- `inspect` detects count/rowid divergence and FTS/DB structural integrity.
  Stale inverted-index tokens with a *consistent* docsize are not directly
  countable through the FTS5 API; the repair `'rebuild'` removes them and the
  writer test proves new writes no longer create them.
- vec (`graph_facts_vec`) is out of scope and untouched; no version pins,
  prompts, web/** or excluded modules were modified.
