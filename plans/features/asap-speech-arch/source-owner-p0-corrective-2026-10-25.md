# P0 CORRECTIVE - Завершить проверку, устранить блокеры деплоя и исправить алиасы

Продолжить текущий P0 без нового эпика и без дополнительных Human Gate.

Production остаётся на 2.58.130. Аудиты выявили реальные дефекты, но workflow остановился на отчёте вместо их устранения.

**Владелец не запрашивал остановку после аудита. Требуется завершить исправления, пройти Reviewer и выполнить штатный production deployment.**

## 1. Устранить технические блокеры релиза

По последнему отчёту:

- L1 направляет два исходных запроса в `casual/compact`, а проверочный сценарий ожидает `research`.
- Запущенный серверный harness не соответствует закоммиченному.
- Production worktree содержит 13 изменённых файлов с неустановленным происхождением.
- RAG/Memory отсутствуют в проверочном payload.
- FREQUENT не проверен в нужной конфигурации.
- Сохраняются мета-вступления и структурированные ответы.
- В старом `lore_stories` присутствуют неподтверждённые события.

Это инженерные проблемы, а не вопросы для владельца.

**DevOps и Builder должны устранить их самостоятельно.**

### 1.1. Исправить проверку L1

Разобраться, почему явный запрос "проанализируй мои сообщения в чате" классифицируется как `casual/compact`.

Не подменять реальные решения L1 искусственно установленным режимом в единственной приёмочной проверке.

Если пользователь просит исследовать историю сообщений, должен быть доступен соответствующий глубокий анализ.

При этом глубина внутреннего анализа не определяет длину ответа. Подробная проверка истории может заканчиваться короткой репликой.

Исправить саму семантику выбора режима, не добавляя хардкод конкретных слов и фраз.

Проверить оба варианта: непосредственный выбор L1 и принудительно выбранный исследовательский режим как отдельный диагностический сценарий.

### 1.2. Исправить проверочный стенд

Использовать проверенный harness из того же commit, что и исправляемый код.

Устранить расхождение между исходниками, исполнением и счётчиками результатов.

Проверить реальные payload с RAG, Memory, актуальным Core и выбранным Expression.

Не принимать результаты, полученные в неэквивалентной конфигурации.

### 1.3. Разобраться с production worktree

Исследовать 13 изменённых файлов.

Определить происхождение изменений и отличия от актуального репозитория.

Не выполнять слепой `git reset --hard`, удаление файлов или перезапись production-конфигурации.

Сохранить необходимые production-изменения, согласовать их с целевым релизом и обеспечить воспроизводимое развёртывание.

### 1.4. Проверить реальные исправления

Повторить офлайн-LLM-пробы с корректными режимами L1, RAG, памятью, Expression и Personality Core.

Проверить оба исходных проблемных запроса, а также короткие повседневные сообщения.

При подтверждённых дефектах исправить их в действующем P0 и повторить проверку.

Не проводить тестовые отправки в рабочие Telegram-чаты.

## 2. Исправить алиасы во всём пути обработки сообщений

**Отдельный обязательный дефект P0: бот продолжает неправильно использовать имена участников.**

Ранее обнаруженная проблема:

`AliasResolver` и его `_aliases`/`_cache` могут сохранять устаревшее состояние. Direct Chat не всегда использует настройки алиасов конкретного чата.

Не считать эту проблему исправленной без проверки runtime.

### 2.1. Единые правила

Идентичность участника определять по Telegram user ID.

Для отображаемого имени использовать следующий порядок:

1. Алиас конкретного чата.
2. Глобальный алиас.
3. Актуальный никнейм пользователя.
4. Telegram username без `@`.
5. Достоверные сведения памяти только как последний fallback, если актуальных данных нет.

Не использовать клиентские имена локальных Telegram-контактов как авторитетный источник.

Не путать автора, адресата, автора цитируемого сообщения и участников обсуждаемой истории.

После изменения алиаса новый вариант должен применяться без рестарта.

Старый алиас не должен продолжать использоваться для текущего обращения из-за кеша или памяти.

Исторические сообщения и старые записи памяти массово не переписывать.

### 2.2. Проверить весь runtime

Проверить:

- `AliasResolver`.
- Загрузку глобальных алиасов.
- Загрузку алиасов конкретного чата.
- Инвалидацию кеша после изменения настроек.
- Direct Chat.
- L1/L2.
- Observer и Initiative.
- Контекст reply.
- Personality Core и формирование prompt payload.
- Memory и GraphRAG.
- Профили пользователей и досье.
- Writer и окончательную генерацию ответа.

Не создавать новую независимую систему имён.

Использовать существующие механизмы, устранив конкурирующие источники разрешения имени.

Память должна сохранять возможность поиска по старым именам и алиасам, но при текущем обращении использовать актуальное каноническое имя по Telegram ID.

### 2.3. Обязательная проверка алиасов

Провести изолированные проверки:

- Локальный алиас имеет приоритет над глобальным.
- Глобальный алиас имеет приоритет над никнеймом.
- Никнейм имеет приоритет над username.
- Изменение алиаса применяется без рестарта.
- Старый кеш не возвращает устаревшее имя.
- Исторические упоминания остаются доступными для поиска.
- Ответ на reply адресуется правильному человеку.
- Упоминание третьего лица не подменяет адресата ответа.
- Два человека со схожими именами не объединяются в одного.
- Старое имя из RAG/Memory не вытесняет актуальный алиас.
- Обычный чат, analysis, Initiative и другие пути генерации используют одинаковые правила.

Проверить фактический LLM payload: правильное имя должно доходить до модели, а не только отображаться в админке.

Отдельно установить источник имени "Гипербореец" в показанном ответе и проверить его соответствие актуальному алиасу соответствующего Telegram ID.

Не угадывать ожидаемое имя по тексту сообщения - получить его из действующих настроек.

## 3. Доделать память и речевое поведение

Исправить оставшиеся проблемы из отчёта:

- Убрать лишние мета-вступления.
- Устранить обязательную структурированность ответов там, где пользователь её не просил.
- Проверить применение полного актуального Core без произвольного бюджетного обрезания.
- Проверить FREQUENT в настоящем режиме FREQUENT.
- Обеспечить участие RAG/Memory в релевантных сценариях.
- Не допускать превращения пересказов L2 в самостоятельные доказательства.

Особое внимание уделить старым записям `lore_stories`.

Исправление генерации новых воспоминаний не обезвреживает уже сохранённые выдумки.

Проверить, что существующий provenance-механизм не позволяет неподтверждённым старым историям становиться фактическими свидетельствами.

Для обнаруженных загрязнённых записей использовать точечное исправление достоверности или исключение из фактического извлечения с сохранением необходимых исторических данных.

Не проводить массовую очистку памяти, не удалять многолетнюю историю чатов и не вводить новые искусственные квоты.

## 4. Reviewer и production deployment

После исправлений Reviewer должен подтвердить:

- Исходные проблемные запросы проверены на корректных маршрутах.
- Реальный payload соответствует выбранным режимам и настройкам.
- Нет неподтверждённых дат и цитат в итоговых ответах.
- Краткость достигается естественным поведением, а не обрезанием текста.
- FREQUENT работает без обязательных few-shot-примеров.
- Алиасы корректно разрешаются по Telegram ID.
- Изменение алиаса действует без рестарта.
- Fallback, retry и существующие технические ограничения сохранены.
- Новые исправления не нарушили ранее закрытые требования P0.

Если проверка не проходит, Reviewer возвращает конкретный дефект Builder/DevOps на исправление. После исправления проверка повторяется.

**Не завершать workflow отчётом о технических блокерах, пока существуют доступные действия по их устранению.**

Не учитывать owner_live_checks как обязательное условие инженерного DONE, процента выполнения или деплоя. Живые проверки владельца остаются внешним последующим наблюдением.

При этом не обходить реальные инженерные проверки ради формального DONE.

Если деплой технически небезопасен, сначала устранить причину, а не игнорировать её.

После успешного Reviewer выполнить штатный production deployment, проверить версию, healthcheck и ошибки запуска.
