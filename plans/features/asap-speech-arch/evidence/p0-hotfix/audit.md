## 1. Реальный путь запроса «проанализируй меня / Ринтаро»

**Отдельного «аналитического» функционального writer'а в коде нет.** Запрос идёт обычным Direct-путём и обрабатывается теми же двумя стадиями, что и болтовня:

```
сообщение
  → direct_chat_service._handle_direct (tool_phase)
      • system: CHAT_SYSTEM_PROMPT (канал) + <Persona>/<Character_Rules> + <Style_Requests>
        + <Speech_Understanding> (+ Lessons)
      • user:   <Global_Context> (L2 + L1 + хвост) / <RAG_Memory> / <Target_User> / <chat_lore>
  → L1 Planner (JSON-план: action, response_act, extent, tone, structure)
  → ResponsePlan → render_extent_block()  («ОЖИДАЕМАЯ ПОЛНОТА»)
  → L2 Writer (Вербализатор) — единственный, кто пишет финальный текст
      • composer (UNIFIED_COMPOSER_ENABLED=1 в проде):
        channel_contract → core → identity → lessons/style/speech → response_plan
        → Speech_Base → expression (+ финальный контракт мата) → humor → few_shot
        → style_policy_hint
      • user: <Response_Plan> + <style_anchors> + контекст/evidence
```

Ключевое следствие: **«аналитичность» — это не отдельный слой, а комбинация (а) решения L1 `response_act=research`/`structure=report`/`extent=detailed`, (б) текста extent-блока, (в) Core, (г) объёма памяти в `<Global_Context>`**. Поэтому «психологическое эссе» — генерация Writer'а по тем инструкциям, что ниже, а не работа какого-то «анализатора».

Подтверждения: `services/direct_chat_service.py:4635-4742` (L2 Writer, единственная точка финального текста), `services/direct_l1.py:652-695` (схема L1), `services/response_extent.py:276-286`, `469-484`.

**COMPACT Core** (`chat_prompts.py:1084`) — один абзац, дефолт runtime (`prompt_registry.py:505-517`, `1205-1215`):

- Совпадает с P0: «не обязан шутить каждый раз», «не объясняй шутки», «не выдумывай реальные события, факты о людях и статистику чата».
- **Не совпадает и не фильтруется**: «развивать… интерпретацию **конкретными деталями и последствиями**»; «Когда есть фактура, **рассказывай через характерные детали и цепочку последствий**».
- Отсюда следует: **на дефолтной конфигурации единственная работающая защита от Core-многословия — отсутствует.** Это не «надо переписать Core», это разрыв между уже принятым фильтром и дефолтным уровнем.

Вывод по §3: полный Core переписывать не нужно; нужно закрыть compact-редакцию одним из двух способов (оба без нового слоя):
1. расширить существующий фильтр `simplify_core_for_prompt` на compact-клаузы (тот же приём, что уже применён к FULL);
2. либо выставить `detail_level=full` — тогда уже одобренный фильтр сам снимает 3 абзаца, а биография/характер остаются в полной редакции.

Оба варианта меняют то, что владелец видит в редакторе/Inspector, и один из них — предпочтение владельца → решение по §6.

## 7. Вывод по архитектуре

**ARCH_REUSE_CONFIRMED — для пяти текстов и для правки анализа.**

Контракты, на которые опирается правка (все существуют и приняты):
- единственный источник текстов речи — `services/mca_expression` (`§2.2` ADD-EXP; `EXP-INSTR.NOPOST`: постпроцессора мата нет);
- единственный рендер блока — `prompt_style_blocks.speech_base_block()`; preview и бой используют один текст;
- единственная точка финального текста — `_l2_write_answer` (`direct_chat_service.py:4635-4742`);
- правка канонов = бамп + `PREV_*`-слепок через `prompt_migrations` (ADR-1013-3); лестница уже содержит нужные ступени для `direct.base.l1_planner` и `direct.base.l2_writer`;
- слой Expression уже доставляет режим мата и в `<Expression_Settings>`, и в финальный контракт из одного объекта — второй регулятор не создаётся.

**ARCHITECT_REQUIRED — один узкий вопрос (не весь P0):** что делать с **compact-редакцией Core**. Сейчас дефолтный Core содержит «развивать… деталями и последствиями» и «рассказывай через… цепочку последствий», а существующий payload-фильтр их не снимает. Варианты различаются по смыслу и по тому, что владелец увидит в редакторе:
1. расширить `simplify_core_for_prompt` на compact-клаузы (код, Core-документ не меняется);
2. перевести чат на `detail_level=full` (только конфиг; уже одобренный фильтр снимает 3 абзаца, характер/биография остаются);
3. оставить Core как есть и полагаться только на BASE/LENGTH/FACTUAL (наименьшее вмешательство, но конфликт C2 остаётся и P0-жалоба воспроизводима).

Это решение о владельческом тексте личности, а не о механике — поэтому оно вынесено отдельно, а не «зашито» в реализацию пяти текстов.

**Известный разрыв, не блокирующий P0:** при `UNIFIED_COMPOSER_ENABLED=0` Speech_Base в Direct-путь не попадает вовсе (`prompt_composer.py:1525-1527`; OFF-ветка `_l2_write_answer` собирается `compose_verbalizer_system` без этого блока). В проде композер ON (`add-exp/evidence/release-25896/deploy/final-verification.txt:15`), поэтому P0-эффект есть; но путь отката останется без новых директив. Добавление блока в OFF-ветку меняет байт-паритет `tests/test_soul1_composer_parity_off.py` — это отдельное решение, не часть хотфикса.

## 8. Ограничения этого аудита

- Не проверялись сырые production-трейсы двух показанных запросов (в этом лейне нет доступа к проду/LLM). Все выводы — по коду и по уже сохранённым evidence; фактический payload конкретного хода должен подтвердить Builder/Reviewer на живом трейсе.
- Не проверялось, какая редакция Core реально лежит в PG (`detail_level`, кастом владельца). От этого зависит, какой из C2/C3 активен: при `full` три абзаца уже сняты фильтром, при `default` (compact) — активны.
- Числовые пороги (`limits.*`), влияющие на объём контекста (сколько памяти видит модель), не менялись и не аудировались — это зона `memory-provenance.md`.
