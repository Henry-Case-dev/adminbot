## 1. Что реально терялось (RED, замер на базе `613fae5d`)

| Фикстура | Бюджет | Кап цитаты | Вложено в цитату | Контрдовод/claim доезжает |
| --- | --- | --- | --- | --- |
| (a) цитата 3000 симв., claim на позиции 1491 | derived 113085 | 1200 | 1200 | **НЕТ** |
| (a) то же | static 1600 (hot) | 640 | 640 | **НЕТ** |
| (a) то же | static 5400 | 1200 | 1200 | **НЕТ** |
| (b) 20 реплик × 4096 | 1600 | 200 | пакет 4894 симв. / 1408 ток. | **НЕТ** (цитата теряет середину) |
| (b) то же | 5400 | 648 | 14414 симв. / 3746 ток. | **НЕТ** |

Причина ровно та, что описана в задании: абсолютный потолок 1200 превращал цитату в
голову 720 + хвост 480, а середина — единственное место, где в длинной цитате стоит
контрдовод — выбрасывалась. На живом производном бюджете (`deepseek-v4-flash`,
окно 131072 → бюджет 113085) кап всё равно оставался 1200.

## 2. Что изменено (P1/P2/P3)

Изменён один модуль — `services/direct_l1.py` (+ тесты). Нового бюджетного движка,
новых квот и справочников нет; инструкции LLM не урезаются (ADDENDUM #3 §2.10).

### P1 — потолки выводятся из бюджета, физический предел = 4096

* Удалены абсолютные `L1_REPLY_BLOCK_CHARS_MAX = 1200` и
  `L1_WINDOW_LINE_CHARS_MAX = 1200`.
* Введён `L1_CLIP_CHARS_MAX = 4096` — предел одного сообщения Telegram. Это только
  платформенная граница, а не «класс C»: эффективный потолок = доля бюджета
  (`L1_REPLY_SHARE = 0.10`, `L1_WINDOW_SHARE = 0.6`), как и раньше; полы 200/400 не тронуты.
* `window_line_chars()` = `max(200, min(4096, budget*4*0.6/rows))`,
  `reply_block_chars()` = `max(400, min(4096, budget*4*0.10))`.

### P2 — срез по границам предложений с ГАРАНТИРОВАННОЙ серединой

`clip_body(body, cap)` вместо head+tail (60/40) теперь:

* голова ≤45 %, хвост ≤30 %, середина ≤25 % (доли бюджета среза, маркеры `CLIP_MARK`
  учитываются в длине — для текста без границ длина ровно `cap`, проверено
  `clip_body("a"*1000, 200) → 200`);
* границы двигаются к ближайшей границе ПРЕДЛОЖЕНИЯ существующим регекспом
  `evidence_policy._SENTENCE_SPLIT_RE` (своего парсера нет);
* середина набирается «от центра текста наружу» и claim-first: высокорисковые
  предложения берутся первыми существующим детектором `evidence_policy._high_risk`
  (версия/цена/дата/число/существование), атомарная часть ≤ `L1_CLIP_ATOMIC_CHARS_MAX`
  = 320 символов; ссылки — атомарные источники (полу-URL хуже, чем перебор на длину
  URL — тот же инвариант, что уже действовал для головы/хвоста);
* границы середины не рвут слово (слак 24 символа), но если пробела нет — длина важнее;
* **справочника «контрдоводов» нет** (§1.3): правило одинаково для любого текста.

### P3 — пропорциональный шаг 0 и общий `clip_body` в шаге 3

* Шаг 0 `_cap_context` больше не лестница 160/120/90, а пропорциональное укорочение ОТ
  ФАКТИЧЕСКОГО капа строки с шагом `L1_CAP_SHRINK_STEP = 0.6` до пола 200. При новом
  потолке 4096 лестница давала первый шаг 160 → голова 72 символа, т.е. **хуже**, чем
  прежние 200. Теперь строки укорачиваются только настолько, насколько нужно.
* Шаг 3 (переполнение внутри `СООБЩЕНИЕ`/`ОТВЕТ НА`) идёт через тот же `clip_body`
  (было: ручной головной срез 60/40 с текстовым маркером) — середина вопроса/цитаты
  сохраняется по тому же правилу.

## 4. Стоимость (честные числа)

* Патологический случай «20 × 4096» на живом бюджете 113085: пакет 85179 символов /
  **21324 токена = 18.9 % бюджета** (было 6517 токенов = 5.8 %). Рост 3.27× — это цена
  доставки всех 20 сообщений целиком; потолок пакета по-прежнему держит `_cap_context`.
* Физическая граница: 20 строк × (4096 + префикс) + цитата 4096 ≈ 86 тыс. символов;
  тест утверждает `tokens ≤ 20 × 4096 / 2 = 40960` (для русского текста ≥2 символа на
  токен) — фактически 21324.
* На static-бюджетах рост минимален: +212 ток. (1600) и +248 ток. (5400).
* Денежных лимитов не касались: `MCA_MONEY_LIMITS_ENABLED` остаётся OFF, `metered_calls`
  не менялся.

## 5. Честная граница (что по-прежнему НЕ доезжает)

* Пол капа строки 200 при static-бюджете 1600 даёт середину ≈48 символов: обычная
  (не высокорисковая) фраза на позиции 325 из реплики 755 символов **не доставляется** —
  до и после одинаково (замер: 1600 → нет, 5400 → да, 112737 → да). Это цена ручного
  капа оператора, а не регрессия.
* Claim-first работает только по существующему детектору `_high_risk`. «Контрдовод»
  вроде «в 1017 нет функции X» детектор не считает высокорисковым (нет единицы
  измерения/версии), поэтому спасается только серединой, а не атомарным правилом.
  Расширять детектор — отдельное решение, в этой полосе не делалось.
* После шага 1 (отброс строк) кап строк не пересчитывается под новое число строк —
  поведение прежнее, кандидат на отдельную правку.

   пределами головы среза, доставляется на полу капа 200 (claim-first), а ОБЫЧНАЯ фраза
