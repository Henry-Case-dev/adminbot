## Блокирующие находки

### F1 (BLOCKER). Автор цитаты в речевой проекции - голая метка без имени

Требование: 5.4 "Кто" (устойчивый субъект + актуальное отображаемое имя), контракт 4.2 п.4
(`цитата (автор: Имя (U1))`), P0-перечень ревью ("потерян автор цитаты").

Наблюдение (фактический payload Direct, прод-проводка):

    цитата (автор: U3): «у мышц свои волокна»

U3 = user 55, которого нет в окне; имени этого человека в payload нет вообще
(`UserResolutionMap` содержит только участников окна). Тот же прогон с переданным
`quote_author_resolver` даёт `цитата (автор: Пётр (U3))` - то есть причина именно в
отсутствии резолвера, а не в шве.

Причина: `thread_chain.collect_thread_chain(..., quote_author_resolver=None)` -
параметр есть только в шве и в `test_evol_reply_context_integrity_seam.py:681`.
Ни один продовый вызывающий его не передаёт: `DirectChatService._collect_thread_chain`
(services/direct_chat_service.py:11842-11847) и `handlers/factcheck._build_reply_chains`
(handlers/factcheck.py:441-444). Поэтому `ChainItem.quote_author_name` в проде всегда
пуст, и `SpeechQuote.render` печатает одну метку.

Влияние: на вопрос "кто это сказал" модель не может назвать человека - остаётся только
адресная метка, которую озвучивать запрещено. Ровно тот пункт, который владелец назвал P0.

Почему это не поймано тестом: `test_quote_text_never_contains_run_labels` и тесты шва
создают `ChainItem(quote_author_name="Марина")` вручную - состояние, которого продовая
проводка не создаёт.

Минимальное исправление: передать резолвер имени (существующий alias-каскад
`DirectChatService._resolve_name`/`row_speaker`) в `direct_chat_service._collect_thread_chain`
и в фактчековый `_build_reply_chains`; при неизвестном имени оставить честное
"автор цитаты не определён", но не голую метку. Проверка: собрать payload с цитатой автора
вне окна и утверждать наличие человеческого имени.

### F2 (BLOCKER, малый объём). Медиа-свидетельство всё ещё вносит сырой `msg:<id>` в payload

Требование: 9.2 (служебные ID не озвучиваются), сц. 67 ("фактический speech payload не
содержит неиспользуемые raw ID в нарративных строках"), 9.3 п.7.

Наблюдение (`media_readiness.MediaReadiness.evidence_block`, блок идёт в user-payload

То есть на каждом медиа-зависимом ходу модель получает `msg:<tg_id>` в нарративной строке.
Обоснование исключения в отчёте ("это провенанс ревизии Vision, а не строка диалога") не
делает payload свободным от служебного ID, а сц. 67 проверяет именно payload.

`SpeechProjection`, обратная карта уже есть в трассе): `изображение M4`. Файл общий с
фактчеком - согласовать с владельцем фактчек-слайса. Проверка: медиа-ход, в payload нет
`msg:`.

### F3 (RELATED_SMALL). Объявление вытеснения окна исчезает, когда пометка не влезает

Требование: 5.4 п.153 / 8 п.5 ("реальное отсутствие помечается как неполнота"), 5.1
"не терять молча". Заявлено в отчёте: "окно теперь объявляет вытеснение, а не теряет

### F4 (RELATED_SMALL, наблюдаемость). Манифест врёт на повторе egress-guard

`context_representation="internal"` и пустой `speech_manifest`, хотя реальные user-блоки -

представление, что реально ушло), и 9.4 требует обратного. Исправление: прокинуть ту же
проекцию в повтор. Проверка: манифест повтора содержит `writer` и счётчики.

## Четыре (пять) заявленных исключений - мой вердикт

1. **`goal`/`rationale` инициативы (свободный текст Наблюдателя)** - приемлемо для этого
   слайса как решение по объёму, но требование не доказано: Наблюдатель получает машинную
   разметку `[msg:ID]` и ничто не мешает ему переписать номер в `goal`, а `goal` едет в
   Writer дословно (`services/direct_chat_service.py:12229-12238`). Это канал условный, не
   систематический, и чинить его надо промптом машинной стадии (9.3 п.5 это прямо
   разрешает - запрет на правку промпта в ТЗ отсутствует). Решение: оставить в этом слайсе,
   но завести явный пункт RC-чеклиста (сц. 60) с решением владельца на волну промптов, а не
   считать сц. 60 доказанной.
2. **`media_readiness.evidence_block`** - НЕ приемлемо в текущем виде: фактический payload
   содержит `msg:<id>` (F2). Либо метка здесь, либо перенос в фактчек-слайс с обязательным
   пунктом приёмочного прогона; "не в списке P1" не отменяет сц. 67.
3. **`<UserResolutionMap>`** - приемлемо. Это объявленная адресная карта "имя - user_id",
   она и существует для различения одноимённых; её инструкция - заводской версионированный
   промпт, а `_map_names` (services/direct_chat_service.py:911-918) читает её из payload.
   Убрать = потерять различение субъектов (5.4 запрещает такую "псевдооптимизацию").
4. **Оценка R7 "дельта размера <= 0"** - приемлемо только вместе с надёжным объявлением
   вытеснения; F3 показывает, что объявление не гарантировано, поэтому исключение пока не
   закрыто.
5. **Две проекции на маршрутах фактчека** (широкий фид и узкое окно) - приемлемо: маршруты
   взаимоисключающие (`handlers/factcheck.py:359-364`), в одном payload всегда одно
   представление. Вне слайса остаётся маршрут suitability-гейта
   (`handlers/factcheck.py:325`: `ctx.render_feed()` без проекции, гейт по умолчанию OFF) -
   это пункт фактчек-слайса для RC-чеклиста, не этого ревью.
