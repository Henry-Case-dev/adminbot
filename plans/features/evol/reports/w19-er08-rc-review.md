### Адверсариальное (моё): окно из плотных высокорисковых сообщений

20 реплик по 4096, высокорисковое предложение каждые ~200 символов, static 1600, кап 200:

| | база | кандидат |
| --- | --- | --- |
| длина срезанной строки при капе 200 | 200 | 294 (при риске каждые ~60 симв. - 490) |
| сообщений доезжает при 1600 | 20 из 20 | 10 из 20 (при риске каждые ~60 - 5 из 20) |
| то же при 2600 | 20 | 20 (при риске каждые ~60 - 10) |

Причина: claim-first добавляет до 320 симв. атомарных фрагментов, строка выходит за кап (при
этом докстринг clip_body обещает длину <= cap, кроме URL), шаг 0 упирается в класс-C пол 200,
и шаг 1 выбрасывает старые реплики 20 -> 10 -> 5. На базе этот случай влезал (20 x 200).

## 2. Реализация: что действительно сделано

  Замерено: идемпотентность clip_body(clip_body(x,640),640) = 598/598; слово и составная
  графема не рвутся (совмещающая кириллица, emoji).

* Квот на инструкции LLM не появилось (ADDENDUM #3 §2.10): промпты не менялись. 320 симв. -
  бюджет фрагмента середины, а не срез инструкций, но это новая константа, и её роль отчёт
  Builder-а не называет.

## 5. Блокирующие находки

### B1. Наблюдаемость ER-08-RC не реализована, а архитектурное решение объявлено отсутствующим

Требование: arch/reply-cap-decision.md §3 "Наблюдаемость" и §6 п.6. Рядом с l1_context_budget/source
в plan_meta и в record_l1_diagnostics должны появиться l1_reply_chars_cap, l1_line_chars_cap,
l1_reply_total_chars, l1_reply_delivered_chars, l1_reply_truncated, l1_kept_mid (числа и bool, без
текста), плюс тест на них.

Факт: ни одного из этих полей в коде нет (grep по l1_reply_truncated / l1_kept_mid /
l1_reply_chars_cap даёт 0 совпадений), теста тоже. Отчёт §1 объясняет это тем, что файл
reply-cap-decision.md "в репозитории отсутствует (проверены рабочее дерево и вся история
git log --all, включая evol/impl)". Это неверно: файл лежит в коммите 98286b2b (02.11 05:22,
evol/impl), он виден из этого же worktree (git log --all -- plans/features/evol/arch/reply-cap-decision.md
даёт 98286b2b) и старше коммита Builder-а f4196cc8 (05:42). Значит решение было доступно, а его
обязательный раздел выпал вместе с ложным выводом об отсутствии документа.

Влияние: в проде не видно, что цитата срезана и сколько из неё доехало, то есть ровно тот класс
молчаливой потери, который полоса закрывает.

Минимальная правка: 6 полей в meta живого пути и в record_l1_diagnostics, один тест на
наличие и отсутствие текста. Проверка после: pytest tests/test_er08_limits_context.py -q.

### B2. Плотное окно: при 1600 теряется половина реплик (на базе не терялась)

Инвариант, который код сам обещает в шаге 0: "все 20 сообщений остаются в пакете, теряется длина,
а не факты"; в решении Architect-а: "одно огромное сообщение не съедает больше доли".

Репро: 20 реплик по 4096 с высокорисковым предложением каждые ~200 симв., budget_tokens=1600.
В пакет попадает 10 реплик (при риске каждые ~60 симв. - 5), на базе 20 из 20. Строка при капе
200 выходит 294 (и 490) символов, шаг 0 упирается в класс-C пол 200, шаг 1 выбрасывает старые
сообщения.

Влияние: до планера не доезжают 10-15 последних сообщений окна (факты и адресация по ним), то есть
по тому же требованию владельца, которое полоса закрывает. Живой бюджет 113085 не задет: срабатывает
только на ручном hot-капе оператора <= 2000 и на fail-open поле L1_CONTEXT_FLOOR_TOKENS=1600.

Минимальная правка (один файл): не давать claim-first раздувать строку окна сверх капа, когда пакет
уже не влезает (например, ограничивать атомарную часть остатком mid_target и добавлять избыточные
claim-фрагменты только при запасе бюджета), и привести докстринг clip_body к фактической границе
(cap + L1_CLIP_ATOMIC_CHARS_MAX). Тест: "окно 20 плотных высокорисковых реплик при 1600 доставляет
не меньше реплик, чем база" и "длина строки <= cap + 320".
Проверка после: тот же сценарий на 1600 / 2000 / 2600.
