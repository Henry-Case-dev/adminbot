## 2. Линза 1 - реализация

Проверены реальные пути исполнения, а не только отчёт Builder:

- **Источники только существующие.** Топология - `db.graph_snapshot(...)`
  (`cognitive_map.py:583-589`), когнитивные классы - bounded SQL в самом
  модуле (`:273-309`), provenance рёбер - `edges.fact_id/origin/created_at/
  last_updated/weight` (`:245-255`). Второго хранилища, второй очереди
  извлечения, LLM и эмбеддингов нет: модуль только читает,
  `services/database.py` не изменён. Размеры классов считаются тем же
  запросом (`COUNT(*) OVER()`), N+1 и второго прохода нет.
- **Изоляция чатов.** В чатовом scope фильтруются все источники
  (`chat_id = ?` в `graph_facts`, `mca_trait_observations`,
  `memory_dream_log`, `edges`, `nodes`); `graph_snapshot(chat_id=...)` сам
  фильтрует и узлы, и рёбра (`database.py:12238-12245`). Ключ узла всегда
  чат-квалифицирован (`fact:<chat>:<id>`, `ent:<chat>:<id>`, `obs:`, `evt:`),
  поэтому одинаковые имена в разных чатах не сливаются. Глобальная область -
  только отсутствие `chat_id` плюс `scope.mode="global"`, с явной пометкой.
- **Права.** `_require_global_admin(request, user)` - та же зависимость, что у
  `/api/memory/graph` и `/api/memory/stats`; собственной проверки прав не
  вводится. Нет БД - прежний `_db_or_503()` (503), новых кодов нет.
- **Границы.** `COG_CLASS_LIMIT=150`, 4 класса, `entity_cap =
  max(150, 800 - когнитивные)`; рёбра не более 2400; порядок обрезки
  фиксирован (`importance DESC, created_at DESC, id DESC` для `graph_facts`,
  `observed_at/run_at DESC, id DESC` для наблюдений и циклов, время плюс id
  для класса «эволюция»). Сумма узлов ограничена 800 (проверено на плотном
  графе, §4). В JSON `caps` попадают реальные константы, а не литералы.
- **Честность модели.** `confidence/strength/freshness` не рассчитываются и
  отсутствуют в payload; раздельные времена (`occurred_at/observed_at/
  saved_at/confirmed_at/updated_at`) с `null` вместо «0»; для рёбер без
  provenance `justification_recorded=false` и `provenance.fact_id=null`;
  `isolated` пересчитывается по фактически показанным рёбрам; вымышленных
  связей нет (только `edges`, `edges.fact_id`, `graph_facts.supersedes`,
  `graph_facts.source_ids`). Парадигмы определяются тем же маркером
  `belief_meta`, что и существующий `count_paradigms`, а не новой эвристикой.
- **Состояния.** `ok/partial/empty/degraded`, `sources[name]=loaded|not_loaded`,
  `degraded.not_loaded` с именами упавших источников; отказ одного источника
  не роняет ответ (200 + честный `degraded`). Новых reason-кодов нет.
- **Адаптер.** `web/static/cognitive-map.js` - IIFE без DOM, vis-network, сети,
  `Date`, `Math.random`; в node грузится как модуль. Функции чистые
  (нормализация, поиск по названию и алиасу, фильтры с разрывом рёбер, камера,
  аллокатор подписей, сводка для легенды), мутации модели нет.

## 5. Блокирующее замечание

**B1 (Builder). Честность полноты: `truncated`/`state` могут утверждать
полноту, когда карта показывает меньшую часть данных.**

- Требование: контракт §4 (`partial/truncated` означает «показано X из Y»,
  полнота не обещается) и §5 (`truncated`/`shown_of` заполняются всегда);
  ТЗ `plans/current_task.md:1285` - «не обещать полноту, когда результат
  обрезан».
- Где: `web/api/cognitive_map.py:837-841` (`by_kind.entity.truncated` берётся
  только из флага снапшота), `:789-792` (`truncated.nodes/edges`),
  `:812-819` (`state`), при `totals` из `:807-810` и `:859-860`.
- Наблюдение (воспроизводимо): 850 сущностей чата, цепочка рёбер; снапшот
  возвращает окрестность 150 сидов - 152 узла и 151 ребро. Ответ:
  `shown_of.nodes=152`, `shown_of.totals.nodes=850`,
  `by_kind.entity={"shown":152,"total":850,"truncated":false}`,
  `truncated.nodes=false`, `truncated.by_class.entity=false`, `state="ok"`.
  Для остальных пяти классов правило другое (`total > shown`), то есть одно и
  то же поле в одном JSON означает разное.
- Влияние: S2 по контракту §4 включает «показано X из Y» только при
  `partial/truncated`; с `state=ok` и `truncated=false` карта будет подана как
  полная, хотя 698 из 850 сущностей в неё не попали. Это ровно тот случай
  «зелено, но неправда», который запрещает ТЗ. На текущем проде (около 356
  узлов) дефект латентный, но S2 унаследует его сразу.
- Минимальная правка: привести флаги к тому же правилу, что у остальных
  классов: `by_kind.entity.truncated = entity_total > shown_entities`,
  `truncated.edges = edge_total > len(edges)` (ИЛИ с прежним cap-флагом);
  `state` тогда сам станет `partial`. Публикуемые `totals` не менять, Y нужен
  для «показано X из Y». Плюс один durable-тест: 300 сущностей цепочкой
  (окрестность сидов меньше общего числа) даёт `truncated.nodes=true`,
  `by_kind.entity.truncated=true`, `state="partial"`.
- Проверка после правки: тот же набор (850 сущностей, показано 152) даёт
  `truncated=true` и `state="partial"`, а маленькая фикстура остаётся `ok`.

## 7. Шесть вопросов Builder к Architect: решения

1. **Названия легенды - отвечает ТЗ, Architect не нужен.**
   `plans/current_task.md:1285` дословно задаёт легенду: «Факты», «Убеждения»,
   «Парадигмы», «Изменения». «Эволюция характера» - название секции лент
   (`:1257`), а не подпись в легенде. Адаптер уже так и делает
   (`KIND_LABELS`); S2 обязан сохранить оба имени в своих ролях.
2. **Серверный `state` против состояний рендерера - отвечает контракт §4.**
   Таблица §4 перечисляет и серверные (`ok/partial/empty/degraded`), и чисто
   клиентские состояния (`loading`, `not_loaded` - vis-network не загружен,
   `stale`, `renderer_failed`, `reduced-motion`). Сервер физически не может
   знать состояние рендерера. Разделение финальное; порог устаревания - это
   константа S2, считается на клиенте от `generated_at`, новых серверных
   состояний не вводить.
3. **Порядок внутри класса «эволюция» - отвечает контракт §5.**
   Зафиксировано «класс, затем importance/recency, затем id»; у событий
   эволюции importance нет, значит действует recency, и текущая реализация
   ему соответствует. Под-приоритет «сначала события, потом наблюдения» был бы
   изменением замороженного контракта, а не дефектом S1; по ТЗ (`:1280`)
   события показываются по реально происходившим изменениям, то есть по
   времени.
4. **Исключение `deep_traits` - отвечает контракт §2 и семантика данных.**
   `deep_traits` - это `memory_dream_log.kind`, строка учёта токенов
   LLM-вызова traits (`services/dream_worker.py:2684`), а не запись изменения
   характера; реальные изменения уже приходят из `mca_trait_observations`
   (включены). Включение дало бы бессодержательные «события» и нарушило бы §2
   («только реальные записи изменений»). Исключение верное.
5. **`unresolved_refs` - не архитектура, а продуктовый вкус S2.** Счётчик
   честности уже отдаётся; обязательной пользовательской строки ТЗ не требует.
   Рекомендация: отдельную новую строку не вводить; при желании S2/S3 может
   показать «часть связей не загружена». Приёмку это не меняет.
6. **Полный текст в payload - отвечает контракт §1 и ТЗ (`:1267`, `:1286`).**
   Контракт прямо требует «заголовок + полный текст» в узле, ТЗ отправляет
   полный текст в панель, а подписи предписывает сокращать. Значит S1 верно
   отдаёт `text` целиком. Открытый пункт - измерение (размер ответа и
   `EXPLAIN QUERY PLAN` на прод-копии, контракт §5/§6), а не решение о
   разделении API; менять контракт до замера нельзя, это уже Architect.

Итог: **ни один из шести вопросов не требует Architect до S2** - четыре
закрыты контрактом, один ТЗ, один это замер плюс необязательная полировка UI.
