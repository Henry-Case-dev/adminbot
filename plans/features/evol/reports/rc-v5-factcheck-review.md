Это разрешено замороженным M4 (близость как разрешение ничьей) и критерием относительного времени из §4.3, но стресс-вариант сценария 10 (кандидаты из разных мест) этим срезом не покрыт - вынести в приёмку 120 сценариев.

## Блокеры

### B1. Маршрут handler -> v2 теряет объявленную contextual-цель (владелец §10.3, §1.5 I1/I2/I3, сц. 24, 42, 52)

Где: handlers/factcheck.py:1188-1199 (ветка v2 передаёт target и v2_text), handlers/factcheck.py:110-122 (_factcheck_pipeline_v2 собирает запрос по target.message_id), services/factcheck_orchestrator.py:764-774 (повторный резолв с target_source=stored_reply) и :813-879 (contextual только при пустой публикации; envelope берёт claim_text лишь при augmented).

Наблюдение (мои прогоны A1 и A2):
- handler объявляет contextual и передаёт в v2 target_text = тезис, target_tg_message_id = пустая цель (913705);
- v2 затем пишет трассу: target_source=stored_reply, claim_origin=target_text, target_tg_message_id=913705, claim_anchor_tg_message_id=913705, text_claim_resolved=true, delivery_reply_to=913705, envelope_built=false;
- сам вердикт считается по правильному тексту (legacy-ветка, тезис совпадает), но объявление и временной envelope потеряны.

Влияние на пользователя: тезис чужого сообщения приписан пустой цели, проверка идёт без envelope (даты и происхождение не берутся), ответ уходит на пустое сообщение, а не на команду. Это ровно тот класс дефекта, который срез обязан был закрыть, только на комбинированном маршруте.

Минимальная правка: в ветке v2 передавать уже разрешённую цель (target_tg_message_id из publication, target_source, claim_origin, анкор) либо не переразрешать публикацию повторно; envelope должен получать claim_text при подмене, доставка при contextual - на триггер.

Проверка после правки: новый тест - v2 включён, Reply на пустую цель, тезис в цепочке; трасса target_source=contextual, анкор равен тезису, envelope не None и содержит тезис, delivery равен триггеру; плюс прежний набор 26 файлов.

### B2. Contextual-тезис из thread_chain объявляется без анкора (владелец §4.1, §4.2, §5.3, §7; I1, I2, I3; сц. 6, 13, 19, 52)

Где: services/factcheck_suitability.py:812-824 (ContextClaim для элемента цепочки создаётся без tg id), источник идентификатора - services/thread_chain.py:187-206 (item_id вида tg:901).

Наблюдение (мои прогоны B и probe_e): публикация получает target_source=contextual, target_tg_message_id=None, claim_anchor_tg_message_id=None, claim_origin=context_window, текст тезиса правильный, доставка на триггер. Envelope затем строится по пустому сообщению-реакции: original_published_at=1792400000 и attribution Kim вместо 1792000000 и Irma у реального тезиса.

Влияние на пользователя: в сценарии владельца Reply на короткую реакцию, у которой тезис в родителе, проверяется правильный текст, но трасса не содержит анкора (пустое поле), а вердикт получает дату и автора реакции. Это нарушает непрерывность target_ref и правило не менять автора/дату утверждения.

Минимальная правка: перенести id из item_id в ContextClaim (одна строка); если id достоверно неизвестен - не объявлять contextual с пустым анкором, оставить тезис контекстом и пометить связь как отсутствующую.

Проверка после правки: тест - тезис старше окна, доступен только через thread_chain; анкор равен id тезиса, envelope.target совпадает с анкором, дата и автор берутся у тезиса; пустых полей в объявленной contextual-трассе нет.
