# CMV-PERF — два дефекта «Когнитивной карты»: диагноз и исправление

База: `720ef838` (ветка `evol/impl`, CMV A–E). Ветка работы: **`cmv/perf`**.
Стенды: `tools/ui_cmv_e_leaks.py` (утечки), `tools/ui_cmv_e_fps_campaign.py`
(FPS), `tools/ui_cmv_perf_shots.py` + `tools/ui_cmv_perf_parity.py`
(пиксельное сравнение «до/после»), `tools/_soul1_w5_visual_server.py`
(живой HTTP-стенд для обычного браузера).

## Дефект 1 — «+665 слушателей, +64 наблюдателя, +26 МБ»

### Что измерено

Разбор по классам (снимок **в момент замера**, а не в момент регистрации;
цели держатся через `WeakRef`, поэтому сам стенд ничего не удерживает):

| класс | что это | за 19 циклов | утечка |
|---|---|---|---|
| (a) наш обработчик, не снятый в `destroyCognitionGraph` | `scene.onClick` («Раскрыть» район) | **0** (`scene.handlers` 10→10, контейнеры после сноса `listenerCount()==0`) | нет |
| (b) внутренний слушатель vis, привязанный к уничтоженной `Network` | Hammer/pointer/click/contextmenu/wheel на контейнере | **0** на живых целях; живых `vis.Network` объектов `1 → 1` | нет |
| (c) намеренный глобальный слушатель `window`/`document` | `resize`, `visibilitychange`, `hashchange`, … | `window 26 → 26`, `document 2 → 2` | нет |
| (d) слушатель на узле, который заменил переход маршрута | `+665` на **отсоединённых** узлах (`liveDetached 40 → 705`) | `+665`, но узлы собираются GC | нет |

Ключевые числа (кандидат, `leaks-cand.json`): `liveConnected 838 → 838`
(слушатели на ЖИВЫХ узлах в документе не растут), живых `ResizeObserver 9 → 9`,
`IntersectionObserver 1 → 1`, `vis.Network 1 → 1`, куча после
принудительного GC `26.4 → 27.5 МБ` (`+1.1 МБ`, немонотонно).

Полноэкранная карта — **маршрут** (`#/status/graph` при `iaV2`), но она
переключается `v-if` внутри той же страницы: узел-контейнер заменяется,
страница заново НЕ создаётся (в DOM всегда ровно одна сцена, `scenes 1`,
канвасов `4 → 4`, узлов `1053 → 1053`). Слушатели на заменённом узле умирают
вместе с ним — это и есть класс (d), утечки нет.

### Почему прежний стенд показывал «+26 МБ» — ошибка инструмента

Прежняя версия `ui_cmv_e_leaks.py`:
1. держала в реестре **сильные ссылки на функции-обработчики**;
2. держала сильные ссылки на объекты наблюдателей в `Set` «живых».

Наблюдатель vis, снятый через `unobserve` (а не `disconnect`), оставался
живым и через замыкание удерживал целую уничтоженную сцену (Network + 702
узла + 2400 рёбер ≈ 1.3 МБ) — отсюда и «+64 наблюдателя», и «+26 МБ».
Контроль без инструментации на том же сценарии: `26.05 → 27.81 МБ`
немонотонно, DOM неизменен.

Стенд переписан: `WeakRef` на цели, дедупликация по числовому id из
`WeakMap` (функции не удерживаются), классификация по `isConnected` в момент
снимка, реальные живые объекты через `Runtime.queryObjects`, GC + пауза перед
чтением кучи. Теперь на ОБОИХ деревьях: `checks=28 fails=0`.

### Что всё-таки исправлено в продукте

* `autoResize: false` в опциях `vis.Network`. В vis 9.1.9 `Canvas.setOptions`
  на КАЖДЫЙ вызов создаёт новый `ResizeObserver` (снимает только
  `unobserve`) и слушатель `window.resize`; собственный наблюдатель контейнера
  у нас уже есть (`_cogOnSceneResize` → `setSize`). Создано наблюдателей за
  20 циклов: **165 → 97** (`leaks-base.json` vs `leaks-cand.json`).
* Убран повторный `setOptions({physics:{enabled:false}})` на пути `hasLayout`
  (опция уже пришла в конструкторе) — минус лишний наблюдатель на инстанс.

## Дефект 2 — 24–27 FPS на 702/2400 в рабочем зуме (прокси: 390×844, DPR 2, CPU ×4)

### Куда уходил кадр (замер, а не догадка)

Инструменты: CDP-сэмплирующий профилировщик + `Performance.getMetrics` +
поочерёдное отключение слоёв (обёртки над `ctx` НЕ использовались — они
искажают кадр сильнее измеряемого). Разложение на 702/2400, рабочий зум:

| компонент кадра | мс/кадр | доля |
|---|---|---|
| рисование рёбер vis (2400 шт., из них 800 пунктирных) | **17–21** | **50–55 %** |
| слой `fx` целиком (свечение + декор + подписи + JS) | 10.2 → **6.7** | 20 → 16 % |
| — из него свечение (`drawImage` ореолов) | 5.2 → 1.7 | |
| — из него декор (`arc`/`fill`/`stroke`) | 4.9 → 1.8 | |
| — из него подписи (`strokeText`/`fillText`) | 4.8 → ~0.4 | |
| узлы vis | ~5 | 12 % |
| страница/композитор (вне карты) | ~8 | 20 % |
| физика | 0 (выключена после стабилизации; `physics:false`) | — |
| GC | 0.8–1.5 % | |

Отдельно измерена цена пунктира: те же 2400 рёбер БЕЗ пунктира — минус
5.7–9.3 мс (24 % кадра), при этом скрытие тех же 800 рёбер целиком даёт лишь
на 2.6–3.5 мс больше. То есть дорог не «рисунок», а `save/setLineDash/
lineDashOffset/reset/restore` на каждое пунктирное ребро внутри
`EdgeBase._drawDashedLine` (видно и в профиле: `setLineDash` 4.0 %, `save` 2.1 %).

Проверена и отброшена гипотеза «75 % рёбер невидимы»: у 1798 рёбер оба конца
ВНЕ кадра, но сами отрезки кадр пересекают — точный тест «отрезок ×
прямоугольник» (Liang–Barsky) отсекает 0 рёбер. Эвристика «по концам» убрала
бы ВИДИМЫЕ линии; от неё отказались (код отсечения не оставлен).

Также проверено и отброшено: `backdrop-filter` карточки (снос фильтра делает
кадр ХУЖЕ: 35.7 → 40.0 мс), DPR слоя `fx` (1× вместо 2×: −0.6 мс — не тот
рычаг), аллокация цвета ребра в vis (цвета уже `rgba(...)`, `ev()`
возвращает строку без аллокации).

### Что исправлено (всё — без изменения картинки)

1. **План подписей не пересобирается на кадре панорамирования.**
   Было: камера входила в ключ с точностью 0.5 px ⇒ сортировка 702 узлов +
   разбор коллизий + 702 объекта **каждый кадр**, плюс `ctx.font`+`measureText`
   на каждом кадре. Стало: ключ плана — структура кадра (LOD/выбор/витрина/
   поиск/позиции/размер/кегль), положение камеры хранится «якорем»; между
   пересборками подписи сдвигаются ЖЁСТКО (взаимные расстояния не меняются),
   пересборка — при уходе камеры за `panLimit` (40 CSS-px), при зуме ВНИЗ
   ≥2 % (зум ВВЕРХ безопасен: центры расходятся, бокс подписи пиксельный).
   Ширина символа меряется один раз на сцену/кегль.
2. **Подпись = спрайт.** Текст+контур растеризуется ОДИН раз в offscreen
   канвас в разрешении слоя и компонуется `drawImage` по целым CSS-px. Кадр
   больше не зовёт `strokeText/fillText`. Позиция выбранного по-прежнему
   принудительная и всегда видимая.
3. **Декор пачкой.** ~450 отдельных `beginPath+arc+stroke/fill` → один путь на
   корзину стиля (тип декора + цвет + толщина с шагом 0.25 px + альфа с шагом
   0.05). `moveTo` перед каждой дугой — фигуры не «сшиваются» хордами.
4. **Кэш спрайтов свечения по целочисленному бакету** (вложенные карты вместо
   строкового ключа: ~820 склейки строк и объектов на кадр → 0) и
   **дедупликация `globalAlpha`** (не присваиваем то же значение 400+ раз).
   Позиция ореола — целые CSS-px (сдвиг <1 px не виден, выборка 1:1 без
   билинейной фильтрации).
5. **Радиус узла в сетевых единицах кэшируется** на смену `fitScaleRef`/набора
   (`_cogApplyNodeSizes`), а не считается через `Math.log` 702 раза на кадр.
6. **`autoResize: false`** (см. дефект 1) — минус работа vis на ресайзе.

### Результат FPS (один и тот же стенд, соседние окна)

Абсолютные числа на этой машине «плывут» (±20 %) из-за параллельной нагрузки,
поэтому ниже — ПАРНЫЕ прогоны (база → кандидат) в одном окне:

| окно | android working | android detail |
|---|---|---|
| A | 28.1 → **30.0** | 45.0 → 38.0 |
| B | 25.6 → **29.8** | 35.7 → 42.4 |
| C | 25.3 → 26.2 | 38.7 → 38.0 |
| D | 24.3 → 26.9 | 38.6 → 36.2 |

Медианный парный выигрыш ≈ **+10 %** (в спокойных окнах — до +17 %, кадр
35.5 → 30.0 мс). Абсолютный ориентир в спокойном окне: **≈30 FPS median,
p95 ≈ 23** при базе 28.1 / 20.9.

На desktop (1536×960, DPR 1) карта упирается в потолок 60 fps и в базе, и в
кандидате; регресса нет (`fps-cand-*.json`).

### Честно: что НЕ закрыто

Половина кадра — собственное рисование vis-network (2400 рёбер, из них 800
пунктирных, у каждого `save/setLineDash/…/restore`). Внутри текущего контракта
(«одна сцена, один canvas для карты», рёбра видны, пунктир = производная
связь) это не сжимается: отсечение невидимого даёт 0 рёбер, а любое
уменьшение числа/стиля рёбер — изменение вида. Чтобы получить запас сверх 30
FPS, нужен отдельный шаг уровня архитектуры: рисовать рёбра самим (один путь
на цвет/альфу в слое ПОД узлами) либо пересмотреть политику пунктира. Это
решение не принималось в одиночку.

Ограничение стенда: `CPU ×4` тормозит главный поток рендерера, но GPU/растр
остаются десктопными. На реальном телефоне растрирование 2400 рёбер и 800
пунктиров будет ДОРОЖЕ измеренного, а JS-часть — сопоставима. То есть
измеренные 30 FPS на прокси — оптимистичная граница, а не гарантия для
телефона; это зафиксировано, а не замазано.

## Визуальная проверка

* Playwright, детерминированный кадр (позиции заданы явно, движение
  выключено): на телефоне в рабочем и детальном зуме разница с базой
  **0.000 %** пикселей (`parity-phone-desktop.json`). На обзоре и на desktop
  сам стенд недетерминирован (контроль «база против базы» даёт тот же порядок
  5–20 %), поэтому там решает живой осмотр.
* Обычный браузер (Browser Use) на живом HTTP-стенде
  (`_soul1_w5_visual_server.py`, 702/2400): обзор — 6 районов с подписями
  «Группа · N», мягкие потоки, ореолы; рабочий/детальный зум — читаемые
  подписи с контуром, ореолы на месте, декор (грани/кольца/ядра) на месте,
  «белого ковра» нет, подсветка связей наведения работает.
