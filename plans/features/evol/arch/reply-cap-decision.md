# ER-08, остаток 1200 символов: как представлять длинную цитату/реплику

**Роль:** ограниченное архитектурное решение. **Дата:** 02.11.2026.
**Код-референсы** — кандидат ER-08 `feat/er08-limits-context` (`d2488cea` + `de20960c`, worktree
`…-6eb8e511`): только там есть `clip_body`/`reply_block_chars`/`resolve_l1_context_budget`; в `evol/impl`
их нет, поэтому правка идёт на ветку ER-08. **Источники:** `services/direct_l1.py:853–1101, 1116–1322`;
`services/auto_budget.py:65–100, 163–238`; `services/model_capacity.py` (реюз, не менялся);
`services/evidence_policy.py:925–968, 1002–1017`; `arch/evidence-routing-contract.md` §4.2/§4.4/§4.5;
`reports/w18-er08-review.md` §R2.5.

## 1. Вердикт

**ARCHITECT_ADJUSTMENT_REQUIRED.** Граница 1200 символов закрывается не большим слепым капом, а **выводом
потолка из того же бюджета + срезом по границам предложений с обязательным представительством середины
(и claim-первым сохранением высокорисковых claim'ов)**. Нового бюджетного движка, конфиг-ручки,
LLM-вызова, поля схемы и миграции не появляется.

Почему не «status quo + формулировка»: видимость claim решает **не текст ответа, а решение**.
`external_claims` заполняет L1 из видимого текста, а policy (`evidence_policy` §1.2 п.6) включает
обязательную проверку по непустым claim'ам или factual-акту. Не доехал контрдовод из середины — проверка
**молча не включается**, и Writer утверждает непроверенное. Владелец требует защищать «reply …
контрдоказательства» прямо, значит остаток — пробел требования, а не косметика.

## 2. Арифметика границы и почему не «просто 4096»

Живой бюджет 112 737 ток. (окно 131 072, mandatory 400); char-бюджет в кодовой конвенции = ×4. Цитата:
112737×4×0.10 = 45 094 симв. при потолке 1200; строка окна 112737×4×0.6/20 = 13 528 при том же потолке;
исходное сообщение min(8192, ×0.5) = 8192 — защищено. Реплика Telegram физически ≤ 4096 симв. (уже в коде:
`L1_MESSAGE_CHARS_MAX=8192` = 2×), т.е. 4096 ≤ 45 094 — потеря середины на живом бюджете есть следствие
**константы**, а не бюджета.

Но фиксированный 4096 при малом бюджете ухудшает поведение: `_cap_context` (`:1237`) не влезает, шаг 0
гонит лестницу 160/120/90 по всем строкам — голова 96 симв.; статический/горячий кап (1600 ток., 20 строк)
получил бы худший результат, чем сегодняшние 200/120. Проблема не в числе: потолок не связан с бюджетом,
а срез не знает границ.

## 3. Выбранное представление (три части одного слайса)

**P1. Потолок выводится из бюджета, максимум — физический размер сообщения.** `services/direct_l1.py`:
`L1_WINDOW_LINE_CHARS_MAX`/`L1_REPLY_BLOCK_CHARS_MAX` перестают быть абсолютными 1200 и становятся
`L1_PLATFORM_MESSAGE_CHARS = 4096`; полы 200/400 и `share`-формулы не меняются. При бюджете ≳34 тыс. ток.
(20 строк) и ≳17 тыс. (цитата) срез не срабатывает вообще — физически возможный текст доезжает целиком;
ниже — работает долей бюджета, как сейчас.

**P2. Срез по границам предложений с обязательной серединой.** `clip_body` (`:931`) сохраняет имя и
сигнатуру, меняет алгоритм: делим по существующему `evidence_policy._SENTENCE_SPLIT_RE` (`:968`), берём
голову (≤45 % капа), хвост (≤30 %) и **середину** (≤25 %, от геометрического центра в обе стороны). Плюс
claim-first: предложение, которое `evidence_policy._high_risk` (`:1002`, существующие
`_RISK_EXISTENCE/VERSION/NUMBER/YEAR+EVENT`) считает высокорисковым, но которое целиком попало в выпавший
промежуток, добавляется принудительно, суммарно ≤320 симв. Границы не рвут URL (`_url_safe_cut` уже есть),
`CLIP_MARK` между фрагментами, предел выхода `cap + 320`. Один сегмент без пунктуации → прежний head+tail.

**P3. Пропорциональная замена лестницы 160/120/90** (иначе P1 опасен): в шаге 0 `_cap_context` сначала
`keep = max(0.15, (window_tokens - deficit) / window_tokens)`, `line_cap = max(90, int(current_cap*keep))`
по измеренному `count_tokens`, ≤3 итераций, затем прежняя лестница как страховка. Шаг 3 (`:1285–1294`) для
«СООБЩЕНИЕ»/«ОТВЕТ НА» тоже идёт через новый `clip_body`, а не через `body[:0.6]+хвост`, — иначе claim,
сохранённый в P2, снова теряется.

**Наблюдаемость** (R17-safe числа/bool, существующие каналы): рядом с `l1_context_budget/source`
(`direct_chat_service.py:5327–5328`, читатель `:729–735`) — `l1_reply_chars_cap`, `l1_line_chars_cap`,
`l1_reply_total_chars`, `l1_reply_delivered_chars`, `l1_reply_truncated`, `l1_kept_mid`; те же оси в
`record_l1_diagnostics`. Без текстов, промптов и URL.

## 4. Токен-стоимость, evidence policy, EVR2

Стоимость: цитата ≤4096 вместо ≤1200 → максимум +2 900 симв. (≈ +1 200 ток. кириллицей) и только если
цитируемое сообщение реально такое. Окно 20×4096 = 81 920 симв. ≈ 20 500 ток. (4 симв./ток.) или ≈34 000
ток. (реальная кириллица) — 18–30 % бюджета 112 737; потолок блока по-прежнему `L1_WINDOW_SHARE=0.6`,
жёсткий кап — `_cap_context` по реальному `count_tokens`. Один длинный ответ пакет не съедает (доля
цитаты 0.10). p95 не меняется (обычные реплики 100–500 симв., замер ревью — 2 296 ток.); рост только на
гигантских вставках, где цена потери выше. Новых квот на инструкции LLM нет (ADDENDUM #3 §2.10).

Policy/EVR2: claim-key и `source_reuse` не трогаются — аннотация `external_claims` строится из **видимых**
предложений, а P2 сохраняет предложения целиком, поэтому аннотация остаётся верной цитате; обязательность
проверки по-прежнему решает runtime (`evaluate_evidence_need`), не модель. EVR2 (пересказ =
`summarization`/`summary`, проверка = `external_claims`) начинает работать там, где сейчас молчит; без
claim'ов поведение прежнее.

## 5. Отвергнутые варианты

1. **Status quo + формулировка** — скрывает пробел требования (§1): проверка не включается, а не «текст
   чуть короче»; допустимо только как явная частичная строка (§7).
2. **Фиксированный 4096 без вывода из бюджета** — регрессия при статическом/горячем капе (§2).
3. **Только границы при капе 1200** — корень не устранён (бюджет позволяет 45 тыс.), гарантии для
   не-claim контрдовода нет.
4. **Детектор «контрдоводов» по словарю** — §1.3 контракта запрещает словники для смысловых фаз;
   `_high_risk` намеренно узкий (фикстура «нет функции X, это переименование» им не ловится), поэтому
   середину защищает структурное правило P2, а не угадывание.
5. **LLM-конспект цитаты** — платный вызов, недетерминизм, второй движок; **6. снять кап/защиту секции** —
   класс C.

## 6. Обязательные тесты (кандидат ER-08 + слайс)

1. **Фикстура A:** цитата 3000 симв., контрдовод с 1500-го; бюджет 112 737 → контрдовод в
   `build_l1_context` дословно, `l1_reply_truncated=False`, тело `ОТВЕТ НА` равно цитате.
2. **A-край:** та же цитата при `hot=1600` → `l1_reply_truncated=True`, честные `delivered/total`, середина
   представлена (зона P2), высокорисковый claim («не существует», «версия 1.2.3», «999 ₽») сохранён.
3. **Фикстура B:** 20 реплик по 4096 при бюджетах 1600/5400/112 737 → `count_tokens(package) <= budget` во
   всех трёх, цитата не выброшена, строка ≤4096+префикс, при 112 737 ни одна строка не срезана.
4. **Класс C:** `window_line_chars(20 строк, 1600) == 200`; `reply_block_chars(1600) == 640`;
   `message_cap_chars` без изменений; `window_line_chars(одна строка) <= L1_PLATFORM_MESSAGE_CHARS`.
5. **Границы/URL и идемпотентность `clip_body`** (не рвёт URL/слово/предложение); **P3-страховка:** бюджет
   6000 при 20×4096 → пакет в бюджете, строки не ниже 90 симв.
6. **Наблюдаемость:** новые оси в `plan_meta`, `record_l1_diagnostics` их принимает, текста нет.
7. **Цепочка до проверки:** claim из середины цитаты виден → `evaluate_evidence_need` с этими
   `external_claims` даёт `required=True` (реюз существующей тест-инфраструктуры policy).

**Законно меняющиеся утверждения (не ослабление):** `test_mid_message_counterargument_at_static_1600_is_lost`
(`tests/test_er08_limits_context.py:167`) и `test_mid_message_counterargument_needs_budget_above_line_cap`
(`:180–206`) утверждают «середина теряется». После P2 это неправда: переписать в **позитивные** («середина
доставлена на 1600») плюс негативный край, который остаётся правдой (один сегмент без пунктуации →
head+tail). §R2.5 отчёта и «порог ≈5400» обновить тем же коммитом.

## 7. Остаточный риск и формулировка PM

R1 (один файл, аддитивная логика, гварды на месте). Остаются и должны быть названы: (а) бюджет ниже
~17 тыс. ток. и текст длиннее капа → промежутки между головой/серединой/хвостом не восстанавливаются
(середина представлена, но не целиком); (б) не-claim контрдовод в выпавшем промежутке может не дойти;
(в) плотность кириллицы расходится с ×4, поэтому у края бюджета срабатывает P3 (видно по meta).

**Строка PM, если привязывать ДО слайса (честно-частичная):**
> ER-08 (reply/контрдоказательства): на производном бюджете (112 737 ток., окно 131 072) подтверждено —
> исходное сообщение, адресация, цитата и контрдовод в её хвосте доезжают; **граница:** при капе ≤1200
> симв. контрдовод в СЕРЕДИНЕ цитаты/реплики длиннее ~1200 симв. не доезжает, поэтому обязательная
> проверка может не включиться; остаток закрывает слайс `ER-08-RC` (потолок из бюджета, физический
> максимум 4096, срез по границам предложений с представительством середины), приёмка — фикстуры «цитата
> 3000/контрдовод на 1500-м» и «20 реплик по 4096 в бюджете». До него строку не формулировать как «reply
> защищён сквозным образом».

**Параллельность:** `PARALLEL_SAFE` для тестов, `SERIALIZE` для `services/direct_l1.py` (один писатель);
`direct_chat_service.py` — две строки meta, брать после освобождения файла.
