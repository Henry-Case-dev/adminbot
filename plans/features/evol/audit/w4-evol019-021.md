## EVOL-019 — «Проверить» подтверждает распознавание, а не HTTP 200

### Что было (аудит фактической семантики)

- `POST /api/vision/test` (`web/api/routes.py:2366+`) зовёт `probe_connection`;
  вердикт `ok` ставится при `2xx` + непустом `choices` (`_classify_success`),
  содержимое ответа НЕ читается ⇒ «200 OK» подавался как «распознавание
  работает» (ровно жалоба владельца).
- `vision_unreadable` — это отказ ЗАГРУЗКИ/валидации байтов
  (`validate_image_bytes`, сниффер/лимиты, статус анализа `unreadable`), а не
  отказ провайдера и не «нет содержимого».
- `validate_or_normalize` — bounded декод-фоллбэк (`image_normalize`), только
  по `vision_unreadable`.
- `analyze_adaptive`/`merge_segment_analyses` — отдельная стадия
  (JSON-схема анализа, `parse_error`/`empty_content` из EVOL-011), кнопкой
  пробы не покрывалась вообще.

### Что сделано

`mca_vision.recognition_check(route=None, *, transport=None, chat_id=None,
fixture_image=None)` — структурированный результат одного реального запроса
по действующему маршруту на локальной детерминированной фикстуре
(`probe_images()`, PNG 512×512/640×512, генерируется в процессе):

| Поле | Смысл |
|---|---|
| `config_ok` | маршрут (адрес/модель/ключ/тип) валиден локально |
| `provider_reachable` | провайдер ответил по сети (`None` — не дошли) |
| `media_accepted` | провайдер принял ИЗОБРАЖЕНИЕ (`False` — отказ модальности/формата, `None` — не доказано) |
| `recognition_completed` | ответ содержит schema-valid completion (`choices[0].message.content` — строка) |
| `content_received` + `content_sample` | текст распознавания непустой; образец ≤160 симв., однострочный |
| `duration_ms`, `model`, `provider`, `source`, `api_type`, `config_revision`, `timestamp`/`checked_at` | происхождение и цена проверки |
| `terminal_reason` + `terminal_reason_label` | закрытый набор причин (см. ниже) |
| `paid_call` + `budget_note` | проверка реально тратит бюджет провайдера — сказано прямо; при конфиг-ошибке `paid_call=false` |
| `pipeline` | производная готовность (модуль/тип медиа/полученное содержимое) + приписка, что маршрутизация реальных пользовательских медиа этим не доказана |
| `media_coverage` | какие типы медиа этой проверкой НЕ подтверждены |

Терминальные причины (каждая — отдельное состояние, `RECOGNITION_REASONS`):
`recognized`, `not_configured`, `api_type_unsupported`, `vision_key_missing`,
`timeout`, `transport_error`, `access_denied` (401/403), `rate_limited` (429),
`provider_error` (5xx), `model_not_found`, `image_modality_unsupported`,
`image_rejected`, `client_error`, `empty_body`, `response_not_json`,
`response_schema_invalid`, `empty_choices`, `empty_content`.

Ключевые различия (закреплены тестами):

- `200 + не-JSON` → `response_not_json`, `recognition_completed=false`,
  `state=schema_invalid` (НЕ «работает»);
- `200 + пустой content` → `empty_content`, `state=content_empty`;
- `200 + пустая схема/`choices: []`` → `response_schema_invalid` /
  `empty_choices` — отдельные причины;
- конфиг-ошибка не тратит бюджет (`paid_call=false`, транспорт не вызывается);
- отказ модальности ≠ «изображение не принято» ≠ таймаут ≠ 401/429.

Телеметрия: событие `vision_recognition_check` (outcome/reason_code из
существующего словаря `mca_events.REASON_CODES`, `duration_ms`, `error_json` с
кодом состояния; образец содержимого в события НЕ пишется — только длина).

Политика медиа (`media_coverage`): проверенной считается ТОЛЬКО группа
«фото и изображения-документы»; `static_stickers`, `gif_animations`,
`animated_stickers`, `video_previews` помечены `tested_by_this_check=false` с
причиной (другой формат / нужно извлечение кадра), чтобы одна проверка не
выдавала `OK` за всю модальность.

Сдвиг строк: вставка 525 строк в `services/mca_vision.py` (только добавления,
0 удалений — `probe_connection`/`_classify_success` не тронуты) между
`probe_connection` (`:950`) и блоком D8 ⇒ номера строк ниже этого места
смещены (`validate_image_bytes` теперь `:1758` вместо `:1330`,
`runtime_snapshot` — `:4452` вместо `:3927`). Номера из
`base-revalidation.md` остаются верны для базы `a02aca0c`; `recognition_check`
занимает `:1401`.

### Разрыв, который закрывает следующая (UI/API) полоса

`POST /api/vision/test` в `web/api/routes.py` пока возвращает СТАРУЮ форму
(`ok`/`capability`/`state`). Роут нужно переключить на
`mca_vision.recognition_check(chat_id=scope_chat)` и отдать новые поля
(`state`, `config_ok`, `provider_reachable`, `media_accepted`,
`recognition_completed`, `content_received`/`content_sample`, `paid_call`,

`probe_connection` остаётся для capability-кеша effective-состояния (это
разные вопросы: «принимает ли модель изображения» vs «получен ли результат»).

## EVOL-020 — «Опыт»: жива ли цепочка и что означают числа

`services/experience_diagnostics.py` (только чтение):

- `experience_pipeline_snapshot(db, *, now=None, chat_id=None, gates=None)` —
  8 этапов: `observation → candidate → validation → activation → retrieval →
  application → outcome → utility`. Для каждого: `enabled`, `state`
  (`working`/`idle`/`broken`/`disabled`/`stale`/`never_run`), `last_run_at`,
  `last_success_at`, `total`, окна 24ч/7д/30д, `skip_reasons` (типизированные
  события опыта), `reason` + RU-подпись.
- `experience_pipeline_reasons(...)` — те же причины за 7 дней для
  раскрываемой детали.
- Классификатор цепочки `classify_experience_state(...)`: выключено → нет
  прогонов → последний прогон с ошибкой → давно не запускалось (>
  2×каденции) → есть свежие уроки/применения → простаивает (наблюдения есть,
  достойных уроков нет / новых наблюдений нет). `evidence` содержит все
  отметки, по которым принято решение.
- Причина «ноль применений» выводится из данных:
  `context_selection_off` (K4 OFF) → `no_active_lessons` (нет активных
  уроков, «это не ошибка») → `no_selection_runs` (активные есть, отбор ни
  разу не запускался) → `nothing_matched` (отбор был, ничего не прошло
  релевантность). Ноль применений САМ ПО СЕБЕ не делает цепочку `broken`.
- `counters.lessons` — по статусам в пределах scope; уроки без chat-scope
  (`global`/`task` без чата) отдаются ОТДЕЛЬНЫМ числом
  `lessons_out_of_chat_scope`, а не схлопываются в chat-числа.
- `definitions` — словарь состояний/причин и пояснение, почему `total` и окно
  не обязаны совпадать и почему `candidate/validated/active` — разные классы
  (это и объясняет «Уроков 0» на верхнем графике против «Уроков 2» в
  детализации — разные классы/окна, а не противоречие backend).

### Реальный дефект в цепочке?

Проверено по коду: цепочка рабочая — review-job (`experience.review`)
валидирует и активирует уроки (`_validate_and_activate`,
`_resume_incomplete`), применения пишутся в `direct_chat_service` при
непустом блоке уроков (`record_applications`, `application_ref=correlation_id`,
идемпотентно), исход линкуется только по независимому событию позже
применения (`_link_outcomes`). Детерминированной поломки, которую можно
доказать из кода (как EVOL-010 `_LAST_EMBED_META`), здесь НЕТ — поэтому
исправление «механизма» не делалось: доставлена честная диагностика,
которая показывает, на каком именно этапе цепочка стоит, и почему. Если на
проде уроки остаются `candidate`, витрина это покажет
(`counters.lessons.candidate`, `validation_failed.last_reason`), не выдавая
их за применённые.

## EVOL-021 — «Истории памяти»: смысл эпизодов + группа восстановления

`services/episode_diagnostics.py` (только чтение, без LLM):

- `episode_summary(row, *, story_ctx, now)` — компактная семантическая
  карточка: `title` + `title_source` (`pipeline`/`first_claim`/`none`),
  `what_happened` (+источник), `event_period` (start/end/known),
  `discovered_at` vs `processed_at`, `discovery_kind`/`discovery_label`
  (`new_event_today` / `discovered_old_event` / `archive`),
  `participants` (primary ≤5 + others), `linked_messages` (точное число
  ключей, `capped`), `claims_count`, `completeness`
  (`ready`/`partial`/`empty`), `verification` (только из связанной истории;
  иначе честное `not_linked`), `story` + `retrievable`, `needs_recovery`.
- `episode_feed(db, chat_id, ...)` — лента ТОЛЬКО готовых эпизодов + сводка
  группы восстановления (`count`, `by_reason`) + `last_build`
  (`last_build_at`, `backfill_state`, `backfill_active` — из уже
  существующего прогресса Витрины, второго агрегатора нет).
- `recovery_group(db, chat_id, ...)` — «Требуют восстановления»:
  `status = unrecoverable | pending_rebuild` + настоящая причина
  (`no_source_messages`, `no_substantive_text`, `summary_not_built`,
  `title_stub_only`), число затронутых записей и разбивка по причинам.
- `episode_card(db, chat_id, episode_id)` — карточка ровно выбранного
  эпизода; чужой чат → `None` (изоляция не зависит от роутера).

Честность:

- техническая заглушка («Эпизод 1780282318», «История 1650…») НЕ становится
  заголовком: `title=None`, причина `summary_not_built`/`title_stub_only`,
  запись уходит в группу восстановления, а не в ленту «новых историй»;
- «Не удалось восстановить сюжет: нет источников» больше не маскируется под
  новую историю: у записи `status=unrecoverable` + `reason=no_source_messages`
  + число затронутых записей; сюжет не выдумывается;
- старый эпизод, впервые обнаруженный сегодня, помечается
  `discovered_old_event` («Обнаружено сегодня (событие ранее)»), а не
  событием сегодняшнего дня;
- связность участников честно `unknown`: авторство по ключам
  `<chat>:tg:<id>` не восстанавливается, и это прямо написано в поле;
- никакого LLM на открытие витрины (структурный тест: в модуле нет
  `llm_client`/`generate(`).

## Итог (RU)

Сделаны три backends-части. «Проверить распознавание» теперь возвращает
структурированный результат и честно различает: конфигурацию, доступность
провайдера, приём медиа, завершённость распознавания и полученное содержимое;
пустой или битый ответ провайдера больше не выглядит как «работает», а
платный характер проверки виден в ответе. «Опыт» получил диагностику всей
цепочки с реальными отметками времени, счётчиками за 24ч/7д/30д, причинами
пропусков и классификатором working/idle/broken/disabled/stale — включая
объяснение «ноль применений» по данным, без выдуманных уроков. «Истории
памяти» получили компактные смысловые карточки эпизодов и отдельную группу
«Требуют восстановления» с настоящей причиной и числом затронутых записей;
технические заглушки больше не выдаются за новые истории, старые эпизоды
помечаются «обнаружено», новых LLM-вызовов на открытие витрины нет. Все
новые тесты зелёные (45 вместе с EVOL-009), `compileall services` чистый,
существующие смежные наборы (vision, experience, stories) не сломаны; три
падения в `TestMigrationV21` — pre-existing на базе и к этой полосе не
относятся.

## §review-fix (EVOL-020, после независимого ревью)

Три блокера витрины «Опыт» — все подтверждены кодом, воспроизведены пробой
(старый модуль из `4fcbf684` подгружался рядом с новым) и закрыты.

### B1. «Работает» из одних предложенных кандидатов

Было: `classify_experience_state` получал `learned_in_window` = уроки,
СОЗДАННЫЕ за 24ч. Два кандидата без проверки давали `working` /
`lessons_flowing` с подписью «Уроки создаются/проверяются в окне», хотя
`validation`/`activation`/`application` = `never_run` и применений 0.

Стало: `working` — только по подтверждённым downstream-фактам в окне:
`applied_in_window` → `applications_flowing`; `activated_in_window` →
`lessons_flowing` (подпись «Уроки проверены и активированы в окне»);
`validated_in_window` → `lessons_validated`; только кандидаты → `idle` +
`lessons_proposed_only` («Уроки предложены, проверка ещё не проходила»).
В `evidence` вместо `learned_in_window` — `proposed_in_window` /
`validated_in_window` / `activated_in_window`.

Проба: OLD `working/lessons_flowing` «Уроки создаются/проверяются в окне» →
NEW `idle/lessons_proposed_only`.

### B2. Причина применения считалась по `total`, а не по окну

Было: `_application_reason(applications=len(application_rows))` — одно
применение 40-дневной давности давало `applications_flowing` при окнах
`{24h:0, 7d:0, 30d:0}`; `outcome`/`utility` при этом заявляли
`no_applications_recorded` («применения не записывались»), хотя строка
применения есть.

Стало: причина применения — по окну 7д; при `total > 0` и нулевом окне —
`applications_not_in_window` («Применения были раньше, но в этом окне новых
нет»). Для `outcome`/`utility` введена отдельная причина
`outcome_not_measured` («Применения есть, но исход ещё не измерен —
полезность не считается»); `no_applications_recorded` остаётся только для
реального отсутствия применений.

Проба: OLD `applications_flowing` + `no_applications_recorded` →
NEW `applications_not_in_window` + `outcome_not_measured`.

### B3. Ложное «отбор ни разу не запускался»

Было: `retrieved` эмитился ТОЛЬКО при непустом отборе
(`select_for_context` возвращал `retrieval_empty` без события), коды
`no_relevant_memory`/`budget_exceeded` нигде не сохранялись. Поэтому
«отбор был, ничего не прошло» читался как `no_selection_runs`, а
`_retrieval_excluded` (обещал коды из payload) всегда был пуст.

Стало: `select_for_context` эмитит `retrieved` и при пустом результате
(`outcome=skipped`, `reason_code=retrieval_empty`) и при сбое чтения
кандидатов (`outcome=failed`), в `usage_json` — bounded-сводка
`{selected, considered, excluded_codes: top-5}` (R17: только коды и числа).
Успешный отбор тоже несёт сводку исключений. Диагностика: `retrieval.total`
= все попытки, `selected_runs_7d` / `empty_runs_7d` / `failed_runs_7d`
разделены; пустая попытка → `idle` + `selection_empty` («Отбор уроков
запускался, но ни один урок не прошёл по релевантности»), сбой чтения →
`idle` + `selection_failed`; `excluded_reasons` заполняется из payload.
Причина применения больше не «отбор не запускался», а `nothing_matched`.
