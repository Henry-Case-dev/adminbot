## 2. Источник данных: один, аддитивный

`loadCognitionGraph()` читает `GET /api/memory/cognitive-map` (S1) и
нормализует ответ адаптером (`normalizePayload`). Старый `/api/memory/graph`
виджетом **не запрашивается**; серверный контракт и маршрут `#/status/graph`
не тронуты (retirement — S4). Загрузка висит на существующем cognition-polling
(15 с), нового поллера нет. Данные не уходят в LLM/эмбеддинги: живой прогон
проверяет ДЕЛЬТУ сетевых запросов за показ/зум/фильтры/полный экран (§8).

Поле `cognitionGraphData` теперь хранит нормализованную модель (а не legacy
снимок) — этим же полем пользуется уже существующий каталог «Память»; его
раздел «Связи» адаптирован к `title`/`relation`/`derived` (выдуманных связей
по-прежнему нет).

## 3. Легенда — слова владельца

Источник формулировок — ТЗ, строка 1285: «Цвет/форма ↔ «Факты», «Убеждения»,
«Парадигмы», «Изменения»». Ровно эти четыре строки обязательны и
показываются всегда (`legendEntries().filter(required)`), в этом порядке.
«Эволюция характера» — заголовок секции лент (строка 1257), в легенду не
попадает (проверяется и в node-тесте, и в живом прогоне).

Различие не только цветом (строка 1280): у класса своя форма — круг (факты),
скруглённый квадрат (убеждения), шестиугольник и больший размер (парадигмы),
ромб (изменения). Токены — существующая палитра (topic/user/indigo/event),
новых цветов нет.

Вторичные классы (`Сущности`, `Наблюдения`) показываются отдельными
приглушёнными строками ТОЛЬКО если такие узлы реально есть в модели: иначе
пользователь видел бы необъяснимые серые/янтарные узлы. Обязательные четыре
строки они не подменяют и не переименовывают (помечены `required:false`).

## 4. «Показано X из Y» — нейтрально

Правило одно на узлы и рёбра (правка B1 в S1): строка включается, когда
`totals > shown` (после B1 это нормальное состояние почти любого реального
чата — снапшот берёт окрестность сидов и отбрасывает сирот). Никакой связи с
серверным `state='partial'`: `partial` не рисуется как тревога и вообще не
упоминается в UI.

Вид: серый `text-gray-500` (`rgb(162,176,198)` по замеру), без иконок,
янтарного/красного и слова «ошибка»; текст «показано 11 из 320 узлов · 6 из 40
связей». Формулировка собирается pure-функцией `completeness()` и проверяется
node-тестом (числа из payload, а не из `state`), pytest-ом (класс нейтрален,
нет `state === 'partial'` в разметке/коде) и живым прогоном (цвет + текст).

Обратная сторона правила тоже проверена: при полном наборе (`totals == shown`)
строки нет (e2e, оба вьюпорта).

## 5. Подписи, LOD, камера, раскладка

* **Слой подписей** — собственный (`nodes.font.size = 0` + событие
  `afterDrawing`), аллокатор — из S1 (`allocateLabels`): приоритет
  (выбранный → парадигма → убеждение → факт → сущность → наблюдение →
  изменение), экранное разрешение коллизий, обрезка за вьюпорт.
  Потолки: 26 подписей на десктопе, 12 на телефоне; LOD по масштабу
  (`overview` ≤6 / `normal` ≤16 / `detail` ≤26). Массовое наложение названий
  невозможно конструктивно (бокс ставится только если не пересекается).
* **Кернинг по DPR**: канвас внутри имеет масштаб устройства, подписи
  рисуются в CSS-пикселях (`setTransform(ratio…)`), координаты — через
  `network.canvasToDOM`.
* **Semantic zoom**: колесо/pinch меняют масштаб, режим зума (far/medium/close,
  гистерезис) переключает детализацию подписей; данные не режутся.
* **Камера**: снимается на каждом кадре и перед сменой экрана
  (`_cogCaptureCamera`, защита от resize-пересчёта), восстанавливается
  `moveTo`. Полный экран и обратный переход дают ту же камеру/масштаб, выбор
  узла сохраняется (проверено на 390 и 1280, допуск 3 ед./0.08).
* **Стабильная раскладка**: при обновлении данных DataSet обновляется
  локально (инстанс жив), позиции известных узлов переиспользуются, новые
  узлы встают рядом с реальным соседом (детерминированная спираль по хешу id,
  без `Math.random`); при возврате на экран физика не запускается вовсе.
* **Mobile-simple** — существующее поведение (`isMobileShell` без полного
  экрана): без перетаскивания узлов, потолок подписей 12, физика сразу off.
* **reduced-motion**: физика выключена, `moveTo`/`focus` без анимации,
  информативность (узлы/подписи/легенда) сохраняется.

## 6. Кластеры — только реальные связи

`computeClusters(model)` — связные компоненты по ПРИНЯТЫМ рёбрам (union-find,
корень = минимальный id). Никакой близости на экране, похожести названий или
LLM. Изолированный узел — честный кластер из одного узла. Подпись кластера:
«Парадигмы: <название>» при наличии реальной парадигмы, иначе
«<доминирующий класс> · N». Детерминизм: повторный прогон и порядок объектов
дают идентичный результат (node-тест).

Фильтр «Все кластеры» — витринный: сужает набор узлов/рёбер, не меняет данные,
не ходит в сеть и не сбрасывает камеру. На фикстуре: 5 кластеров на 11 узлов,
фильтр даёт 3 узла, камера сохраняется.

## 7. Состояния: серверные и клиентские — разные оси

| Что видит пользователь | Как получается |
|---|---|
| `loading` — «загрузка карты…» | модели ещё нет (`/api/memory/cognitive-map` в пути) |
| `not_loaded` — «визуализация грузится — счётчики уже видны» | payload есть, vis-network ещё не загружен (lazy self-host) |
| `renderer_failed` — «визуализация недоступна — данные и счётчики сохранены» + переход в Память | рендерер упал или скрипт не загрузился (не пустой чёрный прямоугольник) |
| `stale` — «данные на HH:MM» + кнопка «Обновить» | `generated_at` старше 15 мин (клиентская константа) |
| `empty` — «в этой области нет фактов и связей» + «Открыть в Памяти» | серверный `state='empty'` или 0 узлов |
| «по выбранному фильтру узлов нет» + сброс | данные есть, но витрина пуста |
| «часть источников не прочитана: …» (янтарная строка) | серверный `state='degraded'` + `degraded.not_loaded` |
| «показано X из Y» | `totals > shown` (нейтрально, §4) |

Клиентское состояние считается `mapClientState()` — чистой функцией с `now` и
порогом на входе; серверный `state` переносится отдельным полем и не
подменяется. `partial` не является состоянием UI.

## 9. Что найдено и исправлено попутно

**vis-инстанс в реактивных данных (реальный дефект старого виджета).**
Vue 3 заворачивает любой объект, прочитанный из экземпляра, в `reactive`-proxy;
методы vis-network обращаются к приватным полям классов, и вызов через proxy
падает с `TypeError: Cannot read private member…`. Воспроизведено на базе
`ba01c082`: в старом «Графе связей» `selectNodes([])`/`selectNodes([id])`
бросали исключение, т.е. кнопки **«Найти» и «Сбросить вид» в проде не
работали** (ошибка не доходила до UI). В S2 экземпляр сети и DataSet
закреплены через `Vue.markRaw` (`cogRaw`) — паритет контролов восстановлен,
а не «перенесён». Это же устраняет риск для карточки S3.

Прочее: подпись «Эволюция характера» к легенде не применялась (решение
Architect в S1-ревью); на телефоне контролы карты перестали занимать столбик
из пяти строк (L01312).

## 13. Что стоит решить до S3 (не блокирует S2)

1. **`degraded` и клиентское состояние.** Сейчас серверный `degraded` даёт
   янтарную строку с именем источника, а клиентское состояние остаётся
   `ready` (рендерер-то работает). Если ожидается, что отказ источника
   понижает и «клиентский» статус карты — это решение Architect, потому что
   смешивает две оси из §4 контракта.
2. **Плотность прода.** Потолок подписей 26/12 — визуальная константа из
   контракта §5; на реальных 356 узлах число подписей в кадре не измерено
   (фикстура маленькая). Если замер на проде покажет «пусто», менять надо
   LOD-пороги, а не данные.
3. **Кластер как продуктовый фильтр.** Реальные компоненты на проде могут
   дать один большой кластер (связность памяти высокая). Тогда фильтр по
   кластеру будет малополезен — это вопрос S4 (нужен ли второй уровень:
   тема/участник), а не дефект S2.
