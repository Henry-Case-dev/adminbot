Источник: `plans/owner_inputs/2026-11-10-vmq-time-refinement.md` + `year-bias-root-cause.md`. Read-only контракт, продуктовый код не менялся.

## 1. Три раздельных свойства (не один score)
- **H — историческая значимость**: `H = cosine(query,fact) × _importance_factor(imp)`. Возраст и `status` в H НЕ входят.
- **R — фактическая достоверность**: `R = weight × provenance` (существующие `graphrag_provenance.read_policy_rank`/классификатор). `archived_fact` **не понижает R**: квота ≠ ложность/неподтверждённость.
- **V — актуальность сегодня**: булев `V = status='confirmed' AND (expires_at IS NULL OR expires_at>now)`. V не множитель H; V задаёт политику (§2) и маркировку (§5). `archived_belief` (убеждение) и `expired` — V=0; существующий `belief_resonance_penalty` остаётся только для `archived_belief`.

## 2. Политику выбирает существующий L1, без словарных триггеров
Единственный L1-вызов (`services/direct_l1.py`, `L1Plan:285`, `_plan_direct_l1` dcs:6414) получает ОДНО опциональное allowlisted-поле `memory_scope: operative|historical|auto` (прецедент: `recheck`, `external_claims`, `preserve_source_facts` — тот же вызов, не новый). Решает смысл запроса.
Нормализация на сервере (`normalize_l1_plan`): мусор/отсутствие → `auto`; `knowledge_origin=open_world`+`search_intent=required` → `auto`; `action ∈ (silent, react)` → `operative`. Модель не может понизить явный `historical`.
Поле уходит в `RetrievalRequest.memory_scope` (mca:481-555) и в `_rag_unified_rows` (dcs:12140). Новых списков слов/регулярок года НЕТ; год из вопроса по-прежнему разбирают только существующие технические парсеры (`extract_history_depth`, `bind_quantitative_range`, tool-регексы dig) — и только как дату.

## 3. Скоринг: что именно меняется в существующем механизме
`_knn_graph_facts` (sm:6044) и `_base_rank_key` FTS-пути (sm:5937): при `policy ∈ (historical, auto)` `score = H × R`; возрастной член перестаёт быть множителем.
`_effective_weight(weight, confirmed_at, now, *, policy)` (sm:948): `operative` — байт-в-байт прежняя формула (half-life 60, floor 0.1): механизм «что действует» сохранён; `historical|auto` — decay к H не применяется, возвращается `weight × (1 − FRESH_TIEBREAK × min(1, age/HORIZON))`, `FRESH_TIEBREAK=0.05`, `HORIZON=1825` сут → максимум 5 % за давность, чего недостаточно, чтобы перевесить разницу H ≥10 %.
V работает как tie-window, не как штраф: при `|Δ(H×R)| < 0.05` предпочитается V=1, иначе порядок по `H×R`.
Пул: статусы через существующий `_fact_statuses(include_archived=True)` (`sm:923-930`) = `confirmed|archived_belief|archived_fact`; только для `historical|auto` `fetch_k = max(GRAPH_MMR_FETCH_K, 3×limit)` (новый `limits.graph_mmr_fetch_k_historical=30`). MMR/дедуп/usage-пенальти/touch/воскрешение не меняются; archived/expired в touch и resurrection не входят, как сейчас.

## 4. Адаптивный подбор доказательств (никакой фиксированной доли)
`operative` — только V=1 (сегодняшнее поведение). `historical` — минимум `HIST_MIN_SLOTS = max(1, limit//5)` = 2 при limit=10, и только если есть кандидат с `H ≥ HIST_REL_FLOOR × max(H по V=1)`, `HIST_REL_FLOOR=0.75`; иначе 0 (честно пусто, без подмены). `auto` — исторический кандидат занимает слот только если его `H×R ≥ H×R` вытесняемого (правило вытеснения, квоты нет); потолок `HIST_MAX_SHARE=0.5` — техническая страховка. Оба лимита регистрируются в `services/param_catalog.py` (`limits_graph`), читаются через `hot.get("limits.…")`; сохранённые пользовательские настройки не меняются.

## 5. Профиль участника: несколько периодов, реальные источники
`DatabaseService.get_user_context_facts(..., scope="operative"|"historical")` (db:12588) — новый keyword-only параметр, default `operative` → прежний SQL байт-в-байт (`image_context_memory:533` и старые тесты не затронуты). `historical` — одно чтение, window-функция SQLite:
`WITH cand AS (SELECT g.*, <yr>, <valid_now> FROM graph_facts g WHERE chat_id=? AND <scope> AND <exclude> AND ((g.status='confirmed' AND (g.expires_at IS NULL OR g.expires_at>?)) OR g.status='archived_fact')), ranked AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY COALESCE(yr,0) ORDER BY valid_now DESC, weight DESC, COALESCE(message_timestamp,created_at) DESC, id DESC) rn FROM cand) SELECT … FROM ranked WHERE rn<=? ORDER BY valid_now DESC, COALESCE(yr,0) DESC, rn` LIMIT `?`.
`yr = CAST(strftime('%Y', COALESCE(NULLIF(message_timestamp,0),NULLIF(created_at,0)),'unixepoch') AS INT)` (NULL — отдельная группа, последняя); `valid_now` = предикат V; `per_year = max(1, limit//5)` = 2 при limit=10 → 10 слотов покрывают до 5 лет. `limit` НЕ растёт (бюджет 4000 симв. не расширяется). `_subject_fact_rows` (mca:957) передаёт `scope='historical'` только при `memory_scope ∈ (historical, auto)`; `identity/appearance/speech_style/relationships` — `operative`.

## 6. As-of/провенанс: Writer не может подать историю как действующее
Reply-путь: существующий `render_evidence_summary(certainty="archive")` → «архивный факт: » + дата (`_SUMMARY_CERTAINTY_PREFIX`, mca:303) для строк с V=0; в `<RAG_Memory>` строка получает префикс `(архив, YYYY)` через существующий `_mark_rag_fact` (dcs:2577), год берётся из `message_timestamp` самой строки. `read_policy_rank` для `archived_fact` перестаёт отдавать 2: R считается из weight+provenance, чтобы архив не читался как «предположение».
Профиль: аддитивные поля envelope `status`, `valid_now`, `as_of_year`; `confidence` остаётся про R и для `archived_fact` вычисляется из weight+provenance, а не из статуса (`tool_router:4183`). Промпты не меняются — маркировка в данных, как «(не подтверждено)».
