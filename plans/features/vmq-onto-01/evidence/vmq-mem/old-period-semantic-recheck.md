# «Семантический поиск по старым периодам» — перепроверка

База: `vmq/time-bias` @ 709865f6, линия прода 92070d0e, read-only. Проверка кода + поведение sqlite-vec 0.1.9 (in-memory проба, без прод-данных и без записи файлов).

**Уточнение прежней формулировки.** Внутри KNN фильтр по aux-колонке запрещён (`An illegal WHERE constraint on a vec0 auxiliary column`), и `WHERE` по aux, спроецированной из KNN-подзапроса, даёт ту же ошибку. Но **соединение KNN-подзапроса по `rowid`** с обычной таблицей и фильтр по её колонке **работает**: `SELECT … FROM (SELECT rowid, distance FROM graph_facts_vec WHERE embedding MATCH ? AND k = ?) v JOIN graph_facts f ON f.id = v.rowid WHERE COALESCE(f.message_timestamp,f.created_at) BETWEEN ? AND ?`. В проде `rowid = fact_id` (`_insert_graph_vec_row`, summary_memory.py:3744+), т.е. форма применима напрямую; отсечение по году идёт **после** k-среза, значит ограничитель — глубина пула, а не отсутствие фильтра.

## 1. Комбинированный retrieval — VIABLE
Механизм: `_rag_unified_rows` (direct_chat_service.py:12289) уже делает базовый векторный поиск без ограничения по времени и периодный добор тем же `retrieve`; проверка времени в Python уже есть — `_rag_append_period_rows`:12436 + `_rag_row_year`:2637 (`message_timestamp`/`created_at`/`rag_ts`). Не хватает вектора в периодном канале и глубины пула.
Минимальные правки: `_RAG_PERIOD_CHANNELS = ("lexical", "vector")` (:12275); периодный результат не обрезать до `limit`, а передавать пул в `_rag_rows_from_result(extra, pool)` (:12379–12381).
Граница `retrieve` переносит overfetch **без изменения общих вызывающих**: `top_k` не клампится (`request_limit`, mca_rc:834), `retrieve_fact_candidates(limit=…)` принимает любую глубину, `fact_rows` собираются по своему `top_k` (mca_rc:1861), фильтр времени — `_apply_filters` по `sent_at = rag_ts` (mca_rc:1377/1942). Overfetch выражается как `top_k` периодного вызова, новой ручки не нужно.
Цена: +1 `retrieve` (второй уже есть) и +1 KNN-скан; k≈128 даёт staged-скан 512 и MMR `O(limit×k)` (оценка порядка ~1 с чистого Python-`_cosine` при dim 3072), k=512 — ~5 с плюс чтение 512 float-векторов (~6 МБ).
Риск: почти-дубли истории; гасится `period_slots`, правилом «только год, которого нет в срезе», исключением self-origin и dedup по id.

## 2. Метаданные времени — VIABLE, но вырождается вероятностно
`graph_facts`: `created_at` NOT NULL, `message_timestamp` (backfill = created_at, database.py:7562), `expires_at`; KNN-путь уже читает строки по id (`get_graph_fact_records` отдаёт `message_timestamp`/`created_at`) → год доступен без нового столбца. SQL-фильтра времени у FTS-фактов **нет** (`search_graph_facts_fts`, database.py:11154 — только `now_ts`/TTL), у FTS сообщений он есть (`search_messages_fts(since_ts/until_ts)`), а оконный год-раздел уже применяется в `get_user_context_facts(scope="historical")` (`ROW_NUMBER() OVER (PARTITION BY год)`).
Вырождение: в чате 22 889 фактов, ≤2024 — 3 277 (14,3 %); измеренный top-10 вектора — 2026×10 в 4/5 классов, но в классе E 2023×1 и 2024×1. Отдача в старый срез **не нулевая, но не гарантирована**: k=128 покрывает 0,56 % фактов чата, k=512 — 2,2 %, и факт вне среза близости не достаётся никаким пост-фильтром.

## 3. Эпизоды/сообщения — NOT VIABLE (в семантике)
В проекте ровно две vec0-таблицы: `graph_facts_vec` и `smart_archive` (summary_memory.py:99/104); индекса эмбеддингов сообщений или эпизодов нет. `_episode_candidates` (mca_rc:2175) ранжирует пересечением токенов, без векторов; `dig_into_lore` идёт через `search_long_term(since_ts/until_ts, order="time")` — лексика с настоящим SQL-окном года. Семантический запрос по окну времени запускать не на чем; индексация сообщений — новая инфраструктура.

## 4. Сводная цена
+1 KNN и +1 `retrieve` на ход, доминирует MMR по пулу. Точная латентность требует замера: на прошлом ревью поколение KNN было `compat_not_proven`, поэтому прод-поведение вектора не измерено и цифры §1 — оценка, не факт.

## 5. Рекомендация для СЛЕДУЮЩЕЙ ступени памяти (НЕ входит в замороженный VMQ-TIME @709865f6)
Вариант 1 в узком виде: вектор в периодном канале с ограниченно-глубоким пулом и пост-фильтром по `rag_ts`, плюс парная дешёвая правка — SQL-окно года в `search_graph_facts_fts` (фильтр до LIMIT). Приёмка только замером на копии прод-БД: доходит ли известный старый факт до финального блока и не растёт ли доля 2026; без замера не принимать. Детерминированную гарантию даёт лишь индексация времени в vec-индексе — это отдельная ступень, не эта.
