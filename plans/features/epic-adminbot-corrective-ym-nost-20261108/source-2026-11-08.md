## 2. TIME-UX: премиальный выбор времени без технического ввода

### 2.1. Результат для пользователя

На странице «Модули → Время» основной элемент — **один searchable combobox**, работающий мышью, клавиатурой и касанием. Пользователь выбирает **город/часовой пояс человеческим языком**. Не нужно знать IANA, искать справочник или вводить `UTC+05:00` вручную. В базовом состоянии отображать текущее эффективное значение и источник наследования.

### 2.2. Готовые тексты интерфейса — использовать дословно как продуктовый baseline

| Элемент | Точный текст |
|---|---|
| Заголовок | **Время чата** |
| Подзаголовок | **Бот использует этот часовой пояс, когда говорит о времени, запускает задачи по расписанию и определяет начало нового дня.** |
| Поле | **Часовой пояс** |
| Placeholder поиска | **Найти город или часовой пояс** |
| Под полем, если свой пояс не выбран | **Сейчас используется общая настройка. Для этого чата можно выбрать другое время.** |
| Под полем, если есть override | **Для этого чата выбран отдельный часовой пояс.** |
| Заголовок текущих часов | **Сейчас в чате** |
| Заголовок подсказок | **Популярные города** |
| Кнопка основная | **Сохранить** |
| Сброс override | **Использовать общую настройку** |
| Успешное сохранение | **Часовой пояс сохранён.** |
| Сброс успешно | **Теперь чат использует общую настройку времени.** |
| Пустая выдача | **Такой город не найден. Попробуйте другое название.** |
| Ошибка загрузки справочника | **Не удалось загрузить список часовых поясов. Попробуйте ещё раз. Текущая настройка сохранена.** |

В UI **не показывать** пользователю строки «источник: global_legacy», `config_version`, «IANA-пояс (пусто = наследование)» и служебные RFC/ISO поля. Эти значения допустимы в разделе диагностики для глобального администратора. Вместо них — «Общая настройка», «Настройка этого чата», «Временная ошибка», «Заводское значение» и т. п.

### 2.3. Представление одного варианта в списке

Основная строка: **`Екатеринбург`**. Вторая: **`Россия · UTC+05:00 · сейчас 17:22`**. После выбора сохраняется *ровно* `Asia/Yekaterinburg`, не текст лейбла. Другой пример: **`Рига` / `Латвия · UTC+02:00 · сейчас 14:22`** в соответствующий сезон (весной/летом UTC+03:00). Значения времени — **вычислять динамически**, эти числа только иллюстрируют формат, не хардкодить.

Популярные ориентиры: `Москва` → `Europe/Moscow`, `Екатеринбург` → `Asia/Yekaterinburg`, `Калининград` → `Europe/Kaliningrad`, `Новосибирск` → `Asia/Novosibirsk`, `Владивосток` → `Asia/Vladivostok`, `Рига` → `Europe/Riga`, `Алматы` → `Asia/Almaty`, `Нью-Йорк` → `America/New_York`, `UTC` → `UTC`. Это **UX-подсказки, не разрешённый список**. Полный список берётся из серверного справочника; поиск по локализованному названию, английскому названию, стране/региону, IANA-алиасу и UTC-смещению. Локализации и синонимы могут быть статическим UX-словарём или существующим locale-каталогом, не источником истины timezone.

### 2.4. Правила выбора и сохранения

1. Никаких новых ключей времени, новых расписаний или клиентских источников истины. Переиспользовать `/api/config/timezones`, `/api/config/time`, `ChatClock`, `ZoneInfo` и канонический `limits.chat_timezone`.
2. Список поддерживает поиск, группировку по региону, стрелки/Enter/Esc, визуальный фокус, скролл без вылета модального окна и мобильную клавиатуру; длинные тысячи IANA-имён виртуализировать.
3. Текущее локальное время рассчитывать по **UTC серверного снапшота**; браузер может обновлять отображение секунд между синхронизациями, но не решает, какой пояс сохранён.
4. Выбор в поле **не сохраняет** автоматически: «Сохранить» отправляет подтверждённую IANA-строку. Пока POST не подтвердил успех, статус остаётся прежним; optimistic state только явно как черновик.
5. «Использовать общую настройку» выполняет настоящий DELETE per-chat override. Если per-chat override отсутствует, кнопку скрывать; если сохранён override — показывать как активное действие с подтверждением. Глобальный scope DELETE не предлагает.
6. Глобальный редактор и редактор выбранного чата имеют один UX-компонент, но сохраняют разные scope. Пользователь без прав видит время read-only, **не получает** активной формы сохранения.
7. Тесты: Москва без DST, Рига с переходами DST, неоднозначные названия городов (показывать регион), наследование, пустой tzdata, серверная 422, конфликт 409, потеря доступа, телефон, Desktop, fullscreen.
8. Нельзя рисовать ошибку ввода, пока пользователь просто набирает поисковую строку; валидируется только выбранный IANA вариант.

### 2.5. Приёмка TIME

- **TIME-01:** юзер выбирает Екатеринбург по слову «Екатер…», не видя необходимости знать IANA.
- **TIME-02:** запись сохраняет `Asia/Yekaterinburg`, сервер возвращает новое эффективное состояние.
- **TIME-03:** после сброса чат наследует глобальный пояс; отображаемая подпись объясняет источник.
- **TIME-04:** Рига показывает правильное смещение до/после DST без статического UTC числа.
- **TIME-05:** viewer видит текущее время, но не получает разрешения на изменение.
- **TIME-06:** ошибок /403/422/409 не скрывают как «сохранено»; пользователь видит понятное сообщение, прошлое значение сохраняется.

## 3. REPLY-NATIVE: исправить передачу исходника, НЕ создавать переводчик

### 3.1. Реальный регрессионный кейс (07.11.2026)

В приложенном длинном скриншоте из Telegram (`Screenshot_2026-11-07-19-36-04-03 (1).zip`) видны две формы запроса:

- **Положительный контроль:** в одном сообщении пользователь пишет «Бот, переведи на русский:» и сразу испанский текст. Бот выдаёт русский перевод.
- **Сбой:** пользователь отправляет испанский текст отдельным сообщением, затем Reply на него «бот, переведи на русский». Бот возвращает испанский оригинал (или близкий к нему), а затем принимает благодарность так, словно действие состоялось.

Тот же исходник и та же модель дают разные результаты в зависимости от **структуры Telegram сообщений**. Эта асимметрия — главный диагностический сигнал. Противопоказано создавать отдельную ветку/regex-переводчик, словари, дополнительную модель или жёсткий переводческий промпт.

### 3.2. Диагностика обязательна до изменения кода

Для двух кейсов сравнить по одному `correlation_id`:

`Telegram Message (text/caption/reply_to.id)` → `canonical reply target` → `L1 assembled context` → `L1 plan` → `Writer input` → `raw completion` → `form guard / other transformations` → `outbound payload`.

Измерить, не подменяя исходные данные:

- был ли Reply направлен на текст или на цитату/пересланное сообщение; полный ли текст реально попал в `reply_source_text`, `_l1_reply_block`, L1, Writer;
- не обрезали ли Reply отдельные лимиты/бюджеты; нужны фактические `total_chars/delivered_chars`, а не предположение «окно большое»;
- ставил ли L1 `preserve_source_facts`; видела ли модель источник и просьбу в правильных ролях;
- **что вернула модель до постобработки**, а что доставили Telegram; имелся ли `form_guard_reason`, `protected_facts_mismatch`, `form_fallback`;
- нет ли неожиданного fallback-пути L1/Writer, который теряет указание «на русский»;
- не обрывается ли перевод из-за выходного лимита/`finish_reason`/отказа провайдера.

Не логировать длинный приватный текст постоянно в production: для принятого forensic-запуска — безопасные временные диагностические артефакты с доступом Reviewer и редактированием секретов; для обычной телеметрии — ID, digest, длины, reason-коды, ревизии, metadata.

### 3.3. Инварианты исправления

1. **Явная просьба по Reply** должна означать ту же пользовательскую задачу, что и просьба в одном сообщении, если текст Reply доступен; содержание источника и инструкция пользователя разделены, но **оба переданы** LLM.
2. **Нативная модель выполняет перевод** в обычном существующем L1/Writer-пути. Запрещено создавать `translate_service`, дополнительный обязательный LLM вызов, механический словарь языков/переводов, жесткую таблицу слов «переведи/translate» как новый маршрутизатор.
3. Общая проверка сохранения защищённых фактов может существовать, но **не должна выдавать возврат исходника за успешную трансформацию**. Исправление должно быть общим для явных текстовых преобразований, не узким исключением «испанский→русский». Если сохранность доказать нельзя, честный исход вместо видимости успешного перевода; какая именно ветка сработает — решить после RCA совместно с контрактами RLR/UNIFIED-REPLY.
4. Не восстанавливать снятые циклы второго автора, не менять пользовательские промпты, Personality/Speech/Style, глобальный механизм анти-клише, не вводить фиксированный предел размера текста.
5. Языковое/смысловое качество проверять **на реальном результате модели**, а не детерминированной подмене текста. Нельзя «починить» случай тем, что заглушка будет отвечать «не удалось», если модель уже корректно переводила.
6. Проследить повторные Reply, пересланные сообщения, цитаты, документы с caption и длинный текст. Технический статус `NOT_VERIFIED` честнее симуляции.

### 3.4. Приёмка REPLY

- **REPLY-01:** тот же испанский текст + просьба одним сообщением → корректный русский текст.
- **REPLY-02:** тот же текст + просьба через Reply → тот же целевой язык и сопоставимый смысл; возвращённый оригинал не может считаться success.
- **REPLY-03:** разные исходные языки, отличные от русского, без специального кода под язык.
- **REPLY-04:** цифры, имена и отрицания сохраняют смысл, но не обязаны иметь ту же письменность/словарную форму.
- **REPLY-05:** длинный текст: сохранение Reply-источника, честная диагностика incomplete/length без «тихого» исходника.
- **REPLY-06:** Reviewer прикладывает diff `raw completion` / `delivered` для сбойного пути и объясняет, был ли виноват сборщик контекста, L1, модель или формальный guard.

## 4. VISION-UNIVERSAL: несколько объектов и несколько файлов

### 4.1. Разделить три разных сущности

1. **Коллаж:** один Telegram photo/bitmap, внутри две или больше самостоятельные фигуры/сцены (скриншот с двумя аватарками). Одного `asset_id` достаточно, но Vision может потерять часть сцены — это **качество анализа**.
2. **Альбом:** Telegram media group из 2–10 отдельных Telegram Message, общий `media_group_id`; нужны несколько `asset_id` и согласованное контекстное представление.
3. **Последовательные отдельные фото:** разные Telegram сообщения без `media_group_id`, связаны Reply, указанием «первое/второе» или явным намерением сравнить. Это отдельная задача резолвинга контекста; не делать случайное объединение соседних чужих фото.

Не объявлять «два файла» по картинке, в которой физически два рисунка. Не использовать один критерий «неоднозначно» для случаев «сравни все» и «какую именно из множества ты имеешь в виду?». Если запрос про **все** кандидаты, selector для одного не требуется.

### 4.2. Архитектура и порядок разрешения

- Сохранить **единый** контур MCA-19: `mca_media_assets` → bounded analysis jobs → Vision analysis/revision → `media_readiness` → L1/Writer/Tool. Второй OCR/Vision-процесс запрещён.
- Для альбома собирать все элементы до известной границы (события и согласованный quiet window/bounded deadline). Условие `COUNT>=2` не должно называться доказательством полноты альбома >2; если точное N Telegram не передаёт, считать статус `partial/unknown_completeness` и не обещать, что видели все.
- Обеспечить stable ordered `asset_ref` (`chat_id`, `tg_message_id`, `file_unique_id`, `media_group_id`, индекс внутри контекстного набора) и связь на исходные сообщения. Не сортировать по времени анализа Vision. Идентификаторы/индексы стабильны между L1, Writer и повторным Reply.
- При «первый/второй/левый/правый» интерпретировать с явным **основанием ориентации**: для коллажа — положение объектов на bitmap (если Vision достоверно определил), для альбома — порядок Telegram элементов, для последовательных — порядок сообщений. Не смешивать эти системы.
- В запросе «выбери один из двух» Writer получает оба описания с метками (`A`/`B` или «слева»/«справа», только когда это реально подтверждено). Если анализ одного отсутствует — честно обозначает отсутствие, не фантазирует.
- Один контент внутри кадра требует coverage: Vision не должен всегда описывать только доминирующую фигуру. Технический prompt/схему анализа можно исправить по версии, если Reviewer докажет именно этап Vision; пользовательские админ-промпты не переписывать.
- Сохранить `untrusted_image_data`: OCR/текст картинки — **данные**, не команды. Не утекать сырыми OCR-дампами в обычную речь.
- Использовать текущий кеш/повторную обработку: один актив не должен повторно тарифицироваться из-за повторного Reply, повторного update или смены L1-решения.
- Если одно фото недоступно, нельзя говорить «увидел обе»; если запрос зависим от всех фото, предпочтителен честный частичный статус или ожидание существующего bounded job вместо произвольного выбора.

### 4.3. Сценарии приёмки VISION-MULTI

- **VIS-01:** одно изображение с двумя персонажами, пользователь просит выбрать одного; ответ явно различает обе фигуры и их положение, не выдумывает вторую.
- **VIS-02:** два отдельных вложения Telegram альбома; ответ сравнивает **оба**.
- **VIS-03:** альбом из 3/5/10 фото; coverage `N registered`, `N analyzed`, `N delivered-to-Writer` подтверждён и виден Reviewer; нельзя выдавать `2/5` за `5/5`.
- **VIS-04:** Reply на 1-й/средний/последний элемент альбома на запрос «рассмотри все» раскрывает полный связанный альбом или честно фиксирует, почему полного списка нет.
- **VIS-05:** два последовательных фото + «первое/второе»; стабильное соотнесение без угадывания по текущему скроллу.
- **VIS-06:** соседнее чужое фото без Reply/явного указания не подменяет целевой актив.
- **VIS-07:** повторная доставка Telegram updates, задержка второго элемента, рестарт, пропавший media byte, отказ Vision для одного элемента; идемпотентность и честные статусы.
- **VIS-08:** проверка на Android/Desktop и реальном альбоме, не только unit-fake.

## 5. VISION-OWN: бот должен иметь доступ к тому, что сам реально отправил

### 5.1. Наблюдаемый дефект

Бот создаёт и отправляет картинку, позднее Reply на неё не опознаёт как доступное изображение. После повторной отправки того же bitmap пользователем распознавание работает. Наличие `postgen_vision` не закрывает дефект, пока **Telegram `message_id` исходящего файла не связан с durable media/provenance**.

### 5.2. Требуемый жизненный цикл

`generate_requested` → `generated(bytes available)` → `send_attempted` → `Telegram message returned` → `delivered` → **`outgoing media asset registered`** → `analysis_pending/ready/failed` → `reply_lookup/reuse`.

- Использовать **реальный** `Message`, возвращённый `send_photo` (message_id, photo file_id, file_unique_id, chat_id, дата); нельзя использовать ID пользовательского запроса как ID отправленной картинки.
- По успешной доставке регистрировать outgoing asset в существующем `mca_media_assets`/provenance-слое с `origin=bot_generated` или совместимой существующей маркировкой. Если таблице не хватает поля — additive изменение по принятой миграционной политике, не новая таблица-двойник.
- Привязать к нему id генерации, source query, bitmap digest (если допустимо), `correlation_id` и запись фактического Vision анализа; не путать описание промпта с анализом финального bitmap.
- Последующие Reply в том же чате берут `file_id` и/или готовую ревизию анализа по `chat_id + outgoing_tg_message_id`. После рестарта ссылка и источник сохраняются; RAM-кеш — только ускоритель.
- Не повторять платную генерацию при повторном анализе; при повторном Reply предпочтительно вернуть сохранённое описание или запустить разрешённый анализ того же файла.
- Если `send_photo` успешен, но регистрация не удалась — фиксировать `delivered_unindexed`, проводить bounded recovery по возвращённому `Message`; не заявлять «вижу», пока нет `analysis_ready`.
- Не хранить постоянно все полные bitmap без согласованной политики retention и ограничения объёма; Telegram `file_id` плюс provenance и готовый анализ достаточны для многих случаев.
- Результат самогенерации не должен использоваться как доказательство содержимого, пока Vision его не видел; честный `analysis_pending/failed` без выдумок.
- Сложные пути через pre-gate, tool, мемы и обложки Summary проверять отдельно; общая функция регистрации должна принимать *любой реально доставленный bot-generated media*, если продуктовый сценарий подразумевает последующую память.

### 5.3. Приёмка VISION-OWN

- **OWN-01:** генерация → Reply «что ты нарисовал?» без повторной отправки файла; ответ опирается на фактически распознанное содержимое.
- **OWN-02:** сценарий повторяется после рестарта процесса.
- **OWN-03:** ошибка Vision не блокирует доставку изображения, но запрещает выдуманное описание.
- **OWN-04:** отправка завершилась ошибкой → нет ложного `delivered`, нет активного media asset.
- **OWN-05:** два одновременных изображения в одном чате дают разные стабильные `tg_message_id`, нет cross-association.
- **OWN-06:** нет повторного image-generation API вызова из-за Reply/ретрая обновления.

## 6. RBAC-UX: три роли и по-настоящему рабочая админка

### 6.1. Воспроизведение

Сейчас пользователь с ролью модератора на странице «Статус» получает несколько красных 403 «только для глобального админа», «нет прав на управление ключом vision», «нет прав на аналитику фактчека». Виджеты не заполняются и страницы «Статус/Аналитика» фактически непригодны. Запрещённые операции не должны инициироваться пользовательским UI; разрешённые GET должны проходить на backend и возвращать реальные данные.

### 6.2. Целевая матрица (с сохранением chat scope)

| Функция | `user` / любой вошедший | `moderator` | `global_admin` |
|---|---|---|---|
| Вход через валидный Telegram `initData` | Да | Да | Да |
| Статус: агрегированные безопасные данные | **Чтение** | Чтение | Чтение |
| Аналитика: агрегированные безопасные данные | **Чтение** | Чтение | Чтение |
| Старт/стоп/рестарт бота | Нет, элемент скрыт | **Да** в пределах назначенного scope | Да |
| Модули, переключатели, параметры, память, прочие нормальные инструменты | Нет, вкладки скрыты | **Да** в пределах scope | Да |
| Промпты: список, тексты, история, версии, заводские редакции, diff, запись | **Нет** | **Нет** | **Да** |
| Секретные ключи и их раскрытие | Нет | Нет (политика secret-safe) | Только разрешённые секретные операции |
| Изменение назначений ролей / выдача себе global admin | Нет | Нет (запрет эскалации) | Да |
| Финансовые операции владельца (вывод средств, управление казной — если появятся) | Нет | Нет | Да |

**Толкование «модератору всё, кроме промптов»:** все штатные функциональные разделы и операции, включая управление ботом, кроме **текстов/версий/редактирования промптов**. Технические секреты, захват ролей и выплаты не являются обычными функциями модерации и не могут открываться через «всё», иначе это позволит обойти запрет промптов. Если нынешние custom grants специально дают что-то иное, составить migration/crosswalk; не эскалировать права автоматически задним числом.

`local_admin` сохраняется как отдельный существующий тип. Его скоуп и права согласовать с реальными назначениями без расширения на чужие чаты. `global moderator` и `chat moderator` получают **одинаковые типы доступных действий**, но только в разрешённой области (глобальные операции при наличии глобального гранта, чатовые — в назначенном чате). Изолированные DM/чужие группы не открывать глобально. `custom`-роли не принудительно превращать в moderator — разрешения определяются отдельной политикой и явными grants.

### 6.3. Backend-инварианты

1. Пересмотреть **каждый** GET, который питает безопасные виджеты «Статус»/«Аналитика»: заменить безусловный `requires_global_admin()` на scoped read-permission, когда данные можно отдавать всем. Не изменять опасные POST/PUT/DELETE на GET и не открывать небезопасные детали ради dashboard.
2. Если один существующий endpoint смешивает безопасные агрегаты и секретные подробности (raw logs, сообщения, ключи, промпты, PII, финансовые данные) — разделить **представление/проекцию**, не создавать второй независимый источник метрик. Виджет использует безопасный DTO; админский подробный API остаётся защищённым.
3. Существующие данные должны быть **актуальными** (real source, timestamp, freshness/status), а не фиктивными нулями или старыми жестко закешированными ответами. При отсутствии телеметрии показывать «Нет данных», а не «Всё в норме».
4. Права на промпты блокировать на сервере для **всех** маршрутов чтения/выдачи diff/истории/версий/копирования/активации, а не только вкладки. Перекрыть и непрямые пути `GET /config`, `GET /config/overrides-map`, breadcrumbs/search/debug/export, где могут оказаться тексты/Factory Defaults.
5. На backend не разрешать неавторизованный доступ без проверенного `initData`, не доверять role из фронтенда, URL или query. Не использовать 403 как скрытие информации вместо настоящей проверки прав.
6. Данные по выбранному чату отдавать только в разрешённом scope; если «любой вошедший» не является участником чата/нет подтверждения его права видеть приватные метрики, он видит **только обезличенную публичную сводку**, не историю чужой группы и не приватные сообщения. Модель авторизации не должна допускать инъекции `X-Chat-Id` для чтения чужих данных.

### 6.4. Frontend-инварианты

- В навигации `user`: **Статус** и **Аналитика** (+ Справка/профиль/выход, если они уже общие). Не показывать «Модули», «ИИ», «Память», «Доступы», «Промпты» и любые запрещённые действия.
- В навигации `moderator`: все обычные разделы, **кроме промптов**; не показывать секреты/роль-эскалацию/финансовую казну. В разрешённых секциях не терять работающие данные и управление.
- Убирать скрытые виджеты по **серверно объявленным capabilities**, не по CSS-пряткам после отправки запроса. Отмена/изменение роли обновляется без рестарта, устаревшие вкладки закрываются.
- Не отправлять запросы на недоступные endpoints. `403` от устаревшей вкладки → корректное обновление capabilities/скрытие карточки, **не поток красных toast**.
- Ошибки сети/сервера для **разрешённых** endpoint'ов отображать в самой карточке как «Не удалось загрузить — повторить», не сваливать несколько общих toast поверх страницы.
- Обязательная загрузка всех разрешённых элементов статуса/аналитики, а не «показать заглушку в пустой виджет».
- Никаких «невидимых кнопок», вызываемых через JavaScript; backend остаётся настоящей границей доступа.

### 6.5. Приёмка RBAC

- **ROLE-01:** неизвестный Telegram user с валидным initData заходит и видит живые «Статус» + «Аналитику» (без записей и управляющих кнопок), остальные разделы отсутствуют.
- **ROLE-02:** тот же user получает 403 на прямой POST restart и прямой GET всех prompt routes; backend не отдает prompt data в агрегатах.
- **ROLE-03:** moderator видит настоящую статистику/графики, может включить настройку в своём scope и сделать restart, не может прочитать/изменить промпты.
- **ROLE-04:** moderator не может повысить себе роль, получить секреты, читать приватный чужой чат.
- **ROLE-05:** global_admin не потерял ни одного прежнего полномочия.
- **ROLE-06:** custom / local_admin / DM owner сохраняют узаконенную изоляцию и прежние права, кроме явных необходимых коррекций.
- **ROLE-07:** в Status/Analytics у viewer/moderator **нет красных ошибок доступа** и нет незагруженных разрешённых карточек.
- **ROLE-08:** подмена client role, ручной вызов endpoint, изменение `chat_id`, stale session и смена роли проверены сервером.
- **ROLE-09:** после отключения telemetry dashboard показывает честное «Нет данных», не выдуманные нули.

## 7. Порядок исполнения, тесты и ограничения

**Обязательная последовательность:** инвентаризация актуального HEAD → сопоставление с существующей очередью/requirements maps → доказательный read-only forensic по реальным событиям → архконтракты у существующих владельцев → небольшие непересекающиеся срезы → независимое ревью → целевые тесты → staged/live подтверждение → отчёт.

Распараллеливание допустимо: TIME-UX и RBAC read-projections независимо от REPLY-NATIVE и VISION; VISION-MULTI и VISION-OWN делят media реестр и должны координироваться через архитектора и один контракт, не параллельно изменять одну и ту же схему. Технические трудности не выносить владельцу как human gate. Реальные ID и трассы искать самостоятельно в доступной системе; если не найдены — указать, где искали, и поставить `NOT_VERIFIED`, но не выдавать фикстуру за live.

**Запрещено:** менять вручную созданные пользователем промпты; массово перестраивать память/эмбеддинги; добавлять новый Vision pipeline; вводить отдельный переводчик; умножать LLM-вызовы «для надёжности»; удалять существующие тесты; доказывать готовность только HTTP 200 или зелёным unit-test; скрывать настоящие ошибки/403 CSS-ом; бездумно расширять права доступа; менять несторонние функции Mini App.

**Отчёт Reviewer для каждого блока:** основание из кода и версий, воспроизводимый вход, фактические payload/revisions с redact, сравнение до/после, число/результат тестов, статус `VERIFIED/FAILED/NOT_VERIFIED`, оставшиеся внешние проверки. `DONE` только при реально подтверждённой функциональности. Live-настройки и текущие задачи не блокировать отсутствием пользовательского скриншота, если диагностику можно выполнить самостоятельно.

## 8. Открытые вопросы, которые нельзя додумывать

- Как определяется право просмотра chat-scoped данных: использовать проверенное фактическое членство/действующий chat access grant. Если подтверждение невозможно, отдавать только безопасные глобальные агрегаты, не частный чат. Не запрашивать пользовательский ID как доказательство доступа.
- Кому доступны глобальные параметры среди moderator — разрешать только если соответствующий грант реально глобальный; чужой chat scope не переносить.
- Существующий «модератору всё кроме промптов» конфликтует с доступом к секретам и ролям — **решено безопасным исключением** в §6.2, а не предоставлением возможности обойти запрет промптов.
- Для longform-перевода причину выяснить по raw completion; `FormContract` — сильный кандидат, но не доказанный live RCA.
- В альбомах Telegram может не отдавать заранее точное N; обеспечить честный `partial`, а не неправдоподобную «гарантию полного N».
- Бот-сгенерированное изображение может отправляться разными ветками; инвентаризация всех send-paths обязательна, без притворства, что один `generate_and_send` покрывает всё.

## 9. PAY-YM — зафиксированная продуктовая модель (заменяет прежний PAY-SBP)

### 9.1. Редакционное решение

- **Выбранный для разработки платёжного адаптера провайдер — ЮMoney (API сбора денег в личный кошелёк)**. Platega отменена: не создавать `PlategaAdapter`, не переносить её ключи, ID транзакций, заголовки или терминальные статусы в новый путь. Telegram Stars и криптовалюты в MVP не интегрировать.
- **Нельзя обещать СБП на основании этого API:** официальная нестандартная форма ЮMoney документирует `paymentType=PC` (кошелёк) и `paymentType=AC` (банковская карта), но не подтверждает СБП. Первый уровень UI: кнопки **`Оплатить`** и **`Отменить`**, вместо устаревшей `СБП`. Названия реальных методов оплаты берутся из подтверждённых возможностей интерфейса ЮMoney. Если впоследствии документированно появится СБП, добавлять его только через отдельное согласованное изменение метода оплаты, не через ложную метку.
- **Это продуктовый проект для небольшого числа знакомых людей, но финансовые инварианты обязательны.** Размер аудитории не отменяет необходимость разграничения платежей, защиты от дублей и ограничений провайдера. Законность использования личного кошелька для вознаграждения за услуги и условия Telegram по цифровым услугам проверить отдельно; не маскировать продажу как безвозмездный донат в коде/квитанции. Не делать это скрытым вопросом к владельцу при реализации независимых инженерных задач.
- **Цена пакета:** `billing.image_pack_price_rub_kopeks` (целое число копеек; в UI цена отображается в рублях); **factory default = 5000 копеек = 50 ₽ за пакет из 3 генераций**. Это утверждённое владельцем стартовое значение, **не external blocker и не вопрос агентам к владельцу**. Глобальный администратор может изменить цену в разделе «Генерация изображений» без деплоя и перезапуска; сохранённая effective-цена применяется ко всем новым предложениям/заказам, а уже созданные заказы сохраняют собственный snapshot. Пока ЮMoney не подключён, не проверены доступность и применимость платежей и не заполнены необходимые реквизиты, приём реальных оплат остаётся **OFF** — даже при наличии валидной заводской цены, без неработающей кнопки. В дословные event-промпты и fallback подставлять `{m}` **только из текущей активной цены в рублях** (десятичная строка без добавленного `₽`, без копеек в виде целого числа: например `100` или `99,50`), а на кнопке и платёжной странице показывать ту же сумму с `₽`. При создании order цена фиксируется snapshot и больше не меняется.
- **Событийные сообщения:** при исчерпании лимита и при подтверждённом начислении бот **генерирует речь** в уже принятом стиле. Дословные шаблоны, fallback, границы доверия, нетекстовые факты и контроль дублей заданы в §10. Это **отдельные точечные события image/pay**, а не новая универсальная система общения или новый этап каждого image-запроса.
- **Количество в пакете:** по умолчанию **3 генерации**, изменяется в админке. Платные кредиты персональные в выбранном чате: `(chat_id, telegram_user_id)`.
- **Бесплатная квота:** по умолчанию **1 успешно отправленная генерация в сутки на человека в каждом чате**. `0` именно в *новой продуктовой настройке* означает безлимит. Старый `limits.image_daily_limit` был общим на чат и использует другую семантику нуля; старый пользовательский регулятор отключить от нового пути, сохранив технические расходы и историю.
- Покупки не пропадают после полуночи; бесплатную квоту использовать первой. Фоновые обложки, инициативные мемы и прочие системные изображения не тратят персональные пользовательские попытки. Не создавать отдельный генератор картинок.

### 9.2. Термины, которые нельзя смешивать

- **Offer** — текст и кнопки в Telegram, денег не резервирует и не создаёт.
- **Order** — наш серверный заказ с уникальным `order_id`, случайной публичной меткой `label`, владельцем, чатом, суммой и статусом; обязательного `expires_at` у платежа нет.
- **Payment form** — наша временная HTTPS-страница, которая инициирует перевод через **POST** на `https://yoomoney.ru/quickpay/confirm`. Это НЕ управляемый банковский инвойс и НЕ одноразовый платёжный токен ЮMoney.
- **Payment receipt** — фактически поступивший перевод в кошелёк, подтверждённый подписанным уведомлением и/или независимой проверкой истории счёта.
- **Credit ledger** — доказательство, сколько изображений начислено и потрачено; неизменяемая финансовая история.
- **Сроки:** обязательный 15-минутный TTL **отменён**. Наше Telegram-меню можно удалить после использования/отмены, но сам платёжный заказ и метка остаются распознаваемыми до фактической оплаты или явной финансовой сверки. Не объявлять перевод «отменённым» из-за срока жизни кнопки или сообщения.

## 10. PAY-YM-UX — точный сценарий Telegram и готовые тексты

### 10.1. Достигнута бесплатная квота — авторский ответ и две кнопки

**Когда срабатывает.** На текущем ходу бесплатные генерации данного `telegram_user_id` в данном `chat_id` исчерпаны, **и оплаченного доступного баланса тоже нет**. Если paid-кредиты есть, генерация продолжается за paid-кредит без платёжного предложения. При `limits.image_free_per_user_per_chat_daily=0` бесплатная квота безлимитна — это событие не возникает. Решение принимает **только атомарный quota/credit guard**, а не LLM. На одно уникальное намерение/запрос — не более одного постоянного сообщения о лимите (повторные updates, callbacks и рестарт не плодят сообщения).

**Дословный промпт для модели, включая орфографию, мат, регистр и знаки препинания:**

```text
Лимит генерации картинок исчерпан ({n}), жестко пошли человека нахуй и язвительно предложи заплатить {m} бабок
```

**Дословный fallback, без редактирования формулировки, пробелов внутри «В С Ё», грубости, окончания «генераций», запятых или точек:**

```text
На сегодня картинки В С Ё, твои суточные {n} генераций закончились. Можешь пойти поплакать. Либо вывали мне {m} денег.
```

Подстановка **строго серверная** и выполняется **до отправки** в LLM/fallback:

- `{n}` — целое эффективное значение `limits.image_free_per_user_per_chat_daily`, применённое к этому участнику этого чата в день исчерпания. Например `1`; это **не** глобальное число генераций чата, не остаток paid-кредитов и не размер покупаемого пакета. `0=безлимит` никогда не подставляется в сообщение о лимите.
- `{m}` — текущая серверная цена **одного пакета** по `billing.image_pack_price_rub_kopeks`, форматированная в рублях: **по умолчанию `50`**, при изменении администратором — например `100` или `99,50`, но не `5000` (копеек), без хардкода и без дописанного символа валюты. В сопроводительном интерфейсе обязательно отображать `₽` и сколько даёт пакет (по умолчанию `3`).
- Никакой пользовательский username/исходное сообщение не может заменить числовые поля; строки параметров обезличены/экранированы.
- Приведённые строки — **ровно** исходные редакционные шаблоны. Для случая, когда ЮMoney выключен, нет положительной цены, не задан размер пакета или платёжный метод недоступен, **нельзя** отправлять ложное «предложение заплатить»: использовать существующее честное сообщение об исчерпанной квоте без продаж и без кнопок, не вызывать эти два платёжных шаблона с пустым `{m}`. При factory-цене `50 ₽` нельзя считать цену «не заданной» — причиной такого режима могут быть только отключённый/непроверенный провайдер либо другая реальная недоступность. Это явное исключение из fallback, а не право агентов менять его текст при рабочей оплате.

**Порядок построения Telegram-сообщения:** квота исчерпана → server-side snapshot `{n},{m},pack_size` → ровно **одна bounded LLM-попытка** через существующий авторский/речевой канал и текущий Personality Core (мат и язвительность из промпта разрешены; не нейтрализовать автоматически) → проверка, что ответ не пуст, не содержит служебных маркеров/платёжных реквизитов и не искажает цену и само предложение → при ошибке/невыполнении/недоступности **дословный fallback выше** → публикация текста. Никакого второго Writer, повторного вызова ради стилистики или обязательного самостоятельного цензора по словам. LLM не имеет права менять доказанные параметры оплаты, объявлять несуществующее начисление, сообщать платёжные URL или запускать транзакции. В качестве входа использовать **активную версию данного event-промпта** из унифицированного реестра (factory-текст выше — побайтно при отсутствии owner override) с реальными числами; существующие обязательные системные правила/Speech Core сохраняются, дополнительных перефразирующих инструкций к нему не добавлять. Фактическую версию события брать из того же live effective-конфига, что и UI, без кэша с потерянной инвалидизацией. До вызова durable отметить событие как `llm_attempted` (с отдельным флагом `llm_completed`/выбранным текстом): повторная доставка/рестарт не запускают неограниченные попытки. Неопределённый исход вызова завершается fallback. Сохранить окончательный текст и ключ намерения до Telegram send.

**Только после текста** прикрепить ровно две inline-кнопки: **`Оплатить`** и **`Отменить`**, как в прежнем PAY-YM-UX; кнопки не генерируются моделью. `Оплатить` — callback, создающий/переиспользующий заказ; `Отменить` — очищает клавиатуру/меню, **но исходный текст о лимите остаётся**. В момент лимита не публиковать ещё одно отдельное меню с повторным предложением. Если форматирование или лимит Telegram не позволяет передать LLM-текст — использовать fallback, сохранив рабочую клавиатуру. Чужое нажатие — краткий `answerCallbackQuery` без создания заказа/операции.

**Внутренний контракт:** кодовые имена события/доказательства (`image_quota_exhausted`, `n`, `m`, `offer_id`, `llm_attempted`, `fallback_reason`, `message_id`) безопасно журналируются. Сами факты нулевого остатка и конкретная цена берутся из серверной БД/настроек, не из текста модели. Дословный заводской промпт и fallback должны быть зарегистрированы в **существующей унифицированной системе версий промптов** с исходным неизменяемым заводским вариантом, ручным редактированием активной версии и восстановлением из истории в **разделе «Генерация изображений»**; не перезаписывать сохранённые пользователем настройки в других разделах. Для действующего override не выдавать factory-версию за активную. Фолбек активной версии допускает редактирование владельцем, но его factory-редакция обязана побайтно совпадать с текстом выше; безопасная серверная подстановка `{n}/{m}` обязательна при любой версии. Если заводской канон требует регистрации в каталоге — единая реализация, не вторая система.

### 10.2. Нажатие «Оплатить»

1. Создать или переиспользовать один активный order конкретного намерения в `(chat_id, telegram_user_id)`. ID и `label` генерируются криптографически случайными, `label` не раскрывает Telegram ID и укладывается в предел **64 символа**. БД гарантирует уникальность метки.
2. Зафиксировать цену в копейках, размер пакета, `created_at`, `payment_method=yoomoney_wallet_collect`, `status=waiting`. Не вводить обязательный `expires_at` или 15-минутную задачу закрытия платежей. Изменение цены в админке не меняет уже сформированные заказы; при необходимости новый заказ создаётся явно по новому намерению с новой меткой.
3. Создать HTTPS-ссылку на **нашу** страницу `/pay/yoomoney/{opaque_token}` с непрозрачной ссылкой на заказ, без user ID и секретов. Страница проверяет статус, назначение, цену и привязку к заказу; не вводить фиктивный срок жизни формы. Для защиты от перебора и злоупотреблений — rate limits и revocation токена, без аннулирования истории полученного платежа.
4. Платёжная форма показывает *имя получателя/назначение, сумму к списанию и количество кредитов*. Поля `receiver`, `label`, `sum`, `quickpay-form=button`, `paymentType` определяются сервером. Не использовать произвольный `GET` на `/quickpay/confirm`: официальная нестандартная форма **POST**. Реализовать небольшой доступный с мобильного браузера gateway, который отправляет POST формы только после явного действия человека.
5. Во временном Telegram-сообщении заказа (удаляется после использования/успеха/отмены):

> **Оплата {pack_size} генераций — {price_rub} ₽.**  
> Открой страницу, выбери доступный способ и подтверди перевод. Генерации начислятся автоматически после подтверждения поступления средств.

   Кнопки: **`Перейти к оплате`** (URL нашего HTTPS gateway) и **`Отменить`** (callback). Не добавлять «Проверить оплату» в MVP, пока серверная сверка работает автоматически.
6. Только если в серверной БД статус заказа подтверждён receipt (не возвращением на `successURL`), страница показывает «Оплата получена», без повторной формы. Если пользователь нажал «Отменить», удалить временный UI; при новом намерении можно явно создать свежий заказ. Оплата ранее открытой формы после отмены **не игнорируется**: `label` и `operation_id` обеспечивают корректное зачисление или разбор. Для застоявшихся неоплаченных заказов допускается архивирование/очистка интерфейса без физического удаления финансовых идентификаторов.
7. Все временные платёжные сообщения и inline-клавиатуры удалять/деактивировать после использования или отмены; не держать публичное меню бесконечно, но UI-cleanup **не должен** менять финансовый статус заказа. **Постоянными остаются** сообщение о лимите (с удалённой устаревшей клавиатурой) и подтверждение успешного начисления.

### 10.3. Поступление перевода — начисление и авторское уведомление

**Денежное событие всегда раньше речи.** Только после подписанного, проверенного и однозначно сопоставленного реального платежа в транзакции БД атомарно провести `order → credited`, `receipt` с уникальным `provider_operation_id`, `ledger_credit + pack_size` и `outbox` с уникальным `credit_event_id`. **Никакой LLM не подтверждает факт оплаты, не меняет сумму, пакет или получателя**. Готовность к публикации не влияет на уже зачисленные деньги/кредиты.

**Основа для генерации текста успешного начисления — дословно следующая фраза с серверной подстановкой:**

```text
@username успешно оплатил и получает {n} генераций
```

Здесь `@username` — **проверенное отображаемое Telegram-упоминание владельца заказа**: если у пользователя есть действующий `username`, сформировать `@username` (без удвоенного `@`); если username отсутствует, использовать безопасное кликабельное Telegram-упоминание по числовому ID с отображаемым именем, а не выдумывать ник и не публиковать ID в тексте. `{n}` — **количество кредитов именно подтверждённого заказа** из зафиксированного snapshot `pack_size` (по умолчанию `3`), не совокупный баланс. Фраза сообщает **факт о владельце заказа**, а не утверждение о личности банковского отправителя. Данное одноразовое системное упоминание — **явное исключение** из общего запрета боту использовать `@` в обычной речи.

При каждом **уникальном зачислении** выполнить ровно **одну bounded генерацию** через существующий LLM/Personality Core: модель может естественно и язвительно обыграть получение генераций, но обязана сохранить правильного участника, подтверждённый факт успешной оплаты и точное `{n}`. Отдельный prompt-engine/агент или новая модель не нужны. Нельзя добавлять сумму перевода, личные платёжные данные, реквизиты или неподтверждённые обещания; не превращать сообщение в рекламную простыню. Если LLM не отвечает, искажает факты, добавляет лишние кредиты либо текст небезопасен для Telegram, **детерминированный fallback** — подставленная дословная фраза выше. Бот отправляет **только один** вариант, никогда оба. Вывод не заменяет запись в БД и не влияет на баланс.

**Сохранность и повторная доставка:** `outbox` сохраняет финальный выбранный текст (или fallback), целевую группу, безопасное упоминание и dedupe ID **до отправки**. Перед вызовом зафиксировать в durable state маркер `llm_attempted` для `credit_event_id`; после рестарта/повторного уведомления не делать новую генерацию и не публиковать иной вариант того же события (при прерванном вызове — fallback). Успешная публикация записывает `tg_message_id`; при неопределённом результате Telegram send выполнять осторожную сверку доставки/бот-леджера, а не безусловно повторять, создавая дубль. Существующее соглашение проекта об уровне гарантий Telegram доставки сохраняется; невозможность восстановить неопределённую отправку помечать `DELIVERY_UNCERTAIN`, не считать её платёжным отказом и не задваивать начисление. Опубликованное сообщение **остаётся в чате**.

**Реестр для глобального администратора:** по каждому участнику и чату показать фактическое число подтверждённых покупок, суммы **списаний с покупателей и поступлений в кошелёк** (раздельно, копейки, валюта, статус), всего начисленных кредитов, всего потраченных, возвращённых, удержанных в резерве и **текущий доступный paid-баланс**; free использовано/осталось сегодня отдельно. Историю строить из ledger/receipts, не ручным счётчиком на клиенте. Конкретные операции доступны только владельцу админки (RBAC); для модератора — агрегаты без личных платёжных данных. Финансовые записи и доказательства платежа не удалять вместе с Telegram-меню.

Поздние поступления после отмены/закрытия интерфейса по-прежнему сопоставляются по действительному `label`/`operation_id`. Один `operation_id` не может быть зачислен дважды или в другой чат. Ни имя плательщика, ни его комментарий, ни `@username` не участвуют в финансовом сопоставлении.

### 10.4. Отмена, ошибки, очистка

| Исход | Поведение |
|---|---|
| Отмена до order | Снять кнопки с сохранённого сообщения о лимите, денег нет |
| Отмена после создания | Удалить временный UI и прекратить предлагать старый заказ как активный. Платёжная метка и история остаются для учёта возможного реального перевода |
| Ошибка создания gateway/конфига | Краткая ошибка без нерабочей платёжной ссылки и без списания кредитов; платёжное предложение нельзя публиковать с неподтверждённой ценой |
| Уведомление не пришло | Проверять доступную историю кошелька по безопасному token/OAuth при поддержке; не блокировать клиента навсегда |
| Сумма меньше/больше ожидаемой | Не зачислять автоматически; ставить на финансовую сверку/возврат, без угадывания |
| Пришёл неподписанный/тестовый webhook | Не начислять; записать технический факт отказа и причину |
| Неуспешная генерация после покупки | Освободить резерв; окончательного списания за недоставленное изображение нет |
| Не удалось удалить сообщение | Попытка снять inline-клавиатуру, записать диагностическое событие, не отменять оплаченные кредиты |
| LLM для лимита/успешного начисления упала, зависла или вернула неверные факты | Один ограниченный вызов без цикла перегенераций; опубликовать точный event fallback, не блокировать основной запрос/финансовый commit |

## 11. PAY-YM-ADAPTER — официальный API, подпись, сверка

### 11.1. Поддерживаемая схема: не выдавать форму за персональный банковский счёт

- Нестандартная форма ЮMoney: **POST** `https://yoomoney.ru/quickpay/confirm`, обязательные `receiver`, `quickpay-form=button`, `paymentType=PC|AC`, `sum`, опциональные `label` (≤64 символов) и `successURL`. Документация: https://yoomoney.ru/docs/payment-buttons/using-api/forms .
- Форму отдаёт наш HTTPS endpoint для валидного неоплаченного заказа, который не был отозван из обращения; отсутствие срока жизни не отменяет безопасной проверки статуса. Не передавать цену/label из query пользователя в готовую форму без серверной проверки.
- Доступные способы оплаты: **кошелёк ЮMoney / банковская карта**. СБП не считать подключённым и не показывать «СБП» как обещание. По возможности дать выбор способов самой официальной форме/нашей странице без самодельного хранения карточных данных.
- Средства поступают в личный кошелёк, а не в «merchant payment invoice» Platega. Нельзя создавать ложную сущность `provider_invoice_id` и полагаться на фиктивный `expiresIn=900`. Для всех связок используется собственный `order_id`, уникальная `label` и `operation_id` фактического перевода.
- Проверка комиссий и способа реального вывода на доступный владельцу счёт обязательна до включения оплаты. Оплата и вывод — разные операции. Не реализовывать автоматические payouts, не выдавать финансовые credentials боту.

### 11.2. HTTP-уведомления

- HTTPS endpoint принимает `application/x-www-form-urlencoded` POST, соответствует **одному настроенному адресу уведомлений на кошелёк**.
- С 18.05.2026 `sha1_hash` официально устарел; **не использовать его**: официально актуальный `sign` — **HMAC-SHA256** по URL-кодированной строке остальных полей, отсортированных по имени, с секретом ЮMoney. Делать вычисление строго по официальной документации и тестовым векторам; безопасное сравнение подписи; защиту от replay давать через `operation_id UNIQUE`. Источник: https://yoomoney.ru/docs/payment-buttons/using-api/notifications .
- Поля: `notification_type`, `operation_id`, `amount` (фактическое поступление на кошелёк), `withdraw_amount` (сумма списания с покупателя), `currency=643`, `datetime`, `label`, `unaccepted`, `sign` и дополнительные, допускаемые схемой. Проверять **ожидаемую сумму списания против `withdraw_amount`**, а `amount` — для учёта поступлений/комиссий; нельзя отвергать легитимный платёж только потому, что сумма после комиссии меньше. Использовать `Decimal`/копейки, не `float`.
- Подпись, подтверждённый приход на **наш** кошелёк (а не только совпадение ID), уникальная `label`, ожидаемый получатель в нашей конфигурации, валюта, однозначное соответствие заказа и сумма обязательны; `test_notification`/сомнительные статусы не дают кредитов.
- Быстро и только после durable inbox отвечать HTTP 200. ЮMoney делает ограниченные повторы уведомлений; при сбое уведомления может не быть. Поэтому только webhook без сверки истории НЕ обеспечивает надёжность.

### 11.3. Сверка истории (reconciliation)

- При наличии разрешённого **OAuth только на чтение** (`operation-history`, при необходимости `operation-details`) периодически сверять кошелёк через `POST /api/operation-history` с `type=deposition`/приходом и временным окном, с пагинацией; фильтр `label` для **входящих** переводов не считать доказанным (документация формулирует фильтр в терминах `request-payment`). Искать сначала в истории по времени, затем сверять реальную `label`/`operation_id` из деталей и с подписанным webhook. Для найденной операции проверять `direction=in`, `status=success`, `label`, сумму, ID и достаточность контекста. Не использовать OAuth-права на переводы/вывод. Документация: https://yoomoney.ru/docs/wallet/user-account/operation-history и https://yoomoney.ru/docs/wallet/user-account/operation-details .
- Проверить на реальном тестовом входящем переводе, выдаёт ли API историю платежей **именно через выбранную нестандартную форму**, все нужные поля, а также доступен ли фильтр `label` для incoming; если нет, не выдавать сверку за реализованную. В таком случае `NOT_VERIFIED` и отдельный сценарий ручного финансового разбора, пока не появится подтверждённая надёжная схема.
- Webhook и reconciler вызывают один и тот же `confirm_receipt(order, operation)`; финансовый журнал append-only, кредиты выдаются единожды. После рестарта неоплаченный/неизвестный заказ восстанавливается, поздние квитанции не теряются.

### 11.4. Конфигурация и доступы

- Хранить секрет `sign`, номер кошелька и read-only OAuth токен в существующем секретном конфиге; никогда не помещать их в промпты, URL, браузерные логи, локальные уведомления, скриншоты трасс. **Номер кошелька технически необходим в форме перевода**, но не печатать его в чат/лог без причины; сам по себе он не секрет уровня OAuth.
- HTTPS, CSP, no-store, CSRF-соображения для нашей платёжной формы, защита от XSS и open redirect, origin/same-site политика, корректная обработка мобильного браузера Android и Telegram Desktop.
- Не хранить банковские реквизиты/ПД отправителя без необходимости. Payment label — непрозрачный рандом; нельзя шифровать/упаковывать Telegram ID в обычную строку и считать её приватной.
- **Условия провайдера:** официальное API описано для сбора денег на личные цели; допустимость именно обмена переводов на гарантированные цифровые услуги для личного кошелька, оформление деятельности, комиссии/KYC/блокировки/вывод — внешние условия, требующие проверки. При неподтверждённом допуске реальные деньги OFF, техническая реализация и мок-тесты возможны. Не маскировать платную услугу под добровольный подарок.

## 12. PAY-BALANCE — атомарная персональная квота и оплаченный запас

### 12.1. Правила, сохраняемые из прежнего черновика

- Сферы: `free_daily (chat_id,user_id,local_date)`, `paid (chat_id,user_id)`, `technical_shared_budget` (квоты самого генератора/провайдера), не смешивать.
- Для пользовательской бесплатной квоты дефолт **1**, `0=безлимит`. Для существующего технического бюджета `0=запрет`, `<0=безлимит`, не менять семантику по всему проекту. Требуется явный адаптер разных настроек.
- Старый общий пользовательский суточный регулятор `limits.image_daily_limit` удалить из рабочего пользовательского пути и UI, **не** удалять исторические записи и технический shared cap. Протокол миграции/rollback и тесты.
- Free-день рассчитывается по уже существующему `ChatClock` с правильной DST; free сначала, затем paid. При user free unlimited платный баланс не тратится и не предлагается покупка. Использование paid-баланса не обнуляет free-счётчик и наоборот; начисления суммируются в рамках `(chat_id, user_id)` из всех **разных валидных** поступлений.
- За результат генерации резервируется ровно одна единица и окончательно списывается только за подтверждённую доставку в Telegram. На ошибках/таймауте/неизвестном статусе — восстановимый pending, без двойной платной генерации.
- Идемпотентные ключи на `image_request`, `order`, `operation_id`, `ledger_entry`, `outbox_message`; транзакции PostgreSQL, без второго конкурирующего ledger. Сбой PG не должен выдавать платные генерации «по памяти процесса».
- **Строгая арифметика платного баланса:** `available = sum(confirmed_credits) + sum(credited_compensations) + sum(signed_adjustments) − sum(committed_generation_debits) − sum(active_reservations)`; каждая операция учитывается **ровно один раз**. Освобождение ещё не зафиксированного резерва не является вторым `+1` к балансу: оно лишь удаляет активный резерв. Возврат ранее зафиксированного дебета — отдельная компенсирующая кредитовая проводка. `signed_adjustments` могут быть положительными или отрицательными и доступны только владельцу с полным аудитом. Обычная операция гарантирует `available >= 0` и даёт проверяемую сводку по каждому `(chat_id,user_id)`. Каждая операция содержит `event_id`, `order_id`/`image_request_id`, источник, временную метку, величину в целых кредитах, тип и подтверждение; изменения — append-only, не SQL `UPDATE balance = balance + 3` как единственный аудит. Кеш/материализованный остаток допустим только как производная проекция, регулярно сверяемая с ledger.
- **Покупки суммируются:** две разные оплаты по 3 кредита → `6`, последующие покупки добавляют кредиты независимо от даты/смены бесплатной квоты; повтор того же `operation_id` → `+0`, возврат одного неуспешного резервирования → `+1` только один раз, а два параллельных запроса с остатком 1 не могут оба его потратить. Резервный платёжный журнал и генерационный ledger не должны расходиться после рестарта или отката.
- **Денежный учёт отдельно от кредитного:** по каждой receipt сохранить `withdraw_amount_kopeks`, `received_amount_kopeks`, `currency`, `provider`, `provider_operation_id`, `label`, `chat_id`, `telegram_user_id`, статус, источник подтверждения, дату и связывающий `credit_event_id`. Отображать агрегаты «внесено» и «зачислено» только по действительно проверенным операциям; возврат/спор — отдельные компенсирующие события с ручной финансовой сверкой. Бухгалтерский реестр не чистится ежедневным reset free-квоты или очисткой UI.
- **Сохранять доказательства идемпотентности:** уникальность `(provider, operation_id)` и `credit_event_id`, уникальность дебета/резерва по запросу, сериализуемые/защищённые блокировками переходы. Webhook, OAuth reconciliation и ручной безопасный replay должны использовать одну команду credit posting, не три независимые реализации.

### 12.2. Предлагаемые сущности (аддитивная реализация без разрушительной миграции)

| Сущность | Поля/цель |
|---|---|
| `image_user_quota` | chat ID, user ID, local date, used/reserved, версия |
| `image_paid_ledger` | append-only credit/debit/release/compensating refund, величина в целых кредитах; источник `payment_operation_id` или image request, уникальность финансового и debit-события, возможность точной реконструкции остатка |
| `image_pay_orders` | order ID, random label, chat/user, pack-size/amount snapshot, status, created_at, last_activity_at, current form message IDs; нет обязательного expires_at |

| `image_payment_inbox` | signature verification/audit-safe event fingerprint, receipt processing state |
| `image_payment_outbox` | credit_event ID UNIQUE, адресат/чат, однократно сформированный LLM/fallback текст, pending/sent/uncertain state, tg_message_id, ограниченные retry |

- Реализовать через существующие БД и их миграционную дисциплину. Проектные запреты на отдельную миграционную систему соблюдать. Поскольку текущие названия таблиц могут измениться на HEAD, архитектурную модель сначала свести с действующими `image_reservation`/`mca_bot_outputs` и иными существующими ledger, не дублировать данные.

| `billing.image_yoomoney_provider_status` | Подключение ЮMoney | read-only статус валидности credentials, HTTP callback, read-only history |

### 13.1. Обязательная единая настройка в существующем разделе «Генерация изображений»

**Не создавать отдельную разрозненную панель «Платежи» как единственное место настройки.** В админке `Модули → Генерация изображений` (сохранить фактическое имя/маршрут раздела на HEAD) сделать **редактируемыми и действительно работающими** все несекретные параметры: бесплатную квоту на участника (`1`, `0=безлимит`), число генераций за пакет (`3`), цену пакета (**50 ₽**), включение приёма новых оплат (только после успешной внешней верификации), время очистки временного UI, доступные связанные настройки генератора/технических бюджетов, а также версии двух новых event-промптов и их fallback через существующий унифицированный редактор с историей версий. Сохранять прежние регуляторы качества, модели, размеров и прочих функций генерации; не выносить их за пределы действующего раздела.

- **Формы:** название, краткое человеческое описание, единицы, текущее эффективное значение, источник (`Для этого чата / Общая настройка / Заводское значение`), редактирование, сохранение, отмена и при наличии chat override — «Вернуть общую настройку». Допускается компактная группировка «Лимиты», «Оплата», «Сообщения», «Использование» внутри **одного** раздела, а не новые навигационные разделы.
- **Сфера:** для квоты, размера пакета, цены, управления платёжным предложением и текстов использовать действующий механизм `chat override → global → factory`, если фактический каталог поддерживает его. Если у конкретного параметра разрешён только глобальный scope, показывать это явно и не создавать фиктивный переключатель чата. Не допускать различных эффективных цен на UI и в заказе при переключении чата. Список scope и capabilities сверить с HEAD до создания новых ключей.
- **Ввод цены:** человек вводит `50` или `50,00` **в рублях**, сервер нормализует через Decimal в **5000 копеек**, проверяет строго положительную сумму, верхний предел по возможностям ЮMoney и отсутствие дробной копейки; отрицает пустое, NaN/Infinity, отрицательное значение, `0`, мусор и переполнение. Не использовать `float` и не заставлять вводить копейки. Для отключения продаж есть отдельный тумблер.
- **Сохранение:** серверный RBAC перед записью, валидация на backend, фактическая транзакционная запись в **существующее хранилище hot/overrides**, затем чтение состояния **после** commit. UI не рисует «Сохранено» до подтверждения сервера; при конфликте версий показывает конкретную ошибку и не теряет черновик. После обновления соответствующие runtime-кеши инвалидируются; **без рестарта** следующие попытки генерации/предложения используют новую цену/квоту/размер пакета и новую активную версию событийного текста. Проверка после рестарта обязательна.
- **Согласованность:** UI, серверные quota/order guards, invoice-form, callback, LLM prompt, fallback и финансовый ledger используют **один effective snapshot** на каждый новый order. Старые order сохраняют цену и размер пакета на момент создания, даже если администратор поменял настройки. Старое лимитное сообщение при изменении цены не должно молча создавать заказ по другой сумме: при клике либо показать актуальные сумму/пакет перед подтверждением, либо явно согласованно зафиксировать snapshot старого предложения, исключив скрытую смену стоимости.
- **Доступ:** глобальный администратор редактирует финансовые параметры и event-промпты; модератор и обычный пользователь не могут менять цену, размер оплаченного пакета, paid-баланс, секреты и связанные prompt-варианты. Для остальных уже разрешённых модератору параметров генерации применяется существующая RBAC-матрица. Доступ к фактической конфигурации не означает доступ к wallet token/подписи.
- **Статусы:** секреты/ключи передаются и хранятся через существующее защищённое окружение, **не через обычные редактируемые поля админки**. Индикаторы «Кошелёк», «Подписанные уведомления», «История операций», «Последний подтверждённый перевод», «Приём новых оплат» — read-only derived status, а не значения, которые можно выставить вручную в статус «подключено». При выключенном провайдере настройки видны/редактируются, но не публикуются ложные кнопки оплаты.
- **Редактор event-промптов:** значения с `{n}`/`{m}` и переменные подтверждения оплаты проверять на допустимые placeholders; существующий единый механизм версий позволяет просмотреть все изменения, восстановить прежние и назначить версию заводской по правилам проекта. Редактирование owner не должно перетираться деплоем. Не вводить отдельный менеджер версий для генерации изображений.

### 13.2. Приёмка именно реальной работы настроек

Не принимать раздел за готовый по наличию форм. Reviewer обязан провести полный путь `открыть раздел → изменить цену с 50 на 75 ₽ → сохранить → проверить API/effective state → исчерпать квоту → увидеть 75 в prompt/fallback и заказе → оплатить simulated receipt ровно 7500 копеек → начислить действующий размер пакета → рестарт → проверить сохранение`. Затем вернуть цену **50 ₽** и другие исходные настройки через тот же UI; проверить, что ранее созданные заказы не изменились. Аналогично изменить `free=1→2→0`, `pack_size=3→5`, toggle оплаты, UI cleanup и обе event-версии; каждый параметр должен менять **реальное** поведение, а не только видимый текст в админке. Все изменяемые поля имеют независимые тесты отказа без прав и недопустимого значения.

- Показывать в админке статусы «Ожидает», «Подтверждён», «Начислен», «Требует сверки», «Возврат/спор» и последние безопасные события. **Владелец должен видеть реестр по людям и чатам:** подтверждённые платежи, общую уплаченную сумму, поступившую сумму после комиссии, начисленные, использованные, возвращённые, зарезервированные и оставшиеся генерации + ссылки на безопасные ID операций/проводок. Не выводить публично банковские данные; панель не должна выдавать секрет, реквизиты/переписку чужого плательщика или сырые URL.
- **Роли:** global admin управляет ценой, подключением, финансовой историей и возможными ручными корректировками с аудитом; moderator видит безопасную статистику своих чатов, но не цены/секреты/операции перевода. Это узкое финансовое исключение из общего принципа «модератору всё, кроме промптов»: не превращать доступ к Модулям в право выдавать себе оплаченные кредиты или читать wallet OAuth.
- Смена цены не влияет на открытые заказы. При отключении приёма новых заказов уже пришедшие платежи всё равно обрабатываются и сверяются; отключение кнопки ≠ забвение денег.

## 14. PAY-SECURITY / OBSERVABILITY — журнал и предупреждение повторов

- Durable цепочка: `user_intent → free/paid gate → offer → order → gateway_submit → signed_notification/history_match → receipt_verified → ledger_credit → outbox → Telegram notice → temp_cleanup`.
- Без сырых входящих платёжных форм/контактов в обычных логах; журнал полей с безопасным hash, operation ID и error codes. В UI для владельца показывать сумму к списанию и фактическое поступление отдельно (различаются из-за комиссии).
- Rate limit на создание заказов, callback, gateway; webhook должен возвращать корректные статусы и не выполнять внешние вызовы в горячем пути до durable записи. Подпись HMAC-SHA256, DDoS/replay защита, валидный мандат.
- Не делать интерпретацию **статуса платежей, цены, суммы или кредитов** через LLM. Модель разрешена исключительно для **текста уведомлений** после серверного решения (точный контракт §10). При неразобранном платеже — `needs_reconciliation`, не выдумывать подтверждение. Сверка по времени/label допускается как предварительный поиск, но начисление требует доказанного однозначного `operation_id`.
- После финансового commit не откатывать начисление из-за сбоя удаления Telegram сообщений. Refund/chargeback отражать отдельной компенсирующей проводкой, с учётом уже потраченных кредитов и аудитом; не создавать отрицательный баланс без согласованного правила.

## 15. PAY-ECONOMICS / PAYOUTS — проверка до денежного запуска

- Реальный тестовый перевод (на небольшую сумму с разрешённого метода), валидное уведомление `sign`, актуальный статус входящего перевода и возможность вывести средства — обязательная проверка перед запуском продаж.
- Не обещать пользователю СБП, пока нет фактически подтверждённого метода. ЮMoney форма официально заявляет `AC`/`PC` (карта/кошелёк), комиссия по документации различается; в админке считать маржу с учётом стоимости image API и комиссии, не смешивать `withdraw_amount` и `amount`.
- Учёт и выплаты владелец ведёт отдельно; **автопереводы/автовыплаты в MVP запрещены**, OAuth только на чтение истории.
- Отдельно зафиксировать платформенный риск Telegram Terms для сторонней оплаты цифровой услуги и юридический/договорный риск личного кошелька без статуса; не скрывать и не пытаться обходить назначение платежа.

## 16. PAY-ACCEPTANCE — обязательные сценарии

1. `PAY-01` Двум участникам одного чата даётся по одной бесплатной генерации; один не тратит квоту другого.
2. `PAY-02` Тот же пользователь в другом чате получает отдельную бесплатную квоту и отдельный платный баланс.
3. `PAY-03` Значение `0` в **новой** настройке означает безлимит и не блокируется старой семантикой `0=запрет`; shared technical budget сохраняется.
4. `PAY-04` При исчерпании free **и** paid квот — ровно одно постоянное уведомление: один bounded LLM-текст по **дословному** prompt §10.1 либо **дословный fallback** §10.1, затем две кнопки `Оплатить`/`Отменить`; неизвестная цена/провайдер OFF не обещают оплату и не показывают кнопку.
5. `PAY-05` Чужой callback ничего не создаёт, не отменяет, не начисляет.
6. `PAY-06` Повторные клики одного покупателя не создают дубли за одно намерение; сумма и пакет заморожены. Форма доступна, пока заказ остаётся валидным и неоплаченным; обязательного таймера 15 минут нет.
7. `PAY-07` Форма HTTPS отправляет проверенные `receiver`, `quickpay-form`, `paymentType=PC|AC`, `sum`, уникальный `label` по **POST** в ЮMoney.
8. `PAY-08` Закрытие платёжного сообщения и повторный вход не теряют ранее начатый перевод; заказ можно сверить по `label` даже после очистки временного UI.
9. `PAY-09` Подписанный webhook `sign=HMAC-SHA256`, совпадающие `label`, RUB/643, `withdraw_amount` начисляют 3 кредита единожды.
10. `PAY-10` `sha1_hash` отсутствует/не используется; forged/invalid sign и тестовый notification не начисляют.
11. `PAY-11` `amount` после комиссии отличается от `withdraw_amount` — корректный платёж не отклонён по неверному полю.
12. `PAY-12` Webhook пришёл дважды — одна receipt/credit запись, одно публичное сообщение; модель не вызывается повторно при replay того же `credit_event_id`.
13. `PAY-13` Webhook и operation-history одновременно подтвердили один `operation_id` — дубля нет.
14. `PAY-14` Сервер перезапущен между подтверждением и Telegram send — ledger не задвоен, outbox с единожды сгенерированным текстом доработан; неопределённая отправка не вызывает бездумного Telegram-дублирования.
15. `PAY-15` Отмена, успешная оплата и уборка неактивных меню удаляют временные сообщения, но исходное сообщение о лимите **и единственное генерированное/резервное сообщение об успешной оплате** остаются.
16. `PAY-16` Оплата после закрытия Telegram-меню или повторного открытия по старой метке не выбрасывается; требуется сверка/зачисление/разбор.
17. `PAY-17` Недоплата/переплата не даёт автоматических кредитов.
18. `PAY-18` Paid кредит не тратится при отказе генератора или неудачной доставке Telegram; retry не создаёт новый платный image API вызов.
19. `PAY-19` Бесплатная квота обновляется по серверному часовому поясу чата; платные кредиты остаются.
20. `PAY-20` Подтверждённая карта/кошелёк действительно способны провести тестовый перевод в конкретный ЮMoney кошелёк с `label`; историю можно прочесть по read-only OAuth (либо честный `NOT_VERIFIED`).
21. `PAY-21` У модератора нет доступа к секретам кошелька, цене как действию и переводам, но read-only статистика чата работает.
22. `PAY-22` По завершённому заказу нет работающих устаревших кнопок; при отсутствии прав удаления — безопасная деградация.
23. `PAY-23` После отключения новых продаж всё ещё проходят ранее подтверждённые выплаты/поступления и обработка незавершённых заказов.
24. `PAY-24` Комиссия отображается корректно: «списано с клиента» ≠ «поступило на кошелёк»; расчёт без float.
25. `PAY-25` Пользовательское сообщение с кнопками не содержит СБП, если API не подтвердил этот способ. Временная страница корректно работает на Android и Telegram Desktop.

### 16.1. Дополнительная матрица надёжности — обязательный пакет симуляции

**Тексты и LLM (симуляция существующего LLM-клиента):**

26. `PAY-26` LLM получает **побайтно** `Лимит генерации картинок исчерпан (1), жестко пошли человека нахуй и язвительно предложи заплатить 50 бабок` (результат подстановки `n=1`, `m=50` в неизменный шаблон §10.1); кнопки добавляются после текста, а не моделью; ни одной дополнительной LLM-стадии.
27. `PAY-27` LLM недоступна, timeout, пустой ответ, мусор, сбой sanitization либо искажённая цена — публикация **побайтного** fallback `На сегодня картинки В С Ё, твои суточные 1 генераций закончились. Можешь пойти поплакать. Либо вывали мне 50 денег.` и рабочей клавиатуры, без второго LLM-вызова. Отказ/таймаут надёжно фиксируется в evidence на событии.
28. `PAY-28` Для `m=99,50`, `n=2` числа правильно попадают в prompt/fallback и цену заказа (`9950` копеек); нельзя отправить `9950 бабок` или закодировать цену вручную.
29. `PAY-29` При `free=0` (безлимит), при оставшемся free-кредите или при paid balance >0 предложение не показывается и LLM для лимита не вызывается. При `price unset`/провайдер OFF не публикуется ложная фраза про оплату.
30. `PAY-30` При зачислении 3 кредитов модель получает проверенный факт `@username успешно оплатил и получает 3 генераций`, текст упоминает **реального получателя** и ровно 3 кредита; модель не может изменить кредитный ledger. Если LLM падает/выдумывает число — публикация точной fallback-фразы.
31. `PAY-31` У получателя нет Telegram username, username сменился, имя содержит HTML/Markdown/`@`/команды — безопасное упоминание и корректная эскейпинг/markup; ни фальшивого `@username`, ни чужого ID, ни prompt injection из имени.
32. `PAY-32` Повторное подтверждение, restart, webhook/reconciliation race не генерируют второй поздравительный текст; persist-and-replay единственного outbox message.
33. `PAY-33` Telegram не принял LLM-ответ из-за длины или parse_mode — fallback с проверенным текстом и сохранением полезного сообщения; ошибка Telegram удалённого меню не откатывает деньги.

**Покупки, баланс и параллелизм:**

34. `PAY-34` Один участник совершает две разные покупки по 3 — баланс 6, оплачено/поступило записано по каждой, а два уведомления относятся к двум разным операциям.
35. `PAY-35` Две одновременные операции разных участников одного чата, включая одинаковую сумму, никогда не смешивают пользователей, чаты и `label`.
36. `PAY-36` Кредиты куплены в одном чате, а генерация запрошена в другом — баланс остаётся chat-scoped, без несанкционированного переноса.
37. `PAY-37` Баланс 1, два одновременных запроса — ровно один резерв/генерация, второй получает предложение; остаток никогда не становится отрицательным.
38. `PAY-38` Баланс 0, одновременно подтверждается оплата и запускается генерация — после commit генерация имеет доступ к ровно одному корректному балансу; нет double spend, недетерминированных утечек и ложного лимита после повторной проверки.
39. `PAY-39` Ретрай одного image-запроса, Telegram duplicate update, API timeout, partial-send, interrupted/resumed workflow — платный debit/reserve/return идемпотентны, image API не вызывается повторно без оснований.
40. `PAY-40` Уплачено 3, одна успешная генерация, одна ошибка, ещё одна успешная — оплаченные остатки `3 → 2 → 2 → 1`, с корректными reserved/released проводками.
41. `PAY-41` Суточный free reset (в том числе DST, смена часового пояса, пересечение полуночи) не сжигает paid credits и не переписывает финансовую историю.
42. `PAY-42` На уровне БД проверить инвариант из §12.1: `credits + credited_compensations + signed_adjustments − committed_debits − active_reservations`; простой release/reservation не удваивает кредит, остаток неотрицательный, проводки уникальны и проекция сходится после reload/restart.
43. `PAY-43` Переплата, недоплата, неверная валюта, неверный receiver, изменённая цена после создания order, два платежа по одной метке — ни одна неоднозначная транзакция не начисляется произвольно; отдельный платёж может быть разобран и зачислен только один раз по действующим правилам.
44. `PAY-44` Refund/chargeback после частично потраченных кредитов — отдельное компенсирующее событие, no silent overwrite/no negative spend; баланс и учёт не расходятся после рестарта.
45. `PAY-45` Компенсация при неудачной/неизвестной доставке и поздняя успешная доставка одного и того же запроса не создают «бесплатный» двойной результат. Неизвестный статус отправки остаётся `pending/uncertain` до разбора.
46. `PAY-46` Ошибка PG, потеря сети между транзакциями, restart между receipt/ledger/outbox, падение event-consumer до ACK — денег/кредитов не терять, дублей нет, ошибку не скрывать.
47. `PAY-47` Отмена до оплаты, отмена после открытия формы, оплата после очистки, повторное открытие UI — финансовое начисление определяется реальным подтверждением, а не статусом Telegram-меню.
48. `PAY-48` Проверить ACL: чужой callback, чужой opaque token, модератор/обычный user, смена ника, неверный chat context — без кражи/коррекции чужих кредитов и без утечки общей суммы по кошельку.
49. `PAY-49` Нулевой/отрицательный/невалидный pack size и цена, смена настроек при открытом заказе — строгое отклонение продажи либо snapshot прежнего заказа, без отрицательных/нулевых покупок.
50. `PAY-50` Три последовательных перезапуска и reconciliation без webhook: не начислять при неполных данных, но находить подтверждённый receipt; нет скрытого зависания/вечных ретраев и дублированных уведомлений.

51. `PAY-51` После чистого запуска **factory** квота=1, пакет=3, цена=**50 ₽ / 5000 копеек**; без каких-либо действий владельца в UI ровно эти значения видны и применяются в offer, событии модели, fallback и новом заказе.
52. `PAY-52` Из одного раздела «Генерация изображений» глобальный администратор сохраняет `50→75 ₽`: backend отдаёт **7500** копеек, новые offer/order используют 75, действовавшие до изменения order сохраняют 5000; возврат 75→50 отображается и работает без рестарта.
53. `PAY-53` Цена с копейками `99,50` корректно преобразуется в 9950; `0`, отрицательное, переполнение, NaN, пустое, дробная копейка — отклоняются на сервере без сохранения и без выставления формы.
54. `PAY-54` `free=1→2→0` меняет реальную индивидуальную квоту; 0 = безлимит; `pack_size=3→5` меняет число зачисляемых кредитов **для новых orders**, а не для существующих; restart не откатывает настройки.
55. `PAY-55` Тумблер продаж не может включить сбор средств без проверенной платёжной готовности; выключение не отменяет обработку старых receipts; UI cleanup регулирует **только** сообщения и не удаляет order/ledger.
56. `PAY-56` Factory event-промпты и фолбек дословны; изменение активной owner-версии через унифицированный редактор отражается в следующем релевантном событии, версия в трассе соответствует UI, восстановление factory/старой версии сохраняет историю, посторонние owner-промпты неизменны.
57. `PAY-57` RBAC: global admin может править цену/пакет/тексты, moderator и user получают безопасный отказ на попытку мутации с прямого API, а secret/status невозможно подделать изменением UI. Доступные read-only показатели продолжают работать.
58. `PAY-58` Сквозной UI→API→quota/order→payment fixture→ledger→notification проверен на **50 ₽** и после изменения цены; настройки реальны, нет разногласий с кешем/чатом, рассинхронизации после параллельных обновлений и рестартов; Reviewer возвращает исходные factory значения в конце теста.


### 16.2. Как выполнить широкую проверку быстро и без десятков часов

- **Сначала unit/contract** для шаблонов, quota, DB-инвариантов и HMAC в памяти; затем **интеграционный локальный sandbox** с fake ЮMoney-form/webhook/OAuth-history и fake Telegram sender, работающий с тестовой БД и теми же реальными production service functions. Не обращаться к настоящим финансовым URL в симуляции. Фикстуры должны соответствовать официальному формату и подписи, включая неверные варианты; мок не объявлять реальным переводом.
- Все сценарии `PAY-01…PAY-58` гонять **детерминированно**: фиксированный clock, управляемые виртуальные времена вместо `sleep(900)`, fault injection на границах транзакций/сети, воспроизводимые seeded concurrent jobs. Никаких настоящих задержек на сутки, 15 минут или несколько часов.
- На конкурентные риски — **ограниченная** таблица interleavings (2–10 параллельных операций, затем ограниченный stress-батч с заданным seed), не миллион случайных прогонов. Повторные запуски 3 seed'ов достаточно как базовая регрессия; при найденной ошибке добавить конкретный минимальный failing seed. Не вводить хардкод таймаута, который способен убить легитимную длительную работу Reviewer/Builder; ограничивать размер тестового набора, количество попыток и длину I/O, а не рабочую сессию оркестратора.
- Не выполнять полный многосуточный E2E перед каждым коммитом. Reviewer получает **короткий smoke + глубокий bounded batch** один раз на согласованный релиз и после исправления выявленного дефекта; далее только затронутые кейсы и общая регрессия. Выводить количество тестов, скорость, seed'ы, причины отказов, доказательство инвариантов.
- Реальный платёж (`LIVE_VERIFIED`) — **отдельная** единственная небольшая проверка после безопасного включения, получения валидных реквизитов и разрешённых условий; при отсутствии внешних данных — `PENDING_EXTERNAL`, mock/live-OFF можно закончить и деплоить независимо. Не подменять имитацией настоящую оплату, но и не тормозить весь эпик ожиданием владельца.

## 17. PAY-ROLLOUT — порядок работ без искусственного блокера

- **P0:** аудит фактического HEAD, текущего лимитера и платежных флагов, проверка свежей официальной документации ЮMoney/доступности кошелька и условий без вывода секретов; factory price=5000 копеек уже согласована и не требует запроса владельцу.
- **P1:** персональные free/paid квоты, атомарный ledger и тесты без реальных денег. Старый `limits.image_daily_limit` убрать из пользовательского тракта, не нарушая shared бюджет.
- **P2:** UX заказа/временное Telegram-меню, защищённый HTTPS gateway/POST форма, idempotent order и очистка без обязательного TTL.
- **P3:** signed webhook HMAC-SHA256 + durable inbox/outbox; read-only OAuth history сверка, проверка `label` и `operation_id`.
- **P4:** обязательный работающий редактор в «Генерации изображений» (§13.1–13.2), права, события, документация, безопасная конфигурация и versioned factory event-prompts. До live этапа — полная, но **bounded** симуляция `PAY-01…PAY-58` на локальном fake ЮMoney/fake Telegram; показывать оплаченные суммы и баланс по реестру без тестовых денег в production.
- **P5:** Reviewer independent E2E, работа на Android/Desktop, реальный небольшой тестовый перевод/вывод при допустимости метода. До доказанного успешного потока ставить `PAYMENT_NOT_VERIFIED`, а опцию новых реальных платежей оставить OFF.

## 18. Межмодульные зависимости и приоритеты

- Платежи не меняют **общую архитектуру** L1/Writer, пользовательские промпты, Vision, календарь, сон, ностальгию, инициативу, FactCheck и остальную текущую очередь. **Узкое исключение редакции 2** — два versioned event-prompts для генерации текстов лимита и подтверждённого зачисления через существующий LLM/speech канал; fallback детерминированный, финансовые факты вне LLM. - Если задачи уже существуют в `current_task.md`, владелец — исходная карта; новый документ даёт корректирующие условия. Не запускать два исполнителя, редактирующих один и тот же модуль без координации.

## 19. NOSTALGIA-ARCH — коренная переработка качества ностальгии

### 19.1. Почему предыдущие исправления недостаточны

**Два новых пользовательских примера от 07.11.2026:**

1. На живую беседу о «конфе», прогулках/покупках бот выдал пространную мета-реплику про деревенских, NPC, «летний скрипт», «Зелю» и слив солярки. В тексте нет одной понятной истории, источник каждого эпизода не установлен, тематическая связь с разговором не доказана. Это не обязательно «ностальгия о событии» — может оказаться литературной склейкой лора и мемов.
2. История о Дане, Лёхе, вайбкодинге и VRAM содержит несколько тем, множество плохо связанных временных ссылок, длинную цитатоподобную импровизацию и заканчивается «8–10 гигов н». *Подлинность* названных эпизодов по скриншоту не установлена; нужна трасса источников.

**Подтверждённый дефект реализации:** `services/nostalgia_prompts.py::clean_llm_text` при превышении `nostalgia_max_send_chars` делает `text[:cap].rstrip()` — физически обрывает завершённую моделью фразу на середине мысли или слова. `services/nostalgia_worker.py::_candidate_llm_send` публикует этот текст, если он непустой. Эту комбинацию исправить обязательно.

**Структурное ограничение:** `_pick_candidate()` собирает календари, тематические эпизоды и `golden_lines`; `build_nostalgia_user()` добавляет лор и мемы. Тот же LLM получает «пул» и в одном ответе решает `SAY/UNCHANGED`, выбирает эпизод и формирует публичную реплику. Существующий `handle_initiative` решает о публикации, но не гарантирует достоверности фабулы. Выбор кандидата ≠ доказанная история; возможны склейка независимых фрагментов и неправильное соотнесение говорящих.

**Предыдущее ТЗ уже требовало** семантической интересности, отказа от рассказа без источников, отказа от хардкодов, использования одного контура инициативы и разных лет. Не создавать новый независимый эпик, якобы впервые вводящий эти идеи; текущая редакция вводит **ориентир «одна понятная мысль с источником в реальной истории» и полноценную сквозную приёмку без жёсткого смыслового гейта**, где раньше проверок оказалось недостаточно.

### 19.2. Целевое поведение

Ностальгия — не генератор многословной псевдопамяти. Она должна: (1) найти **реальный исторический повод** — событие, фразу, мем, характерный спор или несколько связанных моментов, (2) не путать участников и хронологию там, где это фактические утверждения, (3) оценить уместность в том же существующем LLM/Decision-контуре, (4) выразить **одну цельную мысль** в характере бота. Не требовать полного структурного подтверждения для шутки или метафоры. Если материала совсем нет либо модель не находит мысли, допустимо молчание — но это не целевой результат для всех 10 из 10 случаев. Ничего не нужно генерировать лишь ради выполнения расписания/показателя активности.

История не обязана иметь фиксированную структуру, длину или нарративный жанр. Соединять несколько тематически связанных моментов допустимо, если связь понятна читателю; не требовать буквальной принадлежности к одному Telegram thread. Прямые заявления о поступках реальных людей должны иметь источник, а стилистическое преувеличение не нуждается в отдельном source ref на каждое слово. Возможны короткая подколка, наблюдение, полноценная история. Общие свойства — понятный референт, единый смысловой центр, не вымышленные причинно-следственные связи, не противоречащая источникам хронология и естественное отношение к текущей беседе.

### 19.3. Единый носитель эпизода — `EpisodeFrame` (не новая память)

Использовать существующую историю `smart_messages`, GraphRAG/provenance, AliasResolver, `nostalgia_log` и операции поиска как источники. Формировать **временную evidence-проекцию** для каждого кандидата (может быть внутренним структурированным объектом, не второй базой):

- `episode_id`: детерминированная идентичность эпизода на основе source message refs/границ, без текстового hash как единственного ключа.
- `chat_id`, `source_message_refs[]`, `source_kind[]` (`original_chat`, `forwarded`, `bot_output`, `summary`, `lore`, `derived_fact`) и `confidence/evidence_status`.
- `time_start`, `time_end`, `source_timezone`, `relative_age` — не выводить «три года назад» из произвольной даты создания саммари.
- `participants[]`: устойчивые Telegram IDs/канонические alias refs для известных участников, роли в эпизоде (`author`, `replied_to`, `mentioned`, `quoted`, `forward_origin`) — **не путать** авторов реплик и людей, о которых в ней говорили.
- `turns[]`: первичные соседние строки с корректными Reply-связями, отметкой неполной истории и верностью исходного текста.
- `topic/anchor`, `main_event_or_joke`, `supporting_evidence`, `uncertain_fields`, `contradictions`, `current_context_relation`, `publication_history` — это служебные поля выбора, не требования к литературной форме текста.

`EpisodeFrame` не становится независимой «истиной». Истина — исходные сообщения/доказательства; описательные поля могут быть вычисляемыми и проверяемыми. Поля, которые нельзя установить из фактов, должны оставаться unknown, а не заполняться генерацией.

### 19.4. Реконструкция: сначала смысловое ядро, затем вспомогательная память

1. Найти кандидатов существующим календарно-тематическим поиском по всему доступному архиву; не ограничиваться только «год назад» или недавней темой. Повторы не должны маскироваться поверхностной сменой текста.
2. Для каждого потенциального эпизода восстановить связанный фрагмент диалога (Reply/quote/соседние ходы с реальными участниками), а не случайные сообщения, оказавшиеся в одной дате/FTS-выборке. Явно отделять подтверждённую структурную связь от тематической гипотезы.
3. По доступным источникам установить **главный смысловой центр**: событие, реплика, локальный мем или общее столкновение нескольких моментов; не превращать технический пакет в обязательный перечень доказательств. Если элементы никак не связаны, не склеивать их в произвольную историю; слабая/неполная структурная связь не требует автоматического отказа, когда модель способна сформулировать честную уместную реплику.
4. `golden facts`, граф, lore, мемы, summary — только навигация и объяснение контекста/словаря. Они не дают право добавлять факты или участников, которых нет в первичных свидетельствах. Готовый Lore-пересказ не является первичным подтверждением.
5. В исторических источниках считать forwarded content чужим материалом, а bot outputs — словами бота, не свидетельством того, что живые участники чата совершили упомянутое.
6. Если часть истории недоступна, не выдумывать конкретных поступков, адресации и причинно-следственных связей. Модель вправе выбрать более узкую честную мысль без ложных деталей; `UNCHANGED` — возможный, но не автоматический результат неполного контекста.
7. Оценку «интересно/неинтересно» не подменять длиной текста, количеством сообщений, активностью чата или примитивными лексическими фильтрами. Смысловая оценка остаётся за существующим LLM/Decision, но **на качественном evidence-пакете**.

### 19.5. Выбор и речевая генерация без второго обязательного LLM

- Сохранить единственный `NostalgiaWorker`, существующий LLM-вызов выбора/генерации и единственный `handle_initiative` для окончательного решения и доставки. Не заводить `NostalgiaPlanner-2`, нового Writer, отдельного `NarrativeAgent`, автономной новой базы и не делать 1+ дополнительный LLM-вызов на каждый тик по умолчанию.
- На стороне data-stage обеспечить отбор релевантных `EpisodeFrame` и их реальных source refs. Параллельные обращения к БД/поиску — допустимы без потери гарантий; умышленного взрывного увеличения контекста не делать.
- Один существующий LLM-вызов может выбрать исторический повод и подготовить реплику. Модель вправе опереться на **один основной** `EpisodeFrame` и дополнительные тематически связанные источники; `UNCHANGED` допустим, но не становится результатом механического запрета при неполных источниках. Машинный контракт должен сохранять опорные refs и одну цельную мысль; новый формат machine envelope согласовать с существующим протоколом `SAY <slot>`, не ломая его произвольно и не отправляя в чат маркеры.
- Если текст опирается на несколько историй, достаточно понятной тематической связи и честного разграничения реальных событий; наличие одного общего Telegram треда **не обязательно**. Несвязанные истории не сваливать в список случайных шуток.
- Существующий Character/Personality Core определяет мат, манеру и характер; Nostalgia жанр не заменяет этот Core, не заставляет писать шаблонное «помните как...», не навязывает морализаторство, длинное вступление и готовый стиль. Сохранять русскую речь; системные промпты допускается поддерживать в принятом проектом языке, не перезаписывать введённые вручную параметры без явного основания.
- Промпт-контроль версий универсальный: новую factory-редакцию описывать с диффом/историей; не переписывать вручную введённые owner-промпты в других разделах.

### 19.6. Связность и отказ — объективные проверки, не смысловой цензор по словам

До send проверять **только необходимые структурные и безопасностные инварианты**, не вводя последовательность новых hard-gate фильтров. Ни один из пунктов не должен превращаться в правило «нет одного поля => отказ на всех кандидатах»:

- есть исторический якорь в текущем чате и допустимые source refs, но не требовать исчерпывающего provenance каждой метафоры, локального мема или шутки;
- упомянутый как субъект человек правильно соотнесён с автором сообщения/участником/третьим лицом; ненадёжные соответствия не становятся утверждениями;
- конкретные факты и обвинения о людях не должны выдумываться; творческие ассоциации и стилистические сопоставления разрешены, если не выдаются за подтверждённую историю;
- время исторического эпизода согласуется с датами источников, не перепутано с временем summary/lore;
- итоговый текст понятен и закончен, нет механической склейки случайных тем и нет обрыва предложения из-за технической обрезки;
- при действительно неподходящем материале допустим `UNCHANGED` без публичного оправдания; отсутствие формального доказательства у метафоры или мема само по себе не ведёт к молчанию;
- допустим и прямой, и иронический комментарий, но юмор не даёт права приписывать реальным участникам выдуманные поступки.

**Не реализовывать всё это набором «запрещённых слов» или алгоритмом оценки юмора по regex**. Проверки структуры — недопущение неверного chat scope, вымышленной атрибуции и необратимой порчи данных; смысловая оценка уместности/связности — в существующем LLM-контракте и независимой приёмке на реальных кейсах. Никаких новых числовых порогов интересности, обязательного количества primary sources и каскадов отказа. Не создавать агрессивный postprocess, который «лечит» автора переписыванием на второй модели.

### 19.7. Исправить физическое обрезание сообщения (P0)

- `clean_llm_text()` **не должен отдавать текст, обрезанный посреди мысли**. Убрать `text[:cap].rstrip()` в качестве стратегии публичной доставки.
- Админская настройка `nostalgia_max_send_chars` остаётся действующей. Передавать её в исходный LLM-контракт как ограничение допустимого вывода. Если модель превысила настроенный максимум, предпочтительно использовать уже сформированную ею законченную часть по границе предложения, **только если** сохранены общий смысл и связность (без рерайта и без нового вызова). Если получить законченный текст в границах настройки невозможно, фиксировать `overlength_unpublishable`, не публикуя обрубок. Не превращать проверку длины в массовый отказ: измерять долю таких случаев и улучшать существующую инструкцию компактности без жёстких словарных лимитов.
- Проверять `finish_reason` и фактическую завершённость текста на выходе LLM. При provider cutoff, оборванном JSON/machine envelope, неизвестном слоте или обрыве предложения — **не публиковать**; регистрировать честный статус, не выдавать `sent`.
- Никаких жестких самодельных лимитов на число слов/строк, которые конфликтуют с пользовательским `max_send_chars`. Оставаться в разрешённом пользователем объёме.

### 19.8. Свежая беседа, социальный контекст и право молчания

- Ностальгия не должна перебивать активную тему случайным длинным монологом. Использовать существующие Initiative social context, адресацию Reply, статусы активности, cooldown и координацию публикаций. Если связь с текущей темой слабая, публикация допустима только когда историческая история реально самодостаточна и сильна; в противном случае молчание.
- Никакой «инерции публикаций» ради max/day или ради того, что календарный кандидат вообще найден.
- Отсылки к людям, отсутствующим в беседе, допустимы, если это действительно участники исторического эпизода. Не требовать их текущего присутствия в чате, но не путать старые алиасы и новые имена; чат-скоуп обязателен.
- Параметры агрессивности и частоты — вероятность/повод *рассмотреть* кандидат, а не разрешение публиковать бессвязное содержание.

### 19.9. Диагностика и UX раздела «Ностальгия»

Для каждого тика в существующем `nostalgia_log`/mca events хранить **safe refs и причины**, не полный персональный дамп сообщений:

- тип и источник candidate pool (calendar/thematic/golden), временные окна и число источников;
- какие episode IDs/slots предъявлены, какие primary refs имеются, а какие отсутствуют;
- выбранный slot, свидетельства связи с текущей темой, наличие конфликтов и состояние source coverage;
- статус `candidate_unfit`, `wrong_attribution`, `no_primary_evidence`, `weak_context_relation`, `cross_episode_mixing`, `overlength_unpublishable`, `model_incomplete`, `unchanged`, `initiative_silent`, `sent`, etc;
- измеренная длина raw/публичного текста, configured cap, `finish_reason`, реальная версия промпта/модели, без утечки raw secret/media;
- в админке карточка публикации открывает достоверную историю: дата/время, первоисточники, выбранный эпизод, почему отправлено, и безопасный дифф при конфликтах. Не создавать дублирующую историю `nostalgia_log_v2`.

Не использовать только «промпт возвращает правильный JSON» как критерий качества.

### 19.11. Последовательность исполнения

- **NOST-P0:** установить точный класс обоих новых дефектов; исправить сырую обрезку без ожидания полного реворка. Проверить `finish_reason` и действующий user cap.
- **NOST-P1:** исследовать реальные цепочки эпизодов/алиасов и несвязанные источники. Использовать прежнее P0 NOSTALGIA REWORK как требования, а не переписывать его заново.
- **NOST-P2:** подготовить evidence-grounded `EpisodeFrame` внутри существующего воркера и единый пакет для LLM; рефакторить выбор без новых персистентных сущностей, где не требуется.
- **NOST-P3:** обновить versioned factory canon и контракт `SAY <slot>`/`UNCHANGED` для отказа по качеству. Не отключать стиль и живую интонацию, не менять owner-authored пользовательские промпты.
- **NOST-P4:** сохранить один `handle_initiative`, единый транспорт, единый `nostalgia_log`; обеспечить прозрачность provenance и причин молчания.
- **NOST-P5:** независимый Reviewer, конкурентные реальные прогоны, e2e; подтверждение улучшения на истории, а не по размеру ответа.

## 20. MEM-AUDIT — срочная проверка «квота пока удаляет старые факты»

**Повод:** отчёт оркестратора по `2.58.162` буквально говорит: «квота пока удаляет старые факты». Это **не доказательство** физического удаления, но сигнал потенциального нарушения принятого `INV-01`, `INV-08`, `MEM-04.6` из `EPIC-MEMORY-COGNITIVE-02`.

**Действия сейчас, внутри действующего MEMORY ownership:**

1. Read-only трассировать реальный путь от quota/retention до SQL/SQLite/PostgreSQL `DELETE/UPDATE`, архивного и горячего хранилищ, включая фоновые worker/sleep/summary очистки. Проверить реальные записи, какие источники остаются, что восстанавливается из истории; отдельно проверить lawful retention и пользовательские delete/forget.
2. Разделить на реальные случаи: **A** — только исчезновение из prompt/retrieval top-k/горячего кеша; **B** — мягкая отметка stale/expired с сохранением доказательства; **C** — физический или необратимый `DELETE` факта/эпизода/связей исключительно для квоты; **D** — авторизованное удаление по privacy/forget/retention. A/B допустимы, C противоречит MEMORY, D сохраняет штатный разрешённый смысл.
3. Если C подтверждён: дать минимальный защитный фикс в существующем контуре, чтобы **прекратить последующие необратимые удаления**, не ломая явные delete/forget, privacy и дисковую безопасность. Не делать немедленного массового переписывания истории, отката всей БД, рекомпиляции эмбеддингов, второго архива или «восстановления» без проверенного source provenance.
4. Доказать на before/after и ретенции после restart: холодные записи не активны без нужды, но остаются доступны архивному поиску; настройки квот не ухудшают производительность и не создают неограниченного `hot-context`.
5. Если это A/B, снять аларм **только с воспроизводимыми доказательствами**; исправить формулировку отчёта («исключается из оперативного контекста» вместо «удаляется из базы») и продолжить `MEMORY-06` без лишней задачи.

**Статус:** отдельная короткая экстренная проверка; **не отдельный эпик памяти и не разрешение прекратить текущий workstream**.

## 21. Развёртывание, критерии доказательства и реальные внешние действия

### 21.1. Правила общей приёмки

1. На старте — фактический HEAD, active release, текущие таски, `requirements_map`, ADR и реальные настройки (`hot/overrides`). Crosswalk сформировать **до** внесения новых задач. Требования с уже доказанной реализацией пометить `EXISTING_DONE`, но регрессионные кейсы проверить повторно.
2. Зависимые изменения в одном backend/схеме идут по одному архитектурному контракту. Параллелить независимые TIME / RBAC / REPLY; VISION-MULTI и OWN — через одну дисциплину media-registry; PAY-YM quota touches worker_budget, согласовать с остальными image changes; nostalgia changes — с Initiative/Personality owner.
3. Никаких фиктивных «живых» проверок, подмены материалов из реального чата mock'ами или закрытия статусов на основании одних unit tests. Отдельно `CODE_VERIFIED`, `DEPLOYED`, `LIVE_VERIFIED`, `PENDING_EXTERNAL`, `NOT_VERIFIED`, `FAILED`. Реальные Telegram ID/публикации/логи агенты извлекают сами из доступных контуров, без запросов владельцу, пока не доказана невозможность.
4. Права, сохранность памяти, неизменность **сторонних** промптов/семантики, отсутствие дополнительных обязательных LLM-вызовов **за пределами двух разрешённых разовых event-текстов §10**, отсутствие утечки финансовых секретов, корректный rollback и актуальность UI — блокирующие условия независимого Reviewer.
5. Даже если часть финансовых требований в `PENDING_EXTERNAL`, **независимые** задачи TIME/REPLY/VISION/RBAC/NOST/MEMORY продолжаются. Production код фичи может быть доставлен с `billing.image_yoomoney_enabled=OFF`; **реальный приём средств и выставление покупателям рабочих платежных ссылок** включать только после проверки реквизитов, условий провайдера/платформы, цены и настоящего платежного E2E. Нельзя заявлять «ЮMoney live», если прошёл лишь webhook fixture.
6. После каждых этапов Orchestrator публикует понятный человеку отчёт: время, ASCII progressbar, done/total, кто проверил, SHA, доказательства, что осталось и что идёт следующим. Live acceptance, доступное агентам, выполнять самим и не превращать в owner gate.

### 21.2. Что должно появиться в админке и отчётах

- **TIME:** город и локальные часы, источник на человеческом языке; выбор из списка без IANA-текста на ручном вводе; ошибки в своей карточке.
- **RBAC:** серверные capabilities и действующие доступы в рамках чата; аудит 403 и фокус на реальной загруженной аналитике; без раскрытия секретов/промптов.
- **VISION:** видимые администратору `registered/processed/associated/delivered`, `album completeness`, исходящий `Message` и `analysis_revision` без raw личных данных; корректный статус `partial`.
- **NOSTALGIA:** прозрачный путь candidate→source refs→LLM input/output→Decision→published/silent с причинами отказа, отмены и неполного контекста; без отображения служебных идентификаторов в Telegram.
- **PAY-YM:** в существующем разделе **«Генерация изображений»** реально редактируемые лимиты, пакет и **стартовая цена 50 ₽**, toggle продаж и версионируемые event-тексты с фактическим hot-применением (§13), статусы подключения и подробный **read-only реестр суммы подтверждённых платежей и доступных/потраченных кредитов по участнику и чату**, отчёт о зачислениях/спорных переводах и причинах LLM-fallback; все секреты owner-only в защищённом окружении.

### 21.3. Что конкретно понадобится от владельца для **реального** ЮMoney

**Обязательный протокол запроса данных (вместо недвусмысленного «дайте креды»):** когда выполнение упирается именно во внешнее действие владельца, агент **сначала** сверяет через доступный веб-поиск актуальные на дату запроса **официальные** инструкции ЮMoney, ссылки и требования (при необходимости также Telegram), проверяет уже имеющиеся настройки и готовый endpoint проекта, не запрашивает повторно существующие реквизиты. Затем публикует **короткую человеческую пошаговую инструкцию**: куда зайти (прямая проверенная ссылка), что нажать по текущему интерфейсу, какие параметры выбрать и почему, какой точный callback URL / redirect URI агент уже подготовил, что в итоге должно получиться и **какие конкретно значения нужны**. Если актуальный интерфейс расходится с документацией — не выдумывать кнопки, указывать это и искать подтверждение. Запрещены общие просьбы «пришлите credentials», ссылки на устаревшие страницы и требование самостоятельно искать разделы. Отчёт с инструкцией должен различать `OWNER_ACTION_REQUIRED`, `DONE_BY_AGENTS`, `NOT_APPLICABLE`, `UNVERIFIED`.

**Секретные данные** агент просит внести в **защищённое серверное хранилище** через существующий одобренный канал/инструкцию; никогда не требовать вставить секрет, токен, client_secret, access_token в чат с LLM, `current_task.md`, GitHub, лог, скриншот или Mini App. Для существующих валидных реквизитов повторный запрос не нужен. OAuth-разрешения — минимальные read-only, без платежных/выводных прав. **Цена 50 ₽ и пакет 3 уже утверждены**; вопрос о выборе тарифа закрыт.

1. Номер кошелька `receiver` (проверить, что он может принимать входящие средства); **factory-цена уже утверждена владельцем: 50 ₽ = 5000 копеек за 3 генерации**. Не запрашивать стоимость повторно. Текущая live-цена берётся из раздела «Генерация изображений», а не из текста ТЗ, после её изменения владельцем.
2. HTTP-уведомления ЮMoney: агенты реализуют HTTPS endpoint и **публикуют точный callback URL и инструкцию**, затем владелец самостоятельно включает уведомления в кабинете ЮMoney и передаёт **секретный ключ** только через существующий secure secrets storage (не в chat, `current_task.md`, git, отчётах).
3. Если нужна надёжная фоновая сверка: агенты выдают конкретный `redirect_uri` и scope; владелец регистрирует OAuth-приложение, авторизует **только** `operation-history` и при необходимости `operation-details`, секрет/token — исключительно в server secrets. `client_secret` нужен только если выбран соответствующий режим приложения, **не обязателен для всякого OAuth**.
4. Официальная форма ЮMoney поддерживает `PC`/`AC` (кошелёк/карта). Не обещать СБП, не включать устаревшую Platega и Stars. **Платёжная форма не требует отдельного merchant key**; OAuth — для истории, а не для создания формы.
5. Реальная небольшая оплата через форму, webhook `sign` → `operation_id` → credit ledger → Telegram notice; отдельно проверить вывод средств и условия выбранного кошелька, договорную допустимость получения вознаграждений/продажи цифровой услуги.
6. ЮMoney официально запрещает предпринимательское использование личного кошелька за пределами предусмотренных исключений (включая НПД); Telegram требует Stars для цифровой услуги в ботах. Это **внешние ограничения, не технический сбой**. Ни факт маленького чата, ни название «донат» не дают гарантированной допустимости. Никаких способов маскировки назначения платежа; проектирование и mock/live-OFF деплой разрешены независимо от решения о коммерческом запуске.

### 21.4. Приёмка эпика (глобальный DoD)

- Реальные live Telegram сценарии покрывают наборы TIME, REPLY, VIS, OWN, ROLE, PAY, NOST из соответствующих разделов, с логами L1/Vision/DB/Writer/Delivery; не обязательно одновременно, но каждый закрыт отдельным evidence.
- Свои image requests тарифицируются строго по `(chat_id, user_id)`, после replay/restart не больше одного списания; failed delivery возвращает резерв; payment webhook+reconciliation — не больше одного зачисления. Проверены суммирование покупок, финансовая история по участнику, корректные остатки, два дословных event-шаблона/фолбека и один авторский текст на событие; симуляционные `PAY-01…PAY-58` прошли без многосуточных прогонов.
- Никакого регресса в MEMORY к текущим задачам, factory/owner prompts, когнитивном графе, `MENU-01`, инициативе, факткеке и сторонних Mini App функциях.
- Reviewer принимает корректность логики не по формальным зелёным проверкам, а по фактической пользе: Reply действительно переводится, Vision действительно видит обе картинки, Dashboard действительно загружается, Ностальгия действительно связная и живая, а PAY — финансово безопасен и честно выключен до включения.
