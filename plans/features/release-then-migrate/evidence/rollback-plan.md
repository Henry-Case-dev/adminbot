## 2. Возврат ДО того, как новый VPS обработал реальные обновления (фаза §8.1)

Условие применимости: новый `admin_bot` ни разу не обработал реальное пользовательское обновление и не создал новых записей (либо новые записи ограничены стартовой служебной активностью).

Процедура (строгий порядок, один активный экземпляр в каждый момент):

1. **НОВЫЙ остановить полностью:** `systemctl disable --now admin_bot` (NEW); `docker stop adminbot-telegram-bot-api` (NEW). Проверить: 0 процессов bot.py на NEW.
2. **СТАРЫЙ вернуть в строй:** `docker start adminbot-telegram-bot-api adminbot-postgres adminbot-cobalt adminbot-bgutil-pot-provider`; если unit был disabled в окне — `systemctl enable admin_bot`; `systemctl start admin_bot`; если останавливались — `systemctl start caddy xray`.
3. **DNS:** если успели переключить DuckDNS → вернуть `198.46.175.136` (токен — см. §5) ДО старта нового бота, чтобы TMA/медиа не смотрели на пустой новый сервер.
4. **Очередь Telegram:** неконсьюмленные обновления остаются в ЛОКАЛЬНОМ bot-api СТАРОГО сервера (`tqueue.binlog` старого не потреблялся — старый poller останавливался первым). Потеря/дубли не возникают: старый бот продолжает с того же offset в памяти… offset в памяти теряется при остановке — aiogram запросит getUpdates заново от последнего подтверждённого; неконсьюмленные апдейты остаются в локальном bot-api и будут доставлены. Двойной обработки нет, т.к. новый не запускался.
5. Данные NEW после этого не «источник истины» — там только копия; ничего переносить назад не нужно (NEW не писал в период до первого реального апдейта).

## 3. Возврат ПОСЛЕ того, как новый VPS принял сообщения / выполнял фоновые задачи (фаза §8.2)

**Запрещено:** просто включать старый сервер/снапшот — это потеряет данные, созданные на NEW, и/или вызовет повторные отправки.

Обратно-согласованная процедура (backward-consistent), только если она технически безопасна:

1. Остановить писателей NEW: `systemctl stop admin_bot`; `docker stop adminbot-telegram-bot-api`.
2. Дельта NEW→OLD согласованно: SQLite backup API на NEW (тихая копия) → replace живой БД на OLD; `pg_dump -Fc` NEW → `pg_restore --clean --if-exists` в PG OLD; bot-api store дельта NEW→OLD (rsync/tar **без** `--delete`); media дельта; .env OLD не трогать (его родной).
3. Offsets/очередь: `tqueue.binlog` переносится со store; убедиться, что старый бот стартует с очередью, а не с двойной обработкой (сравнить mtime/размер binlog до/после).
4. DNS вернуть на `198.46.175.136` (первым шагом, если откат инициирован из-за NEW-неисправности — домен должен снова показывать рабочий сервер).
5. Запустить OLD стек (контейнеры → admin_bot → caddy/xray). **NEW остаётся полностью остановленным** — два экземпляра исключены всегда.
6. Если безопасный обратный перенос невозможен (расхождение схем, конфликт ID, сомнение в консистентности) — **NEW остаётся единственным источником истины**, проблема устраняется на нём (правило owner §8), OLD остаётся замороженным fallback.

## 4. Критерии принятия решения об откате (в окне, до обработки реальных обновлений NEW)

Откат по §2 выполняется, если в окне cutover:
- расхождение данных с финальным снапшотом (SQLite integrity ≠ ok; row counts/границы ≠ снапшоту; PG counts ≠; роли/настройки админки отсутствуют);
- критическая регрессия при старте (fatal-цикл в journal, приложение падает повторно);
- healthz не достигает 200 после устранения в пределах ~15 минут усилий (ABORT RULE из задания);
- невозможность привязки токена к новому локальному bot-api (повторные 401/conflict после logOut-переключения).

После того как NEW обработал реальные обновления — действует §3/§6 (починка на NEW), не §2.

## 5. DNS (DuckDNS)

Токен DuckDNS в `.env` отсутствует (проверено O1: ключей с `duck` нет). Источник ищется на старом сервере (cron/systemd/скрипты обновления, имена ключей без значений). Если токен не найден к шагу 7:
- **bot** (polling через локальный bot-api → Telegram cloud) от DNS не зависит и может работать;
- админка/TMA/публичные media URL остаются направленными на старый IP, где приложение остановлено → домен фактически недоступен до переключения DNS;
- это фиксируется как открытая аномалия с продлением фактического гэпа для домена; если токен — только владелец, эскалация владельцу (подлинная внешняя зависимость по креденшелу), при этом бот и данные НЕ считаются потерянными, откат по §2 остаётся возможен;
- без возможности переключить DNS новый Caddy НЕ стартует (исключить гонку ACME и двусмысленное обслуживание).

## 6. Эскалация без согласований

- Технический откат внутри разрешённого окна выполняется DevOps самостоятельно (стоячее разрешение владельца на это окно), без Human Gate, с честной фиксацией фактов.
- При неудаче самого отката или подозрении на потерю данных: оба сервера оставить остановленными, ничего не удалять, зафиксировать evidence и вернуть `BLOCKED` с точными фактами Orchestrator/владельцу.
- Тестовые сообщения в рабочие чаты для «проверки отката» запрещены (§0).
