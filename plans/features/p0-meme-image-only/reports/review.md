## 2. Блокеры

### B1. Отложенное второе сообщение: ход с картинкой считается "неотвеченным" (BLOCKER)
- Требование: после картинки второго сообщения нет (MEME-ACC-03, MEME-RULE-01), логика инициативы не меняется (MEME-RULE-05).
- Где: ранний `return` в `services/direct_chat_service.py:5067-5084` обходит `self._mark_turn_text_replied(chat_id)` (:5137). Producer `_f6_maybe_create_unanswered_question` (:3127-3130) срабатывает, если ход не помечен.
- Наблюдение (исполнение): после успешного хода с картинкой маркер не выставлен; для сообщения с "?" (`bot draw a meme about deadline?`) на реальной БД создан durable intent: `intent_id = intent:-100:follow_up:...`, `created = True`, origin `unanswered_question`, активация через 15 минут (INITIATIVE_UNANSWERED_DELAY_SECONDS). `flags.initiative_enabled` по умолчанию ON, то есть поведение живое.
- Влияние: через 15 минут инициатива может дослать текстовое сообщение по уже отвеченному запросу - ровно то "второе сообщение", против которого требование. Плюс ложные "неотвеченные" записи в журнале намерений.
- Минимальное исправление: в подавляющей ветке вызывать `self._mark_turn_text_replied(chat_id)` (одна строка) и добавить регресс-тест "ход с картинкой не создает unanswered_question". Не блокировать создание intent для настоящих неответов.
- Перепроверка: тот же прогон пробы (маркер выставляется, intent не создается) + `tests/test_asap8_f6_initiative.py`.

### B2. После картинки может прийти текст ошибки (BLOCKER)
- Требование: успешная генерация = единственное исходящее сообщение, любой текстовый follow-up запрещен (MEME-RULE-01).
- Где: обработчики `services/direct_chat_service.py:5253-5257` (LLMError) и `:5267-5271` (прочее) отправляют аварийную фразу и не знают о доставленной картинке.
- Наблюдение (исполнение): пре-гейт доставил фото, Writer упал с LLMError -> в чат ушло два сообщения: `photo`, затем `text: я подавился токенами, попробуй позже`. Реалистично: пре-гейт стоит до вызова LLM, поэтому первая же транзиентная ошибка провайдера дает мем плюс текст ошибки.
- Минимальное исправление: в обоих обработчиках пропускать аварийную фразу, если на этом ходу картинка уже доставлена (использовать тот же `image_delivered`/`_image_delivery`), ошибку оставить в логах. Никаких новых фраз не вводить.
- Перепроверка: проба "доставлено + LLMError" дает ровно `['photo']`; плюс тест на этот сценарий.

### B3. Circuit breaker навсегда остается в HALF_OPEN (BLOCKER, надежность)
- Требование: не ломать остальную логику (MEME-RULE-05), не терять работоспособность бота.
- Где: ранний `return` обходит `self._breaker.on_success()` (`:5222-5224`) - единственное место сброса. Проверка `:3238` отказывает всем запросам, пока состояние HALF_OPEN.
- Наблюдение (исполнение): breaker открыт, кулдаун истек, пробный ход оказался запросом картинки -> картинка доставлена, состояние осталось `HALF_OPEN`, `allow_request()` для следующего хода вернул `False`. Дальше каждый следующий ход получает аварийную фразу вместо ответа до перезапуска процесса (все чаты, breaker общий для сервиса).
- Минимальное исправление: в подавляющей ветке вызывать `self._breaker.on_success()` перед `return`; при ошибках LLM (B2) поведение breaker не менять.
- Перепроверка: та же проба (после хода состояние `CLOSED`, `allow_request()` = True).

## 4. Побочный эффект: ничего не пишется в текстовый журнал ответа (оценка)

Что именно пропускается на подавляющем пути и что из этого допустимо:
- `bot_output_ledger.record_delivered_output` (:5193) - записывается только реально доставленный ТЕКСТ. Текста не было, поэтому записи нет. Записывать подавленный текст было бы ложью о доставке. **Допустимо**: у потребителей (quote_resolver приоритет 5, сверка публикаций summary, relay-модули) строка создается под их собственный run/текст, обязательного требования "у каждого хода есть строка" нет.
- `remember_bot_reply` (:5149) - цепочки ответов по тексту бот-сообщений; у сообщения-картинки текста нет, `get_bot_reply` вернет None, цепочка обрывается на боте так же, как на любом не записанном сообщении. **Допустимо, но заметно**: при цитировании картинки бота текстовая ветка цепочки не продолжится.
- `_memorize_direct_reply` (:5214) - двусторонняя память хода; теперь запоминается только запрос, без ответа бота. Строгого потребителя нет, но факт "бот прислал мем" в память не попадает. **Допустимо**, отдельного дефекта не создает.
- `DIRECT_FRESH_GENERATION` и humor-capture - события текстового ответа, а не генерации картинки; humor выключен по умолчанию. **Допустимо**.
- F6-маркер хода (:5137) - это НЕ журнал текста, это признак "бот ответил в этом ходе", который читает producer намерений. Его пропуск ведет к B1. **Недопустимо** - единственный реально сломанный потребитель.

Вывод: пустой текстовый журнал сам по себе корректен (записывать нечего), но "ход отвечен" обязан быть зафиксирован; сейчас он не фиксируется.
