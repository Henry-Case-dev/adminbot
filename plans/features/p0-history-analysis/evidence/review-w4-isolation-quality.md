## Блокеры

### 1. Страховки качества не стоят на ходе

- Владелец: Builder.
- Требования: REQ-HA-QUALITY-CLASSIFY, REQ-HA-QUALITY-NO-INVENTED-ACTIONS, REQ-HA-NO-INVENTED-STATS. H26.
- Где: `services/claim_envelope.py` (функции есть), `services/direct_chat_service.py` `collect_history_segments` / `_segment_json` (не вызывают их). Поиск по `direct_chat_service.py`: ноль вхождений.
- Наблюдение: модель пишет note, код обрезает её до 200 символов и кладёт в `@@HISTORY_COVERAGE`. Шутка может стать чертой, пересланный текст — действием переславшего, «обсуждали 5 раз» при двух refs — свидетельством.
- Влияние: анализ «последних N» снова может выдать широкую характеристику и выдуманную частоту. Инструкция в промпте этого не закрывает: инцидент как раз про то, что модель не держит границу сама.
- Правка: в `_flush`, до записи события в покрытие, применить уже написанные функции к note и строкам сегмента. Чужой ref отбросить (шов `own` уже делает это — не дублировать вторым смыслом). Выдуманное число или дату не класть в note как факт. Конфликт атрибуции пересылки не принимать как действие переславшего. `stable_trait_claim_allowed` должен реально не пускать черту из шутки/единичной реплики/высказывания бота. Маркеры — по границе слова: сейчас `classify_finding_kind("космический корабль")` даёт `external_news`, потому что «сми» — подстрока.
- Перепроверка: один сегментный ход, где модель возвращает шутку как черту, «5 раз» при 2 refs, дату вне refs и «Вася сообщил» на пересылке от РБК. В покрытии этого нет. Ход без выборки байт-в-байт прежний.

### 2. Идентичность — это id сообщения, а не Telegram user ID

- Владелец: Builder.
- Требования: REQ-HA-QUALITY-IDENTITY, H25, строка 475 источника.
- Где: `services/claim_envelope.py` `identity_matches` / `FindingIdentity`; `services/tool_router.py` `_history_lines` / `_resolve_name`.
- Наблюдение: независимый зонд на HEAD. Две строки, user_id 111 и 222, одно имя «Алексей». Обе рендерятся как `[... | Алексей | tg:N]`. У `FindingIdentity` нет поля user_id. `identity_matches` сравнивает `tg:11` и `tg:22` и говорит «разные», хотя тот же человек в двух сообщениях тоже получил бы разные ref. Тест `test_same_display_name_different_refs_not_merged` закрепляет эту подмену.
- Влияние: два участника с похожим или одинаковым именем в анализе последних N сливаются. Различить их по Telegram user ID нельзя: в стенограмме выборки его нет. На прямом контексте uid уже есть (`_speaker_tag`), в истории инструмента — нет.
- Правка: в строки выборки, которые читает анализ, добавить Telegram user ID тем же приёмом, что `_speaker_tag` (имя и uid, не новый формат ref). Сравнивать людей по user id, не по id сообщения. Тест переписать: два uid с одним именем не сливаются; два сообщения одного uid остаются одним человеком.
- Перепроверка: зонд выше должен показать разные uid в строках и отказ слияния. Регрессия страниц/сегментов: парсер `tg:`/`msg:`/`fact:` не ломается.

### 3. При выключенном композере баннер метит и строки выборки

- Владелец: Builder.
- Требования: REQ-HA-ISOLATION-SUPPLEMENTARY, контракт §3 (баннер у конспекта, не у дословного хвоста).
- Где: `services/direct_chat_service.py` около 6192–6198 и `_build_global_context` (9486–9487).
- Наблюдение: `DIRECT_CONTEXT_COMPOSER_ENABLED` по умолчанию включён, путь OFF — штатный рубильник. На нём при `history_sample` баннер клеится ко всей строке `global_ctx`. Эта строка — `<Global_Context>` из конспекта и дословного хвоста (`head + tail`). Хвост — недавние сообщения, часто как раз внутри выборки. Модели сказано, что они не подтверждают события диапазона.
- Влияние: при аварийном выключении композера вопрос «разбери последние N» обесценивает сами сообщения диапазона в фоне. На пути ON этого нет: баннер только у head.
- Правка: на legacy-пути баннер только у конспекта/head, не у дословных строк хвоста. Хвост внутри окна не метить «вне выборки».
- Перепроверка: композер OFF, выборка есть, в global есть и «фон: конспект», и дословная строка окна. Баннер над конспектом есть, над дословной строкой окна нет. Путь ON и ход без выборки не меняются.

### 4. System2 может нести выборку без инструкции качества

- Владелец: Builder.
- Требования: те же QUALITY, шов проводки. Отклонение «coverage не бывает на system2» проверено и принято только наполовину.
- Где: захват `history_sample` до ветки (около 2699), `tool_ctx.history_sample` около 3497, system2 при `not direct_l1_on` около 3921, `_synthesize_direct_answer` без `history_assembly_block`. `collect_history_segments` только внутри `if direct_l1_on` (около 3971).

Но выборка на этот ход всё равно захватывается и кладётся на `tool_ctx`, если L1 выключен (`DIRECT_L1_ENABLED` / `flags.direct_l1_enabled`, оба по умолчанию включены, выключение штатное). `get_recent_history` листает эту выборку. - RAG/dig/nostalgia/head при выборке получают баннер, содержимое не обнуляется. Без выборки баннера нет.
