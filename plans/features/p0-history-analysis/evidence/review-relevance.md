## Блокеры

### 1. Явный вопрос о старой памяти её не находит, если её уже несколько раз подавали

- Требование: H24, §11 («взвешивать, не подавлять»), строки REQ-HA-IMPORTANCE-VS-RELEVANCE и REQ-HA-P07-NO-GLOBAL-OFF.
- Владелец: Builder.
- Где: `services/summary_memory.py`, `_search_graph_facts` / `_rank_key` (~4464–4474) и вычитание того же штрафа в `_knn_graph_facts`. Штраф до 0.30 вычитается из ключа, который на FTS-пути равен только `w_eff * importance_factor` и не знает, насколько запрос попал в этот факт. Вычитание идёт на любом вызове, включая `include_self=False`.
- Наблюдение (проба ревьюера, `:memory:`, decay/MMR выключены, лимит по умолчанию 10): 12 общих фактов «синегорье запись номер N» (вес 0.5, важность 5) и целевой «синегорье старое событие которое спрашивают» (вес 0.5, важность 6). Запрос «синегорье старое событие». Без пометок цель на 1-м месте из 10. После 8 пометок (штраф 0.30) цели в десятке нет. Существующий `test_explicit_query_finds_dampened_memory` кладёт в базу один совпавший факт, поэтому остаётся зелёным и контракт H24 не защищает.
- Что видит пользователь: после нескольких обычных ответов, куда память уже попала, прямой вопрос об этом старом событии может его не вернуть, если в чате есть ещё хотя бы десяток фактов с тем же словом. Это подавление, не взвешивание.
- Почему так выходит: база FTS-ранга для веса 0.5 — около 0.35–0.40. Потолок 0.30 больше разрыва между соседними фактами. Окно 6 часов само по себе разумное, шаг 0.05 доходит до потолка за 6 подач. Счётчик после тишины не сбрасывается: одна новая подача снова включает полный 0.30.
- Минимальная правка: штраф не должен выкидывать из выдачи факт, который без штрафа в неё входил бы. На FTS-пути специфичность запроса (или порядок до штрафа) остаётся главным ключом; 0.30 — только перестановка почти равных, не абсолютное вычитание, способное обогнать важность и совпадение. Добавить регрессию: не меньше `limit` фактов с общим токеном, целевой помечен до потолка, явный запрос всё равно возвращает его. Однофакторный тест не заменять и не считать доказательством.
- Перепроверка: эта проба + `tests/test_history_relevance.py`.

### 2. Повторная подача не учитывается у фактов с telegram id

- Требование: §11, «повторяемость уже использованного воспоминания»; заявленная пометка всех поданных фактов direct-пути.
- Владелец: Builder.
- Где: `get_rag_facts` (~4133–4151) помечает только `item_id`, начинающийся с `fact:`. `resolve_item_id` при наличии `tg_message_id` возвращает `tg:…`. Живая запись факта передаёт этот id (`summary_memory.py` ~3537, `direct_chat_service.py` `_memorize_direct_reply` ~8331–8333).
- Наблюдение: факт с `tg_message_id=424242` вернулся как `tg:424242` и в учёт подач не попал. На второй ambient-подаче он поднялся с 2-го места на 1-е, потому что соседи с `fact:` получили штраф, а он нет. Штатный `bot_direct_reply` с `tg_message_id=777` не помечен; `bot_self_reply` без telegram id помечен.
- Что видит пользователь: обычные факты переписки, привязанные к сообщению, при повторном показе не теряют приоритет. Наоборот, на их фоне приглушаются только факты без telegram id. Тесты вставляют факты без `tg_message_id`, поэтому дыру не видят.
- Минимальная правка: помечать `graph_facts.id` внутри `_search_graph_facts` / `_knn_graph_facts`, пока id ещё известен, и только при `include_self=True`. Не восстанавливать id из `item_id`. Тест: факт с `tg_message_id` помечается и переставляется так же, как факт без него.
- Править вместе с блокером 1. Иначе вновь помеченные факты попадут под тот же выталкивающий штраф.
- Перепроверка: проба второго показа с `tg_message_id` + новый тест + набор relevance.
