## 0. Общий объект границы (нужен всем четырём контрактам)

Единственная копия сообщений — таблица `smart_messages`. В процессе нет второй полной копии истории.

Граница — маленький объект, не архив. Поля:

| Поле | Смысл |
|---|---|
| `sample_id` | `hs_` + 12 hex от `sha256(f"{chat_id}|{anchor_ts}|{anchor_id}|{requested}")`. Стабилен для той же границы, не UUID. |
| `chat_id` | чат выборки |
| `anchor_ts`, `anchor_id` | самое новое сообщение, зафиксированное на старте (`ORDER BY timestamp DESC, id DESC LIMIT 1`) |
| `oldest_ts`, `oldest_id` | N-е сообщение назад от якоря включительно; если в архиве меньше N — фактическое самое старое |
| `requested` | N, которое просили |
| `available` | `min(requested, сколько строк есть на этой границе)` |
| `captured_wall` | `time.time()` момента захвата. Дедлайн продолжения этим полем не читается: срок несёт `exp` внутри cursor (§1). Отдельного monotonic-поля нет. |

Где живёт: локальная переменная хода, затем атрибут `tool_ctx.history_sample` (setattr, **не** новый обязательный аргумент `ToolContext.__init__` — все текущие вызовы остаются совместимыми). Это и есть «существующее хранение контекста хода». Отдельный реестр, таблица и TTL-словарь тел сообщений запрещены.

Захват — до `_build_user_content` (~2415), функция `capture_history_sample(db, chat_id, requested) -> bound | None` в `services/tool_router.py`. Делает два точечных чтения метаданных (якорь + граница N-й строки) и `COUNT` в этом окне. Тела сообщений не выбирает.

Кто вызывает захват: `DirectChatService` непосредственно перед `_build_user_content`, если `extract_history_depth` (ниже) вернул N **или** в аргументах уже есть явный `depth`. Тот же объект потом кладётся на `tool_ctx` при создании (~3178) и передаётся в `_build_user_content` / `_compose_user_content` / `_build_old_episodes` / `_build_rag_block` необязательным аргументом `history_sample=None`. `None` → байт-паритет текущего хода.

Предикат членства (авторитетный, не только timestamp):

```text
chat_id совпадает
AND (timestamp < anchor_ts OR (timestamp = anchor_ts AND id <= anchor_id))
AND строка входит в последние `available` строк этого предиката
    при ORDER BY timestamp DESC, id DESC
```

Новые сообщения после якоря в выборку не входят и выборку не сдвигают (H8).

## 1. CONTINUATION — продолжение через строковый результат

### Выбранный дизайн

Один инструмент `get_recent_history`. Новый параметр схемы — необязательный `cursor` (string). Новый инструмент не создаётся.

Состояние между страницами хранит **сам cursor** (самодостаточный, подписанный) плюс уже захваченный `history_sample` на `ToolContext`. Тела страниц в состоянии не хранятся: следующая страница перечитывается из БД тем же предикатом.

Почему не реестр в процессе и не таблица: реестр — второй источник правды и умирает вместе с процессом, при этом всё равно пришлось бы хранить границу; таблица — новая миграция ради данных, которые уже есть в `smart_messages` и в cursor. Прецедент `_TOOL_DL_PENDING` сюда не переносится: там состояние невосстановимо из аргументов, здесь восстановимо.

### Маршрутизация `_get_recent_history` (заменяет приоритет «query всегда побеждает»)

Порядок жёсткий:

1. В аргументах есть непустой `cursor` → только продолжение этой выборки. Путь B запрещён. Новый якорь не ставится. Одновременные `depth` и `query` не читаются. Неверный cursor не подменяется `depth=50`.
2. Иначе если `getattr(ctx, "history_sample", None)` задан → страница этой выборки. `query` в аргументах путь B не включает.
3. Иначе если аргумент `depth` задан явно → путь A, якорь фиксируется этим вызовом (если сервис ещё не зафиксировал).
4. Иначе если `extract_history_depth(query или ctx.query)` вернул N → путь A с этим N. Это защита simple-пути, который по-прежнему шлёт только `query`. `services/direct_execution.py` не обязателен к правке.
5. Иначе если есть `query` → существующий путь B без изменений.
6. Иначе → `depth = 50`, путь A (дефолт не максимум).

`extract_history_depth(text) -> int | None` — чистая функция в `tool_router.py`. Это не словарь тем. Правило: целое N ≥ 1 (разделитель тысяч — пробел, неразрывный пробел `\u00A0` или запятая: `2 000` / `2,000`) в одном окне — 40 символов до начала числа и 40 после его конца — вместе с единицей счёта (`сообщени`, `messages`, `реплик`) и маркером недавности (`последн`, `last`, `недавн`). Нет числа, нет единицы счёта или нет недавности → `None` (путь B / дефолт, как сейчас). Числа 400 и 2000 не особые. Список тем пуст.

Явный `depth` никогда не уменьшается до 150, до 50 и до результата экстрактора.

### Формат строки (стабильный, разбирается кодом, не моделью)

Блок метаданных — **голова**. Тела — канонические строки `format_context_item` (уже один ряд = одно целое сообщение). Хвост — сентинел, который не заканчивается на `…`, чтобы `tool_result.py` ~550 не помечал конверт `truncated` из-за футера.

```text
@@HISTORY_SAMPLE v1
sample_id=hs_ab12cd34ef56
requested=400
available=400
processed=40
remaining=360
has_next=1
boundary_to=1730000000:18421
boundary_from=1729000000:18001
page_from=1729000000:18001
page_to=1729100000:18040
incomplete=0
reason=
cursor=v2.<b64>.<sig>
@@END_HEADER
[28.10.2026 07:46 | Имя | tg:123]: текст
@@HISTORY_SAMPLE_END
```

Версия головы `@@HISTORY_SAMPLE v1` и версия токена cursor `v2` — разные пространства. Голову до `v2` не поднимать: `parse_history_sample` ищет маркер v1. Пример выше — обычная первая страница без дыры (`incomplete=0`, `reason` пуст), не полная выборка: `has_next=1`. Поле `cursor=` пустое, когда токен не выпускается (`has_next=0` или нет `page_to`).

Правила полей:

- `available` в голове — захваченный размер выборки, не живой `COUNT`. Продолжение не пересчитывает его по текущей БД.
- `processed` — сколько сообщений этой выборки уже отдано, включая текущую страницу (`processed_before + fetched`).
- `remaining = max(0, available - processed)`. Инвариант головы: `processed + remaining == available`, пока `processed <= available`. Дыра в хвосте этот инвариант не ломает: пропавшие строки остаются в `remaining`, а не вычитаются из `available`.
- Первая страница: `has_next=1` только если `remaining > 0` и `fetched > 0`. Если `fetched == 0` и `remaining > 0` — голова с `incomplete=1`, `reason=anchor_missing`, без тел (устаревший `history_sample`, окно пустое). Это не префикс `ОШИБКА`.
- Продолжение по cursor: `has_next` считается по живым строкам после точки курсора, не по `remaining`. Правило и сосуществование с `incomplete=1` — в «Учёт дыры» ниже. Прежняя формулировка «`has_next=1` только если страница не оборвана технической причиной» для продолжения не действует: дыра называется, выживший хвост длиннее страницы дочитывается.
- `boundary_to` — якорь (новое). `boundary_from` — старый край выборки. Оба `timestamp:id`.
- `page_from` / `page_to` — края **этой** страницы, тоже `timestamp:id`.
- `incomplete=0|1`. Поле `reason=` головы — пусто, `tail_missing` или `anchor_missing`. Коды `timeout`, `db_error`, `stale_cursor`, `unknown_cursor` в голову не пишутся: это префикс ошибки. `cancelled` в `reason` не пишется: `CancelledError` пробрасывается.
- Пустая выборка: существующая фраза `_HISTORY_EMPTY`, без блока (паритет). Ошибка cursor/вызова: существующий префикс `ОШИБКА get_recent_history: <code>`, без головы и без тел. Префикс обязателен, чтобы `tool_result` классифицировал ошибку как сейчас.
- Страница не объявляется полной выборкой: при `has_next=1` или `incomplete=1` это видно в голове. Отдельная страница не подаётся модели как «вот все N». `incomplete=1` и `has_next=1` вместе законны.

Парсер: `parse_history_sample(text) -> dict | None` в `tool_router.py`. Ищет `@@HISTORY_SAMPLE v1` … `@@END_HEADER`. Нет блока → `None` (старый результат / путь B / префикс ошибки). `requested`, `available`, `processed`, `remaining`, `has_next`, `incomplete` — `int`, если строка целая; остальные поля — строки.

### Cursor

Токен в поле `cursor=` — `v2.<payload_b64>.<sig>`. Три сегмента через `.`. Средний сегмент — base64url **без padding** сырой pipe-строки, не сама pipe-строка.

Payload (ASCII, без текста сообщений), 13 полей, ровно в этом порядке:

```text
v2|chat_id|anchor_ts|anchor_id|oldest_ts|oldest_id|requested|available|processed|after_ts|after_id|exp|sample_id
```

Кодек: `_history_cursor_encode` / `_history_cursor_decode`.

- `available` / `processed` — захваченные счётчики. `processed` в токене — сколько уже отдано, включая страницу, которая токен выпустила. Продолжение берёт оба числа из подписи. Живой `COUNT` `available` не заменяет.
- `after_*` — последний отданный ряд этой страницы. Следующая страница: предикат окна выборки **и** `(timestamp > after_ts OR (timestamp = after_ts AND id > after_id))`, `ORDER BY timestamp ASC, id ASC`, `LIMIT` размера страницы. Первая страница читается с `after=None` (предиката продолжения нет). Токен с `after_ts=0`, `after_id=0` первой страницей не является и наружу не выпускается.
- Токен пишется только если `has_next=1` и есть `page_to`. Иначе поле `cursor=` пустое.
- `exp` — unix-секунды. Первая страница: `int(time.time() + ttl)` в момент кодирования; `captured_wall` для этого не читается. Продолжение копирует `exp` из разобранного токена и срок не продлевает. `ttl` — тот же резолв, что у tool-loop (`_history_cursor_ttl`): `settings.MCA_TOOL_CHAIN_TIMEOUT_SECONDS`, иначе `TOOL_CHAIN_TIMEOUT_SECONDS` (360). Не новый TTL. Просрочка: `exp < int(time.time())` (`exp`, равный текущей unix-секунде, ещё годен).
- `sig` — первые 16 hex `hmac.sha256(process_key, payload)` по сырой pipe-строке, не по base64. `process_key` — `secrets.token_bytes(32)` на импорте модуля, не секрет `media_share` (чужой контур). Сравнение через `hmac.compare_digest`. Хеш `sample_id` при разборе заново не считается: строка покрыта подписью; decode проверяет префикс `hs_` и длину 15.
- Рестарт процесса инвалидирует подпись → честная ошибка, не новая выборка.
- Формат v1 не читается. Отказ и на префиксе токена `v1.`, и на payload, который не из 13 полей или не начинается с `v2`, даже если подпись текущего ключа верна. Совместимости с payload без `available`/`processed` нет: иначе продолжение молча ужало бы окно до живого `COUNT`.

Отказ cursor (все случаи — fail closed, путь B и дефолт 50 запрещены; страница не читается):

| Случай | reason | Строка |
|---|---|---|
| не 3 сегмента / префикс не `v2` / пустой payload или подпись / base64 не разбирается / подпись не сходится / payload не 13 полей или не начинается с `v2` | `unknown_cursor` | `ОШИБКА get_recent_history: unknown_cursor` |
| `chat_id` cursor ≠ `ctx.chat_id` | `unknown_cursor` | то же |
| `sample_id` не `hs_` или длина ≠ 15 | `unknown_cursor` | то же |
| `available < 1`, либо `processed < 0`, либо `processed > available` | `unknown_cursor` | то же |
| `exp < int(time.time())` | `stale_cursor` | `ОШИБКА get_recent_history: stale_cursor` |
| якорь `(chat_id, id, timestamp)` отсутствует в БД | `anchor_missing` | `ОШИБКА get_recent_history: anchor_missing` (без головы и без тел) |
| `COUNT` строк после точки курсора невозможен | `db_error` | `ОШИБКА get_recent_history: db_error` (без головы и без тел) |

`timeout` на wait_for (10 с) — тот же префикс `ОШИБКА get_recent_history: timeout`, без головы. `CancelledError` не превращается в строку. Прочее исключение — `ОШИБКА get_recent_history: <имя класса>`.

Проверка якоря до чтения страницы: пара `id` + `timestamp` в этом `chat_id`. Пустой probe (строки нет, либо нет сырого коннекта — `_history_probe_row` возвращает `None` и это не исключение) → `anchor_missing`, страница не читается. Только исключение `TypeError` / `AttributeError` на этом probe не блокирует; тогда решает `COUNT`: `None` → `db_error`, не тихая страница.

### Учёт дыры (`tail_missing`)

Только продолжение по уже принятому cursor. Функции: `_history_continue`, `_history_count_in_window`, `_format_history_page`.

- `expected_remaining = available - processed` токена (оба поля cursor, до чтения страницы).
- `survivors_after` — живой `COUNT` строк окна строго после `after_*`. Это сверка, не новый `available`.
- `survivors_after < expected_remaining` → страница всё равно форматируется, выжившие строки отдаются, `incomplete=1`, `reason=tail_missing`. `available` не ужимается до числа выживших. `processed` этой страницы = `processed` токена + сколько строк реально прочитано. `remaining = max(0, available - processed)`. Инвариант `processed + remaining == available` сохраняется.
- `has_next` на этом пути: `1` только если страница непустая и `survivors_after > fetched`. Цепочка дочитывает выживших. Поэтому `incomplete=1` и `has_next=1` вместе законны (дыра названа, живой хвост длиннее страницы). `has_next=0` при `remaining > 0` тоже законно (обещанный остаток не достигнут, живых строк дальше нет).
- Гонка: `COUNT` ещё видел хвост не короче обещанного (`tail_missing` не поставлен), а чтение страницы вернуло 0 строк при `remaining > 0` → `has_next=0`, `incomplete=1`, `reason=anchor_missing`, тела пустые, голова есть. Без гонки пустой хвост ловится сравнением и получает `tail_missing`, не `anchor_missing`.
- Первая страница эту сверку не делает. Короткий архив (`available < requested`, страница дочитала окно) остаётся `incomplete=0`, `reason` пуст.

### Размер страницы

`_HISTORY_PAGE_ROWS = 40` — технический предел **одного** возврата, в целых сообщениях. Не потолок выборки. 40 совпадает с уже существующим техническим батчем эпизода (`episode_max_messages`, дефолт 40) и не является новым «максимумом истории».

Страница заканчивается на границе сообщения. Резать строку посередине нельзя. Одно сообщение длиннее любого транспортного бюджета всё равно занимает страницу целиком и остаётся в счётчике (`reason=single_message_oversize` на сегменте, не `text[:N]`).

Чтение страницы — `services/database.py:get_recent_messages` (DEPTH: порции + `ORDER BY timestamp, id`). Второй reader запрещён. Необязательные kwargs `anchor` / `after` уже на этой функции; дефолт `None` = «последние N» для прочих вызывающих. Новую функцию-дубль не создавать.

Обход страниц делает волна SEGMENTS, не модель и не tool-loop. `TOOL_MAX_TOTAL_CALLS` на этот обход не распространяется.

### Что эта волна явно не меняет

Путь B без количественной границы. Дефолт 50. Таймаут 10 с. Формат канонической строки. Схему других инструментов. Пакер evidence. Personality Core.

## 2. SEGMENT AGGREGATION — шов накопления сегментов

### Выбранный владелец

`DirectChatService.collect_history_segments`, новый метод в `services/direct_chat_service.py`. Вызов — на L1-пути **сразу перед** `_dx.build_evidence_pack` (~3656), когда бюджет evidence уже считается через `l2_evidence_budget_chars`.

Почему не другие кандидаты:

| Кандидат | Почему не владелец |
|---|---|
| `EvidenceBundle` | Собирается до инструментов (`_build_evidence_bundle`), frozen, про retrieval-ссылки. Поля сегментов туда не добавлять. |
| Retrieval Context | Фильтр памяти, не цикл анализа. |
| Context Composer | Только раскладка кусков по окну. Анализировать и подменять выборку конспектом ему нельзя. |
| L2 Writer | Единственный финальный писатель ответа. Не листает БД. |
| Summary / Episode | Фон. Заменой запрошенной истории не являются (§5, §8.2). |

Накопитель результата — уже существующий `EvidenceSource` инструмента `get_recent_history` на `ChainResult.evidence_sources`. Сырой текст страницы в этот source **не** кладётся, если выборка не влезает в один слот: иначе пакер обрежет голову и хвост потеряется. Туда кладётся блок покрытия ниже.

### Когда LLM не вызывается

Если `has_next=0`, `incomplete=0` и длина уже полученной страницы ≤ бюджет evidence этого хода — сегментный LLM не запускается. Страница целиком остаётся содержимым source. Дальше один существующий L2-вызов. Это короткий путь (H1/H2 и любое N, которое реально влезло).

### Когда выборка больше одного слота

Детерминированно, без LLM:

- режется упорядоченная выборка на сегменты целых сообщений;
- размер сегмента — сколько целых сообщений влезает в бюджет одного существующего вызова `self.llm.generate` (тот же бюджет, не новая константа символов);
- верх сегмента также ограничен `_HISTORY_PAGE_ROWS`, чтобы не читать пачку шире страницы;
- перекрытие границы — 2 сообщения. Они помечаются `boundary_context` и **не** считаются вторым событием (множество уже виденных `item_id`).

Семантический проход — только если сегмент не помещается в один слот L2:

- один вызов `self.llm.generate` на сегмент, `module="direct_chat"`, `step="history_segment"`;
- это не Вербализатор, не System2 stage-2, не новый агент, не PG-промпт;
- промпт — приватная константа рядом с методом, по прецеденту `_CHAT_RAG_RERANK_SYSTEM_PROMPT` («не канон, вне PG»);
- промпт машинный: вернуть JSON и ничего больше. Без тем, без имён из инцидента, без инструкций личности.

Форма JSON, которую код принимает:

```json
{"events":[{"refs":["tg:12","tg:15"],"continues":0,"note":"кратко"}],"status":"ok"}
```

Событие без `refs` отбрасывается (это не свидетельство). Битый JSON → сегмент `failed`, не тихий успех. `continues=1` код ставит сам, если `reply_to_id` первого сообщения сегмента указывает в предыдущий сегмент; модель может подтвердить, но не является источником связи.

На сегмент — один такой вызов. Повтор того же сегмента другим вызовом запрещён (H20). На сообщение — ноль вызовов.

После разбора тела сегмента из памяти процесса сбрасываются. Остаются: статус сегмента, диапазон id, список refs, короткие note. Это не копия истории.

### Как это лежит в промпте финального L2

Голова, которую `build_evidence_pack` сохранит даже при `piece[:floor]`:

```text
@@HISTORY_COVERAGE v1
sample_id=hs_ab12cd34ef56
requested=400
available=400
processed=400
remaining=0
complete=1
segments=10
failed=0
reason=
seg 1 tg:18001..tg:18040 status=ok refs=2
seg 2 tg:18039..tg:18080 status=ok refs=3 continues_from=1
@@END_COVERAGE
```

Затем строки событий `refs=... note=...`. Префикс покрытия всегда первый. Если даже строки статусов не влезают в бюджет evidence, лишние сегменты не выкидываются молча: `complete=0`, `reason=findings_budget`, в голове перечисляются индексы сегментов, чьи статусы не попали в слот. Финальный писатель не имеет права объявить полный охват.

Связь через границу: `continues_from=<index>` на строке статуса плюс общие `item_id` перекрытия. Одинаковые `item_id` — одно упоминание, не два события (H17). Смысловое слияние разных id в одну тему делает только финальный L2, который видит все строки статусов; отдельный проход «склеить темы» не добавляется.

Провал сегмента: строка `status=failed reason=timeout|llm_error|db_error`. Остальные сегменты сохраняются. `complete=0`. Дыра не заполняется RAG, конспектом или Old_Episode. `CancelledError` пробрасывается, цикл не глотает отмену. Истечение 360 с останавливает цикл, уже собранное сохраняется, `reason=timeout`, `complete=0` (H14, H19).

Недоступность этого прохода (нет llm / исключение на одном сегменте) не отменяет уже полученные сегменты и не роняет весь ход.

### Что эта волна явно не меняет

`EvidenceBundle`. Приоритеты композера (это волна 4). Пакер evidence — не править, пока голова покрытия лежит первой. Режимы речи. Путь, где выборка влезла в один слот.

## 3. QUANTITATIVE SAMPLE ↔ RANGE ISOLATION

### Выбранный дизайн

Количественная выборка — единственный источник утверждений «это произошло в последних N». Память вне выборки остаётся включённой, но не подтверждает события внутри диапазона.

`RetrievalRequest` для **подтверждения внутри диапазона** заполняется так (реальные края, не эвристика «12 часов» / «последний месяц»):

| Поле | Значение |
|---|---|
| `time_from` | `oldest_ts` включительно |
| `time_to` | `anchor_ts` включительно, зафиксированный на старте, не `time.time()` повторного чтения |
| `scope` | `"time_range"` |
| `mode` | `"auto"` — **не** `"history"` |
| `participants` | не трогать |

`time_from` / `time_to` — секундная точность существующего контракта. Тай-брейк id в `RetrievalRequest` не выразить. Поэтому timestamp-окно — грубый шлюз для кандидатов памяти. Доказательство членства в выборке — предикат §0 (`timestamp` + `id`), не «timestamp попал в интервал».

Новая функция `bind_quantitative_range(request, *, time_from, time_to) -> RetrievalRequest` в `mca_retrieval_context.py`. Возвращает новый frozen-запрос. Старые вызывающие без неё не меняются.

В `retrieve()`: если `scope=="time_range"` и обе границы заданы:

- не повышать `mode` до `history` по `_HISTORY_MARKERS` (список маркеров не менять);
- не применять `history_bias` (эпизоды не ставятся первыми поверх корпуса);
- в `_apply_filters` **только для этого scope** кандидат с `sent_at == 0` не входит в набор диапазона (fail closed). Для всех прочих запросов текущее условие `cand.sent_at and ...` остаётся байт-в-байт.

Запрос без количественной границы этот ветки не касается. «Вспомни, как…» / явный вопрос о старом событии по-прежнему ищет долгой памятью (H24).

### Как ведут себя источники, когда граница есть

Захват границы уже произошёл до сборки блоков, объект передаётся в билдеры.

| Источник | Поведение при `history_sample` |
|---|---|
| Сообщения выборки (этап A) | Единственные первичные свидетельства событий диапазона. Утверждение «X писал/делал в этих N» допустимо только с `item_id` из предиката §0. |
| `<Old_Episode>` | `_build_old_episodes` не вызывает `mode="history"` по всему корпусу. In-range хиты — через `bind_quantitative_range`. `get_messages_around` после чтения клиппится предикатом §0; ряды вне окна в P0-блок не попадают. Дословная пачка 120/60 вне окна запрещена. |
| Старый эпизод как пояснение | Не второй поиск по корпусу. Если хит вне окна всё же нужен для имени/связи, одна строка в новом куске композера (ниже): тема и время, пометка «вне выборки», без дословных 180 сообщений. |
| `<RAG_Memory>`, граф-активация, golden/nostalgia, Lore `<dig_result>`, head-конспект L2/running | Не выключать флаги. Не фильтровать «в ноль». К существующему тексту prepend одна строка-баннер. Origin-метки и `_SELF_ECHO_INSTRUCTION` остаются. |
| Собственные ответы бота | Не становятся доказательством события диапазона. Ранжирование эта волна не меняет (это RELEVANCE). |

Баннер — константа в `direct_chat_service.py`, без тем и имён:

```text
ДОПОЛНЕНИЕ ВНЕ ВЫБОРКИ {sample_id}: не подтверждает события внутри запрошенного диапазона.
```

Кусок композера: новый kind `history_supplement`, приоритет **P2** (как RAG и конспект, не P0), слот в `CANONICAL_ORDER` сразу после `episode` (сдвинуть последующие индексы на +1). P0 остаётся только у клипнутого in-range эпизода. Под давлением окна supplementary вытесняется раньше периода — это правильно. Удалять содержимое памяти нельзя.

`mode="history"` при **отсутствии** количественной границы работает как сейчас, включая маркеры и Old_Episode. Количественная граница перекрывает маркеры только на этом ходе и только для запроса периода.

### Что эта волна явно не меняет

Глобальные флаги GraphRAG / Lore / summary. Текст self-echo. Схему `EvidenceBundle`. Ранжирование `w_eff` и touch-TTL (волна RELEVANCE). `_HISTORY_MARKERS` как кортеж. Поведение retrieval без `scope=time_range`.

## 4. SAMPLE ID + INVALIDATION

Идентичность выборки — `chat_id` + пара якоря `(anchor_ts, anchor_id)` + `requested`, свёрнутая в `sample_id` (§0): `hs_` + 12 hex от `sha256(f"{chat_id}|{anchor_ts}|{anchor_id}|{requested}")`. Одного timestamp недостаточно: при равном времени порядок задаёт `id`. Захват и страницы читают тот же ключ (`ORDER BY timestamp, id` в `services/database.py:get_recent_messages`).

Форма id: `hs_` + 12 hex, только `[a-z0-9]`, длина 15. В логи и в голову строки — да. В публичный ответ пользователю служебный id выносить не требуется. Decode не пересчитывает хеш: префикс, длина и подпись payload.

Инвалидация:

- Новые сообщения после якоря выборку **не** инвалидируют и **не** сдвигают.
- Продолжение после `exp` или с битой подписью — ошибка §1, не новая выборка «последние N от сейчас».
- Токен v1 и v2 с несогласованными счётчиками (`available < 1`, `processed < 0`, `processed > available`) — `unknown_cursor`, fail closed. Это не откат на путь без cursor.
- Удалённый якорь на входе cursor — `anchor_missing` префиксом `ОШИБКА`, без головы. Пустая страница при ненулевом `remaining` — голова с `reason=anchor_missing` (§1), не новая выборка.
- Рестарт процесса — битая подпись, fail closed.
- Новый пользовательский ход без cursor — новый захват (новый якорь). Это другой запрос, не продолжение.
- Отдельного TTL-реестра нет. Срок cursor — тот же wall-clock резолв, что у tool-loop: `settings.MCA_TOOL_CHAIN_TIMEOUT_SECONDS`, иначе 360 с. `exp` первой страницы ставится при кодировании токена; следующие страницы тот же `exp` наследуют и не продлевают.

Параллельные ходы одного чата не делят состояние: у каждого свой `ToolContext` и свой якорь. Cursor чужого `chat_id` отвергается.
