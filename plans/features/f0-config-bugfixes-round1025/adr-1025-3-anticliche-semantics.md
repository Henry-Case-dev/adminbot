# ADR-1025-3 — Анти-клише: семантика «вместимость vs партия», пакетное пополнение, честные статусы

- **Статус:** **Accepted** (Step 2 @Architect, 20.09.2026)
- **Фича:** F0 `f0-config-bugfixes-round1025` — F0.3
- **Тип:** backend (воркер/кэш) + UI (монитор)
- **Связано:** `spec.md` §3; `tasks.md` T-2427…T-2433; ADR-1024-3 (F7 round1024), ADR-1023-4 (F4 round1023)
- **Задачи:** T-2427…T-2433

## Контекст

1. `limits.anticliche_max_patterns` (дефолт 200, clamp 1…1000; `services/param_catalog.py:1441-1447`, `services/anticliche_cache.py:36-52`) применяется и как вместимость БД-кэша, и как число фраз за один LLM-вызов: `EXTRACT_SYSTEM_PROMPT.format(max=anticliche_cache.max_patterns())` (`services/anticliche_worker.py:468-477`).
2. Один запрос «дай 200 фраз» превышает выходной лимит модели → JSON обрезан (`parse_patterns → None` → `mark_status('parse_error')`, кэш сохраняется, `anticliche_worker.py:425-434`) либо исключение провайдера (`llm_error`, `:402-413`). В БД остаётся прежний список (**20** при старом потолке 20), UI: `20 / 200` (`web/index.html:412-413`).
3. `_is_fresh(fetched_at)` < 7 дней → `refresh(force=False)` = `fresh` без LLM (`:361-372`); повышение лимита не запускает пересборку.
4. `build_patterns` дедупит только внутри прогона (`:174-197`), не против БД; пакетного добора нет — один прогон = одна партия.
5. UI безусловно маппит `last_status` (`web/app.js:4524-4530`): `llm_error → 'ошибка модели'`; «0 новых/пусто» не отличается от сбоя.
6. Per-chat trap: воркер читает лимит только глобально (`hot.get`), а ключ категории `limits` формально `per_chat=True` (`param_catalog.py:118-127`). UI форсит global (`web/app.js:4583` `per_chat:false`).

Статусы в коде: `never|ok|fetch_error|llm_error|parse_error|empty` (+ `budget_skip|disabled|fresh` на уровне `refresh`) — `anticliche_cache.py:55-57`, `anticliche_worker.py:347-350`.

## Решение

### D1. Разделить семантики (§4.3)
- **Вместимость** — `limits.anticliche_max_patterns` (1…1000): сколько паттернов хранить и питать детектор.
- **Размер партии за обновление** — новый env-only `ClassVar ANTICLICHE_MAX_PATTERNS_PER_RUN` (default ≤ 40; вне `param_catalog` → Δ каталога = 0): сколько просить за один LLM-вызов, с запасом под выходной лимит модели.
- UI отражает обе величины: `сохранено N / вместимость M`, `за обновление ≤ K`.

### D2. Пакетное пополнение (bounded)
Цикл: читать `stored`; пока `stored < capacity` и `rounds < MAX_ROUNDS` и `worker_budget.consume` разрешает: LLM просит ≤ `per_run` → `parse_patterns` → **дедуп против уже сохранённых** + внутри партии (по нормализованной фразе и по хардкод-правилам) → merge. При 0 новых уникальных — **стоп, успех** («нет новых»). Запись — одна (или инкрементальная) `write_patterns`. Лимит раундов и расходов конечен.

### D3. Честные статусы и «0 новых ≠ ошибка модели»
- Развести: `ok` (записано ≥1), `no_new`/`empty` (валидный ответ, новых уникальных нет — **успех**), `llm_error` (сбой провайдера), `parse_error` (невалидный ответ), `fetch_error`, `budget_skip`, `fresh`.
- UI-маппинг (`clicheStatusLabel`) дополняется отдельной подписью для «нет новых» (успех); `llm_error` показывается как «ошибка провайдера», а не обобщённая «ошибка модели».
- Stale `last_status` не переживает успешный прогон: статус обновляется каждый прогон (в т.ч. при 0 новых).
- `fetched_at` обновляется только при реальном заборе (как сейчас); ошибка не должна маскироваться под свежесть.

### D4. Per-chat trap закрывается как global-only
Кэш — глобальная singleton-сущность. `limits.anticliche_max_patterns` трактуется **только** в глобальном слое: канонический writer (см. ADR-1025-2 D2/D6) не допускает per-chat-запись этого ключа; воркер читает глобал. Регрессионный тест: per-chat-попытка не меняет эффективный лимит воркера.

### D5. Событийная диагностика (§4.4, T-2431)
Структурированные события: `ANTI_CLICHE_UPDATE_START`, `ANTI_CLICHE_MODEL_REQUEST`, `ANTI_CLICHE_MODEL_RESPONSE`, `ANTI_CLICHE_PARSE_ERROR`, `ANTI_CLICHE_DEDUP_COMPLETE`, `ANTI_CLICHE_SAVE_COMPLETE`, `ANTI_CLICHE_UPDATE_COMPLETE`, `ANTI_CLICHE_UPDATE_FAILED`. Поля: `capacity`, `per_run`/`applied_limit`, `initial_count`, `candidates`, `duplicates`, `saved`, `final_count`, `model`, `duration_ms`, `reason`. **Фразы/секреты не логируются** (R17).

## Последствия

**Positive**
- «20 вместо 200» устраняется первопричинно: партия не превышает выходной лимит, база добирается до вместимости.
- «0 новых» перестаёт выглядеть как сбой; статусы честные.
- Диагностика восстанавливает причину по событиям (заданный/применённый лимит, кандидаты, дубликаты, сохранено).
- `smart_cache`/ADR-1024-18 не затрагиваются; Δ DDL = 0, Δ каталога = 0.

**Negative**
- Несколько LLM-вызовов на догон до вместимости → больше расходов; ограничивается `MAX_ROUNDS` + `worker_budget`.
- Новый env-флаг (не в каталоге) — документируется в `.env.example` (Info).

## Альтернативы

- **A1. Просто увеличить `max_tokens` модели** — **отклонено**: не наш контракт, ненадёжно между провайдерами.
- **A2. Оставить один вызов, но просить 200 и резать** — **отклонено**: не наполняет базу, остаётся «20/200».
- **A3. Per-chat лимит анти-клише** — **отклонено**: кэш глобальный; per-chat = неоднозначная семантика и скрытый no-op.
- **A4. Трактовать «0 новых» как ошибку** — **отклонено**: противоречит §4.2 ТЗ.
