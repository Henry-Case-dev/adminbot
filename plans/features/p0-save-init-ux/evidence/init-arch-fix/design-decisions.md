# INIT-ARCH-FIX — дизайн-решения (CONTEXT §2, CATCHUP §3, SMALL)

Лейн: **INIT-ARCH-FIX** (writer; `services/initiative_observer.py` + `services/initiative_diagnostics.py` + тесты).
Источник: `source-p0-followup-2026-10-18.md` §1 (пп. 1.2/1.3/1.5/1.6) + gap-check `init-arch-gap.md` §2.

## 1. Адаптивное окно оценки (CONTEXT, ТЗ §1.3 «10 / 50–200+»)

* Константы: `EVAL_WINDOW_BASE_MESSAGES = 10`, `EVAL_WINDOW_MAX_MESSAGES = 200`;
  жёсткая `EVAL_WINDOW_MESSAGES = 14` удалена (её единственный внешний
  потребитель — trace диагностики — переведён на общий резолвер).
* Закон роста: `window = clamp(backlog, base, cap)`, где
  `backlog` = число **живых** (`import_key IS NULL`) текстовых реплик чата
  с `id > watermark`, замеренное bounded-выборкой (`ORDER BY id DESC LIMIT cap+1`).
  Это буквальный «рост по объёму накопления».
* Почему накопление, а не темп (`recent_message_rate`): накопление с
  watermark — прямое измеримое «сколько обсуждения ещё не оценено», и именно
  оно масштабирует промпт. Темп уже участвует в мягких целях W5 (интервал
  проверок); второй порог-регулятор на том же сигнале удвоил бы эвристику
  без наблюдаемой пользы.
* Явный кап: 200 реплик × `EVAL_MSG_TEXT_CAP=300` символов →
  ≤ ~60k символов user-контента на ОДИН вызов оценки; вызовов ≤
  `MAX_EVALS_PER_PASS=4` на проход и ≤ `eval_llm_budget_per_day` профиля
  (4–24/сутки) — объём bounded и бюджетно ограничен.
* Выборка: `LIMIT min(cap, window) * 3` (запас на неэлигибельные строки),
  возвращаются САМЫЕ СВЕЖИЕ реплики в хронологическом порядке.
* Паритет: дедуп контекста сохраняется — окно детерминировано состоянием БД,
  поэтому повторный проход по тем же данным даёт тот же контекст-хэш
  (свидетель `test_context_duplicate_still_blocks_repeat_evaluation`).
* Диагностика dry-run: trace шага `window` берёт `limit` из
  `runner._window_messages(...)` — боевой путь и «Проверить инициативу» идут
  тем же резолвером (было жёсткое 14).

## 2. Bounded-дайджест пропущенного (CATCHUP, ТЗ §1.2)

* **Триггер**: `since_id` (watermark ДО оценки) > 0 — т.е. «после отсутствия
  пришли новые» — и в интервале `(since_id, rows[0].id)` есть живые реплики;
  bounded-probe (`LIMIT 1000, ORDER BY id DESC`) → `skipped`; дайджест
  строится при `skipped ≥ EVAL_DIGEST_MIN_SKIPPED = 50`.
* **Почему не на первом наблюдении** (watermark = 0): ТЗ §1.1 определяет
  первый запуск как «от актуального хвоста»; всё до хвоста — архив, а не
  «пропущенное с последнего наблюдения». Это же сохраняет байт-паритет
  P0-теста anchor (`llm.calls == 1`).
* **Выборка**: ≤ `EVAL_DIGEST_SAMPLE_MAX = 200` реплик — самые СВЕЖИЕ из
  пропущенного (id DESC → хронологический порядок): ближе всего к текущему
  окну и развитию темы. Более ранняя часть разрыва (за капом) в выборку не
  попадает — осознанная граница сжатия (зафиксирована в SUMMARY «остатки»).
* **ОДИН дешёвый LLM-стрим**: `self._llm.generate(step="skipped_digest",
  temperature=0.2, max_output_tokens=220, timeout=30s)` — существующий
  llm-путь наблюдателя; бюджет — тот же слот оценки (лимиты считают ОЦЕНКИ;
  дайджест — вход к той же оценке; отдельного расходного канала и новых
  каталог-ключей нет, Δcatalog = 0).
* **Форма блока**: детерминированная статистика («сколько пропущено»
  (≥1000 → «не менее»), участников в выборке, период UTC) + LLM-резюме
  ≤500 символов; итог ≤ `EVAL_DIGEST_TOTAL_CHARS = 800`; едет в промпт оценки
  как `<Skipped_Chat_Digest>`.
* **Fail-open**: недоступность/пустой ответ/исключение → `""` (warning в лог);
  оценка идёт по актуальному окну, как до фикса; дайджест НИКОГДА не бросает.
* **Паритет**: разрыв < 50 реплик → дайджеста нет вовсе; именно поэтому
  `test_b01_*`, `p0_*`, `w5_*` швы не меняют число LLM-вызовов.
* **Почему не «задокументированное решение о bounded-окне»** (альтернатива из
  брифа): ТЗ §1.2 прямо требует «смысловое сжатие пропущенного», и реализация
  соразмерна — один вызов только при реальном большом разрыве, с жёсткими
  капами и fail-open. Вариант «окно-кап вместо дайджеста» оставлен бы без
  сжатия «середины» (800 реплик из примера теста), поэтому отклонён.

## 3. SMALL — порог не выше фактической истории

* `required = min(profile.eval_min_messages, max(MIN_EVAL_MESSAGES_FLOOR, depth))`,
  где `depth` — число живых реплик чата (bounded-выборка `LIMIT need+1`).
* Устоявшийся чат (depth ≥ порога) — паритет профиля; чат из 3 реплик не
  оценивается (floor 4 сохраняет качество); новый чат 5–20 реплик получает
  оценку, когда накопление не меньше его же истории.
* Тот же резолвер используют ворота `chat_block_state` (панель «что мешает»
  показывает тот же порог, что боевой путь).

## 4. BACKFILL — «живое = import_key IS NULL» во ВСЕХ чтениях

* Фильтр стоит в 11 чтениях `smart_messages` наблюдателя: anchor (MAX id /
  MIN id), scan, окно, backlog окна, probe и sample дайджеста, темп,
  `live_messages`, `_cursor_lag`, depth для SMALL-порога.
* Anchor считается по ЖИВЫМ строкам: массовый импорт не может «увезти»
  живой старт внутрь пачки импорта.
* Перф-замечание (incidental, вне объёма): выделенного частичного индекса под
  `import_key IS NULL` нет; при очень больших импортах можно добавить
  partial index `smart_messages(id) WHERE import_key IS NULL` (DDL в этом
  лейне не менялся).

## 5. Что осознанно НЕ менялось

* R17: наружу (события/payload/логи) — только ID/коды/числа. Дайджест и
  промпты живут только в user-контенте LLM-вызовов; `rationale` капнут
  каноном цели и едет лишь в контекст повода (opportunity_row), не в события.
* `candidate.source_refs` в ephemeral-ветке: refs уже едут в
  `opportunity_row.source_refs`; менять форму decision-кандидата не требовалось
  (не в объёме брифа, отмечено как incidental).
