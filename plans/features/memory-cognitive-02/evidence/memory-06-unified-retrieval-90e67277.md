## 3. Регрессия второго раунда: 1 факт из 4

**Дефект.** На `40ae401a` профиль человека (purpose `identity`, `biography`,
`appearance`) отбирался FTS/лексическими каналами по тексту запроса. Факт
«работает программистом» о человеке не содержит его имени, поэтому в профиль
не попадал: из 4 фактов о человеке возвращался 1 — тихая потеря памяти.
Двойник с именем в тексте этот дефект скрывал.

**Воспроизведение (независимое, PM).** В отдельном временном worktree на
`40ae401a` подставлен только тест-файл кандидата (реализация осталась
родительской), прогон:

```
python -m pytest tests/test_memory_unified_retrieval_06.py -q
# → 14 failed, 29 passed
```

Фактический вывод ключевого теста на `40ae401a`:

(вернулось ['Лёха носит бороду'])
AssertionError: biography: потеряны факты субъекта без имени в тексте

**Исправление.** Факты о человеке отбираются по субъекту: новый канал `subject`

порядок `weight DESC, created_at DESC`) по `subject_ref_id` (устойчивый ref
разрешается из uid) и по legacy `target_user`. Второго поиска, второго движка и
новых индексов нет — переиспользовано чтение, которым пользовался прежний
`get_user_context` (`ARCH_REUSE_CONFIRMED`).

## 4. Механика субъект-канала

- `RetrievalRequest.subject_names` (имена/алиасы субъекта) — аддитивное поле;
  канал `subject` входит в политику по умолчанию только если запрос объявил
  субъекта ИМЕНЕМ; явный `channels` действует буквально.
- Профильные назначения (`identity`/`appearance`/`biography`) читают
  `channels=("subject",)`, `general` — прежняя политика плюс субъект-канал.
- Строка, отобранная в scope единственного объявленного субъекта, получает
  честную атрибуцию `subject_entity_id` — это питает гейты «не перепутан
  человек»/уместность, а не новое ранжирование.
- `preserve_channel_order` — выдача в порядке самого канала (последовательность
  политики, внутри канала — собственная упорядоченность), без типизированных
  бонусов доверия/свежести и без переупорядочивания identity-prior. Включён для
  профиля субъекта (`weight DESC`), среза `recent` и direct-RAG.
- direct-RAG: отбор фактов ответного блока снова идёт ТОЛЬКО каналом `vector`
  (прежний KNN/MMR `get_rag_facts` с FTS-фолбэком внутри чтения); `score` блока
  = limit − позиция, как у принятой выдачи. exact/lexical (вес 100/80 против 60)
  при малом top-k вытесняли релевантный KNN-топ и меняли состав блока.

## 6. Изоляция архива и bounded-чтение

- Архив (`archived_fact`, вытеснено по квоте) невидим обычной выдаче и виден
  только явному историческому запросу (`include_archived=True`), тест на
  реальном `DatabaseService`: живой факт в выдаче, архивный — только в
  историческом запросе.
- Структурная (поведенческая) гвардия вместо AST-поиска литерала: исполняются
  живые пути (reply, шесть purposes, инициатива, статистика) и проверяется
  ФАКТИЧЕСКОЕ значение `include_archived` в запросе; `dig_into_lore` передаёт
  `True` в канал `graph_facts`.
- Batch-чтение фактов для evidence summary ограничено `_BUNDLE_BLOCK_MAX_REFS`
  ДО обращения к БД (тест на 30 ссылках).

## 7. Паритет direct-RAG

- Ровно один вход единого `retrieve` на ответ; `channels=("vector",)`,
  `preserve_channel_order=True`, `include_archived=False`; прежнее чтение RAG
  не вызывается (`legacy_calls == 0`, `unified_calls == 1`).
- На одном и том же наборе фактов unified-путь и прежнее чтение дают ОДИН И ТОТ
  ЖЕ блок (состав и порядок, ASC-хронология).
- Набор, где FTS-канал нашёл бы третий факт, а типизированный ранг поставил бы
  самый свежий первым, сохраняет состав и порядок KNN-топа (`[1, 2]`, без
  `[3, 1]`); FTS-факт вне top-limit в блок не попадает.

## 10. Живая граница — что НЕ доказано

В тестах канал `vector` работает на двойниках, а внутри чтения срабатывает
FTS-фолбэк: реальных эмбеддингов и `vec0`-KNN на живом корпусе в прогонах нет.
Поэтому настоящим доказательством НЕ являются:

- фактическое качество KNN/MMR-ранжирования на живом корпусе (релевантность
  состава `<RAG_Memory>` и профилей на реальных эмбеддингах);
- поведение при деградации провайдера эмбеддингов / FTS-фолбэке на живых данных;
- попадание субъект-канала и паритета direct-RAG в реальную выдачу Writer.

Условие закрытия (строка `MEM-06-RUNTIME`, `READY_FOR_LIVE`, postdeploy):
на развёрнутом кандидате с реальными эмбеддингами профиль человека возвращает
все известные подтверждённые факты о нём (включая факты без имени в тексте),
архив не протекает, состав и порядок блока RAG direct-ответа совпадают с
принятой выдачей на тех же данных, перекрёстной утечки между одноимёнными
людьми нет; зафиксированы соответствующие события/метрики. До этого строка
остаётся `READY_FOR_LIVE`, а не `VERIFIED`.
