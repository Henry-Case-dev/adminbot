подтверждённой сущности, иначе нейтральная подпись с объяснением.

## 7. Честная продуктовая оценка [pm-binding]

**Технически фича безопасна.** Основания:

1. OFF-паритет обычной выдачи полный: 34/34 по составу и порядку в
   specific и thematic (§6), задержка не растёт.
2. OFF-тик не делает ни одного SQL; таблицы в проде пусты; схема не менялась
   (`user_version 44`), откат — `git revert` на 2.58.167 без схемного шага.
3. Сборка детерминирована и стабильна: 0 created / 0 dropped на повторной
   сборке, 0 аномалий, 100 % reuse id.
4. Стоимость ограничена: p95 7 с на самый большой чат раз в час, вне горячего
   пути; на остальных чатах — десятки миллисекунд.
5. Ошибки изолированы: сборка одного чата не рвёт планировщик; отсутствие
   таблиц/сборки даёт честно пустой канал.

**Ценность сейчас низкая.** Основания:

1. **99.87 % связей — `legacy`** (64 346 из 64 432), а подпись по контракту
   требует `confirmed`/`tentative`. Итог: **все проверенные подписи во всех
   пяти чатах нейтральные** («Сообщество 1/2/3…»), доминирующих нет ни одной.
   Пользователь не увидит смысловых имён — ровно тот сценарий, который §8
   запрещает выдавать за «смысловые сообщества».
2. **Медиана размера сообщества — 2 узла**: половина сообществ это пары.
   Показывать «Сообщество N» из двух узлов — шум, а не структура.
3. Единственный реальный вклад — thematic-канал, который меняет 25 из 34
   запросов, но меняет их **безымянными** сообществами; объяснимой пользы для
   ответа это сейчас не даёт.
4. Цена не нулевая: 7 с работы CPU/IO раз в час на большом чате ради
   нейтральных подписей.

Отсюда: включать флаг «потому что технически безопасно» — неправильный выбор.
Техническая безопасность нужна как условие возможности, а не как причина
включения.

## 8. ИНЖЕНЕРНОЕ РЕШЕНИЕ: временный hold флага OFF (это не вопрос владельцу)

Действует новое постоянное правило проекта (`AGENTS.md`, 09.11.2026):
**готовая** функция при первом production-деплое включается глобально по
умолчанию, а выключение флага **не является** способом закрыть дефект качества —
чинится причина (фильтрация, ранжирование, источник данных). Решение ниже
записано так, чтобы ему соответствовать, и не превращает OFF в постоянное
состояние.

| Поле | Значение |
|---|---|
| Решение | `MCA_MEMORY_COMMUNITIES_ENABLED` **остаётся OFF в этой выкладке** — как временный hold на время исправления причины, **не** как закрытие качества и **не** как постоянный режим |
| Кто решает | инженерный контур (PM/DevOps); **не Human Gate**, не канарейка, не запрос разрешения |
| Дата | 2026-11-09 |
| Состояние прода | флаг OFF, таблицы пусты, job зарегистрирован и инертен |
| Откат | не требуется: поведение = baseline 2.58.167 |
| Условие окончания hold | функция становится «готовой» (есть пользовательский потребитель, причина вырожденных подписей устранена, проверки пройдены) → следующий релиз выходит с **заводским ON**, без нового согласования (PET_PROJECT + правило 09.11.2026) |

Почему правило «включать готовое» здесь пока не срабатывает: функция **не
готова** в продуктовом смысле (контейнер MEMORY-07 PENDING, пользовательского
показа сообществ/метрик нет — §9.2), а негодный результат (все подписи
нейтральные) — это **дефект источника данных** (99.87 % связей `legacy`), а не
свойство безопасного режима. По правилу проекта такой дефект возвращается
исполнителю и исправляется в причине; выключение флага его не закрывает.

Основания для hold: технически безопасно (§7.1), но подписи вырождены
(99.87 % legacy → все подписи нейтральные), половина сообществ — пары узлов, и
часовая сборка стоит ~7 с на самом большом чате. Включать сейчас — заплатить
стоимость и показать пользователю бессмысленные названия; выдавать это за
готовую функцию нельзя.

Обязательное действие по причине (возвращается исполнителю, не владельцу):
поднять плотность подтверждённого провенанса существующим контуром
(бэкфилл §5.3 B3 контракта / factcheck-provenance), чтобы подписи могли
опираться на `confirmed`/`tentative`, и не считать OFF исправлением. Это
инженерная работа, а не ожидание.

### 8.1. Точный триггер пересмотра

Пересмотреть решение (свежим **read-only** измерением на копии прод-БД, без
изменения конфига прода), когда наступит **любое** из двух:

1. **Провенанс-плотность:** доля `confirmed + tentative` среди связей,
   использованных сборкой, станет **материально больше** текущих 0.13 %
   (86 из 64 432) — ожидаемо как результат обязательного действия по причине
   выше, а не пассивного ожидания. Рабочий ориентир «материально»: доля, при
   которой хотя бы часть сообществ получает доминирующую сущность с источником
   (сейчас — ноль сообществ), т.е. непустые `dominant_names` в замере. Порог не
   догма: смотреть на фактическое распределение и на долю сообществ с
   осмысленной подписью, а не на одну цифру.
2. **Потребитель:** визуальный граф (MEMORY-08, строки MEM-08.5/08.7/08.9)
   начинает требовать **живые** community-данные для отрисовки сообществ,
   подписей или счётчика «Сообщества: c».

Процедура пересмотра (та же, что дала этот замер): копия прод-БД через sqlite
backup API → сборка по чатам с гейтом, включённым только в процессе → таблицы
§3–§6 (время, размеры, провенанс, подписи, reuse id, аномалии) → паритет
retrieval 34 запроса в обоих режимах → сравнение с этим артефактом. Включать
только если одновременно: паритет OFF сохранён, подписи перестали быть
поголовно нейтральными (или потребитель явно требует данные), p95 сборки
остаётся в пределах часового периода.

Что **не** является триггером: рост числа узлов/рёбер сам по себе, наличие
пустых таблиц, «фича уже выкачена», просьба «включить, раз безопасно».

### 8.2. Что это решение не означает

- Не означает, что MEMORY-07 закрыт или принят: контейнер остаётся PENDING (§9).
- Не отменяет ни одну обязательную строку §8 и не переводит ни одну строку в
  VERIFIED «по решению».
- **Не означает постоянного OFF.** Держать готовую функцию выключенной
  бессрочно запрещено правилом проекта; hold снимается исправлением причины и
  следующим релизом с заводским ON.
- Не является исправлением дефекта подписей: дефект остаётся открытым и
  назначен исполнителю.
