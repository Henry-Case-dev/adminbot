## 3. Effective-state флага (не каталог, а фактическое значение) [deploy]

| Слой | Значение |
|---|---|
| `env MCA_MEMORY_COMMUNITIES_ENABLED` | не задан (`None`) → env-половина гейта **ON** |

| effective глобально (`chat_id=None`) | **True** |
| effective по 5 чатам с `nodes` | **True** для всех (5/5) |

Скрытого ранее сохранённого `false` в PG нет: OFF-состояние 2.58.168 было только
заводским дефолтом, поэтому перевод дефолта в ON дал effective ON без правок
пользовательских настроек и без backfill.

Вывод **[pm-binding]**: требование «после выката флаг эффективно ON по умолчанию»
выполнено на всех слоях резолва, включая per-chat. Это единственная часть
«live-условия» MEMORY-07, которая раньше была не выполнена.

Отношение к прежнему решению `ED-MEMORY-07-COMMUNITIES-2026-11-09` (hold с флагом
OFF в 2.58.168): временный hold снят выкладкой 2.58.169 — по постоянному правилу
проекта готовая и независимо проверенная функция при первом production-деплое
включается заводским ON, и OFF не может оставаться постоянным состоянием.
Причина качества при этом **не закрыта** (провенанс исправлен только вперёд,
1 proven из 4 163); риск деградированных подписей снят тем, что наружу выходят
только proven-сообщества. В карте решение помечено `superseded` с сохранением
исходных rationale/trigger, чтобы история не переписывалась.

## 9. Измерение качества в масштабе: 1 proven из 4 163

Результат не является сбоем правила и не является регрессией:

- Граф по-прежнему доминирован **legacy**-рёбрами (в измерении волн 3–4 на той же
  базе — 64 346 legacy из 64 432, 99.87 %). Порог PROVEN требует сильного веса
  (`S ≥ 1.0`, `S/T ≥ 0.5`), а сильный вес берётся только из
  `confirmed`/`tentative`. При таком составе графа почти любое сообщество
  объективно WEAK — правило честно это и показывает: 1 из 4 163, доля 0.024 %.
- Исправление провенанса в источнике (`c816e83c`) поднимает долю **только вперёд**:
  оно меняет запись новых крон-триплетов (факт создаётся первым, ребро получает
  `fact_id`) и атрибуцию `subject_ref_id` для резолвимых субъектов. Проверено
  **[pm-code]** по диффу `services/summary_memory.py`: функции `_write_graph_triplets`
  и `_attach_fact_provenance` не содержат бэкфилла и не переписывают существующие
  рёбра/факты — исторические 64 тыс. рёбер остаются legacy, пока не появятся
  новые подтверждённые/сомнительные связи.
- То есть рост proven — ожидаемая функция притока `confirmed/tentative`, а не
  мгновенный эффект релиза. Выключение флага эту причину не устраняет и не
  применялось: флаг ON, наружу выходят только proven-сообщества, поэтому
  деградированные подписи пользователю не показываются (показ сообществ в UI
  вообще не входил в этот релиз).

Практический ориентир на будущее: появление непустых `dominant_names` у
нескольких сообществ и рост proven хотя бы до единиц процентов — признак того,
что провенанс графа восстанавливается.

## 10. Честные пробелы

1. **Автоматический часовой тик не наблюдался.** Job зарегистрирован, тот же код
   успешно строит сообщества на живой БД, но плановый запуск `_tick_communities`
   по расписанию не дожидались. MEM-07.3 остаётся PENDING.
2. **Авторизованное тело `/api/memory/search` не проверялось.** Нужен реальный
   `initData` администратора TMA. Доказан только факт публикации роута (401 без
   токена) и то, что эндпоинт идёт через живой `MemoryManager`.
3. **Визуальный рендер сообществ не входил в релиз.** Клиентской дельты нет;
   строки MEMORY-08/UI остаются PENDING.
4. **Сырьё измерения не приложено.** Отчёт фиксирует числа и процедуру, но не
   дампы; воспроизведение — по §12 на копии прод-БД.
5. **Стабильность id повторной сборкой в этой выкладке не перемерялась** (была
   одна сборка). MEM-07.5 опирается на прежнее измерение волн 3–4 (100 % reuse,
   0 created/dropped) и дополнительного прод-доказательства здесь не получает.
