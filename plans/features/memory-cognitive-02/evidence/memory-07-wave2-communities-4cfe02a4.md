## 5. Детерминизм

- 3 независимых экземпляра БД с одинаковым посевом (80 узлов / 200 рёбер):
  разбиение и членство побайтово совпали — **один sha256** на три прогона.
- Повторная сборка без изменений: тот же `community_id`-набор, новый только
  `build_id` (стабильность относится к `community_id`, не к сборке).
- Неизменённая пересборка реального фикстура: **26 сообществ переиспользованы
  с идентичными id**.

Алгоритм — локальное движение по взвешенной модульности, один уровень, обход
узлов по возрастанию канонического `nodes.id`, строгое улучшение с `1e-12` и
потолок 12 проходов; поэтому результат — функция входа, а не порядка словаря.

## 6. Веса и запрет повышения ассоциаций

- Ровно `confirmed 1.0 / tentative 0.5 / legacy 0.25 / cooccurrence 0.1`;
  других значений модуль не принимает (`test_community_weight_table_matches_contract`).
- Класс факта берётся только из существующего
  `graphrag_provenance.classify_fact_provenance` (тест с monkeypatch доказывает
  делегирование, а не локальную копию правил).
- **Пара только из `mca_associations` остаётся `cooccurrence` 0.1 даже когда
  оба её конца подтверждены и даже когда `status='accepted'`** — повышения до
  подтверждённой связи нет ни по соседству, ни по статусу гипотезы (MEM-07.6:
  связь как гипотеза, не как «доказано/родственники/причина»).

## 7. Идентичность и раскладка

- Схлопнутая сущность появляется в членстве **ровно один раз**, под
  каноническим `nodes.id`; UID в `mca_community_members` не попадает
  (`test_membership_stores_canonical_node_ids_never_uids`).
- Отдельного «merged node» в сообществе нет: разрешение идёт через
  существующий `resolve_entity` (read-only), а не через новую сущность.
- Смена раскладки не меняет `entity_id`.

## 8. Жизненный цикл сборки и публикация

- `building → active`; `active → superseded` только атомарно вместе с
  публикацией полного набора членов; `building → failed` при исключении,
  отмене, нарушении инварианта или неполной публикации. Ровно один `active` на
  чат.
- **Сбой публикации на настоящей SQL-ошибке второго INSERT** (не заглушка
  инварианта): предыдущий `active` остался нетронутым и читаемым, новая сборка
  стала `failed` с **нулём строк членства**, частичного `active` не возникло.
- `failed` не читается и не вытесняет предыдущий `active`
  (`test_failed_build_does_not_displace_active`).
- Retry после сбоя создаёт новый `build_id` и связывает его через
  `prev_build_id`; `community_id` при этом стабильны
  (`test_retry_after_failure_uses_new_build_id_but_stable_community_ids`).
- Отмена помечает сборку `failed` и пробрасывает исключение.

## 10. Что этим доказательством НЕ покрыто (граница производства)

Сознательно не заявляется как проверенное:

- **p95 стоимости сборки на реальном объёме** — не измерялась; замеры только
  на синтетике (40 узлов/380 ассоциаций, 80 узлов/200 рёбер).
- **Drift** (накопленное расхождение структуры и membership между сборками) —
  не измерялся; инкрементальный/пакетный планировщик появится в волне 3.
- **Реальное распределение провенанса** в прод-чате (доли
  confirmed/tentative/legacy/cooccurrence) неизвестно — все веса проверены на
  синтетике.
- **Качество подписей на реальных данных** — не измерялось; проверен только
  механизм: доминирующая сущность с источником либо нейтральное
  «Сообщество N» с основанием, LLM на горячем пути отсутствует.
- **Прод-рантайм не затронут**: кандидат живёт в ветке `integ/unify-release`,
  в `master` (`9be06823`) его нет, в производстве сборок сообществ пока ноль
  строк; `MCA_MEMORY_COMMUNITIES_ENABLED` не включался.
- **Отображение** сообществ в UI/API и **retrieval-join** активной сборки —
  волна 4 (MEM-07.3/07.5-UI/07.6-поиск), сейчас отсутствуют.

## 11. Не блокирует волны 3–4, но зафиксировано в backlog

1. Комбинация «сообщества ВКЛ + идентичность ВЫКЛ» оставляет схлопнутые узлы
   отдельными участниками (честный `unresolved_identity_nodes`, но состав
   сообщества при этом смешанный).
2. Экстремальное накопление одинаковых cooccurrence (200 повторов одной пары)
   сливает кластеры; нормализация — только после реальных замеров.
3. Плотные цепочки фрагментируются под слабыми связями; подбор веса — после
   read-only производственных данных.
