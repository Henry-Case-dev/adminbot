## 1. Что именно фиксирует M3 (и что не фиксирует)

M3 фиксирует контракт, а не реализацию:

1. канонический состав **21 видимой карточки** + 1 скрытого подмодуля, их `kind`, `runtime_gate`,
   `scope_capability`, master/owner-ключ, реальный consumer и способ управления;
2. информационную архитектуру `Каталог → Модуль → вкладка`, группы каталога и правила
   submodule/infrastructure/utility;
3. wireframes каталога, малого, сложного и инфраструктурного workspace, страницы «Время»;
4. состояния loading / empty / error / degraded / read-only / per-chat override /
   GLOBAL vs CHAT / GLOBAL OFF + CHAT ON / stale 409;
5. пять осей состояния (`desired`, `effective_runtime`, `ready`, `observed`, `authorization`) и
   атрибут источника выбора (`source`), с точными русскими подписями;
6. полный copy inventory до/после (`copy-inventory.md`), 401/403/404/503 и причины пустоты;
7. UI/API-контракт: что уже есть, чего не хватает, что переиспользуется;
8. responsive, token mapping, accessibility, данные первого viewport;
9. отображение требований M3 на M4A и приёмку;
10. конфликты и правила непересечения (MEMORY-08 S3, prompt registry, VMQ QRNG, SELF-DIAG,
    frontend-полоса) и **блокирующую зависимость M2.1** (см. §12).

M3 **не** фиксирует:

- реализацию M4A/M4B/M4C и не заменяет их приёмку;
- дизайн «Статуса» и страницы прав заново: действующие `m3-design-freeze.md` §4 и §5 остаются
  frozen-концепцией; M3 rev2 добавляет только карту экранов, навигацию и границы данных (§3.6);
- значения production-флагов; они проверяются live preflight (M4A) и M6;
- новые ACL, registry, storage, endpoints или prompt-версии.

### 2.2. Что не является карточкой

- `factcheck_temporal` — hidden-подмодуль Фактчека, настройки на его странице; карточки нет.
- `mod_character` — submodule с `parent_id=persona`: карточка стоит в группе «Память», но её
  родительская поверхность — `#/permsoc` («PERMsoc»/личности), поэтому чип подмодуля —
  `Часть «PERMsoc»`, **не** «Часть „Характера“» (карточка и есть «Характер»).
- «Диалог» = `mod_direct` «Ответы в чате»; «Анализ» отдельной карточки не имеет (его поверхности —
  табы/секции существующих карточек); «Мем-ветка» = вкладка `memes` карточки «Инициатива».
  Новые top-level карточки не создаются (owner §5.5).
- auth/DB/scheduler core/secret storage/Telegram limits/privacy/network — не модули и не тумблеры.

### 2.3. Расхождения, которые M4A обязан устранить

1. В Python-реестре **11** `ModuleSpec`, в UI **21** карточка; 11 static-карточек не имеют
   серверного описания. M4A добавляет их в `MODULE_REGISTRY` (D2), иначе AC-01/S2-49 невыполнимы.
2. `sleep`, `nostalgia`, `vision` объявлены `global`, но runtime читает chat override
   (`dream_worker`, `nostalgia_worker`, `mca_vision`); `summary`, `budgets`, `images` — per_chat в JS,
   но без `ModuleSpec`. M3 фиксирует фактический scope из таблицы §2.1.
3. `registry_for_frontend.gate` не содержит `state.source`, `emergency_block`, `authorized`,
   `observed`, `conflict`; при этом `source` в `gate` — это **причина гейта**
   (`emergency_env|product_toggle|both`), а не источник значения. UI смешивает их и получает
   противоречия вида «Выключен» + «Работает» (воспроизведено на `#/modules/experience`).
4. `mod_time` — не модуль с мастером, а policy-страница; `master_param` пустой, `scope_capability`
   `limits.chat_timezone` (hidden в общем каталоге, отдельный API `/api/config/time`).
5. `mod_embeddings` — общий сервис без master; chat-использование — `flags.memory_search_enabled`
   (per_chat, consumer `summary_memory`), а не второй тумблер индексации. «Индексация работает» и
   «поиск разрешён в чате» — разные поля.

### 2.4. Per-card матрица: вкладки, источники, «Расширенные», первый viewport (D1)

**База.** Вкладки и подписи — фактические `WORKSPACE_TABS` + `WORKSPACE_TAB_LABELS` +
`WORKSPACE_TAB_LABELS_OVERRIDES` deployed `bca18c1e`; registry-only карточки получают
`['overview','settings']` (ветка `m.tabs = WORKSPACE_TABS[m.id] || [...]`). Пустые вкладки не
рисуются (`_workspaceTabApplicable` + `workspaceTabHasContent`, MAC-S5-EMPTY-01).

**Правила колонок.**

- `history` — новое каноническое id вкладки «История» (подпись `История`), рендерится **только**
  при 200 с реальными данными от именованного источника; 403/503/`available:false`/пусто →
  вкладки нет, роль выполняет компактный блок «Последние события» в «Обзоре» (MAC-S5-TAB-06).
  Если у карточки уже есть собственный событийный таб (`inspector`, `publications`/`diagnostics`,
  инфраструктурные `События`), второй не создаётся — это был бы дубль.
- `Расширенные` (MAC-S5-TAB-07) — **не отдельная вкладка**: в `bca18c1e` это раскрываемая зона
  `advancedItems(grp)` внутри той вкладки, куда маршрутизирована группа (`workspaceGroupTab`).
  Наличие = ≥1 параметр с `progressive_level="advanced"` в settings-группах карточки (проверено по
  deployed `param_catalog.REGISTRY`, 645 params). Промпт-группы не считаются: у них свой редактор.
  Отдельная вкладка не вводится, иначе технические параметры получили бы второй дом («склад»,
  запрещённый самим требованием).
- `default` — таб для `#/modules/<slug>` без tab; «Обзор» наполнен всегда (состояние + checked-at +
  адресные ссылки), поэтому fallback «первый содержательный таб» не срабатывает ни на одной карточке.

  sidebar 200, контент = viewport − sidebar − 48. `✓` — карточка целиком выше сгиба, `◐` —
  начинается выше сгиба, `—` — нет; допуск ±1 карточка при 2-строчных описаниях.
  Высоты: 1440×900, 1280×800, 768×1024, 390×844, 320×568.

### 2.5. 11 новых `ModuleSpec`: обязательные поля (D11)

`validate_spec` требует непустые `status_source`, `help_anchor`, `rationale` (и `master_param` либо
явный «no master» в rationale). Для 11 static-карточек поля **не изобретаются заново**:

- `help_anchor` = канонический заголовок карточки (§7.1). Если записи в словаре справки нет, она
  добавляется с этим заголовком; структура словаря не меняется.
- `status_source` — только существующая поверхность. Если собственного блока статуса нет, поле
  честно фиксирует «нет отдельного блока статуса» и что показывает «Обзор» (без выдуманного
  endpoint).
- `rationale` — классификация + master (или «no master») + почему scope такой.

### 3.1. Маршруты

| Route | Назначение | Владелец среза |
|---|---|---|
| `#/modules` | каталог 21 карточки | M4A |
| `#/modules/<slug>` | workspace модуля; без tab → `overview`, если он наполнен, иначе первый содержательный таб | M4A |
| `#/modules/<slug>/<tab>` | прямой deep link на реальную вкладку | M4A |
| `#/modules/<slug>/<tab>/<promptKey>` | короткая форма промпта (существующая) | M4A (не менять) |
| `#/ai/prompts/<slug>[/<stage>]` | библиотека промптов, та же комната/ключ | M4A (не менять) |
| `#/modules/time` | policy-страница «Время» без табов | M4A |
| `#/modules/embeddings[/<tab>]` | инфраструктурная «Векторная память» | M4A |
| `#/memory/rag`, `#/permsoc` | родительские поверхности submodule-групп; показывают ссылку на owner-страницу | M4A (только ссылки) |
| `#/status` | «Статус», порядок блоков — `m3-design-freeze.md` §4 | M4B |
| `#/access/roles` | «Роли и права» страницей — `m3-design-freeze.md` §5 | M4C |

Правила:

- Последний таб запоминается **только** для пары `scope + module`:
  `adminbot.moduleTab.<scopeType>:<scopeId>:<moduleId>`; смена чата не переносит таб другого чата.
- При смене scope страница целиком перезагружает данные и права; поздний ответ старого scope
  игнорируется по epoch (существующий `scopeEpoch`/`_scopeGuard`).
- Deep link на неприменимый/пустой таб ведёт на первый содержательный таб, не на пустую страницу.
- Submodule-карточка открывает **свою** сфокусированную страницу (уже существует), а родительская
  поверхность показывает объявленные ею группы **ссылкой**, не второй формой (§6.3).
- Новый нижний навбар/второй механизм навигации не создаётся (navigation contract 31.10.2026).

### 3.2. Группы каталога и `catalog_order` (нормативный порядок)

Порядок **групп и карточек** задаётся явным серверным `catalog_order` (целые 1…21, уникальные);
порядок регистрации в `MODULE_REGISTRY`/`MODULES` на рендер не влияет и нормативным не является.
DOM обязан совпадать с `catalog_order` (проверяется в §11.2).

1. **Общение** (1–5): Сводки чатов, Ответы в чате, Фактчек, Поиск, Веб-страницы.
2. **Память** (6–10): Истории и эпизоды, Опыт и уроки, Векторная память, Характер, Случайность.
3. **Автономность** (11–13): Инициатива, Сон, Ностальгия.
4. **Медиа** (14–18): Транскрипт голосовых и видео, Выжимка видео, Скачивание медиа, Генерация
   изображений, Распознавание изображений.
5. **Системные** (19–21): Диагностика, Бюджеты, Время.

```text
catalog_order: 1 mod_summary · 2 mod_direct · 3 mod_factcheck · 4 mod_search · 5 mod_web
               6 mod_stories · 7 mod_experience · 8 mod_embeddings · 9 mod_character · 10 mod_random
               11 mod_initiative · 12 mod_sleep · 13 mod_nostalgia
               14 mod_transcribe · 15 mod_video_summary · 16 mod_media_download · 17 mod_images · 18 mod_vision
               19 mod_checkup · 20 mod_budgets · 21 mod_time
```

21 = 5+5+3+5+3. Подмодули не выносятся в отдельную top-level группу и не дублируются: они стоят
в группе родителя с чипом по фактическому `parent_id`:
`Часть «Памяти»` — Истории и эпизоды, Опыт и уроки, Случайность (`parent_id=memory`);
`Часть «PERMsoc»` — Характер (`parent_id=persona`, поверхность `#/permsoc`);
Векторная память — без чипа «часть», у неё `Инфраструктура`/`Общий сервис` (§4.4).

### 3.3. Иерархия страницы модуля (сверху вниз)

1. Topbar: навигация и **одно название раздела** — `Модули`. На каталожном route topbar —
   единственный носитель заголовка: H1 «Модули» в контенте **не дублируется**; на module route
   topbar показывает `Модули` как родителя, а имя модуля живёт только в H1/крошке. Далее —
   единый scope-selector, аватар/роль, fullscreen.
2. Хлебные крошки `Модули / <Название>` 12 px — только на module route.
3. H1 `<Название>` 20–24 px; на одной линии — scope-чип (см. §4.2).
4. Одна человеческая фраза ≤120 символов; не повторяет H1.
5. Строка управления: GLOBAL-тумблер, CHAT tri-state (если законен), чипы `Настройка`,
   `Исполняется`, `Готовность`, `Измерение`, `Источник`.
6. Локальные табы 38–44 px, `role=tablist`, `aria-current`, стрелки/Tab.
7. Контент выбранного таба; начинается через 16–24 px после табов; без второй шапки.

Никакого `Обзор модуля`-заголовка, повторяющего описание, и никакой кнопки
`Открыть настройки модуля` внутри «Обзора».

### 3.7. Visual Preservation Map (обязательная карта сохранения)

## 5. Модель состояния и точные подписи

### 5.1. Пять осей + источник значения (одна семантика, разные вопросы)

Пять осей — `desired`, `effective_runtime`, `ready`, `observed`, `authorization`. `source` —
**не шестая ось**, а атрибут выбора (`desired`): откуда взялось желаемое значение. В таблице он
идёт отдельной строкой только потому, что отображается отдельной подписью.

| Ось / атрибут | Вопрос | Поле API | Подписи |
|---|---|---|---|
| `desired` | что выбрал пользователь | `gate.state.desired` / `items[].value` | `Включено по настройке`, `Выключено по настройке`, `Наследует: включено`, `Наследует: выключено` |
| `source` | атрибут `desired`: откуда выбор | `state.source` (`chat/global/default`) + `global_source` | `Источник: настройка чата`, `общая настройка`, `заводское значение` |
| `effective_runtime` | что реально исполняется | `state.effective_runtime` / `gate.effective` | `Исполняется`, `Не исполняется`, `Заблокировано` |
| `ready` | есть ли технические предпосылки | `state.ready` (`true/false/null`) | `Готово`, `Не готово: <reason>`, `Готовность не проверяется` |
| `observed` | есть ли подтверждение работы | `state.observed`/`observed_at`/`last_activity_at` | `Последняя активность: <time>`, `Измерение не подтверждено`, `Нет подтверждённой активности` |
| `authorization` | можно ли читать/менять | `permissions.can_read/can_edit` | `Нет права смотреть`, `Только просмотр`, `Нет права изменить` |

`unknown`/`null` **никогда** не показывается как `Норма` или `Выключено`. «Нет права» никогда не
стилизуется как OFF.

### 5.2. Правила приоритета

1. `authorization.can_read=false` → нет данных; показать отказ, не пустую таблицу.
2. `desired=false` → `Выключено` независимо от `ready`; не писать «не работает».
3. `desired=true`, `emergency_block=true` → `Включено, но заблокировано аварийным переключателем
   сервера` + ключ оси в «Технических деталях». Это не OFF пользователя.
4. `desired=true`, `ready=false` → `Включено · сейчас не работает` + `reason_code` (человеческая
   причина, не код): `нет провайдера`, `нужно согласие`, `нет права`, `конфликт гейтов`,
   `не настроена группа`.
5. `desired=true`, `ready=true`, `observed=null` → `Включено · работа ещё не подтверждена`
   (нейтрально/жёлтый, не зелёный).
6. `desired=true`, `effective_runtime=true`, `observed=true`/свежий `observed_at` → `Работает`.
7. `pending_restart=true` → `Изменение применится после перезапуска` (не «сохранено»).
8. `conflict` → `Конфликт настроек: <name>`; не overwrite.

### 5.3. GLOBAL vs CHAT

- GLOBAL: один переключатель `Весь бот`; его OFF означает «новые и наследующие чаты выключены»,
  а не «все чаты принудительно выключены». Подпись: `Общий режим: выключен (новые чаты наследуют)`.
- CHAT: `Наследовать | Включить | Выключить`; выбранное состояние берётся из `chat_state`
  (`inherit/on/off`), не угадывается по значению.
- `GLOBAL OFF + CHAT ON` — законная пара: chat показывает `Включено отдельно для этого чата` и
  `Исполняется`; global не перезаписывается.
- `GLOBAL ON + CHAT OFF` — `Выключено для этого чата`; другие чаты не затронуты.
- Для модулей с `scope=global` в chat scope: `Управляется глобально` + (только admin) кнопка
  `Открыть глобально`; тумблер disabled/отсутствует, override не создаётся.

### 5.4. Запись и 409

| Действие | API | Тело |
|---|---|---|
| GLOBAL switch | `POST /api/config` | `{items:[{key, value:bool, updated_at}]}` |
| CHAT on/off | `POST /api/config`, `X-Chat-Id` | `{items:[{key, value:bool, updated_at}], updated_at}` |
| CHAT inherit | `POST /api/config`, `X-Chat-Id` | `{items:[{key, mode:"inherit"}], updated_at}` (существующий `mode`) |
| Gate-backed CHAT on/off/inherit | `PUT /api/chat/{id}/gates` | `{feature, enabled: true, false или "inherit"}` |
| Timezone | `POST/DELETE /api/config/time` | `{timezone, chat_id}` / query |

Состояния кнопки: `Сохраняем…` → `Настройка сохранена` только после подтверждённого ответа;
ошибка → `Не удалось сохранить: <причина>`; 409 → баннер §4.6, без ложного «Сохранено».
`operation_id` обязателен для повторного POST; двойной клик не создаёт второй записи.
Перед публикацией/выдачей защищённого результата ACL и scope перепроверяются (существующий
`fresh`-путь), после отзыва прав загруженные защищённые данные скрываются.

   (`requested`, `effective`, `source` = `emergency_env|product_toggle|both`, `env_param`,

   (источник значения) теряется, из-за чего UI получает «Выключен» + «Работает».
3. **Gate-backed карточки (`mod_sleep`/`dream`, `mod_nostalgia`)** — состояние **только** через

   `authorized`, `observed`, `reason_code`, `observed_at`, `last_activity_at`, `version`).
   `global_value`/`global_source` берутся из `FLAG_KEYS` (`dream`: `flags.dream_enabled` →
   `memory.dream_enabled`; `nostalgia`: `flags.nostalgia_enabled` → `memory.nostalgia_enabled`).
   Параметр `memory.dream_enabled`/`memory.nostalgia_enabled` показывается как **значение по
   умолчанию / использование** (read-only в строке состояния или в «Технических деталях»), а не как
   второй чатовый контрол: единственная точка записи CHAT — `PUT /api/chat/{id}/gates`

   второй tri-state/чекбокс — иначе два write-point пишут одну ось и расходятся с воркером.
4. **`GET /api/config`** — для per_chat-карточек передавать `state` (сейчас — только для тех, кто

5. **`POST /api/config`** — UI использует существующий `mode:"inherit"`; новых полей не нужно.
6. **`GET /api/memory/embeddings`** — не менять; M4A читает существующий ответ и показывает
   403/503 разными состояниями.
7. **Никаких** новых `/api/modules`, второго registry, второй ACL, второго lesson store,
   второго prompt store и второго чатового контрола для gate-параметров.

- 21 уникальный видимый `id` + hidden `factcheck_temporal`; `registry_for_frontend()` отдаёт ровно

- `catalog_group` ∈ {`communication`,`memory`,`autonomy`,`media`,`system`}; распределение

- `runtime_gate` совпадает с §2.1; **8** перечисленных спецификаций == `per_chat`, и в

- `scope_capability` пуст или является pg-ключом каталога с `per_chat=True` и подтверждённым

### 6.3. Один write-point на группу

- `experience` владеет `memory_experience`; `stories` — `flags_stories`; `character` —
  `flags_character`; `random` — `memory_random`.
- На `#/memory/rag` и `#/permsoc` эти группы показываются **одной строкой-ссылкой**
  `Настраивается в «<Модуль>» →`, без полей и без второго сохранения.
- `flags.memory_search_enabled` — единственное key-level исключение: владелец — «Векторная
  память»; на странице «Память» ключ read-only со ссылкой.
- `models_embeddings` — владелец «Векторная память»; `keys.embedding_*` — на её вкладке «Модели»,
  общие `keys.intel_*`/`keys.llm_*` — только в «ИИ».
- Одинаковый ключ на двух поверхностях допустим только через один и тот же API и 409; второго
  store нет. Для submodule-групп дублирование форм запрещено.
- `memory.dream_enabled`/`memory.nostalgia_enabled` — тот же принцип: единственная чатовая точка
  записи — `PUT /api/chat/{id}/gates`, а сам параметр в «Основных настройках» только читается
  (§6.2 п.3).
- Вкладки `history`/`События`/`inspector`/`Публикации` — read-only (фильтр, детали, `run_id`);
  управляющие действия остаются на поверхности владельца (Истории → `#/memory/rag`, §2.4).

### 6.4. Безопасность и права

- `can_read=false` → backend не отдаёт данные; UI не рисует форму и не подменяет 403 пустотой.
- `can_edit=false`, `can_read=true` → значения видны, контроль disabled, причина роли.
- Секреты — только `{configured,last4}`/маска; raw ключ не в DOM, API, логах, ошибках.
- 401/403/404/503 — разные экраны/тексты (§4.6), не один toast.
- Local admin не получает глобальный API через `X-Chat-Id`/route; чужие чаты/DM — 403.
- M4A не создаёт ACL-политику; использует server `can_*` и существующие `can_view_param/
  can_edit_param`. SELF-DIAG ACL подключается позже одной политикой.

`mod_transcribe`, `mod_video_summary`, `mod_media_download`, `mod_checkup`, `mod_stories`,
`mod_character`, `mod_random`.

**Решение (Оркестратор):** `M2.1` — **отдельный backend-срез и обязательный предшественник M4A**
(не расширение write scope M4A). В нём: эти 12 потребителей, тесты `GLOBAL OFF + CHAT ON` и
`GLOBAL ON + CHAT OFF` на каждом, без изменения stored values и без нового storage. M4A не
начинает рендер CHAT-контролов этих 12 до закрытия M2.1; interim disabled-контрол не нужен, так
как M2.1 идёт первым. Иначе кнопка без runtime-эффекта — блокирующий дефект (owner §9.3).

### 12.3. `nostalgia` master precedence

`feature_gates.FLAG_KEYS["nostalgia"] = ("flags.nostalgia_enabled", "memory.nostalgia_enabled")`;
`memory.nostalgia_enabled` — master карточки, но gate fallback может взять первый ключ. Если
`flags.nostalgia_enabled` явно ON, глобальный тумблер карточки не изменит runtime. **Коррекция:**
`MASTER_FALLBACK_KEYS["nostalgia"] = "memory.nostalgia_enabled"` (как уже сделано для `dream`) или
эквивалентное правило; тест «глобальный тумблер → gate effective» до M4A. Это одна строка +
тест; файл `services/feature_gates.py` вне текущего M4A write scope — включить в M2.1.

### 12.5. Write scope: M2.1 (предшественник) и M4A

**12.5.1. M2.1 — отдельный backend-срез, обязательный предшественник M4A** (решение Оркестратора,
§12.2). Стартует и закрывается до первой строки UI M4A.

- `handlers/direct_chat.py`, `handlers/factcheck.py`, `handlers/search.py`, `handlers/web.py`,
  `handlers/voice_transcription.py`, `handlers/youtube.py`, `handlers/video_download.py`,
  `handlers/checkup.py`, `bot.py` — чтение per-chat значения через
  `chat_params.resolve_param_capability(chat_id, …)` вместо глобального `hot.get`;
- `services/direct_chat_service.py`, `services/factcheck_service.py`, `services/media_download.py`,
  `services/tool_schemas.py`, `services/tool_router.py`;
- `services/mca_gates.py` — `initiative`/`stories`/`character`/`random` без master-AND;
  `services/initiative_observer.py` — снятие master-AND, emergency только env `MCA_INTENTS_ENABLED`;
- `services/feature_gates.py` — precedence `nostalgia` (§12.3) и `gate_state` как единственный
  резолвер для `dream`/`nostalgia`;
- `tests/test_mod_acl_ux_m21_*.py` — `GLOBAL OFF + CHAT ON` / `GLOBAL ON + CHAT OFF` на каждом из
  12 id; `plans/features/mod-acl-ux-01/evidence/m2-1/**`.

M2.1 **не** пишет в `module_registry.py`, `web/app.js`, `web/index.html`, `web/static/app.css`,
`web/api/routes.py`; stored values не меняются, нового storage нет.

**12.5.2. M4A** — начинается только после закрытия M2.1. Текущий `slice-graph.json` M4A:

  `character`, `random`, `factcheck`, `vision`, `nostalgia`, `sleep` → `per_chat`) — декларация

  `tests/fixtures/module_registry_visible.json` — контрактные тесты (включая `catalog_order`,

M4A **не** рисует CHAT-контролы 12 модулей до закрытия M2.1 и **не** пишет в `memory_agi.py`,

### 12.6. Открытые вопросы / проверки (не Human Gate)

1. **Live `IMAGE_MODULE_CARD_ENABLED`** — подтвердить `/api/me.ui_flags` и 21/21 в живом TMA;

2. **Production `flags.nostalgia_enabled` / `memory.nostalgia_enabled`** — какой слой реально
   побеждает; проверяется M2.1-тестом, не догадкой.

5. **M2.1 vs расширение M4A** — **решено:** M2.1 отдельным срезом, обязательный предшественник
   M4A (§12.2, §12.5.1); технический контракт не меняется.

Ни один пункт не является реальным продуктовым выбором владельца: owner уже выбрал
GLOBAL+CHAT, shared-инфраструктуру без фиктивного тумблера и сохранение промптов. Human Gate не
требуется.
