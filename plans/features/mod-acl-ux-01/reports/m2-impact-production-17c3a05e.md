## Доказательства read-only

1. **Поверхность SQL.** В `scripts/mod_acl_effective_state_report.py` нет
   `UPDATE`/`INSERT`/`DELETE`/DDL; путь `--database` вызывает только
   `ConfigCache._load_all()` (3 × SELECT), `ChatLoreStore.list_profiles()`
   (SELECT) и `chat_params.get_all_chat_params()` (`SELECT_PROFILE_SQL`).
   `PgDatabase.init()` (DDL/сид) сознательно не вызывается.
2. **Снимки до/после идентичны:**

   | Метрика | До | После |
   |---|---|---|
   | `bot_settings` строк | 547 | 547 |
   | `chat_profiles` строк | 3 | 3 |
   | профилей с непустыми `chat_params` | 3 | 3 |
   | таблиц в `public` | 30 | 30 |
   | `pg_stat` bot_settings (ins/upd/del) | 547/334/0 | 547/334/0 |
   | `pg_stat` chat_profiles (ins/upd/del) | 3/57/0 | 3/57/0 |

3. **Схема.** `PRAGMA user_version` файла `local_database.db` = **46** до и после
   (открытие `mode=ro&immutable=1`, только чтение). В PostgreSQL таблицы
   `schema_migrations`/иных version-таблиц нет, поэтому маркер v46 проверяется по
   SQLite-файлу и по неизменному числу таблиц (30).

## Остаточные риски

- Отчёт описывает только существующие строки: чаты, добавленные позже, в нём не
  учтены и потребуют повторного прогона.
- Личный чат владельца вне выборки утверждённого скрипта (фильтр `chat_id < 0`),
  покрыт отдельным прогоном того же кода — это дополнительная проверка, а не
  изменение методики.
- Нулевое изменение зафиксировано при текущих глобальных значениях. Смена
  глобального флага после выката теперь будет наследоваться чатами без явного
  выбора — это и есть целевое поведение M2.
- В PostgreSQL нет собственного маркера `user_version`; контроль версии схемы на
  проде опирается на SQLite-маркер и инвентарь таблиц.
