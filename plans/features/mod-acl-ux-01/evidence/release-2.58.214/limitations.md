# Release 2.58.214 — ограничения и честные пробелы (W2b B3 + F1)

Дата: 2026-11-17. Ветка `release/mod-acl-w2b3-2.58.214`, база/откат
`34c25d09` (2.58.213), content tip `885b43e1` (F1 fix), версия **2.58.214**.
Статус: **REVIEW**, не деплой и не VERIFIED.

## 1. Cross-chat содержимое журнала (design-ограничение, не дефект сборки)

- `loadModuleRuns` **не передаёт `chat_id`**: используется существующий
  global-admin `GET /api/oversight/runs?pipeline_type=…&limit=20`, который
  серверно не фильтруется по чату.
- Поэтому вкладка «История» у «Сводок» и «Источника случайности» показывает
  **до 20 последних прогонов ВСЕХ чатов**, а не только выбранной области.
- Каждая строка подписана своим `чат <id>` (реальный `chat_id` прогона), так
  что принадлежность видна и не подменяется.
- Сознательное решение: источник — существующий API, RBAC и контракт не
  расширялись; выборка по чату/области — **W2c/W3**, не этот релиз.
- Клиентская изоляция состояния полная: кэш помечен `scope+epoch`, поздний
  ответ чужой области не применяется, строки разных источников не
  смешиваются (проверено node-юнитом и e2e A→B→A).

## 2. `summary.window` — НЕ источник истории (F1, исправлено)

- Компонентные события окна (`services/summary_memory.py` →
  `_emit_mca("SUMMARY_WINDOW_BUILD")`) пишутся без `pipeline_run_id`;
  `/api/oversight/runs` группирует только `pipeline_run_id IS NOT NULL` и
  фильтрует точный `pipeline_type`. Значит `pipeline_type=summary.window`
  не может вернуть ни одной строки.
- Реальные прогоны Summary: `services/pipeline_events.py` →
  `mca_trace.span_fields(run_id, pipeline_type="summary")`, строки с
  `pipeline_run_id` и `pipeline_type='summary'`.
- Исправление: presentation-метка источника `oversight:summary` (значение
  существующего поля DTO) → API-параметр `pipeline_type=summary`;
  `oversight:summary.window` в карте отсутствует и вкладки не создаёт
  (fail-closed). `random.uses` не менялся.
- Никаких заявлений о «данных `summary.window` в проде» нет и не было.

## 3. Синтетические e2e-ряды

- Ряды Summary (`srun-*`) и Random (`rrun-*`) в
  `tools/ui_mod_acl_m4_catalog_e2e.py` — **синтетический стаб**, форма —
  контракт `GET /api/oversight/runs`; production-строки не запрашивались.
- `GET /api/oversight/runs` серверно не фильтруется по чату, поэтому
  cross-scope ответы областей различаются стабом (`B3_ROWS`): проверяется
  изоляция клиентского состояния/кэша, а не серверная фильтрация.
- Клиент дополнительно проверяется на факт запроса: `B3_TYPES_SEEN` должен
  содержать только `summary` и `random.uses` (`summary.window` — запрещён).

## 4. Копирайт для не-владельца на Summary/Random (LOW, backlog)

- Условие «Обзор»-блока обобщено с `id === 'mod_factcheck'` на
  `historyNeedsOwner(module)`, поэтому не-владелец на «Сводках»/«Случайности»
  видит существующую подсказку «Журнал проверок с источниками доступен
  владельцу бота…» — формулировка фактчека, не журналов сводок/случайности.
- Поведение честное (никакого запроса, никаких выдуманных строк), неточна
  только фраза. Косметика — LOW/backlog, чинится в W2c-полировке копирайта.

## 5. `available:false` печатается как «503» (LOW, backlog)

- Источник различает причины: `503` — ручка выключена, `available:false/
  enabled:false` — гейты наблюдаемости OFF (`_runs_disabled`). Оба дают `off`.
- Текст для `off` один: «История недоступна: журнал выключен (503)». Для
  `available:false` это неточно (не HTTP 503), но и не «0 событий».
- Расширение словаря причин — LOW/backlog (W2c-полировка состояний).

## 6. Деталь прогона запрашивается дважды (наблюдение, не B3)

- При переходе по `#/oversight?view=runs&run_id=…` деталь запрашивается
  2 раза: `oversightApplyDeepLink` срабатывает путём `applyRoute` и повторно
  существующим путём. Поведение было в продукте до B3, продукт не менялся;
  e2e фиксирует `detail_gets >= 1`.
