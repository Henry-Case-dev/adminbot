# M5A / MOD-ACL-UX-01 — деплой 2.58.170 и миграция v45

Запись о фактическом выкате релиза `2.58.170`, на котором срез **M5A**
(`EXP-FIX-01…07, 09, 10`) и живая строка `MAC-EXP-06` попали на прод.
Артефакт фиксирует: что именно развёрнуто, чем развёрнутый SHA отличается от
ревьюированного кандидата, что произошло с БД при миграции `44 → 45` и какие
проверки живучести пройдены.

## 2. Важная оговорка: SHA деплоя ≠ SHA ревью

Ревьюированный кандидат среза M5A — `4e07817e9a4836a6e68837bbb815aa3ffdfe3dc8`.
Между ним и развёрнутым `42f068df` стоят ровно два коммита:

| Коммит | Что делает | Продуктовый код |
|---|---|---|
| `33707364` | `test(pins)`: голова схемы `45` для всех `user_version`-пинов после v45 | только тесты |
| `42f068df` | `chore(release)`: `APP_VERSION` `2.58.169 → 2.58.170`, README, мета-док реестра параметров | только `config/settings.py` (версия) |

Проверка идентичности продуктового кода среза:

- `git diff --name-only 4e07817e 42f068df -- services handlers web` → **пусто**;
- blob-хеши файлов M5A совпадают на обоих коммитах
  (`services/mca_experience_jobs.py` `74266ea5…`, `services/mca_experience.py`
  `f3a5fdcc…`, `services/memory_maintenance.py` `89a0bbc5…`,
  `web/api/memory_overview.py` `71be55ac…`);
- единственное продуктовое изменение во всём диапазоне — строка `APP_VERSION`
  в `config/settings.py`.

Вывод: живое доказательство `MAC-EXP-06`, снятое на `42f068df`, относится
к тому же коду M5A, который проверял Reviewer на `4e07817e`. В карте
`candidate_commit` остаётся ревьюированным `4e07817e`, а `deployed_commit`
указывает на фактически выкаченный `42f068df` — два разных SHA осознанно
разведены по разным полям, а не смешаны в одном.

Отдельно: леджер `m5a-review-ledger-4e07817e.md` — **снимок состояния на момент
ревью** с зафиксированным sha256 (`1d5b1f2d…`), его §2 («Развёрнуто: нет») и §6.4
(«Деплой … deployed_commit пуст») этим релизом **перекрыты** и остаются
исторической записью; переписывать артефакт с зафиксированным дайджестом, чтобы
«освежить» статус, не следует — актуальное состояние деплоя фиксирует этот файл
и поле `deployed_commit` карты.

## 3. Миграция схемы `44 → 45`

| Показатель | До | После |
|---|---|---|
| `PRAGMA user_version` | 44 | **45** |
| `schema_migrations` (число записей) | 33 | **34** |
| `PRAGMA quick_check` | — | **ok** |
| `smart_messages` (строк) | 2 074 529 | **2 074 529** (без изменений) |
| `nodes` | 33 501 | **33 501** |
| `edges` | 65 188 | **65 188** |
| `graph_facts` | 23 354 | **23 354** |
| Заполненных `transcript_*` строк | — | **0 из 843** голосовых строк (backfill не выполнялся) |

Что делает шаг (код `services/database.py` 1818–1835, 3625–3653 на `42f068df`):

- `_SCHEMA_VERSION_VOICE_TRANSCRIPT = 45`;
- четыре аддитивные колонки `smart_messages`:
  `transcript_status TEXT NOT NULL DEFAULT ''`, `transcript_revision INTEGER NOT NULL DEFAULT 0`,
  `transcript_updated_at INTEGER`, `transcript_reason TEXT NOT NULL DEFAULT ''`;
- `ALTER TABLE … ADD COLUMN` под guard `PRAGMA table_info` (повтор — no-op),
  существующие строки не `UPDATE`/`DELETE`-ятся, backfill отсутствует:
  пустой статус означает «STT никогда не сохранял результат», а не «готово»;
- PG — no-op (контур сообщений SQLite-only), второго медиа-реестра не появляется.

Наблюдаемое «0 из 843» согласуется с заявленным отсутствием backfill: колонки
добавлены, но ни одна историческая голосовая строка не получила `ready`-статус
задним числом. Это ожидаемое, а не пропущенное поведение.

## 5. Источник журнала «чекапа» (SELF-DIAG-01 D1)

Живая строка чтения журнала собственного процесса:

```
Checkup log source: systemd invocation=aa277a539c6b482da432dd2ef7b20e68 unit=admin_bot.service pid=3233804
```

Статическая сверка развёрнутого кода (`services/system_logs_fetcher.py` на `42f068df`):

- импорты модуля: `asyncio`, `logging`, `os`, `re`, `contextlib`, `dataclasses`,
  `typing`, `config.settings`, `services.log_ring` — **сетевого клиента нет**;
- сам модуль в докстроке (строка 25) фиксирует: «Сетевых клиентов у чекапа
  больше нет: модуль не импортирует `httpx`…»;
- вхождения `CHECKUP_BETTERSTACK*` в коде на `42f068df` отсутствуют — они
  остались только в исторических `plans/**` (архив/ADR);
- чтение журнала идёт фиксированным `argv` через `create_subprocess_exec`
  (без shell) и только для **своего** экземпляра: матч `_SYSTEMD_INVOCATION_ID`,
  иначе `--unit` из собственного cgroup.

Строки Better Stack в общем журнале относятся к глобальному ingest-контуру и
к «чекапу» больше не относятся.

## 6. Эксплуатационные оговорки на будущее

1. **На VPS нет CLI `sqlite3`.** Любые будущие снапшоты/проверки БД выполнять
   venv-интерпретатором проекта (`.venv/bin/python` + `sqlite3` модуль), а не
   `sqlite3` из оболочки. Иначе проверка молча упадёт «command not found».
2. **Четыре мёртвых ключа `CHECKUP_BETTERSTACK_SQL_*` остались в `.env`**
   (один из них — секрет). Код их больше не читает. Удаление — отдельная
   адресная задача после доказательства, что потребителей нет; в этот релиз
   не входит. Зафиксировано в `plans/backlog.md`.

## 7. Границы: что этим артефактом не доказано

1. **M5C — ограниченный production-proof** (60–90 мин: `deployed_sha`,
   effective K1–K4, last tick, `review_cadence`, последние `experience.review`
   из `task_jobs` с counters и курсорами, сравнение watermark с
   `MAX(smart_messages.id)`, backlog/возраст самого старого pending, counts по
   таблицам опыта) — **не выполнен** и этим артефактом не заменяется.
2. **Вопрос владельцу (`MAC-M5-01`)** остаётся открытым и задаётся после M5C.
3. **Откат не репетировался**: путь отката (cold revert + `predeploy-258170.db`)
   описан и осуществим, но фактического прогона отката не было.
4. **VOICE-контур** (реальное голосовое владельца → `transcript_status=ready` →
   блок Writer) — отдельная внешняя зависимость, см. карту `vmq-onto-01`.
