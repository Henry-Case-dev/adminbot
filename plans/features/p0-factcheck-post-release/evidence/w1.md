## 2. Реализованные правки

### §1/§2.4 — анализ продолжается без внешнего evidence
`services/factcheck_service.py`:

- ветка «не evidence → серверный insufficient» удалена; СУЩЕСТВУЮЩИЙ
  analyst-вызов (`TEMPORAL_ANALYST_SYSTEM` → `_temporal_verdict_json`,
  step `temporal_verdict`, с существующим fallback `_TEMPORAL_FALLBACK_SYSTEM`)
  выполняется всегда (второго аналитика нет, §4.4);
- при пустом evidence в payload добавляется серверная секция
  `<analysis_context>` (`_analysis_context_for_empty_evidence`): статус
  поиска по таксономии §5, разрешение логической/математической/технической
  проверки и внутренней согласованности, запрет выдуманных
  источников/характеристик, рамка происхождения вывода
  (evidence vs reasoning vs assumption через `uncertainty["basis"]`,
  существующая схема — новые enum не вводились);
- `allowed_refs` при пустом evidence теперь `set()` (было `None` =
  без фильтрации): выдуманные `ev-N` не становятся cited evidence
  (top-level и parts);
- серверный guard `_downgrade_unbacked_positive`: положительный вердикт
  (supported/refuted/mixed, top и parts) без внешнего evidence и без
  пометки основания самостоятельной проверки (`uncertainty.basis*`) →
  честный `insufficient_evidence` + оговорка `unbacked_positive` (граница
  §2.4/§2.6: «вспомнил цифру → подтверждено» не проходит; расчёт по
  заданным числам с basis не понижается — F7/F12);
- содержательный вывод без поиска не получает технический заголовок
  «проверка не завершена» (reason-код retrieval снимается при
  `_verdict_is_substantive`, §7.3); состояние поиска остаётся оговоркой в
  `uncertainty.retrieval_state`;
- при двойном сбое LLM техническая причина retrieval (budget/unavailable/
  processing) не затирается fallback-кодом — fallback-режим виден через
  `fallback_used`/trace (§5.3);
- правило (1) `TEMPORAL_ANALYST_SYSTEM` (`services/temporal_factcheck.py`)
  переформулировано минимально: подтверждение/опровержение ВНЕШНЕГО факта
  — только по evidence, но логика/арифметика/принципы/согласованность
  проверяются и без поиска с пометкой основания (снята системная команда
  «нет результатов → insufficient», FC-02D). Словарная директива §8
  (FC-08) — другая лейка, её дословный текст здесь не добавлялся.

### §5 — таксономия причин поиска
- `services/search_aggregator.py`: `AllSearchEnginesFailedException` несёт
  машинную `reason` (`provider_error|timeout|empty_results|irrelevant_results|
  budget`); `level_failure_reason()` классифицирует неудачу уровня
  (httpx.TimeoutException → timeout; irrelevant/empty по типу ошибки);
  итог каскада — `_most_informative_reason` (irrelevant > empty > timeout >
  provider_error; ответившие уровни с пустой/нерелевантной выдачей не
  затираются недоступным ddg-уровнем). Тексты сообщений исключений не
  менялись (совместимость).
- `services/factcheck_planner.py`: `RetrievalOutcome` + `empty_results`,
  `irrelevant_results`; пустая выдача без исключения — `empty_results` (не
  provider_failures); причины логируются (`cause=` в query-failed логе).
- `services/factcheck_service.py::classify_retrieval`: новый класс
  `RETRIEVAL_NO_RESULTS` («no_usable_results») — провайдеры ответили, но
  пригодных материалов нет (пусто и/или нерелевантно, в т.ч. смесь со
  сбоями провайдеров); `search_failed` — только чистая недоступность.
  Словари `_RETRIEVAL_REASON/_RETRIEVAL_CAVEAT/_RETRIEVAL_SITUATION/
  _RETRIEVAL_SEARCH_NOTE` дополнены; тексты situation переформулированы
  как состояние ПОИСКА (не «проверка не завершена»). Новые reason-коды
  реестра не вводились (`insufficient_evidence`/`provider_unavailable`
  существующие).
- `services/factcheck_orchestrator.py::_log_retrieval_metrics`: в
  logger-дайджест и mca-событие добавлены empty/irrelevant счётчики (§5.3).
- §5.2 relevance-фильтр (`is_relevant_result`): анализ показал, что
  генератор ложных отрицаний — требование ОБАХ стемов для
  двухтерминного запроса (пересказ одним другим словом отбрасывал
  документ целиком). Минимальная правка: floor=1 при `len(seen)==2`
  (для ≥3 терминов прежний floor=2; ≥20% порог сохранён; морфология/
  generic-синонимы без предметных хардкодов — как было). Окончное решение
  о пригодности — за аналитиком, не за фильтром; офлайн-замер «реальной
  частоты» на живой выдаче невозможен (без сети) — отмечено как
  LIVE_UNVERIFIED для реальных прогонов.

### §7 — вербализация и renderer
- `_temporal_verbalize`: при отсутствии содержательного анализа
  (insufficient без положительных частей) в payload добавляется
  `limit_note` — короткая честная граница вместо абзацев-компенсаций;
  универсального правила длины НЕТ (содержательный ответ передаётся
  целиком, §7.1). Personality Core/Expression/FREQUENT-шов
  (`speech_owner_block` последним блоком system) не тронут.
- `_temporal_fallback_text`: при содержательном вердикте opener нейтральный
  («разбор сделан без веб-источников») + разбор частей сохраняется
  детерминированно (аналитик-результат не теряется при отказе
  вербализатора); для честного insufficient — прежние открытые формулировки
  причин (добaвлен NO_RESULTS opener).
- `services/factcheck_renderer.py`: §7.3 — при техническом заголовке
  отдельная концовка с тем же ограничением (`_TECHNICAL_NOTICE`) не
  добавляется (заголовок+абзац+концовка = 3 одинаковых сообщения — снято);
  §7.4 — принудительная композиция тела (детерминированный список 2–4
  пунктов, `_points`/`_sentences`) удалена, тело вербализатора проходит
  как есть; разбор ключевых утверждений (`По утверждениям:`) и привязка
  реальных источников (`Источники:`, только EvidenceMap текущего прогона)
  сохранены; экранирование и Telegram-разметка без изменений.
