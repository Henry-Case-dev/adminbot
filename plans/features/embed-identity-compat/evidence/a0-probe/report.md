## 1. Методика

1. **Один** SSH-коннект (один логин, без ретраев). На сервере — read-only SQLite:
   `file:/var/www/admin_bot/local_database.db?mode=ro` + `PRAGMA query_only=ON`.
2. Из `graph_facts_vec JOIN graph_facts` выгружена стратифицированная выборка: по чатам × бакетам длины
   (short <200, mid 200–1999, long ≥2000) × разнообразию `origin`, детерминированно, без `RANDOM()`.
   Для каждой строки: `rowid, fact_id, chat_id, origin, text, embedding (float32)`.
3. Локально воспроизведена **реальная прод-схема** vec0 из DDL и **настоящий** `ecp.compat_probe`
   (без изменений кода) на in-memory копии выборки: эталоны — только старые сохранённые векторы.
4. Embed-вызов — та же проводная форма, что у serving-пути (`LLMClient.embed_once`):
   `POST {EMBEDDING_BASE_URL}/embeddings`, `Authorization: Bearer <EMBEDDING_API_KEY>`,
   тело `{"model": "gemini-embedding-001", "input": [...]}`. Ключ и URL — из локального `.env`, не печатались.
5. В той же SSH-сессии (интерактивный протокол stdin/stdout) для каждого нового вектора выполнен
   **KNN по полному индексу** `graph_facts_vec` (16 003 вектора, `embedding MATCH ? AND k=5`),
   чтобы проверить именно поиск, а не только косинус.
6. Пороги — frozen-константы кода: `MEAN_MIN=0.995`, `MIN_MIN=0.990`, `HIT5_MIN=0.80`,
   floor `0.970/0.940/0.40`, `MIN_SAMPLE=8`, `SAMPLE=12`.

## 6. Ограничения (что эта выборка НЕ доказывает)

1. **42 факта, канонная проба — 12.** Выборка стратифицированная, не случайная; редкие `origin` покрыты 1–2 строками.
   Расхождений 0 из 42 → верхняя 95%-граница доли «чужих» векторов в индексе ≈ 7% (rule of three); на практике
   индекс однороден (одно поколение, один DDL), но это статистическая оценка, а не полный перебор 16 003 строк.
2. **Нет длинных текстов.** В выборке 43–619 символов (медиана 87); фактов 2000–8000 символов не попалось.
   Более того, `compat_probe` по дизайну исключает тексты >2048 токенов (≈8000 симв.), т.е. **сегментированные
   (lossless-сегментация + mean-pool) факты этой пробой не покрыты**. Если в индексе есть такие факты, их
   векторы стоит проверить отдельно (post-deploy canary их тоже пропускает).
3. **Один шлюз / один ключ / одна модель.** Второй credential (`EMBEDDING_FALLBACK_*`) и другие модели не проверялись.
4. Проверено **поведение** (косинус + выдача KNN), а не «ревизия модели» на стороне провайдера: кэширующий
   прокси дал бы такой же результат. Для решения «принимать ли индекс» это не важно — важно, что векторы те же.
5. **Не проверялись** запись/backfill 4 094 фактов, панель `/api/memory/embeddings`, живой поиск после рестарта —
   это post-deploy live-проверки.
6. Маленький личный чат дал 2 строки; пространство общее для всех чатов, поэтому на вывод о совместимости
   это не влияет, но покрытие именно этого чата тонкое.
7. **int8-coarse колонка (`embedding_i8`) отдельно не измерялась**: проба и KNN шли по float-колонке
   (как в самом `compat_probe`). Она квантуется детерминированно из тех же float-векторов, а float совпали,
   поэтому расхождения не ожидается — но это следствие, а не отдельный замер i8.

## 7. Рекомендация для деплоя

**Принимать старый индекс, rebuild не нужен.** Совместимость измерена, а не выведена из имени модели:
косинус 1.0 на 42/42 и top-1 KNN 42/42 по полному индексу.

Обязательные условия перед рестартом и сразу после:

1. **Сверить прод-конфиг с измеренным.** Проба шла с ключом/URL из локального `.env`. В деплой-сессии
   убедиться, что на проде `EMBEDDING_BASE_URL` = `https://apinet.cloud/v1`, `EMBEDDING_MODEL_NAME` =
   `gemini-embedding-001`, а `sha256(EMBEDDING_API_KEY)` совпадает с локальным (сравнивать хэш, ключ не печатать).
   Если прод ходит в другой шлюз/ключ — эта проба к нему не относится, нужен повторный замер.
2. **Post-deploy (live, обязательно):** `GET /api/memory/embeddings` → `compat.serviceable=true`,
   `canary.mean/min/hit5` близки к 1.0, `generation.state` не `building`, лог `EMBEDDING_COMPAT_ADMITTED`;
   один реальный поиск по старым фактам; backfill 4 094 идёт через новый шлюз; `_vec_write_allowed=true`.
3. **Откат:** снять допуск (`status='building'`, `config_revision=NULL`) → поиск снова FTS-only,
   векторы/факты целы. Если стартовая проба неожиданно даст `insufficient`/`incompatible` — adopt не произойдёт,
   индекс останется FTS-only (это не потеря данных), разбираться тем же probe'ом, не форсировать.
