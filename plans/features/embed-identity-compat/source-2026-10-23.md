# ASAP - исправить проверку совместимости эмбеддингов при смене API-провайдера

**Контекст:** основной провайдер эмбеддингов переключён с бесплатного API на платный API.NET. При этом используется та же модель **Gemini Embedding 001**. Изменился API-шлюз, а не намеренно выбранная модель.

Сейчас Adminbot воспринимает изменение endpoint/provider как смену векторного пространства, блокирует семантический поиск и инициирует полную перестройку индекса.

Это неприемлемо: в проекте несколько лет истории сообщений, десятки тысяч фактов и два активных чата. Обычная смена поставщика API не должна приводить к длительной деградации памяти, повторной обработке всей истории и лишним затратам.

## 1. Исправить сам принцип определения совместимости

Разделить два понятия:

- **Embedding Model Identity** - фактическая модель, её версия, размерность, режим формирования эмбеддингов, нормализация и параметры, влияющие на значения векторов.
- **Provider Connection Identity** - URL API, поставщик, ключ, квота, маршрутизация и параметры подключения.

Смена Provider Connection Identity сама по себе НЕ доказывает несовместимость векторов и НЕ является достаточным основанием для полной перестройки индекса.

При совпадении модели и существенных параметров проводить проверку фактической совместимости старого и нового векторного пространства.

При этом одного совпадения названия `gemini-embedding-001` недостаточно для признания совместимости: шлюзы могут использовать разные ревизии модели и настройки.

## 2. Использовать существующий Canary, не создавать новую подсистему

Расширить существующий механизм проверки совместимости в `services/embedding_control_plane.py`.

При смене провайдера без смены заявленной модели:

1. Сверить фактическую размерность, модель, доступную информацию о версии и параметры генерации векторов.
2. Выбрать репрезентативную выборку уже сохранённых векторов и соответствующих исходных текстов из существующей памяти.
3. Получить эмбеддинги этих же текстов через новый API с теми же существенными параметрами.
4. Сравнить старые и новые векторы по косинусной близости. Учесть допустимые численные погрешности.
5. Проверить совместимость на уровне поиска: запросы, закодированные новым провайдером, должны корректно находить документы в старом индексе.
6. Различать подтверждённую совместимость, подтверждённое расхождение и недостаточность данных.

**Критически важно:** нельзя создавать эталоны новым провайдером и затем сравнивать его же результаты с ними. Это проверит стабильность нового API, но ничего не докажет о совместимости со старым индексом.

Проверка должна использовать именно старые сохранённые векторы.

## 3. Поведение при результатах проверки

**Совместимость подтверждена:**

- Продолжить использование существующего векторного индекса.
- Не запускать полный rebuild/reindex.
- Не обнулять кеш и не удалять старые векторы.
- Обновить необходимые метаданные совместимости, сохранив происхождение исходных векторов.
- Обеспечить корректную работу новых записей и поисковых запросов через новый API.
- Не требовать повторного извлечения фактов из старой истории.

**Совместимость не подтверждена из-за недостатка данных:**

- Не объявлять пространство совместимым без доказательств.
- Не запускать автоматически дорогостоящую полную перестройку только из-за смены endpoint.
- Сохранить существующий индекс, факты и возможность отката.
- Использовать доступный FTS-поиск, если безопасное векторное чтение невозможно.
- Вывести понятную диагностику причины и доступных способов восстановления совместимости.

**Несовместимость доказана:**

- Не смешивать несовместимые векторы.
- Использовать существующий механизм контролируемой миграции поколений, сохраняя исходные факты и предыдущий индекс до успешного переключения.
- Не запускать повторное извлечение фактов из многолетней истории: при необходимости перестраиваются векторы уже сохранённых фактов.
- Обеспечить безопасное возобновление после сбоя или рестарта.

## 4. Исправить все связанные точки

Проверить и согласованно исправить:

- `services/summary_memory.py` - `embedding_identity_fingerprint()`, `_identity_fingerprint()`, `_index_generation_ok()` и ключи embedding-cache.
- `services/embedding_control_plane.py` - `profile_identity()`, `classify_identity_compatibility()`, Canary и планирование смены подключения.
- `services/graphrag_rebuild.py` - проверки идентичности и условия запуска rebuild.
- Регистрацию ACTIVE/target generations и связанную диагностику MiniApp.

Не допустить ситуации, когда одна часть системы признала векторы совместимыми, а другая продолжает блокировать поиск из-за другого URL.

Сохранить защиту от реальной смены модели, размерности и дрейфа эмбеддингов.

## 5. Архитектурные ограничения

**Никаких новых сервисов, таблиц, параллельных реестров моделей и дополнительных агентов.** Использовать существующий Embedding Control Plane, Canary, кеш и систему поколений.

Не создавать хардкод под API.NET или Gemini. Решение должно быть универсальным для любых провайдеров одной фактической embedding-модели.

Не подменять полноценную проверку безусловным сравнением строк названия модели.

Не отключать существующие механизмы защиты, не переписывать fingerprint вручную и не объявлять все векторы совместимыми принудительно.

Не вносить изменений, которые могут потерять или повредить многолетнюю историю, факты, графовые связи либо пользовательские досье.

## 6. Обязательная приёмка

Проверить следующие сценарии:

1. Одна модель, одинаковые векторы, разные API-провайдеры - перестройка не запускается.
2. Одна модель, небольшая численная погрешность, сохранённая корректность поиска - совместимость оценивается обоснованно.
3. Одинаковое название модели, но разные фактические векторы - несовместимость обнаруживается.
4. Разные модели или размерности - несовместимые индексы не смешиваются.
5. Недоступность нового API или невозможность сравнения - данные не теряются, автоматического разрушительного переключения нет.
6. Возврат к предыдущему провайдеру - старый подтверждённый индекс может использоваться повторно.
7. Рестарт приложения - результат безопасной совместимости сохраняется и повторная перестройка не начинается.
8. Два чата с общей конфигурацией - нет дублирующих перестроек и нарушения изоляции данных.
9. Уже запущенный rebuild - проверить возможность безопасной отмены ненужной работы после доказанной совместимости без повреждения текущего поколения.
10. Поиск по старым фактам новым API - проверить реальную семантическую выдачу, а не только совпадение размеров векторов.

**Критерий результата:** при смене API-провайдера без изменения фактического embedding-пространства память продолжает работать с существующим индексом без полной перевекторизации.

Это корректировка существующей архитектуры, а не отдельный эпик по созданию новой системы эмбеддингов.

Интегрируй задачу в очередь, согласуй с действующими ASAP и выполняй в штатном workflow. После реализации покажи, как определялась совместимость, почему принято решение использовать старый индекс или перестраивать его, и результаты проверок. Не объявляй совместимость доказанной без фактического сравнения.
