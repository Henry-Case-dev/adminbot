# POSTGEN-DIAG — design note: bounded нормализация и наблюдаемость классов

## Диагноз в одну строку

Прод-отказ `image_postgen_vision=failed/vision_failed` — **провайдерский
non-2xx на тяжёлом payload** (939495 B → base64 ≈1.21 MB), а не наш валидатор,
не таймаут и не декодер; класс причины маскировался (`detail` терялся).
Класс `vision_unreadable` на входящих — **ложный отказ сниффера на легальном
JPEG (fill-байты 0xFF) + неподдержанные декодируемые форматы (TIFF)**; класс
тоже терялся в stage-событии.

## Почему такой фикс (и почему не другой)

1. **Не маскировать провайдер-ошибки** — минимальная и обязательная часть:
   без неё любой следующий шаг слеп. `analyze_image_bytes` теперь несёт
   `detail = http_<status>[/image_rejected|/modality_refused|/model_missing]`
   (R17-safe: только класс, тело ответа не сохраняется).
2. **Bounded нормализация вместо «второго пайплайна»**: ресайз/перекодировка
   ТОГО ЖЕ кадра в JPEG ≤ `MCA_VISION_NORMALIZE_MAX_DIMENSION` (не апскейл).
   Кодек — из уже существующих в окружении:
   * Pillow — если установлен (dev/тесты, локально 12.2.0);
   * иначе ffmpeg — им уже пользуется видео-контур в проде
     (`handlers/video_download.py`, yt-dlp merge); вход через bounded
     temp-файл, т.к. TIFF и др. не читаются из несекаемого pipe
     (проверено локально: pipe → «Output file does not contain any stream»,
     файл → rc=0).
   Нет ни одного кодека → `None` (поведение прежнее, честный отказ).
3. **Ровно один retry** только на image-class отказ (400/413/415/422 или
   явная семантика «image rejected»), только если нормализация дала СТРОГО
   меньший payload и в бюджете осталось ≥3 c. 5xx/429/таймаут/404 не
   ретраятся (не тот класс). Финальный отказ всегда несёт detail последней
   попытки — retry ничего не маскирует.
4. **Фоллбэк входа** (`validate_or_normalize`) — только после
   `vision_unreadable`; валидные входы идут байт-в-байт прежним путём
   (паритет: тест `test_valid_image_untouched`). Это лечит:
   * ложный отказ на легальных JPEG с fill-байтами — **исправлен сам сниффер**
     (stdlib, без декодера: пропуск серии 0xFF);
   * декодируемые форматы, которых сниффер не знает (TIFF и пр.) — через
     нормализацию; HEIC без декодера остаётся честным `vision_unreadable`
     (но теперь с классом в detail).
5. **Bounded latency сохранена**: первый вызов — полный бюджет
   (`IMAGE_POSTGEN_VISION_TIMEOUT_SECONDS`, 20 c); retry — остаток бюджета;
   нормализация — в отдельном потоке (`asyncio.to_thread`) и с таймаутом
   ffmpeg. Доставка изображения происходит ДО анализа и не блокируется.
6. **Киль-свитч** `MCA_VISION_NORMALIZE_ENABLED` (env-only, default ON): OFF →
   прежнее поведение целиком (сниффер+честный отказ, без фоллбэка и retry) —
   откат без остатков; тесты `test_kill_switch_off_keeps_original`,
   `test_retry_skipped_when_normalize_disabled`, `test_disabled_kill_switch`.
7. **R17**: логи — только классы/размеры/статусы; байты и декодированный
   контент не логируются; temp-файл ffmpeg удаляется в `finally`.

## Семантика (Writer не меняется)

Writer по-прежнему получает data-only исход: `ready` (по нему можно
описывать «получилось X, Y») либо честный «содержимое не подтверждено»;
`detail` — служебное поле для журнала/событий (в блок `<image_analysis>` не
рендерится, чтобы Writer не пересказывал внутренние коды).

## Совместимость

- `validate_image_bytes` не менял контракт (синхронный; поведение прежнее).
- `_finish_analysis_or_job(..., detail="")` — keyword-only с дефолтом
  (обратная совместимость; существующие вызовы/тесты без изменений).
- `PostgenVisionOutcome` получил поле `detail` третьим — все конструкторы в
  коде/тестах используют позиционный только для `status` (+ keywords).
- Существующие наборы MCA-19/P0V/POSTGEN/media — зелёные (1131 в кластере).
