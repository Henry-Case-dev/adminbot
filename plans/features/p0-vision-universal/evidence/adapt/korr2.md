## Почему

Владелец: авто-`h≥2×w → segments` — «обязательный этап по форме», а форма и
контент не должны влиять на решение; вместо классификатора — единый поэтапный
механизм; фрагментация — только явный не-дефолтный инструмент.

## Итоговый конвейер (единый для всех входов)

```
1) факт. MIME/размер/разрешение (sniff) + payload = len(bytes)×4/3+256 (Base64+JSON)
2) влезает в лимиты (bytes/pixels/формат) → original: 0 перекодирований
   ЛИМИТ НЕИЗВЕСТЕН (REQUEST_MAX_BYTES=0) → тоже original (адаптация по ответу)
3) заведомо превышает → optimize:
   Этап A — перекодирование БЕЗ изменения разрешения; гарды:
            • нет выигрыша (копия ≥ оригинала) → не перекодируем;
            • прозрачность → PNG-копия (альфа не теряется), не JPEG;
            • анимация → не «сплющиваем» (оптимизация пропускается);
            • ориентация EXIF → применяется (baked) при перекодировании;
   Этап B — постепенный ресайз с пропорциями, масштаб от фактического payload
            (≤3 попытки, floor 256 px, prep-пиксели), максимум разрешения в
            рамках лимитов — без жёсткого 1024;
4) вызов существующего analyze_image_bytes (тот же провайдер/схема/учёт);
5) retry ≤1 — только подтверждённый size/format-отказ (400/413/415/422 или
   класс size/pixels/format/context из ответа), строго МЕНЬШЕЙ копией;
   401/403/429/сеть/прочие 400 — без повтора; повторный отказ → честная
   диагностика (VisionError.detail), никакого «успеха»
```

Гарантии: оригинал неизменен (вход не мутируется, копия не подменяет его);
ноль перекодирований при допустимом оригинале (тест с «кодек не должен
вызываться»); локальная обработка bounded (≤3 попытки Этапа B, таймаут ffmpeg,
общий бюджет адаптивного анализа); нет привязки к модели/провайдеру.
