# F-STALL-01 — 951 s остановка event loop (2026-11-27 02:16:25.150 → 02:32:16.825 UTC)

Диагностика производственного зависания, найденного live-проходом LVS на deployed-линии.
Продуктовый код **не изменялся** (см. §7: точный кадр не доказан — по контракту задачи
изменение продукта в этом случае запрещено). Прод читался **только read-only**
(`sqlite mode=ro`, `SELECT`/`journalctl`/`sar`); сервис не перезапускался, сообщений в
Telegram не отправлялось.

## 0. Атрибуция версии (уточнение предыдущего evidence)

| Факт | Значение |
|---|---|
| Процесс, в котором произошёл stall | PID `753466`, `ActiveEnterTimestamp` 2026-11-27 **01:09:05 UTC** |
| `9516c9125` («2.58.257») | коммит создан **2026-11-27 07:14:08 UTC**, задеплоен 07:30 UTC |
| Разница `9516c9125^ .. 9516c9125` | 29 файлов, только version pins (`APP_VERSION`, тестовые/UI-хelперы): `34 insertions(+), 34 deletions(-)` |

То есть событие 02:16 UTC произошло на `9516c9125^`, а не на самом `9516c9125`.
Функционально код идентичен (bump-коммит не меняет логику), поэтому диагноз на
`9516c9125` валиден, но формулировка «stall на 2.58.257» в
`evidence/live-2.58.257-2026-11-27/index.md` §3.2 неточна: это предыдущая сборка.

## 1. Доказанные факты

1. **Журнал процесса молчит 951.675 s.** Последняя запись — `02:16:25.150`
   (`graphrag RAG int8: chat-scope KNN partial`, `own=11/800`, `k_last=512`,
   `filtered_other_chat=501`), первая после — `02:32:16.825`
   (`[vision] maintenance stage timeout | stage=expire_intents`). Между ними **0 строк**
   (`raw/journal-window-0214-0234.txt`, 340 строк за 20 минут, все до/после окна).
2. **Journald при этом жив и не режет записи.** За 02:20–02:32 другие юниты писали
   (`_COMM=sudo` — 708 строк, cron — 1); `LogRateLimitIntervalUSec=0`,
   `LogRateLimitBurst=0` (rate limit для юнита выключен); строк `Suppressed`/`dropped`
   нет. ⇒ молчал именно процесс, а не журнал.
3. **Планировщик не обслуживался.** 5-секундные `VisionMediaWorker._tick` (≈190 тиков)
   отсутствуют; при возобновлении 7 `was missed` + 1 `skipped: maximum running instances`
   (нормальный «догоняющий» тик после разблокировки).
4. **Наблюдаемость PG не обновлялась.** `uptime_events`: 1 строка/минуту до `02:16:19`,
   затем **ровно 0 строк** до `02:32:19` (gap 960.000 s) — `raw/uptime-gap.json`.
5. **Рестарта, OOM, диска, swap и I/O-шторма не было.** `NRestarts=0`, `MemoryPeak=2.80 GB`
   при `max` cgroup (без лимита) и 3.9 GB RAM, `kernel`-журнал окна — только `[UFW BLOCK]`,
   строк `hung task`/`oom`/`blocked for more than` нет; `df /` — 44 GB свободно (54 %).
6. **CPU: одно ядро было занято ~100 % всё окно.**

```
sar -u  (host, 2 vCPU)
02:10:00  user 6.10%  idle 92.71%
02:20:01  user 23.60% idle 74.99%
02:30:00  user 52.52% idle 47.01%     CPU0 user 90.75% idle 9.11% | CPU1 user 14.28%
02:40:00  user 17.17% idle 81.76%     CPU0 user 28.34%
sar -W   pswpin/s 0.43–1.10, pswpout/s 0.00–0.39 (без thrashing)
sar -b   bread/s ≈ 2261 при 68 rtps (page-cache чтение, не диск-шторм)
```

Бакет 02:20:01–02:30:00 (600 s) целиком внутри окна: CPU0 = **90.75 % user**.
Бакет 02:30:00–02:40:00 содержит 136 s окна и даёт 28.34 % на CPU0 (≈ 22.7 % ожидаемых
+ базовая нагрузка). ⇒ во время окна **один поток непрерывно жёг ~1 ядро**.

7. **Все три «подозреваемых» корутины были жертвами, а не источником.** На 02:16:25
   в полёте: `memory_maintenance._tick_experience_review` (job `8c414411…`),
   deep-sleep шаг `explore` (`DreamWorker._tick` → after-sleep hook, pipeline
   `run_c51f69…`), `VisionMediaWorker._maintenance_sweep` (стадия `expire_intents`).
   При возобновлении 02:32:16.8–.9 они продолжились одновременно с таймерами
   (`wait_for(30)`, aiogram long-poll, scheduler wakeup) — то есть стоял **сам loop**,
   а не отдельный HTTP/LLM-вызов (LLM/HTTP — async, их ожидание loop не блокирует).

## 2. Что исключено (с методом)

| Диск I/O / fsync | `sar -b`, `df`, `kernel` | исключено (`%iowait` 0.09–0.61, 44 GB free) |
| Journald rate-limit/backpressure | `LogRateLimit*=0`, `Suppressed` | исключено (§1.2) |

## 3. Доказанный класс причины

**Синхронная CPU-работа на потоке event loop ~951 s, без единого `await`.**
Это единственная модель, совместная со всеми фактами §1: loop не исполнял callbacks
(нет тиков, таймеров, записей PG), при этом одно ядро было занято 100 %, без I/O,
без OOM, без рестарта; после завершения работы все просроченные таймеры сработали
пачкой за ~5 мс.

Что этим НЕ доказано: **точный кадр** (файл:строка). В сохранившихся durable-артефактах
его нет: ни `task_jobs` (единственная перекрывающая окно задача — `experience.review`,
и её финальный `progress_at`/`finished_at` = 02:32:17), ни `mca_events`, ни
`mca_pipeline_runs` не пишут per-stage timestamps между 02:16:25 и 02:32:16; стека
процесса в момент подвисания никто не снимал (`faulthandler`/loop-lag-проба в продукте
отсутствует). Обе «видимые» активности в окне — жертвы; их следующие шаги измерены и
дёшевы:

* `experience.review` после `fresh_stream_lag`: `json.dumps(payload)` — payload **5 558 Б**
  (`raw/prod-readonly-probes.json`), `_archive_pass` — курсоры `archive_start` 2 391 910 /
  2 404 611 при курсорах 2 391 900 / 2 352 197 (диапазоны 10 и 52 170 строк), `_capture_*`
  — `LIMIT review_batch_max`, `_recheck_stale` — `LIMIT review_batch_max`.
* deep-sleep `explore` после KNN: `facts ≈ 400` (expired top-up), `episodes = 270`
  (max summary 528 симв.), `pool` ≈ 670 → `merged=667` в логе `topic packets` —
  ровно это и наблюдается в 02:32:16.913; `build_topic_packets`/`pick` на таких объёмах
  — единицы миллисекунд.

То есть мучитель — **фоновая задача, не оставившая durable-следа** (у неё не было ни
`task_jobs`-строки, ни события, ни лога до/во время спина).

## 5. Точный план (следующий шаг, даёт file:line при повторе)

1. **Bounded loop-lag watchdog (наблюдаемость, не новый флаг/таблица/очередь).**
   Одна `asyncio`-задача на процесс: `sleep(1)`; если фактическая задержка > `5 s`,
   один раз за инцидент вызвать `faulthandler.dump_traceback(file=sys.stderr,
   all_threads=True)` и записать `event=loop_stall | lag_ms=…`; при лаге > `60 s` —
   повторить дамп (не чаще 1/60 s). Никаких действий над задачами не выполнять.
   Приёмка: тест с искусственным блокирующим CPU-циклом 2 s в loop —
   ожидаемый дамп содержит кадр этого цикла; без блокировки дампов нет
   (RED на текущем коде: дампа нет вообще).
2. **Тот же приём на проде**: при следующем лаге > 60 s журнал отдаст полный стек всех
   потоков, и виновник станет file:line, без гадания.
3. После идентификации — минимальный фикс по классу: либо `await asyncio.to_thread(...)`
   вокруг найденной CPU-функции (loop не блокируется), либо алгоритмическое ограничение
   (`O(k·n)` инкрементальный MMR вместо `O(k²·n·d)`), с тестом «тикающий корутин не
   замирает > 100 мс» по образцу `tests/test_p0_scheduler_loop.py::_max_loop_gap_while`.
4. **Не делать** до получения стека: менять лимиты `graph_mmr_fetch_k`/`deep_sleep_top_k`,
   выключать функции, вводить новые флаги/очереди — это либо смена продуктовой выдачи,
   либо лечение симптома.

## 6. Ограничения

* Точный кадр не доказан (см. §3). Стек в момент события не снимался, ретроспективно
  его взять неоткуда: `faulthandler` не включён, py-spy не запускался.
* `sar` даёт per-CPU, а не per-thread; связка «100 % одно ядро» ↔ «поток loop» опирается
  на одновременную остановку всех asyncio-таймеров и отсутствие I/O (§1.6–1.7), а не на
  прямом измерении потока.
* Использованы 6 SSH-логинов (recon + 5 read-only прогонов), без паролей и перебора;
  временные скрипты исполнялись через stdin и на проде не сохранялись.
* Измерения `_mmr_select`/`build_topic_packets` на реальных объёмах — оценка по коду и
  размерам данных, не прогон на проде (полный прогон занял бы то же время, что и дефект).
