# P0 FACTCHECK — изображения, альбомы, пересланные публикации (source snapshot)

Источник: сообщение владельца в root-чате 25.10.2026 (P0 FACTCHECK). Ниже — полный
нормативный состав требования; формулировки сжаты без потери обязательств.
`plans/current_task.md` НЕ заменяется и не редактируется.

## 0. Очередь и приоритеты

1. Это дополнительное требование в действующую очередь, не новый эпик и не замена
   текущего задания.
2. Все незавершённые задачи сохраняются и доводятся до конца: Speech Architecture и
   Personality Core; естественность речи/краткость/юмор; режимы мата (FREQUENT);
   заводской стиль «Завсегдатай Двача»; Style Policy и кавычки; запрет искусственных
   квот инструкций; алиасы и идентификация; Memory, L2/lore, provenance, self-echo;
   маршрутизация L1 и функциональный анализ; блокеры production deployment.
3. Не переводить незавершённое в DONE ради закрытия очереди; unit-тесты не являются
   доказательством выполнения функционального требования.
4. Параллельная работа разрешена при отсутствии конфликтов; при общем компоненте —
   согласовывать без перезаписи чужих результатов.
5. После Fact-check автоматически вернуться к оставшимся задачам; DONE только после
   закрытия всего обязательного инженерного scope.
6. `owner_live_checks` не блокируют DONE, процент и деплой; живые тесты в рабочих
   Telegram-чатах не выполнять.
7. Human Gate — только при объективно необходимом решении владельца.

## 1. Подтверждённый дефект

В PERMsoc пользователь вызвал «Фактчек» ответом на фотографию из пересланной
публикации с несколькими изображениями и длинным текстом. Бот ответил
«и че тут проверять, пустоту?».

Это неверно: в публикации есть проверяемые утверждения, фотографии — значимый
материал. Где теряются данные (update, сохранение альбома, reply, сборка контекста,
маршрутизация, payload) — не предполагать, а установить по факту. Гипотеза
«отсутствие caption» не считается доказанной без исследования исполнения.
Отдельно проверить одиночное изображение без подписи.

## 2. Сквозной аудит

Путь: `Telegram update → media/reply resolver → message storage → media group
reconstruction → OCR/Vision → Fact-check context → provider payload → model → response`.

Проверить: `message_id`, `reply_to_message`, `media_group_id`; сохранение альбомов и
отдельных элементов; `text`, `caption`, `caption_entities`; подписи пересланных
публикаций; доступность исходных файлов; передачу изображений в существующие
Vision/OCR; определение типа контента при вызове «Фактчек»; проверки пустого текста;
реальные payload к LLM; ошибки и fallback.

Установить: получил ли Fact-check исходную фотографию, полный альбом, подпись и
извлечённый из изображений текст. Не ограничиваться анализом промптов.

## 3. Альбомы

Ответ на элемент альбома должен восстанавливать публикацию целиком:
1. Определить исходные `message_id` и `chat_id`.
2. Проверить `media_group_id`.
3. Найти остальные элементы той же группы в том же чате.
4. Собрать все доступные фотографии и относящиеся к ним подписи.
5. Сохранить связь изображений с текстом публикации.
6. Не терять длинные подписи и переносы строк.
7. Не подменять публикацию текстом команды «Фактчек».
8. Не объединять соседние сообщения вне медиагруппы.
9. Корректно обрабатывать частично отсутствующие элементы.

Caption может быть только у одного элемента. Reply на самостоятельную фотографию —
обрабатывать именно её. Не создавать вторую систему хранения медиагрупп, если
существующую можно исправить.

## 4. Одиночные изображения

«Фактчек» обязан работать при ответе на: обычную фотографию; скриншот с текстом;
мем с проверяемым утверждением; изображение с подписью и без; пересланную
фотографию; картинку с несколькими текстовыми блоками.

Отсутствие обычного текста ≠ отсутствие содержимого. Использовать существующую
обработку визуального содержимого; OCR — для текста, Vision — для понимания
содержания и связи с утверждением. Не полагаться только на OCR. Описание
изображения не доказывает его подлинность, дату или место. Если проверить нельзя —
объяснить, что именно неустановимо и что нужно. Не придумывать результаты.

## 5. Существующая инфраструктура Vision

Использовать существующие Vision routing, OCR, инструменты анализа вложений,
обработку фото в Direct Chat, маршрутизацию провайдеров, retry/fallback. Не вводить
отдельную модель/сервис/pipeline без технической необходимости. Модель без поддержки
изображений → существующий совместимый маршрут/fallback. Недоступное изображение →
честная техническая ошибка, а не «проверять нечего». Лишних LLM-вызовов не добавлять.

## 6. Проверка утверждений

1. Определить проверяемые утверждения.
2. Использовать текст публикации и изображения вместе.
3. Проверять даты, имена, события.
4. Использовать существующие поиск/источники.
5. Отделять подтверждённое от неподтверждённого.
6. Указывать противоречия.
7. Не считать изображение автоподтверждением текста.
8. Не делать категоричный вывод при недостатке данных.

Для альбома не нужен отдельный фактчек каждой фотографии, если они к одному
утверждению, но ни одно значимое изображение не игнорируется. Противоречие
изображений подписи учитывать. Не выдумывать первоисточники, результаты обратного
поиска и «просмотренные сайты».

## 7. Пустой ввод

Найти проверки, которые завершают фактчек при пустом `text`/`caption` раньше
определения наличия медиа. «Пусто» фиксировать только после проверки всех источников.
Различать: нет текста, но есть изображение; нет текста, но есть медиагруппа;
изображение недоступно технически; OCR не нашёл текста; изображение есть, но нет
проверяемого утверждения; данных действительно нет. Не создавать новый классификатор:
использовать фактическое состояние входа и существующих инструментов.

## 8. Общие пути медиа

Если дефект в общем media/reply resolver — проверить Direct Chat, Observer,
Initiative, Memory, Summary и других потребителей; исправлять в общем компоненте, а
не обходом в Fact-check. Не переписывать модули, если дефект к ним не относится.
Отдельные реальные находки фиксировать в очереди, не раздувать P0 гипотезами.

## 9. Регрессионные проверки (15)

1. Текстовый фактчек без изображений.
2. Одна фотография с подписью.
3. Одна фотография без подписи.
4. Скриншот с текстовым утверждением.
5. Альбом из нескольких фотографий.
6. Caption у первого изображения.
7. Caption у другого изображения.
8. Reply на первый/средний/последний элемент.
9. Пересланный альбом.
10. Пересланная одиночная фотография.
11. Альбом с неполными данными.
12. Ошибка получения медиафайла.
13. Недоступность Vision-провайдера.
14. Изображение без проверяемого утверждения.
15. Текст и изображения, которые его не подтверждают.

Отдельно воспроизвести исходный случай PERMsoc по production-логам и сохранённым
данным. Проверять входные данные этапов, а не только финальный текст. В рабочие
чаты ничего не отправлять.

## 10. Reviewer

Не принимать исправление по одному изменению `if not text`. Подтвердить: изображение
доходит; элементы альбома связаны; подпись не теряется; reply разрешается к нужному
сообщению; OCR/Vision выполняется; payload содержит данные; нет выводов о
непрочитанных изображениях; текстовые проверки не сломаны; fallback/retry/лимиты
сохранены; нет искусственных квот инструкций; нет лишних LLM-вызовов. Проверить и
остальные требования очереди по их критериям. Дефект возвращать адресно, не сбрасывая
прогресс по независимым пунктам.

## 11. Завершение и деплой

Сверить всю очередь; дождаться штатных операций активных задач; устранить блокеры
деплоя через Builder/DevOps. Не публиковать финальный отчёт, пока обязательный scope
не закрыт. Деплой — после применимых проверок; частичный релиз не выдавать за полный
P0. Проверить версию, healthcheck, ошибки запуска, применение настроек, работу
исправленных компонентов, отсутствие регрессий, сохранность данных/конфигурации/
fallback. Опасный деплой поверх необследованного production-дерева не выполнять.

## 12. Отчёт

Время отчёта; понятное описание; отдельный ASCII-прогрессбар; процент и
выполнено/всего; оставшиеся работы; production-версия и статус деплоя. Прогресс — по
всей обязательной очереди, не только Fact-check. 100% только при закрытом scope.
Обязательные пункты отчёта: почему увидели «пустоту»; как исправлены фото и альбомы;
какие проверки пройдены; какие другие задачи выполнены; какие дефекты исправлены по
замечаниям Reviewer; версия на production; что осталось и почему.

## Финальные ограничения

Не создавать новый эпик; не заменять `current_task.md`; не терять незавершённое; не
перезапускать выполненное; не создавать архитектурные слои; не вводить лишние
LLM-вызовы; не удалять fallback/retry/технические ограничения; не ломать другие
модули; не делать живых тестов в рабочих чатах; не требовать повторных согласований;
не запускать продолжение поверх работающего агента; не подменять общий прогресс
прогрессом одной задачи; не останавливаться на аудите.
