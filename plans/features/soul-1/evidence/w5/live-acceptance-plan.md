# SOUL-1 / W5 — план live-наблюдения инициативы (24–48ч, канарейка)

Статус: **LIVE_UNVERIFIED**. Ни одного искусственного сообщения в рабочую
группу не отправлено и отправлено не будет: требование §19 п.6 прямо
запрещает спамить ради закрытия отчёта.

## Что уже готово к наблюдению (движок, без публикаций)

* оконная воронка 24ч/48ч — `GET /api/memory/initiative-vitality?chat_id=`
  (global admin; канонический маршрут Статуса в MiniApp — `#/`):
  (global admin): сканы, наблюдённые, элигибельные, оценки, возможности (в
  т.ч. по видам), решения по действиям, молчание с причинами, попытки
  отправки, доставки, дубли, отказы, задержка p50/max, last-штампы,
  честное покрытие окна;
* вердикт `health ≠ outcome` с предупреждением «возможности есть, сообщений
  нет», диагностикой «ноль возможностей при живом чате» и окном низкой
  активности;
* реальное состояние ворот чата (`gates.items` + `gates.state`) — почему
  инициатива сейчас не идёт;
* безопасная проверка `POST /api/memory/initiative-check` — trace до mock
  send, по умолчанию без публикации.

## План (владелец / DevOps; флаги OFF по умолчанию)

1. **T0 — включить наблюдение и набрать окно.** Убедиться, что
   `flags.initiative_observer_enabled` и `initiative.enabled` чата включены;
   ничего не «докручивать» до спама. Дождаться 24ч естественного трафика.
2. **T0+24ч — снять первое окно.** `GET /api/memory/initiative-vitality?
   chat_id=<id>&hours=24` (канонический маршрут Статуса — `#/`, не
   `#/status`):
   зафиксировать `scans`, `observed`, `eligible`, `opportunities`, `evals`,
   `decisions`, `delivered`, `eval_skips`, `coverage`. Нули — это результат,
   а не повод что-то включать.
3. **Критерии «не задушено» (обязательные наблюдения):** при
   `live_messages ≥ 2000/сутки` и `opportunities = 0` — вердикт
   `observer_silent_live_chat` (диагностика); при `opportunities > 0` и
   `delivered = 0` — вердикт `opportunities_no_messages` с распределением
   причин; в обоих случаях рядом должны быть видны конкретные причины ворот
   (`gates.items`) и решений (`silence_by_reason`).
4. **Живые сценарии §19 п.6 (без обращения к боту):** уместный SILENT,
   реакция без текста, короткая реплика, связанная абсурдная шутка, попытка
   send и фактическая доставка. Для каждого — время, `chat_id`,
   `message_id`, исход и (для доставки) ревизии Core/Style из
   `initiative_delivery_manifest`.
5. **Мягкие цели (по желанию владельца, не вместо наблюдения).**
   `initiative.observation_target_interval_seconds` (проверять примерно
   каждые N секунд, не чаще 600 и не выше профиля) и
   `initiative.soft_target_replies_per_day` (цель по числу реплик, не
   обещание; пауза не ниже 30 минут). Дневной лимит, дедуп, темы, бюджет
   оценок и recheck остаются жёсткими — это видно в `gates.soft_targets`.
6. **Реальная send-проверка (только отдельно и явно).** Включается осью
   `flags.initiative_diagnostics_publish_enabled` (default OFF) И
   `confirm_publish=true` в запросе; без обоих условий проверка остаётся
   mock. Наблюдение должно показать РОВНО одно сообщение и его
   `message_id` в ledger.
7. **T0+48ч — свести два окна.** Ожидаемая «здоровая» картина: сканы идут
   (~288 тиков/сутки), `observed` растёт вместе с трафиком, причины
   молчания объяснимы, доставки (если были) подтверждены `message_id`.
   Если за 48ч доставок нет при `opportunities > 0` — разбирать плечи
   writer/recheck по причинам решений, а не «поднимать частоту».

## Что считается провалом наблюдения (а не «нулём»)

* `scans = 0` при живом трафике — наблюдатель не запускается (тик/гейт);
* `delivered > 0` без `message_id`/ledger-строки — нечестная доставка;
* проверка «Проверить инициативу» публикует что-либо при выключенной оси;
* вердикт `ok`/`healthy` при `delivered = 0` — подмена здоровья отправкой.
