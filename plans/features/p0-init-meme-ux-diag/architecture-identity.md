# p0-init-meme-ux-diag — контракт идентичности (A0-ARCH, три остатка)

Дополняет `architecture.md` §3 (он не переписывается). Сверено по коду деплоя `6c11fc08` (2.58.194). Внешних фактов не требовалось: механика репозиторная. Не-цели: новых таблиц, колонок, миграции, очереди, планировщика, второго журнала и новых LLM-вызовов нет ни в одном пункте ниже.

## 1. RW-D4-BOTH-WRITE-FAIL — durable-запись терминальной строки

**Инвариант D.** Терминальная строка попытки, порождённая кодом приложения, либо в журнале, либо в спуле (оба видны читателю), либо удерживается процессом и переносится в первый освободившийся носитель; в крайнем случае её ПОЛНОЕ содержимое уходит в лог. Ни один путь не имеет права свести потерю к анонимному предупреждению.

**Доказано сегодня.** Повтор при транзиентной блокировке (`ATTEMPT_WRITE_ATTEMPTS=3`), durable-спул `<db>.attempts.pending.jsonl` рядом с журналом, слияние спула с таблицей по `attempt_id` (`attempts()`), перенос порциями без потери непрочитанного хвоста, идемпотентность (`INSERT OR IGNORE`), фильтр чужого чата в `attempts(chat_id)`. Тесты: `test_attempt_write_is_retried_before_any_fallback`, `..._survives_permanent_journal_failure_via_spool`, `test_spool_flush_never_drops_unread_rows`, `test_spooled_and_journal_rows_are_merged_in_order` (501 строка, батч 200).

**Что отсутствует.** Совместный отказ. Оба носителя лежат в одном каталоге, значит их одновременный отказ — файловый (диск/права/IO), а не логический: чистая блокировка SQLite запись файла не ломает. В этом окне строка живёт только в `_PROCESS_ATTEMPTS` (кольцо 200, `meme_initiative.py:351`), но читатель берёт кольцо лишь когда журнал не открывается (`coverage: process_local`); при живом журнале строка не видна, а в лог уходят только `attempt[:12]`, chat, stage и тип ошибки — `outcome`, `reason_code` и `detail` (а в `detail` лежит `attempt_mode` и факты публикации) теряются. То есть «не молчаливо» верно только для факта падения, но не для содержания попытки: read-model может выдать более старую попытку за «последнюю» без следа.

**«Acceptable but documented» — законный ответ?** Да, но только для физически недостижимого случая и только при двух условиях ниже. Требование владельца «без потери этапов» направлено против дефекта D4, где потеря возникала на ОБРАБОТАННОЙ ошибке журнала (WARNING и строка исчезла при живом диске). Код не может сохранить строку, когда ни один носитель в каталоге не пишется: это ограничение среды, а не решение реализации. Основание для «принято как риск» без изменения кода отсутствует, потому что сейчас теряется не только durable-состояние, но и само содержание факта.

**Минимальное закрытие (обязательно, Builder).** Только `services/meme_initiative.py` + тест; читатели, группировка, формат спула и схема не меняются.
1. Хелпер `_spool_payload(row)` — вынести существующие 11 полей из `_spool_attempt` и переиспользовать в обоих местах (формат не изобретать).
2. `record_attempt`: при отказе и журнала, и спула — сохранить `dict(row)` в `self._unpersisted` (обычный список на экземпляре, потолок `ATTEMPT_UNPERSISTED_MAX = 200`; вытеснение самого старого сопровождается его полной ERROR-записью). Писать ERROR-строку с `json.dumps(_spool_payload(row))` ЦЕЛИКОМ, `attempt_id` без усечения, чтобы факт можно было восстановить дословно.
3. `_retry_unpersisted()`: вызывать в начале `record_attempt` после `_flush_pending_attempts()`; для каждой удержанной строки — одна попытка `_insert_attempt`, при отказе одна попытка `_spool_attempt`, при успехе любого из них убрать из списка; не более `ATTEMPT_SPOOL_BATCH` строк за вызов; никогда не бросать. Идемпотентность уже обеспечена `attempt_id`.
4. Тест (`tests/test_evol014_meme_initiative.py`): оба носителя выключены → строка удержана, ERROR-запись парсится как JSON и содержит все 11 полей; носители включены → `attempts(-100)` даёт её ровно один раз, спул отсутствует; повторная запись того же `attempt_id` — no-op.
5. Приватность: payload — те же поля, что уже лежат в журнале и отдаются API; новых секретов и промптов в лог не попадает (правило §5 architecture.md сохраняется).

**Остаточный риск (фиксируется, не блокирует).** Если процесс умрёт, пока оба носителя не пишутся, единственный след — ERROR-строка. Это принимается явно и записывается в `residual_windows[RW-D4-BOTH-WRITE-FAIL]` с той же формулировкой; строка `P0IM-ID-FINISH` закрывается пунктами 1–4, а не молчанием.

## 2. P0IM-ID-CONC — параллельные попытки в двух чатах и конкурирующие холдеры

**Инварианты (имена, не код).**
- **ID1 Единственность.** Одна логическая попытка = одно непустое родительское значение, mint-нутое до первого гейта (`job_id` мема / per-chat `run_id` текста); дочерние вызовы только `{родитель}#суффикс`. Идентичность никогда не выводится из времени, текста или порядка строк.
- **ID2 Идемпотентность.** Повторная запись того же `attempt_id` не создаёт вторую попытку и не теряет первую (`INSERT OR IGNORE`; слияние по ключу, durable главнее спула).
- **ID3 Изоляция чата.** Группировка и чтение ограничены `chat_id`; ни один ключ, счётчик или лок не разделяется между чатами.
- **ID4 Свёртка без общего состояния.** Агрегатор — чистая функция над строками; между чтениями нет изменяемого агрегата, поэтому любой порядок вставок даёт один и тот же набор групп.
- **ID5 Один писатель на файл журнала.** Спул-дренаж с `os.replace` предполагает единственный процесс на файл (systemd-инстанс один). Это предусловие контракта, а не свойство кода.

**Доказано сегодня.** ID1 — `P0IM-ID-RUN/CHILD` (ранний отказ с `run_id`, child `{jid}#meme_summary|#meme_joke`). ID2 — `INSERT OR IGNORE`, `merged.setdefault`, тест «повторная запись — no-op». ID3 — фильтры `chat_id` в `attempts()`/`_meme_attempt_rows`/`initiative_diagnostics`, тест `attempts(-101) == []`. ID4 — `_meme_attempts_grouped` и `_text_attempts` без состояния. Бронь: PK `chat_id`, CAS-upsert — конкурирующие холдеры в одном чате сериализуются строкой, в разных чатах независимы.

**Что отсутствует.** Нет ни одного наблюдения/теста уровня агрегатора: (а) две попытки в разных чатах с одинаковым `ts` и похожим текстом дают две группы; (б) конкурирующие холдеры в одном чате дают две терминальные строки с разными родителями (одна проходит, вторая конфликтует) и ни одна не исчезает и не порождает третью `row:{attempt_id}`; (в) ID5 нигде не назван, поэтому будущий второй процесс молча сломает дренаж.

**Минимальное закрытие.** Только тест, без правки продукта: один кейс на (а) и (б) в существующем файле тестов журнала/публикаций; переиспользовать уже доказанный no-op для (в). Реальная гонка двух процессов — вне контракта (ID5) и не является основанием держать строку: она закрывается, когда предусловие единственного писателя названо, а не когда смоделирована невозможная конфигурация.

## 3. Нужна ли схема

**Нет.** Три существующих состояния покрывают всех потребителей эпика: родитель (`job_id`/`trace_id`), дочерний суффикс в существующем correlation-поле, факты в `detail` терминальной строки (`attempt_mode`, `publication.output.tg_message_id`). Трасса S4 читает группу по родителю, «Публикации» — ту же группу с терминальной строкой, ось `last_attempt` диагностики — режим и исход только из терминальной строки, карточка — поля API. Единственный факт, не выводимый из схемы, — «строка не была сохранена»; это окно RW-D4 (§1), а не пробел схемы, и колонка его не решает.

**Параллельность и риск.** §1 меняет `services/meme_initiative.py` (+1 тест) → SERIALIZE с S5-MEME/S4-TRACE, писателями того же файла; §2 — только тест. Риск **R1** (локальная правка без изменения контрактов чтения). Откат — revert двух правок, данные не мигрируют.

**Что закрывает этот документ.** `P0IM-A0-CONTRACT` — сам документ; `P0IM-ID-CONC` — тест §2; `P0IM-ID-FINISH` — пункты 1–4 §1. `P0IM-ID-RUN/CHILD/HIST` не переоткрываются.

CONTRACT CHANGE REQUIRED: путь записи попытки обязан удерживать и повторять строку при совместном отказе журнала и спула, а последняя запись обязана нести полную строку вместо `attempt[:12]`; схема, таблицы, очередь и планировщик не меняются.
