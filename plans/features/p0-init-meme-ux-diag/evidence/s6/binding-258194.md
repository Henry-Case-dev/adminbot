## 2. TIME — `P0IM-S6-TZ` (VERIFIED)

Живой ответ обоих чатов (`live-overview-2.58.194.json`):

```
"time": {"generated_at": 1794439672, "basis": "server_snapshot",
         "timezone": {"name": "UTC", "source": "utc_fallback",
                      "offset_seconds": 0, "default_name": "UTC", "reason": ""}}
```

- Шапка на обоих чатах: «пояс чата не задан — UTC (заводское значение, не часы
  сервера)» — то есть назван **заводской слой**, а не часы сервера и не догадка UI.
- Источник и базис снимка пришли из backend: `data-ini-tz-source=utc_fallback`,
  `data-ini-tz-known=true`, `snapshot_basis="штамп снимка — сервер"`,
  `data-ini-snapshot-basis` присутствует; штамп «снимок: 11.11 23:28 (сервер)».
- Дата и смещение сверены с осью, а не с часами браузера: `last_attempt.at =
  1794439462` = `2026-11-11T23:24:22Z`, и ровно это печатается в строке обзора
  («11.11 23:24»); `offset_seconds=0` верно для UTC.
- Клиент больше не собирает пояс из глобального списка параметров:
  `iniChatTimezone` — **0 вхождений** во всём дереве `6c1…` (`git grep`).
- Чужой чат: карточка берёт пояс из ответа ЭТОГО чата (`iniOtherDiagView`,
  `web/app.js:10275-10301`, сверка `iniPeekChatId` и `d.chat_id`), живой снимок
  `data-ini-card-tz-source=utc_fallback` на обоих чатах (`live-peek-2.58.194.json`,
  `peek_keys` содержит `time`, `peek_busy=false`, `peek_error=""`).
- Наблюдён и честный отказ: в промежуточном снимке 23:28:29Z карточка чужого чата
  показывала «Время: пояс чата не прочитан — время в UTC» (`card_tz_source=unknown`),
  потому что применённого payload с блоком `time` ещё не было. Ни в одном снимке
  чужой пояс не подставлен и пояс вызывающего не взят вместо чужого.
- Положительная ветка (у чата задан IANA-пояс) вживую недостижима без изменения
  сохранённых настроек владельца — этого делать нельзя; она доказана тестами
  кандидата (`test_time_block_names_chat_timezone_and_its_layer`,
  `test_timezone_offset_follows_the_instant`, `s6FreshSuite`) и e2e `run_s6_scope`.
  У обоих реальных чатов пояс не задан, поэтому их собственный эффективный пояс —
  именно UTC, и это показано честно.

## 4. EFFECTIVE — `P0IM-S6-EFFECTIVE` (REVIEW, недобор назван)

Живые слои пришли из сервера с подписью слоя у каждого гейта
(чат −1004482340693, `live-overview-2.58.194.json`):

```
текст (3): модуль инициативы — общий слой; наблюдатель — общий слой;
           тумблер этого чата — общий слой
мемы  (4): то же + настройки мемов — слой чата
```

Это ровно тот контракт, который срез исправил: заводское/общее значение больше не
выдаётся за «настройку этого чата», а слой назван сервером.

**Недобор (почему не VERIFIED):**

- гейт `image_module` (доступность модуля картинок) в живом payload не появился —
  в layers попали 4 гейта из 5; отрицательная ветка «модуль картинок выключен →
  общий слой» на проде не наблюдалась;
- `heartbeat` и `провайдеры` (часть строки 126 источника) в снятом ответе вообще
  не отражены — сверять было нечего;
- на втором чате (−1002661910336) карточки слоёв в снимке не отрендерены
  (`layers_text/layers_meme = null`), то есть живое подтверждение есть для одного
  чата, а не для обоих;
- «сохранённые значения не менялись» подтверждается косвенно (слои `global`/
  `factory`, ни одна настройка в ходе выкладки не записывалась), отдельным
  до/после-срезом настроек — нет.

## 5. SCOPE — `P0IM-S6-SCOPE` (REVIEW, недобор назван)

Живое:

- `payload_chat_id` равен запрошенному чату в обоих ответах (`200`,
  `console_errors: []`), шапка не подписана чужим ответом;
- переключение режима **очищает** карточки: в снимке 23:28:29Z карточка чужого чата
  показывала «не прочитан» вместо чисел прежнего чата, и только следующим снимком
  подставился ответ нужного чата;
- peek-ответ несёт собственные ключи чата (`chat_id`, `time`, `meme`,
  `text_initiative`, `generated_at`) — два независимых payload без безымянного
  агрегата;
- штамп свежести — `time.generated_at` того же ответа, подпись «(сервер)».

**Недобор:** сам guard от позднего ответа другого чата (совпадение `scopeEpoch` и
`payload.chat_id`, один in-flight и один хвост) вживую не воспроизводился — для
этого нужен управляемый race, а искусственно тормозить прод-запросы нельзя. Он
доказан тестами кандидата (`test_stale_response_for_another_chat_is_not_applicable`,
`test_payload_is_scoped_to_the_requested_chat`, `s6FreshSuite`,
e2e `run_overview`/`foreign_chat`) и остаётся предметом проверки Reviewer, а не
самообъявлением.
