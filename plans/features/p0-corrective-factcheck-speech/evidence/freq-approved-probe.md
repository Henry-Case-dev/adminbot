## 2. Payload (0 LLM, реальный композер)

Сборка — `prompt_composer.compose_prompt` (`profile=speech_plain`,
`writer=l2_writer`) с прод-фактами: заводская база писателя, заводской Core
full, global `character.expression = {profanity: frequent, sharpness: sharp}`,
identity/Style_Policy_Hint из живого сэмпла, `response_plan` = `compact`.

| Замер | Значение |
|---|---|
| system | 9283 симв. |
| `system_sha12` | `9155212fc01b` |
| `<Expression_Settings>` | есть, 1 |
| финальный контракт речи | есть, последний блок |
| `<Expression_Examples>` | **нет**, trace `skip_reason=not_owner_approved` |

`system_sha12` **байт-в-байт совпадает** с боевым payload прошлой пробы
(`expression-r3.md` §2, плечо A). Значит числа 3/6 из r3 привязаны к этому
точному system, а не к «примерно такой же» сборке.

Отдельного «плеча с одобренными примерами» построить **нельзя**: одобренных
строк 0 → блок не рендерится; любое отличие payload требует либо одобрения
владельца, либо самовольного approve заводских черновиков (запрещено).
Поэтому «плечо B» в этой пробе отсутствует не из-за упрощения, а потому что
его физически нечем собрать.

## 4. Вердикт — **путь не работает: нечего использовать** (не «не лучше»)

- «Уже одобренных авторских примеров» в реестре **0**. Исходная гипотеза лейна
  не подтверждается фактом данных, а не поведением модели.
- Проверить «лучше/не лучше» нельзя: `approved`-плечо неотличимо от боевого,
  потому что примеров нет. Это честный класс «нет данных», а не «эффекта нет».
- Кодовый фикс эту дыру не закрывает: селектор уже корректно требует
  `owner_approved=1`, а авто-одобрение заводских черновиков запрещено
  (`plans/current_task.md:1885`) и было бы тем самым новым решением владельца.
- Единственное доступное изменение payload — одобрение 4 существующих
  frequent-черновиков. Это **одно действие владельца в уже существующем UI**
  («Примеры» → «Используется» / `POST /speech/examples/{id}/approve`), не
  новый продуктовый выбор и не архитектура.

## 5. Рекомендация (минимальная)

1. **Не менять код.** Проблема FREQUENT на этом шаге — отсутствие данных, а не
   логика отбора/рендера: маркер режима и финальный контракт в system есть,
   квоты сняты, блок примеров просто пуст.
2. **Один запрос владельцу (действие, не выбор):** одобрить 4 заводских
   frequent-примера существующим механизмом. Эффект: в system добавится
   `<Expression_Examples mode="frequent">` — 4 строки, 481 симв. / 121 ток.
   (числа из `expression-r3.md` §2; в старые 700/140 укладывается).
3. **После одобрения** — повторный прогон ровно этой матрицы 6+4 на модели
   прода (system sha изменится; ожидаемый прирост payload +481 симв.).
   Подсказка r3 (4/4 на первых четырёх стимулах при локально одобренных
   черновиках) — только гипотеза: n=4, без контрольной пары.
4. Если владелец не хочет одобрять примеры — честная фиксация уже есть в
   `expression-r3.md` §5: `FREQUENT` проявляется на развёрнутых репликах,
   короткие ответы почти не имеют места под мат. Это ограничение длины/модели,
   а не повод для механической вставки или второго регулятора.
