## 3. Ответ (i): состав агрегатного гейта — binding-верификация, не ре-ревью

**Решение D1 (ADR-1027-11):** полный ре-ревью 8 фич **не проводится**. Гейт = binding-верификация: (a) контент-пины по файлам из архивных ревью + релизные перезакреплённые пины T-4042; (b) focused per-feature тест-срезы; (c) кросс-шовный аудит; (d) DDL-репетиция; (e) **полный pytest + JS + F8 — обязателен независимо от исхода (a)–(d)**.

**Условие правомерности (else → ре-ревью расширяется):** drift всех расхождений дерева против архивных пинов укладывается в политику §6. Любое семантическое расхождение кода фичи вне её финального ревью → per-file re-review этого файла на гейте; если семантика затрагивает принятое поведение фичи → re-review расширяется до среза фичи. ## 5. Ответ (iii): DDL v12→v19 на проде — политика частичного применения

**Решение D3 (ADR-1027-11).** Базис — контракт mca-14 (spec §3/§4.1/§4.2; ADR-1027-1 D1/D2): реестр `MigrationStep{version,name,apply}`, runner применяет `version > current` по возрастанию, книга `schema_migrations(version,name,applied_at,checksum)`, двойная идемпотентность (guard раннера + self-guard шага), backup `VACUUM INTO` + free-space + read-back.

**5.1. Предусловия (порядок обязателен):** WAL-checkpoint → backup `VACUUM INTO` на `var/backups/…` (НЕ удалять, R18) → free-space check → read-back (`integrity_check=ok`, `user_version` копии совпадает) → только затем первая миграция. Жёсткое правило: **ни один новый шаг не применяется в init-цикле, не прошедшем backup-гейт** (реализация делает это до батча новых шагов; per-step backup допустим как усиление — drill T-4045 п.7 фиксирует фактическую гранулярность, ослабления к «без гейта» нет).

**5.2. Атомарность и частичное применение:** каждая миграция атомарна; после успешного шага — ряд книги + новая `user_version` (инвариант INV-4: применённая схема ⊇ всех версий ≤ `user_version`). При сбое на середине (k из v13…v19):
- **СТОП**: runner не продолжает старшие шаги; алерт (R17-safe лог + терминальное событие mca-13);
- предыдущая `user_version` (v12+k) **сохраняется** — состояние консистентно по INV-4;
- сервис **остаётся совместимым**: старт/приём сообщений работают (mca-14 §3: отказ миграции не тушует приём); default-ON фичи на отсутствующих таблицах деградируют fail-soft по своим контрактам (проверено в фичевых ревью), а не роняют цикл;
- один повторный рестарт разрешён (init сойдётся с места `user_version` — идемпотентность), далее — диагностика по логу; **restore из бэкапа — не штатный механизм** (ADR-1027-1 D6);
- `user_version` в диапазоне 13–18 = **НЕ success релиза**: пост-деплой приёмка не проводится, T-4048 не закрывается; путь — fix forward (устранить причину, повторить применение).

**5.3. Success-критерий (обязательный пост-чек T-4047/T-4048):** `PRAGMA user_version = 19` **И** `schema_migrations` содержит ровно v13…v19 (по строке на версию, без дублей, checksum совпадают с реестром) **И** идемпотентный повторный старт — 0 изменений, 0 дублей.

**5.4. Форма DDL-ранбука (T-4047/T-4048 заполняют фактически):**

| # | Шаг | Команда/действие | Ожидаемый результат | Факт | Вердикт |
|---|---|---|---|---|---|
| 1 | Preflight | место на диске ≥ размер БД × safety; анкер `8bd1389` записан | проверки ок | | |
| 2 | Checkpoint | WAL-checkpoint | ok | | |
| 3 | Бэкап | `VACUUM INTO` → `var/backups/…` | файл создан | | |
| 4 | Read-back | открыть копию read-only | `integrity_check=ok`, `user_version=12` | | |
| 5 | Применение | рестарт `admin_bot` (init реестра) | лог v13…v19 по порядку | | |
| 6 | Post | `PRAGMA user_version`; SELECT книги | `=19`; ровно v13…v19, без дублей | | |
| 7 | Идемпотентность | повторный рестарт | 0 изменений, 0 дублей | | |
| 8 | Rollback-compat проба | v12-код (checkout `2deb287`) на копии v19-БД | старт, health 200, данные целы | | |
| 9 | Smoke | per-feature §20-пробы (T-4048 чек-лист) | все ✅ | | |

Каждая строка: факт + вердикт; любой ❌ → политика §5.2 (СТОП/алерт), ранбук не продолжается.

**5.5. Блокер-чек дизайна (проверить на гейте, зафиксировать честно):** **релиз-код не должен требовать v19 для старта.** Проверка: boot-drill на копии v12-БД с `MCA_SCHEMA_MIGRATIONS_ENABLED=false`: сервис стартует, приём сообщений работает, фичи деградируют fail-soft. Если какой-либо модуль волны безусловно (вне kill-switch/try-except) требует таблиц/колонок v13+ на стартовом пути — это **блокер дизайна** релиза: в гейт-отчёт, релиз не авторизуется до разрешения (разрешение кодом запрещено — новый код вне скоупа; путь — эскалация владельцу). Ожидание по архивам: все 8 фич имеют env-only гейты и OFF-паритет — риск Low, проверка обязательна.

**5.6. Cold-rollback-совместимость (честная фиксация):** БД на v19 **обязана** работать с откаченным кодом v12 — гарантия ADR-1027-1 D3/D6 (аддитивность: без rename/drop, новые колонки nullable, новые таблицы не читаются старым кодом) и проверяется drill'ом (§5.4 стр.8) на копии, а не постфактум. Два известных нюанса фиксируются явно: (1) аддитивные объекты остаются в БД после cold-отката — безвредны, писателя нет; (2) legacy-путь миграций старого кода, встретив `user_version=19`, не должен откатывать версию/ломать схему: в волне-0 уже ловился и чинился дефект «downgrade user_version» — drill обязан **наблюдать и записать фактическое поведение** старого кода на v19-копии (старт, health, целостность данных, итоговое значение `user_version`), не считать это самоочевидным. Если drill покажет деструктивное поведение старого кода на v19 — cold-откат деградирует до аварийного контура «revert + restore бэкапа», и это фиксируется в гейт-отчёте **до** деплоя как известное ограничение (эскалация владельцу — только если drill провален).

Процедура: per-file re-review этого файла в агрегатном гейте; при затрагивании принятого поведения фичи — расширение до среза фичи. 3. **Классифицировать дельту** по хункам: (a) **ASAP-пины/фикстуры** — счётчики каталога/версий/коллекции, conftest-фикстуры, импорты уже-закоммиченных модулей → класс «документированное касание»; (b) **семантика** — изменённые/добавленные/удалённые тесты, изменённые assertions о поведении §11.1–§11.4 → класс «семантика».

Инвентарь ≠ 43 или есть дельты класса (b) → **re-review файла в агрегатном гейте** (T-4045) до Approved; расширение до среза фичи — если семантика меняет принятое поведение.
5. Контроль-проба независимо от класса: focused-прогон mca-07 == **43 passed** (уменьшение/рост счёта — вход в шаг 3 заново).

Правило шагов 1–5 — общий шаблон для любого drifted-файла матрицы §3.
