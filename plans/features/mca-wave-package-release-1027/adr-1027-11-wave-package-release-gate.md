## Контекст

8 фич MCA (§93–§100) по отдельности Approved+Archived с `DEFERRED_TO_RELEASE`; владелец санкционировал агрегированный деплой. Ограничения: (1) исторические WTH считались от `05bc870` и после 3 ASAP-релизов байт-в-байт невоспроизводимы; (2) рабочее дерево содержит смешанные M-файлы (волна + уже-закоммиченные ASAP-хунки) и (c)-чужое; (3) прод-БД поднимется с v12 до v19 одним применением; (4) найден дрейф `tests/test_mca07…` (`92bfa016…` ≠ пин `C292E50F…`). Открытые вопросы PM (i)–(v) — T-4043.

## Решения

**D1. Агрегатный гейт = binding-верификация, не ре-ревью (ответ (i); spec §3).**
Выбрано: гейт проверяет **сохранность** пофайлово принятого 8 гейтами, не переоценивает его. Состав: (a) матрица контент-пинов (файл → пин из архива → текущий хэш → классификация: совпадение / документированное касание / недокументированный дрейф); (b) focused-срезы 8 фич с архивными счётами (33/25/17/25/63/34/43/70; уменьшение = блокер); (c) кросс-швы (7 рёбер + совместимость с `2deb287`); (d) kill-switch-инвентарь (~25, матрица OFF→legacy); (e) R17/R18; (f) DDL-репетиция на копии; (g) **полный pytest+JS+F8 обязателен независимо**; (h) import-closure; (i) rollback-готовность. Новый агрегатный WTH по рецепту Эпика 3 (DIFF+STATUS+UNTRACKED, отчёт исключён) + релизные per-file пины T-4042 = binding доставки. Эскалация: недокументированный семантический дрейф → per-file re-review на гейте; продукт-семантика вне принятого → блокер.
Обоснование: полный ре-ревью дельты дублировал бы 8 завершённых гейтов без прироста гарантий; матрица + focused-срезы + полный прогон детектируют потерю/подмену принятого.
Альтернатива: полный WTH-ре-ревью дельты — отклонено (стоимость без прироста; исторические WTH всё равно невоспроизводимы, сравнивать не с чем).

**D2. Стратегия смешанных хунков — таблица решений per-file (ответ (ii); spec §4).**
Выбрано: карта хунков T-4042 (сверка со staging-перечнями `219a55c`/`2deb287`); файл целиком волновой → whole-file; смешанный → хирургический стейджинг волна-хунков (`git apply --cached`; прецеденты ASAP-2.1 `web/index.html`, ASAP-3 35-файловый перечень); неатрибутированный хунок → эскалация. Композиция: **feat-коммит** = 8 untracked-сервисов + 9 тестов + UI-harness mca-17a + bump 2.58.36 + README; **(B)-skip** = `mca_gates.py`/`mca_retrieval_context.py`/`mca_events.py`/`token_counter.py` (уже на проде `2deb287`, blob `2623d81e…` == пину mca-07 — совпадение зафиксировано); **(C)** = `node_modules`/`package.json`/`package-lock.json`/`.playwright-mcp` — никогда (инфра стендов); `tools/asap2_*.png`×7 + `tools/asap21_*.png`×5 + `tools/_asap3_wth.py` — hygiene-часть docs-коммита **на месте** (ссылки `tools/…` в закоммиченных §101/§102/deployment.md не рвутся; конвенция ASAP-3: evidence-инструменты/скриншоты коммитятся); `plans/features/mca-04b…` — НЕ в релизе, живёт WIP до своего цикла. Верификация: staged-дифф == карте; чистый worktree: import OK + полный прогон **до push** (урок ASAP-3: композиционные `NameError: out_excluded`/`TypeError` ловились amend'ами до push).
Альтернативы: (1) коммит всего M-остатка одним файловым проходом — отклонено для смешанных (риск чужих хунков; нарушает (C)-границу); (2) тотальная хирургия всех ~99 M — отклонено (лишний риск повреждения там, где файл чисто волновой); (3) переезд скриншотов в архивные `artifacts/` — отклонено (архивы — исторические снимки, ссылки рвутся).

**D3. Политика частичного применения DDL v12→v19 (ответ (iii); spec §5).**
Выбрано: порядок **checkpoint → `VACUUM INTO` (free-space, read-back `integrity_check=ok`/`user_version`) → первая миграция**; жёстко: ни один новый шаг без прошедшего backup-гейта (per-step backup — допустимое усиление; drill фиксирует фактическую гранулярность). Шаг атомарен; после шага — ряд `schema_migrations` + новая `user_version` (инвариант: схема ⊇ версий ≤ `user_version`). Сбой на шаге k: **СТОП + алерт** (R17-safe лог + событие mca-13), `user_version=12+k` сохраняется консистентной, сервис стартует (приём сообщений не тушуется — mca-14 §3), default-ON фичи деградируют fail-soft; один идемпотентный повтор разрешён, далее диагностика; restore — не штатный механизм (ADR-1027-1 D6). `user_version` 13–18 = не-success: пост-деплой не проводится, fix forward. Success: `user_version=19` + книга ровно v13…v19 без дублей (checksum сверены) + повтор 0/0.
**Блокер-чек:** релиз-код не должен требовать v19 для старта — boot-drill на v12-копии с `MCA_SCHEMA_MIGRATIONS_ENABLED=false`; безусловная зависимость стартового пути от v13+ = блокер дизайна (эскалация владельцу; правка кодом запрещена — вне скоупа).
**Rollback-compat (честно):** БД v19 обязана работать с кодом v12 (аддитивность ADR-1027-1 D3/D6); drill на копии до деплоя. Фиксируются нюансы: аддитивные объекты после cold-отката остаются (безвредны, писателя нет); поведение legacy-пути старого кода при `user_version=19` **наблюдается и записывается** (в волне-0 чинился дефект «downgrade user_version» — самоочевидности нет). Провал drill → cold-откат деградирует до аварийного «revert + restore», ограничение фиксируется в гейт-отчёте до деплоя.
Альтернативы: продолжение применения после сбоя — отклонено (нарушает консистентность версии); авто-restore при сбое — отклонено (ADR-1027-1: restore аварийный); требование «успех только при одном рестарте» — отклонено (идемпотентный повтор — штатная сходимость).

**D4. Drift-политика и вердикт-правило теста mca-07 (ответ (iv); spec §6).**
Допустимо: документированные касания ASAP-треков (пины счётчиков/версий, конвенции, conftest-фикстуры) + присвоенные фичами изменения. Ре-ревью: семантика кода фичи вне её финального ревью (per-file → при затрагивании поведения — срез фичи). **Правило mca-07 (шаблон для любого drifted-файла):** (1) пересчёт sha256 (исключить устаревшую находку); (2) статический инвентарь тест-имён текущего файла против архивного эталона (focused **43 passed**; evidence: 34→43, `test_mca07_reason_codes_registered`, `test_mca07_kill_switches_registered_and_default_on`; файл untracked — архивный инвентарь единственный эталон, принимается как данность); (3) классификация дельты: ASAP-пины/фикстуры vs семантика; (4) инвентарь == 43 и дельта ⊆ пины → **допустимо с фиксацией**, релизный пин `92bfa016…`; иначе → **re-review файла в T-4045**; (5) контроль: focused == 43 passed.
Альтернатива: трактовать любой хэш-дрейф как блокер — отклонено (все касания ASAP-релизами статистически неизбежны: 3 релиза поверх дерева; правило разделяет классы дельты по доказуемому инвентарю).

**D5. PG-only сид — отказ от шага (ответ (v); spec §7).**
Подтверждено фактами: Δ каталога = 0 во всех 8 строках metrics; флаги env-only `ClassVar`; `rg "PG-only"` по 8 архивам — 0. Известная проблема касается ASAP-2 ключей (remediation 2.58.33 применена; системный фикс — follow-up вне скоупа). Шаг сида в ранбуки не включается.

**D6. Состав и форма гейта/ранбука.**
Чек-лист гейта — 10 пунктов (spec §3); F8-шум frozen-hash пинов — только поимённый фиксированный набор (ASAP-2.1: 4 пин-теста; ASAP-3: `TestFrozenInvariants::test_ddl_source_unchanged`/`test_routes_file_unchanged`, срез 525/2), рост набора = блокер, на проде не воспроизводится. Полный pytest сравнивается со свежим прогоном на анкере `8bd1389` (известные WIP-классы — поимённо, вне дельты). DDL-ранбук — табличная форма 9 шагов (spec §5.4), каждая строка «факт + вердикт», любой ❌ → СТОП.

**D7. Risk R3 ратифицирован** (DDL на проде, смешанные хунки, рестарт прода). Триггеры понижения — у @Reviewer после гейта. Реестр по задачам — spec §8.

**D8. Ownership верификаций:** гейт — @Reviewer (T-4045); композиция/чистый worktree — @Builder (T-4046); DDL/деплой — @DevOps (T-4047/4048); rollback-готовность — @DevOps+@Reviewer (T-4049); сверка spec↔tasks — @PM (T-4044, список расхождений spec §12).

## Последствия

- Доставка авторизуется только гейтом по D1; approval привязан к новому WTH+пинам, любое изменение после — stale.
- Композиция воспроизводима и проверяема на чистом checkout; (C)-граница защищает прод от инфра-шума и чужих WIP.
- Прод поднимется на v19 с доказанными (drill'ом) путями отката soft/cold и честно зафиксированными ограничениями cold-отката.
- Долг: невоспроизводимость исторических WTH остаётся данностью — компенсируется релизными пинами; системные F8-пины и PG-only сид — backlog follow-up.
