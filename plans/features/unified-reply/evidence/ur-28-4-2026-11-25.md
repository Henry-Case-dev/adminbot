## Что реально отсутствовало

Планировщик, per-chat слоты 00/06/12/18, claim и `next_due_utc` уже были
(UR-28/28.2/28.3/28.5). Ручной `/summary` уже шёл через
`SummaryGenerator._llm_generate` → `chat_clock.snapshot(chat_id)` (чатовая зона),
но это не было закреплено отдельной проверкой. Отсутствовала UI-поверхность:
read-only payload `/api/config/time` не отдавал следующий плановый запуск, в
шапке модуля «Саммаризация» не было строки «Плановый запуск».

## Реализация

1. `web/api/routes.py`
   - `_build_time_state(..., now_utc=None)` — инъекция мгновения для
     детерминированных проверок; прод-вызовы не передают.
   - `_summary_schedule_state(chat_id, snap, now_utc=...)` — аддитивный блок
     `summary_schedule` в существующем read-only `GET /api/config/time`:
     - `timezone` = эффективный пояс **чата** из того же ChatClock-снапшота;
     - `next_run_utc` = ближайший будущий слот (`slot_claims.next_due_utc`);
     - `next_run_local` = `DD.MM.YYYY HH:MM` в поясе чата (сервер считает
       ZoneInfo, клиент зоны не пересчитывает);
     - `slots` = фактическая шкала планировщика `SLOT_TIMES`;
     - `enabled`/`enabled_source` = единый per-chat резолвер
       `summary_effective_enabled` (честно показывает выключенные сводки);
     - ЛС (`chat_id > 0`) — `next_run_utc`/`next_run_local` = `null`,
       `enabled_source="dm_no_periodic"`: периодических сводок в ЛС нет
       (F-14, `SummarySchedulerService._tick` пропускает такие чаты до
       слотов), поэтому «плановый запуск» там не показывается;
     - глобальный скоуп (`chat_id=None`) — `null` (у расписания нет
       «глобального следующего запуска»).
   - Нового endpoint/таблицы/флага/настройки/миграции нет.

2. `web/app.js` + `web/index.html`
   - `loadSummarySchedule()` читает тот же `/api/config/time?chat_id=…` при
     открытии модуля, deep-link и смене чата; ответ применяется только к
     своему чату (`_chatBound`/`_payloadChatMatches`).
   - В шапке модуля `mod_summary` (видна на любой вкладке) — отдельная строка
     `data-summary-next-run`: бейдж «Плановый запуск», локальные дата/время,
     IANA-пояс и явная пометка «ручной /summary его не сдвигает». Состояния
     `loading | ready | off | no_chat | dm_no_periodic | error` честные; при
     `enabled=false` показывается «плановые сводки выключены», а не выдуманное
     время.
   - Для ЛС — честная ветка вместо даты: бейдж «Личные сообщения» и текст
     «периодических сводок в ЛС нет — работает только ручной /summary»;
     элемент `data-summary-next-run-local` в ЛС не рендерится. Групповой чат
     рендерится как раньше.
   - Клиент не конвертирует зоны браузером (UR-29.2): печатает серверную
     локальную метку.

3. `tests/test_ur_per_chat_schedule.py` (новый)
   - ручной `/summary` (`manual=True`) получает answer-блок с зоной **чата**
     `Asia/Almaty`/`UTC+05:00`, при глобальном `Europe/Berlin` и заводском UTC;
   - payload `_build_time_state` при 12:00 UTC / `Europe/Moscow` отдаёт
     `next_run_local="15.07.2026 18:00"`, `next_run_utc="2026-07-15T15:00:00+00:00"`;
   - ровно один tz-источник в `summary_schedule`, нет `summary_timezone`,
     в каталоге нет второго ключа пояса саммари;
   - endpoint-проверка `GET /api/config/time?chat_id=…` через общий TMA-клиент;
   - глобальный скоуп не выдумывает следующий запуск;
   - `test_time_payload_dm_has_no_periodic_next_run` (B-1): ЛС не имеет
     `next_run_*`, `enabled=None`, `enabled_source="dm_no_periodic"`, при этом
     тот же момент/пояс группового чата даёт реальную дату — дискриминирующий
     контраст, а не «любой None»;
   - `test_time_payload_enabled_follows_per_chat_resolver` (N-1): явный
     `flags.summary_enabled=false/true` даёт `enabled False/True` с
     `enabled_source="chat"` — константа в `enabled` ломает тест.

## Конфигурация / инварианты

- Пояс — единственная каноническая цепочка ChatClock (`limits.chat_timezone` →
  legacy `limits.summary_timezone` → `GOODMORNING_TZ` → factory); нового ключа
  нет, `GOODMORNING_TZ` для саммари не вводился.
- `summary_schedule.timezone` — отображение уже действующего пояса, не вторая
  настройка; `enabled` — тот же per-chat резолвер, что использует планировщик.
- Ветка ЛС только не отдаёт `next_run_*` и помечает причину; слоты/claim/DST,
  семантика планировщика и поведение группового чата не изменены.
- Нет DDL/миграций, флагов, новых store/table, изменений slot-семантики.

## Остаточное / честные ограничения

- Не деплоилось и не мержилось; production-поведение не проверялось (по
  заданию).
- `next_run_local` — серверная метка на момент ответа; при смене пояса/чата UI
  перечитывает payload (кэша расписания нет).
- Для ЛС (`chat_id > 0`) периодических сводок нет (F-14). Ранее в этом файле
  было ошибочно записано, что «блок показывает расписание только для
  группового чата»: на candidate `b423fbccf` блок показывал ЛС выдуманную дату
  (находка B-1). Исправлено в `70ea7d8e7`: ЛС не получает `next_run_*`, UI
  показывает честный текст, ручной `/summary` остаётся доступен; групповой чат
  не изменён.
- UI-стаб подставляет DTO реестра модулей (в тестовом `/api/config` его нет);
  сам блок и загрузчик — настоящие `web/index.html`/`web/app.js`.
