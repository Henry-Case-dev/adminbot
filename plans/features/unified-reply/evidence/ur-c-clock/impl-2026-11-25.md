## 4. RED-доказательства

1. **Бюджет fallback-адаптера.** До правки (и в базе `6123a1469`) тест
   «щедрого» окна падал: `assert '[CAPACITY]' not in content` при бюджете
   `clock_tokens + 50`, т.к. после clock оставалось ~50 токенов, а
   evidence-floor 400 + plain 151 честно давали `fallback_window_exceeded`
   (UR-11b §3.5). Это дефект калькуляции теста, не контракта. Теперь бюджет
   = `clock+plain+evidence+20` (всё физически помещается): блок байт-в-байт,
   as_of сохранён, `[CAPACITY]` нет, `reasons == []`. «Тесный» кейс сделан
   детерминированным (`clock_tokens - floor - 3`): блока нет,
   `[CAPACITY]`, `fallback_clock_dropped` — раньше эта ветка не исполнялась.
2. **Матрица UR-RES-08.** Первый прогон матрицы: видео-контур вызывался без
   снапшота → `AssertionError: video assert 0 == 1`. После явной передачи
   снапшота с границы-хендлера — green. Мутация «убрать блок из контура»
   краснит соответствующую строку матрицы.
3. **URC-CLOCK-R1 (worker_budget).** С ревьюерским repro-стендом
   (per-chat legacy `limits.summary_timezone=Asia/Almaty`, global canonical
   `Europe/Berlin`) временный откат `services/worker_budget.py` к версии
   `0eba142e2` дал:
   `assert wb._chat_tz_name(CHAT_A) == "Asia/Almaty"` →
   `AssertionError: assert 'Europe/Berlin' == 'Asia/Almaty'`
   (ChatClock sync и `meme_initiative` в том же прогоне уже дали
   `Asia/Almaty`), т.е. тест красный ровно на втором резолвере. Файл
   восстановлен из байтовой копии (SHA256
   `9c4d7996fed6639ca104fd79d13e278406ce2a0c142fed3c4bc0d15ee0f4da6a`),
   тест green. В самом тесте оставлен статический RED-детектор:
   `_legacy_chat_tz_name` — копия снятой реализации, и утверждение, что
   `_chat_tz_name != _legacy_chat_tz_name` на этом стенде; возврат к старой
   цепочке роняет тест сразу.

## 5. Честные residuals / ограничения

1. **ЗАКРЫТО (oracle `tests/test_p0im_s6_fresh.py`):** тест
   `test_missing_chat_timezone_falls_back_to_named_default` фиксировал старое
   поведение `meme_initiative` (`name=UTC`, `source=utc_fallback`,
   `offset_seconds=0`). D2 прямо называет дефектом «`utc_fallback` **вместо**
   factory», поэтому после делегирования honest-результат стенда —
   `name=settings.SUMMARY_TIMEZONE` (`Asia/Yekaterinburg`),
   `source="global_legacy"` (слой legacy-global получает заводское значение
   через контракт `hot.get(key, settings-default)` R1), `offset_seconds=+05:00`.
   Ожидание теста обновлено на этот результат (названный пояс, НЕ
   `utc_fallback`, смещение = реальному offset зоны); продукт не менялся.
   Запись-проверка: `meme.resolve_timezone(CHAT)` и
   `chat_clock.resolve_chat_timezone_sync(CHAT)` дают ту же пару
   (`Asia/Yekaterinburg`, `global_legacy`). Прогоны: файл **12 passed**,
   связка с clock/route-матрицами **67 passed**.
2. **Уточнённые `skip_reason` для технических ног:** значения
   `technical_rerank`/`diagnostic_checkup`/`tool_host_turn` не передаются
   через `llm.generate`, т.к. `llm_client.py` заморожен §4. Такие вызовы
   пишут честные `clock_included=false`, `skip_reason=no_time_block` и
   `module/step` маршрута; `skip_reason=no_chat_id` реально пишется на прямых
   транспортных швах без чата. Дублирующую запись ради точного значения не
   вводил (два разных reason на один вызов — нечестная наблюдаемость).
3. **Stream:** помимо записи supervisor'а (`channel=stream`, верный chat_id)
   существует предсуществующая INS-TRACE-запись `llm_client`
   (`module=summary_stream`, `chat_id=None`) — файл заморожен, не менялся.
4. **Pre-existing падения (воспроизведены в `6123a1469`, не наши):**
   6 в initiative-наборах, 2 в `test_summary_generator.py`.
5. **Не проверено этим срезом:** deploy/postdeploy, реальный провайдер,
   effective production config — вне задачи Builder'а.
6. **URC-CLOCK-R1 — что реально изменилось в поведении (честно).** Для
   дефолтной конфигурации (ничего не задано) и для канонического per-chat
   `limits.chat_timezone` пояс `worker_budget` прежний — это закреплено
   отдельными тестами (`…nothing_configured_keeps_factory_zone` →
   `Europe/Moscow`/`global_legacy`; `…canonical_per_chat_override_keeps_zone`
   → `Asia/Tokyo`/`chat`). Меняется только то, что и было дефектом: чат с
   единственным per-chat legacy `limits.summary_timezone` (и, теоретически,
   конфигурация с явным env `GOODMORNING_TZ` без global-слоёв) теперь
   сбрасывает сутки image-лимита по тому же поясу, что ответы/инициативы.
   Это user-visible смена дня сброса для таких чатов — контрактная
   (UR-24.3/UR-25), не «сохранение прежнего поведения». На живой
   PG/проде не наблюдалось (без SSH); доказательство — in-memory слои
   (`read_override_sync`/`hot.get`), как и у ревьюера.
   `image_day()` в новом тесте напрямую не вызывается (зависит от «сейчас»,
   полночь зоны — недетерминированный край); проверяется зона, которую он
   потребляет (`image_timezone` = `_chat_tz_name`).
