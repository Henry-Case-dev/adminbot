## 2. T10-BOUNDARY: решение и аргумент

**Решение: `not_applicable` неверен. Требуется правдивый маркер частичной истории; это малая реализация, а не новая подсистема.**

1. **Требование источника буквальное.** §6.1 #10: «Ответ из видимой части **с честным указанием ограничения**». §3.4: «результат надо честно отражать как **недостаток контекста**». §3.5: Writer «в обычной информационной ветке … ответить … (или честно указать её границу)». Это не следствие, выведенное PM: три независимых места.
2. **Фактическое поведение.** В `T10.L2.json` user-часть (401 симв.) = `<Response_Plan>` + `<Recent_Messages>` (4 реплики) + `<Current_Question>`; ни маркера, ни слова об усечении. Ответ: «Обсуждали ремонт санузла…» — корректен по видимому, но подан как полный обзор. `build_l1_context` (`direct_l1.py:679-683`) рендерит окно без пометки; `_cap_context` (там же, 727-740) молча режет 20→10→5→0 строк; `get_window_messages` (`summary_memory.py:2698-2712`) ограничивает окно `SUMMARY_WINDOW_HOURS` × `SUMMARY_MAX_WINDOW_MESSAGES` и тоже не сообщает об этом. L2-контекст (`direct_chat_service.py:5505-5517`, `_build_global_context_parts` + soft target `CHAT_GLOBAL_CONTEXT_LIMIT`) историю тоже не помечает.
3. **Почему это не «угадывание» и не §8.7.** §8.7 запрещает новые `clarification_*`-подсистемы, классы-анализаторы, magic thresholds и квоты. Здесь ничего не анализируется: факт усечения **уже известен** коду из собственных параметров (временное окно, лимит сообщений, срез `_cap_context`). Передача этого факта — одна строка в существующей секции, без порогов и без нового компонента. Запрет §3.1 («не подменять неспособность самодельной эвристикой») не нарушается: эвристики нет.
4. **Канон уже готов принимать маркер.** `chat_prompts.py:515` (effective L2): «Если для содержательного ответа данных недостаточно, скажи о границе знания естественно, без технических подробностей внутреннего процесса»; `:521`: «Не публикуй … служебные метки» — значит маркер подаётся как данные, а в ответе называется обычными словами. Новый owner-facing текст промпта не обязателен на первом шаге.
5. **Цена и риск.** Реализация: маркер в L2-пакете (и, желательно, в L1-окне). Проверка: 1 L2-вызов на T10 с маркером. Если после маркера оговорки всё равно нет — это уже не «нет сигнала», а «нет инструкции», и тогда нужна одна узкая строка канона (решение владельца/Architect), а не закрытие строки.

**Итог:** строка остаётся PENDING, но решение принято — реализация маркера, не `not_applicable`. Формулировка «в проде evidence pack не помечает неполноту» в `binding-probe-r2.md` §3 подкреплена ссылкой на `prod-snapshot §2`, а §2 — про effective-промпты, не про состав пакета. Факт подтверждается кодом (§2.2 выше), но ссылку надо исправить.

## 3. T20 / T24: что именно не проверено и минимальный прогон

**T20 (2 вызова, максимум 3).** Литеральный сценарий «Запрос → уточнение(период) → «сегодня»» противоречит исправлению: канон не должен спрашивать период, поэтому цепочка не возникает (4 попытки прошлого лейна — `not_reproduced`). Заставлять модель задать период = воспроизводить баг. Минимальный корректный прогон сохраняет смысл #20 («короткий временной ответ применяется к исходной просьбе, а не считается новым запросом») на **легальном** обязательном предмете:

- вызов 1: `L1`: «Бот, скинь отчёт» (объект не назван) → ожидается `clarify=true` с узким target про отчёт;
- вызов 2: `L1` с историей «исходная просьба + реальный вопрос бота из вызова 1 + «сегодняшний»» → ожидается `clarify=false`, продолжение исходного действия (при необходимости вызов 3 — `L2` для текста).

Если вызов 1 не даёт уточнения, сценарий переформулировать (другой обязательный объект, сужаемый временем) и **зафиксировать переформулировку** в evidence: это адаптация внешнего сценария, а не подгонка кода.

**T24 (0 платных вызовов).** Покрыто `tests/test_asap2_clar_contract.py:513-546` (payload равен после нового экземпляра сервиса + перезагрузки истории). Не покрыто и не требует платного вызова: реальный рестарт процесса и чтение окна из БД — при желании закрывается read-only двухпроцессным прогоном `get_window_messages` + `build_l1_context` (0 LLM-вызовов) силами DevOps. Семантическое равенство текста не требовать (temp 0.7).

## 4. Ограничения методики, которые нельзя замалчивать

1. `results.md` §1–§2 называет T10/T18b «answered», но `class` в raw = `tool_use` (у T10 `capabilities_needed=[user_memory]`, у T18b — `statistics`). Это разные величины: `class` считает `probe_r2.classify` (по наличию capabilities), «answered» — человеческая метка «не спросил». Для T10 это значит: L2-текст получен на маршруте, которого в проде не будет (прод уйдёт в `query_chat_memory`). Вывод «не переспрашивает + не выдумывает» остаётся, вывод «прод отвечает так же» — нет.
2. T10a/T10b/P-OBJ2 — только план, без L2-текста. Для «полезности ответа» (§6.5) это половина доказательства; для «нет лишнего переспроса» — полное.
3. r2 L2-пакет упрощён (нет персоны/стиля/памяти/lessons, `protocol.md` §4). Для семантики уточнений допустимо, для «прод-текст байт-в-байт» — нет.
4. `binding-probe-r2.md` §4 (`CLAR-L2-ROLE`) ссылается на несуществующие L2-тексты tool-маршрутов; строку всё равно можно закрыть, но по другому основанию (§1).
5. Oговорка переноса модели: §6.1 #1–#9/#12 гонялись на `deepseek-v4-flash`, модель прода сейчас `deepseek-v4.1-flash` (совпали 11 планов). Не блокер, но и не полный перегон.
