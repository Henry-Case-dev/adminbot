## 0. Конечный продукт и границы

SELF-DIAG-01 превращает имеющийся чекап и обычные инструментальные ответы в доступ к **проверяемому состоянию самого Adminbot**. Пользователь может без специальной фразы спросить о любой подсистеме, сбое, истории релизов, собственных исходниках, железе VPS, задачах, памяти и интеграциях. Бот самостоятельно определяет, какие уже разрешённые инструменты применить, связывает лог с процессом, ревизией и кодом и объясняет найденное без выдуманных причин.

Особая команда **«чекап»** существует и сохраняется: это **единственная специальная лексическая команда для самодиагностики**. Не добавлять regex-фразы или словари с вариантами «что сломалось», «проверь здоровье», «покажи код», «дай промпт» и т. п. для запуска новых диагностических маршрутов. В остальном — семантическое решение модели через действующий механизм Tool Calling и контракты инструментов. Возможные исторически зарегистрированные алиасы/префиксы сначала инвентаризировать; **не расширять** и не использовать их как основу новых веток, совместимость существующего поведения оценить по тестам.

**Прозрачность по умолчанию:** внутреннее устройство, исходники, диагностические метрики, сведения о версиях, ошибках, архитектуре, работающих модулях, технических настройках *без секретных значений* не становятся закрытой информацией лишь потому, что относятся к серверу. Обычный пользователь должен получать максимально полезные сведения в рамках текущего чата.

**Ограниченные данные:** фактически действующие промпты доступны только владельцу и подтверждённым администраторам **своего** Telegram-чата при их явном запросе; настоящие API-токены, пароли, ключи, сессионные секреты, приватные ключи и аналогичные credential values **не выдаются в Telegram никому**, включая владельца и администраторов. Чужие личные сообщения, содержимое других чатов и чужие пользовательские данные не превращаются в общедоступный источник из-за расширенной диагностики.

**Выполнение:** только безопасное чтение. SELF-DIAG-01 не получает права автоматически чинить, деплоить, менять БД, выполнять произвольные команды, удалять файлы, делать git pull/checkout/reset, перезапускать сервис, писать PR или менять настройки.

### Явно не делать

- Нового LLM-агента, второго оркестратора, второго tool-loop, параллельного хранилища телеметрии, ручного словаря фраз-интентов, неограниченного shell/SSH, динамического Python/SQL от модели.
- Каскада Better Stack → journalctl; Better Stack **адресно удалить из чекапа**, не затронув внешние механизмы другого назначения.
- Второго промпта, переписывающего текущий пользовательский «Системный промпт чекапа», и второго стилистического Writer только для чекапа.
- Сокрытия технической информации от обычных пользователей исключительно из-за того, что запрос относится к «внутренностям сервера». Запрет основан на **классе данных, границах чата и наличии секретов**, а не на слове «сервер» или опасениях насчёт всех внутренних деталей.

## 2. Архитектура с одним источником диагностических доказательств

```text
                                    Telegram incoming message
                                              |
                    +-------------------------+----------------------------+
                    |                                                      |
            explicit "чекап"                                  any normal chat / reply
            existing handler                                    existing L1 / Tool Calling
                    |                                                      |
                    +-------------------------+----------------------------+
                                              |
                                  Existing tool / DI layer
                                              |
                              Shared Diagnostic Evidence Collector
                                              |
      +---------------+----------------+---------------+---------------------+
      |               |                |               |                     |
  local runtime    logs/events      active jobs     deploy identity    source_reader
  typed probes     local only       DB/memory      SHA + diffs         GitHub + local
      +---------------+----------------+---------------+---------------------+
                                              |
                          Typed DiagnosticEvidenceBundle + provenance
                                              |
                                 Server-side ACL / data shaping
                                              |
                   +--------------------------+--------------------------+
                   |                                                     |
             existing CheckupService                                existing Writer
             original owner prompt                                 regular conversation
                   |                                                     |
                   +---------------------- Telegram reply ---------------+

   Prompt readback is a SEPARATE authorized artifact endpoint: it does not
   become raw prompt data in the unrestricted diagnostic model context.
   Secret values never leave secret storage for conversation output.
```

### 2.1. Обязательные свойства

1. **Два входа — один collector.** Explicit «чекап» не обязан идти через общий LLM tool-loop, но получает те же структурированные факты, что `get_bot_health`. Нельзя реализовать новый функционал только для свободного Tool Calling.
2. **Один Writer на свой путь.** Explicit command использует действующий `CheckupService` и действующий промпт; обычная реплика использует Unified Writer. Они должны давать сопоставимый технический диагноз при одинаковом evidence, сохраняя свой стиль.
3. **Typed `inspect_runtime` (условное имя).** Один расширяемый read-only инструмент с `area`, `probe`, `scope`, `time_window`, `cursor`, аргументами конкретной зарегистрированной операции. Не плодить по одному LLM tool на команду Linux. Точное имя выбрать после реестрового аудита.
4. **`read_source_code` развивается, а не заменяется.** Для сторонних репозиториев — как прежде; для собственного — identity по repo URL + deployed SHA + приоритет разрешённого локального snapshot, если его целостность подтверждена.
5. **`investigate_incident` — сценарий, не сабагент.** Когда симптомы требуют расследования, уже существующий координатор инструментов обращается к нужным probes, собирает факты и отдаёт Writer. Не требуется дополнительная LLM-стадия ради самой стадии.
6. **Секреты фильтруются до модели и до Telegram.** Промпт-readback и секретные данные не кладутся в общий evidence-буфер и не кэшируются как публичные.
7. **Не завышать доступность.** `tool declared` ≠ `configured` ≠ `probe succeeded` ≠ `healthy`. Результат меняется от реальных измерений и их актуальности.
8. **Новый функционал глобально включён при первом релизе**, при отсутствии прав/источника сообщает `permission_denied`/`unavailable`; сохранённые пользовательские решения не сбрасывать.

## 3. Семантическое использование: никаких новых ключевиков

### 3.1. Единственная явная команда

- `«чекап»` остаётся специальным быстрым вызовом диагностики; в рамках этого проекта не создавать словари «синонимов чекапа» и регулярки для дополнительных выражений.
- Не добавлять hardcoded триггер «покажи промпт» — это обычное намерение пользователя, которое модель должна перевести в структурированный инструмент запрос/ресурс; сервер проверяет полномочия независимо от текста запроса.
- Не добавлять `if "сбой" in message` / `if "код" in text` / классификацию по массиву ключевых фраз. Модель выбирает capability по назначению и tool schemas; если не уверена — может прочитать доступный статус и уточнить смысл, а не выдавать догадку.
- Если пользователь спрашивает об игре, чужом репозитории или технической теории, не путать эти темы с диагностикой себя; использовать конкретный `repo`/контекст, а не автоматическое переключение на Adminbot по любому упоминанию «бот».
- Человеческие описания tools на английском могут пояснять возможные применения и границы, но **без regex-сопоставления запроса на backend**. Детерминированная проверка ACL и аргументов после выбора инструмента — не запретный «хардкод по ключевикам».

### 3.2. Смысловая маршрутизация

- Проверить, что инструменты технически доступны L1/Direct для обычной реплики, упоминания, reply; инициатива не должна автоматически получать повышенные права только потому, что инициирована ботом.
- Capability advertised только когда зарегистрирована и применима, а `ready` только после проверяемого успешного probe. Сведения о неполадке доставляются в `ToolResult` с reason code.
- Учитывать контекст беседы («а что с голосовыми?», «посмотри последнюю правку»), не требовать повторения ключевых слов.
- При явном «чекап» минимальные задачи collector детерминированы (логи/метрики/ревизия/commit metadata), независимо от решения LLM. Глубокое изучение файла — когда есть признаки сбоя или дополнительный прямой запрос.
- При выдаче собственно промпта использовать отдельный *типизированный ресурс* `prompt_readback` с надёжной проверкой `user_id` и `chat_id`, а не «давай модель сама решит, секрет это или нет».

## 4. Собственный репозиторий и точная ревизия production

**Repository URL:** `https://github.com/Henry-Case-dev/adminbot`.

- Канонический repo identity задаётся явно в конфигурации SELF-DIAG-01; не извлекать его из случайного сообщения чата, README или воспоминаний модели. Разрешать смену через админку/настройку владельца; событие смены логировать.
- Репозиторий **публичный на момент проверки**; `SourceReader` может использовать анонимное чтение, токен — только если действительно требуется (лимиты/дополнительные разрешённые источники). Токен не выводить в чат, даже если запросил owner.
- Сначала подтвердить `deployed_sha` работающего экземпляра и id образа/артефакта, затем определить `checkout_sha`, dirty-state и remote `HEAD`. Отдельно показывать `repo_origin`, `deployed_sha`, `local_source_verification`, `upstream_head`, `version_provenance`.
- Сравнение ревизий: нельзя выдавать код `master` или `HEAD` за текущий, если фактический процесс исполняет другой commit, бинарник, другой образ, либо рабочий каталог изменён после запуска.
- Чтение собственного кода: сначала проверенная локальная read-only копия/manifest, затем commit-pinned GitHub. Наличие исходников локально ≠ подтверждение тождества загруженному в память коду; честный статус `local_unverified` обязателен.
- При отсутствии SHA применить локальную идентификацию сборки, но не называть строки `verified_deployed_code` до получения доказательства.
- На **каждый explicit «чекап»** попытаться получить метаданные последних релевантных коммитов с ограниченным бюджетом; не тянуть весь repository tree и diff без потребности.
- При traceback/аномалии сопоставить время событий, установку релиза, изменённые файлы/символы, call chain и commit diff. Новейший commit не виновен просто потому, что он новейший.
- Код сторонних репозиториев продолжает читаться обычным `read_source_code` по явному repo/ref; не отправлять чужие вопросы автоматически на `Henry-Case-dev/adminbot`.
- Дополнительные данные можно получать через уже работающие GitHub / SafeFetcher методы, но не запускать исполняемый код из репозитория.

## 5. Датчики сервера и расширение технического доступа

Цель — максимальное **наблюдение**, а не максимальные права на изменение. Не ограничиваться CPU и парой WARN-строк. Предпочесть typed adapters к существующему процессу, systemd/container API, procfs/sysfs, штатным health и DB метрикам. Все операции — из реального среды с фиксированным способом измерения, временем и проверяемой границей.

| Категория | Набор наблюдений | Границы и нюансы |
|---|---|---|
| Состояние процесса | PID/PPID, uptime, start time, args в очищенном виде, RSS/USS при наличии, CPU%, threads, open FDs, FD limit, task backlog, рестарты, exit reason | `cmdline` может содержать секреты — выдавать типизированные поля, не raw argv |
| CPU/память | cores, load average, CPU utilization/steal при наличии, RAM/swap, cgroup limits, PSI pressure, OOM kills, memory high watermark | различать host и container, не вычислять ложную точность по одному snapshot |
| Диски | объём/свободное, inode exhaustion, mountpoints, device I/O, read/write latency при наличии, том БД, WAL, tmp, logs | не только `/`, поддержка read-only mount и container volumes |
| Файловые дескрипторы / сокеты | число открытых FDs, лимит, сокеты процесса, состояния соединений, DNS failures, TCP errors, listening sockets только своего процесса | не раскрывать auth-headers, payloads, tokens и чужие sockets |
| Локальные логи | journal текущего unit, контейнер stdout/stderr, локальный файл через logging backend; INFO/WARN/ERROR, traceback, time windows, correlation IDs | источник сопоставлен с собственным процессом, лог-файлы не читаются произвольно |
| Systemd/контейнер | actual unit/container identity, state, invocation ID, start/restart counters, last exit code, OOM/system events | если средство отсутствует — `unsupported`, не `healthy` |
| Планировщик | TaskSupervisor, schedules, skipped/late/failed/succeeded, lease, дедлайны, блокировки, orphaned/pending jobs | текущий `next_run` и `last_success` не путать с «выполнено» |
| Доставка Telegram | ingress/queue, accepted, rejected, send error, rate limit, bot output ledger, duplicate retries | только данные текущего разрешённого чата либо обезличенная глобальная техническая агрегация |
| STT/vision/медиа | очередь, provider, transcription status, album cohesion, last success/error, cache hit, timeout, payload metadata | не раскрывать приватные аудио/изображения других чатов |
| LLM/инструменты | provider/model, error type, retry, latency, token use, tool offered/called/success, partial/degraded outcomes | без prompt bodies и raw provider request headers |
| Память/GraphRAG | базы, FTS/vec health, archive stats, provenance, retrieval purposes, ошибки, stale rebuild, memory communities | использовать существующие memory health, не поднимать новый граф |
| БД | SQLite/PG connectivity, DB locks/waits, WAL size, disk pressure, schema/version, failed migrations, readonly quick-check по требованию | не выполнять произвольный SQL; expensive integrity checks отдельно, с бюджетом |
| Конфигурация | selected/effective flags, overrides, updated_at, applied_at, source of truth, pending restart | значения секретов не показывать; названия настроек и не-секретные значения прозрачны |
| Деплой | app version, commit SHA, build ID, branch, dirty state, migration/schema, deploy/boot time, upstream diff metadata | не путать code in repo с реально исполняемым кодом |
| Зависимости | Telegram, LLM, STT, поиск, GitHub, QRNG, БД, storage и иные сервисы, которые реально подключены | `configured` ≠ `live`; никаких вымышленных «онлайн» |
| Сеть | DNS resolution, TLS error, endpoint health только уже настроенных сервисов, latency, connection reset | никаких произвольных host scan, port scan, raw proxy credentials |
| Инциденты | first/last observed, correlated log/error, affected component, regression timing, evidence references, unresolved reason | не создавать новый инцидент из каждого совпадения слова error |

**Расширяемость:** подмодули регистрируют typed `DiagnosticProbe` по существующему реестру, каждый предоставляет контракт, статус и разрешённую область чтения. Не требуется править центральный код всякий раз, когда появляется новый сервис. Единый `inspect_runtime` может перечислять доступные области и запрашивать одну/несколько узких проверок по фактическому запросу.

**CPU/IO измерения:** для delta-метрик требуется два реальных наблюдения/системный агрегат; по одному измерению отдавать текущие счётчики, не «вычисленные» проценты. Процесс мониторинга не должен сам создавать заметную нагрузку.

**Самодиагностика мёртвого процесса:** если единственный экземпляр бота полностью остановился, отвечать в Telegram он не может. В пределах эпика предусмотреть existing external watchdog/monitor integration или правдивую post-restart реконструкцию, а не обещать, что упавший процесс ответит на вопрос.

## 6. Прямые логи, удаление Better Stack и переносимость VPS

### 6.1. Новая политика источников

- Better Stack целиком удаляется **из checkup-related runtime/настроек**. Не оставлять его первым источником, теневым fallback, «подключено, но не используется», устаревшей кнопкой или мёртвым credentials-path.
- Новая цепочка: **идентифицировать собственный процесс и способ запуска** → выбрать доступный локальный runtime log backend → подтвердить принадлежность журнала этому экземпляру → считать ограниченное окно событий → связать с event ledger. Это не означает «journalctl всегда».
- **systemd:** обнаруженный актуальный unit/invocation; вызов фиксированным argv через `create_subprocess_exec` или безопасный API без shell; unit не вычислять из свободного текста LLM. Поддержать override, но отображать и проверять, чем он реально оказался.
- **container:** собственный stdout/stderr или адаптер доступного container log backend; не предполагать наличие journalctl в контейнере.
- **standalone:** файл/stream собственного процесса, либо существующий ring buffer/event ledger. Если нет права доступа — честный отказ и частичная диагностика на иных источниках.
- Проверить log rotation, рестарты, смену hostname, разные версии unit, несколько копий бота, старые инстансы на VPS, пустой журнал, доступность только INFO и отсутствие ERROR. Пустой корректно считанный журнал не равен «сервис здоров».
- Не выполнять произвольные shell-команды, даже если запрос написан администратором. Для глубоких probes — зарегистрированные операции на уровне ОС с лимитами и исчерпывающим журналом вызова.

### 6.2. Точечная очистка Better Stack

Перед удалением составить inventory по живому HEAD: `services/system_logs_fetcher.py`, `CHECKUP_BETTERSTACK_SQL_*` в `config/settings.py`, config catalog/hot config, API backend read/write, UI карточки/поля, tests, fixtures, docs, DI/bootstrap, старые креды. По каждому вхождению пометить владельца: **checkup-only** или **used elsewhere**.

1. Удалить чекaпный HTTP SQL-клиент, retry/error paths, конфигурационные поля, credential reader, UI-формы, описания, мёртвые каталожные ключи и недостижимые тестовые ветки.
2. Заменить устаревший fallback на portable local collector; по возможности сохранить существующие интерфейсы с аккуратной совместимостью и обновить tests/pins.
3. Удаление сохранённых Better Stack secret values — только после доказанного отсутствия других потребителей и безопасного бэкапа/точной миграции, не очищать всю таблицу секретов. Исторические релизные записи не переписывать.
4. Не удалять библиотеку `httpx`, глобальное observability, отправку уведомлений или другие источники только по совпадению слова Better Stack.
5. В отчёте предъявить список удалённых checkup вызовов/полей, сохранённых сторонних интеграций, **0 сетевых запросов к Better Stack в реальном checkup runtime**, а также результаты прямого чтения после переезда VPS.

### 6.3. Конкретный portability-дефект

В проверенной конфигурации существовал `CHECKUP_JOURNALCTL_CMD` со значением `journalctl -u admin_bot -n 300 --no-pager` и `create_subprocess_shell(...)`. Перестроить источник по фактической среде: process identity/cgroup, контейнерные метаданные и release manifest, прежде чем читать лог. Текущий unit может называться иначе, после миграции старый `admin_bot` не должен порождать ложное «ошибок нет».

## 7. Политика доступа: прозрачная инженерия, закрытые промпты и абсолютный запрет выдачи credential values

**Старое правило черновиков «подробная диагностика только владельцу/в DM» ОТМЕНЕНО.** Вместо него действует классовая политика ниже. Внутренние сведения о системе — не секрет сами по себе. Основа разрешения — субъект Telegram, конкретный chat scope, ресурс и тип данных. Не массив запрещённых слов, не угадывание «админ» по сообщению, не проверка моделью.

### 7.1. Роли

- `public_user`: любой участник, запросивший информацию в текущем чате или личном диалоге.
- `chat_admin`: реальный администратор/создатель именно текущей группы. Проверять **числовой Telegram `from_user.id`** и `chat.id` через Bot API `getChatMember`; только статусы `administrator`/`creator`, а не имя, username, должность, самоописание или пересланная цитата.
- `project_owner`: настроенный в существующем контуре владельца numeric Telegram ID, проверенный сервером; не отождествлять автоматически с первым в списке админов Telegram.
- `anonymous_admin`/`sender_chat`: если Telegram не предоставляет удостоверяемый `from_user.id` и связь с конкретным администратором, право на выдачу промпта **не возникает**. Не пытаться угадать владельца сообщения канала.

**Техническая предпосылка:** Telegram `getChatMember` для других пользователей гарантирован, когда бот администратор группы. При отсутствии этого права или ошибке API — статус `auth_unverified`, отказ только в *protected* readback, но **не** в общедоступной диагностике. Проверку статуса делать в момент авторизованного запроса (нельзя полагаться только на старый TTL); инвалидация по изменениям членства допустима как оптимизация, но не замена online проверки.

### 7.2. Уровни данных и матрица

| Data class | Примеры | Обычный участник | Админ этого чата | Владелец |
|---|---|---|---|---|
| `PUBLIC_TECH` | работа сервиса, версии, код публичного репозитория, список ошибок, аптайм, метрики CPU/RAM/disk, модули, техническая архитектура | **Да** | Да | Да |
| `CHAT_SCOPED` | технические события, относящиеся к текущему чату, исходы jobs, сведения о собственных сообщениях | **Да** в своём scope | Да в своём scope | По разрешённому проектному scope |
| `PROMPT_CONTENT` | эффективный пользовательский редактируемый промпт текущего чата, включая наследуемую глобальную версию, которая *действует именно здесь* | **Нет** | **Да, по явному запросу** | **Да, по явному запросу** |
| `OTHER_CHAT_DATA` | чужие сообщения/данные/эффективные промпты другой группы | Нет | Нет | Только если исходный проектный owner scope разрешает, иначе нет |
| `SECRET_VALUE` | API-ключ, токен бота, DB пароль, session cookie, приватный ключ, содержимое credential-файла, signing secret | **Никогда** | **Никогда** | **Никогда через чат** |

- **Администратор вправе явно опубликовать промпт в своём групповом чате.** Если идентичность и полномочия подтверждены и он просит действующий промпт, бот может ответить **прямо в группе**, без обязательного перенаправления в DM и без лишнего повторного согласования: сам запрос авторизованного администратора — действие по раскрытию этой группе. Записать `disclosure_actor`, `chat_id`, `prompt_id`, `revision`, `destination=group` в безопасный audit-log.
- Обычный участник при запросе промпта получает короткий отказ по отсутствию прав, **не фрагмент промпта** и не список тайных инструкций. Он при этом не теряет доступ к информации о работе, логике и технических метриках.
- Админ группы A **не** получает промпт группы B, чужой персональный архив либо непредназначенные этому чату служебные инструкции, даже если вводит точный `prompt_id`. Глобальный effective-параметр можно раскрыть только в том объёме, в котором он действительно применяется к чату A.
- Владелец может запросить собственный разрешённый промпт из группы, где он пишет от своего проверенного аккаунта. Утверждение «я владелец» не считается доказательством.
- Не выдавать секреты под видом настройки, исходника, лога, env, конфигурационного «сыpого файла», diff или части промпта. Возвращать для секретного поля только `configured/not_configured`, masked fingerprint при необходимости и health status.

### 7.3. Не смешивать разные виды «секретности»

- **Содержимое пользовательского промпта** — protected resource, которое сервер может авторизованно вернуть админу. Это отдельный тип доступа, а не `SECRET_VALUE`.
- **Значения credentials** — недоступные в output данные при любом статусе роли. Уровень `project_owner` может управлять ими через предусмотренную админку, но не получать обратно текст ключа из Telegram.
- Если промпт по ошибке содержит credential value, отдавать его даже админу *только с удалённым/замаскированным фрагментом*, статусом `partially_redacted` и предупреждением, что исходный prompt содержит риск. Не выдавать всё «ради точного readback».
- Заводские промпты или инструкции, **уже опубликованные в публичном GitHub-репозитории**, технически публичны. Нельзя обещать их абсолютную секретность через чат-ACL. Защищать в первую очередь **фактические активные и вручную сохранённые значения**; при желании действительно закрыть заводские тексты — отдельная задача о публичности их хранения, не скрытие кнопки.

### 7.4. Серверный enforcement

1. Auth principal берётся только из Telegram update, не из tool args или user text; `user_id`/`chat_id` не могут быть произвольными параметрами модели для повышения прав.
2. Набор разрешений вычисляет существующий авторизационный сервис / policy layer: `(authenticated_actor, chat_scope, resource_class, resource_scope, action, destination)` → `allow|deny|unverified`, с машинным `reason_code`.
3. Проверка происходит **до чтения защищённого ресурса**, **перед формированием результата инструмента** и **перед отправкой**; предотвращает stale cache, race с отзывом прав, подмену reply/forward и публикацию недопустимого объекта.
4. Решение не принимает LLM. Model tool arguments только выражают пользовательский запрос и ресурс; исполнитель игнорирует попытки передать себе новую роль.
5. Защищённый результат имеет собственный auth context, не попадает в public cache, memory, лог, безграничную историю инструментов или reuse между чатами/пользователями.
6. Отказ по protected readback не отключает другие read-only probes и не превращает всю диагностику в «доступ только владельцу».

## 8. Ресурс `prompt_readback`: как реально выдавать промпты

**Решение:** использовать существующий единый реестр промптов и его resolver + versioning. Не делать дублирующее хранилище, копию текста в самодиагностике, отдельный CRUD или скрытую систему «секретных подсказок».

### 8.1. Разрешение запроса

- В обычном чате модель по смыслу понимает, что человек просит действующий промпт, и формирует типизированный tool request: `resource_kind=prompt`, `scope=current_chat`, `prompt_selector` (если нужен), `requested_revision=effective|specific`, `delivery=reply`.
- Для неясного имени промпта — поиск существующей библиотеки и, при необходимости, **один** уточняющий вопрос. Не выбирать чужой промпт наугад.
- Если промпт наследуется из глобальных настроек, возвращается именно **effective** значение для текущего чата с метаданными `source=global_inherited`, `version_id`, `effective_at`, без чтения произвольных чужих override.
- Текст не должен проходить через обычную LLM-вербализацию. Предпочтительная выдача — **сервером непосредственно как экранированный текст / документ**, связанный с конкретным подтверждённым auth context. Так исключается перефразирование, случайная утечка из prompts других чатов и двойной вывод.
- Если ответ длиннее Telegram message limit, отправить целиком через chunked plain text либо текстовый документ. Не усекать молча. Имя/описание файла не должно раскрывать секреты.

### 8.2. Логика прав на этапе чтения

```text
request -> verified Telegram principal -> chat role lookup / project owner
        -> resource scope resolution -> prompt registry effective resolver
        -> secret-value projection / redaction -> outbound authorization
        -> exact typed artifact delivery -> audit metadata
```

- Для `public_user`: `denied`, без первоначального обращения к содержимому промпта.
- Для `chat_admin` и `project_owner`: только разрешённый prompt scope; если в группе админ сознательно сделал запрос, доставка в эту группу разрешена.
- Если Telegram временно не позволяет проверить админство: `auth_unverified`; *не* считать пользователя обычным или админом по тексту, предложить повторить позже либо использовать существующий подтверждённый интерфейс админки.
- Если в результате проверенной редакции отсутствует пользовательский override — честно показывать inherited factory/effective и соответствующую версию. Не создавать новую ревизию из-за чтения.
- Если промпт/часть его содержимого уже присутствовали в логах или выводе модели, это **не** повод полагать, что защита работает. Тестировать действительный endpoint readback и эксфильтрацию через соседние инструменты.

## 9. Защита credential values без keyword-массивов и без самоуспокоения

Требование владельца «ключи и пароли не отдавать ни при каких условиях через чат» исполняется **архитектурой данных, правами и выходным контрактом**, а не массивами русских/английских слов «пароль», «секрет», «token», «api key», которые можно обойти перефразированием.

### 9.1. Типизированная модель данных

- Источник истины о секретных полях — конфигурационный каталог/secret store с **типами и флагом sensitivity**: `SECRET_VALUE`, `PROMPT_CONTENT`, `NON_SECRET_CONFIG`, `PUBLIC_DIAGNOSTIC`. Для нового провайдера метаданные sensitivity обязательны при регистрации.
- Секретный blob никогда не сериализуется в DiagnosticEvidenceBundle или обычный ToolResult. При технической проверке возвращаются `configured`, `effective`, `last_success`, `last_error_code`, `key_fingerprint` (только если уже безопасно принят проектом), но не value.
- Файлы credentials и конфигураций с конфиденциальными значениями не отдаются в инструмент чтения файлов ни при каком scope; безопасные поля берутся через typed settings adapter, не через `cat .env`.
- `read_source_code` не должен возвращать приватные локальные config/secrets paths, backup/dumps, `.git` objects с авторизационными данными и полный environment. Public GitHub может содержать уже опубликованные чувствительные строки — они требуют дополнительной output policy, а не автоматического признания «всё публично, значит можно».
- Логи, traceback, произвольные строки ошибок и комментарии к коду — **недоверенные потенциальные носители утечки**. Перед публикацией предусмотрен **общий структурный sanitizer/redactor** с источниками известных runtime-секретов, форматом typed output, пределами и fail-closed для high-risk raw contents.
- Pattern/heuristic обнаружение случайно попавших секретов можно применять **дополнительно**, но не как единственную защиту. Это не keyword-маршрутизация намерения и не black-list фраз.

### 9.2. Изоляция выходного канала

- Для protected data использовать server-side output projection по role/scope, а не просьбу «не показывай секрет» в prompt.
- Перед реальной Telegram-отправкой выполнить output validation; если безопасность вывода нельзя гарантировать — заменить **только опасный фрагмент/ресурс** на редактированный вариант или честную ошибку. Не выключать весь чекап.
- Исключить секретные значения из caching, traces, debug requests, tool call arguments, retries, structured exception messages, source references и HTML/Markdown preview.
- Удаление доступа к секретам не требует скрывать названия настроек, факт наличия ключа, состояние API или причину `auth_failed`; эти технические сведения остаются прозрачными.
- Регрессионные тесты специально проверяют, что token/private key не появляется ни в raw tool results, ни в ответах, ни в файлах, ни в error path, ни при prompt-readback администратора.
- Не вводить общую маску на весь исходный код: безосновательное сокрытие модулей снижает прозрачность. Защищать значения секретов и реально закрытые источники.

### 9.3. Отдельный риск: промпт уже находится внутри контекста LLM

Даже если сервер **не** выдаёт `PROMPT_CONTENT` через инструмент, обычная LLM может видеть свои действующие system/developer/personalization instructions, поскольку они переданы ей для генерации ответа. Нельзя обещать криптографически надёжную конфиденциальность такого текста только с помощью запрета `prompt_readback`: prompt injection, цитирование и косвенное восстановление остаются предметом отдельного контроля.

**Обязательные меры:** не включать тексты редактируемых админских промптов в публичные инструменты и журналы; не давать LLM читать полный реестр версий, если она не авторизована; отдельно тестировать прямое цитирование, пересказ, продолжение строк, кодирование, role spoofing, многоходовые запросы и эксфильтрацию через внешние tools. Выходные правила и санкционированная доставка должны проверяться реальным сервером. Если необходима **строгая секретность самого текста**, архитектор обязан обозначить пределы использования этого текста как инструкций для неавторизованной LLM и предложить минимизацию/изоляцию чувствительных частей без изменения действующего пользовательского промпта в рамках этого эпика. Не записывать «100% защищён» по результату нескольких тестов.

## 10. Достоверный контракт диагностических доказательств

Описать один сериализуемый `DiagnosticEvidenceBundle` (логический контракт; можно использовать существующий evidence type, а не создавать ненужную таблицу):

```json
{
  "request_id": "opaque-correlation",
  "chat_scope": "current-chat",
  "runtime": {"service_identity": "verified|unknown", "deployed_sha": "...|unknown"},
  "sources": [
    {"kind": "local_logs", "status": "ok", "observed_at": "ISO-8601", "source_id": "...", "latency_ms": 12, "coverage": "partial|complete", "reason_code": null},
    {"kind": "source_code", "status": "not_checked", "reason_code": "no_relevant_error", "verified": false}
  ],
  "claims": [
    {"kind": "observed", "statement": "technical fact", "evidence_refs": ["..."]},
    {"kind": "hypothesis", "statement": "possible cause", "evidence_refs": ["..."], "limitations": ["..."]}
  ],
  "redaction": {"performed": true, "redacted_fields": 0},
  "not_checked": ["..."],
  "access": {"resource_scope": "current_chat", "projection": "public_tech"}
}
```

**Это схема-пример, не приказ вводить вторую БД или copy-paste поля в другой несовместимый контракт.** Конкретная версия должна быть согласована с existing `mca_events`/source_refs и способна отображать:

- `observed_at` — время измерения, а не время генерации ответа;
- `source_id` и истинный owner (journal current unit, system probe, SQL read-only, GitHub commit);
- `scope` — текущий chat/host/instance, нельзя по ошибке читать чужие чаты;
- `status`: `ok`, `degraded`, `unavailable`, `permission_denied`, `not_configured`, `stale`, `unsupported`, `unknown`, `not_checked`;
- `coverage` — какие части лога/кода/окон реально проверены, где обрезка, почему;
- `runtime_sha`, `git_head_sha`, `source_verified`, `commits_since_deploy` (только если можно посчитать); `git_metadata_attempted` и `code_lookup_attempted` отдельно;
- `observed` / `correlated` / `hypothesis` / `unknown` / `not_checked`, никаких принудительных «уверен на 95%» без калибровки;
- `redaction_count` по техническому классу, `permission_decision` (без secret values), `latency_ms` и `reason_code`.

Сохранение причинно важного фрагмента traceback: не обрезать его тупо по первым N символам, выделять stack summary и доступные фрагменты с источниками, поддержать страницы/continuation по budget. Не отправлять целые гигабайтные логи в модель.

## 11. Инцидентный сценарий и качество причинного вывода

**Пример запроса:** «После обновления перестал обрабатывать голосовые. Почему?»

1. Семантический Tool Calling выбирает существующий diagnostic capability; backend удостоверяет chat scope и даёт доступ к техническим данным.
2. Получить фактический runtime, время деплоя и версии, входящие voice-сообщения, STT queue, last success/error, latency, provider status.
3. По correlation IDs найти конкретные таймауты и стадии; проверить, не остановился ли scheduler или не отключён ли effective flag.
4. Если признаки ошибки действительно ведут к коду, найти отвечающий файл, функцию и вызывающий участок. Сверить с **deployed** SHA, затем проверить релевантные изменения между релизами. Не обвинять commit, ещё не развернутый на VPS.
5. Writer объясняет наблюдения, связь и гипотезу; если код не прочитан/нет прав/429 — так и пишет. Никакого «я заглянул в кишки» без подтверждённого чтения.
6. Если всё исправно, вывод может быть язвительным, но не выдумывает падение только ради стиля.

**Другой пример:** обычный пользователь спрашивает «А как устроена твоя память и почему она забывает людей?». Бот может свободно объяснить структуру GraphRAG, memory store, алгоритмы retrieval, показать ссылки на публичный код и технические метрики, не требуя статуса администратора. Если следующий вопрос — «дай действующий системный промпт», сервер ограничивает readback по ACL, но бот не отказывается обсуждать техническое устройство памяти.

## 12. «Чекап» и неизменность характера

### 12.1. Неприкосновенность редактора

- `prompts.checkup_system_prompt` и все пользовательские правки сохраняются **байт-в-байт**. Не менять factory version, активную ревизию, «жанр отчёта», систему контроля версий, дедуп / историю, не создавать новую запись сохранения при простом деплое.
- Сохранить язвительный, грубый, при необходимости матерный «разъеби» по действующему промпту. Проверять характер на реальных ответах: никаких шаблонных канцелярских таблиц вместо живого текста. Не делать дополнительных «смягчающих» system prompt или перефразирования после checkup LLM.
- Все ограничения защищённых ресурсов осуществляются в backend и sanitization слоях; не менять стиль речи ради того, чтобы «повысить безопасность».
- Телеметрия: `prompt_version_used`/hash effective prompt, `diagnostic_bundle_delivered`, `bundle_truncated`, `report_sent` — без записи самого содержимого промпта.

### 12.2. Поведение explicit «чекап»

- Сохранять existing reply, cooldown, реакцию, показатели занятости и доступность bare команды; не задерживать ответ бесконечным поиском коммитов.
- При каждом вызове прочитать доступный локальный лог, метрики реального процесса и памяти, job statuses, deployed identity и попытаться получить ограниченные commit metadata.
- Если есть ошибка — углубиться в относящийся код. Если явных ошибок нет — не читать весь репозиторий ради галочки; честно указать краткие результаты текущего здоровья и версию.
- При отсутствии одной части evidence отвечать по остальным, оставив `partial`/`not_checked`; не изображать все источники работающими.
- Вызов при неверифицируемом chat admin из группы **не блокирует обычный чекап**, только защищённый prompt readback.
- Команда «чекап» не становится командой «покажи промпты». Раскрытие промпта — отдельно установленный явный смысл запроса и авторизация.

## 13. Админка и аналитика

### 13.1. Модули → Диагностика

- **Обзор:** реальные status/probe источников, last observed, runtime type, PID, uptime, deployed_sha, log backend identity, GitHub code-check state, last successful analysis, summary of missing evidence.
- **Основные настройки:** ограничители probes и ожидания, объёмы страниц/временных окон, лог backend override при необходимости, repository URL, connection status, тип runtime, статус read-only доступа; все изменения отражают effective состояние.
- **Промпты:** текущий редактор и единый контроль версий, содержание не перезаписывать и не менять стилистику.
- **Модели/Лимиты:** совместимые текущие параметры; новый набор не должен дублировать каталоги и source of truth.
- **Better Stack:** удалить checkup-only поля, креды, карточки, индикацию соединения, ссылки помощи; сохранить остальные реальные интеграции проекта.
- **Матрица доступов:** компактное отображение прав к `PUBLIC_TECH`/`CHAT_SCOPED`/`PROMPT_CONTENT`/`SECRET_VALUE` и состояний `Telegram role verified/unverified`, без открытого текста credentials. Возможность пересмотреть аудит запросов без содержимого защищённых данных.

### 13.2. Статус

Отдельный визуально связанный блок «Самодиагностика»: snapshot работающей системы, распределение отказов по компонентам, source status, активные задания, CPU/RAM/disk + давление, degraded integrations, source-code correlation, deployed vs upstream, число непроверенных источников. Строки кликабельны: показывают время, источник, lineage и разницу между фактом/гипотезой.

### 13.3. Аналитика

- `checkup_triggered`, `get_bot_health_called`, `inspect_runtime_called`, `read_source_attempted`, `read_source_verified`, `code_unavailable`, `prompt_readback_requested/allowed/denied`, `secret_value_disclosures=0` (не выводить зелёное значение без измеренного enforcement);
- latencies p50/p95 по probes и по полному чекапу; % partial vs complete, отказ по каждому backend; частота retry, cache hits и stale reads;
- реальные инциденты по подсистемам, доли `observed` vs `hypothesis`, случаи false diagnosis в golden eval; количество раз, когда код проверен против неправильного SHA;
- ресурсы VPS и рост очередей во времени, рост DB/WAL и доступного места; derived-samples с временем и корректным разделением процессов;
- ACL аудит с безопасными metadata без пользовательского prompt body или credential values.

**Запрещено** визуально выдавать «нет ошибок» за «всё здорово», «настроено» за «соединение проверено» и количество запусков чекапа за количество реальных аварий. Не вводить бессмысленные проценты «самосознания» бота.

## 14. Производительность, конкуренция и отказоустойчивость

- Минимальные probes быстрые; дорогие (глубокий integrity check, полный diff, history traversal) — только при необходимости. Настройки бюджетов редактируемые, не блокирующий систему хардкод.
- Один короткоживущий validated snapshot на совместимые проверки, дедуп одновременных запросов без смешивания чатов и ролей. Cache по `runtime_sha + probe args + scope + permission class`, своевременная инвалидация после деплоя/рестарта/изменения настроек.
- Credential и protected prompt outputs **не** попадают в общие или cross-user caches. Auth проверяется повторно перед доставкой.
- GitHub latency/429/5xx не блокирует локальный чекап. Не держать DB lock, пока идёт сеть. В случае partial answer сообщить, что source read не завершился.
- Сценарии cancellation/restart: инструмент прекращает работу в рамках поддерживаемого task lifecycle; если задача на фоне — durable job и корректный статус, без обещания доставить ответ без сохранённого delivery path.
- Два параллельных запроса админ/обычный юзер не могут переиспользовать защищённые данные другого. Даже идентичный текст запроса не даёт общего prompt-cache.
- Валидация JSON schema, time ranges, file path; не позволять LLM менять unit на чужой или читать произвольный `root`/путь/SQL. Лимиты размера и времени — контролируемые engineering settings, не ручные keyword-гейты.
- Prompt injection в README, коммитах, журналах, stdout, SQL text — только недоверенные данные; не является полномочием tool-call или системной инструкцией.

## 15. Матрица корнер-кейсов и проверок безопасности

| Case | Ожидаемое поведение |
|---|---|
| Обычный пользователь спрашивает CPU/RAM, используемую модель, причину timeout и код своего бота | Разрешён технический ответ с реально полученными доказательствами, без ложного запрета «только админам». |
| Обычный пользователь просит действующий `prompts.checkup_system_prompt` | `denied(prompt_readback)`, без частичной цитаты, реконструкции или модели, «рассказывающей по памяти». |
| Админ текущего чата просит активный промпт прямо в группе | Реальная online-проверка статуса → серверная выдача эффективной редакции в **эту группу** → audited disclosure; не перефразировать. |
| Владелец спрашивает в группе | Numeric ID проверен, право на этот scope подтверждено → prompt readback допустим; не требовать DM. |
| Админ группы A просит эффективный промпт группы B | `denied(scope_mismatch)`; не подменять глобальной конфигурацией B. |
| Обычный пользователь пишет «я админ» или вставляет цитату admin message | Отказ на protected resource; role определяется только сервером и Telegram API. |
| Админ публикует от имени группы (anonymous admin / sender_chat) | Если numeric principal не установлен — `auth_unverified`, prompt не выдавать; общая диагностика доступна. |
| У админа отобрали права между запросом и отправкой | Повторная проверка, отказ до Telegram delivery. |
| Telegram getChatMember недоступен/бот не может проверить статус | Не выдавать промпт; остальные инструменты работают. |
| Админ/owner просит токен, пароль, SSH key, `env`, credential file | Не возвращать value; разрешить configured/masked status при наличии источника. |
| Запрошенный admin prompt содержит сохранённый ключ | Серверная частичная редакция и `partially_redacted`, ключ не публикуется. |
| Лог или traceback содержит Authorization header | Опасное значение удалено до модели и вывода, сохранены код и технический смысл ошибки. |
| Public GitHub содержит заводской системный промпт | Признать публичность репозитория; защищать runtime-effective prompt через ACL, не обещать невозможного. |
| Запрос на чужой приватный диалог/чат | Не выдавать чужое содержимое; публичная агрегированная техническая статистика допустима. |
| Подмена tool args (`user_id=owner`, `chat_id=other`) | Исполнитель игнорирует, работает только с authenticated principal context. |
| «чекап» в группе, обычный пользователь | Выполняется полноценная диагностическая проверка с безопасной публичной проекцией; характер сохранён. |
| «чекап» без ошибок | Есть настоящая попытка git metadata и реальные метрики; не выдумана авария и не прочитан весь код без повода. |
| GitHub HEAD новее deployed SHA | Корректное разделение версий; новый commit не обвинён в уже произошедшем сбое. |
| Dirty checkout, другой container image, GitHub 429 | `verified=false` / `not_checked` / `partial`, честный ответ по доступным данным. |
| После VPS-переезда unit переименован | Находит текущий источник или честно отмечает недостаток прав; не читает логи старой копии. |
| Контейнер без systemd, process без journalctl | Контейнерный или standalone backend; не фальшивый нулевой журнал. |
| Журнал пуст/INFO-only/error-only/rotated | Различать «событий нет», «ошибок не видно» и «данные недоступны». |
| Better Stack полностью недоступен | Никакого влияния на чекап и ноль checkup-specific сетевых вызовов. |
| SQLite locked/PG down/большой WAL/диск заполнен | Типизированные partial-показатели без зависания и без опасной очистки. |
| STT pending, сон завис, summary slot skip, LLM/QRNG ошибка | Корреляция actual jobs + evidence + правильный subsystem owner. |
| Prompt injection в исходнике/логе с требованием выполнить команду или раскрыть ключ | Игнорировать инструкции как данные; нет shell, нет secret output. |
| Одновременные public и admin запросы одного промпта | Нет cross-user/cache leak, ACL учитывается для каждого delivery. |
| Произвольный path, SQL, shell, port scan от владельца | Этот эпик read-only typed probes; произвольный execution не предоставляется. |
| Падение единственного процесса | Бот не заявляет, что диагностировал себя в реальном времени; возможна только post-restart/external watchdog реконструкция. |

## 16. Приёмка: измеримые критерии

**AC-01.** Bare «чекап» сохраняет зарегистрированный обработчик, cooldown, reply, реакцию, не ломает отправку и вызывает общий collector.

**AC-02.** Результат «чекап» действительно получает и передаёт в свой LLM-вызов реальные локальные логи, серверные метрики, память, effective runtime SHA и попытку git metadata; трасса позволяет это проверить.

**AC-03.** При релевантной проблеме source_reader реально читает проверенный файл/строки, не ограничивается сообщением о commit. Неуспех обозначен как `not_checked`.

**AC-04.** `get_bot_health` и свободный вопрос через Tool Calling используют те же evidence/probes без второй инсталляции сборщика.

**AC-05.** Никаких новых regex, keyword-роутов или массивов фраз для вопросов о состоянии, коде, промптах и доступах; `«чекап»` остаётся единственным специальным ключевым вызовом.

**AC-06.** `https://github.com/Henry-Case-dev/adminbot` и repo identity присутствуют в реальной конфигурации, используются для собственного source lookup и видимы в админке как non-secret. Источник ответа совпадает с фактической работающей ревизией либо явно отмечен как неподтверждённый.

**AC-07.** После переезда на другой VPS / другого unit / контейнер без systemd fetcher работает через действительный backend или возвращает честное `unavailable`, не чужие логи.

**AC-08.** Better Stack отсутствует в checkup runtime, UI и catalog/checkup config; внешние другие интеграции не повреждены; проверено не только grep, но и сетевым trace.

**AC-09.** `prompts.checkup_system_prompt`: effective bytes/hash до и после релиза одинаковы; активная ревизия, ручная версия и история сохранены. Язвительный стиль с матом по действующей настройке подтверждён живыми ответами.

**AC-10.** Публичный юзер видит подробную **техническую** информацию (кроме credential values/чужих chat contents) и может задать произвольный естественный вопрос без «чекап».

**AC-11.** Публичный юзер не может получить действующий prompt readback ни прямым запросом, ни через tool result/cache/metadata, ни через prompt injection.

**AC-12.** Реальный админ чата по запросу получает effective-помпт своего чата **в группу**; текст точен за вычетом объективно секретных фрагментов, корректно обработаны long messages.

**AC-13.** Группа A не выдаёт prompts группы B. Анонимный admin/статус unverified не получает protected readback. Владелец в группе проверяется по numeric ID.

**AC-14.** Token, API key, password, private key, session secret не раскрываются никому через Telegram, включая owner/admin. Проверки на всех error/caching/source/tool/replay routes, включая prompt, лог, config и исходники.

**AC-15.** Авторизация действует на стороне backend (до read, перед ToolResult и перед отправкой), не определяется текстовым «я админ» или LLM verdict.

**AC-16.** Использованы структурные метаданные класса данных, ресурсный ACL, секретный store и общий output sanitizer; не только «чёрный список» слов.

**AC-17.** Реальный GitHub source reader продолжает работать с сторонними репозиториями, discovery/locate/read не регрессировали.

**AC-18.** CPU/RAM/disk/process/job/provider/DB/network metrics основаны на замерах; `timestamp`, `scope`, `source`, `status`, `latency`, `reason_code` присутствуют. Нет «зелёного» placeholder.

**AC-19.** Статус/Аналитика визуально отображают реальное покрытие и отказы; доступ к деталям в рамках ACL, маскировка credential values во всех новых карточках.

**AC-20.** Зависания GitHub или DB, 429, несовпадение SHA, параллельные запросы и перезапуски дают graceful degradation; не блокируют ответы навсегда и не отменяют исправную часть диагностики.

**AC-21.** Инструментальные вызовы всегда read-only; не добавлено arbitrary shell/SSH/SQL и скрытых write-effects.

**AC-22.** Тесты проверяют **истинный путь доставки** (tool result → prompt/message → Telegram) и реальный chat role, а не только mocks, прошедшие unit-test.

**AC-23.** Golden set не менее 25 обезличенных случаев, включая установленные причины, нерелевантные коммиты, недостаток данных, ошибочные роли, реальные секреты в логах и промпте, negative examples. Проверять accuracy, evidence, hallucination, scope isolation и сохранение стиля.

**AC-24.** Проведён read-only аудит и проверка фактического production. Зафиксированы known limitations и live evidence; завершённость не объявляется из-за `healthz=200`, 0 traceback или только зелёного CI.

## 17. Порядок реализации (предложение этапов; финальная очередь — у оркестратора)

**D0 — Discovery + immutability baseline.** Проверить текущий HEAD, реальный VPS, active `current_task`, действующие чекап/get_bot_health/SourceReader, ACL, secrets registry, Telegram admin status APIs, prompt version effective bytes/hash, Better Stack dependencies, deployed SHA. Контракты новых probes согласовать с существующей архитектурой.

**D1 — Corrective: local log backend и Better Stack removal.** Исправить после-VPS discovery и точечно удалить checkup-only Better Stack, не сломав bare чекап. Доказать реальные логи нового VPS.

**D2 — Policy and classification.** Серверные role/scope/resource policies; разделить публичные технические ресурсы, per-chat data, active prompt contents и credential values. Включить fail-closed защищённый readback и отдельную секретную output-проекцию. Этот этап **до** расширения выдачи данных.

**D3 — Typed runtime probes.** Подключить процессы, ресурсы, job ledger, БД, providers, network и другие разрешённые источники к общему collector/capability registry, без нового агента.

**D4 — Git/self source.** Runtime identity, pinned SHA, recent commits на каждый чекап, целевые source/diff на аномалию, GitHub + проверенный local snapshot.

**D5 — Prompt readback.** Серверный prompt resource access с Telegram admin проверкой и chat-scoped disclosure прямо в группе; интеграция с уже действующим prompt version registry, redaction credentials и прямой отправкой, минуя LLM-перефразирование.

**D6 — Dual-path output and UI.** Сохранённый CheckupService prompt и оригинальная манера; Unified Writer для свободной беседы; админка/статус/аналитика с достоверными measured states.

**D7 — Security/quality review, real tests, release.** Пройти AC-01…24, golden set, нагрузку, смену VPS, смешанные роли, race conditions, проверки на реальные креды и фактическую доставку текста; деплой c default ON.

**Параллельность:** D1 может идти как независимый corrective при безопасном окне. ## 1. ОБЯЗАТЕЛЬНЫЙ АРХИТЕКТУРНЫЙ ИНВАРИАНТ: семантическая маршрутизация, никаких хардкодов намерений

Данное требование является обязательным для Architect, Builder, Reviewer и Orchestrator.

В проекте уже принято решение об отказе от лексической маршрутизации естественной речи. Не допускать возвращения ранее удалённых механизмов под новым названием.

### 1.1. Единственный механизм определения намерения

Намерение пользователя определяется существующей LLM-архитектурой принятия решений на основании смысла запроса и контекста разговора.

Модель должна учитывать:

- содержание текущего сообщения;
- предшествующий разговор;
- reply и canonical message context;
- результаты предыдущих инструментальных вызовов;
- диагностические факты, уже полученные в разговоре;
- собственные возможности и доступные инструменты;
- объект исследования: собственный Adminbot, внешний проект либо иной предмет обсуждения.

LLM самостоятельно решает, необходимо ли обращаться к runtime-диагностике, журналу, собственному репозиторию, памяти или другим разрешённым источникам.

Код выполняет структурированное решение модели, проверяет аргументы, доступы и безопасность. Код не угадывает намерение пользователя по словам.

### 1.2. Прямые запреты

ЗАПРЕЩЕНО реализовывать определение диагностического намерения, выбора инструмента или собственного репозитория через:

- regex по словам, фразам, словоформам или сочетаниям слов;
- `if word in text`, `startswith`, `endswith`, `contains`, substring matching и аналогичные проверки естественной речи;
- списки ключевых слов, синонимов, выражений или «семантические словари»;
- отдельные лексические классификаторы, эвристики или scoring по совпадениям слов;
- ручные словари соответствия пользовательских фраз конкретным инструментам;
- комбинации таких механизмов под видом intent resolver, fast path, pre-router, semantic gate, fallback router или safety gate;
- перенос тех же списков из Python в JSON, YAML, БД, админку, конфигурацию или промпт в форме таблицы обязательных соответствий;
- форсирование `read_source_code` на основании наличия слова «код», названия проекта, ссылки на ошибку либо других лексических признаков.

Нельзя реализовать скрытый лексический fallback на случай отказа LLM.

Нельзя заменять один хардкод другим, в том числе вынесенным в настройки.

Нельзя создать новый отдельный LLM-классификатор намерений исключительно для обхода существующего L1. Использовать текущую общую архитектуру.

### 1.3. Разрешённые детерминированные механизмы

Запрет касается именно определения намерения по естественной речи.

Разрешены и должны сохраниться:

- существующая явная команда «чекап» и ранее утверждённые команды проекта;
- структурированное исполнение уже выбранного LLM действия;
- проверка схемы аргументов инструмента;
- разрешение repo/ref/path после установления моделью объекта исследования;
- проверка прав, allowlist/denylist путей, идентификаторов, URL, форматов и технических параметров;
- технический разбор логов, traceback, кодов ошибок, имён модулей и исходников для поиска evidence.

Не использовать технический разбор логов как замену семантическому определению пользовательского намерения.

Наличие reply к чекапу является контекстом, а не автоматической командой читать репозиторий. Само по себе упоминание ошибки не должно запускать диагностический pipeline.

Не расширять список явных команд.

## 3. Подключить исследование собственного кода к основному сценарию чекапа

### Текущее состояние

В релизе 2.58.198 уже существуют:

- `services/checkup_service.py`;
- `services/diagnostic_collector.py`;

Не создавать второй SourceReader, отдельного агента диагностики, новый LLM-клиент, новое хранилище или параллельный диагностический pipeline.

### Целевое поведение

Чекап должен быть полноценной самодиагностикой, а не пересказом заранее собранных логов.

1. Получить актуальные runtime-факты, журнал, ошибки и состояние зависимостей.
2. Передать их модели вместе с информацией о доступных диагностических инструментах.
3. Модель определяет, какие аномалии требуют исследования реализации и какие дополнительные данные необходимо получить.
4. При необходимости модель использует существующие SourceReader, `read_source_code` и `inspect_runtime`.
5. Полученные результаты возвращаются модели для дальнейшего анализа и, при обоснованной необходимости, дополнительных инструментальных действий.
6. Модель сопоставляет runtime evidence с фактически прочитанным кодом и формирует выводы о причинах, степени их подтверждённости и возможных исправлениях.
7. Итоговый отчёт публикуется в существующем стиле чекапа.

Чтение собственного репозитория должно быть доступно непосредственно в ходе стандартного чекапа, без необходимости отдельной команды владельца.

Если обнаруженная проблема требует исследования реализации, чекап должен действительно обращаться к коду.

При этом не форсировать чтение репозитория при каждом вызове независимо от обстоятельств. Не читать код ради искусственного счётчика вызовов. Не превращать каждый чекап в полный аудит репозитория.

Модель выбирает направление исследования по фактическим данным, а не по захардкоженному соответствию «текст ошибки → файл → инструмент».

Поиск технических совпадений внутри исходников и трассировок разрешён как часть уже выбранного исследования.

При продолжении разговора модель должна определять, относится ли новый запрос к этому отчёту, к отдельной обнаруженной проблеме, к собственному приложению или к другой теме.

## 5. Корректная деградация при отказе L1

Зафиксирован production-сценарий:

`LLMBadResponseError: empty content` → `l1 planner outage — deterministic fallback`.

Необходимо проверить, не теряет ли fallback контекст, доступные инструменты и ранее установленное намерение пользователя.

Требования:

- Использовать существующие механизмы fallback-моделей, планирования и исполнения инструментов.
- Сохранять уже установленное структурированное диагностическое намерение и объект исследования, если они остаются применимы к текущему запросу.
- Не терять контекст предыдущего чекапа.
- Если основной L1 недоступен, использовать существующий резервный LLM-маршрут, если он способен выполнить необходимое семантическое решение.
- Не придумывать новое намерение на основании слов запроса.
- Не запускать автоматически диагностику или чтение репозитория при любом отказе L1.
- Не создавать отдельного агента, дополнительного классификатора или бесконечной цепочки повторных LLM-вызовов.

Если намерение не было установлено и доступные LLM-механизмы не позволяют его определить, использовать честную контролируемую деградацию.

Если исследование действительно невозможно, бот сообщает фактическую причину недоступности, а не делает вид, что собственного репозитория не существует.

Наличие технического сбоя не разрешает обход RBAC.

Обеспечить:

- формирование валидного манифеста фактически выкладываемой версии;
- согласованность манифеста с запущенным процессом;
- корректное определение deployed SHA после рестарта и релиза;
- честную диагностику расхождения между checkout и runtime.

Не выдавать checkout SHA за доказательство версии работающего процесса.

Не подставлять фиктивные значения или генерировать доказательства задним числом.

Дополнительно проверить источники показателей, которые могут возвращать ноль при отсутствии данных:

- ошибки журнала;
- Telegram delivery;
- STT.

При отсутствии достоверных наблюдений возвращать корректный статус unknown/unavailable/not_checked, а не доказанный ноль.

Если существующие счётчики не подключены к фактическим операциям, восстановить их существующим механизмом в пределах scope.

Не создавать новые системы телеметрии ради нескольких показателей.

Обнаруженные чекапом продуктовые проблемы памяти, снов, уроков, retrieval и прочих модулей не превращать автоматически в обязательную часть этой коррективы. Зарегистрировать отдельно согласно существующему workflow.

## 7. Доступы, настройки и сохранение архитектуры

Сохранить исходное разграничение SELF-DIAG:

- обычным участникам — разрешённая общая диагностика;
- владельцу — расширенное исследование собственного приложения, кода, логов и разрешённых служебных данных.

Все вызовы инструментов проходят существующую diagnostic_policy, серверную проверку полномочий и publication guard.

Не выдавать токены, содержимое env, секреты, данные других чатов и закрытые служебные материалы.

Чтение исходников не означает разрешение изменять код или выполнять команды на сервере.

Восстановление диагностического намерения после отказа модели не повышает уровень доступа.

Не сбрасывать сохранённые пользовательские настройки.

Не вводить новые OFF/SHADOW-режимы для готовых исправлений. После production-деплоя корректное поведение должно быть активно по умолчанию при соблюдении существующих настроек и прав.

Сохранить текущий характер и стиль чекапа. Допускаются необходимые функциональные дополнения к промптам, но не переписывание пользовательской личности и речевых настроек.

Не добавлять новые искусственные лимиты, бюджеты, квоты или эвристические пороги для чтения собственного кода. Использовать существующие обоснованные технические ограничения без создания второго контура ограничений.

## 8. Приёмка: проверять смысл, а не заученные фразы

### 8.1. End-to-end сценарии

Обязательные проверки:

**A.** Реальный чекап владельца читает системный журнал и получает runtime-факты.

**B.** При наличии проблемы, требующей исследования реализации, модель самостоятельно принимает решение использовать инструменты чтения собственного кода. Фактически прочитанные исходники участвуют в финальном анализе.

**C.** Владелец продолжает разговор после чекапа и просит разобраться в реализации одной или нескольких обнаруженных проблем. Модель понимает контекст, не требует ссылки на собственный репозиторий, самостоятельно получает код и обосновывает выводы.

**D.** Основной L1 недоступен. Существующий резервный механизм обеспечивает корректное продолжение исследования, если это технически возможно. Иначе возвращается честный статус недоступности.

**E.** Журнал или репозиторий недоступны. Отчёт корректно различает отсутствие данных, частичный результат и подтверждённые факты.

**F.** Пользователь без необходимых полномочий не получает закрытые данные.

**G.** Deploy identity подтверждает реально работающую версию.

### 8.2. Проверка семантической обобщаемости

Reviewer самостоятельно формирует разнообразные пользовательские запросы, которых не было в implementation plan и тестовых примерах Builder.

Проверять не совпадение фраз, а сохранение намерения при изменении:

- формулировок и словарного состава;
- краткости сообщения;
- наличия или отсутствия прямых технических терминов;
- опоры на reply, предшествующий отчёт или результаты инструментов;
- разговорного стиля, опечаток и неформальной речи;
- объекта исследования и предмета обсуждения.

Обязательно проверить отрицательные сценарии:

- похожая лексика, но намерение не связано с диагностикой;
- обсуждение внешнего проекта;
- цитирование чужой просьбы без поручения боту;
- обычное продолжение разговора после чекапа;
- просьба объяснить уже полученные данные, для которой дополнительное чтение кода не требуется.

Положительные сценарии должны работать без обязательных слов-маркеров. Отрицательные сценарии не должны запускать исследование только из-за совпадения слов.

Тестовые формулировки являются исключительно входными данными тестов. Запрещено переносить их в runtime-код, словари, конфигурационные таблицы и механизм маршрутизации.

### 8.3. Обязательный антихардкод-аудит Reviewer

Reviewer должен проверить фактический production-путь от входного сообщения до решения об инструменте.

Подтвердить:

1. Намерение определяется существующей LLM-архитектурой.
2. Решение об исследовании собственного репозитория передаётся в структурированном виде.
3. Детерминированный код исполняет решение, а не вычисляет его по лексическим признакам.
4. Не появились новые регулярки, словари, правила substring matching или скрытые лексические классификаторы.
5. Fallback не возвращает запрещённую маршрутизацию по словам.
6. Тесты проходят на новых независимых формулировках, а не только на известных Builder примерах.
7. Проверяются реальные вызовы инструментов, а не один факт наличия класса, схемы или функции.

Любая новая лексическая маршрутизация естественного языка — нарушение архитектурного инварианта и блокер приёмки.

## 9. Порядок работ и Definition of DONE

Architect сначала сверяет фактическое состояние актуального релиза с исходными требованиями SELF-DIAG-01. Фиксирует конечный corrective scope и способ повторного использования существующей архитектуры.

Builder исправляет подтверждённые причины.

Reviewer независимо проверяет end-to-end сценарии и антихардкод-инвариант. Не ограничивается тестами Builder.

Для каждого обязательного сценария представить evidence:

- request/correlation ID;
- фактический маршрут;
- принятое моделью структурированное решение, без необходимости раскрывать приватную цепочку рассуждений;
- вызванный инструмент;
- фактически полученный результат;
- repo/ref/commit/path и диапазон строк при чтении кода;
- соответствующий итоговый ответ.

Не считать мок SourceReader, наличие схемы инструмента или прохождение отдельного helper-теста достаточной приёмкой пользовательского сценария.

Использовать существующую тестовую инфраструктуру. Не создавать новый тестовый завод.

Объединить обязательные исправления в один релиз и выполнить доступный production smoke-check.

Обязательные технические проверки выполнить до DONE. Остаточные проверки, которые требуют неконтролируемого естественного события или самостоятельного действия владельца, зарегистрировать как неблокирующие owner_live_checks. Не выдавать их за проведённые.

После устранения обязательных дефектов закрыть corrective и продолжить утверждённую очередь. Не переоткрывать весь SELF-DIAG-01 и не раздувать scope.

В финальном отчёте отдельно указать:

- почему первоначальная приёмка SELF-DIAG-01 не выявила неработающий конечный пользовательский сценарий;
- какие изменения устранили причину;
- каким способом доказано отсутствие лексического хардкода;
- какие реальные действия выполнил бот в ходе проверки.

**Конечный результат:** бот самостоятельно понимает смысл диагностического разговора, использует собственные инструменты и исследует свой код, когда это необходимо. Никаких новых команд, регулярных выражений по пользовательским фразам, словарей триггеров или ручных маршрутов для отдельных формулировок.
