## 1. Proven root causes addressed

### 1.1 Checkup was a single `llm.generate`, not a self-diagnosis

Proven in base code: `services/checkup_service.py` built system/user messages and called only
`self.llm.generate([...])`; the handler passed `facts_text + logs` and no tool schemas/router.
`services/checkup_prompts.py` had no operational instruction about available diagnostic tools.

Candidate:
- `services/checkup_service.py:58–170` — new optional `tool_runtime` uses the **existing**
  `services.tool_loop.chat_with_tools` with the **existing** `ToolRouter`/`ToolContext`
  (one loop; `TOOL_MAX_ROUNDS`, per-tool timeouts, chain limits unchanged). Tool results are
  returned to the same model in standard `role:"tool"` messages. Without `tool_runtime` the
  single-call path is byte-parity.
- `services/checkup_prompts.py:177–196` — functional addendum `CHECKUP_DIAGNOSTIC_TOOLS_ADDENDUM`
  (use provided read-only tools when facts need verification; don't call for appearance; state
  uncertainty). It is appended only when real tool schemas are supplied and before the fallback
  notice, so `CHECKUP_FALLBACK_NOTICE` remains the last paragraph. Owner genre/personality bytes
  are untouched.
- `handlers/checkup.py:213–255` — `_build_checkup_tool_runtime` builds the schema subset from the
  existing `CAPABILITY_TOOLS` (`read_source_code`, `inspect_runtime`) via existing `active_tools`
  and `schemas_for_names`; real `ToolContext(chat_id, user_id=actor_id, bot=bot)`.
- `bot.py:91–99, 617–621` — the same `_tool_router` instance is registered for checkup after its
  construction (`setup_checkup_tool_router`). No second router/loop/agent/LLM client.

### 1.2 Self repo was not resolvable after the model's structured decision

Proven in base code: `direct_capabilities.CAPABILITY_TOOLS` had no `source_code`/`deep_diagnostics`,
so L1 could not request the existing `read_source_code`/`inspect_runtime` capabilities even though
`diagnostic_policy` maps them; `read_source_code` required a URL/repo/query from the model, and the
model had no way to resolve its own repo without an owner-supplied URL.

Candidate:
- `services/direct_capabilities.py:50–58, 89–92` — existing tool names become addressable
  capabilities (`source_code` → `read_source_code`, `deep_diagnostics` → `inspect_runtime`),
  same `diagnostic_policy` ACL names.
- `services/direct_l1.py:286–370, 871–878` — optional typed field
  `diagnostic_research: {needed, target: self|external|other|unknown, sources: enum[]}` is
  parsed/validated; absent/invalid → `None`/`unknown`, never fails the turn.
  Only `needed=true` + `target=self|external` yields capabilities; `unknown`/`other` yields none
  (does not start a tool).
- `services/source_reader.py:321–410` — `resolve_self_repo_identity()` uses existing
  `flags.self_diag_repo_origin`/`DEFAULT_REPO_ORIGIN` and existing `deploy_identity.collect_identity`
  (read-only; no shell/SQL/network). It prefers a verified deployed SHA; if deployed differs from
  the local checkout it reads the local checkout with explicit `local_checkout_unverified`; if only
  a local snapshot exists it marks `local_snapshot`; otherwise it explicitly marks
  `remote_default_branch` and says this is not proof of the running version. No `master` is
  presented as deployed.
- `services/tool_router.py:1281–1385, 3344–3400, 3480–3510` — `ToolContext.diagnostic_research` is
  set by the service **only** after `target=self`; `_read_source_code` fills the canonical
  repo/ref only when the model's arguments don't name an external repo/URL, and adds a
  `repo_identity` block (repo/ref_source/deployed/checkout/mismatch/dirty/verification/note) to
  the JSON evidence. Model arguments keep priority.
- `services/direct_chat_service.py:8396–8428` — when the structured decision needs research, the
  existing tool phase runs the **existing adaptive orchestrator** (same `run_tool_phase`/limits)
  with the diagnostic schema subset; this is what lets the model choose a tool by actual data
  instead of the deterministic step deriver. Without the decision the mode is unchanged.

### 1.3 Continuation did not have the delivered report

Proven in base code: the checkup handler sent the report and returned; it never persisted the
report into `bot_replies` or the existing bot-output ledger, and `CheckupService` received no
conversation context. A follow-up could not structurally see the report.

Candidate:
- `handlers/checkup.py:257–296, 560–576` — after a successful send, the report is stored through
  existing mechanisms: `bot_replies` (+ parent link, so reply-thread walk works) and
  `services.bot_output_ledger.record_delivered_output(output_kind="checkup_report")`.
  Fail-open; delivery is not affected.
- `services/database.py:871–883` — `checkup_report` added to the existing closed
  `BOT_OUTPUT_KINDS`; no DDL.
- `services/direct_l1.py:415–423, 1796–1850` — L1 context accepts `diagnostic_report` and renders a
  dedicated section. `services/direct_chat_service.py:4032–4062, 7770–7832` reads the latest
  delivered `checkup_report` from the existing ledger within the existing recent-bot-reply window
  (structural `output_kind`, not user words) and passes it to the existing canonical L1 context.
  Reply-to-report works even outside that window through the existing `bot_replies` thread walk.
- L1's existing `bot_replies` section still exists; the new section gives the full report (up to the
  existing message cap of the context budget), not a 400-char slice.

### 1.4 L1 `empty content` fallback lost an established diagnostic decision

Proven in base code: `LLMBadResponseError` is caught by the existing L1 ladder in
`DirectChatService._execute_turn` (slot → main → deterministic `fallback_plan`), but
`fallback_plan` had no diagnostic decision and `get_l1_diagnostics` did not carry one.

Candidate:
- `services/direct_chat_service.py:7438–7448, 7608–7616, 7640–7645` — the last established
  diagnostic decision is read before the current run overwrites diagnostics; on planner outage it
  is exposed to the caller as `meta["previous_diagnostic_research"]`; the current turn records
  R17-safe diagnostic axes.
- `services/direct_chat_service.py:5664–5678` — the deterministic fallback preserves the decision
  **only** when the current turn is structurally a reply to the bot
  (`preserved_diagnostic_research(..., reply_to_bot=...)`). This only announces existing tools; it
  never dispatches one. Without this structural continuation the fallback stays `unknown` and no
  diagnostic tool is announced (honest `not_checked`).
- `services/direct_l1.py:372–397` — pure helper: only `self|external` and `diagnostic_needed=true`
  survive; ordinary follow-ups do not inherit research.
- The existing ladder already uses the configured fallback LLM route (main model) when the L1 slot
  fails; no new classifier/agent/loop was added.

### 1.5 RBAC/publication preserved

- `ToolRouter._diagnostic_guard` / `_diagnostic_output` are unchanged and still run before/after
  each diagnostic tool; the checkup loop passes the real Telegram actor (`handlers/checkup.py`),

- Checkup publication still goes through `diagnostic_policy.publish` and style/cleanup exactly as
  before (`handlers/checkup.py` unchanged around those steps).
- No secrets/env/other-chat data added to tool output or logs; `repo_identity` is machine metadata.

## 4. Anti-hardcode proof

What was checked (not only “no tests use known phrases”):

1. **Production path scan.** `git diff -U0` over all changed production files contains no new
   `re.`, `startswith`, `endswith`, `in text/query`, word lists, synonym tables, scoring, or
   config/prompt phrase→tool tables. The only new maps are closed typed enums:
   `DIAGNOSTIC_TARGETS`, `DIAGNOSTIC_SOURCES`, `DIAGNOSTIC_SOURCE_CAPABILITY`.
2. **Decision authority.** `normalize_l1_plan` accepts `diagnostic_research` only as a typed JSON
   object; it does not receive the user text. `diagnostic_source_capabilities(plan)` reads only
   `needed/target/sources`. `_l1_tool_subset` executes that decision; the model still makes the
   actual tool call in `tool_phase`.
3. **Repo resolution trigger.** `resolve_self_repo_identity` is called only after
   `plan.diagnostic_research.needed` and `target == "self"` (`direct_chat_service.py:6063–6074`)
   or in the explicit checkup tool runtime. There is no word/URL heuristic: `_read_source_code`
   fills identity only when model arguments leave repo/URL empty and the structured context says
   self.
4. **Report context trigger.** `_recent_checkup_report_text` filters the existing ledger by
   `output_kind="checkup_report"`; it does not inspect the current message text. Reply context uses
   the existing `bot_replies` thread.
5. **Fallback.** `preserved_diagnostic_research` uses only the previous typed decision + structural
   reply-to-bot flag; it never parses words and never dispatches a tool.
6. **Behavioral negatives.** The new test file includes similar-sounding text with no model
   decision (no tools), `needed=false` (no tools), external target (no self repo), ordinary
   continuation (no inherited research), and “already received data” (no tool call).
7. **Test phrases isolation.** Grep over `services/`, `handlers/`, `bot.py` for the test phrases
   used in this candidate returns nothing; phrases exist only in
   `tests/test_selfdiag_corrective_research.py`.

Reviewer must independently choose unseen positive/negative phrasings and trace the actual
