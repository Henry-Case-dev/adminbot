**Журнал:** сообщение `journalctl insufficient permissions`, rc=1 — подтвержденный owner-observed symptom, не основание менять права здесь. DevOps уже выполняет разрешённый ремонт; Architect/Builder не трогают unit/groups/journal permissions и не дублируют lane. Результат production-чтения должен быть дан DevOps в evidence и использован в сценарии A.

**Уточнение счётчиков по probes (`services/runtime_probes.py`):** `logs.errors` считает реальные записи текущего `log_ring` (`get_entries(level="ERROR")`), но пустой ring трактуется как status OK + `no_error_entries` и `error_entries: 0`; это «ноль ошибок в ring», а не доказательство полного журнала/окна — coverage/источник должны быть показаны и incomplete journal не должен маскироваться. `telegram.delivery` получает `delivered=len(rows)` из `bot_output_ledger.list_bot_output_history` на чат/окно; пустой ledger возвращает 0 при успешном чтении, отдельно `global_delivery_metrics=None`; ноль означает ноль записей ledger, не доказательство успешности доставки или доступности статистики ошибок (они явно not_checked). `media.stt` читает `get_voice_window`; отсутствие voice rows даёт `failed=0`, `pending=0`, пустые statuses и healthy=None, reason unset — это ноль наблюдённых сбоев, но доступность наблюдений надо указывать через `rows_scanned=0`/window; отсутствие БД/чата/reader и read failure уже дают NOT_CONFIGURED/UNAVAILABLE/UNSUPPORTED. Нельзя менять эти счётчики на другой источник по предположению: уточнить labels/coverage, если UI/renderer представляет их как total error/delivery/STT workload; нулевые вычисленные значения при успешном полном чтении допустимы как факты ограниченного окна.

## Замороженный corrective contract

**Объём:** восстановить исследовательский путь в существующем чекапе, продолжение через существующий Direct L1/ToolRouter, уточнить деградацию пустого L1 ответа, manifest/deployed identity и честность трёх названных счётчиков. Исключить любые исправления DevOps журнала; не исправлять попутные memory/sleep/lessons/retrieval и иные диагностические находки. Не создавать второго SourceReader, агента, LLM-клиента, хранилища, pipeline или telemetry subsystem.

**Минимальная граница изменений:** переиспользовать `CheckupService` + общий `ToolRouter`/`ToolContext`/`tool_loop` + `DiagnosticCollector`/`SourceReader` + существующие `direct_l1` и Direct message-context. Вызов чекапа должен переходить к существующему циклу tool calls с переданным runtime bundle и доступными schemas; результат каждого разрешённого вызова возвращается той же модели для продолжения анализа. Не добавлять новую архитектуру цикла. Continuation использует существующее canonical context и историю фактически отправленного отчёта/результатов — без отдельной Direct-ветки по фразам.

**Структурное решение LLM:** добавить к существующей L1 JSON-схеме optional typed diagnostic decision, не отдельный классификатор. Контракт: `diagnostic_research: {needed: boolean, target: enum(self|external|other|unknown), sources: enum[]}`; `needed=false` означает без вызова; `target=self` разрешает кандидата собственного репозитория; `unknown`/невалидное/отсутствующее поле нормализуется в «не установлено», не запускает инструмент. Самостоятельный tool call в стандартизированной tool-call форме остается допустимым существующим механизмом, если L1 уже выбирает инструменты. Сервер валидирует закрытые enum/типы, наличие объявленного инструмента, JSON Schema аргументов, полномочия через `diagnostic_policy` и publication guard. Это намерение-план, не новый policy bypass. Только после `target=self` разрешить `flags.self_diag_repo_origin` и выбрать текущий deployed SHA/проверенный snapshot по существующему resolver; не подменять deployed SHA checkout/master. Для внешнего объекта использовать только установленную моделью identity/обычный SourceReader flow; неоднозначность — честное уточнение.

**Цикл и ограничения:** выполнять на существующих ограничителях `tool_loop` (`TOOL_MAX_ROUNDS`, общие лимиты вызовов/времени и per-tool таймаут/квоты) и пределах SourceReader/ProbeLimits. Не вводить новые искусственные квоты, лимиты объёма инструкций, порогов или специальный лимит self-read. Остановки/отказов достаточно: завершение модели; существующий исчерпанный цикл; отмена/timeout; ACL deny; недоступный провайдер/источник. Всегда сохранить уже установленный валидный структурированный план при временном отказе следующей стадии; не реконструировать намерение по словам. При пустом L1 использовать существующий резервный LLM route, если он доступен по действующим настройкам. Если ни одна модель не установила решение — controlled degradation `unknown/not_checked`, короткое честное сообщение; не стартовать tools автоматически.

**Данные/безопасность:** runtime/journal/tool результаты остаются evidence с producer/status/coverage; отсутствующее наблюдение = `unknown|unavailable|not_checked`, никогда ноль как доказанный факт. Роль Telegram берётся из реального `ToolContext`; оставить pre-dispatch RBAC, повторную проверку перед возвратом данных, redaction и publication guard. Исходники — read-only; никаких команд/изменений на сервере, env/secrets, других чатов или закрытых материалов. Сохранить характер чекапа: prompt additions только функциональные указания использовать доступные tools и сообщать uncertainty, без переписывания личности/стиля. Существующие настройки не сбрасывать; готовая функция в production активна по умолчанию при сохранении явных override (проектный AGENTS).

**Deploy identity:** исправить фактический pipeline формирования/доставки `.deploy/release.json`, чтобы manifest имел schema-required поля с SHA реально выкладываемой версии и создавался атомарно в штатном deploy пути до рестарта/фиксации релиза. Проверка запускает/сверяет process start, manifest version/SHA, checkout HEAD и dirty state существующим `deploy_identity`; не повышать checkout до доказательства исполнения и не генерировать историю задним числом. Точная точка записи манифеста требует Builder найти её в release scripts; artifact creation и parser must agree. Ошибки probe/counters исправлять только по установленным источникам, не создавать новую телеметрию.

**Откат:** откат единого совместимого релизного набора на последнюю проверенную версию штатным Git release/deploy путем; rollback manifest отражает предыдущий реально запущенный SHA и `effect=rollback`. Схема БД/DDL не нужна. Не менять производство в этой архитектурной задаче.

## Анти-хардкод: исполнимый критерий

Reviewer лично прослеживает production-путь **сообщение + canonical/reply/context → существующий L1 вход/схема → структурированное решение → capability/tool resolution → Router guard/RBAC → фактический tool call → результат → повторная модель → publication/output guard → ответ**. Проверяет все ветви: обычный checkup, continuation, собственный/внешний объект и L1 пустой/недоступный. Для каждого перехода указывает код/строки и runtime trace.

Запрещены в runtime-коде, prompt/config/data-driven tables: regex, слова/подстроки, словари/синонимы, scoring, эвристики или ветвления по естественному тексту для выбора намерения, инструмента или self repo; их скрытые fallback/fast path/safety gate версии; принудительное чтение от reply, слова «код», ошибки/названия проекта/URL без решения модели. Разрешены только явная уже существующая команда и структурные технические проверки/валидация после решения.

Builder доказывает отсутствие лексического маршрута не только поиском совпадений: тестовый ingress→L1/tool-loop с незнакомыми (автор Reviewer) формулировками и перефразированием, где один смысл ведет к self research, похожая лексика с иным смыслом не вызывает tool, внешний проект не резолвится как self, цитата/обычное продолжение не запускают диагностику, уже имеющихся данных достаточно — код не читается. Тестовые фразы живут только в тестовых входных данных, никогда в production prompts/config/словари/роутер. Reviewer добавляет собственные unseen/adversarial phrasing, которых нет в плане и Builder тестах, и лично инспектирует diff/историю регистрации конфигурации на перенос тестовых фраз в runtime.

## Обязательная evidence-матрица A–G (§8.1)

На каждый сценарий сохранять запись с request/correlation ID, конкретной цепочкой (route/L1 source/fallback/tool loop), типизированным decision (без private chain of thought), именем вызванного инструмента либо фактом его корректного отсутствия, результатом инструмента/его статуса, repo/ref/commit/path/диапазоном строк для реального чтения, итоговым опубликованным ответом. Нет чтения — поля кода явно `not_applicable` с причиной; неполный вызов — ошибка и результат, не успешный mock. Секреты и содержимое приватной chain-of-thought не записывать.

- **A:** реальный checkup: подтверждено чтение свежих journal entries текущего invocation в контексте процесса бота (от DevOps); фактические runtime facts; LLM decision; результаты tools, если выбраны; конечный отчет. Журнал root-доступом не доказательство.
- **B:** живой смысловой checkup с evidence anomaly: decision `needed=true,target=self`; реальный `read_source_code` и/или `inspect_runtime` вызов с допуском; verified deployed ref/commit, путь/строки; модельный synthesis с причинной связью между evidence и ответом.
- **C:** реальный continuation reply на checkup report: canonical контекст/предыдущий отчет доступен; decision связывает запрос с ним; собственный repo установлен без URL от пользователя; реальные чтение/результаты/ответ. Проверить и нерелевантное продолжение отдельно.
- **D:** контролируемый отказ основного L1: показать резервную LLM ветвь и корректное структурированное продолжение/tools, если модель это решила; отдельно полная недоступность/пустой результат всех LLM — `unknown/not_checked`, никакого автоматического чтения. Связать attempt/fallback IDs и конечный ответ.
- **E:** независимо отключить/сделать недоступными journal и repository в существующем тестовом/контролируемом окружении: каждый источник получает `unavailable/not_checked`, подтвержденные остальные данные сохраняются, отчет различает непроверенное и установленный факт. Не подменять отсутствующее zero.
- **F:** реальный негативный RBAC прогон principal без владельческих прав: попытка закрытого tool получает deny, нет результата/утечки в модели или публикации; разрешенная публичная диагностика остается. Документировать principal class/решение без ID/секретов.
- **G:** deployed identity из действительного release manifest и живого процесса: manifest SHA/version, runtime version/start, checkout SHA/dirty state и результат сравнения. Показать mismatch/manifest-missing негативную ветку как unknown/unverified; checkout отдельно и не за deployed.

**Независимый аудит Reviewer (§8.3):** сохранить список просмотренных production decision/tool entrypoints и точный candidate; проверить test assertions на возможность падения при поломанной маршрутизации; предъявить собственные unseen положительный и лексически похожий отрицательный кейсы с фактическими трассами. Все A–G evidence candidate-bound, источник/артефакт существует; мок SourceReader, схема без вызова или helper-тест не засчитываются вместо E2E.

## Границы приёмки, параллельность, DONE

`owner_live_checks` — только действительно неконтролируемое реальное естественное событие/окно или добровольное наблюдение; не задача владельцу, не блокирует корректный инженерный DONE, но обязательное production событие остается честно внутренне pending до фактического наблюдения. Все выполнимые агентом проверки (production API/log/runtime, безопасные тестовые сценарии, counters и identity) — mandatory technical evidence; отсутствие доступа фиксируется с точной технической причиной, не owner task.

Оценка риска corrective: **R3** до выполнения production-path и ACL проверок (диагностический доступ/неверная идентичность версии), после доказательства без расширения доступов риск приемки пересматривает Reviewer. Внешних источников не использовано: решения основаны на коде/owner requirements.

Параллельность:
- `SERIALIZE`: общий L1 JSON/schema + prompt registration, общий ToolRouter/tool-loop/context contracts; не допускать конкурентных писателей в эти файлы.
- `PARALLEL_SAFE`: отдельный deploy script/manifest generation; runtime probes/counter provenance (после фиксации источника); checkup-to-existing-tool-loop seam — отдельный исполнитель только после freeze интерфейса.
- `BLOCKED_BY: DevOps journal lane`: настройка systemd permissions не включать в Builder scope; после неё только использовать их proof в A.
- `READ_ONLY_PARALLEL`: Reviewer adversarial scenarios/trace plan, не писать в файлы Builder.

DONE этой коррективы: подтвержденные причины обработаны; единый кандидат объединяет совместимые изменения; независимый Reviewer подтверждает три линзы и анти-хардкод через actual path; сценарии A–G имеют обязательное evidence либо только допустимое явно зафиксированное future natural-event ожидание; counters без наблюдений не маскируются нулем; runtime и checkout/deploy identity разведены; RBAC/redaction/publication сохранены; штатный release и доступный production smoke доказаны. Это не повторное закрытие всего SELF-DIAG-01. До этого — не VERIFIED/DONE. Обнаруженные независимые дефекты — существующий backlog, не данный scope.

## Builder: точный порядок работ

1. **Единый L1/tool-loop/context writer** — определить и замкнуть один существующий call path от CheckupService и continuation к L1 + ToolRouter/tool_loop; замороженные typed decision/schema и propagation; обновить только `services/checkup_service.py`, точку интеграции `handlers/checkup.py` при необходимости, существующие `direct_l1.py`/`direct_chat_service.py`/`tool_schemas.py` и точные существующие context files по фактическому вызову. Владение схемой/роутингом сериализовать внутри этого шага.
2. **SourceReader/identity resolution writer** — подключить уже существующий `configured_repo_origin` только после структурного target=self; сохранить deployed SHA vs checkout distinction; не менять SourceReader API без доказанной необходимости. Write scope: существующая точка resolver/deploy identity; любые общие файлы из шага 1 — интеграционное изменение только после его завершения.
3. **Degradation + observability writer** — сохранить структурный intent на допустимом fallback маршруте, контролируемый unknown при отсутствии решения; установить фактическую семантику и поправить probes для journal-errors/Telegram delivery/STT так, чтобы отсутствующие данные не были нулями.
