## 1. B1 - `SD1-D6-05`: prompt_hash/source не соответствуют effective prompt

**Требование:** телеметрия `checkup_triggered` содержит prompt source/version/hash
эффективного промпта; hash должен описывать реальные байты system-сообщения.

**Факт:** `services/checkup_service.py:67-86,152-169` считает hash по
`system_prompt` ДО `replace("{max_symbols}", ...)` и ДО добавления owner-block/
fallback-notice. В `last_run` попадает hash базового промпта, а не effective
system. `prompt_source` определяется через `hot.get(..., CHECKUP_SYSTEM_PROMPT)`;
при отсутствии PG-значения `hot.get` возвращает code default, и source всё равно
помечается `global`, а не `default`.

**Точное воспроизведение:** fake LLM captured messages, `CheckupService.checkup`
с `chat_id=None`; `CHECKUP_SYSTEM_PROMPT` содержит `{max_symbols}`:

```text
LAST_RUN.prompt_hash = b0c70f974e0e7a78
LAST_RUN.prompt_source = global
ACTUAL_SYSTEM_HASH16 = 5ea40ee17f3d27fb
HASH_MATCH = False
SYSTEM_LEN = 3021, prompt_chars = 3030
```

`handlers/checkup.py:439-449` копирует `last_run` в `checkup_triggered` как есть,
поэтому событие также содержит неверный hash/source. Дополнительно `last_run`
- общий mutable dict сервиса (`checkup_service.py:54,72,128`): при одновременных
чекапах разных чатов один обработчик может прочитать телеметрию другого.

**Минимальный fix:** получать source через существующий
`resolve_prompt_with_source`; считать hash по финальному `system` непосредственно
перед `llm.generate`; возвращать per-run telemetry из `checkup()` (или снимать
локальный snapshot), не полагаться на общий `last_run`. Добавить regression-тест:
fake LLM capture -> hash/source в `last_run` и `checkup_triggered` совпадают с
фактическим system; два конкурентных чата не смешивают telemetry.

## 2. B2 - `SD1-D6-17/18`: успешный checkup/health считается partial

**Факт:** `web/api/routes.py:3665-3707` считает success только `status in ("", "ok")`.
Успешный чекап завершает событие статусом `report_sent` (`handlers/checkup.py:419`),
а `get_bot_health_called` - статусом `called` (`services/tool_router.py:5322`).
Поэтому `_self_diag_stats` для них всегда даёт partial/complete неверно и
`last_success_ts=None`.

**Воспроизведение:** подставить события `checkup_triggered/report_sent/outcome=success`
и `get_bot_health_called/called/outcome=success`:

```text
checkup_triggered: calls=1 partial=1 complete=0 partial_share=1.0 last_success_ts=null
get_bot_health_called: calls=1 partial=1 complete=0 partial_share=1.0 last_success_ts=null
inspect_runtime_called: calls=1 partial=0 complete=1 (контроль)
```

**Минимальный fix:** определять complete по `outcome=success` либо закрытому
маппингу статусов (`report_sent`, `called`, `clean`, `delivered` - success;
`skipped/denied/busy` - не partial-измерение). Добавить тест для checkup и
get_bot_health, а не только inspect_runtime.

## 3. B3 - `SD1-D6-17`: secret_value_disclosures=0 может быть falsely measured

**Факт:** `web/api/routes.py:3810-3816` считает `validated` по всем событиям
`diagnostic_output_validated` (событие эмитится для любого tool-результата), а
`deliveries` - только inspect/checkup/prompt/health. Один посторонний validated
event уже делает `validated >= deliveries`.

**Воспроизведение:** rows = один успешный `checkup_triggered` + один
`diagnostic_output_validated` от другого tool:

```text
secret_value_disclosures = {"value": 0, "measured": true,
                            "reason": "enforcement_measured"}
checkup = {"calls": 1, "partial": 1, "complete": 0, "last_success_ts": null}
```

`0` выдаётся как измеренный, хотя checkup в этом окне не проходил через
`_diagnostic_output`. Это ложный «зелёный» security-показатель.

**Минимальный fix:** считать validated только по доставкам соответствующего
типа/корреляции (или эмитить отдельный checkup-validation event и считать его),
не сравнивать общий счётчик с числом доставок. Добавить тест с посторонним
`diagnostic_output_validated` и с реальной доставкой.

## 4. B4 - `SD1-D6-12/16`: `configured` источников не соответствует среде

**Факт:** `web/api/routes.py:3784` вызывает `probes.probe_catalog(area="")` без
`ProbeDeps`. `probe_catalog` (`services/runtime_probes.py:340-356`) вычисляет
`configured = not missing`, а с пустыми deps зависимости `db/memory/logs/status`
считаются отсутствующими.

**Воспроизведение:** `probe_catalog(area="")` на кандидате:

```text
TOTAL 24, CONFIGURED_FALSE 11
media.stt configured=False requires=["db"]
scheduler.jobs configured=False requires=["db"]
```

В UI это показывается как `configured: нет` в раскрытой строке источника, хотя в
проде db/memory/fetcher существуют. `status` из последнего события может быть
observed, но флаг configured остаётся ложным.

**Минимальный fix:** собрать `ProbeDeps` из существующих сервисов (тот же набор,
что у `ToolRouter._diagnostics`/`checkup._diagnostics_collector`), передать в
`probe_catalog(deps=...)` без исполнения probes; тест endpoint с deps.
