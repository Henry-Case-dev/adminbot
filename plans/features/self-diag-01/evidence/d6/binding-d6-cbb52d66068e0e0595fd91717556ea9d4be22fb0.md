## 1. B1 — `SD1-D6-05`: телеметрия эффективного промпта

**Причина (подтверждена на `61e50806`):** hash считался по шаблону
`system_prompt` ДО `{max_symbols}`/owner-block/fallback-notice; `prompt_source`
определялся через `hot.get(...) == code default` и поэтому давал `global` даже
для кодового канона; телеметрия лежала в общем mutable `CheckupService.last_run`
и могла смешиваться между чатами.

**Фикс:**

- `services/checkup_service.py`: `checkup(..., *, telemetry: dict | None = None)`
  — сервис заполняет per-run словарь вызывающего; `last_run` удалён. Source —
  существующий `resolve_prompt_with_source` (`global` только при реальном
  PG-значении, кодовый канон — `default`). Hash/длина — по ФИНАЛЬНОМУ `system`
  непосредственно перед `llm.generate` (после подстановки, owner-block и
  `CHECKUP_FALLBACK_NOTICE`).
- `handlers/checkup.py`: создаёт `run_telemetry = {}` на вызов и передаёт его в
  `_service.checkup(..., telemetry=run_telemetry)`; в `checkup_triggered`
  попадает ровно эта запись (без общего состояния).
- `services/tool_router.py`: `_note_prompt_readback_outcome` эмитит
  `prompt_readback_allowed` ТОЛЬКО для `status=delivered` (overcount
  `partial/invalid_request/not_found/revision_unavailable` устранён; дубль
  эмиссии в `_emit_tool_outcome` отсутствовал).

## 2. B2 — `SD1-D6-17/18`: success не считается partial

**Причина:** `_self_diag_stats` считал complete только `status in ("", "ok")`;
успешный чекап пишет `report_sent`, `get_bot_health_called` — `called`, поэтому
они всегда попадали в partial, а `last_success_ts` был `null`.

**Фикс (`web/api/routes.py`):** закрытый маппинг
`_SELF_DIAG_SUCCESS_STATUSES` (`""/ok/success/report_sent/called/clean/delivered`),
`_SELF_DIAG_SKIP_STATUSES` (cooldown/denied/busy/no_gate/disabled — не попытка
измерения), `_SELF_DIAG_FAIL_STATUSES` (degraded/blocked/…), outcome — только
фолбэк. `partial_share` считается по измеренным вызовам без skipped;
`last_success_ts` — по complete; `by_stage.failed` — по partial.

**RED (тест на `61e50806`):** `checkup_triggered/report_sent` →
`complete == 0` (`assert 0 == 1`). **GREEN:** complete=1, partial=0,
`last_success_ts` заполнен; `inspect_runtime/degraded` остаётся partial;
`cooldown` → skipped, `partial_share == 0.0`.

Тесты: `TestB2SuccessStatuses` (2) и payload-тест
`test_payload_counts_success_and_never_fakes_zero`.

## 3. B3 — `SD1-D6-17`: ложный измеренный `secret_value_disclosures=0`

**Причина:** `validated` считался по всем `diagnostic_output_validated`, а
`deliveries` — по inspect/checkup/prompt/health; один посторонний validated от
любого tool делал `measured=true`. Чекап вообще не проходит через
`ToolRouter._diagnostic_output`, поэтому его доставка не была доказана.

**Фикс:**

- `handlers/checkup.py`: новое событие `checkup_output_validated`
  (component=`checkup`, status = статус redaction (`clean`/`partially_redacted`/
  `blocked`)) — эмитится ровно после `diagnostic_policy.publish` для конкретного
  отчёта; текста/секретов нет.
- `services/tool_router.py`: `diagnostic_output_validated` теперь несёт
  `stage=<tool>` (inspect_runtime/get_bot_health/prompt_readback/
  read_source_code) — корреляция по типу доставки.
- `web/api/routes.py`: `_self_diag_validation_coverage` сравнивает validated с
  доставками ПО ТИПУ (checkup — отдельное событие; tool — свой stage),
  возвращает `{value, measured, reason, deliveries, validated, gaps}`:
  `value=0` только при отсутствии gaps и наличии доставок; иначе `null` +
  `validation_not_correlated`/`no_deliveries_in_window`.
  `checkup_output_validated` добавлен в `event_counts`.

**RED (payload-тест на `61e50806`):** один `checkup_triggered/report_sent` +
посторонний `diagnostic_output_validated(execute_web_search)` →
`secret_value_disclosures.measured == True` (ложный ноль).
**GREEN:** `measured=false`, `value=null`, `reason=validation_not_correlated`,
`gaps={"checkup": 1}`. При наличии `checkup_output_validated` и парного
tool-stage — `measured=true`, `value=0`.

Тесты: `TestB3SecretMeasured` (3), `TestB2B3PayloadEndToEnd` (2).

## 4. B4 — `SD1-D6-12/16`: `configured` источников

**Причина:** `probe_catalog(area="")` вызывался без `ProbeDeps`; зависимости
`db/memory/logs/status` считались отсутствующими (11/24 `configured=false`,
включая `media.stt`/`scheduler.jobs`).

**Фикс:** `handlers/checkup.py::checkup_probe_deps()` — тот же набор
`ProbeDeps` (db/memory/fetcher/status), что у чекапа/`inspect_runtime`, собранный
из уже работающих сервисов; `_diagnostics_collector()` использует его же.
`web/api/routes.py` передаёт deps в `probes.probe_catalog(deps=...)` (fallback —
`ProbeDeps(db=...)`, если handler не поднят). Probes НЕ исполняются: каталог
читает только метаданные.

**RED/GREEN (probe):**

```text

          media.stt configured=False requires=['db']
          scheduler.jobs configured=False requires=['db']
cbb52d66: deps:  total=24 configured_false=0
          media.stt configured=True requires=['db']
          scheduler.jobs configured=True requires=['db']
```

Тесты: `TestB4ConfiguredSources` (2): configured отражает реальные сервисы;
каталог не исполняет probes (ловушка `_probe_service_runtime` не вызвана).
