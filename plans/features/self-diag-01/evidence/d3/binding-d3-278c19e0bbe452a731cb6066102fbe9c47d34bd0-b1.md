## 1. Blocker B1 — точная причина и исправление

**Причина.** `_probe_config_effective` (`services/runtime_probes.py`) брал
`ConfigCache.get("flags.self_diag_repo_origin")` как есть и клал в
`facts.settings[].effective`; `_build`/`render_page` отдают facts в bundle и
tool page. Ключ non-secret, поэтому `output_projection` его не закрывает:
URL вида `https://user:SECRET-TOKEN-9988@github.com/Henry-Case-dev/adminbot.git`
попадал в страницу/бандл. Это нарушало `SD1-EVD-12` (никаких секретных
значений) и загрязняло источник `config.effective` для `SD1-EVD-14`.

**Исправление (минимальное, без нового модуля/стора).**
Для ключа `flags.self_diag_repo_origin` probe теперь прогоняет значение через
существующую D4-нормализацию `services.source_reader.normalize_repo_origin`
(она уже вырезает userinfo/scheme/host/credentials) и отдаёт только
`owner/name`. Raw URL не покидает probe. Если значение непустое и не
нормализуется — `effective=None` + `reason_code="invalid_repo_origin"`,
исходная строка не возвращается. Это ровно путь D4-B, без второго парсера и
без изменения ключа/каталога.

Затронуто:
- `services/runtime_probes.py` — `_normalize_repo_origin_value` +
  ветка `flags.self_diag_repo_origin` в `_probe_config_effective`.
- `tests/test_diagnostic_probes.py` — регрессионный тест.

Другие D3-поведения не менялись; `_CONFIG_KEYS`, формат остальных настроек,
статусы, кэш, scenario, schemas, tool_router и `memory_health` не тронуты.
