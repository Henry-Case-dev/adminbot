## 1. Что реализовано

Новый модуль `services/deploy_identity.py` + новый файл тестов. Существующие
модули не изменены: `source_reader.py`, `capability_registry.py`,
`handlers/checkup.py`, `checkup_service.py`, `config/settings.py`, `web/*`,
`.gitignore` не тронуты. D3/D5, D6 UI/trace и live-проверки не включены.

Публичный API (schema 1):

```python
CODES = ("verified_deployed", "local_unverified", "mismatch", "unknown", "unavailable")
REASONS  # закрытый набор §2.3 + 3 документированных расширения, см. §4
DEFAULT_REPO_ORIGIN = "Henry-Case-dev/adminbot"
MANIFEST_REL_PATH = ".deploy/release.json"

collect_identity(repo_root=None, *, process_started_at=None) -> dict
recent_commits(repo_root=None, *, limit=5, basis="deployed") -> dict
path_is_denied(rel_path: str) -> bool
```

Порядок источников: `release manifest` → `.git` checkout HEAD →
`ADMINBOT_DEPLOYED_SHA` (только при отсутствии манифеста). `verified_deployed`
требует одновременно: валидный манифест; `deployed_sha == checkout_sha`;
`dirty == false`; `manifest.version == APP_VERSION` загруженного
`config.settings`; `process_started_at >= deployed_at`. Любое недостающее
условие даёт честный код (`local_unverified`/`mismatch`/`unknown`/`unavailable`).

Запись содержит: `schema`, `code`, `reason`, `repo_origin`, `deployed_sha`,
`checkout_sha`, `dirty`, `upstream_head`, `version_provenance`,
`local_source_verification`, `artifact`, `deployed_at`, `observed_at`,
`sources`, `conflict`, `local_identity`, `effect`, `previous_sha`,
`previous_version`; при конфликте манифест/env — `conflict_values` с обоими SHA.

Безопасность: `repo_root` резолвится; `HEAD`/refs/`packed-refs` читаются только
внутри `.git`, `gitdir`/симлинк вне корня → `unknown/path_denied|gitdir_unavailable`;
манифест читается только внутри корня; denylist `path_is_denied`;
`repo_origin` нормализуется до `owner/name` с вырезанием userinfo/токенов;
абсолютные пути хоста в запись не попадают. Код репозитория не импортируется и
не исполняется. `git` вызывается только фиксированным argv, `shell=False`,
таймаут 3 c, без `fetch/pull/ls-remote`; `GIT_OPTIONAL_LOCKS=0`, чтобы
`git status` не переписывал index. Кэша, записи манифеста, планировщика, БД нет.

- **D6:** вызов `collect_identity(repo_root, process_started_at=status.started_at)`

## 4. Честные границы и решения, требующие внимания Reviewer

1. **Прод-манифеста ещё нет.** В production `.deploy/release.json` не создан;
   D4-A в проде без манифеста покажет `local_unverified`. `verified_deployed`
   включится сам после первого штатного deploy-прогона DevOps. Live-deploy в
   этом слайсе не выполнялся.
2. **`process_started_at` — шов.** Функция не импортирует `status_service`,
   чтобы не создавать цикл/скрытую зависимость; D6 обязан передать
   `status.started_at`. Без параметра `verified_deployed` невозможен
   (`local_unverified/no_process_start`), это покрыто тестом.
3. **Три расширения закрытого списка причин:** `no_process_start`,
   `version_unknown`, `internal_error`. Первые два контракт описывает
   семантически (§2.3: `local_unverified` при отсутствии `process_start`), но
   не даёт отдельного reason-кода; `internal_error` — последний рубеж
   never-raise. Все остальные причины — ровно из §2.3.
4. **`local_source_verification`** выводится по §2.2 (`code` + известный
   `checkout_sha`), а не по грубой колонке таблицы §2.3: при `unknown` из-за
   битого манифеста, но известном checkout, значение `local_unverified`.
5. **denylist и `.gitignore`:** предикат `path_is_denied` трактует
   `deploy_*.py` как корневой паттерн, иначе контрактный тест 7 запретил бы
   `services/deploy_identity.py`. При этом фактический `.gitignore` (строка 7,
   `deploy_*.py`) матчит новый модуль на любой глубине. Контракт §5.1/§7.4
   запрещает менять `.gitignore` в D4-A, поэтому файл добавлен через
   `git add -f` и отслеживается коммитом. Остаточный риск: инструменты,
   уважающие `.gitignore` (например, `git clean -X`), могут считать модуль
   игнорируемым. Рекомендация на D4-B/DevOps: при правке `.gitignore` для
   manifest-контракта заменить паттерн на `/deploy_*.py` или добавить
   `!services/deploy_identity.py`. Классификация: `IN_SCOPE` (минимально
   устранено force-add), не блокер D4-A.
6. **`recent_commits`** реализован как часть API §5.1 и покрыт клампом/базисом,
   но реальный бюджет «≤3 git-вызова на чекап» и лог `[checkup] identity`
   принадлежат D6; здесь они не live-проверены.
7. **Read-only:** модуль сам ничего не пишет; `git status` вызывается с
   `GIT_OPTIONAL_LOCKS=0`, тест 3 проверяет побайтовую неизменность
   `.git/index`. Отдельный probe подтвердил `index_unchanged=True`.
8. **UI/визуальных изменений нет** — D6 владеет отображением; Playwright/
   Browser Use для D4-A неприменимы.
9. **Конфигурация:** флагов/провайдеров D4-A не добавляет. Acceptance-critical
   значения: отсутствие `.deploy/release.json` (production) и
   `process_started_at=None` (D4-A) — оба дают честный `local_unverified`;
   `ADMINBOT_DEPLOYED_SHA` не задан в тестовой среде, кроме тестов, где он
   явно выставляется через `monkeypatch`. После D6 effective-конфигурация
   `status.started_at` должна реально передаваться.
10. **Linked git worktree:** в связанном worktree `.git` — это файл с
    `gitdir:` вне корня worktree; контракт §5.1 требует для такого случая
    `unknown/path_denied|gitdir_unavailable`, и это покрыто тестом 6.
    Production — обычный checkout в `/var/www/admin_bot`, поэтому ограничение
    его не затрагивает; запускать identity-пробу на корне linked worktree
    нельзя (получится честный `path_denied`, а не баг).
11. **`dirty_tracked` опционален** по §1.2. Если ключ присутствует и равен
    `true`, `verified_deployed` блокируется (тест
    `test_manifest_dirty_tracked_blocks_verified`); фактический `dirty`
    проверяется всегда через `git status`, независимо от наличия ключа.
