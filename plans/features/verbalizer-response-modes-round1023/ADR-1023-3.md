# ADR-1023-3 — `response_mode` строго в Stage-1, 3 промпта Вербализатора, типографика

- **Статус:** **Accepted** (Step 2 @Architect, 19.09.2026)
- **Фича:** F3 `verbalizer-response-modes-round1023`
- **Тип:** backend/LLM + канон промптов
- **Связано:** ADR-1022-3/4/5 (System 2 two-call), ADR-1022-6 (validator-loop), ADR-1021-3 (стилевые блоки), R11 (саммари), F6 (rich-канал), F8 (UI-табы режимов)

## Context

ТЗ требует, чтобы Синтезатор определял один из трёх режимов (`casual`/`serious`/`deep_research`) и Вербализатор отвечал соответственно. В System 2 жёстко зафиксирован инвариант **physical-two-call-pipeline**: ровно 2 физических LLM-вызова (Stage-1 + Stage-2), tool-loop внутри Stage-1. Любой «роутер третьим вызовом» нарушает инвариант.

Второй конфликт: режим `deep_research` требует Markdown/таблиц, а саммари связано каноном R11 (plain-text без markdown/списков/эмодзи). Канал доставки plain (`parse_mode=None`); rich-канал (`sendRichMessage`) появится только в F6.

## Decision

1. **Роутер — только в Stage-1.** `response_mode` — поле JSON Stage-1 (не отдельный LLM-вызов). Число физических LLM-вызовов остаётся **2**; tool-loop и validator-loop не меняются. Тест числа вызовов обязателен.
2. **Enum + нормализатор в `system2_handoff.py`:** `RESPONSE_MODES = ("casual","serious","deep_research")`; `normalize_response_mode(value) -> "serious"` для неизвестного/пустого/`None` (fail-safe, никогда не бросает).
3. **Три контракта Stage-1:**
   - `parse_factcheck_analysis` / `parse_direct_synthesis` — добавляется поле `response_mode`;
   - `parse_summary_handoff` — **новый**: строгий JSON `{"response_mode": …, "digest": …}`;
   - `validate_summary_digest` **сохраняется** как backward-compatible обёртка (возвращает `digest`); raw-не-JSON, но валидная Markdown-выжимка → `digest=raw`, mode=`serious`.
   Это сохраняет 6962 существующих тестов/вызовов и даёт graceful-деградацию старых Stage-1-промптов.
4. **Промпты Вербализатора — база + общие блоки** (не 9 отдельных констант): narration = модульный базовый narrator + `STYLE_BLOCKS_SUFFIX` + `TYPOGRAPHY_BLOCK` + один из `MODE_CASUAL_BLOCK`/`MODE_SERIOUS_BLOCK`/`MODE_DEEP_RESEARCH_BLOCK`. Меньше канон-миграционных слепков, единая типографика.
5. **R11 vs `deep_research` — разделение «контент» и «канал»** (ответ на топ-вопрос):
   - режим выбирает тон/полноту/структуру **контента**;
   - **канал** определяет рендеринг и его гарантии: plain-канал сохраняет R11 для планового саммари; `casual`/`serious` не ослабляют канальные гарантии;
   - структурированный Markdown/таблицы допустимы **только** на rich-канале (F6 `sendRichMessage`); на plain-канале таблицы запрещены в любом виде (см. п.10);
   - в validator-loop для саммари правило `bullet_list` включается **только на plain-канале**; `plain_no_tables` — на всех plain-каналах; на rich-канале оба не бракуются.
6. **Типографика:** `TYPOGRAPHY_BLOCK` — только `-` и `""`; запрещены `—`/`«»`; разрешён мат/сленг; без «я сделал за тебя работу». Применяется ко всем режимам/модулям.
7. **Fallback** при отсутствии/невалидном режиме → `serious`; kill-switch `SMART_VERBALIZER_MODES_ENABLED=false` → единый прежний Вербализатор (Δ каталога = 0).
8. **Канон-миграция атомарна** (ADR-1013-3): `PREV_*_R1023` + `PROMPT_MIGRATIONS`/`ROLLBACK_MIGRATIONS` + `plans/docs/canon/**` + тесты одним коммитом, ступень `F1 → F2 → F3`.
9. **Порядок с F7:** `response_mode` добавляется первым; F7 добавляет correlation-id **после** F3 — аддитивно, без конфликта полей.
10. **Форматные правила по каналам (UPD владельца 19.09.2026, обязательны).** Разметка привязана к **каналу доставки**, а не только к режиму:
    - **Сценарий А — Прямой чат (обычное сообщение):** таблицы **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ** в любом виде (Markdown `| … |`, HTML `<table>`, ASCII-сетки) — Telegram Bot API не поддерживает таблицы ни в одном `parse_mode`, сырая разметка даёт `BadRequest: can't parse entities` (ParseError) и ответ не уходит. **ОБЯЗАТЕЛЬНО** базовое форматирование: жирный `<b>…</b>` для акцентов + простые буллиты `- `. Запрет таблиц **не** означает монолит.
    - **Сценарий Б — Статья (`sendRichMessage`):** **РАЗРЕШЕНО ВСЁ** — полный Markdown/HTML, сложные таблицы, сетки, глубокая разметка (rich-сообщение — структурированный вход, без text-`parse_mode`).
    - **Реализация:** канальные форматные блоки `FORMAT_PLAIN_BLOCK` / `FORMAT_RICH_BLOCK` в `services/prompt_style_blocks.py`; `MODE_DEEP_RESEARCH_BLOCK` дополняется ровно одним канальным блоком. Guard `plain_no_tables` (bounded-регенерация, fail-open) включается только на plain-канале. Сценарий А для `deep_research` доставляется safe-HTML-паттерном «Летописца» (`escape_lore_html` whitelist + `parse_mode="HTML"` + `TelegramBadRequest`→plain), что согласуется с существующим исключением `parse_mode=None` для plain-каналов.
    - `casual`/`serious` — без Markdown (как было).

## Consequences

- Единый роутер внутри Stage-1 — инвариант physical-two-call-pipeline сохранён.
- Гибкая стилевая адаптация без роста числа LLM-вызовов.
- Общие режимные блоки → меньше канон-дублей; UI-табы F8 редактируют 3 блока.
- `deep_research` разведён по каналам (UPD владельца): plain — safe-формат (жирный + `- `-буллиты, без таблиц), rich-статья — полный Markdown/HTML с таблицами. Ослабление R11 только для планового plain-саммари, которое остаётся plain.
- Guard `plain_no_tables` защищает от `ParseError` Telegram API: табличная разметка не доходит до отправки.
- Backward-compat: старый контракт `validate_summary_digest` жив, старые промпты дают `serious`.

## Alternatives

- **Отдельный LLM-вызов-роутер** — отклонено: нарушает physical-two-call-pipeline (High R1).
- **9 отдельных narrator-констант (по модулю × режим)** — отклонено: канон-дубли, тяжелее миграция.
- **Summary Stage-1 как plain-выжимка + строка-заголовок `MODE:`** — отклонено: не выполняет критерий «`response_mode` в JSON Stage-1».
- **Разрешить Markdown в plain-канале ради deep_research** — отклонено: нарушает R11 и даёт ParseError; канал важнее режима.
- **Единый `MODE_DEEP_RESEARCH_BLOCK` без канального блока** — отклонено: один и тот же промпт не может одновременно требовать таблицы (rich) и запрещать их (plain) — получим либо ParseError, либо обеднённую статью.
- **Единый формат для direct и article** — отклонено UPD владельца: rich-канал обязан использовать свою силу (таблицы/сетки).
- **Игнорировать режим при отсутствии (считать casual)** — отклонено: `serious` безопаснее как нейтральный дефолт.

## Cost / латентность

- LLM-вызовов не больше: 2 физических (+tool-loop Stage-1, +≤2 bounded ретрая Stage-2 при клише). Режим лишь меняет System-промпт Stage-2.
