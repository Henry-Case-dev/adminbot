## 2. Блокирующие находки

### F1 (Builder, API). Строка «Публикаций» теряет реальный исход отправки: решение перетирает публикационное событие

- **Где:** `web/api/initiative_publications.py`, `_text_attempts()` (строки 256-296).
- **Причина:** события читаются `ORDER BY ts DESC`, то есть свежие первыми; ветка `initiative_decided` безусловно перезаписывает уже созданную попытку (`attempts["text:" + corr] = ...`). Более новое событие публикации теряется, `chain_len` остаётся 1.
- **Воспроизведение (мой скрипт):** в `mca_events` чата A две строки с одним `trace_id=T4`: `initiative_decided` (`outcome=success`) 200 с назад и `publication_cancelled` (`outcome=cancelled`, `reason_code=publication_stale`) 150 с назад. `GET /api/initiative/publications?days=7` вернул строку `outcome=success`, `reason_code=""`, `chain_len=1`. Ожидалось `cancelled` + `publication_stale`.
- **Тот же дефект на доставке:** `initiative_decided` (`skipped`) + `publication_sent` + запись в `mca_bot_outputs` дают строку `outcome=skipped`, `delivered=true` - строка противоречит сама себе, хотя сообщение реально доставлено.
- **Влияние:** после P0 у отменённой по `publication_stale` попытки в журнале «Публикации» будет написано «успех / причины нет». Это ровно то смешение «генерация прошла / отправка прошла», которое владелец запретил (§1.3, §2.3). Подробная трасса при этом честная.
- **Минимальное исправление:** сливать события в хронологическом порядке (ASC) или не перетирать попытку решением, если для неё уже есть более новое терминальное событие; пересчитывать `chain_len`. Повторная проверка: тот же скрипт, утверждение «T4 = cancelled + publication_stale», «T1 = published».

### F2 (Builder, интеграция с P0). Конфликты координации текста не попадают в «Публикации»

- **Где:** `TEXT_EVENT_NAMES` (строки 69-74) и `PUBLICATION_PREFIX` (строка 77).
- **Факт:** P0-полоса (`fix/p0-publication-stale`) пишет в `mca_events` события `initiative_publication_conflict` и `initiative_publication_claim`. Ни список имён, ни префикс `publication_%` их не покрывают.
- **Воспроизведение:** строки `initiative_decided` (`skipped`, `window_closed`) и `initiative_publication_conflict` (`publication_conflict`) с общим `trace_id=T5`. Строка попытки есть, но показывает `outcome=skipped`, `reason_code=window_closed`; `GET .../publications?reason=publication_conflict` вернул пустой список; `GET .../detail?attempt_id=text:T5` показал оба события (`initiative_decided`, `initiative_publication_conflict`).
- **Влияние:** §2.3 требует «общий журнал доставок/конфликтов» и фильтр по причине; в объединённом релизе текстовые конфликты будут видны только в отладке.
- **Минимальное исправление:** добавить реальные имена `initiative_publication_*` в читаемые события (или заменить префикс на `%publication_%`) и отдавать их причину; повторная проверка - тот же скрипт, строка с конфликтом должна находиться в списке и под фильтром причины.

### F3 (Builder, UI). Несохранённые правки промптов исчезают молча при переключении вкладки

- **Где:** `web/app.js`, `initiativeTabEnter('memes')` (около строки 12677) вызывает `loadMemeSettings()`, а тот повторно заполняет `memeDraft` из ответа сервера.

## F3. Черновик промпта - ЗАКРЫТ по сути, но добавлен лживый confirm

Что подтверждено моим прогоном:

- на чистой форме индикатора нет; после ввода появляется бейдж «есть несохранённые изменения» и подсказка;
- переход «Обзор» -> «Мемы» сохраняет текст (`ЧЕРНОВИК 123` на месте), POST не отправляется;
- «Отменить изменения» возвращает серверное значение и снимает индикатор без POST;
- после сохранения: `Сохранено для этого чата: prompt_joke`, индикатор и подсказка исчезают, POST ровно один;
- смена чата с черновиком спрашивает подтверждение ОДИН раз («...Переключить область и потерять их?») и это правда: после согласия промпт перечитан из чата B, черновик чата A не утёк, лишних POST нет.

**Новый дефект:** то же подтверждение срабатывает на КАЖДОЕ переключение вкладки, пока черновик не сохранён, и текст его ложный:

```
Есть несохранённые изменения (0) для «Чат A». Уйти со страницы и потерять их?
(Изменения можно сохранить кнопкой «Сохранить изменения»)
```

- правки НЕ теряются (я проверил: текст на месте после согласия), а диалог утверждает обратное;
- счётчик «(0)» неверен - изменено одно поле;
- кнопка названа «Сохранить изменения», реальная кнопка - «Сохранить настройки мемов»;
- это расходится с собственной подсказкой на экране: «они сохранятся при переключении вкладок, но при смене чата приложение спросит подтверждение».

Причина: `memeDraftDirty` добавлен в общий `hasUnsavedEdits`, который проверяет `_dirtyLeaveGuard` при смене hash-маршрута (то есть при клике по вкладке). Для чата это верно, для вкладки - нет.
