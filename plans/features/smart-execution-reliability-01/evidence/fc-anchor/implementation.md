## 2. Причина (воспроизведена offline)

Из разбора §4.1:

1. `_subject_from_decision` склеивает `material_part` и `request_part` одним
   пробелом без границы предложения (`services/factcheck_orchestrator.py:456-463`).
2. Валидатор принимает любую дословную подстроку материала, поэтому LLM-предмет
   начинался с «Она распространена…» — **названия практики в нём не было**
   (полный материал 134 симв. в 420-символьный предмет не помещался).
3. В план уходил **не** полный материал, а `subject.material_part`
   (`factcheck_orchestrator.py:1814-1817`), и даже он использовался только в
   `_claim_anchor_map`, а не в термах запросов.
4. Запрос части вопроса строился из `(uents + uterms)[:10]` от текста вопроса
   («Реально ли есть страны с этой традицией…»), поэтому уходил в общий поиск.

Записанные в прогоне запросы: `…распространено она распространена во многих
странах африки…` и `Франция Великобритания Германия реально страны этой
традицией…`. `run_retrieval` пометил claim вопроса `confirmed` с 2 citation по
страницам `cbinsights` (manybot/whatshelp) и новости БРИКС; `stop_reason=sufficient_evidence`.

## 3. Изменение (минимальное, структурное)

`services/factcheck_orchestrator.py` — `_run_inner` передаёт в план **полный**
материал предмета отдельным параметром:

```python
subject_full_material_text=str(getattr(subject, "material_text", "") or "")
```

`services/factcheck_planner.py`:

1. `ClaimUnit.from_glued_request` — часть добавлена структурной гарантией
   вопроса, потому что вопрос склеен с материалом без границы предложения
   (ключи вычисляет `_request_glued_keys`, `_unit_key` вынесен на модульный
   уровень из `_claim_units`).
2. `_material_anchor_terms(material_text)` — первые `_MATERIAL_ANCHOR_TERMS = 3`
   содержательных терма начала материала (`_claim_terms`, единый токенизатор).
   Детерминированно, без списков стран/предметных словарей.
3. `_with_material_anchor(terms, anchor_terms)` — дописывает недостающий анкер
   ПЕРЕД термами части, поэтому существующий потолок `[:10]` не может вытеснить
  тему из запроса.
4. `build_retrieval_plan(..., subject_full_material_text="")` — полный материал
   приоритетен, `subject_material_text` остаётся fallback'ом для старых
   вызывающих.
5. `_build_plan_inner` — единая гарантия `_needs_material_anchor(unit)`:
   - часть из склеенного вопроса (`from_glued_request`) — всегда;
   - единица, построенная из **вошедшей** части материала — только если темы в
     этой части уже нет (`material_anchor_lost`: в `subject_material_text` нет ни
     одного анкерного терма), т.е. ровно случай «LLM сузил `material_part`».
   Анкер применяется и к базовому запросу части, и к её уточнениям
   (numeric/temporal).

Не менялись: `_subject_from_decision` (склейка/пунктуация), отсев «покрытых»,
лимиты термов `[:10]`, `_QUERY_MAX_CHARS`, бюджеты плана, `run_retrieval`,
правила релевантности/`off_topic_sources_dropped`, промпты, флаги.

## 4. Before/after на записанном сценарии

Воспроизведение: `probe_before_after.py` (в этом каталоге) — базовый
`services/factcheck_planner.py` из `0beed63d` и текущий файл, одинаковые входы
оркестратора.

```
material (134 симв.): «Женское обрезание — древняя традиция, которая существует уже
                       тысячи лет. Она распространена во многих странах Африки и
                       Ближнего Востока, и на её сохранение повлияли США.»
material_part:         «Она распространена во многих странах Африки и Ближнего
                       Востока, и на её сохранение повлияли США»   (темы нет)
request_part:          «Реально ли есть страны с этой традицией, которые не влияли
                       на её сохранение: Франция, Великобритания и Германия?»
```

До (`0beed63d`) — 2 запроса, темы нет ни в одном:

```
c1 (материал): «она распространена во многих странах африки ближнего востока»
c2 (вопрос):   «Франция Великобритания Германия реально страны этой традицией которые не влияли»
```

После (`b0f6ec79`) — те же 2 запроса (число не изменилось), оба с темой:

```
c1 (материал): «женское обрезание древняя она распространена во многих странах африки ближнего востока»
c2 (вопрос):   «женское обрезание древняя Франция Великобритания Германия реально страны этой традицией которые не влияли»
```

Второй запрос совпадает с записанным в прогоне `153116Z` началом запроса
(`fc-12-09-residual-investigation.md` §4.1 приводит его усечённо:
`Франция Великобритания Германия реально страны этой традицией…`) — те же термы
в том же порядке. Значит реконструкция входов воспроизводит наблюдавшуюся ветку
кода, а не гипотетическую.

Термы вопроса («страны», «Франция», «Германия», «влияли») сохранены — анкер
добавляется перед ними, потолок `_QUERY_MAX_CHARS = 200` остаётся единственным
ограничителем длины формулировки (это лимит поисковой фразы на стороне
провайдера, а не квота инструкций; тема стоит первой и обрезана быть не может).

## 6. Ограничения и что не доказано

- Точные границы `material_part`/`request_part` в raw JSON прогона не
  сохранены (разбор §8); сценарий восстановлен по preview, длинам и
  `text_overlaps_material`. Реконструкция воспроизводит записанный запрос
  байт-в-байт, но исходный JSON не переигрывался.
- Анкер — «первые 3 содержательных терма материала». Если материал начинается
  с общих слов (а не с названия предмета), анкер будет менее предметным:
  механизм детерминированный, без предметных словарей, и это осознанный выбор.
- Ветвь `unit.foreign_terms` (запрос по латинским именам/тикерам) и
  цитатный `INTENT_ORIGIN`-запрос остаются без анкера: у них свой словарь, в
  записанном сценарии они не участвуют. Это предсуществующее поведение, объём
  фикса не расширялся.
- Контролируемый агрегатор — синтетические строки выдачи, записанные в прогоне;
  реальных provider-вызовов не делалось. Целевые метрики live-canary
  (`claims_with_direct_evidence` по вопросу с релевантными refs,
  `direct_answer_on_question`) остаются непроверенными до деплоя и чистого
  прогона (`fc-12-09-residual-investigation.md` §7.3) — это Reviewer/DevOps и
  live-этап, не этот лейн.
- Прод не трогался: deployed остаётся `0beed63d` / 2.58.202.
