- Дата: 2026-11-14.
- Разбор дефекта (read-only): `plans/features/smart-execution-reliability-01/evidence/postdeploy/live/fc-12-09-investigation.md`.

- Production-кандидат, на котором наблюдался дефект: `0e4a144d` (2.58.200).

## 2. Причина (подтверждена воспроизведением)

`_subject_from_decision` склеивает материал/пересказ и `request_part` одним
пробелом без границы предложения (`services/factcheck_orchestrator.py:456-463`).
Планировщик строил единицы только из предложений предмета
(`factcheck_planner._claim_units`), а `subject_request_text` попадал только в
анкоры (`_claim_anchor_map`). В результате вопрос, приклеенный к концу
пересказного предложения:

1. не становится отдельной единицей (`re.split` по `[.!?;]` + отсев «покрытых»);
2. теряется внутри материального запроса из-за лимита `(uents + uterms)[:10]`;
3. `run_retrieval` исполняет только материальные запросы и останавливается на
   `sufficient_evidence`.

## 3. Изменение (минимальное, структурное)

Файл: `services/factcheck_planner.py`

1. `_claim_units(items, claim, *, cap=None, request_text="")` — после
   существующей логики, если `request_text` непустой, каждое предложение
   `request_text` добавляется единицей, если его нормализованный текст (без
   завершающей пунктуации) ещё не совпадает с уже принятой единицей.
   Никаких лексических правил/списков слов/новых категорий.
2. `build_claim_units(..., request_text="")` прокидывает аргумент в
   `_claim_units`.
3. `_build_plan_inner` передаёт `request_text=subject_request_text` (тот же
   структурный сигнал, который уже используется для анкоров).

Дедупликация: если вопрос уже стал отдельным предложением предмета (сценарии
D/E/F, вариант с терминатором), новой единицы и нового запроса НЕ появляется.

Не менялись: `_subject_from_decision` (граница предложения/пунктуация),
отсев «покрытых» на `_claim_units:592-600`, лимиты терминов `[:10]`,
`run_retrieval`, бюджеты, флаги/настройки, DDL.

Анкор: гарантированная единица из `request_part` не совпадает с claim-item,
поэтому `_claim_anchor_map` присваивает ей существующий `origin=user_request`
и анкор сообщения-запроса (`subject_anchor_tg_message_id`) — новый код анкоров
не добавлялся.

## 5. Offline-воспроизведение точных входов SFC-12-09 (без сети/БД/прода)

Скриптовая LLM-стадия `subject_resolve` (детерминированный двойник, JSON —
реконструкция по записанным инвариантам прогона), затем реальный
`resolve_check_subject` и `_build_plan_inner` с теми же kwargs, что передаёт
`factcheck_orchestrator`:

- материал (дословно из харнесса): «Женское обрезание — древняя традиция, она
  распространена во многих странах Африки и Ближнего Востока, и на её
  сохранение повлияли США.» (134 символа);
- вопрос (дословно): «Фактчек, бот, реально есть страны с этой традицией на
  которые не влияли такие гегемоны как Франция/Великобритания/Германия/США?»
  (127 символов);
- пересказ LLM: 304 символа, БЕЗ завершающей точки (восстановленная форма
  ответа из отчёта; точный текст прогона не сохранён — см. ограничения).

Итоговый предмет: `MATERIAL + " " + RETELLING + " " + QUESTION` = **567**
символов, `origin=mixed`, `resolved_by=llm`, `material=134`, `request=127`.

Запись метрик запроса — та же функция, что в харнессе (`overlap_ratio`:
содержательные токены ≥4 символов, порог 0.2).

### Базовая линия (deployed 0e4a144d, `planner_base.py`)

```
subject: chars=567 origin=mixed resolved_by=llm material=134 request=127
units:   2  (134 = предложение материала; 432 = пересказ + " " + вопрос)
plan:    claims=2 queries=2 intents=[entity_check, entity_check]
queries: "Африки Ближнего Востока женское обрезание древняя традиция она распространена во"
         "Африки Ближнего Востока подтверждение тезиса женское обрезание древняя традиция распространённая"
anchors: c1:None/- ; c2:5011/user_request
question_coverage: 0.0   (search_built_from_question = false)
```

Первые два запроса **побайтово совпали** с записанным production-планом прогона
`093904aea444462ebc41ae208e4ac0ee` (см. `fc-12-09-investigation.md` §5): вход
воспроизводит наблюдавшийся дефект детерминированно.

### С фиксом

```
subject: chars=567 origin=mixed resolved_by=llm material=134 request=127
units:   3  (134; 432 = пересказ + вопрос; 127 = вопрос отдельной единицей)
plan:    claims=3 queries=3 intents=[entity_check ×3]
queries: "Африки Ближнего Востока женское обрезание древняя традиция она распространена во"
         "Африки Ближнего Востока подтверждение тезиса женское обрезание древняя традиция распространённая /германия/сша?"
         "Франция Великобритания Германия фактчек бот реально страны этой традицией которые /германия/сша?"
anchors: c1:None/- ; c2:5011/user_request ; c3:5011/user_request
question_coverage: 0.692  (> 0.2 → search_built_from_question = true)
```

Что это даёт: третья часть плана — вопрос; `run_retrieval` исполняет её
отдельным проходом, поэтому `sufficient_evidence` больше не может наступить,
не попытавшись исследовать вопрос, а `search_built_from_question` перестаёт
быть ложным.

### Паритет (фикс не меняет другие сценарии)

Тот же прогон на базовом и исправленном планировщике даёт идентичные результаты:

- контрфакт «пересказ заканчивается точкой»: 3 запроса, coverage 0.692,
  тексты запросов совпадают между базой и фиксом (добавления нет —
  дедупликация);
- ordinary (без пользовательского текста), D (условие), E (subject = вопрос),
  F (доп. факт отдельным предложением): число единиц и тексты запросов
  совпадают `with request_text` и `without request_text` (см. тесты §4.5).

## 6. Наблюдение вне объёма фикса (не блокирует SFC-12-09)

В исправленном прогоне второй/третий запрос получают хвост
`/германия/сша?`. Это **предсуществующее** поведение, не появившееся от фикса:

- причина — `_claim_timeframe` (`factcheck_planner.py:747-786`) ищет префикс
  месяца «ма» подстрокой: «германия» содержит «ма» → `timeframe="/германия/сша?"`;
  хвост попадает в запрос только когда нет слота на отдельное уточнение
  (`refine_room == 0`, т.е. при ≥3 единицах);
- на deployed-коде тот же хвост уже есть: (а) в контрфакте с терминатором
  (базовая линия, запрос №3 = `… /германия/сша?`), (б) в обычном фактчеке для
  материала из трёх предложений: запрос №2 базовой линии =
  `распространение влияли франция великобритания германия сша германия и сша.`;
- классификация: `BACKLOG_ONLY` (независимый предсуществующий дефект
  извлечения временного интервала, вне объёма SFC-12-09). Минимальное
  исправление — привязка префикса месяца к границе слова; менять
  `_claim_timeframe` в этом срезе не стал, чтобы не расширять объём на
  temporal-эвристики.

## 7. Влияние на соседние строки

- **SFC-12-02 / SFC-13-01 (обычный фактчек, наблюдаемость):** обычный вызов
  не имеет `request_text` → ни новых единиц, ни запросов; три ordinary-запроса
  побайтово закреплены тестом. Метрики `claim_units`/`queries_attempted` для
  mixed-сценариев вырастут на число предложений вопроса — это существующие
  честные поля, новых метрик нет.
- **SFC-12-07 / SFC-5-10 (объём исследования, бюджеты):** добавляется ≤1
  запрос на предложение вопроса; при `budgets_enabled=false` (текущий прод)
  ограничения не применяются; при ON вопрос конкурирует в общем бюджете.
  «Достаточность доказательств» теперь требует покрытия и вопроса — это и есть
  требуемая §6.3/§12.8 семантика.
- **Смежные срезы корректирующего эпика:** пересечений по файлам нет;
  `settings.py`, DDL, флаги не тронуты.

## 8. Ограничения

- Разбор и этот фикс не проверяют живой production: нужен новый кандидат +
  независимое ревью + деплой, затем чистая canary `original_production_scenario`
  на стабильном LLM-провайдере. Ожидаемые наблюдаемые значения:
  `plan.queries` содержит запрос с терминами вопроса, `claim_anchors` c
  `origin=user_request`, попытка поиска/доказательства по вопросу,
  `search_built_from_question=true`.
- Точный JSON-ответ `subject_resolve` из прогона не сохранён (в артефакте только
  `text_preview`); пересказ восстановлен по всем записанным инвариантам и даёт
  побайтово тот же план — но формулировка модели могла отличаться. На вывод это
  не влияет: гарантия «вопрос → единица/запрос» теперь структурная.
- Провайдерская деградация того же окна (`temporal_validator`/
  `temporal_verbalize`, WARN-фолбэк) — отдельное внешнее состояние; она не
  отменяет retrieval-дефект и не входит в этот фикс, но чистая canary нужна и
  для answer-assertions (`direct_answer_on_question`,
  `ambiguity_acknowledged`).
- Трактовку `direct_answer_on_question` (засчитывает только место/place-like
  токен) стоит зафиксировать на ревью до canary, чтобы честный отрицательный
  ответ без названий стран не дал ложный красный.
