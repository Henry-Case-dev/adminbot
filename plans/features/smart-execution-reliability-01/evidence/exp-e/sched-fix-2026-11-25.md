## 1. Дефект (по измерению, а не по гипотезе)

Замер 25.11.2026: лаг **2 033 541** строк (`semantic_pending` = 0/0, main cursor 61 836, самая старая
необработанная 2022-12-07), `experience.review` не создавался **17.48 ч** при живом планировщике
(`intent_heartbeat_liveness` 24 с, gate ON, cadence `daily`).

Причина — в due-гейте `semantic_backlog()` (`services/mca_experience_jobs.py`):

1. Он брал только **transient** `semantic_pending.actionable_rows` и **устаревший**
   `semantic_lag.actionable_rows`. Второе вычисляется в конце прошлого прохода и не переоценивается;
   при `actionable_rows=0` (единственный отстающий чат был в backoff на момент замера) даже лаг
   2 033 541 строка не планировался.
2. `next_retry_at` собирался **только из `retry_at > now`**. Когда срок `retry_at` истекал
   (24.11 11:51:28Z), запись выпадала совсем → `due_at = 0` → молчаливый `not_due` (ветка
   `due_at <= now` была недостижима by construction).
3. Сам `not_due` нигде не логировался — причину нельзя было увидеть в журнале (§6.1 замера).

Механизм догоняющих проходов внутри job'а (`_semantic_catch_up_active` читает `semantic_lag.rows`)
исправен; не хватало именно **постановки** прохода.

## 2. Что изменено (bounded; WHEN, не объём)

`services/mca_experience_jobs.py`:

1. **Due-гейт от измеренного лага.** `_measure_semantic_lag()` теперь durable пишет `rows_by_chat`
   (≤ `SEMANTIC_LAG_MEASURE_MAX_CHATS` чатов). `semantic_progress_snapshot()` пересчитывает
   `lag_ready_rows/lag_ready_chats` **на момент тика** по durable per-chat замеру и **текущим**
   backoff-состояниям (`_semantic_chat_deferred`: tail retry + fresh-полоса). `semantic_backlog()`
   планирует проход по `lag_ready_rows`, а не по устаревшему `lag_actionable_rows`.
   Payload прежних версий (без `rows_by_chat`) поддержан fallback'ом
   (`legacy_actionable` / `legacy_retry_due`) — первый тик после выката на проде 2.58.244 попадёт в
   `legacy_retry_due` (retry уже истёк) и поставит проход.
2. **Истёкший `retry_at` — это готовность.** `semantic_progress_snapshot()` считает
   `retry_due_chats` (включая `retry_at=0`); `semantic_backlog()` разрешает проход, если срок
   наступил. `next_retry_at` сохранён с прежней семантикой (ближайший будущий), новые поля добавлены
   рядом — API/UI-контракт не менялся.
3. **Наблюдаемость.** `_log_tick_decision()` — одна INFO-строка на тик:
   `[mca16] experience review tick | status=<...> | reason=<...> | <числа>`; причины:
   `gate_off` / `singleflight` / `no_lag` / `deferred` / `lag_unmeasured` / `pending` /
   `measured_lag` / `retry_due` / `cadence` / `queue_read_failed` / `enqueue_failed`.
   Отдельной таблицы/флага/счётчика/планировщика нет; числа без содержимого сообщений (R17).
4. **Bounded-пределы сохранены:** per-pass row/batch/time лимиты, fresh-vs-tail полосы, типизированная
   обрезка, durable retry/backoff не менялись. Ускорение — только за счёт частоты постановки прохода
   (тик 900 с), не за счёт увеличения окна.
5. **Гигиена retry (защита от busy-loop):** `_prune_stale_semantic_retries()` убирает истёкшую
   retry-запись, за которой уже нет работы (курсор догнал данные, pending пуст); выключенный чат
   снимает свой backoff. Текущий/будущий retry не трогается.
6. **Свежая полоса в замере:** `_deferred` учитывает готовность fresh-полосы (она планируется
   независимо от tail backoff), поэтому fresh-строки не считаются «отложенными» из-за tail retry.

`services/memory_maintenance.py`: только docstring тика (причина по-прежнему пишется самим тиком;
подавление логов для silent-статусов не менялось, чтобы не дублировать строки).

## 4. Честные остатки / что НЕ доказано

1. **Живой эффект не измерен этим кандидатом.** Критерии (лаг между снимками падает, throughput >
   притока, fresh-полоса не отстаёт, нет `not_due`-сталлов > 1 ч) — повтор замера DevOps
   (≥24 ч после выката), как и записано в `lag-live-check-2026-11-25.md` §8. Здесь — только
   детерминированные тесты + чтение кода.
2. Разбивка `rows_by_chat` пишется для ≤16 чатов (`SEMANTIC_LAG_MEASURE_MAX_CHATS`); при большем числе
   чатов замер остаётся `partial`, планирование идёт по измеренной части (честная неполнота, не ноль).
3. Payload, записанный **до** фикса, не содержит `rows_by_chat`: первый тик использует fallback
   (`legacy_retry_due`/`legacy_actionable`); со следующего прохода разбивка точная.
4. Если дренаж доходит до нуля, планирование возвращается к продуктовой каденции (`daily`), как и
   раньше; «свежий поток» ускоряется только пока измеренный хвост > 0 (это и есть контракт E-LAG).
5. **Archive re-anchor** (`EXP-E-B03-N01`) не выполнялся — вне scope, остаётся nonblocking backlog.
6. Pre-existing fail `test_deep_sleep_not_mixed_with_lessons` не чинился (вне scope, не связано с
   планированием; правка «заставить текст не упоминать graph_facts» была бы косметикой вне контракта).
7. `next_retry_at` сохранён как «ближайший будущий retry»; истёкшие отражает новое поле
   `retry_due_chats`, поэтому старые потребители снимка не меняют трактовку.
