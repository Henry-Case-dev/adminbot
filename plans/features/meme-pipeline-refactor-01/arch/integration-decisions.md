## 1. Этапы на существующем пайплайне

- Точка входа остаётся `services/meme_initiative.py:1001 consider_chat`: `:1121-1130`
  (`_default_summarize`, `:1241`) — это этап **A (выжимка)**.
- **B (прикол)** — новый обязательный LLM-вызов **внутри `consider_chat`**, между проверкой
  непустой выжимки и броней квоты (`:1144` → `:1146`). Функция `_default_joke(llm, summary, *,
  budget, system_prompt, chat_id)`, тот же `llm.generate(..., module="initiative",
  step="meme_joke")`, свой таймаут ≤30 с (рядом с `SUMMARY_TIMEOUT_SECONDS`, `:1238`).
- **C (картинка)** — остаётся `:1166-1171` (`_default_image`, `:1285`), но получает промпт,
  собранный из шаблона + **прикола**, а не выжимки.
- Артефакт выжимки сегодня — только локальная переменная `summary` (`:1123-1130`), в БД не пишется;
  наружу попадают лишь итоговый промпт (`AttemptResult.prompt`, `:910`) и строка журнала.
- Порядок важен: B **до** `ledger.reserve` (`:1146`) — провал B не съедает платный слот, как и
  guard «генерация уже идёт» (`:1119`). Отвергнуто: отдельный модуль/воркер/капабилити мема;
  вызов B внутри `_default_summarize`; B после брони.

## 2. Бюджет длины — одна функция `resolve_meme_budget`

- Заменяет `resolve_length_limit` (`:386-418`), у которого `summary_target = L - prefix - 1`
  (`:410-411`) — арифметика верная, но приложена к **выжимке**. Одна функция
  `resolve_meme_budget(*, model_chars, admin, explicit, template) -> MemeBudget`: `L` = min
  кандидатов как сейчас (`initiative.meme_length_override`, `initiative.meme_length_limit`,
  capability модели — `:397-408`); `T = len(render(template, ""))`; `J = max(0, L - T)` (§3 ТЗ);
  `known=False`, если `L` неизвестен.
- **Плейсхолдер.** Шаблон поддерживает не более одного `{joke}`: есть — прикол подставляется на
  его место (T считается по `render(template, "")`); нет — историческое поведение
  `template + " " + joke`, `T = len(template) + 1` (совместимо с `MEME_IMAGE_PROMPT`, `:41`).
  Два и более `{joke}` → 422 при сохранении, в рантайме литерал + факт
  `template_placeholder_invalid`. Инвариант: `T + len(joke) ≤ L`.
- Инструкция модели: `joke_instruction = joke_prompt.strip() + "\n\n" + JOKE_LENGTH_DIRECTIVE`,
  где `JOKE_LENGTH_DIRECTIVE = "Сгенерируй прикол длиной не более {n} символов. Верни только
  текст прикола."` — дописывается **после** редактируемого промпта: правка в админке не отменяет
  потолок.
- Защитная обрезка — только fallback: `len(joke) > J` → обрезка по границе слова до `J`, факт
  `trimmed=true` и исходная длина. Отказа `exceeded_precomputed_limit` (`:432-433`) больше нет.
- Выжимка больше не ограничивается: `_default_summarize` вызывается с `target=None`, в payload нет
  `target_chars` (`:1263-1269`); `J<=0` → skip `no_joke_budget` **до** LLM-вызова B.
- Числа UI = числа рантайма: `web/api/routes.py:3959-3961` сегодня считает по заводской константе
  `mi.MEME_IMAGE_PROMPT`, а не по эффективному шаблону (чат-override/глобал) — это и есть источник
  расхождения. Обе стороны обязаны звать `resolve_meme_budget` с эффективным шаблоном.

  пустое/пробельное значение **проваливается на следующий слой** (пустота не обнуляет промпт).
  Инварианты реестра держим зелёными: `tests/test_soul1_registry_completeness.py:60-77` —

## 8. Что докажет приёмку

1. Матричный тест бюджета: без плейсхолдера / с `{joke}` / два плейсхолдера / `J=0` / `L`
   неизвестен / пустой шаблон.
2. Один и тот же шаблон → одинаковые `L/T/J` в payload витрины и в рантайме (сравнение вызовов).
3. Порядок этапов: провал B не вызывает image-провайдера и не создаёт бронь квоты.
4. Bypass-матрица `/meme`: квота 0, активный кулдаун, мало сообщений, промах random, выключенные
   тумблеры → публикация всё равно происходит; неготовый image-провайдер → честный skip-код.
5. Не-админ: ни ответа, ни удаления, ни генерации (журнал `manual` отсутствует).
6. Сбой `delete()` не мешает публикации; строки журнала — отдельные `summary/joke/image/publish`,
   у `joke` есть `limit` и `chars`.
7. Реестр/каталог: `test_evol018_prompt_audit`, `test_soul1_registry_completeness` зелёные,
   метки и печати обновлены в том же коммите.
8. Доставка: один вызов sender с изображением, без caption и без текстовых сообщений.
9. Живой прогон `/meme` в чате владельца (картинка пришла, команда исчезла) — наблюдение на
   стороне владельца (PET_PROJECT), агентская часть — существующим harness.

## 10. Автоудаление сообщения `/meme` (дополнение владельца 03.11.2026)

Источник: `plans/owner_inputs/2026-11-03-meme-command-autodelete.md`. Раздел уточняет §4 и
§6, не меняя ни пайплайн, ни правило выдачи результата.

### 10.1 Порядок в обработчике (заморожен)

`handlers/meme_command.py`, последовательность строго такая:

1. **RBAC** (`services/roles.py:140-220`, §4) — локальная проверка без сети. Не-админ:
   полная тишина, **ни удаления, ни пайплайна** (чужое сообщение не трогаем).
2. Разбор команды (`Command("meme")`; аргументы не используются и не парсятся).
3. **Удаление сообщения команды — первое сетевое действие обработчика**, до любого этапа
   пайплайна (`consider_chat`, LLM, провайдер картинки, запись журнала): след исчезает сразу,
   даже если пайплайн идёт десятки секунд или падает.
4. Пайплайн: `consider_chat(db, chat_id, manual=True, ...)` (§4).
5. Доставка: изображение при успехе, одно короткое сообщение при неуспехе (§6).

Удаление — `await message.delete()` (через `message.bot`, как `handlers/summary.py:663-677`),
ровно **один** вызов, без батча `deleteMessages` и без повторов. Ожидание ограничено
`DELETE_TIMEOUT_SECONDS = 5.0` (`asyncio.wait_for`): зависший сетевой вызов не отодвигает
старт пайплайна. Любой исход удаления (403, 400, таймаут, любое исключение) обработчик
переживает: **исключение не выходит наружу, запуск не отменяется, фоновая задача-добиватель
не создаётся**.

### 10.2 Куда уходит ответ

- В **тот же чат** (`message.chat.id`): он же источник чатовых настроек/оверрайдов пайплайна
  и адресат доставки. Подмены чата и хардкода «отправить в DM админу» нет.
- Ответ — **обычное новое сообщение, не reply**: `reply_parameters`/`reply_to_message_id` не
  передаются ни при успешном удалении, ни при сбое. Причины: (а) после удаления цель reply
  не существует и Telegram отвечает ошибкой на такую отправку; (б) исход доставки не должен
  зависеть от исхода удаления — иначе два разных поведения и удвоенные тестовые ветки.
  Прецедент ровно тот же: `handlers/info.py:80-102` (`deleted → reply_parameters=None`).
- Успех = только изображение, без caption и без follow-up: путь отправки
  `services/initiative_observer.py:1147-1171` не меняется (§6).

### 10.3 Telegram: что реально возможно (проверено 03.11.2026)

Официальный контракт `deleteMessage`
(<https://core.telegram.org/bots/api/methods/deletemessage.md>, Bot API, дата проверки
03.11.2026): сообщение удаляемо, только если отправлено **менее 48 часов** назад; сервисные
сообщения о создании супергруппы/канала/темы удалять нельзя; кубик в ЛС — только старше 24 ч
(к команде не относится); **бот может удалять входящие сообщения в личных чатах**; в группе —
только если бот администратор (в супергруппе — право `can_delete_messages`).

| Ситуация | Что делает бот | Что видит пользователь |
|---|---|---|
| ЛС или бот-админ в группе | один `deleteMessage`, INFO-лог | сообщение команды исчезает; картинка (успех) или одно короткое сообщение (неуспех) — как раньше |
| Бот не админ / нет `can_delete_messages` (403) | один вызов, WARNING, пайплайн продолжается | сообщение остаётся обычным сообщением; результат — как раньше, без упоминания удаления |
| Сообщение старше 48 ч (только при отложенной доставке апдейта после простоя/рестарта) | то же | то же |
| Сетевой сбой или таймаут 5 с | то же (таймаут логируется как сбой) | то же |
| Сообщение уже удалено автором | то же (WARNING с типом исключения) | ничего лишнего; результат — как раньше |

Никаких замен удаления «редактированием в пустое», никаких повторных попыток, никаких
компенсирующих сообщений: пользователь никогда не узнаёт о сбое удаления.

**Логи (единственное свидетельство):** при успехе —
INFO `[/meme] command deleted | chat=<id> msg=<id>`; при сбое —
WARNING `[/meme] command delete failed (<ТипИсключения>) | chat=<id> msg=<id>` без traceback
(причина детерминирована: нет прав / >48 ч / сеть; образец `handlers/summary.py:663-677`).
Токен, текст команды и содержимое пайплайна в лог не попадают (R17).

**В журнал попыток мемов удаление не пишется:** набор стадий §5 остаётся
`considered → eligible → summary → joke → image_generation → publish (+failed/skipped)`,
иначе аналитика получит несуществующий этап и поедет витрина.

### 10.4 Тестовый контракт (фейковый Telegram-клиент)

Фейк — расширение образца `tests/test_p0_meme_image_only.py:34-57` (`_RecordingBot`):
добавляется `delete_message(self, chat_id, message_id)`, пишущий `("delete", chat_id,
message_id)`, и флаг `fail_delete` (`TelegramBadRequest`/`RuntimeError`). **Все** фейки (бот,
суммаризатор, генератор прикола, провайдер картинки, sender) пишут в **один общий**
`events: list[str]` — иначе порядок «удаление раньше пайплайна» недоказуем.

Файл: `tests/test_meme_command_autodelete.py` (`PARALLEL_SAFE`, та же задача; bypass-матрица
§8.4 остаётся в `tests/test_meme_pipeline_refactor_01.py`). Обязательные проверки:

- **T1 — ровно один delete и он первый:** `events == ["delete", "summary", "joke", "image",
  "publish"]`; delete-вызовов 1, `message_id` равен id команды.
- **T2 — успех:** исходящий вызов ровно 1 — фото, текстов 0, `caption` отсутствует.
- **T3 — сбой удаления (`fail_delete`):** пайплайн всё равно исполняется (в `events` есть
  `summary`, `joke`, `image`, `publish`), исходящих ровно 1 — фото, текстов 0. Число
  исходящих вызовов **равно** T2.
- **T4 — сбой пайплайна:** при успешном удалении и при проваленном — исходящих ровно 1
  (короткий текст), фото 0; сообщений про удаление нет ни в одном случае.
- **T5 — отсутствие ретраев и проброса:** `await handler(msg)` завершается нормально, число
  delete-вызовов остаётся 1.
- **T6 — не-админ:** 0 delete, 0 исходящих, пайплайн не вызывался (в журнале нет строки
  `manual`).

Ассерты — по записанным вызовам в порядке их совершения и по строкам журнала попыток, а не по
факту «мок был вызван». Живая приёмка остаётся наблюдением владельца (PET_PROJECT, §8.10):
после `/meme` сообщение команды исчезло, картинка пришла.

### 10.5 Совместимость

- **Правило «успех = только изображение» не затронуто:** удаление касается исключительно
  входящего сообщения команды; путь отправки (§6) не меняется, поэтому действующие тесты
  `tests/test_p0_meme_image_only.py` остаются валидными, а новых текстов в чате не появляется.
- **Безопасность/RBAC не обходится:** гейт §4 выполняется ДО удаления; удаление не является
  проверкой прав и ничего не выдаёт; сбой удаления не расширяет ни один доступ и не меняет
  набор обходимых ограничений §4.
- **Нет хардкода под чат/пользователя:** чат берётся из апдейта, права — из `roles`, поведение
  одинаково в ЛС и в группе; различается только доступность удаления, и это свойство Telegram,
  а не ветвление в нашем коде.
- Риск дополнения — **R0** (локальное поведение обработчика: ни схемы, ни контракта доставки,
  ни бюджета не касается); общий риск задачи остаётся R2 (§9).
