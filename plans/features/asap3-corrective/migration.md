## 1. Итог: миграция данных не требуется

Новые сущности не заводятся, поэтому **ни DDL, ни UPDATE, ни INSERT в PostgreSQL не нужны**:

| Что | Как устроено сейчас | Запись в PG |
|---|---|---|
| `hint_limits` (лимит размера/количества) | Поле существующего документа `style.policy`. Отсутствие поля = `{max_chars: 0, max_items: 0}` = OFF (`style_policy.py::merge_hint_limits`); явный `0` — осознанный OFF слоя | не нужна |
| Правило «длинное тире» | Заводское `dash.hard.factory` **синтезируется в рантайме** в `effective_policy_sync`, если ни global, ни chat не содержат строку с этим id; `source=factory` | не нужна |
| Потолки привычек/правил (L2) | 64/64 в коде (`SOFT_INSTRUCTIONS_MAX`, `RULES_MAX`); превышение — fatal-диагностика, не молчаливая обрезка | не нужна |
| Новые ключи каталога параметров | Не добавлялись (§1.2 запрещает второй store/страницу) | не нужна |
| Алиасы | Те же ключи `limits.summary_aliases` (global) и чатовые override; меняется только **чтение** (merge по uid) | не нужна |

Единственное «заводское» изменение — **код** (значения по умолчанию и merge), а не
содержимое БД. Это совпадает с `arch-design.md` §11: «Factory: `dash.hard.factory`
в коде (PG не пишем), `hint_limits` отсутствует = OFF».

## 2. Какие значения считаются заводскими

| Параметр | Заводское значение | Где видно |
|---|---|---|
| `hint_limits.max_chars` | `0` (без ограничения) | «Стиль письма»: «Без ограничения»; Inspector: лимит/`off` |
| `hint_limits.max_items` | `0` (без ограничения) | там же; счётчики «входит N из M» |
| `dash.hard.factory` (`kind=dash`) | `enabled=true`, `strictness=hard`, `source=factory` | список правил «Стиль письма»; Inspector: точная редакция hint |
| `SOFT_INSTRUCTIONS_MAX` | `64`, превышение блокирует save | ошибка сохранения + `document.global_issues` |
| `RULES_MAX` | `64`, превышение блокирует save | там же (`rules_truncated`) |
| Остальные L3–L9 (бюджет композера, участники, thread depth, summary parts) | **не менялись** | видны там, где настраиваются; бюджет — `budget_excluded` в Inspector |

Проверка «заводскости» без БД: `sp.effective_policy_sync(None, None)` даёт
`hint_limits == {"max_chars": 0, "max_items": 0}` и активное `dash`-правило —
это покрыто `test_s1_...`, `test_s6_dash_is_replaced_in_plain_speech`,
`test_s6_dash_reaches_outbound_pass`.

## 3. Существующие настройки владельца

Ничего не перезаписывается и не «нормализуется» задним числом:

- `validate_document` делает round-trip: `hint_limits` (включая явный `0`),
  привычки, правила, пресеты, историю и ревизию возвращает без потерь
  (`test_hint_limits_round_trip_and_inheritance`).
- `save_policy_document` **сохраняет прежний `hint_limits`**, если редактор не
  прислал поле (правка правил в старом UI не стирает лимит); удаление — только
  явным `hint_limits` (`test_save_keeps_hint_limits_when_editor_omits_field`).
- UI отправляет **только собственные поля слоя** (`hint_limits.layers`), поэтому
  чатовая правка не «замораживает» унаследованные глобальные значения.
- Merge правил/привычек — по `id`; чатовое выключение `dash` — явная запись того
  же id с `enabled=false`, остальные правила не затрагиваются
  (`test_s8_disabled_dash_rule_does_not_touch_text`).
- Алиасы: merge по каждому `user_id`, чатовое значение перекрывает только свой
  id; удаление чатового возвращает глобальный; пустая строка не переименовывает
  (`test_a2/a3/a7`, `test_empty_alias_value_...`). Глобальной замены строк в БД
  нет — исторические сообщения, память, GraphRAG и досье не переписываются
  (§6, `test_a14`, `test_dossier_keeps_fact_with_stable_uid_after_rename`).

## 4. Идемпотентность и обратимость

- **Идемпотентность.** Повторный `validate_document` не меняет документ;
  повторный save не плодит `hint_limits` и не добавляет вторую строку `dash`
  (factory синтезируется только при отсутствии id); повторный проход тире —
  no-op (`again == out` в `test_s6_dash_is_replaced_in_plain_speech`).
- **Обратимость.** Откат кода возвращает прежнее поведение; данные в PG не
  менялись, поэтому откатывать нечего. Если владелец включил лимит — он остаётся
  в документе и после отката кода просто перестаёт учитываться старой версией
  (значение не теряется; при повторном накате снова действует).
- **Нет обязательного migration-script.** Запускать нечего; «миграция» — это
  деплой кода + проверка эффективной конфигурации (§5), а не операция с БД.

## 5. Прод-проверка после деплоя (read-only план, не выполнялся)

Порядок — только чтение; ни одного `UPDATE/INSERT`; живые сообщения в рабочие
чаты агент не отправляет (нужен отдельный владелец сессии/разрешение).

### 5.1 Доступность

1. `GET https://<prod-host>/healthz` → `200` (сервис жив; SSH не требуется).

### 5.2 Эффективная политика: лимиты OFF, `dash` активен

2. В сессии администратора Mini App: `GET /api/speech/style?chat_id=<CHAT>`.
   Проверить в ответе:
   - `hint_limits.max_chars == 0` и `hint_limits.max_items == 0`,
     `hint_limits.off == true` (если владелец не включал лимит);
   - `hint_limits.sources` — `default` для незаданных полей, `chat`/`global`
     только там, где значение реально задано;
   - `hint_limits.layers.chat == {}` для чата без override (глобальный слой не
     подменяет чатовый и наоборот);
   - в `rules` есть `dash.hard.factory` (`kind="dash"`, `enabled=true`,
     `source="factory"`), в `rule_kinds` присутствует `dash`;
   - `hint_render.total_items == included_items`, `excluded == []`,
     `overflow == false` — скрытой потери нет.
3. Повторить для второго чата: значения не зависят от первого.

### 5.3 Inspector показывает оба слоя и фактическую сборку

4. `GET /api/speech/inspector?chat_id=<CHAT>`:
   - `preview.style.documents` — `global_present`/`chat_present` и ревизии
     обоих слоёв;
   - `preview.style.hint_text` совпадает с блоком, который композер отдаёт
     моделью (слой `style_policy_hint`);
   - `preview.style.limits.off == true` (или фактический лимит владельца),
     `preview.style.excluded` пуст при OFF;
   - `sent.style.layer.state` — `rendered` либо честный `budget_excluded`/
     `absent`; `last_run_present` не выдумывается (`false` → «снимка хода нет»).

### 5.4 Алиасы (read-only, на сервере)

5. `python manage.py diag aliases --chat-id <CHAT>` — только SELECT:
   `global_present`, форма/число ключей, наличие чатового override, без значений.
6. `python manage.py diag aliases --chat-id <CHAT> --show-names` — локальный
   вывод merged-вида: по каждому uid `chat_alias`/`global_alias`/`effective`/
   `source`; `display_collisions` без слияния личностей. Записать вывод в
   evidence (не в публичный лог).

### 5.5 Прямые read-only SQL (если нужен снимок БД)

```sql
-- глобальные документы: наличие style.policy и форма алиасов
SELECT key, value FROM bot_settings
 WHERE key IN ('style.policy', 'limits.summary_aliases');

-- чатовые override: сам документ и его hint_limits
SELECT chat_id,
       chat_params -> 'overrides' -> 'style.policy'            AS style_doc,
       chat_params -> 'overrides' -> 'style.policy' -> 'hint_limits'
                                                              AS hint_limits
  FROM chat_profiles
 WHERE chat_params ? 'overrides';
```

Критерии PASS:
- в `style.policy` нет `hint_limits` с положительными значениями (если владелец
  их не включал); отсутствие поля допустимо и означает OFF;
- нет строки `dash.hard.factory` с `enabled=false` без решения владельца
  (иначе правило выключено — это уже не заводское состояние, зафиксировать);
- `limits.summary_aliases` не пуст и не изменился по форме (ключи прежние,
  значения не переписаны) — merge работает на чтении.

### 5.6 Изменение лимита/алиаса без рестарта (postdeploy, функциональная часть)

7. Лимит: в «Стиль письма» включить «Ограничивать количество инструкций» = `N`
   (существующий `POST /api/speech/style`), затем `GET /api/speech/inspector`
   **без перезапуска** → `preview.style.limits.max_items == N`,
   `included_items == N`, `excluded` называет не вошедшие, `overflow == true`.
8. Алиас: сохранить чатовый алиас в «Имена и алиасы», следующий ход бота в этом
   чате → `diag aliases --show-names` показывает `source=chat`/`effective` новый
   алиас, Inspector `sent.style` не содержит старого имени. Перезапуск не нужен.
9. Вернуть прежние значения (лимит OFF, алиас удалить) и убедиться, что
   наследование восстановилось (S4/S5/A7).

Шаги 7–9 требуют реального чата и выполняются DevOps/владельцем по политике
проекта; сеть/прод в этой полосе запрещены, поэтому здесь только план.

## 7. Критерий «миграция завершена»

Не по изменённому factory-default в коде, а по **эффективной конфигурации в PG +
Inspector** (§5.2–5.4):

1. эффективные лимиты — OFF (или явные значения владельца, не перетёртые);
2. `dash` активен как заводское правило, выключение возможно только явной
   записью владельца;
3. существующие инструкции, правила, пресеты и алиасы сохранены (формы/ревизии
   не обнулены, значения не переписаны);
4. изменение лимита и алиаса применяется без рестарта (следующий ход);
5. Inspector показывает оба слоя и фактическую сборку, а не «желаемые»
   настройки.
