## 2. Корневая причина: строки карты и аудит говорят о разных требованиях

Строки `SMR-INV-13..27` в карте построены из §3 владельческого документа `source-2026-11-10.md`: каждая строка — абзац расследования (`source_line` 93, 95, 97, 103, 108, 110, 112, 116, 120, 126, 128, 132, 134, 136, 138). То есть `SMR-INV-17` — это «текущий вопрос не заменяется Reply/расшифровкой/медиа/историей», а `SMR-INV-20` — «почему L1 выбирает видеозадачу и нет ли подмены решения после планирования».

Аудит же трактует те же ID как внутренние инварианты другого набора: `INV-13` — capability detection, `INV-17` — бюджеты генерации изображений, `INV-18` — параллельная волна, `INV-19/20` — adaptive chain и `ChainBudget`, `INV-21/22` — L1-контекст и его бюджет, `INV-23/24` — память расшифровок.

Подтверждение, что это рассинхронизация ID, а не ошибка карты:
- карта впервые появилась в коммите `620e7800` (2026-11-10 03:59 +1200), аудит датирован **2026-11-09**, то есть написан до этой карты;
- в релизной линии `34213999 → 2b7e9c7f` карты `plans/features/smart-module-semantic-routing/requirements-map.json` не существует ни в одном коммите (проверено `git show 68267d89:...`, `f4115214:...` — путь отсутствует);
- поиск `detect_action_intent` и текста acceptance `SMR-INV-17` по истории карты даёт единственный коммит — `620e7800`.

Вывод: ID были переиспользованы под новый источник, аудит остался привязан к смыслу прежнего набора. Привязка доказательств по такому аудиту приписала бы строкам §3 владельческого ТЗ чужие доказательства.

## 4. Отдельно: SMR-IMG-06 и вопрос allowlist

**Acceptance строки карты:** «Tool Calling и исполнение `generate_image` проверены как отдельный обходной путь: инструмент вызывается только по подтверждённому намерению (L1 или явная команда), а не по лексическому совпадению».

Факты в `2b7e9c7f`:

1. Единственная детерминированная дверь — явная команда: `services/direct_chat_service.py:10845–10846` (`if not image_generation.is_image_keyword(query): return ""`), сам регекс — `services/image_generation.py:130–137`, обёртка `is_image_keyword` — 228–237 (обращение «бот» + императив рисования, с отменой в той же реплике).
2. Пре-гейт выставляет маркер прогона: `4059–4063` (`image_block = await self._image_pre_gate_block(...)`, `image_pre_gate_fired = bool(image_block)`).
3. У лексики нет авторитета: `services/direct_capabilities.py:415–419` (`INTENT_CREATE_IMAGE` детектором не выдаётся) и `459–475` (словари `_DRAW_VERB_*`/`_IMAGE_OBJECT` удалены), `_image_capability_gate` детектор не вызывает — `direct_chat_service.py:10671–10696`.
4. `tool_choice` не форсируется: `direct_chat_service.py:10829` и `image_generation.py:116–118`.
5. Tool-путь исполняется только по вызову модели/плана L1, плюс защита от двойной генерации на ходу: `services/tool_router.py:5258–5267` (`ctx.image_request_handled` → `{"status":"skipped","reason":"already_handled"}`), маркер ставится в `direct_chat_service.py:4860–4865`.
6. Живая проба выката (артефакт `p0-release-2.58.176.md`, строки 177–181): команда «Бот, нарисуй …» → `is_image_keyword=True`; фраза про мангу («…её японцы рисуют…») → `is_image_keyword=False`, `detect_action_intent` даёт пустой intent, `_image_capability_gate=False`, отправлено 0 сообщений.

**Поправка к аудиту (существенная).** Утверждение аудита «`image capability` не передаётся в `tool allowlist`» верно только для хода, на котором сработал пре-гейт команды: `direct_chat_service.py:4448–4449` (`if image_pre_gate_fired: image_enabled = False`) убирает `generate_image` из `active_tools` (`4453–4456`, `services/tool_schemas.py:1099–1134`). **На обычной фразе инструмент в наборе остаётся**, если включён модуль: `resolve_module_enabled` (`image_generation.py:256–273`) по умолчанию True (`config/settings.py`: `IMAGE_GENERATION_ENABLED` и `IMAGE_GENERATION_MODULE_ENABLED` default ON), а провайдерская готовность в анонс не входит. То есть «capability отсутствует в allowlist на обычном предложении» — **неверно**; верно другое: лексика больше не решает генерацию, а вызов требует выбора L1 либо явной команды.

**Второй мёртвый аргумент аудита.** «Когда capability fires → `image_enabled=False`, `image_pre_gate_fired=True`» (`3440` в аудите) в выкаченном дереве соответствует `4732–4736`, но эта ветка недостижима: `_l1_capability_consistency` больше не выполняет генерацию и не выставляет `fired` (`direct_chat_service.py:10743–10748`, `10794`, `10815` — возврат `fired` всегда False). Опираться на неё как на действующий механизм нельзя.

**Вердикт по SMR-IMG-06:** acceptance строки (вызов только по подтверждённому намерению, не по лексическому совпадению) подтверждается пунктами 1–6, поэтому строка привязана — но с явной фиксацией, что формулировка аудита про allowlist неверна. Если владелец подразумевал именно отсутствие capability в наборе инструментов на обычной фразе, требование **не выполнено** и строку следует вернуть в PENDING/FAILED отдельным решением.
