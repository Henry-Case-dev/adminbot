# P0 CORRECTIVE: NOSTALGIA REWORK + POST-ASAP5 DEFECTS

**Тип:** обязательная корректировка существующего релиза  
**База:** production 2.58.135, релизная ветка `release/p0-2026-10-26`  
**Назначение:** исправление архитектурных дефектов, удаление семантического хардкода, переработка механизма Ностальгии  
**Очередь:** последняя задача после уже зарегистрированной POST-ASAP5 и остальных незавершённых поручений  
**Приоритет внутри задачи:** P0 для подтверждённых дефектов, остальное - по порядку разделов

## 0. Основное распоряжение

Текущая реализация Ностальгии неудовлетворительна по архитектуре.

ASAP 5 устранил ряд ошибок, но вместо полноценного решения проблемы смысловой релевантности частично добавил проверки конкретных текстовых выражений.

Это недопустимо.

**Категорически запрещено исправлять семантическое поведение LLM-бота перечислением фраз, на которые модель должна реагировать определённым образом.**

Нельзя подменять понимание смысла регулярными выражениями, словарями ожидаемых формулировок или правилами, написанными специально под конкретные сообщения из Telegram.

При этом запрет не распространяется на технически оправданную детерминированную логику: парсинг идентификаторов, дат, JSON, Telegram-структур, служебных протокольных маркеров, проверку прав, состояний и иных формальных контрактов.

Разграничение строгое:

- Смысл, релевантность, связность, интересность, коммуникативное намерение - семантическая задача.
- Даты, идентификаторы, происхождение сообщений, SQL-диапазоны, статусы и права - детерминированная задача.
- Проверка фактической связи источников - задача доказательств и provenance.
- Формулирование естественной реплики - задача LLM с действующим Personality Core.

Не переносить семантическую проблему в другой словарь или условный оператор.

Не добавлять новый Decision Making, альтернативный пайплайн Ностальгии, независимый речевой движок или второй источник истины.

Нужно исследовать и расширить уже работающую архитектуру.

### 0.1. Перед началом работ

Провести read-only сверку текущей реализации и существующих требований.

Сверить также решения предыдущих ASAP и P0 DELTA.

Найти уже существующие механизмы извлечения эпизодов, их продолжений, хронологии, источников и связей между участниками.

**Если пригодный механизм существует, использовать его, а не реализовывать второй.**

Результатом начального аудита должна стать конкретная карта:

1. Что уже существует и используется.

5. Какие ранее принятые требования затрагиваются.

Не превращать аудит в самостоятельную бесконечную фазу.

После установления фактических зависимостей переходить к реализации.

# ЧАСТЬ I. ПОЛНАЯ ПЕРЕРАБОТКА НОСТАЛЬГИИ

## NOST-01. Удалить семантический хардкод ASAP 5

В `nostalgia_prompts.py` реализованы:

- `_SELF_DECLINE_VERDICT_RES`
- `_SELF_DECLINE_NOTHING_RE`
- `_SELF_DECLINE_NOTHING_REV_RE`
- `_SELF_DECLINE_ALL_RES`
- `is_self_declining_text()`

В `nostalgia_worker.py` результат этой проверки используется для подавления публикации.

Существующая реализация ориентируется на конкретные выражения вроде "не та история" и "вспоминать нечего".

**Удалить эту семантическую эвристику из рабочего пути полностью.**

Не заменять её:

- Другими регулярными выражениями.
- Перечнями синонимов.
- Поиском определённых смысловых слов.
- Чёрными списками формулировок.
- Специальными исключениями для конкретных событий.
- Скрытым набором шаблонов "плохого воспоминания".
- Новым детерминированным классификатором связности текста.

Сохранить формальный контракт отказа `UNCHANGED`, поскольку это машинный управляющий результат, а не попытка определить смысл человеческого текста.

Модель должна принимать решение о содержательной пригодности воспоминания до публикации через существующий механизм LLM/Decision.

Если решение отрицательное, пользователь не должен получать сообщение с объяснением отказа.

Не создавать отдельный публичный ответ "вспоминать нечего".

Отказ означает отсутствие публикации.

При необходимости скорректировать контракт существующего LLM-вызова, чтобы решение об отказе и готовый текст не противоречили друг другу.

Допустимо возвращать типизированный результат принятого решения через существующий вызов, если это совместимо с остальным runtime. Не создавать ради этого новый независимый сервис.

## NOST-02. Отказаться от модели "один год назад - три ближайших сообщения"

Сейчас используется примерно следующая схема:

`now - 365 суток → временное окно → 3 ближайших сообщения → вес 0.7 → LLM`

Она не обеспечивает поиск интересных событий.

Близость сообщения к конкретному часу ничего не говорит о его содержательной ценности.

Новая система должна работать с **историческими периодами и событиями**, а не только с отдельными строками переписки.

### 2.1. Поиск по нескольким годам

Ностальгия должна использовать всю доступную глубину архива.

Обязательно поддержать поиск:

- Год назад.
- Два года назад.
- Три года назад.
- Более ранние годы, если архив действительно содержит соответствующие сообщения.

Количество доступных исторических лет определять по реальным границам данных конкретного чата.

Не считать, что история каждого чата начинается в одном и том же году.

Не создавать жёсткую конструкцию из трёх SQL-запросов, где каждый запрос соответствует конкретному году.

Механизм должен формировать исторические периоды динамически.

В частности, для архива с 2022 года в 2026 году могут рассматриваться материалы за 2022, 2023, 2024 и 2025 годы.

Для чата, созданного в 2025 году, система не должна пытаться искать события за 2022 год или выдавать отсутствие результата за ошибку.

Отсутствие материалов за конкретный год не должно запрещать поиск по другим годам.

### 2.2. Корректная календарная арифметика

Не использовать `365 * 86400` как универсальную замену календарного года.

Учитывать:

- Високосные годы.
- Часовой пояс чата.
- Переходы календарных дат.
- Исторические периоды на границе месяцев.
- Эпизоды, переходящие через Новый год.

Дата исторической годовщины должна вычисляться календарно, а не простым вычитанием секунд.

При невозможности однозначно сопоставить дату, например 29 февраля с невисокосным годом, использовать документированное календарное правило. Не изменять даты исходных сообщений.

Время публикации исторической реплики не должно создавать впечатление, что событие происходило именно в этот час, если это не подтверждено.

## NOST-03. Адаптивные временные окна

Искать события исключительно в пределах нескольких часов вокруг годовщины недостаточно.

Исторический эпизод может происходить:

- В течение нескольких минут.
- За один день.
- На протяжении недели.
- В течение нескольких недель.
- На протяжении целого месяца.

Новая система должна поддерживать адаптивный временной поиск.

### 3.1. Уровни детализации

Использовать последовательное расширение области исследования.

**Уровень A - календарный день.**

Исследовать исторический день целиком, а не только час, соответствующий текущему времени.

**Уровень B - неделя.**

Если в пределах одного дня найден фрагмент события, проверить связанные сообщения за соседние дни.

Также допускать исследование полной исторической недели при наличии соответствующего повода.

**Уровень C - месяц.**

Если событие развивалось продолжительное время, исследовать подходящий исторический месяц, включая связанные события на его границах.

Не трактовать месяц исключительно как 30 последовательных дней.

**Уровень D - продолжение события.**

Если установлена содержательная связь между сообщениями за пределами первоначального окна, разрешить расширение периода по фактической продолжительности события.

Например, обсуждение могло начаться в конце одного месяца и завершиться в начале следующего.

Не обрывать историю механически на календарной границе.

### 3.2. Принцип расширения

Расширение должно зависеть от найденного материала.

Не требуется каждый раз читать целиком все месяцы каждого года.

Алгоритм обязан:

1. Найти потенциальные события в доступных временных периодах.
2. Определить, требуют ли они исследования соседних сообщений.
3. Восстановить необходимый контекст.
4. Остановить расширение, когда дальнейшие сообщения перестают относиться к событию.
5. Сохранить фактические границы найденного эпизода.

Временная близость сама по себе не является доказательством принадлежности сообщений к одному событию.

**Два сообщения из одной недели не обязательно описывают одну историю.**

### 3.3. Адаптивность обязательна

Нельзя заменить старую фиксированную выборку тремя новыми фиксированными окнами, из которых произвольно выбирается самое широкое.

Необходим именно адаптивный поиск.

День, неделя и месяц - масштабы исследования, а не три обязательные стадии, которые всегда выполняются полностью.

## NOST-04. Исторический эпизод вместо отдельного сообщения

Центральное изменение архитектуры.

**Основной единицей смыслового отбора должен стать связный эпизод.**

Эпизод может состоять из одного сообщения, если оно самодостаточно и содержательно интересно.

Но он также может включать несколько связанных сообщений, длительный диалог, повторяющуюся ситуацию, изменение отношений или развитие конфликта.

Не вводить обязательное минимальное число сообщений.

### 4.1. Использовать существующую память

Исследовать возможность повторного использования:

- `mca_episodes`
- связей между эпизодами
- существующих story-структур
- GraphRAG
- фактов памяти
- сырых сообщений
- reply-связей
- идентичности участников
- существующих средств исторического поиска

Приоритет отдавать проверяемым структурам, для которых можно восстановить первичные сообщения.

L2, готовые истории и lore допускаются как навигационные подсказки и вспомогательный материал, но не как самостоятельные подтверждения исторических событий.

Не считать готовую художественную историю доказательством фактов.

Не создавать второе постоянное хранилище эпизодов, если существующее можно использовать.

### 4.2. Реконструкция истории

Для найденного кандидата необходимо установить:

- Что произошло или обсуждалось.
- Кто участвовал в разговоре.
- Какие сообщения относятся к одному сюжету.
- Когда начался эпизод.
- Как он развивался, если развитие действительно присутствует.
- Чем завершился, если завершение известно.
- Почему этот эпизод представляет интерес сейчас.

Отсутствующие части истории не достраивать вымыслом.

Нельзя выводить причинно-следственную связь только из соседства сообщений.

Нельзя превращать случайный набор реплик в единый сюжет ради получения красивого текста.

Нельзя смешивать нескольких участников из-за похожих имён.

### 4.3. Продолжительные события

Поддержать случаи, когда событие развивалось в течение нескольких дней или недель.

Необходимо различать:

- Одно событие с несколькими стадиями.
- Несколько самостоятельных событий с общей темой.
- Повторяющуюся ситуацию.
- Независимые сообщения, оказавшиеся рядом по времени.

Связи должны происходить из данных, а не создаваться ради драматургии.

### 4.4. Не превращать всё в хронологию

Реконструкция истории необходима для правильного понимания материала.

Это не означает, что итоговое сообщение обязано пересказывать весь эпизод от начала до конца.

Иногда наиболее удачный результат - короткая ремарка об одной характерной детали.

Иногда - полноценное воспоминание о развитии ситуации.

Выбор формы остаётся за существующим речевым механизмом.

## NOST-05. Пересмотреть критерии интересности и релевантности

Сейчас у кандидата есть фиксированный вес, определяемый преимущественно его происхождением.

Такой подход неадекватен.

В частности, историческое сообщение из календарного окна получает вес независимо от того, содержит ли оно что-то интересное.

Необходимо пересмотреть `_pick_candidate`, `_threshold` и связанные функции отбора.

### 5.1. Что считается пригодным материалом

Оценивать кандидата по содержательным характеристикам:

**Связность:** можно ли из источников выделить законченную мысль или понятный эпизод.

**Контекстная релевантность:** существует ли осмысленная связь с текущей беседой.

**Самостоятельная интересность:** представляет ли эпизод интерес без связи с сегодняшней темой.

**Характерность:** раскрывает ли эпизод привычки, отношения, противоречия, характер участников или историю сообщества.

**Развитие:** содержит ли материал содержательную последовательность, изменение или неожиданный поворот.

**Узнаваемость:** можно ли связать эпизод с людьми, обстоятельствами или местными мемами, известными чату.

**Надёжность:** достаточно ли источников для утверждений, которые могут прозвучать в итоговом тексте.

**Новизна:** не повторяет ли кандидат уже недавно опубликованное воспоминание.

Это смысловые критерии, а не обязательный перечень признаков для каждого события.

Не требовать наличия всех характеристик одновременно.

Не вводить жёсткую формулу, в которой каждое качество выражается произвольно выбранным числом.

Допускаются технические ранжирующие признаки для предварительного отбора, но окончательное решение о пригодности не должно сводиться к фиксированной арифметике.

### 5.2. Не подменять интересность активностью

Количество сообщений не равно ценности эпизода.

Длительный бессмысленный спор не обязательно интереснее короткой запоминающейся реплики.

Количество участников также не является универсальным признаком интересности.

Мат, конфликт, токсичность и резкость не должны автоматически увеличивать или уменьшать ценность события.

Не вводить морализаторство или фильтрацию тем.

### 5.3. Связь с текущей беседой

Существуют два равноправных сценария.

**Контекстное воспоминание:** бот замечает связь между текущим разговором и прошлым эпизодом.

**Самостоятельное воспоминание:** бот вспоминает интересное событие, которое само по себе заслуживает внимания, даже если тема сегодняшнего разговора другая.

Ни один сценарий не должен полностью вытеснять другой.

Для контекстного сценария учитывать содержание текущего разговора, а не только последние пять сообщений в виде набора отдельных слов.

Для самостоятельного сценария требовать достаточной содержательной ценности события.

Не заставлять бота искусственно привязывать любое воспоминание к текущему сообщению.

## NOST-06. Поиск по всей истории, а не только по годовщинам

Механизм исторических годовщин важен, но не должен быть единственным способом найти воспоминание.

Если участники сегодня обсуждают определённую тему, бот может вспомнить связанный эпизод двухлетней или трёхлетней давности, даже когда он произошёл в совершенно другой месяц.

Поэтому поддержать два режима поиска:

1. **Календарный:** подходящие события в исторические дни, недели или месяцы предыдущих лет.
2. **Тематический:** события за всю доступную историю, связанные с содержанием текущего разговора.

Оба режима должны использовать общие средства поиска, реконструкции эпизодов и оценки кандидатов.

Не реализовывать два независимых движка Ностальгии.

Выбор режима и кандидата должен зависеть от ситуации.

Нельзя гарантированно предпочитать календарное совпадение тематически более уместному воспоминанию.

Также нельзя запрещать самостоятельные исторические воспоминания при отсутствии тематического совпадения.

## NOST-07. Источники и историческая достоверность

Использовать действующий provenance-механизм.

Строго различать:

- Собственные сообщения участников.
- Пересланные публикации.
- Внешние новости.
- Цитаты третьих лиц.
- Сообщения бота.
- Сводки памяти.
- Пересказы L2.
- Lore.
- Непосредственные исторические свидетельства.

### 7.1. Пересланные публикации

Репост внешней новости не становится личным событием автора пересылки.

Персона, упомянутая во внешней новости, не становится участником чата.

Обсуждение новости участниками может быть полноценным историческим событием чата.

При реконструкции сохранять эту разницу.

Не использовать содержимое новости как подтверждение биографии участника чата.

### 7.2. Self-echo

Собственные предыдущие ответы бота не должны превращаться в независимое подтверждение события.

Если бот однажды выдумал историю, дальнейшее повторение этой истории не делает её достоверной.

Сохранить действующую защиту P0 от self-echo и проверить её на новом механизме поиска.

### 7.3. Идентичность участников

Основной идентификатор - Telegram user ID.

Использовать уже установленную последовательность выбора имени:

1. Алиас текущего чата.
2. Глобальный алиас.
3. Актуальный никнейм.
4. Username.
5. Резервное представление идентичности.

Старые имена должны оставаться пригодными для поиска по истории, но не должны подменять актуальные алиасы при формировании ответа.

Не переписывать исторические сообщения.

### 7.4. Недостаток данных

Не заполнять пробелы домыслами.

Если источник позволяет установить только фрагмент обсуждения, не придумывать начало, причины и развязку.

Система должна иметь право отказаться от публикации.

При этом не нужно превращать обычную разговорную реплику в научную работу с обязательными оговорками и ссылками.

Источники используются для внутренней проверки.

## NOST-08. Отбор, разнообразие и повторяемость

Расширение исторического поиска не должно приводить к постоянному выбору одних и тех же событий.

### 8.1. Не зацикливаться на одном периоде

При наличии нескольких сопоставимо интересных кандидатов обеспечивать разнообразие исторических периодов.

Не создавать правило, что каждый год обязан появляться с одинаковой частотой.

Период выбирается по содержанию, а не ради статистической равномерности.

### 8.2. Не повторять одну историю

Перед публикацией учитывать уже опубликованные воспоминания.

Использовать существующие журналы отправки и идентичность эпизода.

Если одинаковая история была извлечена из разных сообщений или разных представлений памяти, это всё равно одно событие.

Повторный рассказ допустим при наличии нового существенного контекста или самостоятельного нового повода.

Не использовать исключительно буквальное сравнение текстов: один и тот же эпизод можно сформулировать разными словами.

### 8.3. Не создавать искусственную новизну

Не компенсировать отсутствие новых кандидатов:

- Пересказом старой истории другими словами.
- Добавлением вымышленных подробностей.
- Соединением независимых сообщений.
- Принудительным упоминанием случайного участника.
- Необоснованной драматизацией.

Если подходящего повода нет, Ностальгия молчит.

## NOST-09. Формирование естественной реплики

Ностальгия не должна иметь обязательный литературный шаблон.

Не предписывать каждый раз:

- Начинать с "кстати".
- Использовать одинаковую вводную конструкцию.
- Перечислять события по датам.
- Объяснять, почему событие интересное.
- Писать обязательно коротко.
- Писать обязательно длинно.
- Заканчивать афоризмом.
- Добавлять шутку.
- Упоминать участника по имени.
- Строить причинно-следственную историю там, где её нет.

Сохранять действующий Personality Core, настройки стиля, режим мата, характер общения и свободу выражения.

Содержательное воспоминание может выглядеть как короткая ремарка, наблюдение, история, шутка или естественное продолжение разговора.

Единственное универсальное требование к форме: сообщение должно иметь смысл в контексте собственного содержания.

Не вводить морализаторство, искусственную вежливость, обязательные предупреждения или запреты на грубый юмор.

### 9.1. Переработать системные инструкции

Проверить оба действующих канона:

- `NOSTALGIA_PROMPT`
- `NOSTALGIA_CORE_CANON`

Убрать предпосылку, что память всегда состоит из нескольких сообщений годичной давности.

Не закреплять жёсткую литературную форму "обычно 1-2 короткие фразы кстати".

Обеспечить совместимость с SOUL-1 и Composer.

Не переписывать Personality Core.

### 9.2. Пересмотреть скрытые ограничения длины

Проверить `_MAX_WORDS`, `nostalgia_max_send_chars` и связанные ограничения.

Не позволять внутренним константам незаметно превращать содержательное воспоминание в обрезанный текст.

Сохранить техническую безопасность отправки сообщений.

Если существуют пользовательские настройки длины, соблюдать их.

Не вводить новые скрытые ограничения и не изменять уже выбранные владельцем настройки без необходимости.

## NOST-10. Использование существующего Decision Making

Ностальгия уже делегирует кандидатов в существующий механизм инициативы через `handle_initiative`.

Сохранить эту архитектуру.

Целевой маршрут:

**Исторический поиск → связные кандидаты → оценка пригодности → готовая реплика или отказ → существующий Decision/Initiative → публикация или молчание.**

Это логические этапы, не обязательное требование создавать отдельный Python-сервис для каждого.

Уточнить ответственность каждого существующего компонента.

Нельзя:

- Создавать второго Observer.
- Создавать нового независимого Decision Making.
- Делать параллельную отправку вне Initiative.
- Передавать в Initiative заведомо неподходящее воспоминание с надеждой, что транспорт исправит его содержимое.
- Создавать дополнительную LLM-цепочку только ради имитации более глубокого анализа.

Сначала исследовать, можно ли совместить оценку пригодности и формирование реплики в текущем LLM-вызове.

Если потребуется изменить форму структурированного ответа модели, сохранить совместимость со штатными механизмами отказа, логирования и доставки.

При техническом сбое не публиковать случайный резервный факт.

## NOST-11. Эффективная работа с большим архивом

В больших чатах могут храниться сотни тысяч или миллионы сообщений.

Переработка не должна означать чтение всей истории каждого чата при каждом тике.

### 11.1. Поэтапное извлечение

Использовать:

- Индексируемые временные диапазоны.
- Существующие поисковые индексы.
- Предварительно выделенные эпизоды.
- Связи GraphRAG.
- Семантический поиск.
- Выборочное раскрытие первичных сообщений.

Не отправлять в LLM сырой месячный архив без отбора.

### 11.2. Сначала отбор, затем детализация

Получить набор потенциальных событий.

Проверить их содержательную ценность.

Для перспективных кандидатов запросить дополнительный исторический контекст.

Не делать дорогостоящую глубокую реконструкцию для каждого случайного сообщения.

### 11.3. Не терять важное из-за первых строк

Не использовать `LIMIT` таким образом, чтобы все кандидаты приходили из начала или конца исторического периода.

При необходимости применять временную стратификацию, уже существующие эпизоды и подходящие поисковые индексы.

Выборка должна покрывать исследуемый исторический период, а не только его наиболее удобную для SQL часть.

### 11.4. Ошибки отдельных источников

Недоступность одного источника памяти не должна автоматически останавливать всю систему, если оставшиеся данные позволяют восстановить достоверный эпизод.

Но нельзя выдавать частичный результат за полное исследование архива.

Сохранять существующие механизмы обработки ошибок и восстановления.

Не создавать второй глобальный кеш памяти без необходимости.

## NOST-12. Настройки админки

Проверить существующий раздел "Ностальгия".

Сохранить уже работающие настройки:

- Включение/выключение.
- Периодичность.
- Тихие часы.
- Cooldown.
- Суточную частоту публикации.
- Паузы после неотвеченных сообщений.
- Агрессивность отбора.
- Действующие настройки речи.

Новые параметры добавлять только там, где они действительно нужны для управления поведением системы.

Обязательно обеспечить:

**Глубина исторического поиска.** Возможность использовать автоматически доступный архив, с необязательным пользовательским ограничением глубины.

**Временное исследование.** По умолчанию адаптивное: день, неделя, месяц и необходимое продолжение эпизода.

**Диагностика.** Понятное отображение реальных результатов последнего запуска.

В диагностике показывать:

- Какие исторические периоды исследованы.
- Какие источники памяти использованы.
- Сколько кандидатов найдено.
- Был ли выбран содержательный эпизод.
- Почему публикация состоялась или была отклонена.
- Какой механизм доставки использовался.
- Была ли ошибка доступа к архиву.
- Не является ли результат повтором ранее опубликованной истории.

Диагностика должна отражать фактические runtime-данные.

Не создавать декоративные показатели, которые всегда показывают успех.

Не раздувать админку множеством второстепенных тумблеров.

Изменения настроек должны применяться штатным способом без рестарта, если соответствующая система конфигурации это допускает.

# ЧАСТЬ II. КРИТЕРИИ ПРИЁМКИ НОСТАЛЬГИИ

## NOST-13. Проверки поиска по годам

Обязательные сценарии:

**T1.** Архив содержит один полный исторический год. Поиск не обращается к отсутствующим годам.

**T2.** Архив содержит три исторических года. Рассматриваются все доступные соответствующие периоды.

**T3.** Архив содержит историю более трёх лет. Поиск не обрывается искусственно на третьем году.

**T4.** Архив содержит пропущенный год. Другие периоды продолжают обрабатываться.

**T5.** Архив начинается или заканчивается посреди года. Пустые периоды не считаются ошибкой.

**T6.** Исторический период включает 29 февраля или смену года. Календарное сопоставление корректно.

**T7.** Событие произошло утром, а текущий тик выполняется вечером соответствующего дня. Сообщения доступны независимо от часа тика.

## NOST-14. Проверки длительности событий

**T8.** Самодостаточное интересное сообщение в пределах одного дня может стать полноценным кандидатом.

**T9.** Диалог растянут на несколько часов. Его части могут быть собраны в один эпизод.

**T10.** Обсуждение продолжается три дня. Связанные части доступны реконструкции.

**T11.** Событие развивается на протяжении недели.

**T12.** Событие начинается в конце месяца и заканчивается в следующем.

**T13.** В пределах одного дня существуют несколько несвязанных обсуждений. Они не объединяются автоматически.

**T14.** Два разных события с одними участниками и похожей темой не становятся одной историей без подтверждённой связи.

**T15.** Сообщения одного эпизода разнесены по времени, но имеют явные связи. Эти связи не теряются.

## NOST-15. Проверки смысловой релевантности

Проверять не конкретные ожидаемые фразы, а свойства результата.

**T16.** В архиве есть случайный малозначимый факт и полноценный связный эпизод. Выбор не определяется одной лишь близостью первого факта к годовщине.

**T17.** В текущей беседе обсуждается тема, которой посвящён старый эпизод вне календарной годовщины. Тематический поиск может найти его.

**T18.** Исторический эпизод интересен сам по себе. Он не обязан искусственно связываться с текущей темой.

**T19.** В памяти есть только разрозненные случайные сообщения. Система может отказаться от публикации.

**T20.** Эпизод содержит краткую, но характерную реплику. Он не отбрасывается только из-за малого размера.

**T21.** Эпизод содержит много сообщений без содержательного развития. Количество сообщений само по себе не обеспечивает выбор.

**T22.** Результат содержит утверждения, которых нет в источниках. Такой результат не принимается за достоверное воспоминание.

**T23.** LLM отвергла публикацию. В чат не уходит объяснение отказа.

## NOST-16. Проверки независимости от конкретных фраз

Обязательно проверить, что:

- Решение не зависит от наличия фраз "не та история", "вспоминать нечего" и их синонимов.
- Семантический хардкод старой реализации удалён.
- Содержательные ироничные реплики не подавляются из-за случайного совпадения слов.
- Бессвязный текст не становится допустимым исключительно потому, что не содержит известных запрещённых выражений.
- Изменение конкретных имён, дат и предметов обсуждения не нарушает общую логику.
- Тесты не используют полный текст ранее показанного production-инцидента как единственный критерий успеха.

Запрещены "зелёные" тесты, которые доказывают только точное совпадение подготовленной тестовой фразы с написанным под неё условием.

Нужны сценарии, проверяющие архитектурный контракт.

В тестах с LLM-моками разделять проверку маршрута и проверку реального качества семантического решения.

Не объявлять семантическое качество доказанным только потому, что мок вернул ожидаемое значение.

## NOST-17. Проверки происхождения и идентичности

**T24.** Пересланная новость остаётся внешней публикацией.

**T25.** Обсуждение внешней новости участниками допускается как самостоятельный эпизод чата.

**T26.** Исторический алиас не подменяет актуальное имя участника.

**T27.** Два участника с одинаковым именем не объединяются.

**T28.** Старый ответ бота не используется как независимый источник для подтверждения события.

**T29.** Готовый Lore-пересказ без первичных свидетельств не становится подтверждённым фактом.

**T30.** Событие с неизвестным завершением не получает придуманную развязку.

## NOST-18. Сквозные регрессии

Проверить совместимость:

- Nostalgia → Initiative.
- Nostalgia → Decision.
- Nostalgia → Personality Core.
- Nostalgia → Authorial Speech.
- Nostalgia → Memory.
- Nostalgia → GraphRAG.
- Nostalgia → provenance.
- Nostalgia → alias resolution.
- Nostalgia → admin settings.
- Nostalgia → журналы и диагностика.
- Nostalgia → сценарии активной и неактивной беседы.

Не выполнять тестовые публикации в рабочих Telegram-чатах.

Реальные технические проверки проводить через существующие разрешённые средства, изолированный стенд или read-only диагностику.

Owner Live Checks остаются необязательными и не блокируют инженерное завершение задачи.

# ЧАСТЬ III. ОСТАЛЬНЫЕ ДЕФЕКТЫ ПОСЛЕ ASAP 5

Следующие пункты входят в тот же corrective.

Не создавать для них новые независимые эпики.

## COR-01. Image Edit: единая конфигурация

Обнаружена несогласованность:

`capability_registry._build_image_edit()` учитывает настройки чата, а `tool_router._edit_image()` использует глобальные значения через `image_generation._resolve_str()`.

Требование:

- Проверка возможности и исполнение должны использовать один effective-набор настроек.
- Настройки конкретного чата должны учитываться одинаково на обоих этапах.
- Фактический провайдер исполнения должен совпадать с провайдером, способность которого была проверена.
- Исправить возможную потерю исходного формата при сохранении изображения во временный файл `.png`.
- Не создавать новые конфигурационные системы.

Проверить минимум два чата с различными настройками провайдеров.

## COR-02. Image Intent: семантическое определение редактирования

Текущий `direct_capabilities.py` содержит словари `_EDIT_VERB`, `_EDIT_REMOVE` и выражение `_EDIT_LOCATIVE_RE`.

Не расширять эти словари ради покрытия очередных пользовательских фраз.

Пересмотреть роль детерминированного pre-gate относительно существующего L1.

Смысловое поручение редактировать существующее изображение не должно теряться исключительно из-за несовпадения слов.

Не путать создание нового изображения с редактированием существующего.

Не выполнять генерацию вместо редактирования при отсутствии подходящего инструмента.

Проверить разнообразные естественные формулировки, включая случаи с reply на изображение.

## COR-03. Tool Loop: структурированный результат исполнения

В `tool_loop._sync_claim_with_outcome` успешность действия определяется поиском текстовых фрагментов в результате инструмента.

Пересмотреть реализацию.

Успех, ошибка и подтверждённая доставка должны определяться через структурированный контракт результата там, где он существует.

Не допускать ситуации, когда случайное совпадение текста трактуется как успешная операция.

Не удалять уведомления о недоступности функции, если реальный результат не подтверждает успешного исполнения.

Сохранить уже реализованную синхронизацию Capability Registry и Writer.

## COR-04. Vision: проверить заявленные возможности

Сверить работу:

- Статических изображений.
- GIF.
- TGS.
- WebM.
- Превью видео.
- Видеосообщений.
- Недоступных превью.
- Pending/Ready/Failed.
- Медиа, созданных самим ботом.

Не считать обложку полноценным анализом движения.

Не объявлять отсутствие извлечения кадров новым дефектом, если эта функция не входила в утверждённый scope.

Проверить соответствие действительных возможностей отображаемым настройкам админки.

Не переписывать работающий Vision без подтверждённой причины.

## COR-05. Fact-check: контекстная релевантность

Исправление durable-восстановления альбомов сохранено.

Повторно его не реализовывать.

Проверить только риск ошибочного выбора тезиса из широкого контекста.

Если пользователь запускает Fact-check на сообщение без самостоятельного проверяемого утверждения, соседнее обсуждение не должно автоматически становиться целью проверки без установленной связи.

Использовать существующие reply-связи, структуру публикации, авторство и контекстные механизмы.

Не добавлять словарные исключения под отдельные реплики.

## COR-06. L1/Lore: неопределённые планы

Проверить разрешающий fallback в `lore_story_delivery_allowed()`.

При недостаточно определённом намерении пользователя готовая Lore-история не должна автоматически подменять аналитический ответ только потому, что явный запрет не сформирован.

Сохранить возможность полноценных художественных воспоминаний, когда запрос действительно предполагает такой жанр.

Не навязывать универсальную композицию ответа.

# ЧАСТЬ IV. ИНЖЕНЕРНАЯ ДИСЦИПЛИНА

## DEV-01. Не исправлять один скриншот

Все ранее предоставленные примеры - иллюстрации возможных дефектов.

Они не являются нормативными образцами ответа.

Запрещено использовать их для создания:

- Обязательных вводных фраз.
- Обязательных концовок.
- Словесных запретов.
- Исключений по именам.
- Специальных веток для конкретных участников.
- Локальных сценарных шаблонов.
- Системы, которая выдаёт однотипные ответы ради прохождения тестов.

Цель - обобщаемое поведение на неизвестных данных.

## DEV-02. Не подменять архитектурное исправление промптом

Если проблема заключается в неправильном SQL-поиске, исправлять SQL-поиск.

Если проблема заключается в потере provenance, исправлять передачу provenance.

Если проблема заключается в неправильном определении эпизода, исправлять механизм извлечения и реконструкции.

Если проблема заключается в Decision, исправлять существующий Decision.

Если проблема заключается в стиле, корректировать соответствующие речевые инструкции.

**Нельзя пытаться вылечить все перечисленные проблемы одним системным промптом.**

При этом не вводить новые подсистемы там, где достаточно расширения существующих.

## DEV-03. Не создавать искусственную сложность

Предпочитать:

- Повторное использование существующих данных.
- Общие функции.
- Один источник истины.
- Действующие инструменты памяти.
- Уже существующие runtime-маршруты.
- Минимальные необходимые изменения интерфейсов.

Не добавлять новые агенты, слои, маршрутизаторы и LLM-вызовы исключительно ради организации работы.

Участие Architect в оценке затронутых контрактов обязательно.

Builder отвечает за изменение кода.

Reviewer проверяет поведение и регрессии, а не только наличие строк в требованиях.

## DEV-04. Не менять другие действующие задачи

Эта корректировка заменяет предыдущее поручение POST-RELEASE AUDIT CORRECTIVE в части перечисленных дефектов.

Не дублировать одинаковые требования в очереди.

Уже реализованное и подтверждённое не переделывать.

Существующие незавершённые поручения сохраняют свои статусы и порядок.

Не очищать `current_task.md`.

Не выполнять reset или удаление пользовательских изменений рабочего дерева.

При пересечении изменений разных агентов выполнять осмысленное объединение.

Не выбирать одну версию файла вместо другой автоматически.

## DEV-05. Проверка изменений

Применить обычные инженерные проверки:

1. Зафиксировать исходное состояние и воспроизводимые дефекты.
2. Провести архитектурную оценку затронутых путей.
3. Реализовать исправления.
4. Написать или адаптировать регрессионные тесты.
5. Проверить отрицательные и пограничные сценарии.
6. Проверить интеграцию с действующими модулями.
7. Получить независимое ревью.
8. Выполнить штатный деплой.
9. Проверить работающую версию и техническое состояние production.

Не вводить дополнительные циклы ревью без новых содержательных замечаний.

Не блокировать деплой требованием доказать субъективное качество всех возможных LLM-ответов.

При этом не выдавать тесты с моками за полноценное подтверждение реального поведения модели.

Формально завершённая карта требований не заменяет исправления обнаруженного дефекта.

# ЧАСТЬ V. УСЛОВИЯ ЗАВЕРШЕНИЯ

Задача считается инженерно завершённой только при выполнении следующих условий.

### Архитектура Ностальгии

- Удалён семантический хардкод по фразам отказа.
- Не введён эквивалентный хардкод в другой части runtime.
- Поиск работает с несколькими историческими годами.
- Глубина определяется доступным архивом.
- Поддерживаются день, неделя, месяц и фактически связанное продолжение события.
- Поиск не привязан к совпадению часа.
- Основной материал отбора - содержательный эпизод, а не случайное сообщение.
- Предусмотрен тематический поиск вне календарной годовщины.
- Кандидаты проходят оценку содержательной пригодности.
- При отсутствии интересного материала допускается молчание.
- Несвязанные события не склеиваются.
- Источники и участники не смешиваются.
- Повторные публикации одного эпизода контролируются.
- Действующие Personality Core, Initiative и Memory сохранены.

### Остальные исправления

- Image Edit использует согласованные effective-настройки.
- Исходные изображения корректно передаются редактору.
- Семантический pre-gate не блокирует понятные поручения из-за неполного словаря.
- Успех медиаинструмента определяется корректным контрактом исполнения.
- Возможности Vision соответствуют действительным функциям.
- Fact-check не подменяет цель случайным соседним сообщением.
- Неопределённый L1-план не приводит к необоснованной подмене анализа Lore-рассказом.

### Приёмочные доказательства

Для каждого изменённого функционального пути должны существовать:

- Ссылка на конкретный код.
- Проверка исходной причины.
- Регрессионные сценарии.
- Негативные и пограничные проверки.
- Подтверждение совместимости.
- Статус независимого Reviewer.

Статус `DONE` не выставлять только на основании изменения текста промпта.

### Финальный отчёт

Вместо длинного перечня внутренних требований дать владельцу понятный отчёт:

**Что было неправильно:** реальные причины дефектов.

**Что изменено:** изменения механизма, а не только текста инструкций.

**Как теперь работает Ностальгия:** простой пример схемы поиска и выбора эпизода без превращения конкретного примера в эталон ответа.

**Что переиспользовано:** существующие средства памяти, Decision и Initiative.

**Какие дефекты устранены:** подтверждённые результаты.

**Что осталось непроверенным:** реальные ограничения инженерной проверки.

**Production:** фактическая версия, commit, состояние сервиса и результат деплоя.

## Итоговая директива

**Ностальгия должна перестать быть механизмом извлечения случайной старой реплики по календарному совпадению.**

Она должна стать механизмом естественного обращения к многолетней истории сообщества.

Для этого необходимо исследовать доступные исторические периоды, находить содержательные эпизоды, восстанавливать их фактический контекст, оценивать уместность воспоминания и только после этого формировать реплику через существующую систему речи и инициативы.

Важны не количество просмотренных лет, не число собранных сообщений и не красивость формулировки сами по себе.

Важен результат: бот может вспомнить что-то действительно характерное, смешное, неожиданное или содержательно связанное с разговором, не выдумывая историю из случайных фрагментов.

**Никаких семантических regex-костылей, сценарных исключений по именам, искусственных шаблонов хорошего ответа и имитации понимания через списки фраз.**

Выполнить эту корректировку в конце существующей очереди, сохранив все остальные незавершённые задачи. Не останавливать workflow после аудита или частичного исправления.

Довести изменения до инженерной приёмки, штатного деплоя и проверки фактического результата.
